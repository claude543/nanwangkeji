# 0. 先给出一句话结论

**V3.2 解决“板子现在有没有资格向 RT-LAB 提供外部命令”；V4 在这个已经验收通过的安全框架里面，第一次真正让板子运行基础 AGC，但暂时不让板端六路命令控制设备。**

所以 V4 的核心不是再造一套 Modbus，也不是直接进入板端闭环，而是完成三件事：

```text
第一件：
真实 RT-LAB 数据
→ 板子
→ C 版 AGC 真正计算

第二件：
C 版 AGC 的历史状态
只能在命令真正成功发布以后推进

第三件：
板端计算结果通过真实 Modbus 写回 RT-LAB
但暂不接管六台设备
```

因此 V4 的准确定位是：

> **在 V3.2 安全通信基础上，对板端 C 版基础 AGC、状态提交机制、真实输入数据、真实 Modbus 读写和日志进行影子运行验收。**

# 1. 先把 V3.1、V3.2、V4、V5 放到同一条路线里

## 1.1 V3.1 解决什么

V3.1 主要解决“数据能不能正确传”。

它验证：

```text
寄存器地址
INT16 / UINT16
缩放
正负数补码
工程量 ↔ raw
FC03读取
FC16写入
```

所以 V3.1 回答：

> **我发的这个数，到对面以后还是不是同一个数？**

---

## 1.2 V3.2 解决什么

V3.2 不接正式 AGC，主要解决：

```text
数据现在是不是还新鲜
RT-LAB是不是还在运行
板子是不是还活着
测量是不是可信
当前是否允许外部控制
通信异常时能不能迅速撤销资格
恢复后会不会直接误投入
```

因此 V3.2 建立：

```text
DISCONNECTED
WAIT_VALID
ENABLED
```

以及：

```text
40115 MODEL_STATUS
40116 RTLAB_HEARTBEAT

40010 EXT_AGC_ENABLE
40011 CMD_SEQ
40012 BOARD_HEARTBEAT
```

所以 V3.2 回答：

> **数据虽然能传，但现在这批外部数据有没有资格被信任？**

---

## 1.3 V4 新增什么

V4 在 V3.2 已经通过的前提下增加：

```text
C版基础AGC
```

但不是简单加一个函数就结束。

V4 还专门增加了：

```text
同一批测量快照
AGC调度条件
候选状态
成功提交
UPDATED / HELD / ERROR
新的CMD_SEQ语义
首次有效AGC结果门槛
PCC方向适配
逐周期CSV
```

所以 V4 回答：

> **板子不仅“有资格通信”，而且能不能基于真实 RT-LAB 数据正确运行 AGC，并且只在命令真正发布成功时推进自己的控制历史？**

---

## 1.4 V5 才解决什么

V4 中：

```text
板端40001～40006
× 不接六台设备Pref
```

V5 才会：

```text
板端40001～40006
→ RT-LAB安全门控
→ 六台设备Pref
→ 六台设备真实响应
→ PCC变化
→ 401xx反馈板端
```

所以 V5 才回答：

> **板端 AGC 能不能真正接管六台设备并形成硬件在环闭环？**

# 3. 为什么必须做 V4-shadow，而不是 V3.2 后直接进入 V5

如果直接从 V3.2 跳到 V5，那么下面这些变化会一次发生：

```text
测试值 → 真实测量
无板端AGC → C版AGC
影子结果 → 真实设备命令
本地MATLAB控制 → 板端控制
通信安全验证 → 真实功率闭环
```

如果 PCC 出问题，就很难马上判断原因到底是：

```text
C算法错误？
PCC符号错？
寄存器缩放错？
FC16写错？
状态机错？
AGC历史状态错？
六路命令顺序错？
设备真实响应问题？
```

V4 把问题拆开。

V4 中设备仍由已经跑通的本地 MATLAB AGC 控制，因此电气系统有一个已知参考。

板端同时运行 C AGC：

```text
同样读取PCC、PVmax、SOC
→ 自己算六路命令
→ 写回RT-LAB
→ 但不让设备执行
```

于是可以先比较：

```text
本地MATLAB AGC结果
vs
板端C版AGC结果
```

如果两者一致，再进入 V5。

因此 V4 的作用是：

> **在不承担设备控制风险的情况下，把板端算法、通信、状态机、时间调度和状态提交全部先跑真。**

# 4. V4 为什么必须完整保留 V3.2，而不能重新写一套安全逻辑

V4 需求明确要求：

```text
直接在已验收V3.2程序中集成AGC
```

而不是：

```text
V4重新写通信
V4重新写状态机
V4自己判断心跳
```

必须完整保留：

1. `DISCONNECTED / WAIT_VALID / ENABLED`
2. FC03 / FC16
3. MODEL_STATUS
4. RT-LAB 心跳
5. BOARD_HEARTBEAT
6. 核心测量范围检查
7. 连续 3 个有效周期
8. 任一异常立即撤销 40010
9. CMD_SEQ
10. 自动重连和安全恢复
11. V3.2 原有编码、补码、舍入、限值

为什么？

因为 V3.2 已经验证的是：

```text
通信安全层
```

V4 要验证的是：

```text
在这个安全层里面加入AGC以后
算法是否还能正确工作
```

如果 V4 连安全层都重写，那么出了问题就不能判断：

```text
是新增AGC错
还是重写的V3.2错
```

所以 V4 的设计原则是：

> **安全层不动，只往里面增加算法层。**

# 6. 40101～40116 在 V4 中被分成四种不同角色

V4 不是“16个点全部送AGC”。

这是最容易混淆的地方。

---

## 6.1 第一类：基础 AGC 真正使用的 5 个动态测量

```text
40101 PCC_P
40105 PV1_P_MAX
40106 PV2_P_MAX
40107 ESS1_SOC
40108 ESS2_SOC
```

它们直接进入 C 版基础 AGC。

作用分别是：

| 点 | AGC为什么需要 |
|---|---|
| PCC_P | 计算当前联络线功率偏差 |
| PV1_P_MAX | 限制PV1还能增加多少 |
| PV2_P_MAX | 限制PV2还能增加多少 |
| ESS1_SOC | 判断ESS1是否允许继续充/放电 |
| ESS2_SOC | 判断ESS2是否允许继续充/放电 |

---

## 6.2 第二类：继续读取和记录，但当前 AGC 不使用

```text
40102 PCC_Q
40103 PCC_V
40104 PCC_F

40109 PV1_P_MEAS
40110 PV2_P_MEAS
40111 ESS1_P_MEAS
40112 ESS2_P_MEAS
40113 EV1_P_MEAS
40114 EV2_P_MEAS
```

其中 40109～40114 特别重要。

它们必须：

```text
读取
解码
打印
记录CSV
```

但当前基础 AGC **故意不能使用**。

为什么故意不用？

因为当前 V4 要复现基础 AGC：

```text
PCC总量反馈
+
内部历史命令
```

后续论文才准备研究：

```text
加入六路实测功率
→ 重建设备真实执行状态
```

所以如果 V4 提前使用 40109～40114，就把以后要比较的“基础算法”和“改进算法”混在一起了。

---

## 6.3 第三类：安全状态机使用，不属于 AGC 算法输入

```text
40115 MODEL_STATUS
40116 RTLAB_HEARTBEAT
```

它们决定：

```text
这批数据有没有资格被AGC使用
```

而不是：

```text
AGC应该输出多少功率
```

这两个层次必须分开。

---

## 6.4 第四类：不来自寄存器，而来自板端 JSON / 调度

AGC 还需要：

```text
time_s
enable

P_target
p_unit
p_dead
soc_min
soc_max
ts_agc
pv_init
ev_init
```

其中：

```text
time_s
```

来自板端单调时钟。

而：

```text
P_target等
```

来自 JSON。

# 7. 为什么必须强调“同一次 FC03 的同一批数据”

V4 明确要求：

> 一次 AGC 计算使用的 PCC、PVmax、SOC 必须来自同一次成功 FC03。

假设错误实现成：

```text
PCC      = 第100周期
PV1_MAX  = 第99周期
PV2_MAX  = 第100周期
SOC1     = 第98周期
SOC2     = 第100周期
```

虽然每个数单独看都可能是合理的，但组合起来并不代表系统在任何一个真实时刻的状态。

所以正确做法是：

```text
一次FC03
↓
16个寄存器全部成功返回
↓
统一解码
↓
形成一个完整snapshot
↓
这一份snapshot整体交给AGC
```

可以把 snapshot 理解为：

> **同一通信周期拍下的一张完整系统状态照片。**

V4 不允许拿几张不同时间的照片拼成一个控制输入。

---

# 8. 为什么 V4 要专门增加“新的完整测量快照”条件

AGC 不能因为主循环跑了一次就一定更新。

必须确认：

```text
本周期确实取得一批新的完整FC03数据
```

才能推进 AGC。

否则可能发生：

```text
FC03失败
但程序还留着上次PCC
↓
主循环继续调用AGC
↓
AGC把同一个旧PCC再次当成新测量
↓
历史命令又推进了一次
```

这正是要避免的“旧数据重复驱动新控制”。

所以：

```text
无新数据
→ 不推进AGC
```

---

# 9. PCC 符号为什么在 V4 中必须专门加 pcc_sign_gain

这里存在两套已经冻结的方向约定。

## 9.1 Modbus 点表 40101

现有点表保持：

```text
购电 = 正
送电 = 负
```

例如：

```text
微电网从大电网购120 kW
40101解码 = +120 kW
```

---

## 9.2 C 版基础 AGC

C AGC 沿用本地 MATLAB AGC 的内部定义：

```text
送电 / 发电 = 正
购电 / 充电 = 负
```

同一个物理状态在 C AGC 中应该是：

```text
-120 kW
```

---

## 9.3 所以中间必须转换

V4 规定：

```text
P_pcc_for_agc
=
pcc_sign_gain × PCC_P_decoded_kw
```

当前：

```text
pcc_sign_gain = -1
```

于是：

```text
40101解码：
+120 kW   （点表：购电为正）

× (-1)

C AGC输入：
-120 kW   （算法：购电为负）
```

---

## 9.4 为什么不直接把 -1 写死在 AGC 代码里

因为：

```text
协议方向
```

和：

```text
算法内部方向
```

应该是两个独立层次。

如果以后更换点表或接口，使 PCC 本身已经采用正送负购，那么 JSON 可以改为：

```json
"pcc_sign_gain": 1.0
```

而不需要修改 AGC 算法核心。

因此 `pcc_sign_gain` 是：

> **协议层与算法层之间的方向适配参数。**

---

## 9.5 P_target 为什么也必须和转换后的 PCC 同方向

AGC 计算：

```text
dP = P_target - P_pcc_for_agc
```

如果：

```text
P_target采用正送负购
PCC却还采用正购负送
```

那么两个数根本不在同一个坐标系中。

例如真实购电 120 kW，目标购电 100 kW：

正确算法内部应为：

```text
PCC    = -120
target = -100

dP = -100 - (-120)
   = +20 kW
```

表示需要让微网净出力增加 20 kW。

所以 V4 要求：

> `p_target_kw` 与 `P_pcc_for_agc` 必须使用同一方向定义。

# 10. V4 JSON 每一个新增参数到底管什么

V4 基线：

```json
{
  "algorithm_mode": "agc_shadow",
  "test_mode": false,
  "external_enable_request": true,
  "agc_enable": true,

  "p_target_kw": -100.0,
  "pcc_sign_gain": -1.0,

  "p_unit_kw": 100.0,
  "p_dead_kw": 2.0,

  "soc_min": 0.2,
  "soc_max": 0.9,

  "ts_agc_s": 1.0,

  "pv_init_kw": 0.0,
  "ev_init_kw": 60.0,

  "agc_reset_on_reconnect": false,
  "agc_csv_enable": true
}
```

逐项理解：

| 参数 | 作用 | 不是什么 |
|---|---|---|
| algorithm_mode | 标识当前是V4影子AGC | 不决定通信是否连接 |
| test_mode=false | 关闭V3.2固定测试输出 | 不等于关闭AGC |
| external_enable_request | V3.2是否允许进入ENABLED | 不等于AGC计算使能 |
| agc_enable | 是否允许调用C AGC | 不等于40010 |
| p_target_kw | AGC目标PCC功率 | 不是测量值 |
| pcc_sign_gain | 点表方向→算法方向 | 不是控制增益 |
| p_unit_kw | 1 pu对应多少kW | 不是PCC基准 |
| p_dead_kw | AGC死区 | 不是通信范围检查 |
| soc_min/max | AGC充放电边界 | 不是V3.2测量有效范围 |
| ts_agc_s | AGC最小更新周期 | 不是RT-LAB基本步长 |
| pv_init_kw | AGC内部PV初值 | 不是PVmax |
| ev_init_kw | AGC内部EV初始充电幅值 | 对外输出仍为负pu |
| agc_reset_on_reconnect | 普通重连是否重置AGC | 当前要求false |
| agc_csv_enable | 是否记录AGC CSV | CSV失败不能影响控制 |

---

# 11. external_enable_request 和 agc_enable 为什么必须分成两个开关

它们看起来都像“enable”，但作用完全不同。

## external_enable_request

属于 V3.2。

它回答：

> **是否申请让外部控制链取得安全资格？**

如果为 false：

```text
WAIT_VALID
无法进入ENABLED
```

---

## agc_enable

属于 V4 的算法层。

它回答：

> **即使通信和数据都安全，现在要不要真正运行C版AGC？**

所以可能出现：

```text
V3.2 = ENABLED
但 agc_enable = false
```

这时：

```text
通信安全条件正常
但AGC不计算
40010也不能成为V4有效AGC结果
```

因此：

```text
安全资格
≠
算法运行使能
```

---

# 12. 为什么板端 time_s 必须使用单调时钟

需求明确：

```text
time_s 使用板端单调时钟
不使用系统日期时间
```

因为 AGC 关心的是：

```text
距离上次更新过去了多久
```

而不是：

```text
现在是几点几分几秒
```

系统日期时间可能被：

```text
NTP校时
人工修改
时区修改
```

而发生跳变。

单调时钟只会沿着程序运行时间向前增加，更适合控制器计算：

```text
dt
```

---

# 13. V4 的 AGC 到底什么时候允许执行

必须同时满足：

```text
1. agc_enable = true
2. V3.2状态 = ENABLED
3. 本周期FC03成功
4. 核心测量有效
5. 本周期有新的完整snapshot
6. 达到AGC调度条件
```

缺一不可。

---

## 为什么 WAIT_VALID 不能算

WAIT_VALID 的含义是：

```text
TCP虽然连上
但系统还没有连续证明自己可靠
```

所以不能推进 AGC 历史。

---

## 为什么 FC03 失败不能算

因为没有新数据。

---

## 为什么核心测量越界不能算

因为 AGC 可能基于错误的：

```text
PCC
PVmax
SOC
```

产生错误命令。

---

## 为什么恢复后不补算历史周期

假设通信断了 5 秒。

错误做法：

```text
恢复以后
为了“补回”5秒
连续调用AGC五次
```

这会瞬间把 5 个控制周期压缩到同一个实际时刻，重新制造命令积累。

正确做法：

```text
恢复
→ 得到第一份新数据
→ 最多执行一次AGC
→ 后面继续按正常节奏
```

# 14. 通信周期 1 s 和 AGC 周期 1 s 是什么关系

当前：

```text
Modbus通信周期 ≈ 1 s
AGC ts_agc_s = 1 s
```

所以理想情况下：

```text
每获得一批新的有效FC03
≈
有机会执行一次AGC
```

但必须注意：

> “每个通信周期”不等于“每个周期必定 UPDATED”。

因为 C 模块仍可能返回：

```text
HELD
ERROR
```

主程序也可能因为安全条件不满足而根本不调用 AGC。

---

# 15. V4 主循环的 12 步为什么必须严格按这个顺序

V4 规定每个通信周期：

```text
1 FC03读取
2 全部解码
3 V3.2检查
4 更新状态机
5 固定snapshot
6 candidate_state上调用AGC
7 检查AGC输出
8 编码40001～40009
9 生成40010～40012
10 FC16一次写12路
11 根据FC16结果决定commit
12 写CSV
```

下面逐项解释。

---

## 第1步：FC03读取

目的：

```text
取得同一批40101～40116
```

---

## 第2步：全部解码

不能一边读一边算。

要先完成：

```text
raw
→ INT16 / UINT16
→ scale
→ 工程量
```

---

## 第3步：V3.2检查

先判断：

```text
这批数据能不能信
```

再考虑：

```text
AGC怎么算
```

安全判断必须先于控制算法。

---

## 第4步：更新状态机

确认当前是：

```text
DISCONNECTED
WAIT_VALID
ENABLED
```

AGC只允许在ENABLED继续。

---

## 第5步：固定snapshot

从这一刻开始：

```text
本次AGC使用的数据不再变化
```

保证 PCC、PVmax、SOC 是同一批。

---

## 第6步：candidate_state上算AGC

注意不是：

```text
直接修改正式agc_state
```

而是：

```text
candidate_state = agc_state
→ 在candidate上计算
```

这是 V4 最核心的新设计之一。

---

## 第7步：检查输出

必须检查：

```text
finite
范围
status合法
remain非负
```

避免 NaN/Inf 或非法命令进入寄存器。

---

## 第8步：编码40001～40009

将 C AGC 工程量输出变成：

```text
Modbus raw
```

继续沿用 V3.2 已验证的：

```text
缩放
舍入
INT16/UINT16
限幅
补码
```

---

## 第9步：生成40010～40012

安全管理量不能由 AGC 核心自己随意生成。

仍由 V3.2 / V4 主程序统一管理。

---

## 第10步：FC16一次写12路

把：

```text
40001～40009
+
40010～40012
```

作为一批发送。

---

## 第11步：根据FC16决定commit

这是“现实世界是否真正收到命令”的确认点。

只有 FC16 成功：

```text
新的AGC历史
才允许成为正式历史
```

---

## 第12步：最后写CSV

因为只有到这里才知道：

```text
FC16到底成功没有
candidate_cmd_seq有没有真正提交
committed_cmd_seq是多少
```

如果提前写CSV，就会记录一个尚未发生的“未来结果”。

---

# 16. V4 最核心的概念：正式状态、候选状态、已提交结果

V4 中必须同时分清三个东西。

## 16.1 正式 AgcState

表示：

> **截至当前，已经被系统认可的 AGC 历史状态。**

可以理解为：

```text
最后一次真正成功发布以后
控制器确认有效的历史
```

---

## 16.2 candidate_state

表示：

> **本周期刚计算出来，但还没有被现实通信确认的新状态。**

它只是候选。

---

## 16.3 committed_regs / committed_cmd_seq

表示：

> **最后一次已经成功通过FC16发布出去的寄存器和命令序号。**

---

## 三者关系

```text
正式AgcState
   │
   ├──复制──→ candidate_state
   │             ↓
   │          AGC计算
   │             ↓
   │        candidate_outputs
   │             ↓
   │          编码寄存器
   │             ↓
   │           FC16
   │          /    \
   │       成功     失败
   │        ↓        ↓
   │      commit    丢弃candidate
   │        ↓
新的正式AgcState
新的committed_regs
新的committed_cmd_seq
```

---

# 17. 为什么不能直接在正式 AgcState 上运行 AGC

这是 V4 最重要的设计理由。

假设控制器当前正式状态认为：

```text
PV1 = 20 kW
PV2 = 20 kW
```

这一轮 AGC 算出：

```text
PV1 = 30 kW
PV2 = 30 kW
```

如果程序先直接把正式状态改成 30/30，再执行 FC16：

```text
正式状态先前进
↓
FC16失败
↓
RT-LAB实际上没有收到30/30
```

此时：

```text
板子认为设备已经来到30/30
现实仍然是20/20
```

下一轮板子会在错误历史基础上继续算。

这就是：

```text
控制器内部状态
≠
真实成功发布状态
```

V4 的 candidate_state 设计就是为了阻止这种失配。

---

# 18. candidate_state 为什么和论文前期发现的问题直接相关

离线通信试验已经发现：

```text
下行失败
→ AGC内部命令仍继续前进
→ 设备实际命令停留
→ 恢复时累计命令突然跳变
```

V4 的候选提交规则针对的是其中最直接的一层：

```text
如果命令没有成功发布
→ 正式控制器历史就不能假设它已经发生
```

因此 V4 的状态提交不是普通编程细节。

它是在工程程序中明确区分：

```text
算出来了
和
真正成功发布了
```

这两个状态。

---

# 19. UPDATED、HELD、ERROR 分别是什么意思

C 模块返回：

```text
AGC_STEP_UPDATED
AGC_STEP_HELD
AGC_STEP_ERROR
```

必须严格区分。

---

## 19.1 UPDATED

表示：

```text
这次真正产生了一次新的AGC历史状态
```

处理：

```text
candidate_cmd_seq = committed_cmd_seq + 1
↓
检查输出
↓
编码
↓
FC16
↓
成功才commit
```

所以 UPDATED 只是：

> **产生了新候选结果。**

它本身还不代表成功提交。

---

## 19.2 HELD

表示：

```text
本周期没有推进AGC历史状态
```

这不是错误。

可以继续发送：

```text
最近一次成功提交的40001～40009
```

但是：

```text
CMD_SEQ不变
AgcState不前进
```

HELD 的含义是：

> **继续保持上一份已经确认有效的控制结果。**

---

## 19.3 ERROR

表示：

```text
算法输入/参数/计算异常
```

处理：

```text
不提交candidate_state
不增加CMD_SEQ
40010 = 0
记录错误
```

---

# 20. 为什么 HELD 不是通信失败

HELD 是：

```text
算法层
```

的结果。

FC16成功/失败是：

```text
通信层
```

的结果。

两者完全不同。

可能发生：

```text
AGC = HELD
FC16 = SUCCESS
```

含义是：

```text
本周期没有新的算法更新
但板子成功重复发送了最后一份已提交命令
```

也可能发生：

```text
AGC = HELD
FC16 = FAIL
```

此时仍然：

```text
AGC历史不变
CMD_SEQ不变
```

---

# 21. V4 的 CMD_SEQ 和 V3.2 相比，语义发生了什么变化

这是必须特别记住的一点。

## V3.2 中

CMD_SEQ 更接近：

```text
成功发布的FC16批次数
```

即使测试值没有变化，只要成功写了一批新数据，序号也增加。

---

## V4 中

需求明确重新规定：

```text
只有
UPDATED
+
输出有效
+
编码成功
+
FC16成功

CMD_SEQ才增加
```

HELD 即使 FC16 成功重复发送旧命令：

```text
CMD_SEQ也不增加
```

因此 V4 的 CMD_SEQ 更准确表示：

> **成功提交了第几次新的 AGC 控制状态。**

而不再简单等于：

> 每成功通信了多少轮。

所以以后看到：

```text
BOARD_HEARTBEAT一直增加
CMD_SEQ一段时间不变
```

不一定是异常。

它可能表示：

```text
板子程序正常运行
FC16也在运行
但AGC这段时间一直HELD
```

---

# 22. BOARD_HEARTBEAT 与 CMD_SEQ 在 V4 中为什么更容易区分

## BOARD_HEARTBEAT

证明：

```text
板子主程序还活着
```

只要通信循环运行，应持续变化。

---

## CMD_SEQ

证明：

```text
有新的AGC状态成功提交
```

只有真正的新控制结果被成功发布，才变化。

因此：

```text
BOARD_HEARTBEAT：程序生命
CMD_SEQ：新控制状态提交进度
```

两者不应同步要求。

# 23. FC16 重试为什么必须重复同一候选报文

假设：

```text
candidate_cmd_seq = 25
candidate命令 = 某一组40001～40009
```

第一次 FC16 失败。

错误做法：

```text
重新调用AGC
→ 得到另一组命令
→ CMD_SEQ变26
→ 再发
```

这会把一次通信失败变成额外一次控制推进。

正确做法：

```text
同一个candidate_state
同一组candidate_regs
同一个candidate_cmd_seq=25
↓
直接重试发送
```

如果最终成功：

```text
commit 25
```

如果最终失败：

```text
candidate丢弃
正式状态保持24
```

# 24. 为什么普通 Modbus 重连不能 reset AGC

V4 默认：

```json
"agc_reset_on_reconnect": false
```

通信暂时断开时：

```text
暂停AGC
不推进历史状态
保留最后成功状态
40010=0
```

恢复后：

```text
重新完成V3.2连续3周期验证
↓
从保留状态继续
```

为什么不 reset？

因为普通网络瞬断并不代表：

```text
设备物理系统重新初始化
```

如果每次断网都把 AGC 重置到：

```text
PV=0
ESS=0
EV=-0.6
```

而设备实际可能还在执行断线前的其他功率，就会人为制造新的状态跳变。

所以 V4 当前选择：

> **短时通信故障只暂停控制历史，不把历史抹掉。**

# 25. 什么时候才重新初始化 AGC

当前需求规定：

```text
板端程序重新启动
```

才重新初始化。

启动时先：

```text
agc_controller_reset(&agc_state)
```

第一批 FC03 成功且核心测量有效后，再：

```text
agc_controller_init()
```

初始化：

```text
PV内部初值 = pv_init_kw
ESS内部初值 = 0
EV内部正充电幅值 = ev_init_kw
AGC_STATUS = 0
dP = 0
remain = 0
```

---

# 26. 为什么 EV 的内部初值是正 60 kW，但输出是 -0.60 pu

当前算法内部保存：

```text
EV充电幅值
```

例如：

```text
ev_init_kw = 60
```

表示充电功率大小为 60 kW。

但设备功率接口采用：

```text
EV负值 = 充电
```

所以对外：

```text
-60 / 100
=
-0.60 pu
```

不能把：

```text
ev_init_kw = 60
```

误认为设备最终输出是 `+0.60 pu`。

# 28. V4 中 40010 的含义为什么比 V3.2 更严格

V3.2 中，40010 主要表示：

```text
板子认为通信和数据条件满足
```

V4 中增加了真正的 AGC 以后，仅仅“通信条件满足”已经不够。

V4 要求 40010=1 至少满足：

```text
当前无状态异常
当前无测量异常
当前无算法异常
当前无编码异常
```

所以 V4 中 40010 更准确表示：

> **板端当前存在一份安全、有效、并且已经真正成功发布过的 AGC 控制结果。**

# 29. 为什么程序刚启动时，即使已经 ENABLED，40010 也不能马上为 1

假设：

```text

→ ENABLED
```

但板端还没有任何一份 AGC 输出真正通过 FC16 成功发布。

此时如果直接：


相当于声明：

```text
现在已经有一份可使用的板端AGC命令
```

因此 V4 增加：

```text
has_committed_agc_result
```

概念。

在第一份：

```text

→ 输出有效
→ 编码成功
→ FC16成功
```

之前：

```text
40010必须保持0
```

# 31. 用当前 -100 kW 目标通俗理解第一次 AGC 动作

假设 Modbus 点表读到：

```text
PCC_P_decoded = +120 kW
```

点表含义：

```text
当前购电120 kW
```

经过：

```text
pcc_sign_gain = -1
```

得到 C AGC 输入：

```text
P_pcc_for_agc = -120 kW
```

目标：

```text
P_target = -100 kW
```

于是：

```text
dP = -100 - (-120)
   = +20 kW
```

`dP>0`。

资源顺序：

```text
PV增加
→ ESS放电
→ EV减少充电
```

所以算法首先尝试提高微网净出力，使 PCC 从：

```text
-120
```

向：

```text
-100
```

移动。

这一方向与当前本地 MATLAB AGC 已经跑通的逻辑一致。

# 33. FC16 失败完整故事

# 36. TCP 断线与恢复完整故事

断线时：

```text

committed结果保留
```

因为网络已经断掉，40010=0 可能无法真正写到 RT-LAB。

这时仍依靠 V3.2 的：

```text
BOARD_HEARTBEAT停止
```

恢复以后：

```text

→ WAIT_VALID
→ 连续3周期
→ ENABLED
```

然后从原 AgcState 继续。

# 37. 为什么 40109～40114 在 V4 的 CSV 中必须出现

# 39. 为什么 CSV 必须在 FC16 处理完以后再写

假设本周期：

```text
candidate_cmd_seq = 20
```

如果在 FC16 前写 CSV：

```text
CSV可能先写“20”
```

随后：

```text
FC16失败
```

最终真实 committed 仍然是 19。

那 CSV 就不能准确描述真实程序状态。

所以正确顺序：

```text
FC16
↓
知道成功/失败
↓
知道最终committed_cmd_seq
↓
再写CSV
```

# 40. 为什么 CSV 写失败不能影响控制

CSV 是：

```text
记录功能
```

不是：

```text
控制必要条件
```

可能出现：

```text
磁盘问题
目录问题
文件打开失败
```

这不能导致：

```text
Modbus停止
AGC停止
状态机停止
```

因此：

```text
agc_csv_enable=false
```

时程序仍必须完整工作。

# 52. 为什么 candidate commit 更适合作为工程基础，而不一定单独构成论文创新

candidate commit 是一个非常必要的设计。

它直接修复：

```text
FC16失败

```

不过它本身主要属于：

```text

通信提交安全
```

后续论文更有研究价值的问题仍可能是：

```text

```

所以 V4 可以看成：

> **先把最基础的“发布一致性”做好，再为后续“执行状态一致性”研究提供干净平台。**

# 53. 一轮 V4 通信周期，用一句一句的话彻底串起来

假设现在程序已经连接并进入 ENABLED。

1. 板子向 RT-LAB 发 FC03。
2. 一次拿到 40101～40116。
3. 按每个点的数据类型和 scale 解码。
4. 检查 MODEL_STATUS。
5. 检查 RTLAB_HEARTBEAT。
6. 检查五个核心动态测量是否越界。
7. 确认这是一批新的完整 snapshot。
8. 把 40101 乘 `pcc_sign_gain`，转换成 C AGC 的方向。
9. 把 snapshot 和 JSON 参数组成 `AgcInputs`。
10. 复制正式 `agc_state` 得到 `candidate_state`。
11. 在 candidate 上调用 `agc_controller_step()`。
12. 如果 ERROR，40010=0，不提交。
13. 如果 HELD，不推进状态，不增加 CMD_SEQ。
14. 如果 UPDATED，生成 candidate CMD_SEQ。
15. 检查六路输出、status、dP、remain。
16. 编码成 40001～40009。
17. 生成 40010、40011、40012。
18. 一次 FC16 写 40001～40012。
19. 如果 FC16 成功且本轮是 UPDATED，正式提交 candidate。
20. 如果 FC16 失败，candidate 不成为正式历史。
21. 最后把本周期全过程写入 CSV。
22. 进入下一个 1 s 通信周期。

这就是 V4 的完整一轮。
