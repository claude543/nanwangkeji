# V4-shadow 模型侧改动完整原理与串联理解

> 项目：暑期南网科技项目  
> 当前阶段：V4.0-shadow 联调前模型侧准备  
> 适用模型状态：在 V3.2 安全通信基线 + 六逆变器完整实时模型 + 本地 MATLAB AGC + 15 策略 + 83 维 Target 日志基础上完成 V4 模型侧改造后的版本  
> 本文只解释 **Simulink / RT-LAB 模型内部改动**。RT-LAB Modbus TCP 点表 Configuration 映射和工程师板端 V4 程序不在本文范围内。

---

# 1. 先用一句话理解：V4 模型侧到底改了什么

V3.2 时，40101～40114 主要还是为了通信验收而设置的**测试量/测试常量**。

V4 要让真实板端 C 版 AGC 开始进行 shadow 计算，因此 RT-LAB 必须真正向板子提供：

- 真实 PCC 有功 P；
- 真实 PCC 无功 Q；
- 真实 PCC 电压 V；
- 真实 PCC 频率 F；
- 两路真实 PV 最大可用功率；
- 两路真实 ESS SOC；
- 六台设备真实有功 Pmeas；
- 原 V3.2 的 MODEL_STATUS；
- 原 V3.2 的 RTLAB_HEARTBEAT。

所以 V4 模型侧最核心的改动就是：

```text
模型内部真实物理量
        ↓
按 V3.2/V4 点表规定换算成“寄存器 raw 计数”
        ↓
变成明确的 INT16 / UINT16 16 位数据
        ↓
送入原来的 40101～40116 出口
        ↓
以后由 RT-LAB Modbus 点表映射
        ↓
板端 FC03 一次读取 40101～40116
```

同时，我们又从这条通信链上分出一条**纯记录支路**：

```text
40101～40116 raw
+
40001～40012 板端写回 raw
+
RT-LAB 内部安全状态
        ↓
V4_COMM_LOG_MUX34
        ↓
第二个 Target OpWriteFile
        ↓
v4_comm_target_data
```

因此，V4 模型侧实际上新增了两件大事：

1. **把 40101～40114 从“测试值”升级为真实模型数据。**
2. **建立一套完整的 V4 通信与安全状态 Target 记录链。**

注意：V4 仍然是 **shadow**。

也就是说：

```text
板端 C AGC 算出的 40001～40006
        ↓
RT-LAB 可以收到、显示、记录、检查
        ↓
但不进入六台设备 Pref
```

六台设备在 V4 阶段仍然由模型内部原 MATLAB AGC 控制。

真正让板端命令接管 Pref 是后续 V5 的事情。

---

# 2. 为什么 V3.2 已经能通信，V4 还必须改模型

V3.2 的主要任务不是让板端真正参与微电网控制，而是验证：

- 40101～40116 能不能正确读；
- 40001～40012 能不能正确写；
- MODEL_STATUS 是否正确；
- RTLAB_HEARTBEAT 是否变化；
- BOARD_HEARTBEAT 是否能被 RT-LAB 判断；
- ENABLE / WAIT_VALID / DISCONNECTED 状态机是否正确；
- 通信异常时能否撤销外部使能；
- 恢复后能否重新进入正常状态。

所以 V3.2 中的 40101～40114 可以使用人为设置的已知测试值。

这样方便判断：

```text
我设置 40105 = 650
板子是不是确实读到了 650？
```

这是“通信通不通”的验收思路。

而 V4 不一样。

V4 板端要运行真实 C AGC：

```text
FC03 读取真实 RT-LAB 测量
        ↓
V3.2 安全判断
        ↓
C 版 AGC shadow 计算
        ↓
FC16 写回 40001～40012
```

此时如果 40101～40114 仍然是 Constant，那么板端即使算法完全正确，也只是在对“假数据”计算。

因此 V4 必须完成：

```text
测试点表
→
真实点表数据源
```

但我们又不能破坏已经验收成功的 V3.2 安全逻辑。

所以采取的是：

```text
40101～40114：换成真实模型量
40115～40116：完全保留 V3.2 原逻辑
40001～40012：完全保留 V3.2 原接收结构
```

这就是整个 V4 模型改造的原则。

# 3. 最终模型可以分成六层理解

建议以后看到模型时，不要把它看成很多 Gain、Round、Mux，而是分成六层。

## 第 1 层：真实物理/控制信号层

这里是真实模型内部的数据：

```text
PCC P/Q/V/F
PVmax1/2
SOC1/2
PV1/2 Pmeas
ESS1/2 Pmeas
EV1/2 Pmeas
```

这些量本来已经在模型里存在。

我们没有重新计算第二套。

---

## 第 2 层：协议数值编码层

这里就是你第一张图中的：

```text
From
→ Gain
→ round
→ RAW_01 ... RAW_14
```

这一层的任务只有一个：

> 把“工程量”转换成“点表规定的 raw 计数值”。

例如：

```text
SOC = 0.6000 pu
        ↓ ×10000
6000
        ↓ round
6000 raw count
```

---

## 第 3 层：寄存器数据类型层

这里就是你第二张图中的：

```text
V4_CAST_40101_INT16
V4_CAST_40102_INT16
V4_CAST_40103_UINT16
...
```

这一层不是再改变物理数值，而是把：

```text
double 类型的整数值
```

转换成：

```text
真正符合点表要求的 int16 / uint16
```

然后送给原 401xx 出口。

---

## 第 4 层：RT-LAB Modbus 点表层

这一层你还没有正式配置。

以后会形成：

```text
模型 Op40101～Op40116
        ↓
RT-LAB I/O Interfaces / Configuration
        ↓
Modbus Holding Register 40101～40116
        ↓
FC03
        ↓
板子
```

这一层是“地址映射”。

前面的 Gain / Round / Data Type Conversion 则是“数据内容和格式”。

两者不是同一件事。

---

## 第 5 层：板端写回 shadow 层

板端以后计算：

```text
40001～40006 六路命令
40007 AGC_STATUS
40008 dP
40009 remain
40010 EXT_AGC_ENABLE
40011 CMD_SEQ
40012 BOARD_HEARTBEAT
```

通过 FC16 写回。

模型原来的 40001～40012 接收链没有被脚本改掉。

---

## 第 6 层：Target 证据记录层

我们新增：

```text
V4_TX_RAW_MUX16
+
现有 40001～40009 raw
+
现有 40010～40012 raw
+
现有 RT-LAB 5维安全状态
        ↓
V4_COMM_LOG_MUX34
        ↓
第二个 OpWriteFile
```

它只负责记录证据，不参与控制。

# 4. 脚本为什么先从“已有验证信号”取数据，而不是重新找一遍

`v4_model_prep_hybrid_v2.m` 的一个重要设计不是“新建测量”，而是：

> 尽量复用当前已经通过正式 Target 记录验证过的信号线。

脚本首先定位原有：

```text
AGC_CORE_MUX23
```

然后从已经冻结的输入位置直接反查信号源：

```text
input 14  PV1_Pmeas
input 15  PV2_Pmeas
input 16  ESS1_Pmeas
input 17  ESS2_Pmeas
input 18  EV1_Pmeas
input 19  EV2_Pmeas

input 20  PV1max
input 21  PV2max
input 22  SOC1
input 23  SOC2
```

为什么这样做非常重要？

因为如果为了 V4 又重新去模型里找：

```text
“哪个信号看起来像 EV1 P？”
```

就可能重新接错。

例如我们以前已经出现过 EV1 误接 ESS1 测量的问题。

现在直接从原 23 维正式日志使用的同一根线分支：

```text
正式日志看到的 EV1 Pmeas
=
板子通过 40113 读到的 EV1 Pmeas
```

这样模型里只有一个“真值源”。

这叫：

> **single source of truth，单一真实来源。**

PCC 四个量则直接从已经验证过的：

```text
J2_PCC_Measurements
```

取：

```text
out1 = Freq
out2 = Ppcc
out3 = Qpcc
out4 = Vab_rms
```

所以脚本没有重新建立任何 PCC 测量模块。

# 5. 为什么要新增 V4_SRC_xxx Goto

脚本在 SM_Master 根层从这些真实信号上**分支**，然后建立：

```text
V4_SRC_PCC_P
V4_SRC_PCC_Q
V4_SRC_PCC_V
V4_SRC_PCC_F
V4_SRC_PV1_P_MAX
...
```

这些块本质是 Goto。

标签例如：

```text
V4SRC_PCC_P_KW
V4SRC_PCC_Q_KVAR
V4SRC_PCC_V_V
V4SRC_PCC_F_HZ
V4SRC_PV1_MAX_KW
V4SRC_SOC1_PU
V4SRC_EV1_PMEAS_PU
```

---

## 5.1 Goto 有什么作用

Goto 的作用不是计算。

它只是：

> 给当前这根信号线起一个全局可引用的名字。

可以理解为：

```text
原真实 PCC_P 信号
       │
       ├────────→ 原 AGC / 原日志 / 原模型
       │
       └────────→ Goto: V4SRC_PCC_P_KW
```

原信号链没有被切断。

---

## 5.2 为什么不用一根很长的线直接拉到 401xx

因为 V4 的编码模块位于原 V3.2 的 RT-LAB→Board 区域，而 PCC、PVmax、SOC、Pmeas 分散在 SM 中。

如果全部使用实体长线：

```text
PCC -----------------------------→ 40101
PVmax ---------------------------→ 40105
SOC -----------------------------→ 40107
六Pmeas -------------------------→ 40109~14
```

模型会变得非常混乱。

Goto / From 可以做到：

```text
真实信号
→ Goto("V4SRC_PCC_P_KW")

另一位置：
From("V4SRC_PCC_P_KW")
→ 使用这个信号
```

---

## 5.3 Goto / From 会不会改变数值、采样时间或增加延时

不会。

它是 Simulink 的信号路由方式。

它：

- 不做乘法；
- 不做滤波；
- 不采样；
- 不保持；
- 不延迟；
- 不通过网络；
- 不跨 RT-LAB 任务通信。

这里所有 V4SRC 标签仍然在 SM 内部。

脚本使用独特的 `V4SRC_` 前缀，也是为了避免和旧模型标签重名。

# 6. 第一张图：V4_40101_40114_RAW_ENCODER 到底是什么

你第一张图就是脚本创建的：

```text
V4_40101_40114_RAW_ENCODER
```

这个 Subsystem 有 14 条完全平行的编码通道。

每一条结构都是：

```text
From
  ↓
Gain
  ↓
Rounding Function(round)
  ↓
Outport RAW_xx
```

这里需要把三个模块分别理解。

---

# 7. From 模块：只负责把真实量“取进来”

例如第一路：

```text
V4SRC_PCC_P_KW
       ↓
From_PCC_P
```

它找到前面对应的：

```text
GotoTag = V4SRC_PCC_P_KW
```

因此这里得到的仍然是模型真实的：

```text
PCC_P，单位 kW
```

它不是 raw，也不是 Modbus 数据。

同理：

```text
V4SRC_SOC1_PU
→ From_ESS1_SOC
```

此时仍然只是：

```text
SOC = 0.6 pu
```

所以 **From 只解决“信号从哪里来”**。

---

# 8. Gain 模块：解决“工程单位怎么变成寄存器计数”

这是第一张图里最关键的模块之一。

Modbus 401xx 中不会直接存：

```text
-119.8861 kW
49.9987 Hz
0.6000 pu
```

Holding Register 本质只有 16 位。

协议必须先规定：

```text
1 count 代表多少物理量
```

例如：

```text
40101 PCC_P
scale = 0.1 kW/count
```

所以：

```text
120 kW
÷ 0.1 kW/count
=
1200 count
```

实际上就是：

```text
×10
```

Gain 就是做这一步。

---

# 9. 为什么 40101 的 Gain 是 -10，而不是 +10

这是 V4 中最关键的符号转换。

当前模型内部的 PCC 方向定义是：

```text
P_model > 0 ：微电网向外送电
P_model < 0 ：微电网从外部购电
```

也就是：

```text
正送，负购
```

但是既有 V3.2 Modbus 协议定义：

```text
40101 > 0 ：购电
40101 < 0 ：送电
```

也就是：

```text
正购，负送
```

两边方向正好相反。

因此必须先乘：

```text
-1
```

同时 40101 的分辨率是：

```text
0.1 kW/count
```

还要再乘：

```text
10
```

合起来就是：

```text
Gain = -10
```

所以：

```text
P_model = -120 kW
```

经过 Gain：

```text
-120 × (-10)
= +1200
```

得到：

```text
40101 raw = +1200
```

板端按协议解码：

```text
+1200 × 0.1
= +120 kW
```

在协议语义中：

```text
+120 kW = 购电 120 kW
```

完全正确。

而 V4 板端 C AGC 配置里还有：

```text
pcc_sign_gain = -1
```

因此 C AGC 内部再变回：

```text
+120 × (-1)
= -120 kW
```

最终 C AGC 内部又与 MATLAB AGC 的：

```text
正送、负购
```

保持一致。

完整串联是：

```text
模型 PCC
-120 kW
（负=购电）
    ↓ ×(-10)
40101 raw
+1200
    ↓ ×0.1
板端协议工程量
+120 kW
（正=购电）
    ↓ pcc_sign_gain=-1
C AGC 内部
-120 kW
（负=购电）
```

# 10. 为什么 40102 Q 的 Gain 是 +10

40102：

```text
PCC_Q
scale = 0.1 kvar/count
```

所以只需要：

```text
Q_kvar × 10
```

当前冻结协议没有对 Q 再做像 PCC_P 那样的方向反转，因此是：

```text
Gain = +10
```

这里的 Gain 解决的是：

```text
kvar
→
0.1 kvar/count
```

---

# 11. 为什么 40103 电压明明 Gain=1 还要保留 Gain 模块

40103：

```text
PCC_V
1 V/count
```

理论上：

```text
raw = V
```

所以 Gain：

```text
1
```

从计算结果看它似乎“什么都没做”。

但保留 Gain 有两个意义。

第一，编码结构统一：

```text
From → Gain → Round
```

14 路形式完全一致。

第二，它明确告诉读模型的人：

> 这里正在进行“工程量→raw”的编码，只不过该寄存器比例恰好是 1 V/count。

比如：

```text
10004.3 V
×1
=
10004.3 raw count
```

后面仍需 Round。

所以 Gain=1 不是冗余，而是**显式表达比例系数为 1**。

---

# 12. 为什么 40104 频率 Gain=100

40104 定义：

```text
0.01 Hz/count
```

所以：

```text
raw = F / 0.01
    = F × 100
```

例如：

```text
F = 49.997 Hz
```

经过 Gain：

```text
49.997 × 100
=
4999.7
```

后面 Round：

```text
5000
```

板端解码：

```text
5000 × 0.01
=
50.00 Hz
```

# 13. 为什么 PVmax 是 ×10

40105/40106：

```text
PV1_P_MAX
PV2_P_MAX

scale = 0.1 kW/count
```

因此：

```text
65 kW
×10
=
650 raw
```

板端：

```text
650 ×0.1
=
65.0 kW
```

这两路是 V4 基础 C AGC 真正参与动态计算的输入。

# 14. 为什么 SOC 是 ×10000

40107/40108：

```text
SOC scale = 0.0001 pu/count
```

因此：

```text
raw = SOC / 0.0001
    = SOC ×10000
```

例如：

```text
SOC = 0.6000 pu
```

得到：

```text
6000
```

板端：

```text
6000 × 0.0001
=
0.6000 pu
```

# 15. 为什么六路 Pmeas 是 ×1000，而不是 ×10

这是第一张图最容易产生疑问的地方。

40109～40114 的协议尺度是：

```text
0.1 kW/count
```

但当前从原 23 维正式日志复用过来的六路 Pmeas 是：

```text
pu
```

而项目固定：

```text
P_unit = 100 kW
```

所以第一步：

```text
P_kW = P_pu ×100
```

第二步，因为：

```text
0.1 kW/count
```

所以：

```text
raw = P_kW ×10
```

两步合并：

```text
raw
= P_pu ×100 ×10
= P_pu ×1000
```

所以 Gain：

```text
1000
```

例如 EV：

```text
EV1 Pmeas = -0.600 pu
```

表示：

```text
-0.600 ×100
=
-60.0 kW
```

再转 raw：

```text
-60.0 ×10
=
-600
```

因此：

```text
40113 raw = -600
```

完全正确。

# 17. Round 模块为什么必须存在

第一张图中，Gain 后面全部有：

```text
Rounding Function
Operator = round
```

它的任务是：

> 把连续浮点工程量经过比例换算后的 raw 数值量化到最近的整数 count。

例如：

```text
PCC = -119.8861 kW
```

经过 -10：

```text
1198.861
```

但寄存器不可能存：

```text
1198.861 count
```

协议只有整数 count。

所以：

```text
round(1198.861)
=
1199
```

---

## 17.1 为什么不用 floor

如果用 floor：

```text
1198.861 → 1198
```

会始终向下偏。

如果负数：

```text
-599.7 → -600
```

又会产生不同方向偏差。

使用 round：

```text
取最近整数
```

可以让量化误差一般控制在：

```text
±0.5 count
```

例如 PCC 0.1 kW/count：

```text
最大普通量化误差约 ±0.05 kW
```

# 18. 一个极其重要的概念：Round 后仍然不等于 INT16

这正是我们第一次 Ctrl+D 报错的根本原因。

很多人直觉会认为：

```text
round(1198.861)
=
1199
```

既然已经是整数了，那么它就是“整数类型”。

**不对。**

在 Simulink 中要区分：

```text
数值是不是整数
```

和：

```text
数据类型是不是整数
```

这是两个概念。

Round 后：

```text
数值 = 1199
```

但如果输入是 double，那么输出通常仍然是：

```text
double 类型的 1199.0
```

可以理解为：

```text
值看起来是整数
类型仍然是 double
```

所以第一版脚本形成：

```text
Gain
→ Round
→ double 1199
→ Op401xx要求 UINT16/INT16
```

Ctrl+D 就检测到：

```text
Data type mismatch
```

这就是为什么后来必须增加你第二张图里的：

```text
Data Type Conversion
```

---

# 19. 第二张图中的 V4_CAST_xxx 到底干什么

最终补丁：

```text
v4_fix_401xx_data_types_v2.m
```

在 Round 输出到 401xx 出口之间插入：

```text
Data Type Conversion
```

例如：

```text
V4_CAST_40101_INT16
V4_CAST_40102_INT16
V4_CAST_40103_UINT16
...
```

它不再改变比例。

例如：

```text
double 1199
```

经过：

```text
Data Type Conversion → int16
```

变成：

```text
int16(1199)
```

数值基本没变。

改变的是：

```text
存储/接口数据类型
```

所以要牢牢记住：

```text
Gain
负责比例和符号

Round
负责量化成整数 count

Data Type Conversion
负责把整数 count 变成真正的 16 位类型
```

三者职责完全不同。

---

# 20. 为什么有的必须 INT16，有的必须 UINT16

## INT16

有符号 16 位整数：

```text
-32768 ～ +32767
```

能够表示负数。

所以以下量必须允许负数：

```text
40101 PCC_P
40102 PCC_Q
40109～40114 六路设备 Pmeas
```

因此：

```text
40101～40102 → INT16
40109～40114 → INT16
```

为什么六路 Pmeas 一定要 signed？

因为：

```text
PV发电      >0
ESS放电     >0
ESS充电     <0
EV充电      <0
```

例如 EV：

```text
-600 raw
```

UINT16 根本不能直接表达这个负数语义。

---

## UINT16

无符号 16 位整数：

```text
0 ～ 65535
```

适用于本身不会为负的量：

```text
PCC_V
PCC_F
PVmax
SOC
MODEL_STATUS
RTLAB_HEARTBEAT
```

因此：

```text
40103～40108 → UINT16
40115～40116 → UINT16
```

---

# 21. 为什么 Data Type Conversion 开启 SaturateOnIntegerOverflow

脚本为 40101～40114 的类型转换设置：

```text
SaturateOnIntegerOverflow = on
```

这意味着：

如果某个 double 数值超出了 int16/uint16 本身能够表示的物理位宽，不发生二进制回绕。

例如 int16 理论最大：

```text
32767
```

如果错误数值是：

```text
40000
```

开启 saturation 后会限制在类型上限，而不是因为二进制溢出变成一个完全不同符号的值。

注意：

这不是我们在做“V3.2 有效范围限制”。

例如：

```text
SOC raw = 12000
```

虽然从业务角度属于异常 SOC：

```text
1.2 pu
```

但：

```text
12000 < 65535
```

所以它仍然会作为：

```text
uint16(12000)
```

传给板子。

板端 V3.2 仍然可以发现：

```text
SOC 超出合法业务范围
```

也就是说：

```text
Data Type Conversion saturation
```

只防止**16 位数值表示层的溢出**。

它没有替代：

```text
V3.2 业务有效性 / range check
```

二者完全不同。

---

# 22. 为什么不直接用 Data Type Conversion 同时完成 Round

理论上，可以依赖浮点转整数时的某种取整规则。

但这样模型语义不清楚。

我们现在明确分开：

```text
Gain
→ Round
→ Cast
```

好处是任何人打开模型都能直接看出：

```text
第一步：比例换算
第二步：按最近整数做量化
第三步：换成指定16位类型
```

不会把“取整策略”隐藏在 Data Type Conversion 的内部配置中。

这也是为什么当前结构虽然多一个模块，反而更适合作为工程验收模型。

# 23. 最终 40101～40114 实际出现了“两条分支”

最终结构不是简单的一条：


而是：

```text
                  ┌→ Data Type Conversion → Op401xx
Round(double raw) ┤
                  └→ V4_TX_RAW_MUX16 → 日志
```

这是理解第二张图的关键。

---

## 23.1 上面的 Cast 分支是真正通信路径

例如：

```text
RAW_01

    ↓
V4_CAST_40101_INT16
    ↓
int16 1200
    ↓
Op40101
    ↓
以后点表映射
    ↓

```

这是给板子的正式路径。

## 23.2 下面直接进黑色竖条的分支是日志路径

你第二张图下方的黑色竖条就是：

```text
V4_TX_RAW_MUX16
```

它只负责把 16 路 raw 合成一个向量用于 Target 记录。

40101～40114 的日志分支直接使用：

```text
Round 后的 double raw
```

例如：

```text

```

而不是再把 int16 重新转换回来。

为什么这样做？

因为在正常可表示范围内：

```text

```

和：

```text

```

代表的协议数值相同。

日志关注的是：

```text

```

而不是 MATLAB 内存中的数据类型。

统一使用 double 后，后面的一个 Mux 和 OpWriteFile 更容易稳定记录、MAT 文件也更容易分析。

# 24. 40115 / 40116 为什么处理方式不一样

40115 和 40116 是 V3.2 已经验收好的：


它们原来已经是正确的 UINT16。

因此 V4 原则是：

> 不碰它们的正式通信路径。

也就是：

```text

    ↓
原 UINT16
    ↓
40115

原 RTLAB_HEARTBEAT 逻辑
    ↓
原 UINT16
    ↓
40116
```

完全保持。

我们只额外分支：

```text
   ↓

   ↓
```

# 25. 为什么 40115 / 40116 不能像 40101～40114 一样重做

因为 V3.2 已经完整验收过：

```text

```

它们属于安全协议层。

V4 的原则是：

```text

```

不是：

```text

```

所以这些安全量必须被冻结。

这也是脚本专门写：


的原因。

# 26. 为什么要删除 V3.2 的 40101～40114 Constant

V3.2 原来类似：

```text
Constant 1200
→ Op40101
```

它的作用是：

```text
给板子一个固定已知值
测试板子能不能读对
```

V4 中这个测试使命已经完成。

所以脚本把：

```text
Constant
→ Op401xx
```

改为：

```text
真实模型量
→ 编码
→ Cast
→ Op401xx
```

旧 Constant 如果已经没有其他用途，就删除。

脚本还有保护：

只有确认它原来真的是：

```text
BlockType = Constant
```

才允许 apply 自动替换。

这就是防止脚本误覆盖你后来人工修改的真实链路。

---

# 27. V4_TX_RAW_MUX16 为什么存在

它把：

```text
40101
40102
...
40116
```

对应的 raw 数值按固定顺序合成一个 16 维向量。

顺序严格是：

```text
1  → 40101
2  → 40102
...
14 → 40114
15 → 40115
16 → 40116
```

它不做任何运算。

Mux 的功能是：

> 多根标量信号线 → 一根向量信号线。

因此：

```text
16 个标量
→
长度16的 vector
```

---

# 28. 为什么这个 Mux 的 16 路要统一成 double

因为 16 路实际通信类型并不相同：

```text
40101/02       int16
40103～08      uint16
40109～14      int16
40115/16       uint16
```

如果直接把这些不同类型混到一个普通 Mux 中，Simulink 可能产生数据类型传播冲突。

而日志并不要求保留这些变量的内存类型。

日志只需要记录：

```text
raw数值
```

所以最终统一成：

```text
double
```

就非常干净：

```text
[1200, ..., 6000, ..., -600, ..., 7, 23]
```

全部能够作为普通数值进入一个日志向量。

真正的正式寄存器路径仍然保持 int16/uint16。

所以要区分：

```text
通信路径：严格类型
日志路径：统一 double
```

---

# 29. 为什么又增加 V4_TX_RAW16_GOTO / FROM

`V4_TX_RAW_MUX16` 位于原 401xx 模块所在的子系统内部。

而第二个 Target 日志最终放在 SM_Master 更合适。

为了不从子系统内部拖一条很长的 16 维线，脚本增加：

```text
V4_TX_RAW_MUX16
        ↓
Goto: V4_TX_RAW16
```

然后在 SM 根层：

```text
From: V4_TX_RAW16
        ↓
V4_COMM_LOG_MUX34
```

作用和前面的 V4SRC 一样：

> 只做清晰的内部信号路由。

它不是 OpComm，不跨 RT-LAB 子模型任务，也不经过网络。

# 30. V4_COMM_LOG_MUX34 为什么叫 34，但只有 5 个输入端

这是一个非常容易误解的地方。

它的 5 个输入端不是 5 个标量，而是：

```text
input1：SM Clock                   1维
input2：40101～40116              16维
input3：40001～40009               9维
input4：40010～40012               3维
input5：RT-LAB安全状态             5维
```

所以：

```text
1 + 16 + 9 + 3 + 5
=
34
```

因此 Mux 输出：

```text
34维
```

# 34. 为什么脚本没有自动创建 OpWriteFile

所以整个 V4 是“影子闭环观察”，不是物理接管。

# 47. `v4_model_prep_hybrid_v2.m` 的安全检查到底做了什么

这个脚本不是一上来就改模型。

它先有：

```matlab
v4_model_prep_hybrid_v2('audit')
```

audit 只检查，不修改。

主要检查：

1. 当前打开的模型是谁；
2. 是否存在 `SM_Master`；
3. 是否能唯一找到原 23 维正式 Mux；
4. 是否能找到 `J2_PCC_Measurements`；
5. 40101～40116 的出口块是否唯一；
6. 40101～40114 当前是否仍然由 V3.2 Constant 驱动；
7. 是否找到现有 40001～40009 raw vector；
8. 是否找到现有 40010～40012 management vector；
9. 是否找到现有 `rtlab_status_vec`；
10. 已有 OpWriteFile 使用了哪些 Acquisition Group；
11. 是否已经存在脚本生成的 V4 块，防止重复执行。

只有满足：

```text
模型还是干净的V3.2/V4前基线
```

才允许 apply。

# 48. 为什么脚本必须使用 `mdl = bdroot(gcs)`

我们以前已经吃过模型名写死的亏。

所以脚本没有写：

```matlab
mdl = 'K12_xxx';
```

而是：

```matlab
mdl = bdroot(gcs);
```

含义：

> 以你当前点击的 Simulink 模型作为目标。

好处：

- 模型复制/改名后脚本仍然可用；
- 不会因为名字不同找错模型；
- 不需要每次手改脚本模型名。

这是项目后续所有自动化脚本应继续遵守的原则。

---

# 49. 为什么 apply 前要求模型 Dirty=off

脚本要求你先：

```text
Ctrl+S
```

然后才运行 apply。

原因：

如果模型本来就有一堆未保存的手工改动，然后脚本又自动改几十根线，一旦出错，很难判断：

```text
哪些是你刚改的
哪些是脚本改的
```

所以：

```text
先保存一个明确断点
→
再自动改
```

风险最低。

# 50. 为什么自动备份后来改成“尽力而为”

最初脚本希望通过：

```matlab
get_param(mdl,'FileName')
```

获得模型 SLX 路径并自动复制备份。

但 RT-LAB Edit 环境下这个路径没有按普通 Simulink 环境返回可直接访问的文件路径。

因此第一次 apply 在真正改模型前就报：

```text
无法获取当前模型文件路径
```

后来 V2 改成：

```text
先尝试 FileName
→ 再 which
→ 再当前工作目录
→ 仍找不到就跳过自动备份
```

重要的是：

> 备份失败不能阻断真正的模型改造。

所以自动备份属于脚本保护功能，不属于 V4 模型功能。

# 51. 为什么第一次类型修复脚本又报“有其他分支”

第一版类型补丁假定：

```text
Encoder output
→ 只有 Op401xx 一个目的端
```

但实际模型已经同时有：

```text
Encoder output
├→ Op401xx
└→ RAW_MUX16日志
```

所以脚本看到：

```text
除 Op401xx 外还有其他分支
```

就保护性停止。

这不是模型错误。

而是补丁对真实分支结构判断过于严格。

# 52. 最终 `v4_fix_401xx_data_types_v2.m` 如何安全处理分支

最终补丁采用：

1. 找到 Encoder output；
2. 保存这条线当前的所有 destination；
3. 找出 Op401xx 那一个 destination；
4. 暂时删除整条分支；
5. 原样恢复所有“非 Op”的日志分支；
6. 只在去 Op401xx 的路径中插入 Data Type Conversion；
7. 重新连接 Op401xx。

所以最终：

```text
日志支路不被破坏
+
通信支路增加正确类型
```

这也是你当前第二张图为什么会呈现：

```text
一部分线进入 Cast
另一部分线进入黑色 Mux
```

的根本原因。

# 54. 为什么不能只保留第一张图

如果没有 Data Type Conversion：

```text

```

Simulink Ctrl+D 已经实际证明会报 mismatch。

以后 RT-LAB 点表也无法得到干净、确定的 16 位寄存器语义。

所以第一张图只能完成：


不能完成：


# 55. 为什么不能只保留第二张图

如果只把：

```text
-119.9
```

直接 cast 成 int16：

```text
-120
```

然后发给 40101，

板端按：

```text
0.1 kW/count
```

解码会得到：

```text
-12.0 kW
```

完全错误。

所以 Data Type Conversion 不会自动帮你完成：

```text
kW → count
Hz → 0.01Hz count
SOC → 0.0001pu count
```

这个必须由 Gain 完成。

因此：

```text
Gain
和
Data Type Conversion
不能互相替代。
```

# 56. 为什么不能省掉 Round

如果 Gain 后直接：

```text

→ int16
```

最终结果将依赖 Data Type Conversion 的整数舍入配置。

而我们希望协议明确规定：

```text
raw = round(...)
```

所以将 Round 显式画在模型里，更透明、更可验收。

# 59. 现在看到任何一个模块，都可以用一句话解释

## Goto / From

```text
作用：路由信号。
不改变值，不改变类型，不改变采样时间。
```

---

## Gain

```text
作用：工程单位 / 符号
→
协议 raw count。
```

---

## Round

```text
作用：浮点 raw
→
最近整数 count。

但类型仍可能是 double。
```

---

## Data Type Conversion

```text
作用：
double 整数值
→
真正 int16 / uint16。

不负责单位比例。
```

---

## Outport RAW_xx

```text
作用：
把 Encoder 内部14条通道按固定顺序输出。
```

---

## Mux16

```text
作用：
40101～40116 raw
→
一个16维日志向量。

只打包，不计算。
```

---

## Goto/From V4_TX_RAW16

```text
作用：
把子系统内部16维 raw 向量干净地送到 SM 根层日志区。
```

---

## Mux34

```text
作用：
把 Clock + 401xx + 400xx + 安全状态
组合为34维V4日志向量。
```

---

## OpWriteFile

```text
作用：
在 Target 端正式记录数据到 MAT。

不参与控制。
```

---

## INT16

```text
有符号16位。
用于可能为负的P/Q/Pmeas。
```

---

## UINT16

```text
无符号16位。
用于V/F/PVmax/SOC/status/heartbeat。
```

# 60. V4 模型侧现在“完成”的真正含义

模型侧准备完成，不代表：

```text
现在板子已经能直接控制六逆变器。
```

而是代表：

```text
① 板子需要读取的16个401xx真实数据
已经全部从真实模型中产生

② 每一路都已按协议完成
单位、比例、符号、取整、16位数据类型处理

③ 原V3.2安全状态40115/16没有被破坏

④ 板子写回40001～40012的原接收链仍然保留

⑤ RT-LAB内部板子心跳/外部命令有效性判断仍保留

⑥ V4 shadow阶段板端命令仍然不会控制Pref

⑦ 新增了独立34维Target通信证据链
```

因此后面真正缺的是：

```text
RT-LAB Modbus点表 Configuration
+
工程师 V4 C 程序
+
联调
```

而不是再继续重构 Simulink 主模型。

# 61. 最后用“人话”再串一次

当前微电网模型里本来就已经知道：

```text
现在PCC是多少
现在PV最多能发多少
ESS SOC是多少
六台设备现在实际发/充多少
```

V3.2以前只是拿一些人为数字测试板子会不会读。

V4现在做的是：

> 把这些真实物理量真正送进通信协议。

但是模型里的真实值是：

```text
-119.9 kW
0.6000 pu
49.997 Hz
-0.600 pu
```

而 Modbus 16 位寄存器不能直接理解这些工程量。

所以先用 Gain 规定：

```text
每一个count代表多少工程量
```

再用 Round 把：

```text
1198.861 count
```

变成：

```text
1199 count
```

然后再用 Data Type Conversion 告诉 Simulink：

```text
这个1199不再是普通double，
而是协议要求的int16/uint16。
```

这样真正的 401xx 数据格式才成立。

同时，我们又在正式发送之前/旁边分一条日志：

```text
“我这一周期究竟准备发了什么raw？”
```

板子写回以后也记录：

```text
“这一周期板子究竟写回了什么raw？”
```

再把：

```text
RT-LAB认为板子活不活
命令有没有资格
```

全部记录在同一条 Target 时间线上。

所以 V4 模型侧改造的本质不是“多加了很多模块”。

而是建立了一条完整、可验证的数据生命线：

```text
真实物理状态
→
协议编码
→
正确16位数据类型
→
Modbus出口
→
板端shadow算法
→
板端写回
→
RT-LAB安全检查
→
Target证据记录
```

而六台真实设备的控制路径暂时不改变。

这就是 V4-shadow 模型侧准备工作的完整逻辑。
