# 3. 第一项核心工作：把“15策略判断”真正变成“15策略闭环执行”

## 3.1 原模型真正缺的是什么

原模型中15种策略已经能够输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

问题在于：

> 15个 `cmd（原始控制建议）` 的物理意义完全不同。

例如：

- S2 / S7：有功调节量；
- S3：无功需求；
- S5：孤岛判断；
- S6：光伏变化率超限；
- S8：减载量；
- S14：黑启动阶段；
- S15：并离网/恢复请求。

因此不能：

```text
15个cmd直接相加
```

也不能：

```text
15个cmd直接连接6台设备
```

必须增加一个完整执行架构。

---

## 3.2 最终形成的LOCAL15结构

### 专业讲解版

```text
Advanced_Microgrid_15_Strategies
15策略原始判断
        ↓
Request Normalization
请求标准化
        ↓
按执行域分类
        ├─ Active-P Domain（有功域）
        ├─ Reactive-Q Domain（无功域）
        └─ Mode / Recovery Domain（模式/恢复域）
        ↓
各域内部仲裁 / 状态管理 / 资源分配
        ↓
Command Source Routing
控制源路由
        ↓
u_commit
        ↓
Execution Fault / Actual Applied
执行差异 / 实际采用
        ↓
最终设备控制接口
        ↓
2PV + 2ESS + 2EV Plant
```

### 通俗理解版

可以把15个策略理解成15个“专家”。

它们只负责说：

> “现在系统发生了什么，我建议怎么处理。”

但真正操作设备以前，还需要一个“调度中心”：

- 先判断这条建议属于有功、无功还是运行模式；
- 同一类建议发生冲突时先仲裁；
- 确定系统总共要调多少；
- 再决定六台设备分别承担多少；
- 最后经过安全检查，真正送给逆变器和PCC断路器。

# 4. 有功P链：从多个策略建议变成六设备Pref

## 4.1 为什么有功策略还要再次分类

有功策略不是同一性质。

### 主目标

```text
S7  联络线有功控制
S9  削峰填谷
S10 周期计划
S12 新能源消纳
S13 多目标协调
```

这些回答：

> “当前整个微电网有功应该往哪个方向、调多少？”

同一时刻只能选一个主目标。

### 硬约束

```text
S1  需量限制
S4  防逆流
S11 外送限制
```

这些回答：

> “无论主目标是什么，都不能超过这个边界。”

因此形成：

```text
objective_dP
主目标有功调节量
        ↓
S1 / S4 / S11约束
        ↓
effective_dP
最终允许执行的有功调节量
```

---

## 4.2 AGC角色重新定义

AGC（自动有功调节）不再同时负责：

```text
为什么调
+
谁承担
```

而只负责：

> 已知 `effective_dP（最终有效有功调节量）` 后，在2PV+2ESS+2EV之间分配任务。

这使系统形成清晰分层：

```text
策略层
决定“总任务”

AGC层
决定“资源分工”
```

---

## 4.3 S6和S8为什么在AGC之后

S6光伏平滑和S8减载不是新的PCC主目标。

它们属于：

> 在基础调度命令形成以后，对特定设备进行局部快速修正。

- S6：主要用ESS补偿PV快速变化；
- S8：通过减小EV充电功率实现可控负荷释放。

因此：

```text
P主目标 / 约束
↓
AGC六资源基础分配
↓
S6 / S8辅助执行
↓
最终六设备Pref
```

# 5. Q链：从S3总无功需求到六设备Qref

## 专业讲解版

S3 AVC（自动电压控制）先形成总无功需求：

```text
Q_request
```

然后根据六台设备当前有功运行点计算剩余无功能力：

```text
Qcap_i ≈ sqrt(1 - Pref_i²)
```

再按剩余能力比例分配：

```text
6 × Qref
```

## 通俗理解版

每台逆变器就像有一个固定“容量圆”。

如果它已经承担很多有功P，就没有太多空间再承担无功Q。

所以不是：

```text
总Q ÷ 6
```

而是：

> 谁还有余量，谁多承担一点无功。

# 6. Mode / Safety / Recovery：从“策略判断”变成真实并离网动作

## 6.1 为什么模式控制必须独立

功率控制回答：

> 发多少P、Q。

模式控制回答：

> 当前设备应该跟网还是构网？PCC是否闭合？系统是NORMAL还是ISLANDED？

这两类问题不能混在一个连续功率控制器里。

---

## 6.2 S5安全判断

S5不能简单：

```text
通信异常
→ PCC跳闸
```

LOCAL15重新区分：

```text
electrical_bad
电气异常

comm_bad
通信异常
```

只有真正电气异常才能形成真实离网资格。

这保证：

> 纯通信异常不会误跳PCC。

---

## 6.3 S14黑启动

黑启动不只是改变一个模式变量。

它必须同时完成：

```text
PCC断开
↓
选定一个ESS成为GFM（构网型）主机
↓
逐阶段恢复资源
Stage1 主ESS建立系统
Stage2 非主ESS
Stage3 PV
Stage4 EV
```

所以S14天然横跨：

- 模式链；
- 设备GFM/GFL链；
- PCC断路器；
- P链Pref门控。

---

## 6.4 S15受控重同步

最终补齐：

```text
孤岛
↓
比较Grid / PCC
ΔV
Δf
Δθ
↓
Fref trim
主ESS频率参考修正
↓
同步条件连续满足
↓
PCC重合闸
↓
保持
↓
GFM → GFL
↓
NORMAL
```

这使LOCAL15真正形成完整：

```text
并网
→ 离网
→ 孤岛
→ 同步
→ 重合闸
→ 返回并网
```

闭环。

# 8. 工况设计不是“调参数让策略亮”，而是做可预测的因果实验

## 8.1 主目标与约束故意冲突

典型：

- S1；
- S4；
- S11。

例如：

```text
主目标希望进口100 kW
S1只允许进口50 kW
```

则可以预先判断：

```text
约束应产生约50 kW量级修正
```

这样测试结果具有明确可解释性。

---

## 8.2 正向 + 负向安全测试

典型S5：

```text
真正电气异常
→ 必须离网

只有通信异常
→ 不允许误跳闸
```

测试不只是证明“会动作”，也证明“不该动作时不会乱动作”。

---

## 8.3 双方向测试

典型S6：

```text
PV上升
→ ESS充电补偿

PV下降
→ ESS放电补偿
```

用于发现符号方向错误。

---

## 8.4 透明回归

新增Router（路由器）、Gate（门控）或Safety Layer（安全层）：

```text
新功能关闭
↓
最终输出必须等于旧系统
```

证明：

> 新结构本身没有破坏原系统。

---

## 8.5 状态机分阶段测试

典型：

- S14黑启动；
- S15重同步。

不是只看终点，而是逐阶段验证：

```text
进入条件
↓
中间状态
↓
实际动作
↓
退出条件
```

# 14. C模块测试采用了哪些方法

针对：

- 边界；
- 非法输入；

大量随机合法组合，用于增加覆盖、发现人工没有想到的边界。

```text

```

- retry；
- commit；

- measurement break；
- execution feedback。

# 16. C10：从“算法控制器”到“真实工程控制器”

C10是这一阶段最关键的工程化步骤之一。

## 16.1 candidate / pending / commit

算法计算出新命令：

```text
candidate
候选
```

先保存成：

```text
pending
待提交
```

只有：

```text
40001～40064完整FC16成功
```

才：

```text
controller_commit
正式提交
```

---

## 16.2 为什么必须这么做

如果：

```text
算法内部认为已经执行新命令
但FC16发送失败
```

真实Plant仍执行旧命令。

于是：

```text
Controller State
≠
Plant State
```

所以必须明确：

```text
计算成功
≠
发布成功
```

---

## 16.3 Measurement Snapshot（测量快照）

每次完整40101～40124读取形成一份：

`Measurement Snapshot（测量快照）`

候选命令必须和产生它的Snapshot绑定。

### 同一Snapshot

FC16失败但还没有新测量：

```text
可以精确重试
```

### 新Snapshot已经到达

旧candidate对应旧Plant状态：

```text
不能无条件继续发送
↓
应重新计算
```

---

## 16.4 reconnect ≠ reset

普通网络重连：

```text
TCP恢复
```

不意味着：

```text
算法内部历史全部清零
```

所以最终明确：

```text
普通Modbus reconnect
≠
controller reset
```

显式Reset由：

```text
CONTROLLER_RESET_SEQ
```

控制。

# 21. 为什么需要数据类型、Scale和bitmask

## 数据类型

```text
INT16
适合正负量

UINT16
适合非负量 / 状态 / 序号
```

## Scale（缩放）

例如：

```text
raw = 4998
scale = 0.01
→ 49.98 Hz
```

## enum（枚举）

整数表示离散状态：

```text
0 NORMAL
1 EMERGENCY
...
```

## bitmask / bitfield（位掩码 / 位域）

一个16位寄存器同时携带多个布尔状态。

这些都是工业控制中常见的数据接口方法。

# 22. Runtime Config为什么必须原子更新

如果40201～40280正在被更新，Board中途读取：

```text
一半新参数
+
一半旧参数
```

会形成一套从未真正配置过的控制器。

因此设计：

```text
CONFIG_SEQ
CONFIG_SEQ_ECHO
seq_before
seq_after
```

只有：

```text
before = echo = after
```

才接受整块配置。

这保证了配置一致性。

# 28. 通俗版总结：如果只用一个故事解释这段工作

最开始我们有15个“会出主意的策略”。

但这些策略就像15个部门：

- 有的管有功；
- 有的管无功；
- 有的管安全；
- 有的管黑启动；
- 有的管并离网。

如果所有部门同时直接下命令，系统一定会乱。

所以第一步是建立一个“总调度系统”：

```text
先分类
再仲裁
再把任务分给六台设备
最后才真正执行
```

之后还不能因为“模块有输出”就说成功。

于是我们给15个策略逐个设计“考试题”：

- 什么时候应该动作；
- 什么时候不应该动作；
- 动作方向对不对；
- 最后的设备和PCC有没有真的响应。

15个策略全部通过以后，把这一套模型冻结成标准答案。

然后我们开始把这套标准答案搬到真实控制板。

这时问题就不再只是控制算法，还包括：

- 程序状态；
- 通信；
- 配置；
- 网络发送成功还是失败；
- 命令什么时候才算真正生效。

所以把算法拆成C01～C10，逐块验证，再用C10专门管理：

```text
“算出来”
和
“真的发送成功”
```

之间的区别。

最后，为了让外部工程师可以真正把它做成板端程序，又把所有信号整理成正式Modbus点表，并把运行顺序写成版本要求。

因此这一段工作的本质是：

> **把一个“仿真中的15策略算法集合”，逐步做成一套“可验证、可移植、可通信、可由第三方工程实现”的控制系统。**
