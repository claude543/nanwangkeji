# BOARD15 最终板端程序与模型侧总体架构通俗理解
## ——围绕《智能微电网高级应用仿真模型及算法介绍》15项功能的最终目标、控制算法层与实现分工

> **日期**：2026-08-18  
> **性质**：项目内部理解与后续BOARD15设计基线  
> **功能范围**：后续主要围绕《智能微电网高级应用仿真模型及算法介绍》中已经具体实现的15项高级应用功能展开，不再额外扩展当前15策略体系之外的功能。  
> **核心原则**：只做为了实现15项功能真实闭环、板端控制、CHIL验证以及后续控制算法升级所必须做的设计，不为了“架构漂亮”增加无明确作用的复杂机制。

---

# 1. 最终到底想实现什么

最终目标可以用一句话概括：

> **让外部控制板真正运行完整的15项微电网高级应用策略，通过 Modbus TCP（工业以太网通信）实时读取 OP5700 中 2PV + 2ESS + 2EV 微电网的状态，完成策略判断、策略仲裁和资源协调，形成有功、无功、运行模式、断路器及重同步相关命令，再写回 RT-LAB 真正控制六逆变器实时对象，最终形成完整 CHIL（控制器硬件在环）闭环。**

最终闭环：

```text
OP5700实时微电网模型
        ↓
P/Q/V/f、PVmax、SOC、六设备Pmeas等真实测量
        ↓
Modbus FC03
        ↓
BOARD15外部控制板
        ↓
15策略判断
        ↓
请求标准化 + 模式管理 + 策略仲裁
        ↓
P/Q/模式/负荷等不同执行域
        ↓
仲裁型基础AGC及其他执行逻辑
        ↓
形成完整控制命令
        ↓
Modbus FC16
        ↓
RT-LAB最终安全接管
        ↓
2PV + 2ESS + 2EV真实响应
        ↓
形成新的测量
        ↓
下一控制周期
```

因此最后的成果不是：

```text
“板子能和RT-LAB通信”
```

也不是：

```text
“板子能算一个AGC”
```

而是：

> **板子真正成为15项高级应用功能的协调控制器。**

---

# 2. 当前主要对应哪15项功能

后续以《智能微电网高级应用仿真模型及算法介绍》中已经形成统一策略接口的15项功能为主：

1. 需量控制  
2. AGC  
3. AVC  
4. 防逆流  
5. 防孤岛  
6. 平滑处理  
7. 联络线功率控制  
8. 低压/低频减载  
9. 削峰填谷  
10. 周期计划  
11. 自发自用余电上网  
12. 新能源最大化消纳  
13. 多目标优化控制  
14. 黑启动控制  
15. 并离网切换  

原始高级应用模块已经能够输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

分别表示：

```text
status
策略状态

alarm
告警状态

metric
策略指标/中间量

cmd
策略建议控制量
```

原始模型的定位主要是：

```text
15策略
会判断
会告警
会给建议量
会记录
```

而当前 LOCAL15 和未来 BOARD15 做的事情，是继续完成：

```text
策略建议
↓
仲裁
↓
资源分配
↓
执行映射
↓
真实设备命令
```

从而把15项功能真正变成闭环控制。

# 3. 15种策略是不是一直全部参与闭环控制

## 3.1 结论

> **15种策略可以持续参与系统监视、状态判断和控制请求生成，但并不是15种策略在任何时刻都同时拥有最终设备控制权。**

正确结构：

```text
15种策略持续读取系统状态
        ↓
分别输出状态/告警/指标/控制建议
        ↓
Request Normalizer
请求标准化
        ↓
Mode Manager
运行模式管理
        ↓
Arbiter
控制请求仲裁
        ↓
只有当前允许执行的请求
进入对应执行域
        ↓
最终设备闭环
```

---

## 3.2 为什么不能15个策略全部直接控制设备

因为它们输出的物理意义不同。

例如：

```text
S3 AVC
→ 无功调节请求

S7 联络线控制
→ 有功调节请求

S8 低压/低频减载
→ EV负荷削减请求

S15 并离网切换
→ 模式/断路器/重同步请求
```

这些请求不能简单：

```text
cmd1 + cmd2 + ... + cmd15
```

因此必须先“翻译”和“仲裁”。

---

## 3.3 哪些可以同时工作

例如：

```text
S7
联络线有功控制
```

和：

```text
S3
AVC无功/电压控制
```

可以同时工作，因为：

```text
S7主要负责P
S3主要负责Q
```

S6平滑还可以作为快速辅助层叠加到有功执行域。

---

## 3.4 哪些不能同时抢主控制权

例如：

```text
S7
S9
S10
S12
S13
```

本质上都可能形成一个“当前主有功运行目标”。

所以不能在同一时刻把五个目标直接叠加。

需要通过：

```text
P_OBJECTIVE_MODE
有功主目标选择
```

确定当前哪个功能提供主目标。

其余策略仍然可以：

```text
计算
监视
输出status/alarm/metric
```

但不拥有最终主P控制权。

# 4. 最终板端程序的总体结构

最终BOARD15不需要设计成非常复杂的软件。

真正必要的结构可以压缩成六层。

---

# 4.1 第一层：Modbus通信层

作用：

> **负责控制板和OP5700之间的数据交换。**

主要包括：

```text
FC03
读取RT-LAB测量和必要配置

FC16
写回完整控制命令

TCP连接
断线重连
通信超时
```

这是所有板端闭环的基础。

---

# 4.2 第二层：数据与通信安全层

作用：

> **判断当前数据是否可信，以及Board当前是否还有资格进行闭环控制。**

继续继承已经验证过的：

```text
DISCONNECTED
通信断开

WAIT_VALID
通信恢复但数据尚未连续验证通过

ENABLED
允许Board正常控制
```

同时判断：

```text
MODEL_STATUS
RT-LAB模型状态

RTLAB_HEARTBEAT
RT-LAB心跳

BOARD_HEARTBEAT
Board程序心跳

FC03成功/失败
FC16成功/失败
数据范围和有效性
```

这层解决：

```text
通信已经异常
但Board还拿旧数据继续闭环计算
```

的问题。

---

# 4.3 第三层：真正的Project15控制算法层

这是最终BOARD15最核心的部分。

它不是一个简单：

```text
AGC()
```

而是一整套协调逻辑。

我们计划实现：

```text
15策略判断
        ↓
Request Normalizer
请求标准化
        ↓
Mode Manager
运行模式管理
        ↓
Arbiter
策略仲裁
        ↓
按执行域拆分
        ├─ 有功控制
        ├─ 无功控制
        ├─ 模式/安全控制
        └─ 可控负荷控制
        ↓
Execution Mapper
执行映射
        ↓
完整设备命令
```

这一层是：

> **把15种“高级应用功能”真正变成设备可以执行的控制命令。**

---

# 5. Project15核心控制算法层具体怎么设计

这一部分是整个BOARD15最核心的软件设计。

---

## 5.1 第一步：15策略判断层

对应：

```text
Advanced_Microgrid_15_Strategies
微电网15种高级应用策略判断模块
```

输入：

```text
PCC P/Q/V/f
PV最大可用功率
ESS SOC
六设备Pmeas
时间
策略参数
```

输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

作用：

> **分别判断15个功能当前是否触发，以及它希望系统做什么。**

这部分原则上由我们根据已经验证过的LOCAL15/原策略算法转成C代码。

---

## 5.2 第二步：Request Normalizer
## 请求标准化器

为什么需要：

```text
cmd[15]
```

里的15个量不是同一种东西。

例如：

```text
S7：
+40 kW有功调节请求

S3：
+30 kvar无功请求

S8：
削减50 kW EV负荷

S15：
进入重同步状态
```

所以 Request Normalizer 的作用就是：

> **把15个不同含义的策略输出翻译成统一、明确、带物理意义的标准控制请求。**

例如变成：

```text
P目标请求
P硬约束
Q总需求
平滑辅助请求
EV减载请求
模式切换请求
Breaker请求
重同步请求
```

---

## 5.3 第三步：Mode Manager
## 运行模式管理器

作用：

> **判断整个微电网当前究竟处于什么运行模式，并决定哪些策略现在可以拥有执行权。**

例如：

```text
NORMAL_GRID
正常并网

ISLANDED
孤岛运行

BLACK_START
黑启动

RESYNCHRONIZATION
重同步

RECLOSE
准备/执行重新并网
```

为什么必须有：

因为：

```text
正常并网时允许的策略
```

和：

```text
黑启动/孤岛期间允许的策略
```

不一样。

例如黑启动过程中，普通日常经济运行目标不能继续抢控制权。

---

## 5.4 第四步：Arbiter
## 控制请求仲裁器

作用：

> **当多个策略同时提出控制要求时，决定最终谁优先、谁是约束、谁暂时不执行。**

例如：

```text
S10周期计划：
希望PCC出口80 kW

S4防逆流：
禁止向主网出口
```

最终不是：

```text
80 + 0
```

而是：

```text
S10给运行目标
↓
S4作为硬约束
↓
最终目标被限制到允许范围
```

这是整个15策略能够同时存在、又不互相打架的关键。

# 6. 按执行域拆分到底是什么意思

仲裁以后，不能再把所有控制量混在一起。

需要按照最终控制对象拆成不同执行域。

---

## 6.1 Active-P Domain
## 有功功率执行域

主要处理：

```text
S1
S2
S4
S6
S7
S9
S10
S11
S12
S13
```

最终形成：

```text
6 × Pref
```

即六台设备有功参考。

其中最核心的是：

```text
仲裁型基础AGC
```

# 7. 仲裁型基础AGC到底是什么

为了避免和后续其它改进方法混淆，建议不要把它简单叫“改进AGC”。

更准确：

> **Arbitrated Baseline AGC  
> 仲裁型基础AGC**

或者：

> **External-dP Baseline AGC  
> 外部有功调节请求型基础AGC**

原基础AGC：

```text
Ptarget
Ppcc
↓
AGC内部算：
dP = Ptarget - Ppcc
↓
六资源分配
```

现在：

```text
15策略
↓
目标选择/硬约束
↓
得到最终P目标或dP_request
↓
Baseline AGC
↓
在2PV + 2ESS + 2EV之间分配
```

所以AGC现在只负责：

> **“已确定需要调多少功率以后，这个调节任务应该怎么分给六种资源。”**

而不负责决定：

> “为什么要调、当前究竟执行S7还是S10。”

后者由策略和仲裁层决定。

---

# 8. Reactive-Q Domain
## 无功功率执行域

主要对应：

```text
S3 AVC
Automatic Voltage Control
自动电压控制
```

流程：

```text
PCC电压/无功状态
↓
S3 AVC
↓
Q总需求
↓
Q Allocator
无功分配器
↓
6 × Qref
```

因此P和Q可以同时控制：

```text
P通道
→ AGC / 有功协调

Q通道
→ AVC / 无功分配
```

---

# 9. Mode / Safety Domain
## 运行模式与安全执行域

主要对应：

```text
S5 防孤岛
S14 黑启动
S15 并离网/重同步
```

最终产生：

```text
GridOn
设备跟网/构网选择

Droop
下垂控制使能

PCC Breaker
PCC断路器请求

Fref trim
频率参考修正

Selected Master
构网主机选择

System Mode
系统运行模式
```

这一执行域决定：

> **系统是并网、孤岛、黑启动还是重同步，以及哪台ESS负责构网。**

---

# 10. Load Domain
## 可控负荷执行域

主要用于：

```text
S8
低压/低频减载
```

当前2PV + 2ESS + 2EV系统中，最自然的可控负荷就是：

```text
EV1
EV2
```

例如：

```text
一级减载
先减少EV2充电

二级减载
继续减少EV1充电
```

最终仍表现为：

```text
EV Pref调整
```

---

# 11. Execution Mapper
## 执行映射器

前面各执行域产生的是：

```text
P要求
Q要求
模式要求
负荷要求
```

但六台设备最终需要的是：

```text
PV1 Pref
PV2 Pref
ESS1 Pref
ESS2 Pref
EV1 Pref
EV2 Pref

6 Qref
6 GridOn
6 Droop
PCC Breaker
Fref
```

Execution Mapper的作用：

> **把“策略和执行域语言”转换成最终设备命令语言。**

# 12. 板端程序的调度方式

目前规划采用最低复杂度方案：

```text
100 ms
主通信/控制循环
```

每100 ms：

```text
FC03
↓
解码与数据有效性
↓
形成同一批Measurement Snapshot
↓
15策略判断
↓
Normalizer / Mode Manager / Arbiter
↓
Q、S6、S8、S14、S15等执行
↓
必要时更新命令
↓
FC16
```

基础有功AGC：

```text
1 s
```

执行一次。

所以不是复杂的多线程控制器，而是：

```text
一个100 ms主循环
+
一个1 s AGC子周期
```

这与现有V4/V5板端程序结构比较接近，工程实现难度可控。

# 13. candidate / commit为什么必须保留

必须区分：

```text
算法算出了什么
```

和：

```text
RT-LAB真正收到什么
```

所以：

```text
u_calc
算法候选命令

↓ FC16成功

u_commit
最近一次成功提交命令
```

如果FC16失败：

```text
不能认为新命令已经正式发布
```

因此：

```text
命令类内部状态
```

不能继续假装已经执行到新状态。

这继续继承V4已经建立的安全思想。

---

# 14. FC03失败和FC16失败不能混为一谈

## FC03失败

代表：

> **Board没有新的可信Plant状态。**

所以：

```text
不应该拿旧PCC/旧Pmeas继续形成新的正常闭环决策
```

---

## FC16失败

代表：

> **Board知道系统状态，也算出了新candidate，但这份新命令没有成功发布。**

所以：

```text
candidate不commit
```

这两个异常对内部状态的处理不同。

# 22. 图片中每一个英文模块的标准中文含义

| 英文 | 中文 | 最简单理解 |
|---|---|---|
| `Advanced_Microgrid_15_Strategies` | 微电网15种高级应用策略判断模块 | 15个策略分别判断“现在该不该动作” |
| `status` | 状态 | 当前策略处于什么状态 |
| `alarm` | 告警 | 是否触发策略条件 |
| `metric` | 指标 | 当前误差、阶段、百分比等 |
| `cmd` | 控制建议量 | 策略希望系统做什么 |
| `Request Normalizer` | 请求标准化器 | 把15种不同控制建议翻译成标准请求 |
| `Mode Manager` | 运行模式管理器 | 判断当前正常并网/孤岛/黑启动/重同步等 |
| `Arbiter` | 控制请求仲裁器 | 多策略冲突时决定谁真正执行 |
| `Active-P` | 有功功率执行域 | 形成六设备有功命令 |
| `Reactive-Q` | 无功功率执行域 | 形成六设备无功命令 |
| `AVC` | 自动电压控制 | 根据电压/无功状态调Q |
| `Qalloc` | 无功功率分配 | 把总Q请求分给六台设备 |
| `GFM` | 构网型控制 | 设备建立电压和频率基准 |
| `GFL` | 跟网型控制 | 设备跟随已有电网电压和频率 |
| `Breaker` | 断路器 | PCC并离网开关 |
| `EV Shed` | 电动汽车充电负荷削减 | 低压/低频时减少EV充电 |
| `Execution Mapper` | 执行映射器 | 把策略请求变成设备实际接口 |
| `Command Source Router` | 控制命令源路由器 | 决定当前听V5A、LOCAL15还是BOARD15 |
| `u_commit` | 正式提交命令 | 当前正式发布的控制状态 |
| `Execution Fault Injector` | 执行故障注入器 | 人为制造“提交命令≠实际执行”的测试条件 |
| `u_applied` | 执行侧实际采用命令 | Plant最后真正采用的控制命令 |
| `Plant` | 被控对象/微电网实时对象 | 2PV+2ESS+2EV和电气网络 |
