> → 各自进入该去的执行部门
> → 某些部门存在前后依赖
> → 最终汇总成完整命令”
> ```

# 1. 先回答第一个核心疑问：为什么会有 `P Objective / Constraint`

## 1.1 不是所有15种策略都先经过P Objective / Constraint

这是首先必须纠正的认识。

`P Objective / Constraint（有功目标/约束）` **只属于有功P执行域**。

它主要处理：

```text
S1  需量控制
S2  PCC跟踪/AGC
S4  防逆流
S7  联络线功率控制
S9  削峰填谷
S10 周期计划
S11 自发自用/余电上网
S12 新能源最大化消纳
S13 多目标协调
```

而：

```text
S3
→ Q无功域

S5
→ Mode模式/安全域

S6
→ P辅助执行域

S8
→ Load/有功辅助执行域

S14
→ 黑启动模式与恢复序列

S15
→ 并离网/重同步模式域
```

它们并不是全部先进入 `P Objective / Constraint`。

---

# 2. 为什么有功策略必须先经过“目标/约束管理”

因为有功类策略本身也分成不同性质。

## 2.1 第一类：主有功目标

包括：

```text
S7  联络线功率控制
S9  削峰填谷
S10 周期计划
S12 新能源最大化消纳
S13 多目标协调
```

这些策略本质上都可能回答：

> **“当前系统整体有功应该往哪个方向、调多少？”**

例如：

```text
S7：
希望PCC跟踪 -100 kW

S10：
按照计划曲线，现在希望PCC是 -60 kW

S12：
新能源有弃光风险，希望系统增加内部吸收

S13：
综合多目标后，希望形成另一套P调节请求
```

它们不能同时作为五个“总有功目标”直接相加。

否则：

```text
S7要求 +30 kW
S10要求 -20 kW
S12要求 -40 kW
S13要求 +10 kW

直接相加
= -20 kW
```

这个结果没有明确物理含义。

因此需要：

```text
P Objective Selection
有功主目标选择
```

决定：

```text
当前谁是主目标
```

---

## 2.2 第二类：硬约束

包括：

```text
S1  需量控制
S4  防逆流
S11 自发自用/余电上网限制
```

它们通常不是说：

> “我希望PCC一定运行在某个目标。”

而是说：

> **“无论当前主目标是谁，都不能违反这个边界。”**

例如：

```text
S7：
希望进口100 kW

S1：
最大需量只允许进口50 kW
```

那么：

```text
S7给出主目标
↓
S1对它进行限制
↓
最终只能允许进口50 kW附近
```

因此在LOCAL15里形成两个非常关键的量：

```text
objective_dP
主目标要求的有功调节量

effective_dP
考虑硬约束以后真正允许执行的有功调节量
```

---

# 3. 所以有功域真正的逻辑是什么

不是：

```text
所有策略
→ AGC
```

而是：

```text
S7 / S9 / S10 / S12 / S13
         │
         │ 选择当前主目标
         ▼
    objective_dP
         │
         │
S1 / S4 / S11
作为硬约束
         │
         ▼
    effective_dP
         │
         ▼
P Coordination / AGC
         │
         ▼
六设备基础Pref
```

这就是 `P Objective / Constraint` 必须存在的原因。

它回答的是：

> **在六设备分配之前，系统整体究竟应该调多少有功？**

---

# 4. AGC为什么一定在P目标/约束后面

因为AGC解决的不是：

> “为什么要调？”

而是：

> **“已经决定总共要调多少以后，六台设备分别承担多少？”**

例如：

```text
effective_dP = +80 kW
```

这意味着：

> 微电网总净出力还需要增加80 kW。

AGC再考虑：

```text
PV还能增加多少
ESS SOC是否允许放电
EV还能减少多少充电
```

最终得到：

```text
PV1 +20
PV2 +20
ESS1 +15
ESS2 +15
EV1减少充电5
EV2减少充电5
```

所以一定是：

```text
先决定“总任务”
↓
再分配“谁承担”
```

而不能：

```text
六台设备先随便分配
↓
最后再决定系统到底想实现什么目标
```

---

# 5. 但S6和S8为什么又在AGC后面

这是第二个很关键的问题。

因为S6和S8不是新的“主PCC目标”。

---

## 5.1 S6平滑是什么

S6说的是：

> **“光伏变化太快，ESS需要临时补偿。”**

例如基础AGC已经得到：

```text
ESS1 Pref = +0.2
ESS2 Pref = +0.2
```

突然PV最大可用出力快速上升。

S6可能要求：

```text
ESS临时往充电方向修正
```

于是：

```text
基础P命令
↓
S6局部修正ESS
↓
得到最终更平滑的有功命令
```

S6并不应该重新成为：

```text
新的PCC主目标
```

所以它放在基础AGC之后。

---

## 5.2 S8低压/低频减载是什么

S8说的是：

> **“现在发生低压/低频，需要减少可控负荷。”**

当前可控负荷主要是：

```text
EV1
EV2
```

所以S8直接修改：

```text
EV Pref
```

让EV充电功率向0移动。

它同样不是：

```text
一个新的PCC计划目标
```

而是：

```text
在基础运行命令上增加紧急负荷动作
```

因此也在AGC后面。

---

# 6. 所以S6/S8的位置为什么很合理

实际LOCAL15冻结位置是：

```text
P Objective / Constraint
        ↓
Baseline AGC
        ↓
Execution Mapper
        ↓
P Auxiliary Executor
├─ S6
└─ S8
        ↓
Command Source Router
        ↓
u_commit
```

这里有三个层级：

```text
第一层：
决定全系统有功目标

第二层：
六资源基础分配

第三层：
针对局部快速/紧急需求修正具体设备命令
```

所以：

```text
S6/S8
```

不是“所有策略统一通过S6/S8”。

而是：

> **只有基础有功命令会经过S6/S8这个辅助修正层；S6/S8没有触发时，它就是透明直通。**

---

# 7. Q控制为什么看起来又放在P后面

S3 AVC本质属于独立的Q无功域。

它不是：

```text
P → Q
```

这种因果关系。

正确理解：

```text
P控制目标
和
Q控制目标

本质上是两个并行控制域
```

但是在当前六台变流器中：

> **同一台变流器的P和Q共同占用其视在容量。**

如果某设备已经：

```text
Pref ≈ 1.0 pu
```

那么它剩余的Q能力就很小。

因此Q分配需要知道：

```text
当前最终P命令是多少
```

才能计算：

```text
Qcap_i
=
sqrt(max(1 - Pref_i^2, 0))
```

所以在最终C执行顺序里：

```text
先形成当前周期最终P candidate
↓
再根据P占用了多少容量
计算6台设备剩余Q能力
↓
分配S3总Q请求
```

这不是：

> “Q策略必须服从P策略。”

而是：

> **P和Q独立决定目标，但由于共享同一个变流器容量，Q的设备级分配需要知道当前P占用了多少容量。**

---

# 8. Mode模式域为什么又不是简单排在Q后面

这一点需要特别纠正。

模式控制不能简单理解成：

```text
P算完
→ Q算完
→ 才开始Mode
```

实际上Mode有两个作用。

---

## 8.1 作用A：提前决定“哪些控制现在有资格执行”

例如当前进入：

```text
BLACK_START
```

那么普通：

```text
S7正常联络线跟踪
S10周期计划
S6普通平滑
```

就不能像正常并网时一样继续拥有执行权。

所以Mode Manager要提前给出：

```text
allow_normal_p
allow_normal_q
allow_s6
当前系统模式
```

这些“权限”会影响后面的P/Q计算。

因此：

> **Mode Decision（模式判断）在逻辑上应当较早发生。**

---

## 8.2 作用B：最后形成真实模式命令

Mode还要最终产生：

```text
6 × GridOn
6 × Droop
PCC Breaker
Selected Master
System Mode
```

这些是Plant真正要执行的模式命令。

因此Mode又会在最终命令汇总阶段参与。

---

# 9. 所以Mode其实分成“判断”和“执行”两层

正确结构：

```text
S5 / S14 / S15原始判断
        ↓
Mode Normalizer
        ↓
Mode Manager
        ↓
得到：
当前模式
模式优先级
P/Q执行许可
黑启动/离网/恢复请求
        │
        ├──────────────→ 影响P链
        ├──────────────→ 影响Q链
        └──────────────→ Mode执行链
                           ↓
                     GridOn/Droop
                     Breaker
                     Master
                     Fref
```

所以绝不能说：

```text
所有东西先经过Q，再经过Mode
```

---

# 10. S14黑启动为什么看起来又“在P后面”

S14有两个身份：

```text
身份1：
模式策略
决定系统要进入BLACK_START

身份2：
执行序列
决定黑启动阶段里设备功率怎么逐步恢复
```

---

## 10.1 模式身份

S14先参与Mode Manager：

```text
S14 black-start request
↓
Mode Manager
↓
BLACK_START
↓
PCC open
selected ESS = GFM
```

这一部分逻辑上很早。

---

## 10.2 Pref Gate身份

进入黑启动以后，正常P协调可能仍然计算出六设备Pref。

但是黑启动不能一开始就：

```text
PV、ESS、EV全部同时恢复
```

所以增加：

```text
Black Start Pref Gate
```

对正常P候选进行阶段门控。

当前LOCAL15阶段语义：

```text
Stage 1：
六设备Pref = 0
主ESS先以GFM建立电压/频率

Stage 2：
恢复非主ESS

Stage 3：
恢复PV

Stage 4：
恢复EV负荷
```

因此它必须放在：

```text
普通P协调
+
S6/S8
```

得到基础候选命令以后，再进行：

```text
“黑启动阶段到底允许哪些设备放行”
```

所以：

> **S14不是整个控制器最后才开始判断；它的模式请求较早参与Mode，而它的Pref Gate在P命令接近最终输出的位置执行。**

---

# 11. S15为什么又不是“黑启动后必然执行”

S15是：

```text
并离网与受控重同步恢复
```

不是：

```text
S14完成以后自动下一关
```

它只在对应运行条件成立时参与。

S15最终负责：

```text
已孤岛
↓
收到恢复请求
↓
RESYNCHRONIZATION
↓
比较Grid/PCC：
ΔV
Δf
Δθ
↓
调selected ESS Fref
↓
连续满足同步窗口
↓
请求PCC重合闸
↓
确认Breaker闭合
↓
保持一段时间
↓
ESS GFM → GFL
↓
返回正常并网
```

所以S15主要影响：

```text
System Mode
Breaker
Fref trim
selected master的GFM/GFL转换
```

而不是让：

```text
所有正常P/Q命令都“经过S15算法处理”
```

# 12. 15种策略真正应该怎样分类

这是理解整个系统最重要的一张表。

| 策略 | 核心功能 | 主要进入哪个执行域 | 最终怎么影响Plant |
|---|---|---|---|
| S1 | 需量控制 | P约束 | 限制最终`effective_dP` |
| S2 | PCC跟踪/AGC KPI | P主目标/监视 | 专项时可提供P请求，综合时防止与S7重复 |
| S3 | AVC | Q域 | 形成总Q请求→六路Qref |
| S4 | 防逆流 | P约束 | 限制过量外送 |
| S5 | 防孤岛 | Mode安全域 | 电气异常时形成离网资格 |
| S6 | 光伏平滑 | P辅助域 | 修正ESS Pref |
| S7 | 联络线有功控制 | P主目标 | 综合运行主要P目标来源 |
| S8 | 低压/低频减载 | Load/P辅助域 | 调整EV Pref向0减载 |
| S9 | 削峰填谷 | P主目标 | 被选中时提供P运行目标 |
| S10 | 周期计划 | P主目标 | 被选中时提供计划P目标 |
| S11 | 自发自用/余电上网 | P约束 | 约束最大外送 |
| S12 | 新能源最大化消纳 | P主目标 | 被选中时产生吸纳P请求 |
| S13 | 多目标协调 | P主目标 | 被选中时提供综合P目标 |
| S14 | 黑启动 | Mode + P阶段Gate | PCC解列/GFM + 分阶段恢复Pref |
| S15 | 并离网/重同步 | Mode/Sync域 | Breaker + Fref + GFM→GFL |

看到这张表就应该理解：

> **没有任何理由让15种策略全部统一经过同一个AGC、S6、Q或S15。**

# 14. 谁为什么在前，谁为什么在后

现在把上图按因果顺序彻底串一次。

---

## 14.1 Measurement Snapshot必须最前

所有策略必须基于：

```text
同一批PCC
同一批PVmax
同一批SOC
同一批Pmeas
同一批V/f/phase
```

不能：

```text
S1用14:01:01的数据
S15用14:01:02的数据
```

否则同一控制周期会出现内部状态不一致。

所以最前面永远是：

```text
同一批测量快照
```

```text
cmd
```

还不是最终设备命令。

所以必须先翻译成统一标准请求。

## 14.4 Mode Decision应当比较早

因为它决定：

```text
正常Q能不能继续
```

所以它必须在最终P/Q命令形成以前给出“许可和模式”。

所以先有正常P candidate，才有“Gate什么”的对象。

# 46. 工程主程序最终到底怎么调用

“工程主程序只调用 `controller_step()`”是一种简化说法。

完整生命周期是：

## 启动

```text
controller_reset()
↓
FC03拿到第一批fresh数据
↓
controller_init()
```

## 正常每100 ms

```text
FC03
↓
decode
↓
ControllerInput

↓
controller_step()

↓
ControllerOutput

↓
encode
↓
FC16
```

FC16成功：

```text
controller_commit()
```

FC16失败：

```text
不commit
```

如果进入：

```text

```

则：

```text
controller_abort_pending()
```

所以：

> **正常周期的唯一算法计算入口确实是`controller_step()`；但控制器生命周期还需要reset/init/commit等接口。**

# 50. Board算出来的命令最终还不是Plant一定执行的命令

还要保持三层语义：

```text
u_calc
Board本轮算出的candidate

↓ FC16成功

u_commit
最近一次成功发布到RT-LAB的完整命令

↓ RT-LAB安全/执行故障

u_applied
Plant真正采用
```

所以：

```text
Board controller_step
```

只产生：

```text
u_calc
```

工程主程序成功FC16后才变成：

```text
u_commit
```

Plant最后执行的是：

```text
u_applied
```

# 52. 为什么这样以后我们自己就能切换实验

最终Execution-Aware模块编译进同一个Board二进制以后：

```text
RT-LAB Runtime Config
↓
P_COORDINATION_MODE
METHOD_VARIANT
```

就可以切：

```text
Baseline
Assessment
Assessment + Recovery
Full
```

工程开发方不需要：

```text
改源码
重新编译
重新部署
```

# 53. 你最终应该怎样向别人讲整个项目控制逻辑

可以直接这样说：

> 我们最开始已经有一套S1～S15高级应用策略算法，但它主要输出每种策略的状态、告警、指标和建议量，本身还不能直接形成六设备统一闭环。所以LOCAL15阶段没有把15种策略简单串在一起，而是建立了“统一策略判断—请求标准化—按控制域执行”的架构。  
>
> 其中有功类策略又分成主目标和硬约束：S7/S9/S10/S12/S13负责提供当前主有功目标，S1/S4/S11负责约束这个目标，最终形成`effective_dP`；AGC只负责把这个总有功任务分给2PV、2ESS和2EV。S6和S8不是主目标，所以在AGC后对ESS和EV做辅助修正。  
>
> S3属于独立无功域，通过AVC形成总Q需求，再根据当前P占用后的剩余容量分配六路Qref。S5、S14、S15属于模式与安全域，负责并网、孤岛、GFM/GFL、PCC断路器、黑启动和重同步。S14同时还有一个黑启动Pref阶段门控，S15负责孤岛后的ΔV、Δf、Δθ同步判断、Fref修正和重合闸恢复。最后P、Q和模式三个执行域汇合，形成一份完整Board命令。  
>
> 转C时我们不会一次写完整程序，而是C01～C08逐块迁移和逐块与LOCAL15 Golden Reference对比。C01验证原15策略判断，C02验证P目标/约束，C03验证AGC资源分配，C04验证S6/S8，C05验证Q控制，C06验证模式控制，C07验证黑启动，C08验证重同步。每一块PASS后才组合。最终这些不是8个程序，而是作为多个C模块一起被`project15_core`调用，对工程主程序只暴露一个正常周期入口`controller_step()`。工程主程序仍只负责Modbus、安全状态机、配置、编码、FC16和commit。这样既能保持当前15策略项目完整闭环，也能让以后新的P协调算法只替换P协调子模块，而不用重写整套Board程序。

# 54. 最后用一句话把整个体系压缩

> **一套S1～S15负责“判断系统需要做什么”，Normalizer和Mode负责“把不同请求分类并决定谁现在有资格执行”，P Objective/Constraint负责“确定最终总有功任务”，P Coordination负责“决定六资源怎么分担”，S6/S8负责“对具体P命令做辅助和紧急修正”，S3/Q Allocator负责“独立形成六路无功”，S14/S15和Mode执行链负责“决定系统以什么电气模式运行以及如何黑启动、离网、重同步”，最后这些控制域汇合成一份完整Board命令；C01～C08只是把这套完整逻辑分块迁移、逐块证明正确，最终全部组合进同一个BOARD15控制器。**
