# 截止8.1 Build遇到的问题

## 核心判断

现在已经排除：

- 工程缓存污染；
- 顶层三条普通通信线接错；
- Memory没有放在Outport前；
- `BlockReduction`和`OptimizeBlockIOStorage`；
- 跨子系统Goto/From、Data Store；
- 三个SS的OpComm参数不一致；
- RT-LAB环境普遍无法构建并行模型。

因此，当前问题不是"再换一种Delay是否能好"，而是：

> **整体迁移后，SM与SS之间形成了一个RT-LAB认为仍含当前步直接依赖的通信闭环。我们此前只处理了其中肉眼可见的24维普通信号边，却没有确认RT-LAB真正判定为串行的是哪一类通信边。**

日志显示SM已经完成TLC和C代码生成，随后才在`opvalidatemodel → opVerifySendReceiveRTPriority`检查`SM_Master`与`ss_ess`的执行顺序时失败。说明当前直接失败点是**任务分离和通信调度关系**，不是PLL、AGC、Modbus或电气参数无法生成代码。

RT-LAB的工作机制是：计算子系统必须先收到OpComm的全部输入才能开始本步计算；OpComm本身是直接传递块。只有来源于上一时步的状态量，或者经过Delay的量，才能解除当前步依赖。官方也把Memory和Integrator列为状态模块。（[Opal-RT][1]）

---

# 一、为什么此前一直没有找到根因

从最后一次成功Build到当前模型，我们不是只改变了一个变量，而是同时改变了四件事：

1. 从一台EV2扩展为六台变流器；
2. 从一个SS扩展为三个SS；
3. 每个SS从一个低压电气网络变成两个独立电气网络；
4. 新增三条24维`SM → SS`普通通信。

因此，最后成功点和首次失败点之间的改动范围过大。

后面我们不断修改Unit Delay、Memory、优化参数，但这些都只针对第4项。若真正问题来自第2项或第3项，这些修改自然不会有效。

另外，错误目前显示在`ss_ess`，并不说明ESS一定是唯一故障。RT-LAB按照生成顺序检查，遇到第一组不满足调度规则的任务就停止，因此PV和EV可能尚未被完整验证。

# 二、目前真正剩下的四类可能性

## 可能性1：普通24维通信边没有被RT-LAB识别为状态输出

虽然源模型中是：

```text
24维Mux → Memory → Outport
```

但仍存在以下可能：

- RT-LAB分离后的SM模型中，Memory没有位于实际发送块之前；
- 24维聚合向量的处理方式与单个标量不同；
- Memory的编译采样时间或直接传递属性异常；
- 当前源模型和RT-LAB实际Build的文件不是同一个副本。

Memory默认不是直接传递块，但它存在一个"线性化时直接传递输入"的参数；开启该参数会把模块设置为直接传递模式。Unit Delay则明确属于无直接传递的离散状态模块。（[MathWorks][2]）

但由于Memory和Unit Delay都试过仍失败，所以这不是唯一重点。

---

## 可能性2：每个SS包含两个独立Stubline电气网络

这是目前最值得怀疑的结构变化。

成功的官方母模型是：

```text
SM ↔ 3条Stubline ↔ 一个SS中的一台变流器
```

当前每个SS是：

```text
SM ↔ 6条Stubline ↔ 一个SS中的两台彼此独立的变流器
```

生成文件中，`ss_ess`和`ss_pv`分别产生了：

```text
EquivalentModel1
EquivalentModel2
```

说明一个SS中确实存在两个独立的ARTEMiS电气等效网络。这个结构是否能够由RT-LAB正确生成同一组任务通信优先级，目前没有被成功Build证明。

ARTEMiS的Distributed Parameters Line和Stubline本来就是任务解耦元件，依靠线路固有延迟分隔两个电气网络；官方说明该电气信号无需通过OpComm，并要求线路位于RT-LAB模型顶层。Distributed Parameters Line明确无直接传递，文档同时说明其任务解耦步骤也适用于Stubline。（[Opal-RT][3]）

但"一个Stubline网络能Build"不能自动证明"同一对SM/SS之间并列两套独立Stubline网络也能Build"。

---

## 可能性3：某一组复制的Stubline或PMIO拓扑不完全正确

即使模块数量正确，也可能存在：

- PMIOPort编号重复或顺序错位；
- 第二台设备的Stubline两端方向与第一台不同；
- 某条Stubline并未直接连接到对应SM/SS端口；
- 某台设备存在跨过Stubline的物理支路；
- 六条Stubline中有一条Mask参数不同；
- 两套三相差分边界在同一SS中的端口排列与顶层连接不一致。

`Ctrl+D`能够拆成多个SSN网络，只能证明ARTEMiS离线电气网络分组成功，不能证明RT-LAB任务通信优先级也正确。

---

## 可能性4：一个SM同时连接三个SS的通信图产生问题

RT-LAB官方支持一个SM和多个SS，所以"有三个SS"本身不是非法结构。（[Opal-RT][1]）

但当前不是普通的三个独立SS，而是：

```text
每个SS：
SM → 普通24维信号
SM ↔ 多条Stubline物理信号
```

这种"一个SM同时连接三组普通通信＋十八条电气通信"的组合，需要通过最小模型验证，不能仅凭官方简单示例推断。

---

# 三、下一步不能再盲目改模块，应先做一次决定性分流试验

这是目前信息量最高的一次Build。

## 试验A：彻底去掉普通SM→SS通信，只保留18条Stubline

在当前模型的诊断副本中操作，正式模型不动。

另存为：

```text
EV2_OfficialBase_S2_DIAG_NO_SIGNAL
```

### SM内部

删除三个普通Outport：

```text
ev_io_vec
ess_io_vec
pv_io_vec
```

三个Memory输出暂时在SM内部接Terminator。

### 模型顶层

删除：

```text
SM → ss_ev
SM → ss_ess
SM → ss_pv
```

三条普通Simulink信号线。

18条Stubline及全部PMIOPort保持不变。

### 三个SS内部

删除普通Inport：

```text
ev_io_vec
ESS_io_vec
PV_io_vec
```

将OpComm改回官方物理模型使用的零输入OpComm。

在每个SS中放置本地Constant：

```matlab
zeros(24,1)
```

直接连接原来的`[12 12]`Demux，使控制器结构仍可编译。

这次只验证Build，不执行仿真，所以常量数值是否能正常运行暂时不重要。

# 四、试验A结果如何解释

## 结果A1：仍报SM和SS串行

可以确定：

```text
问题与24维向量、Memory、Unit Delay、普通OpComm无关。
```

根因位于：

```text
Stubline / PMIO / 一个SS内两个独立电气网络
```

此时下一步从官方成功的Transformer Stubline母模型重新建立一个极小验证模型：

### 验证P1

```text
一个SM
一个SS
一台设备
3条Stubline
无普通通信
```

这个已知能够Build。

### 验证P2

只复制第二台设备：

```text
一个SM
一个SS
两台设备
6条Stubline
无普通通信
```

Build。

- P2失败：可以确定"一个SS承载两个独立Stubline电气网络"就是结构问题；
- P2成功：说明结构允许，当前模型中某一台设备的复制或连接有误。

### 若P2成功

在当前模型中按组二分：

```text
只保留ss_ev
→ Build

加入ss_ess
→ Build

加入ss_pv
→ Build
```

找到首次失败的资源组后，再在该组中：

```text
只保留第1台
→ Build

加入第2台
→ Build
```

这样最多几次Build就能定位到具体某一台设备或某一组边界。

---

## 结果A2：去掉普通通信后Build成功

可以确定：

```text
18条Stubline和三个双设备SS的电气结构可以被RT-LAB接受。
问题只在普通SM→SS通信和状态识别。
```

此时不再检查电气参数，而执行以下验证。

### 验证S1：在成功的rtdemo2中验证当前状态边界

利用可以Build的官方`rtdemo2`：

1. 保留它原有SM/SS结构；
2. 将SM输出扩展成24维向量；
3. 使用与当前模型完全相同的Memory参数；
4. Build。

结果：

- 成功：RT-LAB可以识别"24维向量＋Memory"，当前模型还存在另一条普通直接依赖；
- 失败：说明当前Memory配置或24维聚合方式不被该验证器接受。

### 验证S2：逐条恢复当前普通通信

在诊断模型中：

```text
先只恢复SM → ss_ess
```

因为当前日志首先在ESS处停止。

若ESS单独成功，再恢复EV和PV；若ESS单独失败，再把24维向量拆成两条12维输出，每台设备一条，并在每条输出前单独设置状态模块。

这能判断问题是否来自：

```text
一个状态块承载两台设备的24维聚合向量
```

而不是继续猜Memory与Unit Delay的区别。

# 五、必须检查RT-LAB分离后的模型，而不是只检查源模型

你此前上传的是生成文件路径清单，不是文件本体。下一步最有价值的文件是：

### 当前失败模型

```text
Opcommon\ev2_officialbase_s2_1_sm_master.slx
Opcommon\ev2_officialbase_s2_1_sm_master.sfp

Opcommon\ev2_officialbase_s2_3_ss_ess.slx
Opcommon\ev2_officialbase_s2_3_ss_ess.sfp
```

### 成功的官方Transformer Stubline模型

重新Build成功后，上传其：

```text
Opcommon\*_sm_*.slx
Opcommon\*_ss_*.slx
对应的*.sfp
```

### 成功的rtdemo2

上传：

```text
Opcommon\*_sm_controller.slx
Opcommon\*_ss_plant.slx
对应的*.sfp
```

这三组文件可以直接比较：

- RT-LAB插入了哪些发送和接收块；
- Memory是否保留在实际发送路径上；
- 当前ESS是否生成了额外通信边；
- 单设备Stubline和双设备Stubline生成的SFP优先级关系有什么差别。

失去最后一次成功的微电网模型并不会阻断分析，因为成功的官方Stubline模型正好可以作为电气通信参考，成功的rtdemo2可以作为普通OpComm参考。

# 六、目前不要再做的事情

暂时不要：

- 再互换Memory和Unit Delay；
- 调整Stubline的R、L、C数值；
- 修改变压器参数；
- 处理PLL路径特殊字符警告；
- 清理To Workspace和Scope；
- 改三个OpComm的采样时间；
- 再新建工程或继续Clean。

这些操作都不能回答"串行依赖究竟来自普通通信还是电气通信"。

## 当前唯一正确的下一步

建立诊断副本，**彻底去掉三条普通SM→SS通信，只保留18条Stubline，然后Build一次**。

这一次结果会把整个问题明确分成：

```text
普通OpComm/状态边界问题
```

或：

```text
Stubline/PMIO/双设备SS结构问题
```

之后的排查才会真正收敛。
