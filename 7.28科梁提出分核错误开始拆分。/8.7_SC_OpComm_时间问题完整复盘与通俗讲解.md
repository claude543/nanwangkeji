# 暑期南网科技项目｜SC / Probe / OpComm / Target 时间问题完整复盘与通俗讲解
**日期：2026-08-07**  
**目的：把本次“SC 时间轴异常—排查—最终转向 Target 侧正式记录”的完整过程讲透。**

---

# 0. 先给最终结论

这次真正的问题并不是 AGC 没有在正确时间执行，也不是 RT-LAB 的 Target 实时计算变慢，更不是模型从 15 s 到 40 s 才真正投入 AGC。

真正的问题是：

> **实时模型在 OP5700 Target 上按正确的仿真时间运行；但是 SC_Console 通过 OpComm / Probe 从 Target 获取数据时，Console 侧的数据采集是异步的，而且会出现漏帧、重复保持旧帧、不同 Acquisition Group 之间时间不一致的问题。**

所以我们一开始在 SC 的 To Workspace 里看到：

- AGC Enable 明明设在 15 s；
- SC 记录里却像是在 40.03 s 才变化；
- 后来统一到一个 Acquisition Group 后，虽然顺序正常了一些，但仍然出现：
  - SC 时间在走；
  - SM Clock 大量重复；
  - Missed data 很大；
  - 60 s 内真正拿到的 Target 新快照只有约 60 份。

最终我们改变了思路：

> **SC 只负责“看”；正式数据不再绕 SC，而是在 SM_Master 内直接把同一组信号分支到 OpWriteFile，由 Target 自己按 Target Simulation Time 写 MAT 文件。**

结果 Target MAT 中：

- Target Simulation Time 与 SM Clock 基本完全一致；
- 记录周期主体为 0.01 s；
- AGC Enable 真实发生在约 15.002 s；
- PV 命令同步开始动作；
- EV 后续在约 17.002 s 首次参与；
- 证明此前 40 s、15.87 s 等异常时刻都是 **SC 数据采集问题，不是控制算法真实执行时刻**。

从此以后，本项目正式采用：

```text
Target / OpWriteFile MAT
    → 正式数据、正式时序、论文时序分析

SC_Console / Scope / Display
    → 在线观察、调试、看趋势
```

这就是本次问题的最终解决方案。

# 1. 先把几个最容易混淆的概念彻底分开

## 1.1 什么是 Target？

在我们的 RT-LAB / OP5700 系统里，可以简单理解成两台“世界”：

### Windows 主机 / Host / Console 世界

就是你平时操作的电脑：

- RT-LAB 软件界面；
- MATLAB / Simulink；
- SC_Console；
- Scope；
- Display；
- To Workspace；
- 你看到的监控界面。

### Target 世界

就是 OP5700 实时机内部真正执行实时模型的 Linux 实时环境。

我们的：

- `SM_Master`
- `SS_Slave`
- `SS_Slave2`
- `SS_Slave3`

这些实时任务最终是在 **Target CPU** 上执行的。

所以以后看到“Target 侧”，可以直接理解为：

> **OP5700 实时机内部真正算模型的那一侧。**

---

## 1.2 SC_Console 是什么？

`SC_Console` 不是承担电气实时计算的 SM/SS。

它更像一个：

> **观察室 / 仪表盘 / 上位机显示端。**

它主要负责：

- Scope；
- Display；
- To Workspace；
- 在线监视；
- 从 Target 取得需要观察的数据。

关键点：

> **SC 和 Target 不是同一个实时计算时基。**

SC 可以向 Target 请求数据，但它不等于 Target 每一个实时计算步都能无损、严格同步地传到 SC。

---

## 1.3 什么是 OpComm？

可以把 `OpComm` 理解成 RT-LAB 各任务之间的数据接口。

在我们这次问题中，最关键的是：

```text
SM_Master 中的信号
    ↓
SM Outport
    ↓
顶层任务通信
    ↓
SC Inport
    ↓
SC 内的 OpComm
    ↓
Scope / Display / To Workspace
```

所以 SC 里面的 OpComm 做的是：

> **把 Target 那边的实时信号“取到”Console 侧。**

它不是 AGC 算法的一部分，也不是电气模型的一部分。

调整 SC 的 OpComm 参数，主要影响的是：

- SC 多久尝试获得一次数据；
- 它属于哪个 Acquisition Group；
- 是否同步；
- 是否插值；
- 是否输出漏数据诊断。

它**不会改变 Target 上 SM/SS 的 100 μs 实时计算步长**。

---

## 1.4 Probe / Probe Control 到底是什么？

这次最容易理解错的就是 Probe。

Probe Control 可以理解为：

> **RT-LAB 对“Target 数据采集并送往 Console”这件事的采样控制器。**

它不是探头硬件，也不是模型里的电压电流测量探头。

它控制的是：

- 一个 Acquisition Group 以什么节奏取数据；
- 每次取多少个点；
- 是否重复采样；
- Console 是否对某个 Group 采用 blocking / 同步等待方式；
- 是否触发采集。

所以：

```text
Target 实时计算
        ↓
Probe 决定“怎么抓数据”
        ↓
OpComm 决定 SC 从哪个 Group 接收
        ↓
SC Scope / To Workspace
```

这是比较通俗的理解。

# 2. Hz、采样周期、计算时刻到底是什么关系？

最简单公式：

```text
频率 Hz = 1 / 周期 s
```

---

## 2.1 Target 基本步长 100 μs 是什么意思？

我们的实时模型：

```text
Ts = 100 μs
   = 0.0001 s
```

所以：

```text
1 / 0.0001
= 10000 Hz
= 10 kHz
```

意思是：

> Target 每秒要完成 10000 个基本实时步。

也就是每 100 μs：

- SM 算一次；
- SS 算一次；
- 实时电气网络推进一个步长。

这叫 **Target 基本计算频率 10 kHz**。

它和 SC 每秒显示多少点不是同一回事。

---

## 2.2 0.01 s 是多少 Hz？

```text
0.01 s = 10 ms
1 / 0.01 = 100 Hz
```

所以我们后来想要正式记录：

```text
每 0.01 s 记录一个点
```

就是：

```text
100 Hz 数据记录
```

注意：

> Target 仍然 10 kHz 计算，只是我们每 100 个 Target 步取一个点保存。

---

## 2.3 AGC 的 1 s 又是什么？

我们的基础 AGC：

```text
Ts_agc = 1 s
```

也就是：

```text
1 Hz
```

这不代表整个模型 1 s 才算一次。

真实关系是：

```text
电气模型：100 μs = 10 kHz
正式记录：0.01 s = 100 Hz
AGC更新：1 s = 1 Hz
```

三个频率是三件不同的事。

可以想象成：

```text
Target：
|.|.|.|.|.|.|.|.|.|.|.|.|.|.|.|.|.|...  每100 μs算一次

记录：
|---------|---------|---------|---------|... 每10 ms记一次

AGC：
|----------------------------------------|... 每1 s更新一次
```

---

# 3. 这个问题最开始是怎么暴露出来的？

本地 AGC 闭环接好以后，我们做了一个非常明确的测试：

```text
PCC 基线约 -120 kW
Ptarget = -100 kW

AGC Enable：
15 s 时 0 → 1

Ts_AGC：
1 s
```

从物理结果看：

- PCC 确实从约 `-120 kW` 调到了 `-100 kW`；
- PV / EV 实测功率确实发生了变化；
- 没有 NaN / Inf；
- 实时模型没有 Overrun。

所以“控制闭环本身”看起来是工作的。

但问题出在 SC 正式记录。

我们发现 SC 里某组 AGC 命令 / Enable 的 To Workspace 数据显示：

> 明明模型里 Enable 是 15 s Step，记录里却像在 **40.03 s** 左右才发生变化。

这显然不合理。

如果真的是算法 40 s 才执行，那么：

- 15 s 的 Step 没有执行；
- PCC 不应该在 15 s 左右开始响应。

但实际 PCC / Pmeas 的变化又明显更早。

因此矛盾出现了：

```text
模型设定：
Enable = 15 s

物理响应：
大约15 s后已经开始变化

某些SC记录：
像40 s才变化
```

所以第一判断就是：

> **必须区分“真实控制时间”与“SC看到这个事件的时间”。**

---

# 4. 第一轮怀疑：是不是 To Workspace 自己的问题？

我们先怀疑：

- To Workspace 格式；
- 插值；
- Decimation；
- 各 Scope / To Workspace 的连接方式。

于是做了几件事：

1. 统一 To Workspace 格式为 `Structure With Time`；
2. 关闭 Interpolation；
3. 避免不必要的 Demux→Mux 再重组；
4. 检查不同记录的 sample time / decimation。

但结果：

> **40 s 类的时间错位没有根治。**

这说明：

> 问题不只是 MATLAB To Workspace 怎么存，而是在 To Workspace 之前，SC 拿到的数据本身就可能不是连续的新 Target 数据。

---

# 5. 第二轮排除：是不是 RT-LAB 实时执行速度不对？

我们又确认 RT-LAB：

```text
Execution mode = Software synchronized
Time factor = 1
```

如果 Time factor 不是 1，或者执行模式本身不是正常实时同步，确实可能出现：

```text
仿真时间
≠
墙钟时间
```

但当前配置是正确的。

同时 Monitoring 也没有说明 Target 本身大幅变慢。

所以进一步排除：

> **不是 Target 整体从“1 秒仿真时间”跑成了“2 秒、3 秒墙钟时间”。**

问题继续锁定在：

```text
Target → SC 的数据采集路径
```

---

# 6. 第三个关键发现：我们之前在比较不同 Acquisition Group

最开始 SC 中不同信号不是全部从同一个 OpComm / 同一个 Acquisition Group 来的。

例如：

- AGC 命令可能来自一个 Group；
- Pmeas 来自另一个 Group；
- PCC 又可能来自其他通信链；
- 各自 Sample time 也不完全相同。

而 RT-LAB Console acquisition 有一个关键特性：

> **不同 Acquisition Group 之间不能天然当成同一个严格同步的时间轴。**

也就是说，即使两个 Scope 都显示：

```text
SC time = 20 s
```

它们底层对应的 Target 快照时间可能不同。

这解释了为什么：

- 命令看起来晚；
- Pmeas 看起来早；
- PCC 又是另一个时间；
- 跨图比较会得到错误的“控制延迟”。

---

# 7. 为了排除“跨 Group 错位”，我们做了统一23维观测链

我们在 `SM_Master` 里建立：

```text
AGC_CORE_MUX23
```

把需要比较的关键量一次性打包。

最终固定顺序：

```text
1   SM Clock
2   Ptarget
3   Ppcc
4   Enable
5   Status
6   dP
7   Remain

8   PV1_cmd
9   PV2_cmd
10  ESS1_cmd
11  ESS2_cmd
12  EV1_cmd
13  EV2_cmd

14  PV1_Pmeas
15  PV2_Pmeas
16  ESS1_Pmeas
17  ESS2_Pmeas
18  EV1_Pmeas
19  EV2_Pmeas

20  PVmax1
21  PVmax2
22  SOC1
23  SOC2
```

然后整个 23 维向量：

```text
AGC_CORE_MUX23
    ↓
SM Outport
    ↓
SC Inport
    ↓
一个新的 SC OpComm
    ↓
同一个 Acquisition Group 9
    ↓
agc_full_log + Demux23 + Scope
```

这样做的意义是：

> **以后这23个量来自同一批 Target 数据，不再拿不同 Group 的数据硬比较。**

同时 Scope 也全部只从这个 Demux23 接。

---

# 8. OpComm 我们到底改了什么？为什么？

新建 / 调整后的 SC OpComm 主要采用：

```text
Number of inports        = 1
Acquisition Group        = 9
Subsystem sample time    = 0.01
Synchronization          = ON
Interpolation            = OFF
Threshold                = 1.0
Missed data output       = ON
Samples/sec output       = ON
```

下面逐项理解。

---

## 8.1 Number of inports = 1

因为我们已经把 23 路信号先在 SM 中合成一个 23 维向量。

所以 OpComm 不需要 23 个单独入口，而是：

```text
1个输入
里面装23个元素
```

这样最干净。

---

## 8.2 Acquisition Group = 9

这是本次新统一观测链专用 Group。

目的：

> 让 Ptarget、Pcc、Enable、命令、Pmeas、PVmax、SOC 全部属于同一个采集组。

这样至少消除了“Group A 的20 s”和“Group B 的20 s”其实不是同一 Target 快照的问题。

---

## 8.3 Subsystem sample time = 0.01 s

这表示 SC 这条观测链希望按：

```text
10 ms
= 0.01 s
= 100 Hz
```

处理数据。

它不是把 Target 模型改成 10 ms。

Target 仍然是：

```text
100 μs = 10 kHz
```

只是 Console 观测链目标是 100 Hz。

---

## 8.4 Synchronization = ON

目的：

> 尽可能让该 SC acquisition 与指定采集组按同步规则工作，而不是完全自由异步地取最新值。

但注意：

> Synchronization ON 并不能保证 Console 永远无漏帧。

后面的实际结果就证明，SC acquisition 仍会出现大量 Missed data。

---

## 8.5 Interpolation = OFF

为什么关掉插值？

因为我们做的是 **控制时序诊断**。

如果某个 Target 新帧没到，插值可能会在两个值之间造出“看起来很平滑”的中间数据。

这对画趋势可能好看，但对判断：

```text
Enable到底哪一刻变1？
PV命令哪一刻第一次更新？
```

反而会误导。

所以：

> 宁可看到保持旧值，也不希望系统给我们“编”一个中间值。

---

## 8.6 Missed data = ON

这个非常重要。

它直接告诉我们：

> Console acquisition 过程中到底漏了多少数据。

后来它给出了很大的值：

```text
Missed data max ≈ 60931
```

这成为证明 SC 不是可信正式时基的重要证据。

---

## 8.7 Samples/sec = ON

这个输出用来观察采集吞吐。

我们看到大约：

```text
Samples/sec ≈ 109
```

但是这里有一个非常重要的认识：

> **Samples/sec 显示有数据输出，不等于每个点都是新的 Target 独立快照。**

因为 SM Clock 后来证明：

- SC 有很多输出点；
- 但大量点的 SM Clock 完全相同；
- 本质是 Console 多次输出 / 保持了同一份 Target 快照。

---

# 9. Probe Control 我们改了什么？为什么？

为了让 Group 9 尽可能按我们希望的 100 Hz 方式工作，我们又检查 / 调整了 Probe Control。

关键设置：

```text
Basic step                   = 0.100 ms
Group 9 Decimation           = 100
Number of samples per signal = 1
Trigger                      = OFF
Trigger offset               = 0
Repetitive sampling          = ON
Re-arm                       = 0
Console blocks on group      = 9
Blocking / Block             = ON
Output                       = Last value
```

---

## 9.1 Basic step = 0.100 ms

这就是：

```text
0.100 ms = 100 μs
```

对应 Target 基本步长。

所以 Probe 的 Decimation 可以理解成：

```text
基础步长 × 抽取倍数
```

---

## 9.2 Decimation = 100

```text
100 μs × 100
= 10000 μs
= 10 ms
= 0.01 s
```

所以理论上 Group 9 的采集节奏是：

```text
100 Hz
```

这和 OpComm 的：

```text
Subsystem sample time = 0.01
```

一致。

我们的意图是：

```text
Target 10 kHz计算
↓ 每100步取一次
Probe 100 Hz采集
↓
OpComm 100 Hz接收
↓
SC 100 Hz记录
```

---

## 9.3 Number of samples per signal = 1

表示每一个采集动作只要当前这一份样本，而不是一次打一个很大的批次。

这样做是为了在线连续观察。

---

## 9.4 Repetitive sampling = ON

表示采集不是只触发一次就结束，而是：

> 一直重复进行。

否则我们只能拿到一帧 / 一批，不适合连续 Scope。

---

## 9.5 Trigger = OFF

我们不需要外部事件触发。

我们希望：

> 一启动就持续采集。

所以 Trigger 关闭。

---

## 9.6 Console blocks on group = 9 / Block = ON

这一步是为了让 Console 对 Group 9 采用 blocking / 同步等待方式。

通俗理解：

> Console 不要随便从不同组各拿一个“最新值”就往前跑，而是尽量以 Group 9 作为同步基准。

这能改善不同信号之间的对齐，但还是不能保证网络 / Console acquisition 永不漏帧。

另外我们当时发现：

> `Console blocks on group = 9` 在其他 Group 页签也会显示 9。

这不是每个 Group 都被改成 9，而是它是一个 Console 全局阻塞组选择。

---

## 9.7 Output = Last value

意思是：

> 如果当前没有新的完整样本，就输出最近一次拿到的值。

这对在线 Scope 很实用，因为画面不会断。

但它也有副作用：

> 如果新 Target 帧没及时到，SC 会重复同一个旧值。

后来 SM Clock 大量重复，就是这个现象的重要表现。

---

# 10. 为什么统一 Group + Probe 后，还是没有真正解决“正式时序”问题？

统一23维 + Group9 后，情况确实比一开始好。

例如我们看到的顺序已经合理：

```text
Enable
→ PV动作
→ 后续EV动作
```

不再出现最离谱的“Enable 40 s 才发生”。

但新的诊断数据显示：

```text
agc_full_log：约6001个SC点
SC时间：0 → 60 s
SM Clock：并没有每0.01 s都更新
```

其中一轮甚至只有大约：

```text
61个不同的 SM Clock 快照
```

而 SC 有：

```text
约6001个记录点
```

这说明：

> SC 很多时候只是在重复保存最近一次 Target 快照。

并且：

```text
Missed data max ≈ 60931
Samples/sec ≈ 109
```

这就形成完整证据链：

```text
SC时间一直在走
↓
但是SM Clock经常不走
↓
说明SC当前这几个点对应的是同一Target旧快照
↓
因此SC时间不能被当成事件真实发生时间
```

# 11. SM Clock 为什么这么关键？

这是整个排查过程中最重要的诊断信号之一。

## 11.1 SM Clock 是什么？

我们在 `SM_Master` 中放入 Simulink `Clock`。

这个 Clock 反映：

> **SM 模型自己认为当前的仿真时间是多少。**

由于 SM 在 Target 上实时执行，所以可以把它理解为：

```text
Target模型内部时间戳
```

---

## 11.2 在 SC 里记录 SM Clock 能说明什么？

假设 SC 记录：

```text
SC time     SM Clock
10.00       9.12
10.01       9.12
10.02       9.12
10.03       9.12
...
```

这说明：

> SC 自己的记录时间在前进，但它一直拿着 Target 在 9.12 s 时的同一份旧数据。

所以只看 SC time 会误以为：

> 某个值在 10.03 s 发生。

但实际上这个值可能是 Target 9.12 s 的快照。

---

## 11.3 为什么后来 Target MAT 中 SM Clock 又很重要？

OpWriteFile 会自动写：

```text
第1行：Target Simulation Time
```

而我们23维向量第1个信号本身又是：

```text
SM Clock
```

所以 Target MAT 里同时有：

```text
Target自动时间
SM Clock
```

两者基本完全一致，就说明：

> **SM内部时间、Target记录时间是同一个真实时间轴。**

这相当于我们自己做了一次“时钟交叉验证”。

---

# 12. 为什么最后要彻底转向 Target 侧记录？

到这里，我们已经证明：

1. Target 实时模型本身正常；
2. SC 同 Group 后内容映射也正常；
3. 但 SC acquisition 仍然会漏帧、保持旧帧；
4. 继续花大量时间调 Probe，最多让“看图”更舒服；
5. 但我们以后论文还要分析：
   - 命令动作时刻；
   - Pmeas响应时刻；
   - PCC响应时刻；
   - 心跳超时；
   - 板端延迟；
   - 恢复瞬间。

这类问题要求：

> **时间戳必须可信。**

所以我们改变方向：

> 不再问“怎样让 SC 变成论文级记录器”，而是直接在 Target 上记录。

这是本次最关键的思路转变。

---

# 13. 新方向：AGC_CORE_MUX23 直接分支到 OpWriteFile

最终结构：

```text
                 ┌→ SM Outport → SC Inport → OpComm → Scope/Display
AGC_CORE_MUX23 ──┤
                 └→ OpWriteFile → Target本地MAT文件
```

这里非常关键：

> **SC显示支路和正式记录支路来自同一个23维向量。**

所以内容定义完全一致。

但正式记录支路：

```text
不经过SC
不经过SC OpComm
不经过不同Acquisition Group
不经过Console To Workspace
```

而是：

```text
SM内部信号
→ OpWriteFile
→ Target磁盘
```

这就从根本上绕过了本次问题源。

---

# 14. 为什么 OpWriteFile 前面不加 Memory？

我们一开始对跨任务通信比较谨慎，经常在普通通信 Outport 前加 Memory。

但这里：

```text
AGC_CORE_MUX23 → OpWriteFile
```

并不是跨任务闭环反馈。

它只是：

> **把当前 Target 信号写文件。**

所以没有必要为了记录再增加一个 Memory。

否则反而会人为增加一个步长延迟。

因此最终：

```text
AGC_CORE_MUX23
→ 直接分支
→ OpWriteFile
```

# 15. OpWriteFile 最终参数及每个参数为什么这样设置

最终参数：

```text

Real Time Path               = ./
Non Real Time Path           = .\

Simulation Mode              = OFF

Nb. Samples Per Signal       = 1000

```

---

## 15.1 Decimation = 100

Target：

```text
Ts = 100 μs
```

所以：

```text
100 × 100 μs
= 10 ms
= 0.01 s
= 100 Hz
```

这正是我们想要的正式记录频率。

---

## 15.2 为什么不是每100 μs都记录？

如果完全按10 kHz记录：

```text
60 s × 10000点/s
= 600000点
```

23个信号再加时间，数据量会很大。

而我们目前要分析的是：

- AGC 1 s更新；
- PCC几秒级调节；
- 设备功率响应；
- 后续Modbus 1 s级周期。

100 Hz 已经足够细。

---

## 15.3 Variable name = agc_target_data

这样 MATLAB `load` 后直接得到：

```matlab
agc_target_data
```

便于统一脚本分析。

---

## 15.4 Acquisition Group = 26

OpWriteFile 使用的是专用文件采集 Group 范围。

我们选一个未占用的：

```text
26
```

它和 SC Group9 不是同一用途。

---

## 15.5 Number of samples = 1000

OpWriteFile 内部不是每来一个点就立刻单独写一次磁盘。

它会使用缓冲。

1000 个样本作为一批，是一个比较稳妥的缓冲长度。

---

## 15.6 Buffer = 262144 bytes

我们有：

```text
23路输入
+ 1路自动Target时间
= 24路double
```

一批1000点最少大约：

```text
24 × 1000 × 8
= 192000 bytes
```

所以设置：

```text
262144 bytes
```

足够容纳。

---

## 15.7 File size limit = 5 MB

60 s、100 Hz、24行数据，量级远小于5 MB。

所以：

```text
5000000
```

留有余量。

---

## 15.8 Simulation Mode = OFF

我们要的是实时 Target 记录。

如果开启会采用更偏向“保证写文件、不丢数据”的非实时等待行为，可能影响实时性。

因此：

```text
Simulation Mode = OFF
```

优先保证实时任务。

# 16. 为什么加 OpWriteFile 后必须重新 Build？

因为我们不是只改一个 Scope。

我们实际修改了 `SM_Master` 的实时模型：

```text
新增 OpWriteFile
新增 Target 侧记录连接
```

这属于实时任务代码结构变化。

所以必须：

```text
Ctrl+D
→ Build / Rebuild
→ Load
→ Execute
```

# 17. 为什么 Reset 后 MAT 文件才回到 Windows？

OpWriteFile 的数据首先写在 Target。

所以：

```text
Execute
→ Target持续记录
→ Reset
→ 结束本轮Target记录并传回Host
```

因此最后的 Reset 不只是“停模型”，还承担：

> **让本轮文件完成并回传。**

## 18.1 为什么不是60 s，而是约110 s？

因为虽然 Simulink 中曾设置 Stop Time=60 s，但 RT-LAB Target 实际保持 Execute，直到约110 s才 Reset。


这说明：

> 正式试验要以 RT-LAB Target 的实际 Execute / Stop / Reset 为准。

## 18.2 Target Time 和 SM Clock 基本完全一致

本轮记录中：

```text
Target Simulation Time
≈

```

二者差异接近浮点数计算误差量级。

这说明：

> Target自动记录的时间和SM模型内部时间是一致的。

这是我们第一次真正拿到可信的同一时基数据。

## 18.3 记录主体周期约0.01 s



因为真实记录在缓冲边界附近可能存在轻微非严格等间隔，直接使用真实 Target 时间最稳妥。

## 18.5 PV和EV真实动作时刻

# 19. Target记录还顺便暴露了真正的AGC算法问题

Target侧正式记录解决了“时间真假”的问题以后，我们反而第一次清楚看见：

> **基础AGC在长时间运行中存在资源对冲 / 历史命令漂移。**

也就是：

```text
PV越来越往正方向增加
同时
EV越来越往负方向增加充电
```

但二者互相抵消，使：

```text
PCC仍然维持在约 -100 kW
```

这不是 SC 假象。

这是 Target 真值。

因此项目的判断变成：

```text
SC时间问题
→ 已解决，不是算法问题

PV/EV长期对冲
→ 是真实算法问题
→ 恰好成为后续论文改进方向
```

这两个问题必须严格区分。

# 20. 为什么“转到 Target 侧记录”是更好的长期架构？

因为后面 V4 / V5 会越来越依赖严格时序。

例如：

```text
板端命令到达时间
CMD_SEQ变化时间
BOARD_HEARTBEAT
RTLAB_HEARTBEAT
EXT_AGC_ENABLE
命令→Pmeas响应
通信中断→撤销
通信恢复→重新接管
```

如果继续靠 SC 不同 acquisition group 比时间：

> 很容易把 Console 延迟误认为控制延迟。

而 Target记录：

```text
控制在Target发生
↓
记录也在Target发生
```

少了一整个异步传输层。

所以最终架构很清楚：

```text
Target：
负责实时模型 + 正式记录

SC：
负责在线观察

板端CSV：
负责板端软件自己的单调时钟和通信周期记录
```

后续需要比较板端和Target时，再通过：

- CMD_SEQ；
- 周期序号；
- 明确事件；
- 必要时同步标志；

进行对齐，而不是简单拿SC墙钟硬比较。

# 22. 本次以后必须牢牢记住的10条结论

1. `Ts=100 μs` 是 Target 实时模型基本步长，即 `10 kHz`。
2. `0.01 s` 是正式记录周期，即 `100 Hz`，不是模型计算步长。
3. `Ts_AGC=1 s` 是 AGC更新周期，即 `1 Hz`。
4. SC_Console 的时间不能天然等同于 Target真实事件时间。
5. 不同 Acquisition Group 的信号不要直接做精确时延比较。
6. Probe Control 管的是 Console acquisition，不是电气模型控制周期。
7. OpComm 的 sample time / group 主要影响 SC获取与显示，不会把Target的100 μs模型改成10 ms。
8. SM Clock 是判断 SC 当前数据究竟来自哪个Target时刻的关键诊断信号。
9. SC time前进而SM Clock重复，说明SC在重复旧Target快照。
10. 正式论文 / 验收时序统一使用 Target OpWriteFile MAT；SC只做实时观察。

# 24. 最后的理解方式

把整个系统想成“高速工厂 + 监控室”：

```text
Target
= 工厂生产线
每100 μs真正生产一次结果

Probe / OpComm / SC
= 摄像头 + 传输线路 + 监控室
```

如果摄像头掉帧：

> 工厂并没有停。

如果监控室同一画面重复了100次：

> 也不能说工厂在那一刻重复生产了100次。

`SM Clock` 就像每一个产品上打的“工厂时间戳”。

`OpWriteFile` 则相当于：

> 直接在工厂内部的质量记录仪上记数据。

所以最后我们选择：

```text
监控室用来观察
工厂内部记录用来下正式结论
```

这就是本次问题从发现、误判风险、逐层排除，到最终彻底解决的完整逻辑。
