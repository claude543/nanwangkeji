## 1. 15 s：第一次AGC动作，只应该调PV

我们设置的是：

```text
Ptarget = -100 kW
15 s前PCC ≈ -120 kW
```

所以15 s第一次AGC计算：

```text
[
dP=P_{target}-P_{PCC}
=-100-(-120)
=+20\text{ kW}
]
```

代码中只要：

```text
dP > 0
```

资源调用顺序就是：

```text
PV增加
→ ESS放电
→ EV减少充电
```

代码确实先执行`alloc_up(Ppv,...)`，只有PV剩余裕度不够、`remain`还存在时，才继续调用ESS和EV。

而15 s时：

```text
PV1_MAX = 65 kW
PV2_MAX = 65 kW

当前PV初始 = 0
总PV向上裕度 = 130 kW
```

只需要+20 kW。

因此理论上第一次分配：

```text
PV1 ≈ +10 kW
PV2 ≈ +10 kW

ESS = 0
EV继续保持-60 kW
```

**所以EV在15 s不应该动作。**

你的波形也是这样：

```text
约15 s：PV开始增加
约20 s：EV才开始变得更负
```

这与算法完全一致。

## 2. 那为什么20 s左右EV又开始增加充电？

关键就在15～20 s这一段。

PV命令增加后：

```text
PV实际出力开始增加
↓
PCC从约-120 kW向-100 kW上升
```

而AGC不是计算一次就结束，它每：

```text
Ts_AGC = 1 s
```

重新读取一次PCC，再重新计算：

```text
[
dP=P_{target}-P_{PCC}
]
```

并且它内部的：

```text
Ppv
Pess
Pev
```

都是**persistent历史状态**，每次是在上一次命令基础上继续修改，而不是重新从零计算。

所以过程大致是：

```text
15 s：
PCC≈-120
dP≈+20
→ 增加PV

16 s：
PV还没有完全响应
PCC可能仍低于-100
→ dP仍为正
→ PV继续增加一点

17 s、18 s……
→ PCC继续向-100靠近
```

由于设备本身有动态响应，同时还有Droop、Supervisor和低层控制，PV实际Pmeas并不是瞬间严格等于Pref。

所以有可能发生：

```text
PV持续增加
↓
真实PCC最终超过-100 kW
```

例如某个AGC时刻：

```text
PCC = -97 kW
```

那么：

```text
[
dP=-100-(-97)=-3\text{ kW}
]
```

**dP就从正数变成负数了。**

---

## 3. 一旦dP变负，算法第一个调的就是EV

这是最重要的一点。

代码中：

```text
dP < 0
```

资源调用顺序不是"先把刚才增加的PV减回来"，而是：

```text
EV增加充电
→ ESS充电
→ PV降低
```

代码首先：

```text
alloc_up(Pev,...)
```

随后才是ESS，最后才会：

```text
alloc_down(Ppv,...)
```

也就是说：

> **当PV前期调节使PCC已经略微过头时，算法不会马上降低PV，而是优先把EV充电功率增加，用EV去抵消前面的PV增加。**

因此20 s左右出现：

```text
EV：
-0.60
→ -0.62
→ -0.65……
```

是完全符合算法的。

## 4. 所以最终为什么PV和EV都偏离初值？

这不是在**同一个AGC周期**里同时调PV和EV。

而是：

```text
第一阶段 dP>0：
PV上调
EV不动

        ↓

PCC逐渐接近并越过目标

        ↓

第二阶段 dP<0：
PV已经保持着前面累积出的较高命令
EV开始增加充电进行反向修正
```

由于AGC命令具有历史记忆：

```text
Ppv、Pev都是persistent状态
```

后面进入`dP<0`时，并不会自动把PV恢复到0。

而负方向资源顺序又明确规定：

```text
EV
→ ESS
→ PV
```

所以只要EV的调节裕度足够：

```text
remain在EV阶段已经被分完
```

后面的：

```text
ESS
PV降低
```

根本不会执行。

这就形成了最后看到的状态：

```text
PV：已经被前面的正向调节抬高

EV：后来又因为反向调节增加充电

ESS：始终没有机会参与
```

这就是为什么最终：

```text
PV1、PV2 > 0
EV1、EV2 < -0.6
ESS1、ESS2 ≈ 0
```

## 5. 为什么ESS始终没有参与？

这个也可以直接由算法解释。

### 正向阶段

```text
dP > 0
```

先用PV。

PV有：

```text
130 kW
```

可调裕度，远大于我们的几十kW误差。

因此：

```text
PV已经把remain分完
→ ESS没有机会动作
```

### 反向阶段

```text
dP < 0
```

先用EV。

两台EV从60 kW充电还可以继续增加到100 kW：

```text
EV1剩余40 kW
EV2剩余40 kW
总向下调节裕度≈80 kW
```

反向误差也没有大到超过80 kW。

所以：

```text
EV已经把remain分完
→ ESS仍然没有机会动作
```

因此SOC一直：

```text
SOC1 = 0.6
SOC2 = 0.6
```

完全符合算法。

## 6. AGC虽然没接Pmeas，为什么还能闭环？

现在把这个闭环彻底串起来：

```text
AGC只读取：
Ptarget
PCC
PVmax
SOC
        ↓
根据PCC误差修改内部历史命令
        ↓
六路Pref
        ↓
六台逆变器真实响应
        ↓
六台真实Pmeas发生变化
        ↓
整个微网的净功率发生变化
        ↓
PCC测量发生变化
        ↓
下一次AGC重新读取PCC
```

所以：

```text
Pmeas虽然没有直接进入AGC
```

但：

```text
Pmeas的物理效果
→ 已经包含在PCC里
→ AGC下一周期能看到
```

这就是一个典型的**总量反馈闭环**。

## 7. 但是这里恰恰暴露了一个很重要的问题

AGC知道的是：

```text
"我上一次给了什么命令"
+
"现在总PCC是多少"
```

它不知道：

```text
PV1真实执行了多少
PV2真实执行了多少
ESS真实执行了多少
EV真实执行了多少
```

所以它内部认为的资源状态：

```text
Ppv
Pess
Pev
```

其实是：

> **AGC自己的历史命令状态**

而不是：

> **设备当前真实执行状态。**

这在本次运行里已经非常明显。

最终记录：

```text
AGC内部命令：
PV1 ≈ 0.155
PV2 ≈ 0.155
EV1 ≈ -0.657
EV2 ≈ -0.657
```

而真实Pmeas：

```text
PV1 ≈ +0.330
PV2 ≈ +0.331
EV1 ≈ -0.828
EV2 ≈ -0.827
```

单台设备差得不少。

但是六路实际功率之和：

```text
≈ -99.32 kW
```

又恰好等于PCC：

```text
≈ -99.30 kW
```

所以AGC看到：

```text
总PCC已经正确
```

就停止调节了。

它并不知道：

```text
内部认为PV≈15.5 kW
实际PV≈33 kW

内部认为EV≈-65.7 kW
实际EV≈-82.7 kW
```

这是非常值得注意的现象。

## 8. 这也解释了为什么20 s以后出现PV和EV"对冲"

从控制效果看：

```text
PV增加发电
        ↑
        │ 相互抵消
        ↓
EV增加充电
```

最后：

```text
PV实际总出力 ≈ +66 kW
EV实际总负荷 ≈ -165 kW

净值 ≈ -99 kW
```

所以PCC目标实现了。

但实现方法包含明显的：

> **资源对冲。**

而原因并不是PV能力不足，而是：

```text
AGC按照总PCC闭环反复增量调节
+
不读取设备实际执行状态
+
内部命令状态和真实Pmeas之间存在偏差
+
dP变号以后资源优先级又改成EV优先
```

最终就形成：

```text
先增加PV
→ PCC过目标
→ 再增加EV充电反向修正
```

这和我们以前通信延时试验中看到的"资源对冲"机制其实是同一种基本现象，只不过这次没有通信异常，来源更多是**设备实际状态与AGC内部命令状态的差异及动态响应**。之前的算法资料也明确规定了这种正、负误差下不同的资源优先顺序。

我们真正要找的是：

```text
15 s附近：
dP > 0
→ PV开始增加

约20 s附近：
dP从正变负
→ EV开始增加充电
```

**若这个表正好显示dP在EV开始变化前后由正变负，那么PV先动、EV后动的整个机制就被完整实测证明了。**
