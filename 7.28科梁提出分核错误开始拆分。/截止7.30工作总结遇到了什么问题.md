# 截止7.30工作总结：遇到了什么问题

## 阶段结论

从上一轮阶段总结到现在，我们完成了三件关键工作：

1. **证明了任务级分核模型能够在 Simulink 中建立，并能基本保持原模型电气特性。**
2. **找到了普通 Stubline 导致模型不等效的原因，并验证了"迁移变压器漏阻抗"这一改进办法。**
3. **当前卡在 RT-LAB 的任务并行识别阶段：离线等效已基本通过，但 RT-LAB 仍将 SM 与三个 SS 判断为串行，尚未完成真正四核 Build。**

当前最重要的判断是：

> 现有 `SM ＋ SS_PV ＋ SS_ESS ＋ SS_EV` 和 OpComm 控制接口可以保留；下一步不再继续盲目增加 Memory 或修改普通信号，而应按 OPAL-RT 官方的变压器 Stubline 结构，先重做一台设备的两任务原型，确认 RT-LAB 能够真正识别为并行任务。

---

## 一、上一轮总结时处于什么状态

上一轮已经确认：

- 六逆变器原模型在 100 μs 步长下约需 970～981 μs，无法严格实时。
- 三逆变器原 SSN 模型设置 `Cores=4` 和 `Cores=1` 时均约 700 μs。
- 这说明 4 个核虽然在界面中已经分配给 `sm_circuit`，但主要计算没有得到有效并行。
- 后续决定放弃继续调整原 SSN 核数，改用真正的任务级分核：

```
1 个 SM
＋ 3 个 SS
＋ 1 个 SC
```

RT-LAB 通用规则要求一个 SM 和多个 SS 分别承担实时计算任务，而 SC 只承担上位机显示；实时子系统之间的普通输入需要通过 OpComm，任务要依靠状态信号避免同一步互相等待。

---

## 二、第一版任务级分核做了什么

最初按照原电气拓扑，建立了：

```
sm_circuit
├─ PV1
├─ PCC、电网、负荷
└─ 公共控制

ss_feeder1
├─ ESS1
├─ ESS1—EV1 之间的线路
└─ EV1

ss_pv2_ess2
├─ PV2
└─ ESS2

ss_ev2
└─ EV2
```

普通控制信号被整理成控制向量：

```
SM 中的 Mux
→ 顶层信号线
→ SS 中的 OpComm
→ Demux
→ 设备控制输入
```

电气三相物理连接则使用顶层 ARTEMiS Stubline。因为普通 OpComm 不能替代三相电气网络的电压、电流和节点约束，跨 SM/SS 的电气网络需要 ARTEMiS 解耦元件。

### 第一版结构结果

`Ctrl+D` 成功，原来的 39 个开关被拆为：

```
sm_circuit：9 个开关
ss_feeder1：12 个开关
ss_pv2_ess2：6 ＋ 6 个开关
ss_ev2：6 个开关
```

说明：

> 电气网络已经从一个 39 开关的大组，成功拆成多个较小网络。

这证明 SM/SS 结构、顶层电气端口和 OpComm 控制向量的总体思路是可行的。

## 三、第一种 Stubline 方案为什么失败

第一版直接用原 RL 线路参数配置 Stubline：

```
R = 0.065 Ω
L = 0.66845 mH
Ts = 100 μs
```

Stubline 为了实现一个仿真步的传播解耦，会自动形成等效电容。每条 Stubline 约产生：

```
C ≈ 14.96 μF
```

四条合计造成约 2.04 Mvar 容性无功。

离线结果为：

| 指标 | 原模型 | 第一版拆分模型 |
|------|--------|---------------|
| PCC 无功 | 约 −0.1 kvar | 约 2042.8 kvar |
| PCC 线电压 | 约 10021.7 V | 约 10422.8 V |
| 设备有功 | 正常 | 基本正常 |

因此确定：

> SM/SS 结构没有失败，失败的是使用小线路电感配置普通 Stubline，附加电容严重改变了无功和母线电压。

## 四、补偿型 Stubline 尝试

随后查找了：

```
ARTEMiS 3-phase Coupled Stubline
Compensation Block
```

并读取官方 IEEE 13 节点示例，确认：

```
Coupled Stubline
→ Compensation Block
```

应串联使用，补偿参数由 Stubline 自动写入补偿块。

但我们的原线路只有 R、L，没有真实线路电容。将电容矩阵设为 0 后，补偿块出现：

```
Cdiff = NaN / Inf
补偿电感约 9.75 H
```

说明补偿计算发生奇异，不能使用。

阶段结论：

> 在没有真实线路电容和电缆参数的情况下，不能为了使用补偿块人为编造电容参数。补偿型 Stubline 路线停止。

---

## 五、变压器漏阻抗迁移方案

随后转向更有物理依据的方案：

```
将变压器高压侧漏阻抗
从变压器内部移出
→ 由顶层普通 Stubline 承担
```

变压器参数为：

```
额定容量：110 kVA
高压侧：10 kV
绕组1：Yg，R1=0.0015 pu，L1=0.03 pu
绕组2：Delta(D1)
```

换算得到高压侧漏阻抗：

```
R1 = 1.36363636 Ω
L1 = 0.0868117871 H
```

新的 Stubline 参数为：

```
R = 1.36363636 Ω
L = 0.0868117871 H
Ts = 100 μs
```

由于电感增大约 130 倍，Stubline 自动形成的电容下降到：

```
约 0.1152 μF
```

同时将对应变压器绕组 1 改为：

```
[Vnom_prim, 0, 0]
```

以避免漏阻抗重复计算。

## 六、EV2 单支路验证

首先只对 EV2 进行验证：

```
EV2 变压器高压侧漏阻抗清零
→ 顶层 Stubline 承担原漏阻抗
→ 原 Line_EV2 保留
→ PCC
```

结果：

| 指标 | 四条旧 Stubline 模型 | EV2 漏阻抗迁移后 |
|------|--------------------|-----------------|
| PCC 无功 | 2042.8 kvar | 1503.2 kvar |
| PCC 线电压 | 10422.8 V | 10319.8 V |
| EV2 有功 | −0.999334 pu | −0.999120 pu |

单条 EV2 改造使无功下降约 539.6 kvar，与一条旧 Stubline 的附加无功基本一致，且 EV2 有功几乎不变。

由此证明：

> 变压器漏阻抗迁移到普通 Stubline 的物理思路有效。

## 七、建立最终 2 ＋ 2 ＋ 2 结构

基于 EV2 验证结果，从原始六逆变器模型重新建立了更均衡的任务结构：

```
sm_circuit
├─ 上级电网
├─ PCC、负荷、断路器
├─ 所有原始 RL 线路和接入节点
├─ PCC 测量
└─ AGC、通信及公共控制

ss_pv
├─ PV1
└─ PV2

ss_ess
├─ ESS1
└─ ESS2

ss_ev
├─ EV1
└─ EV2
```

每台设备均采用：

```
设备变压器绕组1漏阻抗清零
→ 顶层普通 Stubline 承担漏阻抗
→ SM 内原有线路和接入点
→ PCC
```

共使用 6 条 Stubline。

同时建立三个控制向量：

```
pv_ctrl_vec
ess_ctrl_vec
ev_ctrl_vec
```

每个 SS 内部结构均为：

```
Inport
→ OpComm
→ Demux
→ 两台设备
```

## 九、进入 RT-LAB 后遇到的变量问题

导入 RT-LAB 后，Build 首先在模型分离阶段报错：

```
Vgrid_line 无法识别
```

原因是该参数之前只通过基础工作区或回调提供，而 RT-LAB 拆分 SM/SS 时会重新加载和处理模型，基础工作区变量不能可靠继承。

处理方式：

```
将 Vgrid_line 和 Ts 写入模型工作区
```

并检查回调。现有回调只有：

```
PostLoadFcn：Ts=1e-4
InitFcn：Ts=1e-4
```

没有 `clear` 或删除变量的命令。

这一变量问题已经定位，后续固定参数应逐步转移到模型工作区或数据字典，不能依赖临时基础工作区。

## 十、RT-LAB Build 的串行通信问题

变量问题之后，Build 进入代码生成阶段，但报错：

```
Communications found between SM and SS are serial
sm_circuit waits data from ss_pv / ss_ess / ss_ev
Add state variables before outputs
```

说明 RT-LAB 认为 SM 与三个 SS 仍存在同一步直接依赖，无法并行。

### 尝试一：在 SM 控制向量输出前增加 Memory

将：

```
Mux → Outport
```

改为：

```
Mux → Memory → Outport
```

分别处理 PV、ESS 和 EV 三个控制向量。

结果：

> Build 仍然报相同串行通信错误。

原因是报错方向是：

```
SS → SM
```

而 Memory 处理的是：

```
SM → SS
```

所以未解决真正依赖。

### 尝试二：处理隐藏的 GridOn

检查发现三个 SS 内部仍通过：

```
From [GridOn]
```

跨任务读取 SM 中的 Goto 信号。

随后进行了以下改造：

- 六台设备新增显式 `GridOn` 输入；
- 三个控制向量由 7 维扩展为 8 维；
- `GridOn` 作为第 8 路经 Memory、OpComm 和 Demux 送入 SS；
- 删除三个 SS 内全部 `From [GridOn]`。

命令检查返回：

```
ss_pv 中的 From [GridOn] 数量：0
ss_ess 中的 From [GridOn] 数量：0
ss_ev 中的 From [GridOn] 数量：0
```

结果：

> Build 仍然报相同串行通信错误。

## 十一、进一步检查普通信号

执行了模型扫描，结果表明：

- `ss_pv` 只有一个普通输入 `pv_ctrl_vec`；
- `ss_ess` 只有一个普通输入；
- `ss_ev` 只有一个普通输入；
- 三个 SS 均无普通 Outport；
- 无 Data Store Read/Write；
- `GridOn` 已不再以 From 方式跨任务传递。

因此可以排除：

- 普通 SS 输出反馈；
- Data Store 跨任务通信；
- GridOn 隐藏传输；
- 控制向量未经过 OpComm。

## 十二、当前没有解决的核心问题

现在最可能的根因是：

> 现有"三相变压器 ＋ 普通三相 Stubline"的简化变压器解耦方案，虽然能够离线运行并基本等效，但没有被 RT-LAB 任务调度器识别为可以并行的状态边界。

目前使用的是：

```
原三相变压器
绕组1漏阻抗清零
＋
普通 N=3 Stubline
```

它在物理数值上基本成立，但 RT-LAB 仍认为：

```
sm_circuit 需要等待 SS 当前步的电气结果
```

因此四个任务仍被判断为串行。

OPAL-RT 官方变压器跨 CPU 示例采用的结构更复杂：

```
3 台单相变压器
＋
差分输入 Stubline
＋
重新组成 Y 或 Delta 连接
＋
正确处理单相容量和相电压基值
```

这与目前简化的三相 Stubline 结构不同。

下一步停止继续修补当前六设备模型，不再增加 Memory 或修改普通控制信号。

优先寻找并读取官方示例：

artemis_Transfo_StublineRT
