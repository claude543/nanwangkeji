# 拆分后的板端联调闭环过程

## 结论

1. **板子写入的全部寄存器首先进入 `SM_Master`，不直接送给三个SS，也不直接送SC。**
2. 最终V5中，板子写入的六路命令经SM解码、安全判断和命令选择后，替换六台设备的 `Pref`；再利用目前已经存在的三组24维 `SM→SS` 通道送到三个SS。
3. RT-LAB送给板子的量也统一由SM发布。PCC、PVmax、SOC、状态和心跳都在SM生成；六路设备实测功率以后需要从三个SS返回SM。
4. **当前恢复V3.1、V3.2以及V4影子运行时，三个SS不需要添加任何模块或通道。**
5. 最终V5接管命令也不需要新增 `SM→SS` 通道；现有24维通道已经包含Pref。只有未来真实化40109～40114时，才需要新增三组 `SS→SM` 的2维功率反馈。

---

## 1. 板子写入的量最终给谁

板子通过FC16写：

```text
40001～40012
```

它们先经过：

```text
板子
→ Modbus TCP
→ OP5700 Modbus Slave寄存器
→ RT-LAB Configuration
→ SM_Master中的OpInput
```

板子不会直接访问SS。V3.1建立的就是这套板子与RT-LAB之间的正式通信接口。

### 40001～40006：六台设备功率命令

```text
40001 → PV1 Pref
40002 → PV2 Pref
40003 → ESS1 Pref
40004 → ESS2 Pref
40005 → EV1 Pref
40006 → EV2 Pref
```

但不能从OpInput直接接设备，需要经过：

```text
Modbus raw
→ int16恢复正负号
→ double
→ ×0.0001恢复pu
→ 设备范围检查或限幅
→ 外部命令有效性判断
→ 命令选择Switch
→ 最终Pref
```

最终命令选择关系是：

```text
EXTERNAL_COMMAND_VALID = 1
    → 使用板端命令

EXTERNAL_COMMAND_VALID = 0
    → 使用本地安全命令
```

本地安全命令可以先保留当前固定命令；V5前再冻结断线时到底是保持、回退还是采用指定安全值。

### 40007～40009：不直接控制设备

```text
40007 AGC_STATUS
40008 dP
40009 remain
```

它们用于：

- SC显示；
- 日志；
- AGC运行状态判断；
- V4影子结果比较。

不会进入设备本地控制器。

### 40010～40012：通信安全管理量

```text
40010 EXT_AGC_ENABLE
40011 CMD_SEQ
40012 BOARD_HEARTBEAT
```

其中：

- `40010`表示板端声明当前命令可用；
- `40011`表示命令批次；
- `40012`证明板端程序仍在更新。

SM不会只相信40010，而是形成：

```text
EXTERNAL_COMMAND_VALID
=
(EXT_AGC_ENABLE == 1)
AND
BOARD_HB_OK
```

板子断线后，即使40010残留为1，只要40012停止变化，SM仍会撤销外部命令资格。

## 2. 六路命令怎样进入三个SS

现在三组24维下行通道中，每台设备的12维数据已经包含：

```text
Vabc[3]
Iabc[3]
Fref
Vref
Droop_On
Pref
Qref
GridOn
```

因此V5时只修改SM中 `Pref` 的来源：

```text
当前：
固定Constant
→ 设备IO Mux的Pref输入

最终：
本地命令 ───────┐
                 ├→ Switch → 设备IO Mux的Pref输入
板端解码命令 ───┘
          ↑
EXTERNAL_COMMAND_VALID
```

随后仍然沿用：

```text
PV1/PV2两个12维
→ PV_Group_Mux24
→ Memory
→ SM Outport
→ SS_Slave3 Inport
→ OpComm
→ 两台PV本地控制器

ESS组、EV组同理
```

所以：

> **最终板端接管不需要新增SM→SS通道，只是在SM中替换现有Pref信号源。**

## 3. RT-LAB送给板子的量由谁产生

板子通过FC03读取：

```text
40101～40116
```

发布路径是：

```text
SM中的Simulink信号
→ OpOutput
→ RT-LAB Configuration
→ Modbus Holding Registers
→ 板子FC03读取
```

板子是Master，所以每个通信周期由板子主动发起读取。V4规定每次一次性读取40101～40116，完成解码、安全判断和AGC后，再一次性写回40001～40012。

### 最终各类信号的来源

#### SM直接产生

```text
40101 PCC_P
40102 PCC_Q
40103 PCC_V
40104 PCC_F
```

直接来自现在已经恢复的：

```text
J2_PCC_Measurements
```

```text
40105 PV1_P_MAX
40106 PV2_P_MAX
```

以后由SM中的PVmax标准块产生。

```text
40107 ESS1_SOC
40108 ESS2_SOC
```

以后由SM中的SOC标准块产生。

```text
40115 MODEL_STATUS
40116 RTLAB_HEARTBEAT
```

由SM的状态与心跳逻辑产生。

#### 最终需要从SS返回SM

```text
40109 PV1_P_MEAS
40110 PV2_P_MEAS
40111 ESS1_P_MEAS
40112 ESS2_P_MEAS
40113 EV1_P_MEAS
40114 EV2_P_MEAS
```

这些实测功率存在于设备控制系统内部，而设备目前分别位于三个SS。

最终真实化时需要：

```text
SS_Slave：
EV1_Pmeas、EV2_Pmeas → 2维返回

SS_Slave2：
ESS1_Pmeas、ESS2_Pmeas → 2维返回

SS_Slave3：
PV1_Pmeas、PV2_Pmeas → 2维返回
```

统一回到SM后，再由SM同时提供给：

```text
40109～40114
SC观察
后续状态重建算法
```

但基础V4 AGC明确只使用：

```text
40101
40105
40106
40107
40108
```

40109～40114在V4中继续读取和记录，但不参与基础AGC计算。

## 4. 拆分后的完整闭环过程

### 当前V3.1阶段

现在只是通信验收：

```text
SM测试Constant
→ 40101～40116
→ 板子FC03读取
→ 板子从JSON取得固定测试命令
→ FC16写40001～40009
→ SM接收和解码
→ SC显示
```

此时：

```text
板端命令不进入设备Pref
三个SS仍执行当前固定Pref
```

因此不是控制闭环，只是双向通信语义闭环。

### V3.2阶段

在V3.1基础上增加：

```text
双方心跳
MODEL_STATUS
CMD_SEQ
EXT_AGC_ENABLE
BOARD_HB_OK
EXTERNAL_COMMAND_VALID
```

板端命令仍不接管设备。

### V4影子运行

```text
SM测量/测试量
→ 40101～40116
→ 板端C版AGC
→ 40001～40012
→ SM接收
→ SC记录和比较
```

但：

```text
40001～40006
不接设备Pref
```

这正是V4的影子运行边界。

### V5正式闭环

最终流程是：

```text
SM中的PCC、PVmax、SOC等测量
→ 40101～40116
→ 板端FC03读取
→ V3.2安全判断
→ 板端AGC计算
→ FC16写40001～40012
→ SM解码
→ EXTERNAL_COMMAND_VALID判断
→ 六路Pref选择Switch
→ 三组现有24维SM→SS通信
→ 三个SS中的本地控制器
→ PWM和变流器
→ Stubline
→ SM公共电网与PCC
→ 新的PCC测量
→ 再送板端
```

这就是最终闭环。

## 5. 与未拆分模型相比，逻辑是否相同

**上层控制逻辑相同，信号传播方式发生了变化。**

### 未拆分前

```text
板端命令
→ SM内设备Pref
→ 同一个子系统里的本地控制器
→ 变流器
→ PCC
```

信号基本都在一个实时子系统内部直接连接。

### 拆分后

```text
板端命令
→ SM中的Pref选择
→ 24维通信边界
→ SS本地控制器
→ 变流器
→ Stubline电气边界
→ SM中的PCC
```

区别是增加了两类任务边界：

```text
控制信号边界：
Memory + OpComm

电气边界：
Stubline
```

控制层级没有变化：

```text
板端：上层慢速AGC
SM：公共电网、PCC测量、Modbus、安全判断和命令分发
SS：快速本地控制、PWM和变流器
```

## 6. 三个SS究竟什么时候需要修改

| 阶段 | 三个SS是否修改 |
| --- | --- |
| V3.1通信恢复 | 不修改 |
| V3.2安全通信恢复 | 不修改 |
| V4影子AGC | 不修改 |
| V5六路命令接管 | 不新增通道，只使用现有24维Pref |
| 40109～40114真实化 | 新增三组2维SS→SM反馈 |
| 后续论文状态重建 | 使用上述实测功率反馈 |

SS不应该直接连接SC。

正确原则始终是：

```text
SS实际量
→ SM统一汇总
→ 一支送Modbus
→ 一支送SC
```

这样板端读取值、SC显示值和后续算法使用值来自同一信号源，不会形成两套口径。

---

## 现阶段最准确的架构

```text
                    ┌→ SC监视
板子 ↔ Modbus ↔ SM ┤
                    ├→ 24维EV命令 → SS_Slave
                    ├→ 24维ESS命令 → SS_Slave2
                    └→ 24维PV命令 → SS_Slave3

三个SS
→ Stubline电气反馈
→ SM电网和PCC
```

当前恢复V3.1和V3.2时，只动：

```text
SM
SC
I/O Interfaces
Configuration
```

三个SS保持冻结。
