# 暑期南网科技项目｜V5-A模型侧改造完整理解

> 日期：2026-08-14  
> 对象：由V4-shadow基线继续改造成的V5-A模型  
> 目的：让外部控制板上的基础C版AGC从“只计算、只写回、不接管”升级为“真正控制2PV + 2ESS + 2EV六台设备的Pref”  
> 本文重点：**V5模型侧到底改了什么、为什么这样改、每一块起什么作用、哪些地方没有改，以及这些改动怎样串成完整闭环。**

---

# 0. 先用一句话说清V4和V5的区别

V4和V5最本质的区别不是“有没有Modbus”，也不是“板子有没有算AGC”。

V4其实已经有完整的：

```text
RT-LAB测量
→ 40101~40116
→ 板端FC03读取
→ 板端C版AGC计算
→ 40001~40012
→ FC16写回RT-LAB
```

但是在V4中：

```text
板端40001~40006
```

只是被RT-LAB接收、记录和比较，**并没有真正送到六台设备的Pref**。

真正控制六台设备的仍然是：

```text
SM_Master中的本地MATLAB基础AGC
```

所以V4叫：

```text
shadow
影子运行
```

可以把它理解为：

> 板端已经坐到了驾驶座上，也已经会计算方向盘该打多少，但方向盘还没有真正连到车轮。

V5-A做的事情就是：

> **把板端的六路命令真正接到六台设备的Pref，同时在接管前加上符号解码、安全资格判断、失效保持和完整日志。**

所以V5-A之后，真实控制链变成：

```text
RT-LAB测量
→ 板端C AGC
→ Modbus写回六路命令
→ V5安全接管逻辑
→ 六台设备Pref
→ 六台变流器真实响应
→ PCC重新变化
→ 再反馈给板端
```

这才形成真正的：

```text
板端AGC闭环
```

# 1. V5-A完整闭环先串起来

先不要看具体模块，先建立一条完整主线。

## 1.1 测量从模型出去

实时模型中能够得到：

```text
PCC有功P
PCC无功Q
PCC电压
PCC频率

PV1/PV2可用功率PVmax
ESS1/ESS2 SOC

PV1/PV2/ESS1/ESS2/EV1/EV2实际功率Pmeas

MODEL_STATUS
RTLAB_HEARTBEAT
```

它们经过既有V4通信映射进入：

```text
40101~40116
```

板端通过FC03读取这些真实模型量。

---

## 1.2 板端根据这些测量运行C版AGC

板端拿到当前：

```text
PCC
PVmax
SOC
设备状态
```

以后，每个AGC周期运行一次C版基础AGC。

基础AGC根据：

```text
dP = Ptarget - Ppcc
```

判断当前PCC距离目标还有多大偏差，然后生成：

```text
PV1 Pref
PV2 Pref
ESS1 Pref
ESS2 Pref
EV1 Pref
EV2 Pref
```

板端再通过FC16把它们写入：

```text
40001~40006
```

同时还会写：

```text
40007 AGC_STATUS
40008 dP
40009 remain
40010 EXT_AGC_ENABLE
40011 CMD_SEQ
40012 BOARD_HEARTBEAT
```

这部分在V4中已经存在，V5没有重新设计Modbus协议。

---

## 1.3 V5模型真正新增的是“40001~40006之后怎么办”

这正是V5-A的核心。

V4：

```text
40001~40006
→ 接收到
→ 记录
→ 不控制设备
```

V5：

```text
40001~40006
↓
补码解码
↓
pu缩放
↓
BOARD_CMD[6]
↓
EXTERNAL_COMMAND_VALID判断
↓
安全接管Switch
↓
FINAL_APPLIED_CMD[6]
↓
六台设备Pref
```

最终设备真正执行的是：

```text
FINAL_APPLIED_CMD
```

而不是：

```text
本地MATLAB AGC输出
```

也不是简单地直接拿：

```text
40001~40006 raw
```

去控制。

这中间每一层都有明确作用。

# 2. 第一项改动：把40001~40006从“监视量”引到V5接管区

你图中左侧有：

```text
V5A_RAW4001
V5A_RAW4002
...
V5A_RAW4006
```

它们分别对应：

| Modbus寄存器 | 设备 |
|---|---|
| 40001 | PV1 |
| 40002 | PV2 |
| 40003 | ESS1 |
| 40004 | ESS2 |
| 40005 | EV1 |
| 40006 | EV2 |

V4里这些量已经存在于模型中，因为板端已经能够写回RT-LAB。

V5没有重新建立Modbus Configuration，而是在原来的：

```text
Modbus_4001_raw
...
Modbus_4006_raw
```

输出上增加支路，通过：

```text
Goto
→ From
```

引到新的V5-A工作区。

例如：

```text
Modbus_4001_raw
→ V5A_GOTO_RAW4001
→ V5A_PV1_RAW_FROM
```

其余五路完全类似。

## 为什么使用Goto/From？

不是因为信号经过了网络。

Goto/From仍然只是同一个Simulink模型内部的信号连接方式。

它的作用只是：

> **避免从模型左边的Modbus区域一直拉六根超长连线到V5工作区。**

可以把它理解成：

```text
Goto = 给这根线贴一个名字
From = 在另一个位置按名字把这根线取出来
```

它没有改变数值，也没有增加新的通信延时。

# 3. 第二项改动：必须对40001~40006做INT16补码解码

这是V5最容易被忽略、但非常关键的一步。

你图中的每一路都有：

```text
RAW
├→ -65536
├→ >=32768
└→ SIGNED_SWITCH
```

例如PV1：

```text
V5A_PV1_RAW_FROM
      ↓
  >= 32768 ?
   /       \
是           否
↓            ↓
raw-65536    raw
   \        /
SIGNED_SWITCH
```

## 3.1 为什么不能直接raw × 1e-4？

因为Modbus寄存器本质上只有16 bit。

板端发送的六路命令语义是：

```text
INT16
```

也就是说既要表示正功率，也要表示负功率。

但是RT-LAB这边原始读取出来时，某些链路会把16位寄存器按：

```text
0~65535
```

的无符号数形式表现出来。

于是负数并不会直接显示成：

```text
-6000
```

而可能显示成：

```text
59536
```

因为：

```text
65536 - 6000 = 59536
```

所以：

```text
59536
```

实际上代表：

```text
-6000 count
```

而不是“+59536”。

---

## 3.2 V5怎样恢复真正的有符号命令？

采用最标准的16位补码恢复方式：

```text
如果 raw < 32768
→ signed = raw

如果 raw >= 32768
→ signed = raw - 65536
```

例如：

### 正命令

```text
raw = 6500
< 32768

signed = 6500
```

### EV充电负命令

```text
raw = 59536
>= 32768

signed
= 59536 - 65536
= -6000
```

这就是图中的：

```text
MINUS65536
GE32768
SIGNED_SWITCH
```

三块存在的原因。

# 4. 第三项改动：把寄存器count转换成pu

经过补码解码以后，我们得到的是：

```text
有符号count
```

还不是模型里设备Pref真正使用的pu。

所以图中每一路又经过：

```text
Gain = 1e-4
```

即：

```text
BOARD_CMD_pu
=
signed_raw × 0.0001
```

因为当前六路功率命令采用：

```text
1 pu = 10000 count
```

所以：

```text
6500 count
→ +0.6500 pu

-6000 count
→ -0.6000 pu

-10000 count
→ -1.0000 pu
```

因此这里真正完成的是：

```text
Modbus语言
↓
模型控制语言
```

即：

```text
16位寄存器raw
→ 有符号整数
→ pu功率指令
```

到这里才真正得到：

```text
BOARD_CMD[6]
```

# 5. 第四项改动：把EXTERNAL_COMMAND_VALID真正变成“控制权开关”

这是V4到V5最重要的功能变化之一。

V4中已经有：

```text
EXTERNAL_COMMAND_VALID
```

它不是V5新发明的。

原来的安全逻辑已经判断：

```text
EXTERNAL_COMMAND_VALID
=
(40010 == 1)
AND
BOARD_HB_OK
```

其中：

```text
40010 = EXT_AGC_ENABLE
```

表示：

> 板端主动声明：我现在具备外部控制资格。

而：

```text
BOARD_HB_OK
```

表示：

> RT-LAB自己确认40012 BOARD_HEARTBEAT还在持续更新，没有超时。

两者必须同时成立。

---

## 为什么不能只看40010？

因为通信中断以后：

```text
40010
```

可能还会停留在上一次写进去的：

```text
1
```

它只是寄存器里的旧值，并不会因为板端突然死亡而自动变回0。

如果模型只判断：

```text
40010 == 1
```

那么可能出现：

```text
板端已经死了
但是40010还残留1
模型却误以为板端还活着
```

所以必须再用：

```text
BOARD_HEARTBEAT
```

独立判断板端是否真的还在线。

最终：

```text
40010=1
AND
心跳正常
```

才得到：

```text
EXTERNAL_COMMAND_VALID=1
```

---

## V4和V5对它的用法有什么不同？

V4：

```text
EXTERNAL_COMMAND_VALID
```

主要用于：

```text
监视
验收
判断板端资格
```

但是即使它等于1：

```text
六台设备还是本地MATLAB AGC控制
```

V5则第一次把它真正接到：

```text
六个TAKEOVER_SWITCH
```

所以现在它代表的是：

> **板端有没有资格真正拿到六台设备的控制权。**

---

# 6. 第五项改动：六个TAKEOVER_SWITCH完成真正接管

图中的核心模块就是六个：

```text
V5A_PV1_TAKEOVER_SWITCH
V5A_PV2_TAKEOVER_SWITCH
V5A_ESS1_TAKEOVER_SWITCH
V5A_ESS2_TAKEOVER_SWITCH
V5A_EV1_TAKEOVER_SWITCH
V5A_EV2_TAKEOVER_SWITCH
```

每个Switch都有三路：

```text
上输入：当前BOARD_CMD
中输入：EXTERNAL_COMMAND_VALID
下输入：LAST_APPLIED
```

逻辑是：

```text
如果 EXTERNAL_COMMAND_VALID = 1
→ 输出当前BOARD_CMD

如果 EXTERNAL_COMMAND_VALID = 0
→ 输出LAST_APPLIED
```

所以：

```text
FINAL_APPLIED_CMD
=
BOARD_CMD       ，板端有效时

FINAL_APPLIED_CMD
=
LAST_APPLIED    ，板端失效时
```

这就是V5真正的“控制权切换”。

# 7. 第六项改动：增加LAST_APPLIED，通信异常时不是乱跳，而是HOLD

每个TAKEOVER_SWITCH后面都有一个：

```text
Unit Delay
```

例如：

```text
V5A_PV1_LAST_APPLIED
```

它的作用不是给正常板端命令人为增加1秒延时。

它做的是：

> **一直记住上一拍真正送给设备的最终命令。**

结构是：

```text
TAKEOVER_SWITCH输出
      ↓
FINAL_APPLIED
      ↓
Unit Delay
      ↓
LAST_APPLIED
      └────────→ Switch失效侧输入
```

这形成一个简单的记忆环。

---

## 正常通信时

例如：

```text
BOARD_CMD = 0.35 pu
EXTERNAL_VALID = 1
```

那么：

```text
FINAL = 0.35
```

同时：

```text
LAST_APPLIED
```

也会在下一拍记住：

```text
0.35
```

---

## 通信突然异常时

假设最后一条真实执行命令是：

```text
0.35 pu
```

下一拍：

```text
EXTERNAL_VALID：
1 → 0
```

Switch不再使用当前BOARD_CMD，而改用：

```text
LAST_APPLIED = 0.35
```

于是：

```text
FINAL仍然 = 0.35
```

设备不会突然跳到：

```text
0
```

也不会突然切到另一个内部状态完全不同的MATLAB AGC。

所以这就是当前V5-A最基础的：

```text
HOLD最后真实施加命令
```

---

# 8. 为什么V5失效时没有自动切回本地MATLAB AGC？

这是一个非常重要的设计选择。

表面看，好像可以这样：

```text
板端正常
→ 用板端AGC

板端异常
→ 马上切回本地MATLAB AGC
```

但问题是：

```text
板端AGC内部状态
```

和：

```text
本地MATLAB AGC内部状态
```

虽然算法公式相同，却不一定拥有完全一样的运行历史。

特别是板端真正接管以后：

```text
板端经历的commit历史
≠
本地MATLAB AGC自己独立计算出来的历史
```

如果通信一断就直接切到本地AGC，可能出现：

```text
当前设备正在执行0.3 pu

本地AGC此时内部已经走到了0.8 pu

通信刚断
→ Pref瞬间0.3 → 0.8
```

反而人为制造一次功率突跳。

所以V5-A采用的是更简单、更确定的：

```text
通信失效
→ HOLD最后真实施加值
```

而不是：

```text
通信失效
→ 自动切本地AGC
```

这也为后面的：

```text
Strategy7
RECONSTRUCTION
RECOVERY
```

留下了清晰的研究空间。

# 9. 第七项改动：给六个LAST_APPLIED设置正确初始值

V5模型刚Execute时，板端不可能第一拍就立刻具备控制资格。

需要经历：

```text
建立TCP连接
↓
首次FC03
↓
确认RTLAB_HEARTBEAT变化
↓
WAIT_VALID
↓
连续有效周期
↓
ENABLED
↓
产生并成功提交板端命令
↓
40010=1
↓
EXTERNAL_COMMAND_VALID=1
```

所以在这段时间里：

```text
EXTERNAL_COMMAND_VALID = 0
```

六个Switch必然走：

```text
LAST_APPLIED
```

因此必须给LAST_APPLIED一个合理初值。

本次设置为：

```text
PV1  = 0
PV2  = 0

ESS1 = 0
ESS2 = 0

EV1  = -0.6
EV2  = -0.6 pu
```

即：

```text
[0, 0, 0, 0, -0.6, -0.6]
```

这与当前基础模型原始运行初值保持一致。

所以板端尚未取得资格时，系统不会出现随机命令或全部清零，而是保持原本已经验证过的初始工况。

# 10. 第八项改动：真正切断本地MATLAB AGC到六台设备Pref的控制线

这一项在你截图里不明显，但它才是“真实接管”成立的关键。

V4原来是：

```text
MATLAB基础AGC
│
├→ PV1_IO_Mux12 input 6
├→ PV2_IO_Mux12 input 6
├→ ESS1_IO_Mux12 input 6
├→ ESS2_IO_Mux12 input 6
├→ EV1_IO_Mux input 6
└→ EV2_IO_Mux input 6
```

这些Mux的第6路就是对应设备下发到SS侧的：

```text
Pref
```

所以V4虽然板端已经把命令写入40001~40006，但是设备真正执行的仍然是：

```text
MATLAB Function的6路输出
```

---

## V5做了什么？

V5删除了这六条直接控制连接：

```text
MATLAB Function
→ 六个设备IO Mux input 6
```

然后改成：

```text
V5A_FINAL_PV1
→ PV1_IO_Mux12 input 6

V5A_FINAL_PV2
→ PV2_IO_Mux12 input 6

V5A_FINAL_ESS1
→ ESS1_IO_Mux12 input 6

V5A_FINAL_ESS2
→ ESS2_IO_Mux12 input 6

V5A_FINAL_EV1
→ EV1_IO_Mux input 6

V5A_FINAL_EV2
→ EV2_IO_Mux input 6
```

所以设备真正收到的是：

```text
FINAL_APPLIED_CMD
```

而：

```text
FINAL_APPLIED_CMD
```

又由：

```text
BOARD_CMD
+
EXTERNAL_COMMAND_VALID
+
LAST_APPLIED
```

共同决定。

这一步完成以后，板端才真正从“影子控制器”变成：

```text
实际控制器
```

# 11. GOTO_FINAL为什么又使用Goto/From？

图中每一路Switch输出后都有：

```text
V5A_GOTO_FINAL_PV1
V5A_GOTO_FINAL_PV2
...
```

它们也是为了整理模型连线。

例如：

```text
TAKEOVER_SWITCH
→ V5A_GOTO_FINAL_PV1
```

然后在原PV1_IO_Mux附近：

```text
V5A_FINAL_PV1_TO_DEVICE
```

通过From重新取出来。

因此：

```text
GOTO_FINAL
```

不是另外一层控制，也不是网络通信。

它只是把：

```text
最终真实施加命令
```

以统一名字送到模型其他需要使用它的位置。

# 12. 第九项改动：ESS的SOC计算必须改成使用FINAL_APPLIED_PREF

这一项也不在你截图的主要区域中，但非常重要。

V4原来的ESS SOC计算支路使用：

```text
本地MATLAB AGC的ESS Pref
```

也就是说原来：

```text
MATLAB AGC给ESS1多少命令
→ SOC模块就按这个命令更新
```

V4中没有问题，因为真正控制ESS的也是本地MATLAB AGC。

---

## V5如果只改设备Pref、不改SOC，会出现什么错误？

假设：

```text
板端命令ESS1 = -0.2 pu
```

但是本地MATLAB AGC独立计算：

```text
ESS1 = +0.8 pu
```

如果设备已经执行板端命令，而SOC还接本地AGC，就会变成：

```text
真实ESS：
正在充电 -0.2 pu

SOC内部：
却按放电 +0.8 pu计算
```

这会造成严重的“物理状态和控制状态不一致”。

---

## 所以V5同时删除了：

```text
MATLAB AGC ESS1输出
→ DelayESS1_PREF_PU_SOC

MATLAB AGC ESS2输出
→ Delay_ESS2_PREF_PU_SOC1
```

改成：

```text
FINAL_ESS1_PREF
→ ESS1设备Pref
→ 同时进入ESS1 SOC链

FINAL_ESS2_PREF
→ ESS2设备Pref
→ 同时进入ESS2 SOC链
```

因此现在：

> **ESS真实执行什么功率，SOC就按照同一条最终施加命令演化。**

这个修改保证了：

```text
控制命令
设备执行
SOC状态
```

三者在逻辑上统一。

---

# 13. 第十项改动：本地MATLAB AGC没有删除，只是退出“执行权”

V5并没有把：

```text
MATLAB Function基础AGC
```

从模型里删掉。

它仍然继续计算。

原因有三个。

## 13.1 作为对照基准

我们可以同时看到：

```text
LOCAL_CMD
```

和：

```text
BOARD_CMD
```

从而判断：

```text
板端C算法和原MATLAB算法在相同/不同历史下表现怎样
```

---

## 13.2 保留已有日志体系

原来Group26中的大量：

```text
AGC内部状态
dP
remain
六路本地命令
策略状态
```

仍然可以继续记录。

这让V5和V4之间的数据具有连续性。

---

## 13.3 为后续论文实验提供“控制器认知状态”参照

板端接管以后，本地AGC继续独立演化。

它可能与真实设备执行历史逐渐分开。

这种：

```text
内部认知状态
≠
真实执行状态
```

本身正是后续论文要研究的重要问题之一。

所以V5没有把本地AGC删掉，反而保留它作为很有价值的对照对象。

# 14. 第十一项改动：引入CMD_SEQ到V5诊断日志

V5把既有：

```text

```

通过：

```text
V5A_CMD_SEQ_FROM
```

引到V5日志区。

它没有参与六台设备控制。

```text
板端CSV
```

中的：

```text

```

和：

```text
RT-LAB Target里的CMD_SEQ
```

一一对齐。

```text

↓

↓

↓
最终设备执行了什么
```

CMD_SEQ相当于给每一组正式命令加了一个：

```text
流水号
```

# 15. 第十二项改动：新增V5A_DIAG_MUX14

你图中最右侧黑色竖条：


是V5专门新增的诊断Mux。

它一共收集14路：

```text

2  BOARD_PV2
3  BOARD_ESS1
4  BOARD_ESS2
5  BOARD_EV1
6  BOARD_EV2

8  FINAL_PV2
9  FINAL_ESS1
10 FINAL_ESS2
11 FINAL_EV1
12 FINAL_EV2

14 CMD_SEQ
```

这里最关键的是同时记录：

```text
BOARD_CMD
```

和：

```text
FINAL_CMD
```

因为两者含义完全不同。

---

## BOARD_CMD是什么？

```text
板端当前写给RT-LAB的命令
```

它回答：

> 板端想让设备干什么？

---

## FINAL_CMD是什么？

```text
V5安全逻辑最后真正送给设备的命令
```

它回答：

> 设备最终到底被要求干什么？

---

通信正常时：

```text
BOARD_CMD = FINAL_CMD
```

通信异常时：

```text
BOARD_CMD
```

可能仍然停留着旧寄存器值，甚至未来可能发生变化，

但是：

```text
FINAL_CMD
```

可以根据安全逻辑进入：

```text
HOLD
```

所以后续通信异常实验真正应该看的是：

```text
FINAL_CMD
```

而不是只看40001~40006。

# 18. 第十五项改动：Group26的Buffer Size必须扩大

这一项完全不在你截图里，但是V5模型配置必须同步修改。

原Group26：

```text

```

double每个数8 byte。

```text

= 664000 bytes
```

原来的：

```text

672026
```

本次设为：



留出足够余量。


# 21. V5-A启动时到底发生什么？

此时板端还没有取得资格：

```text

```

所以六台设备执行：

```text
LAST_APPLIED初值
=
[0, 0, 0, 0, -0.6, -0.6]
```

## 阶段2：板端建立Modbus连接

板端开始：


第一拍只能看到：


还不能证明它真的在变化。

```text

```

这是正常的。


```text
模型不是一个冻结的旧寄存器页面
```

```text
WAIT_VALID
```

继续累计有效周期。

递增。


```text
看现场数据

```


不能真正控制。

### 第一件：翻译命令

```text
Modbus raw
→ 正负号恢复
```

```text
40010
+
```

相当于确认：

```text
失效
```

这四件事情合起来，就是现在V5-A模型侧新增部分的本质。

# 27. V5-A和未来论文算法之间是什么关系？

现在一定不要把V5-A的HOLD理解成最终创新。

当前V5-A解决的是：

```text
“板端能不能真正安全接管六台设备？”
```

答案现在已经是：

```text
能
```

但更深的问题才刚刚开始。

例如：

```text
通信断了几秒
↓
设备一直执行最后命令
↓
板端内部AGC到底停在哪里？
↓
真实设备已经运行到了哪里？
↓
恢复时板端当前计算状态
是否还对应设备真实执行状态？
```

这就可能产生：

```text
controller perceived state
≠
plant/device real execution state
```

后续论文方法才针对它增加：

```text
Strategy2
Tracking + Execution-State Assessment
        ↓
判断设备真实执行状态

Strategy7
NORMAL / HOLD / RECONSTRUCTION / RECOVERY
        ↓
管理通信异常和恢复阶段

Improved AGC
        ↓
根据真实有效能力重新分配六台设备任务
```

所以整个发展顺序是：

```text
V4：
先证明板端算法算得对
但是不接管

↓

V5-A：
让基础C AGC真正接管
建立真实板端闭环

↓

V5异常baseline：
制造通信中断/恢复
观察状态失配和恢复问题

↓

论文正式算法：
Strategy2 + Strategy7 + Improved AGC

↓

最终CHIL：
证明改进算法比baseline恢复更合理
```

这就是V5-A在整个项目中的准确位置。

# 28. 最后压缩成一张“改了什么—为什么—作用”表

| V5改动 | 为什么必须改 | 最终作用 |
|---|---|---|
| 40001~40006增加Goto/From支路 | 原来板端命令只是监视 | 把六路板端raw命令引到真实接管区 |
| `raw>=32768 → raw-65536` | Modbus负数采用16位补码 | 恢复ESS/EV等负功率命令 |
| `Gain=1e-4` | raw count不是模型pu | 转成六设备Pref使用的pu |
| 引入EXTERNAL_COMMAND_VALID | 不能只要收到命令就接管 | 只有板端真正有效才获得控制权 |
| 六个TAKEOVER_SWITCH | 需要明确控制权选择 | valid=1用板端，valid=0用HOLD |
| 六个LAST_APPLIED Unit Delay | 通信失效不能让Pref乱跳 | 保存并保持最后真实施加命令 |
| 初值`[0 0 0 0 -0.6 -0.6]` | 启动初期板端尚未有效 | 保持原验证工况平稳启动 |
| 删除本地AGC→六设备Pref直连 | 否则板端仍然只是影子 | 真正把执行权交给板端 |
| FINAL_CMD重新接六设备Mux input6 | 设备必须执行安全选择后的命令 | 完成真实板端接管 |
| ESS SOC改接FINAL_ESS Pref | SOC必须跟真实执行功率一致 | 避免“设备执行板端、SOC按本地AGC算” |

# 29. 最应该记住的五句话

如果以后很久不看这份文档，只记住下面五句话就够了。

**第一句：**

> V4已经让板端“会算、会写”，V5-A才让板端“真正控制六台设备”。

**第二句：**

> 40001~40006不能直接进Pref，必须先把16位补码恢复成有符号数，再乘`1e-4`变成pu。

**第三句：**

> 真正决定板端有没有控制权的不是40010单独，而是`EXTERNAL_COMMAND_VALID = 40010有效 AND BOARD_HB_OK`。

**第四句：**

> 板端有效时`FINAL_CMD = BOARD_CMD`；板端失效时`FINAL_CMD = LAST_APPLIED`，所以当前V5异常基线是HOLD最后真实施加命令。

**第五句：**

> V5-A只完成“基础C AGC真实接管”；通信恢复后的状态重构、受控恢复和真实能力重分配，才是后面Strategy2 + Strategy7 + Improved AGC要解决的问题。
