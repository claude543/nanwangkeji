# 3. 第一篇不是“四套改进”

真正主体是：

```text
策略2
= 看清真实状态
= PCC跟踪状态 + 设备执行一致性评估

↓

策略7
= 决定当前处于什么阶段
= NORMAL / HOLD / RECONSTRUCTION / RECOVERY
= 形成当前有效总调节需求

↓

改进AGC
= 把总调节需求分给2PV + 2ESS + 2EV
```

SOC放在改进AGC内部：

```text
理论物理裕度
+
设备真实执行状态
+
SOC状态
↓
形成有效可调能力
↓
完成六资源分配
```

所以：

> **策略2负责“看”，策略7负责“决定现在怎么走”，AGC负责“具体怎么分”，SOC只是帮助AGC更合理地分。**

# 9. 为什么建议“策略7给总调节需求，AGC负责分配”

正常：

```text
Ptarget = -100 kW
Ppcc   = -120 kW

策略7：
根据当前NORMAL状态
给出有效总调节需求约 +20 kW

↓

改进AGC：
决定这20 kW怎样分给
PV1、PV2、ESS1、ESS2、EV1、EV2
```

异常时：

```text
策略2发现：
测量不可信 / 命令未成功提交 / 设备状态失配

↓

策略7：
决定HOLD、重构或恢复
并决定当前允许释放多少调节需求

↓

AGC：
只负责把这个需求分给资源
```

因此策略7输出的不是简单裸：

```text
Ptarget - Ppcc
```

而是：

> **结合当前状态处理后的“有效总调节需求”。**

AGC专心解决：

> **“怎么分”。**

这样职责最清楚。

```text
↓

↓

```

### 为什么必须先本地验证？

如果第一次实现就直接上板：

```text
算法错误
+
C代码错误
+
Modbus错误
+
状态机错误
+
点表问题
```

会混在一起。

本地阶段只回答：

> **“算法本身能不能工作？”**

### 本地先测什么？

```text
Case A 正常运行
→ PCC能否稳定跟踪？

Case B 资源能力变化
→ 能否合理重新分配？

Case C 人工冻结上行反馈
→ 是否HOLD而不继续错误推进？

Case D 人工阻断下行命令
→ 是否保持最后成功状态？

Case E 恢复
→ 是否先重构再重新接管？

Case F 恢复第一拍
→ 是否存在巨大命令跳变？
```

这里用 Switch、Hold、Delay 等人工异常即可。

目的不是证明真实通信，而是验证控制逻辑。

# 20. 为什么整个顺序必须这样排

## 原因1：蓝图先于核心文献

没有蓝图：

```text
不知道为什么读
```

有蓝图：

```text
带着问题读
```

## 原因2：核心文献先于最终算法

避免：

```text
重复别人
把成熟机制误当创新
```

## 原因3：算法设计先于代码

先写清：

```text
输入、输出、状态、公式、状态转移
```

再写代码，调试成本低很多。

## 原因4：本地验证先于板端

先隔离：

```text
算法本身有没有问题
```

再验证：

```text
真实板端通信有没有问题
```

## 原因5：V4必须先于V5

V4先证明：

```text
通信层 + 安全层 + 基础C AGC
```

V5才允许真实控制六设备。

## 原因6：V5正式实验先于最终论文结论

```text
本地验证
= 证明算法逻辑

板端CHIL
= 最终工程证据
```
