# 0. 先记住最终结论：策略2到底是什么？

一句话：

> **策略2负责“看清六台设备真实执行到了哪里”，而不是负责决定系统接下来怎么控制。**

论文主线是：

```text
策略2
看清现实：
六台设备到底执行得怎么样？
        ↓
策略7
根据现实决定：
系统现在应该 NORMAL / HOLD / 状态对齐 / RECOVERY？
        ↓
改进AGC
根据策略7确认后的真实有效资源状态：
剩余调节任务到底重新分给谁？
```

因此三者职责必须严格分开：

```text
策略2 = 识别
策略7 = 状态管理与决策
改进AGC = 功率任务分配与执行
```

当前策略2已经实现的核心能力是：

```text
正常设备动态
不能被误判为执行失败
        +
真正持续执行失配
能够被识别
        +
一旦确认失配
不能因为AGC又发新命令就“洗白”
        +
真实执行恢复后
经过连续恢复证据才解除失配
```

当前状态编码：

```text
0 = UNTRUSTED
    当前不可评估 / 数据不可信

1 = TRACKED
    已稳定执行

2 = RESPONDING
    正常响应中

3 = MISMATCH
    已确认执行失配
```

最重要的不是这四个数字本身，而是策略2建立了这样一条证据链：

```text
当前可信命令
↓
根据设备正常动态预测此刻应该响应到哪里
↓
Pexpected
↓
与真实Pmeas比较
↓
execution residual
↓
结合动态允许带 + 持续时间
↓
逐设备执行状态
```

# 1. 这件事最开始为什么会进入论文蓝图？

## 1.1 原始论文问题并不是“通信会不会丢包”

项目最终对象是：

```text
2PV + 2ESS + 2EV
        ↓
六逆变器并网光储充微电网
        ↓
PCC / 联络线有功协调
        ↓
外部控制板
        ↕ Modbus TCP
OPAL-RT OP5700
        ↓
最终CHIL
```

早期通信试验已经看到：

```text
下行异常
→ 控制命令和设备真实执行可能失配

上行异常
→ 控制器看到的反馈可能已经陈旧

恢复以后
→ 控制器认知状态和真实物理状态可能不一致
```

但经过文献检索以后，我们明确不能把：

```text
通信延时
丢包
HOLD上一命令
恢复后resume
anti-windup
普通无扰切换
Modbus + CHIL
```

本身当成论文主要创新。

因此论文真正往深处压成了：

> **当“控制器认为设备应该是什么状态”和“设备真实已经执行到什么状态”出现分叉以后，系统如何发现这种分叉，并据此进行后续状态管理和资源重分配？**

这就是策略2存在的根本原因。

# 2. 原来的策略2到底是什么？为什么不够？

仓库原始 `Advanced_Strategy_Core1.m` 中，策略2核心是：

```matlab
agcErr = abs(Pt - P);

mt(2) = 100.0*agcErr / ...;

al(2) = double(mt(2) > eb);

cmd(2) = Pt - P;

st(2) = double(al(2) < 0.5);
```

通俗理解：

```text
Ptarget是多少？
↓
PCC实际是多少？
↓
两者差多少？
↓
误差是不是太大？
```

所以原策略2其实是：

> **PCC有功跟踪误差评价器。**

它能回答：

```text
PCC跟踪得好不好？
```

但它不能回答：

```text
到底是哪台设备没有正常执行？

PV1还在正常爬升，还是已经执行不足？

ESS1命令变了以后，当前Pmeas属于正常动态还是异常？

EV1真实执行和AGC内部认知是否已经失配？
```

更关键的是，原策略2和原策略7数学上几乎重复：

```text
策略2：
cmd(2) = Pt - P

策略7：
tieErr = P - Pt
cmd(7) = -tieErr = Pt - P
```

因此论文如果直接拿原策略2和策略7去写：

```text
策略2 + 策略7
```

实际上并没有形成真正不同的职责。

这就是为什么必须改造。

# 3. 基础AGC真正缺少的是什么？

当前 `AGC_Controller.m` 不是PI控制器。

它真正保存的内部资源状态是：

```text
Ppv
Pess
Pev
```

对应：

```text
Ppv(1)  = PV1内部历史分配
Ppv(2)  = PV2内部历史分配

Pess(1) = ESS1内部历史分配
Pess(2) = ESS2内部历史分配

Pev(1)  = EV1内部充电功率幅值记忆
Pev(2)  = EV2内部充电功率幅值记忆
```

通俗理解：

> **AGC记得的是“我上一次给这六台设备分配到了哪里”。**

但是：

```text
AGC记得自己给了什么
≠
设备已经真实做到什么
```

这两个东西之间至少隔着：

```text
设备本地控制器
逆变器
滤波器
变压器
网络
正常响应动态
通信/执行状态
```

所以必须区分四个概念：

```text
u_calc
控制器算出来的候选命令

u_commit
最后真正成功提交的命令

u_applied
设备实际采用的设定值

Pmeas
设备最后真实输出的有功功率
```

当前V4候选—提交机制已经把：

```text
“没发送成功却把内部状态继续推进”
```

这种较低级的软件问题处理得更干净。

所以论文真正剩下的深层问题是：

> **即使命令已经成功提交，也不等于设备已经真实执行完成。**

策略2就是专门补上这一层“真实执行状态认知”。

# 4. 为什么不能直接写 `Pcmd - Pmeas`？

这是整个策略2设计中你最应该掌握的第一个方法论。

假设AGC在某一时刻给PV：

```text
0 → 0.2 pu
```

如果设备是真实物理对象，它不会瞬间：

```text
Pmeas：0 → 0.2
```

而是：

```text
0
→ 0.05
→ 0.10
→ 0.15
→ 0.18
→ 0.20
```

所以如果直接定义：

```text
|Pcmd - Pmeas| > threshold
→ 异常
```

那么命令刚变化以后一定会出现：

```text
Pcmd已经变了
Pmeas还没跟上
```

结果就是：

> **把正常设备动态误判成执行异常。**

这会直接毁掉策略2。

因此在正式写策略2之前，我们必须先回答：

> **“正常设备在收到功率命令以后，按正常物理过程应该怎样变化？”**

这就是为什么先做设备动态辨识。

# 5. 动态辨识阶段：我们到底做了什么？

## 5.1 为什么不能继续用原来的AGC闭环数据直接辨识？

原来的 `Ptarget=-100 kW` 闭环数据中：

```text
AGC每1 s重新计算
↓
PV命令变化
↓
PCC又变化
↓
下一轮AGC又可能改EV/ESS
```

这意味着：

```text
多个设备
多个控制动作
PCC闭环
```

同时耦合。

如果用这种数据直接辨识：

```text
Pref → Pmeas
```

很难区分：

```text
这是设备自己的动态
还是AGC下一轮又改了命令？
```

因此我们另建动态辨识副本：

```text
关闭上层AGC自动调节
↓
保留设备本地Control System
保留PWM
保留逆变器
保留正式电气网络
保留Measurements
↓
直接给设备Pref施加错时阶跃
```

核心原则：

> **一次只让一台设备发生阶跃，其他设备保持不变。**

但为了省Build：

> **六台设备的阶跃错开时间，一次Build、一次Execute全部测完。**

# 8. 动态辨识对论文最重要的结论

当前AGC：

```text
Ts_AGC = 1 s
```

而设备：

```text
90%正常响应时间
约0.9～1.5 s
```

因此：

```text
AGC下一轮已经来了
↓
上一轮设备可能仍然没有完全响应完
```

这就证明：

> **“上一轮命令还没完全执行完”本身是正常现象。**

所以策略2必须显式存在：

```text
RESPONDING
正常响应中
```

不能只有：

```text
正常
/
异常
```

这是策略2最核心的物理依据。

# 9. 为什么最后选“一阶预期模型”？

三类设备的63%响应时间都集中在约：

```text
0.4～0.6 s
```

而典型一阶系统在：

```text
t = τ
```

时达到约63%的最终变化量。

因此第一版没有必要直接上复杂高阶模型，而是采用：

```text
PV τ ≈ 0.47 s
ESS τ ≈ 0.50 s
EV τ ≈ 0.52 s
```

这不是说：

> “真实逆变器严格就是一个一阶系统。”

而是：

> **为了执行状态判断，我们只需要一个足够描述“正常响应应该走到哪里”的低复杂度预期模型。**

这是工程研究里很重要的方法：

```text
模型复杂度
不是越高越好

只要模型复杂度
足够支撑当前决策任务
就是合理的
```

# 10. 为什么不直接改 `Advanced_Strategy_Core1.m` 的策略2几行？

原来的高级策略核心输入很多，但它没有直接输入：

```text
六路AGC命令
六路Pmeas
```

新策略2真正需要的是：

```text
每台设备的命令
+
每台设备的Pmeas
+
正常动态
```

所以如果强行只改原策略2四行：

```matlab
agcErr = ...
mt(2) = ...
al(2) = ...
cmd(2) = ...
```

根本不够。

因此采用：

> **原15策略框架暂时保留 + 新增独立“策略2执行状态评估模块”。**

这也是当前模型架构。

原策略2仍保留：

```text
PCC tracking KPI
```

新独立模块负责：

```text
逐设备 execution-state assessment
```

论文层面可以把两者合起来理解成：

> **PCC Tracking + Execution-State Assessment（PCC跟踪 + 执行状态评估）**

但模型实现上当前是两条并列支路：

```text
原高级策略核心
→ 保留PCC跟踪摘要

新Strategy2_Execution_Assessment
→ 输出六设备详细执行状态
```

# 11. 为什么最终采用“16个标量输入”？

最开始我们尝试过：

```text
Pcmd[6]
Pmeas[6]
```

两个6维向量直接输入MATLAB Function。

结果Simulink在脚本自动创建MATLAB Function时出现：

```text
无法确定Pmeas维度
默认被推断成1元素
```

随后又遇到：

```text
6维Mux已有残留连接
```

这些都不是算法逻辑问题，而是：

> **Simulink / MATLAB Function 自动建模时的接口尺寸与连接鲁棒性问题。**

最后我们主动简化接口：

```text
全部标量输入
```

变成：

```text
t
assess_enable
cmd_valid
meas_valid

PV1_cmd
PV2_cmd
ESS1_cmd
ESS2_cmd
EV1_cmd
EV2_cmd

PV1_meas
PV2_meas
ESS1_meas
ESS2_meas
EV1_meas
EV2_meas
```

共：

```text
16个输入
```

这样做的好处：

1. RT-LAB/Simulink更稳定；
2. 不依赖向量尺寸自动推断；
3. 每条线肉眼都能追踪；
4. V5以后可以逐路把本地AGC命令换成板端最后成功提交命令；
5. 出问题时容易定位到底是哪台设备哪根线。

这是很值得保留的工程经验：

> **实时仿真模型中，接口“可验证、可追踪、可维护”往往比追求形式上的简洁更重要。**

当前V0.2：

```text
1  t
2  assess_enable
3  cmd_valid
4  meas_valid

5  PV1_cmd
6  PV2_cmd
7  ESS1_cmd
8  ESS2_cmd

11 PV1_meas
12 PV2_meas

14 ESS2_meas

```

---

## 12.1 `t`

Target真实运行时间。

作用：

```text
计算dt
↓
推进一阶Pexpected
↓
累计异常持续时间
↓
累计恢复持续时间
```

---

## 12.2 `assess_enable`

当前本地阶段直接复用：

```text
AGC Enable
```

因此：

```text
0～15 s
策略2不正式判断
只做状态贴合初始化

15 s以后
策略2正式执行
```

这样避免：

```text
模型刚启动
Pexpected初值错误
↓
产生巨大假residual
↓
误判异常
```

---

## 12.3 `cmd_valid`

当前本地验证：

```text
Constant = 1
```

意思是：

```text
我们假设当前策略2收到的命令是可信的
```

V5以后应替换成真实语义，例如：

```text
最后成功提交命令是否有效
```

它是为：

```text
u_commit
```

预留的接口。

---

## 12.4 `meas_valid`

当前本地验证：

```text
Constant = 1
```

意思是：

```text
六路Pmeas当前都可信、新鲜
```

V5以后可连接：

```text
上行数据是否新鲜
设备测量是否有效
```

它和 `cmd_valid` 故意分开。

因为以后可能出现：

```text
命令可信
但测量不可信
```

或者：

```text
测量可信
但当前命令语义不可信
```

两种情况不能混成一个开关。

---

## 12.5 六路 `cmd`

当前阶段来自：

```text
本地MATLAB AGC真实命令
```

设备顺序固定：

```text
PV1
PV2
ESS1
ESS2
EV1
EV2
```

以后V5最重要的接口变化是：

```text
本地AGC命令
↓
板端最后成功提交的u_commit
```

注意：

> **策略2不应该用“候选命令”作为执行判断依据。**

因为候选命令：

```text
算出来了
```

不代表：

```text
已经成功提交
```

---

## 12.6 六路 `Pmeas`

来自当前正式六设备测量链。

不是重新建立第二套Measurements。

原则是：

> **复用已经验证过的单一真实来源。**

所以：

```text
正式日志里的Pmeas
=
板端点表将来使用的Pmeas
=
策略2使用的Pmeas
```

尽量避免同一个物理量在模型里重新计算多套。

# 13. 为什么策略2不是直接使用 `u_applied`？

这是论文逻辑中非常关键的一点。

我们的受控故障试验里确实额外记录了：

```text
applied_pref
```

但：

> **它只是故障试验的“真值标签”，没有作为策略2算法输入。**

策略2真正看到的是：

```text
AGC / 最后可信命令
+
Pmeas
```

而不是：

```text
设备实际Switch输出
```

为什么？

因为真实系统里最困难的恰恰就是：

```text
你未必直接知道设备实际采用了什么
```

所以策略2要通过：

```text
可信命令
+
正常动态模型
+
真实Pmeas
```

去判断：

> **设备是不是还符合正常执行。**

故障试验记录 `applied_pref` 的作用只是：

```text
我们作为实验者知道
设备实际上被我们强制成了什么
↓
以后分析MAT时
可以证明state=3不是“算法自己乱报”
而是真有执行失配
```

这叫：

而不是控制算法输入。

# 14. 策略2当前19个输出分别是什么？

## 14.1 六路 `Pexpected`

对应：

```text
PV1
PV2
ESS1
ESS2
EV1
EV2
```

它代表：

> **如果设备当前是正常的，根据最后可信命令和正常动态，此时此刻它应该响应到哪里。**

它不是：

```text
AGC命令
```

而是：

```text
AGC命令经过正常设备动态以后
此刻应该出现的功率
```

例如：

```text
cmd = 0.2 pu

刚下命令
Pexpected还接近旧值

过一段时间
Pexpected逐步逼近0.2

最后
Pexpected ≈ 0.2
```

## 14.2 六路 `residual`

定义：

```text
residual
=
平滑后的Pmeas
-
Pexpected
```

它有正负号。

例如：

```text
Pexpected = 0.20
Pmeas     = 0.18

residual = -0.02
```

表示：

```text
实际比预期偏低0.02 pu
```

真正判断失配时看的是：

```text
|residual|
```

---

## 14.3 六路 `state`

```text
0 = UNTRUSTED
1 = TRACKED
2 = RESPONDING
3 = MISMATCH
```

这是策略2以后给策略7最重要的信息。

## 14.4 `overall`

六台设备汇总状态。

优先级：

```text
MISMATCH
>
RESPONDING
>
TRACKED
```

因此：

```text
六台全TRACKED
→ overall = 1

至少一台RESPONDING
但没有MISMATCH
→ overall = 2

至少一台MISMATCH
→ overall = 3

当前数据不可信
→ overall = 0
```

注意：

> `overall` 只是执行层摘要，不等于策略7的系统状态。

它不能直接等价成：

```text
overall=3
→ 系统一定HOLD
```

是否HOLD属于策略7的职责。

# 15. `Pexpected` 在代码中到底怎样算？

V0.2内部参数：

```matlab
TAU = [0.47;0.47;0.50;0.50;0.52;0.52];
```

对应：

```text
PV1  0.47 s
PV2  0.47 s

ESS1 0.50 s
ESS2 0.50 s

EV1  0.52 s
EV2  0.52 s
```

代码：

```matlab
a = min(dt/max(TAU(i),1e-6),1.0);

pexp(i) = pexp(i) ...
        + a*(last_cmd(i)-pexp(i));
```

可以写成：

\[
P_{\mathrm{expected},i}(k)
=
P_{\mathrm{expected},i}(k-1)
+
\alpha_i
\left[
P_{\mathrm{cmd},i}(k)-P_{\mathrm{expected},i}(k-1)
\right]
\]

其中：

\[
\alpha_i
=
\min\left(\frac{\Delta t}{\tau_i},1\right)
\]

通俗理解：

```text
Pexpected不要瞬间跳到命令
↓
每个实时步只往新命令靠近一点
↓
靠近速度由tau决定
```

# 16. 为什么还要平滑 `Pmeas`？

原始100 Hz数据本身存在：

```text
约0.03 pu量级的正常瞬时波动
```

所以不能：

```text
原始Pmeas某一个采样点跳一下
↓
马上判异常
```

在线代码采用：

```matlab
TAU_MEAS = 0.10;
```

递推：

```matlab
am = min(dt/TAU_MEAS,1.0);

pfilt(i) = pfilt(i) ...
         + am*(Pmeas(i)-pfilt(i));
```

也就是：

> **对Pmeas做一个很轻的一阶低通平滑。**

注意：

```text
TAU_MEAS = 0.10 s
```

不是设备动态时间常数。

它只是测量平滑时间常数。

# 17. 为什么异常阈值不是固定值？

当前允许带：

```matlab
band_i = EPS0 + K_DYN*dyn_gap;
```

其中：

```matlab
EPS0 = 0.020;
K_DYN = 0.30;
```

而：

```matlab
dyn_gap = abs(last_cmd(i)-pexp(i));
```

所以：

\[
B_i
=
0.020
+
0.30
\left|
P_{\mathrm{cmd},i}-P_{\mathrm{expected},i}
\right|
\]

通俗理解：

### 稳态时

```text
Pexpected已经基本到命令
dyn_gap很小
```

于是允许带接近：

```text
0.02 pu
```

### 命令刚变化时

```text
Pexpected离新命令还很远
dyn_gap较大
```

于是允许带自动扩大。

意义：

> **设备正在正常过渡时，判断要宽松；设备已经进入稳态时，判断可以严格。**

这比一个固定阈值更符合物理过程。

# 18. 为什么不能一超阈值就判3？

因为真实测量可能有：

```text
纹波
瞬时扰动
数值波动
```

所以V0.2要求：

```matlab
T_BAD_CONFIRM = 0.30;
```

也就是：

> **只有残差连续超出允许带约0.30 s，才确认MISMATCH。**

代码逻辑：

```text
|residual| > band
↓
bad_timer持续累加

如果中途恢复正常
bad_timer清零

只有bad_timer ≥ 0.30 s
↓
state = 3
```

因此最终实际检测时间不是机械地：

```text
0.30 s
```

而是：

```text
测量滤波
+
Pexpected动态
+
允许带
+
持续确认
```

共同决定。

实际三类资源检测约：

```text
0.34～0.43 s
```

这和代码逻辑一致。

# 19. `RESPONDING` 到底怎样定义？

代码有两个条件：

```matlab
since_cmd(i) < T_RESP
```

或者：

```matlab
dyn_gap > SETTLE_GAP
```

其中：

```matlab
T_RESP = 1.60 s
SETTLE_GAP = 0.030 pu
```

只要：

```text
命令刚变化还没超过1.6 s
```

或者：

```text
Pexpected仍离命令大于0.03 pu
```

并且尚未确认失配：

```text
state = 2
```

也就是：

> **我现在看到了偏差，但它仍然可以被正常设备动态解释，因此不判故障。**

这是策略2区别于简单阈值判断的核心。


# 23. 为什么 `3 → 2 → 3` 从论文逻辑上不合理？

假设策略2已经有充分证据确认：

```text
PV1持续没有按正常动态执行
```

此时AGC又发了一条新命令。

新命令并不能证明：

```text
PV1突然恢复正常
```

所以不能：

```text
新命令
→ 自动把MISMATCH清掉
```

正确逻辑应该是：

```text
已经确认执行失配
↓
继续保持MISMATCH
↓
后续命令仍然更新Pexpected
↓
但只有真实Pmeas重新持续符合正常执行
↓
才解除MISMATCH
```

这就是V0.2。

# 24. V0.2最核心的新增机制：失配保持

V0.2增加：

```matlab
mismatch_latch
```

通俗理解：

> **“这台设备已经被确认执行失配”的记忆。**

一旦：

```text
bad_timer ≥ T_BAD_CONFIRM
```

则：

```matlab
mismatch_latch(i) = true;
state(i) = 3;
```

此后：

```text
AGC来了新命令
```

只会：

```text
更新last_cmd
重新推进新的Pexpected
```

但：

```text
不会清除mismatch_latch
```

所以：

```text
state持续保持3
```

# 25. V0.2怎样判断“真的恢复了”？

新增：

```matlab
good_timer
```

和：

```matlab
T_RECOVER_CONFIRM = 0.50;
```

但不是：

```text
残差一回来
马上解除3
```

恢复必须同时满足：

```text
① |residual| <= 当前动态允许带

② dyn_gap <= SETTLE_GAP
   即Pexpected本身已经接近当前命令

③ 上述情况连续保持至少0.50 s
```

也就是：

```text
真实设备重新跟上
+
预期模型也已经进入接近稳态
+
不是偶然一瞬间碰巧重合
```

才解除：

```text
MISMATCH
```

因此虽然：

```text
T_RECOVER_CONFIRM = 0.5 s
```

实际故障解除以后退出 `state=3` 会更慢。

因为还要等待：

```text
设备真实响应
+
Pexpected重新靠近命令
+
最后0.5 s连续确认
```

所以实测恢复时间约：

```text
1.9～2.6 s
```

这是合理的，不是代码“慢了2秒”。

```text
或
```

则：


这个区别以后V5非常重要。

# 33. 故障注入模型到底怎样制造“执行失配”？

以PV1为例：

原来：

```text

↓
PV1真实Pref
```

```text
                  ┌→ 正常AGC命令
                  │
AGC命令 ──────────┤
                  │
0 pu ─────────────┤
                  ↓
                Switch
                  ↓
             PV1真实Pref
```

Switch控制信号：

```text
25 s前：0
25～35 s：1
35 s后：0
```

因此：

```text
25 s前
PV1执行AGC命令

25～35 s
PV1实际执行0

PV1重新执行AGC命令
```


```text

原AGC命令

=
Switch后的故障值
```

这就是：

```text

↓

```

```text

```

只增加：

```text

```

其他试验条件全部不变。

这样才知道：

```text
结果改善到底是因为哪一个修改
```

这是非常重要的对照实验思想。
