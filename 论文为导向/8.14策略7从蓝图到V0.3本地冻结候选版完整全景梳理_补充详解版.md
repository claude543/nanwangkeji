# 0. 先记住最终结论：策略7到底是什么？

一句话：

> **策略7不是判断“哪台设备执行异常”的，也不是直接做六资源功率分配；策略7负责根据策略2给出的执行状态，决定整个协调控制系统当前应该处于什么管理阶段，以及此刻AGC到底还能不能继续推进。**

论文主线已经形成：

```text
策略2
回答：六台设备真实执行得怎么样？
        ↓
策略7
回答：根据这些真实执行状态，
系统现在该继续、暂停、对齐，还是受控恢复？
        ↓
改进AGC
回答：在允许继续调节时，
剩余可信资源到底怎样承担PCC调节任务？
```

因此三者最核心的职责分工是：

```text
策略2 = 识别现实
策略7 = 管理现实与控制器之间的协调状态
改进AGC = 在策略7允许的条件下进行资源功率分配
```

当前策略7已经发展成：

```text
0 = INACTIVE
1 = NORMAL
2 = HOLD
3 = RECONSTRUCTION
4 = RECOVERY
```

并进一步具备：

```text
持续执行失配
→ 监督层隔离该资源
→ 该资源 trust=0
→ 不再阻塞整个系统
→ 剩余可信资源继续恢复协调
```

# 1. 为什么策略2做完以后还必须有策略7？

策略2能回答：

```text
PV1现在执行正常吗？
PV2正常吗？
ESS1现在是正常响应，还是已经确认失配？
ESS2正常吗？
EV1、EV2现在是否可信？
```

但即使策略2已经告诉我们：

```text
ESS1 = MISMATCH
```

系统仍然没有回答：

```text
发现ESS1失配以后，AGC还要不要继续每1 s更新一次？

是立刻继续算新的功率分配，还是先暂停？

设备恢复以后，能不能直接重新进入NORMAL？

AGC内部保存的Ppv/Pess/Pev
如果已经和真实设备状态不一致，
要不要先重新对齐？

恢复时是一步把全部PCC误差重新交给AGC，
还是逐渐放开？

如果ESS1一直坏着，
是不是整个系统永远HOLD？
还是把ESS1临时剔除，剩下5台设备继续调节？
```

这些都不是“执行状态识别”问题，而是：

> **系统级协调状态管理问题。**

所以策略7就是策略2和AGC之间必须存在的监督层。

# 2. 原始策略7是什么？为什么不够？

项目原始15策略中的策略7，本质上仍是联络线有功偏差：

```text
tieErr = Ppcc - Ptarget
cmd(7) = -tieErr
       = Ptarget - Ppcc
```

而原策略2也基本是：

```text
cmd(2) = Ptarget - Ppcc
```

所以原始策略2和策略7高度重复：

```text
策略2：看PCC误差
策略7：还是看PCC误差
```

如果论文直接写：

```text
策略2 + 策略7
```

就没有形成真正的：

```text
识别层 → 监督层 → 分配层
```

因此策略7必须从“另一个PCC误差计算块”改造成：

> **联络线协调 + 异常保持 + 状态对齐 + 受控恢复管理器。**

# 3. 策略7在整个论文架构中的准确位置

当前最准确的结构是：

```text
PCC真实功率、六设备Pmeas
        +
当前可信命令
        ↓
策略2
Execution-State Assessment（执行状态评估）
        ↓
六设备 state：0 / 1 / 2 / 3
        ↓
策略7
Coordination + Recovery Management（协调与恢复管理）
        ↓
mode
 dP_request
 agc_update_allowed
 reconstruction_request
 trust1~6
 isolation状态
        ↓
改进AGC
状态对齐 + 有效能力重分配
        ↓
六资源新命令
```

最重要的是：

> **策略7本身不负责算“PV1具体应该变成0.42 pu还是0.46 pu”。**

它只决定：

```text
现在是否允许AGC算？
允许AGC处理多少dP？
哪些资源还能被认为是可调可信资源？
现在是否需要先重新对齐AGC内部状态？
```

# 4. 为什么最终采用四状态，而不是简单NORMAL/HOLD？

如果只有：

```text
NORMAL
HOLD
```

那么异常解除后只能：

```text
HOLD → NORMAL
```

问题是HOLD期间：

```text
设备可能继续有物理动态
真实设备已经到达新的Pmeas
AGC内部Ppv/Pess/Pev却停留在旧记忆
```

若异常解除瞬间直接NORMAL：

```text
AGC会基于错误内部状态继续分配
```

所以必须增加：

```text
RECONSTRUCTION
```

专门做：

> **控制器内部资源状态与真实执行状态重新对齐。**

而即使状态对齐完成，如果直接：

```text
RECONSTRUCTION → NORMAL
```

又可能把完整PCC误差一次性交回AGC，因此还需要：

```text
RECOVERY
```

用于：

> **受控地重新释放调节权限，而不是瞬间恢复全部动作。**

最终：

```text
NORMAL
↓ 异常确认
HOLD
↓ 异常解除 / 异常资源被管理
RECONSTRUCTION
↓ 状态对齐完成
RECOVERY
↓ 恢复过程完成
NORMAL
```

# 5. 四个状态到底分别是什么意思？

## 5.1 INACTIVE = 0

表示策略7没有投入。

当前代码中当：

```text
enable <= 0.5
```

会清空：

```text
mode
各类计时器
isolation latch
HOLD原因
```

这是算法真正的停用/初始化状态。

## 5.2 NORMAL = 1

表示当前没有“尚未被管理”的异常阻止协调控制继续进行。

此时：

```text
dP_raw = Ptarget - Ppcc
dP_request = dP_raw
agc_update_allowed = 1
```

V0.3中，即使某台资源已经被隔离，只要剩余系统稳定，也可以回到：

```text
mode = NORMAL
reason = 9
```

因此必须理解：

```text
NORMAL ≠ 六台设备全部健康
NORMAL = 当前不存在尚未被管理的异常阻止剩余系统继续协调
```

## 5.3 HOLD = 2

表示当前发现了需要先阻止AGC继续推进的异常，例如：

```text
某设备state=3
命令证据无效
测量证据无效
执行状态不可评估
```

此时：

```text
dP_request = 0
agc_update_allowed = 0
```

最重要的是：

> **HOLD不是把PCC误差变没，而是暂时不允许AGC继续依据这个误差改变内部资源分配状态。**

## 5.4 RECONSTRUCTION = 3

表示：

> 在重新允许AGC继续计算前，先把AGC内部六资源分配记忆重新放到接近现实的位置。

此时：

```text
reconstruction_request = 1
agc_update_allowed = 0
dP_request = 0
```

AGC完成后返回：

```text
reconstruction_done = 1
```

策略7收到后才能进入RECOVERY。

## 5.5 RECOVERY = 4

表示状态对齐完成后，逐步把闭环调节能力交还AGC。

当前本地版：

```text
recovery_alpha：0 → 1
```

并：

```text
dP_request = recovery_alpha × dP_raw
```

当前候选：

```text
T_RECOVERY_RAMP = 2.00 s
T_RECOVERY_CONFIRM = 0.50 s
```

# 6. 为什么HOLD不是“把设备命令清零”？

当前策略7的HOLD做的是：

```text
停止AGC内部资源分配继续推进
```

不是：

```text
把六台逆变器Pref全部置0
```

所以：

```text
HOLD = 监督层冻结新的协调分配动作
```

而不是：

```text
HOLD = 物理设备紧急停机
```

这对论文非常重要，因为我们研究的是控制状态管理，不是保护跳闸逻辑。

---

# 7. 为什么恢复斜坡作用于dP_request，而不是直接插值六路命令？

我们没有让策略7直接做：

```text
六个旧命令 → 六个新命令的线性插值
```

而是做：

```text
dP_request = alpha × dP_raw
```

这样：

```text
策略7决定“允许处理多少”
AGC决定“谁具体处理多少”
```

好处：

1. 策略7仍然只是监督层；
2. 六资源分配逻辑仍集中在AGC；
3. 不会出现两个功率分配器职责冲突；
4. 后续有效能力重分配仍能自然接入。

# 8. 策略7 V0.1：第一版为什么先做影子版？

第一版文件：

```text
Strategy7_Coordination_Recovery_V01_SCALAR.m
ADD_STRATEGY7_V01_SHADOW.m
```

当时它只：

```text
计算mode、dP_request、trust等
↓
记录到MAT
↓
不真正控制AGC
```

原因是：

> **新监督算法第一次加入模型时，先shadow验证状态逻辑，再active integration，是更稳妥的工程方法。**

否则状态机一旦有错误，就会直接改变六台设备命令。

# 10. 15个输入分别起什么作用？

## t

Target时间，用于所有持续时间判据和恢复斜坡。

## enable

当前本地复用AGC Enable。

```text
enable=0 → 真正停用和初始化策略7
enable=1 → 投入策略7
```

## Ptarget / Ppcc

形成：

```text
dP_raw = Ptarget - Ppcc
```

其中：

```text
Ptarget
= PCC联络线有功目标

Ppcc
= 当前真实PCC有功功率
```

它们回答的是：

> **系统现在客观上还差多少有功功率需要协调。**

---

## cmd_valid：当前“命令依据”是否可信？

这是一个非常容易误解的量。

策略2要判断某台设备有没有正常执行，必须同时知道两件事：

```text
第一件：
“我认为设备应该执行什么？”

第二件：
“设备实际上做到了什么？”
```

`cmd_valid`负责第一件事中的“可信性判断”。

最通俗地说：

> **cmd_valid = 我现在手里这条‘设备应该执行的命令’到底能不能相信。**

### 当前本地阶段

现在我们没有真实板端通信异常，因此直接设：

```text
cmd_valid = 1
```

意思是：

```text
当前命令来源明确
可以拿它作为策略2正常响应预测的起点
```

### V5以后为什么它会变得重要？

V5以后命令链不再只是一个简单的“AGC算出来多少”。

而要区分：

```text
u_calc
= 板端当前刚算出来的候选命令

u_commit
= 最后一次真正成功提交/下发的命令

u_applied
= 设备最终真实采用的命令
```

例如：

```text
板端刚算出：
ESS1 = +0.40 pu

但是FC16写失败
```

那么：

```text
u_calc = +0.40 pu
```

并不代表设备真的收到了：

```text
+0.40 pu
```

如果策略2仍然拿 `u_calc` 去预测：

```text
“ESS1现在应该向0.40 pu响应”
```

这个预测起点本身就是错的。

所以V5最终应该围绕：

```text
最后成功提交的u_commit
```

建立命令依据。

`cmd_valid`未来大致回答：

> **当前是否存在一条足够可信、足够新鲜的最后成功提交命令，可以拿来预测设备正常响应？**

最终它可能结合：

```text
FC16成功/失败
CMD_SEQ
最后成功commit时间
板端heartbeat
通信状态
```

形成，但**具体V5定义现在还没有冻结**。

## meas_valid：当前“测量依据”是否可信？

它对应另一边：

```text
Pmeas
```

最通俗地说：

> **meas_valid = 我现在看到的设备实测功率，是不是一份可信而且足够新的现实证据。**

例如板端读到：

```text
ESS1_P_MEAS = +0.25 pu
```

还需要问：

```text
这是刚刚读到的新值吗？

还是通信中断前残留的旧值？

FC03本轮成功了吗？

这批六设备测量是不是来自同一批有效快照？
```

### 当前本地阶段

现在模型内部直接获得Pmeas：

```text
meas_valid = 1
```

### V5以后

它可能需要结合：

```text
FC03成功/失败
测量数据新鲜度
最后更新时间
RT-LAB heartbeat
测量范围有效性
```

来形成。

最终意义仍然是：

> **只有当测量证据可信时，策略2和策略7才能把它当成“现实”。**

## 为什么cmd_valid和meas_valid一定要分成两个输入？

因为现实中存在四种情况：

| cmd_valid | meas_valid | 实际含义 |
|---:|---:|---|
| 1 | 1 | 命令依据和测量依据都可信，可以进行执行状态判断 |
| 0 | 1 | 看得到设备，但不知道它最后真正收到哪条命令 |
| 1 | 0 | 知道最后成功下发什么，但看不到设备现在真正做到哪里 |
| 0 | 0 | 命令和测量两边证据都不可靠 |

所以：

```text
通信不可观
```

不能简单等同于：

```text
设备执行故障
```

这也是V0.3为什么规定：

```text
如果全局cmd_valid / meas_valid失效
→ 先HOLD
→ 不直接累计某台设备的isolation timer
```

因为：

> **证据本身都不可信时，没有资格直接宣布某台设备物理执行异常。**

## reconstruction_done：AGC“重新对账已经完成”的返回确认

这个输入来自AGC。

策略7进入：

```text
RECONSTRUCTION
```

以后输出：

```text
reconstruction_request = 1
```

要求AGC：

```text
把内部Ppv / Pess / Pev
重新对齐当前现实执行状态
```

AGC完成以后返回：

```text
reconstruction_done = 1
```

所以它是：

> **AGC告诉策略7：“这一次内部资源状态已经重新对齐完成，可以准备进入RECOVERY。”**

---

## recovery_done：恢复阶段是否已经由外部确认完成？

这个输入与 `reconstruction_done` 不一样。

```text
reconstruction_done
= 状态对齐完成没有？

recovery_done
= 整个恢复阶段可以结束没有？
```

### 当前本地阶段

我们现在实际上设置：

```text
recovery_done = 0
```

因为当前V0.2/V0.3由策略7自己的内部时间逻辑决定：

```text
alpha达到1
+
再稳定T_RECOVERY_CONFIRM
→ RECOVERY → NORMAL
```

所以目前不依赖外部 `recovery_done`。

### 为什么仍然保留这个输入？

因为V5以后，可能出现：

```text
板端安全状态机
更高层恢复管理器
真实通信恢复判据
资源重新加入管理器
```

其中某个模块拥有更可靠的“恢复完成”证据。

那它就可以通过：

```text
recovery_done = 1
```

明确告诉策略7：

> **外部已经确认恢复条件满足，可以结束RECOVERY。**

当前代码允许：

```text
外部recovery_done=1
        或
内部恢复时间判据满足
        ↓
RECOVERY → NORMAL
```

所以它目前属于：

> **为V5真实恢复握手预留的接口。**

---

## recovery_alpha / recovery_alpha_external：外部最多允许恢复到什么程度？

它也是一个未来接口。

最通俗理解：

> **recovery_alpha_external = 外部系统允许当前恢复“开到几成”。**

范围：

```text
0 ~ 1
```

例如：

```text
0
= 完全不要重新放开控制

0.3
= 当前最多只允许恢复30%

0.7
= 当前最多允许恢复70%

1
= 可以完全恢复
```

### 当前本地阶段

我们主要使用策略7自己生成的：

```text
alpha_internal
```

当前 `recovery_alpha_external` 没有真正参与限制，通常设为0，表示：

```text
没有外部alpha限制
→ 使用内部alpha
```

### 当前代码怎样处理？

大意是：

```text
如果external alpha > 0：

alpha_used
=
min(alpha_internal, alpha_external)

否则：

alpha_used
=
alpha_internal
```

例如：

```text
alpha_internal = 0.8

但外部只允许：
alpha_external = 0.4
```

最终：

```text
alpha_used = 0.4
```

也就是说：

> **内部觉得可以恢复80%，但外部安全/通信条件只允许40%，最终只放开40%。**

所以它不是：

```text
设备健康度
资源分配权重
SOC权重
```

它只是：

> **恢复过程的外部权限上限。**

V5以后到底需不需要真正使用这个接口，要结合真实板端结构再决定。

## 11.1 mode：系统“现在正在做什么”

`mode` 是策略7真正的主状态。

当前固定有5种：

| mode | 名称 | 通俗含义 |
|---:|---|---|
| 0 | INACTIVE | 策略7未投入 |
| 1 | NORMAL | 正常协调，AGC正常处理PCC误差 |
| 2 | HOLD | 先暂停AGC正常状态继续推进 |
| 3 | RECONSTRUCTION | 正在让AGC重新对齐内部六资源状态 |
| 4 | RECOVERY | 状态对齐后，正在逐步恢复正常协调 |

因此：

```text
mode
```

回答的是：

> **“整个协调控制系统此刻处于哪个控制阶段？”**

例如：

```text
mode = 2
```

只能说明：

```text
现在处于HOLD
```

但还没有告诉你：

```text
为什么HOLD？
```

这就是 `reason` 的作用。

---

## 11.2 reason：系统“为什么处在这个状态”

最简单一句话：

```text
mode
= 我现在在干什么

reason
= 我为什么会处在这里
```

当前主要编码：

| reason | 含义 |
|---:|---|
| 0 | inactive，策略7未投入 |
| 1 | normal，正常协调 |
| 2 | execution mismatch，执行状态失配 |
| 3 | command invalid，命令证据无效 |
| 4 | measurement invalid，测量证据无效 |
| 5 | command + measurement invalid，两边证据都无效 |
| 6 | reconstruction，正在状态对齐 |
| 7 | recovery，正在恢复 |
| 8 | execution state untrusted，当前执行状态不可可信评估 |
| 9 | normal with managed isolated resource，已有资源被隔离但剩余系统正常协调 |

例如同样都是：

```text
mode = 2 HOLD
```

可能出现：

```text
mode = 2
reason = 2
```

表示：

```text
因为设备执行失配而HOLD
```

也可能：

```text
mode = 2
reason = 3
```

表示：

```text
因为命令证据不可信而HOLD
```

还可能：

```text
mode = 2
reason = 4
```

表示：

```text
因为测量证据不可信而HOLD
```

一个更重要的例子：

```text
mode = 1
reason = 1
```

表示：

```text
六资源正常协调
```

而：

```text
mode = 1
reason = 9
```

表示：

```text
系统已经恢复正常协调，
但例如ESS1仍处于isolated状态，
现在是剩余5台资源维持的“降级正常协调”
```

所以：

> **mode用于状态机控制，reason用于解释和诊断状态。**

---

## 11.3 reconstruction_request：策略7向AGC发出的“重新对账请求”

当策略7进入：

```text
mode = 3 RECONSTRUCTION
```

它输出：

```text
reconstruction_request = 1
```

它不是一个设备功率命令。

它的意思是：

> **“AGC，暂时不要继续算新的PCC功率分配，先把你内部保存的Ppv/Pess/Pev重新对齐当前真实执行状态。”**

完整握手：

```text
Strategy7：
reconstruction_request = 1
            ↓
AGC：
使用Pexec1~6
重新写入内部Ppv/Pess/Pev
            ↓
AGC：
reconstruction_done = 1
            ↓
Strategy7：
确认状态对齐完成
            ↓
进入RECOVERY
```

所以：

```text
reconstruction_request
```

是：

> **策略7对AGC发出的“状态对齐动作请求”。**

而：

```text
reconstruction_done
```

是AGC返回的：

> **“状态已经对齐完成”的确认。**

---

## 11.4 recovery_active：当前是否正在恢复

它最简单：

```text
mode = RECOVERY
→ recovery_active = 1

其他mode
→ recovery_active = 0
```

所以：

> **recovery_active = 当前系统是否处于受控恢复阶段的显式标志。**

当前版本里真正决定AGC动作的主要还是：

```text
dP_request
agc_update_allowed
recovery_alpha_used
```

`recovery_active`目前主要用于：

```text
Target MAT记录
SC在线观察
以后给其他模块作为状态接口
```

它不是现在直接生成六设备功率命令的量。

---

## 11.5 把四个输出放在一起理解

```text
mode
= 我现在在哪个控制阶段

reason
= 为什么处在这个阶段

reconstruction_request
= 如果现在处于RECONSTRUCTION，
  是否正在要求AGC重新对齐内部状态

recovery_active
= 如果现在处于RECOVERY，
  是否明确告诉其他模块“正在恢复”
```

例如：

```text
mode = 3
reason = 6
reconstruction_request = 1
recovery_active = 0
```

意思是：

> 当前正在状态对齐，策略7正在请求AGC重新对账，还没有进入恢复。

再例如：

```text
mode = 4
reason = 7
reconstruction_request = 0
recovery_active = 1
```

意思是：

> 对账已经结束，现在处于逐步恢复阶段。

# 12. dP_raw和dP_request为什么一定要分开？

这是策略7最重要的架构思想之一。

```text
dP_raw = 现实世界真正存在的PCC偏差
```

而：

```text
dP_request = 当前监督状态允许交给AGC处理的偏差
```

例如HOLD时：

```text
dP_raw = -40 kW
dP_request = 0
```

不是PCC误差消失，而是：

> 我知道有40 kW误差，但当前先不允许AGC继续追这个误差。

# 13. agc_update_allowed到底冻结什么？

它控制的是：

> **AGC内部 `Ppv/Pess/Pev` 是否允许执行下一次正常分配更新。**

不是控制物理设备是否还能响应。

在HOLD中：

```text
agc_update_allowed = 0
```

后来MAT明确验证到：

```text
HOLD期间六路AGC命令停止继续推进
```

所以策略7不是仅做状态记录，而是真正接管了AGC更新权限。

---

# 14. trust1~6到底是什么？

当前trust是0/1，表示：

> **这台资源当前是否可以被AGC作为可信调节资源使用。**

V0.1/V0.2：

```text
state=1或2 → trust=1
state=0或3 → trust=0
```

如果全局命令/测量证据无效，当前语义下六路trust都置0。

V0.3以后：

```text
isolated=1 → trust强制为0
```

所以最终：

```text
trust=1
需要：
数据有效
+ 未被隔离
+ state属于TRACKED/RESPONDING
```

# 15. reason输出为什么存在？

mode只告诉你“在哪个状态”，reason告诉你“为什么”。

当前主要编码：

```text

1 normal
2 execution mismatch
3 command invalid
4 measurement invalid
5 command & measurement invalid
6 reconstruction
7 recovery
8 execution state untrusted
9 normal coordination with managed isolated resource
```

其中 `reason=9` 表示：

> 系统已经回NORMAL，但有资源被监督层隔离，属于降级正常协调。

# 19. 为什么一定要加100 μs Unit Delay？

当前RT-LAB基本步长：

```text
Ts = 100 μs
```

如果两端MATLAB Function直接反馈，容易形成同一步代数环。

加入Unit Delay后变成：

```text
k时刻的监督决策
↓
k+1实时步被另一模块使用
```

100 μs相对于：

```text
AGC周期 = 1 s
设备动态 = 约1 s量级
```

可以忽略，但从实时因果结构上非常重要。

# 22. Pexec为什么来自策略2？“状态识别和状态对齐使用同一套现实执行估计”到底是什么意思？

这是理解策略2和策略7/AGC怎样衔接的关键。

---

## 22.1 策略2手里本来就有两条功率曲线

策略2在判断一台设备执行是否正常时，会构造：

```text
Pexpected
=
如果设备正常执行当前可信命令，
按照已识别的正常动态，
它现在理论上应该到哪里
```

同时还有：

```text
filtered Pmeas
=
设备真实Pmeas经过TAU_MEAS滤波以后，
得到的较平滑现实执行值
```

然后策略2计算：

```text
residual
=
filtered Pmeas - Pexpected
```

例如：

```text
Pexpected = 0.40 pu

filtered Pmeas = 0.25 pu
```

那么：

```text
residual = -0.15 pu
```

通俗解释：

> **正常情况下应该做到0.40 pu，但现实只做到了0.25 pu，所以比预期少了0.15 pu。**

---

## 22.2 为什么又定义Pexec_est？

我们定义：

```text
Pexec_est
=
Pexpected + residual
```

代入：

```text
residual
=
filtered Pmeas - Pexpected
```

得到：

```text
Pexec_est
=
Pexpected
+
(filtered Pmeas - Pexpected)
```

前后抵消：

```text
Pexec_est
=
filtered Pmeas
```

所以：

> **Pexec_est本质上就是策略2已经平滑处理后的“当前真实执行功率估计”。**

这里的名字之所以叫：

```text
Pexec_est
```

是为了强调它在后续AGC里承担的是：

```text
execution estimate
= 当前执行状态估计
```

而不是普通原始测量量。

---

## 22.3 “状态识别和状态对齐使用同一套现实执行估计”是什么意思？

假设策略2现在判断ESS1异常时使用：

```text
filtered Pmeas = 0.25 pu
```

于是策略2的结论实际上基于：

```text
“我认为ESS1当前现实执行大约是0.25 pu”
```

随后策略7进入：

```text
RECONSTRUCTION
```

如果这时AGC又另外直接拿：

```text
某一瞬间raw Pmeas = 0.30 pu
```

作为状态对齐值，就会出现：

```text
策略2眼里的现实：
0.25 pu

AGC眼里的现实：
0.30 pu
```

即：

> **同一套论文算法链对“设备现在到底执行到哪里”出现了两个不同答案。**

这会让方法逻辑变得不一致。

所以我们统一：

```text
策略2判断执行状态
→ 使用filtered Pmeas

AGC重新对齐内部状态
→ 也使用同一个filtered Pmeas
```

也就是：

> **用同一把尺子看现实。**

这就是文档里那句话：

> “状态识别和状态对齐使用同一套现实执行估计，避免重复建模。”

---

## 22.4 为什么不让AGC自己再建一套滤波/执行估计器？

如果AGC重新做：

```text
另一套Pmeas滤波
另一套设备动态估计
另一套执行状态计算
```

就会造成：

```text
Strategy2一套现实估计

AGC又一套现实估计
```

不仅重复，而且两套参数稍有不同就可能互相矛盾。

所以当前架构明确：

```text
Strategy2
负责“看清现实”

AGC
直接使用Strategy2已经形成的现实执行估计
```

这也保持职责分层。

---

## 22.5 为什么不直接使用原始瞬时Pmeas？

因为设备Pmeas存在：

```text
100 Hz纹波
瞬时电气波动
局部动态
```

如果RECONSTRUCTION那一瞬间直接：

```text
Ppv = raw Pmeas
```

AGC内部长期记忆可能被某个瞬时纹波值带偏。

策略2已经有：

```text
TAU_MEAS = 0.10 s
```

的测量平滑，所以我们直接复用：

```text
filtered Pmeas
```

作为更稳定的现实执行起点。

---

## 22.6 新增的AGC输入Pexec1~6到底是干什么的？

最终给AGC新增六个输入：

```text
Pexec_PV1
Pexec_PV2
Pexec_ESS1
Pexec_ESS2
Pexec_EV1
Pexec_EV2
```

它们不是：

```text
六台设备新的功率控制命令
```

而是：

> **AGC执行RECONSTRUCTION时，用来重新设置自己内部六资源分配记忆的“状态对齐目标值”。**

正常NORMAL阶段：

```text
Pexec1~6
不会每100 μs覆盖AGC内部状态
```

只有：

```text
reconstruction_request = 1
```

时，AGC才执行一次：

```text
Ppv  ← Pexec_PV

Pess ← Pexec_ESS

Pev  ← -Pexec_EV
       （注意EV内部保存正充电幅值）
```

所以可以把：

```text
Pexec1~6
```

理解成：

> **“重新对账时，现实账本上这六台设备现在分别是多少。”**

---

## 22.7 最通俗的“账本”比喻

假设AGC内部账本写着：

```text
ESS1 = +0.20 pu
```

但策略2根据平滑Pmeas判断现实是：

```text
ESS1 ≈ +0.30 pu
```

策略2已经说：

```text
“现场现实大约是+0.30 pu”
```

那么进入RECONSTRUCTION以后，AGC就不应该再自己重新猜。

而应该直接：

```text
Pess1内部记忆
0.20
→
0.30
```

这就是：

```text
状态识别
和
状态对齐
```

使用同一套现实执行估计。

---

# 23. 为什么最初MAT里看不到RECONSTRUCTION？

第一次真实握手时：

```text
RECONSTRUCTION
→ AGC很快done
→ Strategy7很快进入RECOVERY
```

可能只有几个100 μs步。

但OpWrite约：

```text
100 Hz = 10 ms一个记录点
```

所以真实发生的：

```text
mode=3
reconstruction_request=1
reconstruction_done=1
```

可能刚好落在记录点之间。

这不是逻辑错误，而是可观测性问题。

---

# 24. 为什么V0.2增加50 ms RECONSTRUCTION最小停留？

我们没有为了看见状态而把全部OpWrite提高到高频，而是让监督状态本身有合理驻留时间：

```text
T_RECON_MIN = 0.05 s
```

100 Hz下约5个点。

意义有两层：

1. 日志明确可见；
2. 状态机握手更稳健。

---

# 25. Strategy7 V0.2到底加入了什么？为什么alpha反复出现？

文件：

```text
Strategy7_Coordination_Recovery_V02_SCALAR.m
UPDATE_STRATEGY7_V01_TO_V02_FULL_LOCAL_CYCLE.m
```

V0.2主要完成：

```text
1. RECONSTRUCTION最小保持50 ms
2. RECOVERY内部alpha斜坡
3. RECOVERY自动返回NORMAL
```

于是第一次真正形成：

```text
NORMAL → HOLD → RECONSTRUCTION → RECOVERY → NORMAL
```

---

## 25.1 alpha到底是什么？

一句话：

> **alpha = RECOVERY阶段的“控制权限开度”。**

范围：

```text
0 ≤ alpha ≤ 1
```

它不是：

```text
设备健康度

不是trust

不是PV/ESS/EV资源分配权重

不是SOC权重
```

它只回答：

> **状态对齐完成以后，当前要把多少比例的PCC调节任务重新交给AGC？**

---

## 25.2 为什么不能RECONSTRUCTION结束就直接NORMAL？

假设状态对齐完成时：

```text
dP_raw = +40 kW
```

如果直接：

```text
RECONSTRUCTION
→ NORMAL
```

下一次AGC可能马上收到：

```text
dP_request = +40 kW
```

也就是说：

```text
刚刚把AGC内部账本重新对齐
↓
下一刻就把完整40 kW误差全部交给AGC
```

恢复动作可能过于突然。

因此我们增加：

```text
RECOVERY
```

在这个阶段逐渐放开调节权限。

---

## 25.3 alpha怎样作用？

核心公式：

```text
dP_request
=
alpha × dP_raw
```

例如：

```text
dP_raw = 40 kW
```

刚进入RECOVERY：

```text
alpha = 0

dP_request = 0
```

随后：

```text
alpha = 0.25

dP_request = 10 kW
```

再后来：

```text
alpha = 0.50

dP_request = 20 kW
```

最终：

```text
alpha = 1

dP_request = 40 kW
```

最通俗比喻：

```text
alpha = 水龙头开度

dP_raw = 水源里客观存在的水压/需求

dP_request = 当前真正允许流给AGC的那部分
```

所以：

```text
alpha=0
→ 水龙头关着

alpha=0.5
→ 开一半

alpha=1
→ 全开
```

## 25.4 为什么alpha作用在dP_request，而不是直接乘六路设备命令？

因为如果策略7直接做：

```text
PV命令 × alpha
ESS命令 × alpha
EV命令 × alpha
```

策略7就开始决定六资源具体功率。

那它会和AGC职责重叠。

当前明确分层：

```text
Strategy7
= 决定“允许处理多少总PCC误差”

AGC
= 决定“这些功率具体由谁承担”
```

因此：

```text
alpha
只作用于dP_request
```

而不是直接作用于六路Pref。

## 25.5 alpha_internal、alpha_external、alpha_used有什么区别？

### alpha_internal

策略7自己根据恢复时间生成：

```text
0 → 1
```

当前由：

```text
T_RECOVERY_RAMP
```

控制上升速度。

### alpha_external

未来外部系统可以给出的恢复权限上限。

例如：

```text
内部认为：
alpha_internal = 0.8

但外部安全条件只允许：
alpha_external = 0.4
```

最终只能：

```text
alpha_used = 0.4
```

### alpha_used

真正进入：

```text
dP_request = alpha_used × dP_raw
```

的最终恢复系数。

当前代码大意：

```text
如果没有外部限制：
alpha_used = alpha_internal

如果存在外部限制：
alpha_used = min(alpha_internal, alpha_external)
```

因此文档里反复出现alpha，是因为它贯穿整个RECOVERY阶段：

```text
RECOVERY开始
→ alpha≈0

恢复进行中
→ alpha逐渐增加

恢复接近完成
→ alpha≈1

alpha=1后再稳定确认
→ NORMAL
```

# 27. V0.2/V0.3四个核心时间参数到底分别在管什么？

当前本地候选参数：

```text
T_CLEAR_CONFIRM    = 0.50 s
T_RECON_MIN        = 0.05 s
T_RECOVERY_RAMP    = 2.00 s
T_RECOVERY_CONFIRM = 0.50 s
```

它们不是四个随便堆出来的延时。

最容易记的方式：

```text
T_CLEAR_CONFIRM
= “异常真的消失了吗？”

T_RECON_MIN
= “状态对齐阶段至少待多久？”

T_RECOVERY_RAMP
= “恢复权限从0开到100%要多久？”

T_RECOVERY_CONFIRM
= “已经全开以后还要稳定多久，才正式回NORMAL？”
```

---

## 27.1 T_CLEAR_CONFIRM = 0.50 s：异常消失确认时间

它发生在：

```text
HOLD
```

阶段。

例如ESS1原来：

```text
state = 3 MISMATCH
```

突然某一个时刻变成：

```text
state = 1 TRACKED
```

我们不能立即：

```text
HOLD → RECONSTRUCTION
```

因为可能只是一个瞬间正常点，下一刻又回到：

```text
state = 3
```

所以要求：

```text
异常连续消失0.50 s
```

才认为：

```text
“恢复证据足够稳定”
```

然后允许：

```text
HOLD → RECONSTRUCTION
```

通俗比喻：

> **不是看到病人一次体温正常就宣布康复，而是要连续稳定一段时间。**

所以：

```text
T_CLEAR_CONFIRM
```

回答的是：

> **异常解除证据要持续多久，我才相信它真的解除？**

---

## 27.2 T_RECON_MIN = 0.05 s：状态对齐阶段最小驻留时间

它发生在：

```text
RECONSTRUCTION
```

阶段。

我们第一次真实握手时实际发现：

```text
Strategy7进入RECONSTRUCTION
↓
AGC几个100 μs实时步就完成状态对齐
↓
立刻进入RECOVERY
```

而正式Target OpWrite只有：

```text
100 Hz
=
每10 ms记录一次
```

结果MAT看起来像：

```text
HOLD
→
RECOVERY
```

中间的：

```text
RECONSTRUCTION
```

完全看不到。

所以加入：

```text
T_RECON_MIN = 0.05 s
```

要求进入RECOVERY必须同时满足：

```text
reconstruction_done = 1

并且

RECONSTRUCTION已经至少持续0.05 s
```

0.05 s = 50 ms。

对于100 Hz日志：

```text
50 ms / 10 ms
≈ 5个记录点
```

所以它有两个作用：

```text
作用1：
让RECONSTRUCTION成为明确稳定的监督阶段

作用2：
让正式MAT能够清楚记录
mode=3 / request=1 / done=1
```

---

## 27.3 T_RECOVERY_RAMP = 2.00 s：alpha从0升到1的时间

它发生在：

```text
RECOVERY
```

阶段。

当前本地版近似：

```text
alpha_internal
=
recovery_timer / T_RECOVERY_RAMP
```

再限制在：

```text
0~1
```

因此：

```text
RECOVERY刚开始：
0 s
alpha ≈ 0

0.5 s：
alpha ≈ 0.25

1.0 s：
alpha ≈ 0.50

1.5 s：
alpha ≈ 0.75

2.0 s：
alpha = 1
```

也就是说：

> **T_RECOVERY_RAMP决定恢复控制权限“开闸”的速度。**

如果很短：

```text
恢复快
但控制动作可能更突然
```

如果很长：

```text
恢复更平滑
但PCC误差恢复更慢
```

当前：

```text
2.00 s
```

只是V5前本地候选值，不是最终最优参数。

---

## 27.4 T_RECOVERY_CONFIRM = 0.50 s：完全恢复后的稳定确认时间

当：

```text
alpha = 1
```

时，说明：

```text
dP_request = dP_raw
```

也就是已经把全部正常PCC调节权限重新交回AGC。

但我们仍不立刻：

```text
RECOVERY → NORMAL
```

而是再观察：

```text
0.50 s
```

如果这段时间：

```text
没有新的未管理异常
```

才正式：

```text
RECOVERY → NORMAL
```

所以：

> **T_RECOVERY_CONFIRM = 控制权限已经100%恢复以后，再确认系统确实稳定多久。**

它和：

```text
T_CLEAR_CONFIRM
```

看起来都是0.5 s，但位置完全不同。

```text
T_CLEAR_CONFIRM
= HOLD结束前
  确认“故障真的消失/已经不再阻塞”

T_RECOVERY_CONFIRM
= RECOVERY结束前
  确认“全部控制权限恢复后仍然稳定”
```

## 27.5 把四个时间参数放在一次可恢复故障里完整串起来

假设ESS1发生故障：

```text

↓
Strategy7进入HOLD
```

后来ESS1恢复。

第一阶段：

```text

↓
连续稳定0.50 s
T_CLEAR_CONFIRM
↓
允许离开HOLD
```

第二阶段：

```text

↓
AGC执行内部Ppv/Pess/Pev状态对齐
↓
即使done很快变1
也至少保持0.05 s
T_RECON_MIN
```

第三阶段：

```text

↓
alpha在2.00 s内
0 → 1
T_RECOVERY_RAMP
```

第四阶段：

```text
alpha=1
↓
再稳定0.50 s
T_RECOVERY_CONFIRM
↓
进入NORMAL
```

所以从：

```text

```

到：

```text
正式NORMAL
```

在没有新异常的理想情况下，大约：

```text
2.00 + 0.50
=
2.50 s
```

这正好与我们V0.2实际MAT中：

```text
RECONSTRUCTION → RECOVERY
到
RECOVERY → NORMAL
```

约2.5 s的现象一致。

# 52. 策略7与普通HOLD有什么区别？

普通HOLD可能只是：

```text
异常
→ 保持上一命令
→ 通信恢复
→ resume
```

我们现在的链：

```text
发现执行失配
↓
冻结AGC继续推进
↓
区分短时恢复与持续异常
↓
必要时监督隔离异常资源
↓
重新对齐AGC内部资源状态
↓
受控释放dP_request
↓
剩余资源继续协调
```

论文价值不在“HOLD这个动作”，而在HOLD前后的完整证据与恢复链条。

```text

→ isolated=1
→ trust=0
→ 剩下5台资源继续恢复协调
```

这就是策略7。
