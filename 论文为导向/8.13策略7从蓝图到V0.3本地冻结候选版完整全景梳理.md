# 0. 先记住最终结论：策略7到底是什么？

一句话：

> **策略7不是判断“哪台设备执行异常”的，也不是直接做六资源功率分配；策略7负责根据策略2给出的执行状态，决定整个协调控制系统当前应该处于什么管理阶段，以及此刻AGC到底还能不能继续推进。**

论文主线已经形成：

```text
策略2
回答：六台设备真实执行得怎么样？
        ↓
策略7
回答：根据这些真实执行状态，
系统现在该继续、暂停、对齐，还是受控恢复？
        ↓
改进AGC
回答：在允许继续调节时，
剩余可信资源到底怎样承担PCC调节任务？
```

因此三者最核心的职责分工是：

```text
策略2 = 识别现实
策略7 = 管理现实与控制器之间的协调状态
改进AGC = 在策略7允许的条件下进行资源功率分配
```

当前策略7已经发展成：

```text
0 = INACTIVE
1 = NORMAL
2 = HOLD
3 = RECONSTRUCTION
4 = RECOVERY
```

并进一步具备：

```text
持续执行失配
→ 监督层隔离该资源
→ 该资源 trust=0
→ 不再阻塞整个系统
→ 剩余可信资源继续恢复协调
```

# 1. 为什么策略2做完以后还必须有策略7？

策略2能回答：

```text
PV1现在执行正常吗？
PV2正常吗？
ESS1现在是正常响应，还是已经确认失配？
ESS2正常吗？
EV1、EV2现在是否可信？
```

但即使策略2已经告诉我们：

```text
ESS1 = MISMATCH
```

系统仍然没有回答：

```text
发现ESS1失配以后，AGC还要不要继续每1 s更新一次？

是立刻继续算新的功率分配，还是先暂停？

设备恢复以后，能不能直接重新进入NORMAL？

AGC内部保存的Ppv/Pess/Pev
如果已经和真实设备状态不一致，
要不要先重新对齐？

恢复时是一步把全部PCC误差重新交给AGC，
还是逐渐放开？

如果ESS1一直坏着，
是不是整个系统永远HOLD？
还是把ESS1临时剔除，剩下5台设备继续调节？
```

这些都不是“执行状态识别”问题，而是：

> **系统级协调状态管理问题。**

所以策略7就是策略2和AGC之间必须存在的监督层。

# 2. 原始策略7是什么？为什么不够？

项目原始15策略中的策略7，本质上仍是联络线有功偏差：

```text
tieErr = Ppcc - Ptarget
cmd(7) = -tieErr
       = Ptarget - Ppcc
```

而原策略2也基本是：

```text
cmd(2) = Ptarget - Ppcc
```

所以原始策略2和策略7高度重复：

```text
策略2：看PCC误差
策略7：还是看PCC误差
```

如果论文直接写：

```text
策略2 + 策略7
```

就没有形成真正的：

```text
识别层 → 监督层 → 分配层
```

因此策略7必须从“另一个PCC误差计算块”改造成：

> **联络线协调 + 异常保持 + 状态对齐 + 受控恢复管理器。**

# 3. 策略7在整个论文架构中的准确位置

当前最准确的结构是：

```text
PCC真实功率、六设备Pmeas
        +
当前可信命令
        ↓
策略2
Execution-State Assessment（执行状态评估）
        ↓
六设备 state：0 / 1 / 2 / 3
        ↓
策略7
Coordination + Recovery Management（协调与恢复管理）
        ↓
mode

 agc_update_allowed
 reconstruction_request

        ↓
改进AGC
状态对齐 + 有效能力重分配
        ↓

```

最重要的是：

> **策略7本身不负责算“PV1具体应该变成0.42 pu还是0.46 pu”。**

它只决定：

```text
现在是否允许AGC算？
允许AGC处理多少dP？
哪些资源还能被认为是可调可信资源？
现在是否需要先重新对齐AGC内部状态？
```

# 4. 为什么最终采用四状态，而不是简单NORMAL/HOLD？

如果只有：

```text
NORMAL
HOLD
```

那么异常解除后只能：

```text
HOLD → NORMAL
```

问题是HOLD期间：

```text
设备可能继续有物理动态
真实设备已经到达新的Pmeas
AGC内部Ppv/Pess/Pev却停留在旧记忆
```

若异常解除瞬间直接NORMAL：

```text
AGC会基于错误内部状态继续分配
```

所以必须增加：

```text
RECONSTRUCTION
```

专门做：

> **控制器内部资源状态与真实执行状态重新对齐。**

而即使状态对齐完成，如果直接：

```text
RECONSTRUCTION → NORMAL
```

又可能把完整PCC误差一次性交回AGC，因此还需要：

```text
RECOVERY
```

用于：

> **受控地重新释放调节权限，而不是瞬间恢复全部动作。**

最终：

```text
NORMAL
↓ 异常确认
HOLD
↓ 异常解除 / 异常资源被管理
RECONSTRUCTION
↓ 状态对齐完成
RECOVERY
↓ 恢复过程完成
NORMAL
```

# 5. 四个状态到底分别是什么意思？

## 5.1 INACTIVE = 0

表示策略7没有投入。

当前代码中当：

```text
enable <= 0.5
```

会清空：

```text
mode
各类计时器
isolation latch
HOLD原因
```

这是算法真正的停用/初始化状态。

## 5.2 NORMAL = 1

表示当前没有“尚未被管理”的异常阻止协调控制继续进行。

此时：

```text
dP_raw = Ptarget - Ppcc
dP_request = dP_raw
agc_update_allowed = 1
```

V0.3中，即使某台资源已经被隔离，只要剩余系统稳定，也可以回到：

```text
mode = NORMAL
reason = 9
```

因此必须理解：

```text
NORMAL ≠ 六台设备全部健康
NORMAL = 当前不存在尚未被管理的异常阻止剩余系统继续协调
```

## 5.3 HOLD = 2

表示当前发现了需要先阻止AGC继续推进的异常，例如：

```text
某设备state=3
命令证据无效
测量证据无效
执行状态不可评估
```

此时：

```text
dP_request = 0
agc_update_allowed = 0
```

最重要的是：

> **HOLD不是把PCC误差变没，而是暂时不允许AGC继续依据这个误差改变内部资源分配状态。**

## 5.4 RECONSTRUCTION = 3

表示：

> 在重新允许AGC继续计算前，先把AGC内部六资源分配记忆重新放到接近现实的位置。

此时：

```text
reconstruction_request = 1
agc_update_allowed = 0
dP_request = 0
```

AGC完成后返回：

```text
reconstruction_done = 1
```

策略7收到后才能进入RECOVERY。

## 5.5 RECOVERY = 4

表示状态对齐完成后，逐步把闭环调节能力交还AGC。

当前本地版：

```text
recovery_alpha：0 → 1
```

并：

```text
dP_request = recovery_alpha × dP_raw
```

当前候选：

```text
T_RECOVERY_RAMP = 2.00 s
T_RECOVERY_CONFIRM = 0.50 s
```

# 6. 为什么HOLD不是“把设备命令清零”？

当前策略7的HOLD做的是：

```text
停止AGC内部资源分配继续推进
```

不是：

```text
把六台逆变器Pref全部置0
```

所以：

```text
HOLD = 监督层冻结新的协调分配动作
```

而不是：

```text
HOLD = 物理设备紧急停机
```

这对论文非常重要，因为我们研究的是控制状态管理，不是保护跳闸逻辑。

---

# 7. 为什么恢复斜坡作用于dP_request，而不是直接插值六路命令？

我们没有让策略7直接做：

```text
六个旧命令 → 六个新命令的线性插值
```

而是做：

```text
dP_request = alpha × dP_raw
```

这样：

```text
策略7决定“允许处理多少”
AGC决定“谁具体处理多少”
```

好处：

1. 策略7仍然只是监督层；
2. 六资源分配逻辑仍集中在AGC；
3. 不会出现两个功率分配器职责冲突；
4. 后续有效能力重分配仍能自然接入。

# 10. 15个输入分别起什么作用？

## t

Target时间，用于所有持续时间判据和恢复斜坡。

## enable

当前本地复用AGC Enable。

```text
enable=0 → 真正停用和初始化策略7
enable=1 → 投入策略7
```

## Ptarget / Ppcc

形成：

```text
dP_raw = Ptarget - Ppcc
```

## cmd_valid

当前用于判断执行状态的命令证据是否可信。本地阶段固定1，V5后应由最后成功提交命令及其新鲜度定义。

## meas_valid

当前六设备测量证据是否可信。本地固定1，V5后根据真实上行测量新鲜度/通信状态定义。

## state1~state6

来自策略2：

```text
0 UNTRUSTED
1 TRACKED
2 RESPONDING
3 MISMATCH
```

策略7不重新计算residual，只消费策略2识别结果。

## reconstruction_done

来自AGC，表示内部资源分配记忆已完成本次状态对齐。

## recovery_done

为未来板端/更高层恢复完成握手预留。

## recovery_alpha_external

为未来外部恢复策略预留。本地版自己生成alpha。

# 12. dP_raw和dP_request为什么一定要分开？

这是策略7最重要的架构思想之一。

```text
dP_raw = 现实世界真正存在的PCC偏差
```

而：

```text
dP_request = 当前监督状态允许交给AGC处理的偏差
```

例如HOLD时：

```text
dP_raw = -40 kW
dP_request = 0
```

不是PCC误差消失，而是：

> 我知道有40 kW误差，但当前先不允许AGC继续追这个误差。

# 13. agc_update_allowed到底冻结什么？

它控制的是：

> **AGC内部 `Ppv/Pess/Pev` 是否允许执行下一次正常分配更新。**

不是控制物理设备是否还能响应。

在HOLD中：

```text
agc_update_allowed = 0
```

后来MAT明确验证到：

```text
HOLD期间六路AGC命令停止继续推进
```

所以策略7不是仅做状态记录，而是真正接管了AGC更新权限。

# 14. trust1~6到底是什么？

当前trust是0/1，表示：

> **这台资源当前是否可以被AGC作为可信调节资源使用。**

V0.1/V0.2：

```text
state=1或2 → trust=1
state=0或3 → trust=0
```

如果全局命令/测量证据无效，当前语义下六路trust都置0。

V0.3以后：

```text
isolated=1 → trust强制为0
```

所以最终：

```text
trust=1
需要：
数据有效
+ 未被隔离
+ state属于TRACKED/RESPONDING
```

# 19. 为什么一定要加100 μs Unit Delay？

当前RT-LAB基本步长：

```text
Ts = 100 μs
```

如果两端MATLAB Function直接反馈，容易形成同一步代数环。

加入Unit Delay后变成：

```text
k时刻的监督决策
↓
k+1实时步被另一模块使用
```

100 μs相对于：

```text
AGC周期 = 1 s
设备动态 = 约1 s量级
```

可以忽略，但从实时因果结构上非常重要。

# 20. 第一次整合为什么还是出现代数环？

当时我们已经给：

```text
Strategy7 → AGC
AGC → Strategy7
```

加了延迟，但漏了：

```text
AGC命令
↓
策略2
↓
Pexpected + residual
↓
Pexec_est
↓
AGC
```

即：

```text
AGC → Strategy2 → AGC
```

仍然直接闭环。

策略2、AGC都包含persistent状态，Simulink因此报algebraic loop。

# 22. Pexec为什么来自策略2，而不是策略7自己重新估计？

Pexec实际进入AGC，构造为：

```text
Pexec_est = Pexpected + residual
```

而策略2：

```text
residual = filtered Pmeas - Pexpected
```

所以：

```text
Pexec_est = filtered Pmeas
```

这样状态识别和状态对齐使用同一套“现实执行估计”，避免重复建模。

---

# 23. 为什么最初MAT里看不到RECONSTRUCTION？

第一次真实握手时：

```text
RECONSTRUCTION
→ AGC很快done
→ Strategy7很快进入RECOVERY
```

可能只有几个100 μs步。

但OpWrite约：

```text
100 Hz = 10 ms一个记录点
```

所以真实发生的：

```text
mode=3
reconstruction_request=1
reconstruction_done=1
```

可能刚好落在记录点之间。

这不是逻辑错误，而是可观测性问题。

---

# 24. 为什么V0.2增加50 ms RECONSTRUCTION最小停留？

我们没有为了看见状态而把全部OpWrite提高到高频，而是让监督状态本身有合理驻留时间：

```text
T_RECON_MIN = 0.05 s
```

100 Hz下约5个点。

意义有两层：

1. 日志明确可见；
2. 状态机握手更稳健。
