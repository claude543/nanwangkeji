# 2. Ppv / Pess / Pev到底是什么？

它们是：

> **AGC内部对六台资源当前分配功率的记忆。**

对应：

```text
Ppv(1)  = PV1当前内部功率分配记忆
Ppv(2)  = PV2当前内部功率分配记忆

Pess(1) = ESS1当前内部功率分配记忆
Pess(2) = ESS2当前内部功率分配记忆

Pev(1)  = EV1内部“充电功率正幅值”记忆
Pev(2)  = EV2内部“充电功率正幅值”记忆
```

所以AGC不是每1 s都从零重新算六个功率，而是在：

```text
上一次内部状态 Ppv/Pess/Pev
```

基础上继续增加或减少。

---

# 3. 为什么这一点对论文特别重要？

因为：

```text
AGC内部记忆 ≠ 设备真实执行状态
```

例如AGC认为：

```text
ESS1 = +20 kW
```

但设备实际因为执行故障可能已经：

```text
ESS1 = +30 kW
```

如果AGC下一次仍从：

```text
+20 kW
```

继续分配，那么控制器“账本”和真实物理系统已经分叉。

这就是为什么论文不能只做：

```text
发现异常 → HOLD → 恢复
```

而必须进一步做：

```text
恢复前
把AGC内部六资源状态重新对齐现实
```

```text

```

```text
t - last_t >= Ts_AGC
```

所以：

```text
实时模型步长 = 100 μs
AGC协调更新周期 = 1 s
```

# 7. EV为什么特别容易看错符号？

AGC内部：

```text
Pev
```

保存的是：

```text
正的充电功率幅值
```

例如：

```text
Pev = 60 kW
```

模型输出：

```text
Pev_pu = -Pev/P_UNIT = -0.6 pu
```

因此：

```text
EV充电越强 → 模型输出越负
```

但AGC内部Pev数值越大。

所以状态对齐时EV必须：

```text
Pev(i) = -Pexec_EV_i × P_UNIT
```

不能漏负号。

# 10. 同一类型两台设备原来怎样分？

基础AGC不是简单50%/50%。

它已经按当前剩余调节余量比例分配。

例如两个PV向上：

```text
head1 = PVmax1 - Ppv1
head2 = PVmax2 - Ppv2

total = head1 + head2
```

若本轮需要这类资源承担 `used`：

```text
PV1增加 = used × head1/total
PV2增加 = used × head2/total
```

所以必须记住：

> **基础AGC本来就有“同类资源按实时余量比例分配”。**

因此不能把“从平均分配改成余量分配”写成我们的创新，因为代码事实不是这样。

# 14. supervisory_update_allowed为什么是第一核心接口？

原AGC只要：

```text
enable=1
+
到达1 s更新时刻
```

就继续更新。

即使策略2已经发现：

```text
ESS1执行失配
```

原AGC仍可能继续改变：

```text
Ppv/Pess/Pev
```

于是内部认知可能越走越远。

加入 `supervisory_update_allowed` 后：

```text
Strategy7 NORMAL → allow=1
Strategy7 HOLD → allow=0
Strategy7 RECONSTRUCTION → allow=0
Strategy7 RECOVERY → 根据alpha逐步允许
```

所以AGC第一次真正接受策略7监督。

---

# 15. dP_request为什么替代AGC自己计算的dPnow？

基础AGC：

```text
dPnow = Ptarget - Ppcc
```

改造后正常分配部分变成：

```text
dPnow = dP_request_kW
```

意义：

> **AGC不再自己决定“现在允许处理多少PCC误差”，而只执行策略7批准的调节请求。**

所以：

```text
NORMAL：dP_request ≈ dP_raw
HOLD：dP_request = 0
RECONSTRUCTION：dP_request = 0
RECOVERY：dP_request = alpha × dP_raw
```

这正式建立了：

```text
监督层 → 分配层
```

的接口。


# 17. Pexec1~6究竟是什么？

不是原始瞬时Pmeas。

来自策略2：

```text
Pexec_est = Pexpected + residual
```

而策略2中：

```text
residual = filtered Pmeas - Pexpected
```

所以：

```text
Pexec_est = filtered Pmeas
```

即：

> **策略2已经处理后的平滑真实执行估计。**

---

# 18. 为什么状态对齐不直接用瞬时Pmeas？

原始Pmeas包含：

```text
100 Hz纹波
瞬时波动
局部动态
```

如果直接写入 `Ppv/Pess/Pev`，AGC内部记忆会被高频波动污染。

策略2已有：

```text
TAU_MEAS = 0.10 s
```

测量平滑，因此统一用 `Pexec_est` 更合理。

# 19. Pexec在Simulink中怎样构造？

策略2输出：

```text

7~12  residual1~6
```

```text
STR2_EXEC_EST_PV1

STR2_EXEC_EST_ESS2
STR2_EXEC_EST_EV1
STR2_EXEC_EST_EV2
```

每个：

```text
Pexec = Pexpected + residual
```

然后经过六个100 μs Delay进入AGC。

# 20. 为什么Pexec反馈必须加100 μs Delay？

第一次整合漏掉这一步，形成：

```text
AGC命令
↓
Strategy2
↓
Pexec
↓
AGC
```

即：

```text
AGC → Strategy2 → AGC
```

代数环。

修复后：

```text

↓
100 μs Delay
↓
AGC使用Pexec(k-1)
```

对于1 s AGC周期几乎没有性能影响，但实时因果结构明确。

# 21. reconstruction_request到来以后AGC到底怎么改内部状态？

如果：

```text
reconstruction_request > 0.5
```

且Pexec均有限，则：

## PV

```text
Ppv(1) = clamp(Pexec_PV1 × P_UNIT, 0, PVmax1)
Ppv(2) = clamp(Pexec_PV2 × P_UNIT, 0, PVmax2)
```

## ESS

```text
Pess(1) = clamp(Pexec_ESS1 × P_UNIT, -P_UNIT, +P_UNIT)
Pess(2) = clamp(Pexec_ESS2 × P_UNIT, -P_UNIT, +P_UNIT)
```

## EV

由于内部Pev是正充电幅值：

```text
Pev(1) = clamp(-Pexec_EV1 × P_UNIT, 0, P_UNIT)
Pev(2) = clamp(-Pexec_EV2 × P_UNIT, 0, P_UNIT)
```

# 22. 为什么状态对齐必须改persistent，而不能只改输出？

如果只在某时刻把六路输出改成Pexec，但内部：

```text
Ppv/Pess/Pev
```

仍是旧值，则下一次1 s AGC更新又会从旧值继续算。

所以真正状态重构必须：

> **改控制器内部记忆本身。**

这才是：

```text
controller internal allocation state reconciliation
```

而不是简单output correction。

---

# 23. 为什么状态对齐后要设置last_t=t？

代码：

```text
last_t = t
```

意义：

> **把重构时刻重新定义为下一段AGC调度的时间起点。**

否则可能刚重构完成，同一时刻又因为已超过1 s而立刻正常更新，破坏阶段边界。


# 25. recon_handled有什么作用？

Strategy7会让 `reconstruction_request` 保持一段时间。

如果AGC每100 μs都重新：

```text
Ppv ← Pexec
Pess ← Pexec
Pev ← Pexec
```

则RECON期间内部状态会不断覆盖。

所以使用：

```text
persistent recon_handled
```

实现：

```text
request第一次到来
→ 对齐一次
→ recon_handled=true

request继续保持
→ 不重复对齐
→ done仍保持1

request撤销
→ recon_handled=false
→ 为下一轮重新武装
```

# 32. trust在AGC里怎样处理？

代码先：

```text
clamp(trust, 0, 1)
```

当前Strategy7实际给：

```text
0或1
```

但AGC接口允许0~1连续值，为以后可能的：

```text
连续可用度/性能折减
```

保留接口。

当前V0.1不要把它描述成复杂连续权重，当前真实语义就是：

```text
trust=1 → 可参与
trust=0 → 当前不参与
```

# 33. 改进AGC核心定义：当前有效调节能力

当前定义：

```text
有效调节余量
=
当前物理调节余量
×
trust
```

所以：

```text
物理余量很大但trust=0
→ 有效能力=0

物理余量较小且trust=1
→ 只能按当前剩余物理余量参与
```

这是从“理论可调”到“当前可信可调”的关键升级。

# 34. dP_request > 0时六设备有效能力怎么算？

含义：

```text
微电网净出力需要增加
```

## PV1/PV2

```text
eff_PV_i
=
trust_PV_i × max(PVmax_i - Ppv_i, 0)
```

## ESS1/ESS2

正方向需要增加放电。

默认：

```text
essUpper = +P_UNIT
```

若：

```text
SOC <= SOC_LOW
```

则：

```text
essUpper = 0
```

有效能力：

```text
eff_ESS_i
=
trust_ESS_i × max(essUpper_i - Pess_i, 0)
```

## EV1/EV2

正方向需要减少充电。

内部Pev为正充电幅值，所以：

```text
eff_EV_i
=
trust_EV_i × max(Pev_i, 0)
```


```text
SOC连续权重
SOC一致性优化
寿命成本
```

原因是文献已经有大量成熟方法，SOC在本论文中定位为约束/辅助，不抢占主创新。

# 38. 资源级调用优先顺序改了吗？

没有。

仍然：

```text
dP > 0：PV → ESS放电 → EV减少充电

dP < 0：EV增加充电 → ESS充电 → PV降低
```

这样可以把本轮变量集中在：

```text
执行状态感知
状态对齐
有效能力
```

而不是同时引入经济性、SOC权重、性能权重等多个新变量。

# 39. 同一类型两台资源现在怎样分？

仍然按余量比例，但余量改成：

```text
有效余量 = 物理余量 × trust
```

例如ESS：

```text
h1 = trust_ESS1 × physical_margin_ESS1
h2 = trust_ESS2 × physical_margin_ESS2

total = h1 + h2
used = min(req, total)
```

再：

```text
ESS1变化 = used × h1/total
ESS2变化 = used × h2/total
```

所以若：

```text
trust_ESS1 = 0
```

则：

```text
h1 = 0
```

同类ESS任务自然落到ESS2，只要ESS2还有能力。

---

# 40. alloc_up_margin函数到底做什么？

向上调整：

```text
x_i(new)
=
x_i(old)
+
used × margin_i / total_margin
```

其中：

```text
used = min(req, total_margin)
```

保证：

1. 不超过本类总有效能力；
2. 同类资源按有效余量比例增加；
3. trust=0资源不会增加。

---

# 41. alloc_down_margin函数到底做什么？

向下调整：

```text
x_i(new)
=
x_i(old)
-
used × margin_i / total_margin
```

同样：

```text
used = min(req, total_margin)
```

用于各内部变量向下调整的场景。

---

# 42. remain输出现在是什么意思？

每次AGC更新：

```text
rem = abs(dP_request)
```

每类资源承担一部分后：

```text
rem = rem - used
```

最终：

```text
remain
=
当前这一轮仍然没有被资源能力覆盖的调节需求
```

若：

```text
remain > P_DEAD
```

则状态会反映当前总能力不足。

# 44. 为什么eff是方向相关的？

同一台设备向上和向下能力不同。

例如EV当前：

```text
Pev = 60 kW
```

向增加微电网净出力方向：

```text
最多减少60 kW充电
→ 上调能力60 kW
```

向降低微电网净出力方向：

```text
最多从60增加到100 kW充电
→ 下调能力40 kW
```

所以eff必须根据：

```text
dP_request符号
```

动态计算。

# 45. eff_total是什么？

```text

```

表示：

> **当前这个调节方向上，六资源总共还有多少可信有效调节余量。**

若某资源trust=0，它对总能力贡献为0。

# 46. 一个必须知道的代码细节：eff在哪个时刻计算？

当前代码先用函数进入时的：

```text

```

对100 Hz正式日志和控制结果没有实质影响，但理解代码时应知道。
