# 0. V0.2相比V0.1的核心变化

V0.1：

```text
execution-state mismatch
→ controller/resource-state reconstruction
→ controlled re-entry
→ heterogeneous resource reallocation
```

V0.2收窄为：

```text
committed-command state
≠
current physical execution state
        ↓
per-DER execution evidence assessment
        ↓
conditional resource-allocation-state reconciliation
        ↓
controlled re-entry
        ↓
execution-aware heterogeneous resource reallocation
```

原因：

1. generic controller-state reset/reinitialization 已有成熟理论；
2. match-before-transfer / bumpless recovery 已有成熟理论；
3. ACK / actuator-applied-input estimation 已有成熟理论；
4. 本项目基础AGC没有PI积分器，不能照搬“恢复时重构AGC积分器”的叙事。

真正需要研究的是：

> 六资源协调器内部保存的“资源分配记忆状态”与当前物理执行状态之间如何判定是否失配，并在必要时重新对齐。

---

# 1. N2后的一句话研究问题

> 当外部控制板通过Modbus TCP协调2PV+2ESS+2EV跟踪PCC有功目标时，最后成功提交的设备指令并不必然等价于设备当前已经形成的物理功率状态；设备正常动态、通信异常/恢复、安全门行为以及资源能力变化均可能使协调器内部的资源分配记忆与当前真实执行状态出现偏离。如何利用逐设备执行证据判断这种偏离是否真实存在，在必要时重新对齐资源分配状态，并在受控恢复后基于当前真实有效能力重新分配联络线调节任务？

# 2. 必须严格区分的状态链

```text
u_calc
= 本轮算法算出的候选命令

u_commit
= 经过candidate/commit并在FC16成功后正式提交的命令

u_applied
= 执行侧实际采用的设定状态
= 当前点表中没有独立直接反馈量

Pexpected
= 在可信u_commit/估计u_applied和正常设备动态下应出现的物理响应

Pmeas
= 设备真实测量有功功率

x_alloc
= AGC/资源分配器内部保存的六资源分配记忆状态
```

因此论文最核心的分叉不应只写：

```text
u_calc ≠ u_commit
```

因为V4 candidate/commit已经阻止失败候选进入正式AGC历史。

更值得研究的是：

```text
u_commit
↓
实际执行链 + 正常设备动态
↓
Pexpected
↕
Pmeas
↓
当前真实执行状态
↕
x_alloc
```

# 3. 当前基础AGC真正有哪些内部状态

仓库当前 `AGC_Controller.m` 的persistent状态：

```text
Ppv
Pess
Pev
last_t
status
last_dP
last_remain
```

真正决定下一轮资源分配起点的是：

```text
Ppv  = [PV1内部功率记忆, PV2内部功率记忆]
Pess = [ESS1内部功率记忆, ESS2内部功率记忆]
Pev  = [EV1充电功率正幅值记忆, EV2充电功率正幅值记忆]
```

因此定义：

```text
x_alloc =
[Ppv1, Ppv2, Pess1, Pess2, Pev1, Pev2]
```

注意：`Pev`内部保存正的充电幅值，最终输出到模型时取负号。

其他状态：

```text
last_t = AGC更新时间调度状态

status
last_dP
last_remain
= 状态/结果历史
```

当前基础AGC**没有PI积分器**。

所以后续论文不能照搬：

```text
恢复时重构AGC integrator state
```

真正应该讨论的是：

```text
resource-allocation memory reconciliation
```

# 4. V4 candidate/commit对论文问题的影响

V4已明确：

```text
agc_state
= 已确认成功发布的正式AGC历史

candidate_state
= 本次新算出的临时候选历史
```

只有：

```text
UPDATED
+ 输出合法
+ 编码成功
+ FC16成功
```

以后才：

```text
agc_state = candidate_state
CMD_SEQ + 1
```

FC16最终失败时：

```text
candidate_state丢弃
agc_state保持原值
CMD_SEQ不变
```

因此：

> V5 Baseline不能再直接沿用早期离线模型中“下行失败但AGC内部继续累计”的失效描述，除非V5真实试验重新证明存在另一层状态推进。

早期通信异常结果仍可用于“问题发现和研究动机”，但正式论文Baseline必须以V5真实板端基础C AGC为准重新确认。

# 5. candidate/commit之后仍然存在什么问题

即使candidate/commit完全正确，仍有：

```text
成功提交了什么
≠
执行侧实际采用了什么
≠
物理设备当前做到什么
```

当前项目可直接知道：

```text
u_commit
Pmeas
PVmax
SOC
CMD_SEQ
通信/安全状态
```

当前项目不能直接知道：

```text
u_applied
```

因为40101～40116中没有独立的“设备实际采用命令回显”。

因此：

> FC16成功只能定义“正式提交”，不能直接等同于“物理执行完成”。

# 6. Strategy 2的新定位

继续使用工作名称：

> **PCC Tracking + Execution-State Assessment**

但核心问题改成：

> **设备当前物理响应是否仍与最后可信控制状态相一致？**

建议证据链：

```text
u_commit
↓
当前PVmax / SOC / device status
↓
正常响应模型或动态允许带
↓
Pexpected
↓
与Pmeas比较
↓
execution residual
↓
execution state / confidence
```

不能采用：

```text
u_commit != Pmeas
→ 执行异常
```

因为设备存在正常动态。

必须区分：

```text
正常“还没响应完”
vs
真正“没有按预期执行”
```

所以Strategy2需要：

```text
normal-response model
或
normal-response tolerance band
```

具体形式暂不冻结。

# 7. Strategy 7的新定位

工作名称建议收窄为：

> **Tie-Line Coordination + Execution-State Reconciliation + Recovery Management**

保留：

```text
NORMAL
HOLD
RECONSTRUCTION
RECOVERY
```

但RECONSTRUCTION不再表示“一恢复就reset整个控制器”。

---

# 8. NORMAL / HOLD

## NORMAL

```text
通信/安全信息可信
+
PCC反馈可信
+
资源执行状态在正常允许范围内
↓
正常形成总调节需求
↓
交给改进AGC
```

## HOLD

HOLD仍是成熟必要组件，不作为创新。

```text
关键输入/执行证据不可信
↓
禁止继续错误推进
↓
保留最后可信正式状态
```

必须与V4 candidate/commit一致，不能再创建另一套互相冲突的“冻结”。

---

# 9. RECONSTRUCTION应改成“条件触发的状态对齐”

未来不应：

```text
通信恢复
→ 无条件reset
```

而应：

```text
恢复fresh data
↓
Strategy2检查执行证据
↓
如果x_alloc仍与真实执行状态一致
→ 无需数值重构

如果确认发生执行状态偏离
→ 才进入allocation-state reconciliation
```

因此它更准确地叫：

> **条件触发的资源分配状态对齐。**

第一优先级重构对象：

```text
x_alloc =
[Ppv1, Ppv2, Pess1, Pess2, Pev1, Pev2]
```

而：

```text
status
last_dP
last_remain
```

可以根据新输入重新计算。

`last_t`属于调度状态，应单独设计恢复规则，但当前不冻结。

---

# 10. 为什么不能简单令 x_alloc = Pmeas

因为：

```text
u_commit = 控制参考状态
Pmeas    = 物理响应状态
```

正常情况下也可能暂时不同。

例如：

```text
u_commit刚发生阶跃
↓
设备处于正常动态过程
↓
Pmeas尚未达到目标
```

如果此时每一拍都：

```text
x_alloc ← Pmeas
```

就会把正常动态误判为状态错误，可能造成重复调节。

因此至少需要：

```text
execution residual持续越过正常动态允许带
+
数据可信
```

以后才讨论是否依据Pmeas/估计u_applied重新初始化x_alloc。

## A. Command state

## B. Physical execution state


# 12. RECOVERY的新定位

成熟文献已经覆盖：

```text
output matching
bumpless transfer
ramp
blending
dwell time
threshold gate
```

这些只能作为组件。

我们的RECOVERY负责：

```text
allocation-state reconciliation完成
↓
fresh measurement持续有效
↓
执行一致性恢复
↓
重构后的分配起点合理
↓
命令连续性满足要求
↓
受控恢复到NORMAL
```

最终选ramp、rate limit还是blending以后再定，不作为主要创新。

---

# 13. 改进AGC的新逻辑

V0.1里：

```text
R_eff = R_phys × w_SOC × w_exec
```

容易退化成已有普通performance-aware allocation。

V0.2改成强调：

```text
reconciled allocation base state
+
current physical capability
+
current execution consistency
+
SOC auxiliary state
↓
effective regulation capability
↓
heterogeneous resource allocation
```

执行状态不只是“乘一个历史性能权重”，而是先决定：

> **当前分配基准状态是否仍可信。**

然后再计算资源真正可靠的调节能力。

# 14. 四篇theory-neighbor对蓝图的裁剪

## Battistelli 2013

已经证明：

```text
根据当前闭环数据
计算新的controller state
并优化切换瞬态
```

属于成熟状态初始化思想。

结论：

```text
generic state reset
不能作为主要创新
```

可借：reset map、performance-oriented initialization。

## Rosenthal 2018 + Vargas 2023

已经证明：

```text
controller-designed input
≠
actuator-applied input
```

且可利用ACK、buffer state、plant measurement修正控制器认知。

结论：

```text
applied-input estimation / ACK synchronization
不能作为主要创新
```

我们的路线必须推进到：

```text
physical DER response
+
resource allocation state
```

## Zheng 2009

已经证明：

```text
待接管控制器先匹配当前在线输出
↓
满足条件
↓
再切换
```

所以match-before-transfer不能作为主要创新。

## Onat 2011

已经证明：

```text
synchronized ↔ interrupted
```

以及：

```text
fresh actual measurement
→ internal model重新同步
→ 拒绝不一致控制序列
```

因此fresh-state resynchronization状态机本身也不是主要创新。


```text
current effective capability

受控回到NORMAL
```


# 24. V0.2一句话总纲

> 这篇论文不再把“通信恢复后重置控制器状态”作为创新，而是研究：在已经具有candidate/commit和安全状态机的实际板端协调系统中，如何从最后成功提交命令、设备正常动态和真实Pmeas形成逐DER执行证据，判断协调器内部六资源分配记忆是否仍代表真实可用状态；若发生偏离，则有条件地重新对齐资源分配状态，再依据当前有效能力重新分配PCC调节任务并受控恢复正常协调。
