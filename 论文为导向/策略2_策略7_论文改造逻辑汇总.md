# 暑期南网科技项目｜策略2、策略7与论文改造逻辑汇总

> 用途：统一说明当前15项策略中策略2、策略7的代码含义、`mt`指标的意义，以及第一篇项目论文计划如何改造策略2、策略7和AGC。  
> 说明：本文整合此前三轮解释，删除重复内容，只保留当前最重要的逻辑。

---

# 1. 先明确当前模型中的基本量

当前项目统一采用：

```text
P > 0：微电网向上级电网送电
P < 0：微电网从上级电网购电
```

当前联络线/PCC目标：

```text
Pt = -100 kW
```

例如：

```text
实际 P = -120 kW
目标 Pt = -100 kW
```

表示：
- 当前从大电网购电120 kW；
- 希望最终只购电100 kW；
- 因此微电网自身还需要增加20 kW净出力。

总调节需求为：

```text
Pt - P
= -100 - (-120)
= +20 kW
```

这里的 `+20 kW` 表示：微电网净出力应往正方向增加20 kW，而不是说PCC目标变成+20 kW。

---

# 2. 当前策略2到底做什么

当前策略2的代码核心为：

```matlab
agcErr = abs(Pt - P);

mt(2) = 100.0*agcErr / ...
    max(abs(max(abs(Pt), pRated)),1e-6);

al(2) = double(mt(2) > eb);

cmd(2) = Pt - P;

st(2) = double(al(2) < 0.5);
```

当前策略2可以理解为：

> **PCC有功跟踪误差评价器。**

它主要回答：
1. PCC现在距离目标差多少？
2. 这个误差相对于系统功率规模来说严重不严重？
3. 是否超过允许误差？
4. 当前还需要往哪个方向调多少功率？

各变量含义：

```text
agcErr = PCC绝对跟踪误差
mt(2)  = 归一化后的误差百分比
al(2)  = 是否超过允许误差阈值
st(2)  = 当前跟踪状态是否正常
cmd(2) = 当前建议的总功率修正量
```

例如：

```text
Pt = -100 kW
P  = -120 kW
```

则：

```text
agcErr = 20 kW
cmd(2) = +20 kW
```

表示当前还需要增加约20 kW微电网净出力。

需要注意：当前15项策略的 `cmd` 只是观察/记录量，并没有直接接到六台设备的 `Pref`。

---

# 3. `mt` 为什么这样计算

`mt` 是 `metric`，即策略评价指标。

策略2和策略7当前使用的基本形式都是：

```text
mt = 100 × |Pt - P| / max(|Pt|, pRated)
```

代码中再加入 `1e-6`，只是为了防止分母为0。

它的目的不是算新的控制命令，而是把：

```text
误差多少kW
```

变成：

```text
误差相对于系统参考功率规模占多少百分比
```

例如：

```text
Pt = -100 kW
P  = -120 kW
误差 = 20 kW
pRated = 200 kW
```

则：

```text
mt = 100 × 20 / 200
   = 10%
```

意思是：当前PCC跟踪误差约占系统参考功率规模的10%。

随后：

```matlab
al(2) = double(mt(2) > eb);
```

再判断这个10%是否超过允许阈值 `eb`。

因此可以简单记成：

```text
cmd   = 还需要调多少kW
mt    = 这个误差严重到什么程度
alarm = 是否已经超过允许范围
```

需要特别说明：这个 `mt` 公式不是行业强制规定，而是原15项策略代码中人为定义的归一化KPI。以后论文改造策略2时，可以重新设计更有物理意义的评价指标。

# 4. 当前策略7到底做什么

当前策略7的代码核心为：

```matlab
tieErr = P - Pt;

mt(7) = 100.0*abs(tieErr) / ...
    max(abs(max(abs(Pt), pRated)),1e-6);

al(7) = double(mt(7) > eb);

cmd(7) = -tieErr;

st(7) = double(al(7) < 0.5);
```

它原本希望表示：

> **联络线有功偏差及其修正方向。**

例如：

```text
Pt = -100 kW
P  = -120 kW
```

则：

```text
tieErr = -20 kW
cmd(7) = +20 kW
```

含义仍然是：微电网净出力应增加20 kW，把PCC从−120 kW拉向−100 kW。

---

# 5. 为什么当前策略2和策略7几乎重复

策略2：

```matlab
cmd(2) = Pt - P;
```

策略7：

```matlab
tieErr = P - Pt;
cmd(7) = -tieErr;
```

展开后：

```text
cmd(7)
= -(P - Pt)
= Pt - P
```

因此：

```text
cmd(2) = cmd(7)
```

同时：

```text
|Pt - P| = |P - Pt|
```

所以在相同参数下：

```text
metric(2) ≈ metric(7)
alarm(2)  ≈ alarm(7)
status(2) ≈ status(7)
cmd(2)    = cmd(7)
```

也就是说，当前代码中：

```text
策略2 ≈ PCC误差评价器
策略7 ≈ 换一种写法再次评价PCC误差
```

二者还没有形成真正不同的控制职责。

这也是论文为什么不能直接把现有策略2、策略7当作创新，而要进一步改造。

---

# 6. 当前基础AGC又做什么

现在真正控制六台设备的是基础AGC。

它的大致逻辑是：

```text
PCC误差
↓
计算总调节需求
↓
按照固定优先级和理论能力分配
↓
PV / ESS / EV
```

当前主要依据：

```text
理论功率上下限
PVmax
SOC边界
AGC内部保存的历史命令
固定资源优先级
```

例如：

```text
dP > 0
PV增加
→ ESS放电
→ EV减少充电

dP < 0
EV增加充电
→ ESS充电
→ PV降低
```

问题在于：AGC知道自己之前“算过什么”，但不知道设备到底真实执行到了哪里。

因此必须区分：

```text
u_calc    控制器算出的候选命令
u_commit  最后真正成功提交的命令
u_applied 设备真正采用的设定值
Pmeas     设备最终真实输出功率
```

这几个量在通信异常或设备动态存在时，并不一定相等。

---

# 7. 为什么论文必须改造

当前基础方法存在两个核心问题。

## 7.1 正常情况下也可能出现认知状态与真实设备状态不完全一致

AGC主要依赖内部历史命令，而设备存在正常动态响应过程。

因此：

```text
命令已经改变
≠
设备功率立即达到新值
```

如果AGC一直按照自己的历史命令判断资源状态，就可能继续分配新的任务，引起资源之间长期对冲。

目前实际Baseline已经观察到：

```text
PV越来越正
EV越来越负
```

虽然PCC总体还能保持在目标附近，但资源内部出现不合理的相互抵消。

## 7.2 通信异常时问题更加明显

下行异常可能出现：

```text
控制器继续计算新命令
↓
但设备仍执行旧命令
↓
控制器内部状态继续推进
↓
恢复后一次性下发累计结果
↓
命令突跳、PCC超调
```

上行异常可能出现：

```text
控制器继续使用旧PCC / 旧Pmeas
↓
真实系统已经变化
↓
控制器仍根据陈旧状态继续调节
↓
恢复后发现现实与内部状态差很多
↓
出现反向修正和超调
```

因此论文真正研究的不是“通信会不会丢包”，而是：

> **通信异常和设备动态导致控制器内部认知状态与真实设备执行状态发生分叉以后，如何重新建立一致状态并恢复协调控制。**

# 8. 论文最终改造哪三部分

论文计划改造：

```text
策略2
+
策略7
+
AGC
```

三者职责要真正拆开。

# 9. 改造策略2：从“PCC误差统计”升级为“真实执行状态评估”

当前策略2只知道：

```text
PCC目标是多少
PCC现在是多少
误差是多少
```

改造后，它要进一步判断：

```text
PCC测量是不是新鲜的？
最后真正成功提交的命令是什么？
每台设备按照正常动态应该响应到什么程度？
六台设备真实Pmeas是多少？
哪台设备正在正常响应？
哪台设备执行不足？
哪台设备已经失去可靠调节能力？
```

未来策略2的定位：

> **PCC Tracking + Execution-State Assessment**

即：

```text
PCC跟踪状态
+
逐设备执行状态评估
```

可能形成：

```text
u_commit
↓
正常设备响应模型 / 容差带
↓
Pexpected
↓
与Pmeas比较
↓
每台设备execution state
```

其中 `Pexpected`、execution residual、时间窗、confidence 等具体形式目前还没有最终冻结。

通俗说：

> **策略2负责“看清现实”。**

---

# 10. 改造策略7：从“再算一次PCC误差”升级为“联络线协调与恢复总指挥”

策略7以后不再只是：

```text
Pt - P
```

而是根据策略2提供的真实执行状态判断：

```text
现在还能不能正常继续调？
当前真正还需要调多少？
通信异常时是否应该暂停？
恢复以后是否需要先重新建立控制器状态？
什么时候可以重新接管？
恢复第一拍如何避免突跳？
```

未来考虑形成控制逻辑状态：

```text
NORMAL
↓
HOLD
↓
RECONSTRUCTION
↓
RECOVERY
↓
NORMAL
```

其中最关键的是 `RECONSTRUCTION`。

通信恢复后，不直接按照旧内部状态继续控制，而是利用：

```text
最新PCC
+
六路Pmeas
+
最后成功u_commit
```

重新建立AGC内部对六台资源当前状态的认识。

然后：

```text
状态对齐
↓
避免恢复第一拍大跳变
↓
受控重新接管
↓
回到NORMAL
```

通俗说：

> **策略7负责“根据现实决定现在整个系统该怎么行动”。**

---

# 11. 改造AGC：从“理论能力分配”升级为“真实有效能力分配”

当前AGC认为一台设备“还能调多少”，主要依据：

```text
理论功率上下限
PVmax
SOC边界
内部历史命令
```

改造后，需要增加策略2提供的设备当前真实执行状态。

例如：

```text
PV1理论上还能增加30 kW
```

但实际发现：

```text
连续增加PV1命令
Pmeas却没有正常增加
```

那么改进AGC就不能继续把这30 kW全部视为可靠能力。

而应该：

```text
降低PV1当前有效调节能力
↓
少分任务给PV1
↓
把剩余任务重新分给PV2 / ESS / EV
```

因此未来AGC核心变化是：

> **从“按理论能力分配”变成“按当前真实有效调节能力动态分配”。**

SOC仍会使用，但只作为辅助约束或辅助权重，而不是论文主体创新。

---

# 12. 三部分改造后的完整关系

最终架构可以压缩为：

```text
策略2
“现在真实发生了什么？”
↓
PCC状态 + 六台设备执行状态

策略7
“根据这个真实状态，现在整个微电网应该怎么行动？”
↓
总调节需求 + NORMAL/HOLD/RECONSTRUCTION/RECOVERY

改进AGC
“这份真实调节任务具体分给谁？”
↓
PV1 PV2 ESS1 ESS2 EV1 EV2
```

最容易记忆的一句话：

> **策略2负责看清现实，策略7负责根据现实决定怎么调，AGC负责把任务具体分给六台设备。**

# 13. 改造前后最直观的区别

## 改造前

例如PCC表面还差20 kW：

```text
PCC差20 kW
↓
AGC认为还需要再分20 kW
↓
但它不知道上一拍命令设备究竟执行到了哪里
```

因此可能出现：

```text
重复调节
资源对冲
通信恢复时命令突跳
PCC超调
反向修正
```

## 改造后

仍然看到PCC表面差20 kW：

```text
策略2先检查六台设备实际状态
↓
发现上一拍已经提交20 kW
但其中12 kW仍处于正常动态响应过程中
↓
真正尚未解决的调节缺口只有8 kW
↓
策略7决定当前真正有效调节需求
↓
改进AGC只重新分配必要的8 kW
```

因此目标是减少：

```text
重复调节
无效调节
资源对冲
恢复命令跳变
PCC超调
恢复时间
```

# 14. 通信恢复前后最核心的区别

## Baseline

```text
通信中断
↓
控制器内部状态可能继续或保持旧认识
↓
通信恢复
↓
直接继续旧控制逻辑
↓
命令跳变 / PCC超调
```

## Proposed

```text
通信恢复
↓
读取真实PCC和六路Pmeas
↓
确认最后成功u_commit
↓
重构控制器内部资源状态
↓
与现实重新对齐
↓
受控重新接管
```

论文当前最核心的研究链条就是：

```text
execution-state mismatch
↓
explicit reconstruction
↓
controlled re-entry
↓
heterogeneous resource reallocation
```

---

# 15. 最终一句话理解整篇论文

> **原来的控制器只知道“我想让设备做什么”；我们准备把它改成“我先确认设备实际上做到了什么，再根据真实状态决定系统现在还需要做什么，最后把真正需要完成的任务重新合理分给六台设备”。**

这就是策略2、策略7和改进AGC三部分改造之间的完整逻辑。
