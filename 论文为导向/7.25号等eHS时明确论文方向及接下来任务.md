## 2. 对当前策略 7 和 AGC 关系的理解

### 当前模型中的实际关系

目前策略 7 和 AGC 是两个**并行、相互独立计算**的模块。

策略 7 读取联络线目标和 PCC 实际功率，计算：

$$cmd\_7 = P_{\mathrm{target}} - P_{\mathrm{PCC}}$$

并输出四类结果：

- `status`：当前策略状态
- `alarm`：是否发生越限或异常
- `metric`：跟踪误差等评价指标
- `cmd`：建议调节的总功率

与此同时，`AGC_Controller` 也独立读取目标功率和 PCC 功率，再重新计算：

$$dP = P_{\mathrm{target}} - P_{\mathrm{PCC}}$$

然后将这个偏差分配为六台设备的功率指令。

当前实际控制链是：

```
Ptarget、PCC
        ↓
AGC_Controller 自己计算 dP
        ↓
六路 PV/ESS/EV 指令
        ↓
通信链路
        ↓
六台逆变器
```

策略 7 则是：

```
Ptarget、PCC
        ↓
策略 7 自己计算偏差
        ↓
status / alarm / metric / cmd
        ↓
显示、记录、评价
```

模型说明中也明确把 15 种高级策略定位为并行监测和建议模块，而真正生成六台设备功率指令的是 AGC；现有高级策略**不参与设备控制闭环**。

### 四类输出是不是完全没有被使用

准确说法是：

> 它们目前没有被 AGC 或六台设备的指令生成链路采用，但可能被显示、记录、告警或测试模块使用。

所以它们不是完全无意义，而是主要用于：判断策略是否触发、输出告警、统计指标、给出一个建议量、为以后形成闭环预留接口。

但从"实际控制设备"的角度看，当前策略 7 确实站在控制闭环旁边。它计算出的 `cmd(7)` 没有决定六台逆变器最终执行什么，因此存在与 AGC 重复计算、却没有实际接管控制的问题。

## 3. 改进后应该怎样连接

改进后不应把策略 7 的四类输出全部接给 AGC。

真正需要送给 AGC 的是：**策略 7 计算出的总有功调节需求 $\Delta P_{\mathrm{total}}$**。

建议形成如下结构：

```
联络线目标功率
PCC 实际功率
通信状态和数据质量
        ↓
改进后的策略 7
联络线功率外层控制器
        ↓
ΔP_total：系统总共需要增减多少有功
        ↓
AGC 资源分配器
        ↓
PV1、PV2、ESS1、ESS2、EV1、EV2 六路指令
```

其他输出仍有各自用途：

| 策略 7 输出 | 改进后的用途 |
|-------------|-------------|
| $\Delta P_{\mathrm{total}} / cmd$ | 送入 AGC 作为总调节需求 |
| `status` | 表示正常、降级、保持、退出、恢复等状态 |
| `alarm` | 提供通信异常或联络线越限告警 |
| `metric` | 记录跟踪误差、数据质量和控制性能 |

### AGC 内部还要不要计算偏差

最终结构中，**AGC 资源分配部分不应再重复计算 $P_{\mathrm{target}} - P_{\mathrm{PCC}}$**。

现有 AGC 应拆分成两个逻辑部分：

```
现有 AGC：

第一部分：
dP = Ptarget - Ppcc

第二部分：
根据 dP 分配六台设备
```

改进后：

```
策略 7：
负责第一部分，生成 ΔP_total

AGC 分配器：
只负责第二部分，把 ΔP_total 分配给六台设备
```

也就是把原来的 `AGC_Controller` 重构为类似 `TieLine_Controller` + `AGC_Resource_Allocator`。在实际程序里，它们不一定必须是两个完全独立文件，也可以是同一个程序中的前后两个函数。关键是**逻辑职责分清楚，不能两边重复计算偏差**。

---

## 4. 为什么不能简单把原 `cmd(7)` 直接接过去就结束

当前策略 7 只有一个非常简单的关系：$cmd(7) = P_{\mathrm{target}} - P_{\mathrm{PCC}}$。如果只是把这一根信号接给 AGC，那么只是消除了重复计算，还不构成论文改进。

真正研究的内容应当发生在策略 7 产生 $\Delta P_{\mathrm{total}}$ 的过程中。例如，在通信正常时使用最新 PCC 实测值计算 $\Delta P_{\mathrm{total}}$；当数据延时、丢包或冻结时，判断数据是否仍可信 → 决定使用实测值、估计值还是保持值 → 限制 $\Delta P_{\mathrm{total}}$ 继续累积 → 通信恢复时逐步重新接管。

因此，论文的改进对象不是"把一根线接上"，而是：

> **把原来只会用当前 PCC 数值做减法的策略 7，升级为能够处理通信非理想情况的联络线功率外层控制器。**

## 5. 离线情况下完全可以先实现

在板子接入前，可以在普通六逆变器 Simulink 模型中形成完整闭环：

```
PCC 测量
        ↓
通信延时、丢包、冻结仿真模块
        ↓
改进后的策略 7
        ↓
AGC 资源分配器
        ↓
六路功率指令
        ↓
模型内部通信链路
        ↓
六台逆变器
        ↓
PCC 重新变化
```

这个阶段可以完成：

- 原始策略 7 和改进策略 7 的对比

- AGC 六资源分配
- PCC 功率跟踪
- 命令累积与超调分析
- 通信恢复过程
- 论文大部分离线仿真结果

所以论文工作不需要等待 eHS 许可。

## 6. 最终可以完整部署到板子上

最终板端可以按照下面的顺序运行：

```
板子读取 RT-LAB 测量量
PCC、PVmax、SOC、六台实测功率、状态量
        ↓
检查通信和数据有效性
        ↓
改进后的策略 7
计算总调节需求 ΔP_total
        ↓
AGC 资源分配器
生成六路功率指令
        ↓
限幅、使能、序号和安全管理
        ↓
Modbus TCP 写回 RT-LAB
```

RT-LAB / eHS 侧运行：

```
六台逆变器主电路
PLL
功率环
电流环
PWM
滤波器
变压器
电网与负荷
```

因此最终形成：

```
RT-LAB / eHS 六逆变器
        ↓ 测量
外部板：策略 7 + AGC
        ↓ 六路命令
RT-LAB / eHS 六逆变器
        ↓
新的 PCC 反馈
```

这就是最终论文要展示的**控制器硬件在环闭环**。

策略 7 和 AGC 在板上可以表现为两个 C 函数，也可以编译成一个整体程序，但逻辑上必须保持：

```
策略 7 决定总共调多少
AGC 决定六台设备怎样分
```

## 7. 论文主攻方向是否已经明确

目前已经明确到足以开始工作的程度。

### 研究对象

2PV + 2ESS + 2EV 六逆变器光储充微电网

### 原始控制结构

策略 7 只监测和建议，AGC 独立计算偏差并分配六路指令

### 结构性改进

策略 7 升级为联络线功率外层控制器 → 输出总调节需求 → AGC 只负责六资源分配

### 要研究的问题

通信延时、丢包、数据冻结和恢复条件下，怎样保证联络线功率跟踪和六资源协调控制

### 最终验证

六逆变器 eHS 实时模型 + 外部控制板 + Modbus TCP 闭环

老师提出在 eHS 暂缓期间先研究控制策略并用仿真进行验证，也与这条工作路线一致。

但目前尚未最终冻结的是：

- 具体采用哪一种数据处理方法
- 是否使用预测补偿
- 是否使用命令—实测融合
- 如何设计通信恢复
- 最终公式和论文标题

这些必须根据基线试验暴露出来的真实问题再确定。

因此准确说法是：

> **论文的研究场景、控制层级和总体方向已经明确；最终算法形式尚需通过基线试验确定。**

## 8. 接下来开始六逆变器离线基线试验

是的，下一阶段在普通 MATLAB/Simulink 六逆变器模型中进行，暂不在 RT-LAB 平台进行。

RT-LAB 当前只保留已有的 CPU 性能结果，等待 eHS 条件明确后再进行实时迁移。离线仿真不受 100 μs 实时计算超限影响。

基线试验分三层推进：

### 第一层：模型物理基线

确认和整理：

```
六台设备功率方向
PV1 / PV2 响应一致性
ESS1 / ESS2 充放电一致性
EV1 / EV2 响应一致性
稳态功率平衡
命令—实测响应时间
```

其中部分已经完成，不重复做，只补第二台设备和完整六设备一致性。

### 第二层：正常通信下的控制基线

保持原始 AGC 不改，完成：

```
正向小阶跃
负向小阶跃
大阶跃跨资源层级
资源能力不足
remain
SOC 上下限
六台设备限幅
```

### 第三层：论文问题基线

保持原算法不改，加入：

```
固定通信延时
随机或连续丢包
PCC 数据冻结
六台设备实测数据冻结
完全通信中断
通信恢复
```

记录：

```
PCC 功率
目标功率
dP
六路命令
六路实测功率
remain
通信状态
恢复时命令跳变量
```

然后才能准确判断原方法最主要的问题究竟是：使用旧 PCC 数据、命令重复累积、实测响应未跟上、资源分配不合理、恢复时指令跳变，或者几种问题共同存在。

> **当前第一项具体工作不是立即修改策略 7，而是先复制并冻结一个六逆变器原始基线模型，然后核对策略 7 四类输出的实际终点、AGC 输入和六路指令链路，形成改进前的正式结构图。**
