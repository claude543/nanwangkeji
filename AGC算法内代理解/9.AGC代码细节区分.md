# AGC代码细节区分

## 正式第十一轮内化：AGC连续执行时序、周期保持，以及 `status`、`dP`、`remain` 的真实含义

前两轮分别解决了：

```text
第九轮：
各类资源的裕度从哪里来

第十轮：
alloc_up和alloc_down怎样分配裕度
```

这一轮把这些静态计算串成一个**连续运行的控制器**。

本轮需要彻底理解：

```text
1. Simulink多久调用一次AGC函数？
2. AGC多久真正重新计算一次指令？
3. 两个AGC周期之间输出为什么能够保持？
4. enable=0时究竟会发生什么？
5. status、dP和remain各自表示什么？
6. remain=0为什么不代表PCC实际误差已经为0？
7. 仿真时间回退时，程序到底重置了什么？
```

当前代码依据为上传的 `AGC_Controller.m`。

---

## 一、先理解两个不同的"运行周期"

AGC代码在Simulink模型中存在两个时间尺度。

### 第一种：函数调用周期

Simulink模型每运行一个仿真步长，MATLAB Function模块就可能调用一次：

```matlab
AGC_Controller(...)
```

例如，假设模型固定步长是 `100 μs`，那么1秒内函数可能被调用 `10000` 次。

这里的100 μs只是举例，模型最终以RT-LAB实际配置的固定步长为准。

### 第二种：AGC指令更新周期

虽然函数被频繁调用，但真正的功率分配只在满足以下条件时执行：

```matlab
if enable > 0.5 && ...
   (last_t < 0.0 || (t-last_t) >= T_UPDATE)
```

其中 `T_UPDATE = Ts_agc`，经过最小值保护后得到。

假设 `Ts_agc = 1 s`，则AGC通常只在 `t=0 s, 1 s, 2 s, 3 s……` 附近重新计算一次。

因此：

> **函数可以被快速调用，但AGC分配算法只按自己的慢周期更新。**

---

## 二、为什么不用 `mod(t, Ts_agc)`

之前讲解时曾用下面这种形式帮助理解：

```matlab
if mod(t,Ts_agc)==0
```

但当前实际代码并不是这样写的。

真实代码使用：

```matlab
(t-last_t) >= T_UPDATE
```

即当前时间减去上一次更新时间，是否已经达到AGC周期。

这种方法通常比直接判断 `mod` 更稳妥。因为实时仿真的时间点未必刚好等于 `1.000000 s`、`2.000000 s`，可能是 `1.0001 s`、`2.0002 s`。只要已经超过设定周期，就会在当前调用中执行更新。

---

## 三、`last_t` 是什么

```matlab
persistent last_t
```

它保存：AGC上一次真正执行功率分配时的时间。

例如：

```text
上一次更新：last_t = 5 s
现在：t = 5.4 s
Ts_agc = 1 s
```

则 `t - last_t = 0.4 s < 1 s`，不重新分配。

当 `t = 6.0 s`，则 `t - last_t = 1 s`，达到更新周期，重新计算。

更新开始时：`last_t = t`，把当前时间保存为新的上一次更新时间。

---

## 四、初始化时为什么 `last_t = -1`

初始化代码为：

```matlab
last_t = -1.0;
```

而更新时间条件中包含：

```matlab
last_t < 0.0
```

所以，只要 `enable > 0.5`，AGC第一次运行时就会立即计算，不需要先等待一个完整的 `Ts_agc`。

完整含义是：

```text
last_t < 0：
从未执行过正式AGC更新

因此：
立即运行第一轮控制
```

---

## 五、AGC初始化时六路指令是什么

第一次调用时，持久变量尚未建立，程序执行：

```matlab
pvInit = clamp(PV_init_kW,0.0,P_UNIT);
evInit = clamp(EV_init_kW,0.0,P_UNIT);

Ppv = [
    min(max(Ppvmax1_kW,0.0),pvInit), ...
    min(max(Ppvmax2_kW,0.0),pvInit)
];

Pess = [0.0,0.0];
Pev  = [evInit,evInit];
```

因此初始状态是：

- 光伏：取PV初始设定和当前PV最大可用出力中的较小值
- 储能：初始不充不放
- 充电桩：按 `EV_init_kW` 开始充电

假设：

```text
P_UNIT = 100 kW
PV_init = 20 kW
EV_init = 50 kW
Ppvmax = [80,60] kW
```

则初始化后：

```text
Ppv  = [20,20] kW
Pess = [0,0] kW
Pev  = [50,50] kW
```

EV输出为负，是因为内部 `Pev` 保存正的充电功率大小，最终接口采用负荷为负的符号。

---

## 六、一次函数调用究竟经过哪些步骤

当前函数每次被调用时，大致经过：

```text
参数保护
    ↓
首次调用则初始化
    ↓
更新PV最大可用出力
    ↓
限制Ppv和Pev范围
    ↓
检查仿真时间是否回退
    ↓
判断是否达到AGC更新条件
    ↓
满足条件才计算dP和分配资源
    ↓
无论是否更新，均输出当前持久状态
```

注意：

> 不是只有达到 `Ts_agc` 时，整个函数才运行；而是函数一直运行，只有核心分配部分受周期条件控制。

---

## 七、两个AGC周期之间，什么会保持不变

如果尚未达到更新时间 `(t - last_t) < T_UPDATE`，则不会重新执行：

- dP计算
- 死区判断
- 资源层级分配
- status更新
- last_dP更新
- last_remain更新

持久变量继续保存上一轮结果。

所以通常表现为：

```text
六路设备命令保持上一轮值
status保持上一轮值
dP保持上一轮采样值
remain保持上一轮结果
```

这相当于数字控制中的**零阶保持**。可以把它理解为调度员每1秒下达一次新任务。在两次下令之间，所有设备继续执行最近一次指令。

---

## 八、但并不是所有量都绝对保持

这是当前代码中非常重要的细节。

更新周期判断之前，程序每次调用都会执行：

```matlab
pvmax = [
    clamp(Ppvmax1_kW,0.0,P_UNIT), ...
    clamp(Ppvmax2_kW,0.0,P_UNIT)
];

Ppv = min(max(Ppv,0.0),pvmax);
Pev = min(max(Pev,0.0),P_UNIT);
```

### 1. 光伏指令可能在AGC周期之间发生变化

假设上一轮 `Ppv1` 命令 = 80 kW，当前还没到新的AGC更新时间。但光伏最大可用出力突然由100 kW下降为50 kW。程序立即执行 `Ppv1 = min(80, 50) = 50 kW`。因此，光伏命令会立即被压缩到新的最大可用出力，不必等待下一个AGC更新周期。

### 2. EV始终被限制在 `0 ~ P_UNIT`

如果由于异常数据导致内部 `Pev` 超出范围，也会在每次函数调用中被重新限制。

### 3. 储能没有同样的周期外全局限幅

代码没有在更新判断之前执行 `Pess = clamp(Pess, -P_UNIT, P_UNIT)`。因此，Pess不像Ppv和Pev那样在每次调用中统一修正。这也是之前发现的SOC边界问题能够存在的原因之一。

---

## 九、这意味着 "enable=0" 不等于全部冻结

当 `enable ≤ 0.5` 时，核心AGC分配不会执行。因此：

- 不会计算新的dP
- 不会重新分配PV、ESS、EV
- 不会更新status、last_dP、last_remain

但是前面的保护性限幅仍然会执行。

所以准确表述是：

> **enable=0时，AGC协调分配停止，但周期判断外的光伏和EV限幅仍然有效。**

例如AGC关闭时：原 `Ppv1` 命令 = 70 kW，新 `Ppvmax1` = 40 kW，`Ppv1` 仍然会被降低到40 kW。

因此，当前代码的 `enable` 不是"把整个函数完全冻结"，而是禁止执行新的AGC偏差分配。

---

## 十、enable关闭后，`status` 可能保持旧值

假设上一轮 `status = +2`（正向调节资源不足）。随后 `enable = 0`。由于代码没有在关闭使能时主动执行 `status = 0`，所以输出的 `status` 仍可能继续保持 `+2`。

`dP` 和 `remain` 也会保持关闭前最后一次更新的值。

这意味着监控界面不能简单把 `status = +2` 理解为"当前时刻AGC仍在运行且资源不足"，还必须同时查看AGC enable状态。

### 工程关注点记录

V4板端程序中应明确区分：

```text
AGC未使能
AGC正常运行
AGC资源不足
AGC通信无效
```

不能只依靠一个旧的 `agc_status` 判断当前运行状态。

---

## 十一、`dP` 输出到底是什么

正式更新时：

```matlab
dPnow = P_target_kW - P_pcc_kW;
```

之后保存：

```matlab
last_dP = dPnow;
```

最终输出：

```matlab
dP = last_dP;
```

因此，输出 `dP` 表示：

> **最近一次AGC更新开始时测得的PCC功率偏差。**

它不是当前每一个仿真步长的实时偏差，也不是资源分配完成后的剩余偏差。

### 例子

在 `t=1 s` 更新时：`P_target = 100 kW`，`P_pcc = 60 kW`，所以 `dP = 40 kW`。AGC随后分配了40 kW功率指令。即使分配后内部 `remain = 0`，输出 `dP` 仍然是 `40 kW`，因为它记录的是本轮控制开始时发现了40 kW偏差。

---

## 十二、`remain` 到底是什么

初始化：

```matlab
rem = abs(dPnow);
```

随后每完成一层资源分配，就执行：

```matlab
rem = rem - used;
```

最终：

```matlab
last_remain = max(rem,0.0);
```

因此，`remain` 表示：

> **按照当前资源命令边界完成分配后，仍未能分配给任何资源的调节需求。**

它是一个非负值，不带调节方向。调节方向需要结合 `dP` 符号或 `status` 符号判断。

### 例子1：全部需求都分配完成

原始 `dP = +100 kW`，PV承担60 kW，ESS承担40 kW。则 `remain = 100 - 60 - 40 = 0 kW`，表示算法已经找到100 kW的指令分配方案。

### 例子2：资源能力不足

原始 `dP = +100 kW`，PV最多承担30 kW，ESS最多承担40 kW，EV最多减少10 kW。则 `remain = 100 - 30 - 40 - 10 = 20 kW`，说明仍有20 kW需求没有资源可以承担。

---

## 十三、`remain = 0` 不等于PCC实际误差已经消失

这是本轮最重要的概念之一。

假设 `dP = +100 kW`。AGC成功生成PV增加60 kW、ESS增加40 kW。于是代码得到 `remain = 0`。

这只能说明控制器在数学上已经把100 kW任务分给了设备。但此时设备可能还没有完成响应。

真实过程是：

```text
AGC生成新指令 → 通信发送 → 设备本地控制器接收 → 功率逐渐变化 → PCC功率发生变化
```

因此，在指令刚产生的瞬间，PCC实际偏差可能仍接近100 kW。所以 `remain = 0` 不代表 `P_target - P_pcc = 0`，它只代表**未分配的指令需求 = 0**。

---

## 十四、为什么下一周期还需要重新测量PCC

如果设备能够立即、准确执行，下一周期PCC偏差可能接近0。但实际中可能存在：

- 设备响应滞后
- 功率环动态过程
- 限流
- 本地保护
- 通信延迟
- 光伏最大出力变化
- 负荷再次波动

因此下一周期必须再次读取 `P_pcc_kW`，重新计算 `dPnow = P_target - P_pcc`。

这就是PCC闭环存在的意义。控制器不是一次分配结束，而是：

```text
测量 → 分配 → 执行 → 再测量 → 再修正
```

---

## 十五、`status` 的五种状态

| 数值 | 含义 |
| ---: | --- |
| `0` | 本轮偏差位于死区内，或尚未正式执行更新 |
| `+1` | 正向调节，资源分配后剩余量不超过死区 |
| `-1` | 反向调节，资源分配后剩余量不超过死区 |
| `+2` | 正向调节资源不足，剩余需求仍超过死区 |
| `-2` | 反向调节资源不足，剩余需求仍超过死区 |

判断代码为：

```matlab
if rem > P_DEAD
    status = 2.0*sign(dPnow);
end
```

因此：

```text
dP > 0 且 remain > P_DEAD：status = +2
dP < 0 且 remain > P_DEAD：status = -2
```

---

## 十六、`status = ±1` 不一定代表 `remain = 0`

这是一个容易误解的细节。

代码判断资源不足的条件是 `rem > P_DEAD`，不是 `rem > 0`。

假设 `P_DEAD = 5 kW`，原始需求 = 50 kW，资源只能承担47 kW。则 `remain = 3 kW`。因为 `3 ≤ 5`，代码仍保持 `status = +1`。

含义是：虽然还有3 kW未分配，但它已经进入允许死区，不再判定为明显资源不足。

同样，如果 `remain` 恰好等于5 kW，由于判断使用 `>` 而不是 `>=`，状态仍是 `+1` 或 `-1`。

---

## 十七、死区内的 `remain` 为什么不是0

假设更新时 `dP = 3 kW`，`P_DEAD = 5 kW`。

```matlab
rem = abs(dPnow) = 3;
status = 0;
```

因为 `abs(dPnow) > P_DEAD` 不成立，所以不进入资源分配。但程序仍执行 `last_dP = dPnow`、`last_remain = max(rem, 0)`。

因此输出：

```text
status = 0
dP = 3 kW
remain = 3 kW
```

它表达的是：当前有3 kW偏差，但3 kW属于允许死区，因此控制器不动作。不能把 `status = 0` 理解为偏差绝对为0。

## 十八、完整连续运行例子

设定：

```text
P_UNIT  = 100 kW
P_DEAD  = 5 kW
Ts_agc  = 1 s

PV_init = 20 kW
EV_init = 50 kW

Ppvmax = [80,60] kW
SOC均正常
enable = 1
```

初始化状态：

```text
Ppv  = [20,20]
Pess = [0,0]
Pev  = [50,50]
```

### 第一次更新：t = 0 s

假设 `dP = +90 kW`。

光伏向上裕度：PV1 = 80 - 20 = 60 kW，PV2 = 60 - 20 = 40 kW，总裕度 = 100 kW。需求90 kW全部由光伏承担。

按比例：PV1增加 `90 × 60/100 = 54 kW`，PV2增加 `90 × 40/100 = 36 kW`。

新命令：

```text
Ppv  = [74,56]
Pess = [0,0]
Pev  = [50,50]
```

输出状态：

```text
status = +1
dP = 90
remain = 0
```

注意，`remain = 0` 仅表示90 kW已经分配完，不代表PCC已立即达到目标。

### 中间调用：t = 0.2 s

因为 `0.2 - 0 < 1`，尚未达到新周期。假设 `Ppvmax` 没有变化，则输出继续保持：

```text
Ppv  = [74,56]
Pess = [0,0]
Pev  = [50,50]

status = +1
dP = 90
remain = 0
```

即使此时实时PCC偏差已经变成30 kW，`dP` 输出仍然保持90 kW，因为尚未进行新的AGC采样更新。

### 第二次更新：t = 1 s

假设设备响应后，当前PCC仍差 `dP = +20 kW`。

当前光伏裕度：PV1 = 80 - 74 = 6 kW，PV2 = 60 - 56 = 4 kW，总计10 kW。

光伏先承担10 kW：`Ppv = [80,60]`，`remain = 10 kW`。

然后储能承担剩余10 kW。两台储能能力相同，所以平均分配：`Pess = [5,5] kW`。

最终：

```text
remain = 0
status = +1
dP = 20
```

### 第三次更新：t = 2 s

假设此时 `dP = +3 kW`。因为 `3 < 5`，进入死区。

六路命令不变：

```text
Ppv  = [80,60]
Pess = [5,5]
Pev  = [50,50]
```

输出：

```text
status = 0
dP = 3
remain = 3
```

这表示：仍有3 kW实际偏差，但控制器允许其存在，不再继续调整。

### 中间调用：t = 2.5 s

未达到新周期，输出保持：

```text
status = 0
dP = 3
remain = 3
```

这三个输出都是上一轮AGC更新结果，而非2.5 s时的连续实时计算结果。

### 第四次更新：t = 3 s

假设系统发生反向波动 `dP = -50 kW`。

代码首先增加EV充电负荷。当前 `Pev = [50,50]`，两台都还能增加50 kW负荷，总能力100 kW。需要50 kW，因此每台增加25 kW：`Pev = [75,75]`。

对外输出变为：`Pev_pu = [-0.75, -0.75]`。

状态：

```text
status = -1
dP = -50
remain = 0
```

整个过程说明，AGC不是每轮都从初始状态开始，而是从上一轮保存的 `Ppv`、`Pess`、`Pev` 继续调节。

## 十九、仿真时间回退时发生什么

代码中：

```matlab
if t < last_t
    last_t = -1.0;
end
```

例如模型重新开始一个仿真过程：之前 `last_t = 100 s`，现在 `t` 重新变成0 s。程序发现时间回退，把 `last_t = -1`。如果AGC使能，后面的更新判断立即成立，从而重新执行一轮AGC计算。

但是需要注意：**代码只重置了 `last_t`，没有重新初始化 `Ppv`、`Pess`、`Pev`。**

也就是说，源代码层面的逻辑是：更新时间基准重新开始，但原来的设备命令状态仍然保留。同样没有在这一行主动清零 `status`、`last_dP`、`last_remain`。

如果希望整个控制器完全回到初始状态，需要重新初始化MATLAB Function持久变量，或在代码中增加明确reset输入和复位逻辑。

---

## 二十、时间回退后为什么同一次调用就可能更新

代码顺序是：

```matlab
if t < last_t
    last_t=-1;
end

if enable>0.5 && ...
   (last_t<0 || ...)
    % 执行更新
end
```

因此，如果 `t < last_t` 且 `enable = 1`：先把 `last_t` 变为 -1，随后发现 `last_t < 0`，立即执行一次AGC更新。不需要等到下一次函数调用。

---

## 二十一、当前代码中三种"保持"要区分

### 1. 设备命令保持

未到更新周期时，主要依靠 `persistent Ppv/Pess/Pev` 保存上一轮命令。但Ppv仍可能因为最新 `Ppvmax` 下降而被强制降低。

### 2. 状态输出保持

未到更新周期或enable关闭时：`status`、`last_dP`、`last_remain` 保持上一轮值。

### 3. 物理设备保持

设备是否真正保持在命令值，取决于本地控制器、电气模型、设备能力、通信状态。这不是AGC持久变量本身能够保证的。

这三类保持不能混为一谈。

---

## 二十二、这一轮与板子V4有什么关系

板子上的C版AGC必须复现同样的时序逻辑：

```text
1. 保存上一轮六路内部命令
2. 保存上一次AGC更新时间
3. 按Ts_agc判断是否更新
4. 未到周期时继续输出上一轮命令
5. 更新时重新读取PCC、PVmax和SOC
6. 计算dP、status和remain
```

影子运行时不能只比较六路功率指令，还应同时比较 `agc_status`、`dP` 和 `remain`。并且必须在以下时刻比较：

- 首次使能
- 正常更新周期
- 死区内
- 资源不足
- enable关闭和重新打开
- 仿真时间重启
- PVmax突然下降

## 二十三、这一轮发现的工程问题

### 问题1：enable关闭后状态仍可能显示旧故障

可以考虑在未来工程版中区分：disabled、normal、resource shortage、communication invalid。但基础移植版先保持与当前代码一致。

### 问题2：PV限幅不受Ts_agc限制

它提高了光伏指令对可用出力下降的安全适应性，但也意味着PV指令并非严格只在AGC周期更新。测试时必须考虑这一点。

### 问题3：时间回退不等于命令复位

后续可能需要独立的 `AGC_RESET` 实现确定性复位。

### 问题4：remain只是算法未分配量

不能用它代替实际PCC跟踪误差。论文评价时需要同时记录：

```text
dP实际轨迹
remain算法轨迹
设备实际功率
设备指令功率
```

## 二十四、本轮论文关注点记录

本轮与RT-LAB最相关的研究问题是：

> 控制器认为已经完成指令分配，但通信和设备动态导致实际功率尚未完成响应。

这会形成 `remain = 0` 但实际PCC误差仍较大的情况。

可以进一步研究：

- 通信延时下的指令有效性判断
- 基于设备实际响应的二次校正
- 控制周期与设备响应时间的协调设计
- 命令序号与陈旧数据识别
- 丢包情况下的指令保持与安全回退

这正好能够结合当前V3.2已经建立的 `CMD_SEQ`、`BOARD_HEARTBEAT`、`RTLAB_HEARTBEAT`、`EXTERNAL_COMMAND_VALID`，形成后续论文候选。
