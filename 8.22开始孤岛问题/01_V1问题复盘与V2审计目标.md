# E2CR V2 架构问题复盘与本轮一次性审计说明

日期：2026-09-19  
模型：`K26_K50_CLEAN_P1`  
本文件只做问题复盘和审计说明，不代表 V2 已经改模。

## 1. 先回答两个核心问题

### 1.1 “ESS1先承担，Coordinator观察ESS1负担，再让GFL慢慢分担”是不是设计过但没有真正落实？

**不是完全没落实，而是只落实了一半。**

V1 已经真正加入了：
- ESS1 capability / burden（储能1能力/负担）计算；
- ESS2 capability（储能2能力）计算；
- `Pbase / pb3` 正常基础任务慢更新；
- S14-80 Normal Responsibility Release（正常责任释放）；
- P/Q联合能力、限速、记录和通信。

所以“ESS1长期负担 → ESS2慢慢分担”这条路径确实进入了模型。

但是，旧的 `Frequency Secondary（二次频率积分） → GFL有功分配` 仍然同时存在，而且在本次100 s真实运行里压倒了Pbase路径：

- Pbase ≈ -0.0145 pu；
- Primary ≈ -0.0674 pu；
- Secondary ≈ -0.1346 pu；
- 最终有功请求 ≈ -0.2165 pu；
- Primary + Secondary 占总请求约93.3%；
- Pbase仅约6.7%。

因此真正的问题是：**新的“ESS1负担→GFL分担”路径已经有了，但旧“频率二次→GFL长期P”没有退出，两个慢层级的职责重叠，旧路径把新设计盖住了。**

电压侧同理：V4.8 q-bias仍然把慢电压误差积分成GFL长期Iq，因此“ESS1作为唯一GFM直接管理长期V基准”的职责并未建立。

### 1.2 “现在是不是还要给所有跟网设备做余量监控？”

要做，但不能把ESS1和GFL的“余量”当成同一个概念。

**ESS1需要的是 GFM reserve/headroom（构网备用/余量）**：
- 当前长期承担了多少P/Q；
- 电流/调制还剩多少；
- 是否还有能力继续独自吸收扰动；
- 这些量决定“何时应该让GFL分担”。

**每台GFL需要的是 capability envelope（可调能力包络）**：
- available；
- Pmin/Pmax；
- Qmin/Qmax；
- SOC/能源约束；
- current headroom；
- modulation headroom；
- health/valid。

它回答的是“Coordinator现在最多能给我多少任务”。

因此V2不是再造很多“余量控制器”，而是：
1. ESS1继续提供GFM reserve；
2. ESS2/PV/EV逐步统一成标准 capability interface；
3. Normal Coordinator用同一个资源池分配任务。

ESS2在V1中已经有能力计算。V2要审清楚哪些结构可以抽象并复用到PV/EV，而不是每恢复一台再复制一套算法。

## 2. 最近几轮暴露的问题：必须全部带进V2审计

### 2.1 控制架构问题

1. **长期频率恢复职责错位**  
   旧 Frequency Secondary 把频差积分成GFL P任务。黑启动只有ESS2 available，于是长期调频几乎全部压到ESS2。

2. **长期电压恢复职责错位**  
   V4.8 q-bias把慢电压误差积分成GFL Iq。黑启动只有ESS2参加，于是ESS2成为主要长期电压慢调执行器。

3. **Normal Responsibility被旧Secondary覆盖**  
   Pbase慢分担真实存在，但100 s运行中只占最终请求约6.7%。

4. **能力层只看到设备可执行性，没有充分看到网络方向性风险**  
   故障前中央仍给出很宽的P可行区间，但Vpu已经降到约0.803 pu。V2必须审计在哪里加入“低压时只收紧继续增加吸收的方向”。

5. **母线基准恢复与资源分担没有彻底解耦**  
   正确V2应是：GFM Reference Secondary负责长期Fref/Vref；GFL Normal Coordinator负责P/Q分担和有限Primary。

### 2.2 动态数据已经证明的事实

这组证据足以支持“内部P循环来自频率链”的结构结论。

### 2.3 工具/改模层的返工经验

本轮V1正式改模还暴露了多种脚本工程错误，V2必须避免重复：

1. 误用内部Inport块数量代替父子系统真实外部PortHandles；
2. 包根目录重复拼接、说明文档被错误设成硬依赖；
3. Selftest状态机persistent未隔离；
4. 把生产Stateflow源码塞进人工Harness导致假失败；
5. `last_t` persistent在Coder下未先初始化；
6. CorrectionGain反馈形成代数环，需要Z1一拍延时；
7. OpComm/OpWrite边界误做成Nx1列矩阵，RT-LAB只接受1-D/[1×N]；
8. R3 preflight源块解析多取一层Parent导致误判。

因此V2 Patch必须继续沿用：
- read-only Audit；
- 语义preflight；
- byte-identical scratch；
- scratch Update/compile；
- formal whole-file backup；
- save exactly once；
- reopen verify；
- 独立Verifier；
- Build后Target Verify；
- OpComm/OpWrite边界统一 `Demux scalar → Mux 1-D`。

## 3. 本轮审计为什么不是“再做一次泛审计”

本轮只读审计仍然遍历四个实时任务，以防漏掉跨任务信号；但所有设计问题都围绕V2架构。

重点一次性回答35个问题，分为六组：

1. **ESS1 Fref/Vref最终参考链**：准确找到最终注入点；
2. **旧P Secondary / q-bias完整执行链**：找到V2应该切断或改义的位置；
3. **Normal P/Q dispatch与capability**：确认V1哪些可复用、哪些职责冲突；
4. **多GFL资源统一接口**：为PV/EV后续接回做一次性规划；
5. **OpComm / OpWrite /在线参数**：在改模前冻结；
6. **planned-island兼容与保护区**：保证V2只改变黑启动路径。

审计不会：
- `set_param`；
- add/delete block；
- add/delete line；
- save_system；
- 编译；
- 连接RT-LAB；
- Execute；
- 改在线参数。

源模型SHA、Dirty和SimulationStatus会在审计前后核对。

## 4. 这次审计必须给我们什么答案

审计结果上传后，下一轮设计必须能够明确写出：

1. `Fref_base → ΔF_secondary → Fref_eff → ESS1 Droop` 的精确插入位置；
2. `Vref_base → ΔV_secondary → Vref_eff → ESS1 voltage/droop` 的精确插入位置；
3. old P Secondary在黑启动V2下如何退出ESS2最终P，同时保留planned-island兼容；
4. q-bias中央Verror积分如何退出“母线电压二次”职责，但保留Router/Finalizer供未来Q-sharing；
5. ESS2最终P只保留 `Pbase + bounded Primary` 的唯一命令链；
6. ESS1 reserve与GFL capability的统一接口定义；
7. PV/ESS/EV如何逐台Join同一个Normal Coordinator pool；
8. bus-voltage directional derating插在哪个能力层；
9. 是否需要扩27/59 OpComm，若需要具体追加几项；
10. G27/G29/G30下一版最少记录什么、从哪个源端口来；
11. 哪些参数必须显式Constant暴露，Build后Target Verify；
12. 下一Patch的保护区和最小修改清单。

没有这些答案，就不写V2 Patch。
