# ESS2 下一阶段：慢速调频、Q环节复用、正常权限放开设计

日期：2026-09-18

## 1. Slow Secondary 的目标不是“死抠 50.000 Hz”

当前项目没有冻结一个特别严格的最终频率误差指标，因此下一阶段不应人为规定：

```text
必须 50.000 ± 0.01 Hz
```

更合理的功能验收是：

```text
Primary 后存在持续频差
↓
Frequency Secondary 慢速建立
↓
二次有功修正方向正确
↓
时间平均频差明显减小
↓
进入一个稳定、可接受的频率带
↓
Secondary 不持续积分到限幅
```

也就是说：

> 需要的是“有一个真正工作的慢速恢复层”，而不是追求数学上精确等于50 Hz。

最终允许频差带可以根据：
- GFM droop；
- PLL/频率测量噪声；
- 实际稳定数据；
- 项目要求；

再冻结，不在没有依据时拍一个过严数字。

## 2. Q外环不参与，不妨碍Frequency Secondary

当前两条控制轴独立：

```text
频率—有功：
f error
→ Primary / Frequency Secondary
→ P command

电压—无功：
V error
→ Q / q-bias / voltage support
→ q-axis current
```

因此：

```text
ESS2旧Q PI OFF
```

并不妨碍：

```text
Frequency Secondary ON
```

Frequency Secondary只需要：
- 可靠频率；
- ESS2有功调节能力；

即可工作。

## 3. 之前计划孤岛设计的Q环节还能不能复用？

可以复用，但必须明确“复用哪一个Q环节”。

### 不建议直接复用旧Q PI

当前planned-island Stage2~4本来就是：

```text
旧Q PI:
Qerror = 0
并hold基础q
```

也就是说旧Q PI在岛内不是正常主控权。

### 真正适合复用的是 V4.8 q-bias 路线

原planned-island Stage3已经设计：

```text
PCC voltage error
↓
SM central q-bias coordinator
↓
Router
↓
transport slot
↓
device Decoder
↓
V48 Finalizer
↓
Final Iq reference
```

这个结构的物理目的就是：

> 慢速恢复孤岛稳态电压工作点。

而且S14改造已经处理过：
- central q-bias 的stage语义；
- Q source router；
- ESS2 local decoder；

之间的语义一致性。

所以从结构上：

> **这套q-bias是黑启动完成后最值得复用的Q/V控制路径。**

但不能直接在下一轮和Frequency Secondary一起打开，因为黑启动初始条件不同，而且会同时增加两个控制责任。

正确顺序：

```text
Primary 已通过
↓
Frequency Secondary 单独验证
↓
持续监控 V / ESS1 Q / current / modulation
↓
如果电压和ESS1 Q余量一直健康
    q-bias继续OFF也可以
如果电压偏差或ESS1 Q压力明显
    再单独复用V4.8 q-bias
```

## 4. 当前authority到底是什么

当前Coordinator本身有设备能力范围。

对ESS2：
- 基础物理范围先由SOC等形成 `pmin3 / pmax3`；
- 在S14黑启动期间，再用 `auth3` 把范围缩成：

```text
pmin3 >= pb3 - auth3
pmax3 <= pb3 + auth3
```

因此：

```text
auth3
```

本质是：

> 黑启动恢复后，Coordinator围绕当前baseline允许ESS2再移动多远。

当前正式试验：

```text
auth3 = 0.001 pu
≈ ±100 W
```

这是commissioning小权限。

它不是正常运行的最终范围。

## 5. 当前是否已经设计好了“小权限→正常权限”？

### 有总体路线

项目此前已经冻结：

```text
handover
↓
Primary @ small authority
↓
Secondary @ small authority
↓
dynamic ESS1 GFM reserve
↓
authority expansion
↓
PV/EV逐台恢复
```

### 但最终动态authority还没有在模型里实现

现在仍然是：

```text
Python/Constant
→ 固定auth3
→ Coordinator限制在pb3±auth3
```

所以：

> **当前已经有“小权限机制”，但“根据ESS1/ESS2真实能力自动扩大成normal authority”的最后一层还没有实现。**

## 6. 正常authority应该怎么定义

孤岛中：

```text
ESS1 = 唯一GFM
ESS2 = GFL
```

ESS2改变P以后，ESS1必须承担相反方向的功率变化。

因此必须看方向。

### ESS2增加P（更大发电/更少充电）

系统中ESS1需要减少自己的P贡献。

所以ESS2向上权限必须受：

```text
ESS2自身向上能力
+
ESS1向下reserve
```

限制。

### ESS2减小P（更少发电/更多充电）

ESS1必须增加自己的P贡献。

所以ESS2向下权限必须受：

```text
ESS2自身向下能力
+
ESS1向上reserve
```

限制。

概念上：

```text
Auth_up_target
=
min(
    ESS2_up_headroom,
    ESS1_down_reserve,
    engineering_limit_up
)

Auth_down_target
=
min(
    ESS2_down_headroom,
    ESS1_up_reserve,
    engineering_limit_down
)
```

同时还必须受：

```text
ESS1 Q/current/modulation
ESS2 current/modulation
V/f health
```

约束。

## 7. 为了不把模型搞复杂，第一版怎样实现

当前Coordinator只接受一个对称 `auth3`。

为了复用当前结构，第一版不必马上改成双向两个authority输入。

可以先做：

```text
AuthNormalTarget
=
min(
    Auth_up_target,
    Auth_down_target
)
```

然后仍然喂给现有：

```text
auth3
```

这样虽然保守，但：
- 不需要重写Coordinator分配器；
- 不改变已有pmin/pmax结构；
- 能完成ESS2正常恢复阶段的能力放开；
- 后续多资源时若确实需要非对称能力，再升级成up/down两个权限。

## 8. authority怎么平滑从小变成正常

不能由Python运行中一点一点改。

建议模型新增一个：

```text
Authority Release Manager
```

输入：

```text
commissioning_auth = 0.001
AuthNormalTarget
Stage / health
```

输出：

```text
auth_used
```

时序：

```text
S14-60 Primary
auth_used = 0.001
↓
S14-70 Frequency Secondary
仍保持0.001
↓
Secondary验证完成
系统健康
↓
S14-80 NORMAL_AUTH_RELEASE
↓
auth_used
0.001
→ AuthNormalTarget
通过Rate Limiter慢慢扩大
```

如果普通小波动：

```text
冻结当前auth_used
或暂停继续扩大
```

不要立即终止试验。

如果明确严重异常：

```text
authority回缩 / 保护
```

这符合当前“普通波动记录观察，不轻易停止”的原则。

## 9. 怎样计算ESS1 reserve

不需要一开始做复杂优化器。

第一版只需要把“还有多少能力”转换成保守约束。

至少看：

```text
ESS1 P
ESS1 Q
ESS1 current
ESS1 modulation

ESS2 P
ESS2 current
ESS2 modulation

bus V
bus f
```

然后根据设备允许边界算：

```text
ESS1 P-up reserve
ESS1 P-down reserve
ESS2 P-up headroom
ESS2 P-down headroom
```

如果：

```text
current/modulation/V/f
```

接近边界，就收紧authority。

这就是动态GFM余量监督的本质。

## 10. 下一版模型应该一次准备好什么

为了减少反复Build，建议下一次小改模一次把剩余ESS2正常化基础设施准备好，但仍然通过Mode/Enable分阶段验证。

一次Build中加入：

1. `S14-70 FREQUENCY_SECONDARY`
2. Frequency Secondary独立enable
3. q-bias独立enable，默认OFF
4. ESS1 reserve / health输入
5. Authority Release Manager
6. `S14-80 NORMAL_AUTH_RELEASE`
7. 新增记录：
   - frequency secondary command
   - q-bias enable / actual
   - ESS1 P/Q/current/modulation reserve
   - AuthNormalTarget
   - auth_used
   - authority freeze/reduction reason

然后分阶段试验：

```text
Phase A:
Primary-only（已证明）

Phase B:
Frequency Secondary @ 0.001

Phase C:
正常authority平滑扩大

Phase D:
只有V/Q数据需要时才开q-bias
```

这样不需要每增加一个功能都重新Build。

## 11. 什么才算ESS2从“小权限”走到“正常运行”

不是：

```text
auth=0.02
```

或者某一个固定数字。

真正正常是：

```text
Coordinator ownership = 1
Primary = active
Frequency Secondary = active
authority不再由commissioning常数固定
而由系统实时能力约束
+
V/f健康
+
ESS1/ESS2无持续限流/调制饱和
```

也就是：

> ESS2能在整个孤岛需要它的时候承担合理的功率调节，同时不会把唯一GFM ESS1推到危险边界。
