# ESS2 下一阶段：从“小功率、小权限”到“正常恢复并网”最终规划 V1

日期：2026-09-18

---

# 1. 结论先行

当前已经完成并有真实 RT-LAB 动态证据：

```text
ESS1 GFM 建网
→ ESS2 同期/真实合闸
→ ESS2 -0.005 pu 小功率
→ Restore-state7
→ S14 → Coordinator 无扰接管
→ Beta = 1
→ 小权限 Primary
```

因此下一阶段**不再重复 -0.005 → -0.006**。

下一阶段的目标应直接变成：

> **让 ESS2 在 Coordinator 已经取得控制权以后，能够接受“新的正常基础有功任务”，平滑扩大功率，并在新基础任务稳定以后再平滑开放 Primary。**

这才是真正从“小功率、小权限”走向“正常恢复并网”。

---

# 2. 下一阶段是否需要改模？

## 2.1 如果只想做一次“更大 Pbase”试验：不需要改模

当前 R2.2 已经有：

```text
Mode4
CFG_E2HH_NEXT_TARGET_PU
CFG_E2HH_APPROVED_LIMITS
```

在 S14-60 中：

```text
Mode4
→ Primary OFF
→ Coordinator 的 Pbase 从当前值
   按批准变化率
   平滑移动到 NEXT_TARGET
```

所以如果只是想验证：

```text
-0.005
→ 某个更大负功率目标
```

完全可以只写 Python Runner：

```text
Mode = 4
NEXT_TARGET = 新目标
APPROVED_LIMITS = [Pmin, Pmax, up_slew, down_slew]
```

不改模型。

---

## 2.2 但如果目标是“真正正常恢复后长期运行”：当前模型还差一个小改动

当前源码实际分工是：

```text
Mode4
= baseline / 正常基础任务更新
= Primary OFF
```

```text
Mode5
= Primary ON
= baseline 不再按照 NEXT_TARGET 更新
```

因此当前模型能分别证明：

```text
正常任务会变化
```

或者：

```text
Primary 会围绕原 -0.005 工作
```

但还没有形成最终应有的：

```text
新的正常 Pbase
+
围绕新的 Pbase 做 Primary
```

长期组合。

这就是当前模型距离“ESS2正常恢复并网”还差的最关键一点。

### 推荐

**不要再为 Mode4 单独跑一轮。**

直接做一个很小的模型修正：

```text
Mode5
从：
固定 -0.005 baseline + Primary

改成：
正常 baseline update
+
baseline 到位、健康稳定
+
再开放 Primary
```

这样下一次 Build 后的一轮正式试验，就可以直接完成真正的“正常恢复”。

# 3. 最小改模应该怎么做

不增加第二套协调器，不重写 S14，不改 P PI。

仍然保持：

```text
S14-40  恢复/小功率资格
S14-50  ownership handover
S14-60  normal ESS2 operation entry
```

只把 S14-60 内部明确分为两个执行阶段。

## 3.1 S14-60A：Normal Base Ramp

条件：

```text
Beta = 1
Restore-state7
ESS2 available
Coordinator 已完全接管
```

行为：

```text
Primary correction = 0
Secondary = 0

Pbase:
当前接管基准
→ NEXT_TARGET

经过：
[Pmin, Pmax]
+
up/down slew
```

也就是：

```text
Pbase(k+1)
=
rate_limit(
    Pnormal_target,
    approved_limits
)
```

这一阶段只改变正常基础任务。

---

## 3.2 S14-60B：Normal Primary

当：

```text
Pbase 已到 NEXT_TARGET
+
Pmeas 跟踪正常
+
V/f/I 正常
+
无 CurrentLimit
+
保持一段健康时间
```

然后：

```text
CorrectionGain
0 → 1
```

继续复用当前已经 Build 和实测成功的：

```text
AA15_S14V2_CORRECTION_GAIN_RATE_LIMITER

rise = 0.25 /s
```

所以大约 4 s：

```text
Primary effective authority:
0%
→ 100%
```

不需要再额外造一个“authority ramp”。

# 4. 正常功率任务到底应该是什么？

这是一个非常重要的定义。

## 4.1 正常任务不是 PCC 联络线目标

J1 OPEN 时：

```text
上级电网并不存在供需交换通道
```

因此不能继续说：

```text
ESS2正常任务 = 为了跟踪PCC外送目标
```

这在孤岛里没有物理意义。

---

## 4.2 正常任务是“设备级有功调度目标”

定义一个量：

```text
P_ESS2_normal_ref
```

含义：

> 正常功率管理希望 ESS2 此时承担多少有功功率。

当前符号约定：

```text
P > 0
ESS2 向交流母线送电 / 放电

P < 0
ESS2 从交流母线吸收功率 / 充电
```

当前：

```text
-0.005 pu
≈ -500 W
```

就是小功率充电状态。

---

## 4.3 当前调试阶段谁给这个任务？

现在不用急着做完整 EMS。

下一阶段仍然可以由 Python 在第一次 Execute 前配置：

```text
CFG_E2HH_NEXT_TARGET_PU
```

把它当成：

```text
“模拟正常EMS给ESS2下发的正常任务”
```

这足以验证整个控制链。

---

## 4.4 最终工程里谁给？

后续真正正常运行时：

```text
EMS / 微电网功率管理
↓
根据：
岛内负荷
PV可用功率
ESS1/ESS2 SOC
储能余量
EV需求
能量计划
↓
给 ESS2 Pnormal_ref
```

S14不应该自己算长期调度。

S14只负责：

```text
恢复
资格
交权
什么时候允许正常控制接手
```

# 5. 下一轮正常任务应该选多大？

不再用：

```text
-0.006 pu
```

收益确实太低。

下一轮建议把第一个真正有意义的正常基础任务设为：

```text
Pnormal_target = -0.020 pu
≈ -2 kW
```

理由不是“2 kW就是正常额定值”。

而是：

```text
当前 -0.005
→ -0.020
```

相当于基础任务扩大 4 倍；

同时仍只是 100 kW 基准的 2%，属于明显但仍保守的扩展点。

它比：

```text
-500 W → -600 W
```

更有工程收益。

```text
启动/资格任务：
-0.005 pu

正常基础任务：
-0.020 pu

baseline approved range：

baseline下降速度：

```



这是连续斜坡，不是突然阶跃。

# 7. Primary权限下一轮怎么定义？

当前已经验证：

```text
authority = 0.001 pu
```

```text
Pbase = -0.020
```

```text
-0.022 ~ -0.018 pu
```

```text
APPROVED_LIMITS
```

# 8. 所谓“权限”到底有哪几种？

一定不能混淆。

## 8.1 Ownership 权限

```text
Beta
```

回答：

> 谁给 ESS2 最终 P 命令？

现在已经完成：

```text
Beta = 1
```

说明 Coordinator 100%拥有ESS2命令。

以后不需要再扩大Beta。

---

## 8.2 Normal dispatch envelope

```text
[Pmin, Pmax]
+
slew
```

回答：

> ESS2 正常基础任务允许走到哪里、走多快？

例如下一轮：

```text
Pbase目标 -0.020
```

但必须：

```text
-0.022 <= P <= -0.004
```

并且每秒不能变化超过批准速度。

---

## 8.3 Primary authority

```text
ess2_auth
```

回答：

> 在当前正常 Pbase 周围，调频最多再修正多少？

例如：

```text
Pbase=-0.020
auth=0.002
```

表示一次调频最多把它临时推到约：

```text
-0.022 ~ -0.018
```

# 9. 权限怎样“平滑切换”？

不建议运行中由 Python：

```text
auth 0.001
→ 0.002
→ 0.005
```

这样又把Host写参引进正式动态。

更合理：

## 启动前就写最终批准的 authority

例如：

```text
auth = 0.002
```

但是：

```text
CorrectionEnable = 0
```

所以实际上：

```text
有效Primary权限 = 0
```

---

## baseline 到位以后

模型自己：

```text
CorrectionEnable = 1
```

再经过现有：

```text
CorrectionGain Rate Limiter
```

使：

```text
有效Primary权限
0
→ 0.002
```

平滑放开。

也就是：

```text
effective_auth
=
CorrectionGain × auth
```

这是最简单、最干净的方式。

# 10. 当前模型是否已经“完善”？

## 已经完善的部分

有真实证据：

```text
ESS1黑启动建网
ESS2真实合闸
Restore-state7
ESS2小功率有功控制

```

这些不再是设计猜想。

---

## 还没有完全完善的部分

### 缺口1：正常baseline + Primary尚未合成一个最终运行模式

这是下一次最小改模要解决的问题。

### 缺口2：正常任务目前还是测试Constant

现在：

```text
NEXT_TARGET
```

仍是调试参数。

最终应该接：

```text
正常EMS/功率管理输出
```

但当前阶段不需要马上做完整EMS。

### 缺口3：ESS1动态余量监督还没有形成完整闭环

当前：

```text
APPROVED_LIMITS
auth
```

是人工批准的工程范围。

还不是：

```text
ESS1 P/Q/current/modulation实时余量
↓
自动算ESS2可用范围
```

下一轮可继续使用保守静态范围，但扩大到更高功率之前应逐步补这个监督。

### 缺口4：ESS2正常Q策略还没有最终冻结

当前旧Q PI仍保持隔离。

最终需要明确：

```text
ESS2正常保持Q≈0
```

还是：

```text
ESS2提供有限电压/Q支持
```

这可以在有功正常恢复以后单独处理，不要和下一轮同时修改。

# 11. 到底怎样才算“ESS2正常恢复并网”？

建议分两个层级。

## 11.1 ESS2有功正常恢复并网 —— 当前近期目标

至少同时满足：

### A. 物理连接

```text
真实breaker CLOSED
Restore-state7
FailCode=0
```

### B. 控制权

```text
Beta=1
Coordinator ownership
```

### C. 正常调度能力

ESS2不能再只会：

```text
固定 -0.005
```

而要能够：

```text
接收新的 Pnormal_ref
→ 平滑更新 Pbase
→ 到达目标
→ 稳定保持
```

### D. 一次协调能力

在新的 Pbase 上：

```text
Primary可以平滑投入
```

并遵守：

```text
authority
P上下限
slew
```

### E. 电气健康

全过程：

```text
V/f有界
CurrentLimit=0
无持续clip
ESS2电流有界
调制正常
无Fail
```

同时：

```text
ESS1 GFM没有明显进入能力边界
```

达到 A~E 后，可以正式写：

> **ESS2已完成黑启动后的有功正常恢复并网，并进入正常Coordinator管理。**

---

## 11.2 ESS2完整正常功能恢复

如果项目还要求ESS2承担Q/电压辅助，则还需：

```text
明确正常Q策略
+
验证Q/电压功能
```

否则当前最多是：

```text
有功正常恢复完成
```

不能把尚未验证的Q功能一起宣布完成。

# 13. 下一步究竟是改模还是Python？

## 推荐答案

**做一个小改模，然后Python配置参数。**

不是大改。

模型只改：

```text
Mode5 / S14-60
```

让它：

```text
先 baseline ramp
↓
到位健康
↓
再 Primary
```

Python只负责第一次Execute前设置：

```text
Mode=5

pickup=-0.005

normal target=-0.020

approved limits=
[-0.022, -0.004, 0.0025, 0.0025]

```

之后：

```text
第一次Execute以后

```

# 14. 为什么这是现在最合理的推进

它直接回答真正的下一阶段问题：

```text
ESS2能不能从调试小功率
平滑进入一个明显更大的正常功率工作点
```

以及：

```text
到了新的正常工作点以后

```

这两项一旦通过，我们就不再只是：

```text
“ESS2恢复后能带500~600 W”
```

而是可以开始把它定义为：

```text
“已经进入正常有功调度体系的恢复资源”
```

然后下一阶段才是：

```text
继续扩大ESS2允许范围
+
ESS1余量监督
+
下一台GFL恢复
```
