# 7.21日试验2为什么一定要做

## 结论

我们现在做的不是"重新证明老师搭的模型对不对"，也不是单纯为了证明`AGC周期0.1 s不合理`。

我们在做的是：

> **给现有模型建立一套可用于板端接入、算法改进和论文对比的真实基线。**

老师给出的15项策略波形，主要证明策略层在设定工况下能输出相应的状态、告警、指标和建议控制量；但其中很多`cmd`还没有真正接管设备，文档也明确说明，形成闭环实控还需要策略仲裁和设备功率分配。 

而我们现在验证的是另一层问题：

```text
命令是否真正到达设备
→ 设备实际功率怎样响应
→ PCC怎样变化
→ 基础AGC使用的假设是否成立
→ 板端接入后应该读取什么、怎样控制
```

这部分是老师提供的15项策略波形无法替代的。

# 一、刚完成的两个试验得出了什么

## 1. PCC功率方向试验

两台光伏总命令由60 kW增加到100 kW：

```text
PCC平均值：−59.89 kW → −20.08 kW
变化量：+39.81 kW
```

这证明当前Simulink模型中：

```text
PCC功率增加方向 = 微电网向外送电方向
PCC正值 = 向外送电
PCC负值 = 从外部购电
```

而我们发给工程师的通信点表采用的是：

```text
正值购电
负值送电
```

所以后续40101不能直接接模型原始PCC信号，必须在接口处取反，或者统一修改整个工程约定。

这是直接推动工程的结果，不是论文试验。

---

## 2. PV1命令—实测响应试验

测试条件：

```text
PV1命令：0.30 pu → 0.50 pu
额外通信延时：0
丢包：0
AGC：关闭
```

得到：

```text
开始明显响应延迟：约0.076 s
10%～90%上升时间：约0.964 s
达到90%总时间：约1.040 s
最终实测均值：0.5000 pu
稳态平均误差：接近0
```

这个结果说明：

### 稳态方面

PV1最终能够准确跟踪50 kW命令，没有明显长期偏差。

### 动态方面

命令已经变成50 kW时，设备实际功率还要大约1 s才能接近目标。

因此：

```text
稳态时：命令≈实测平均值
动态时：命令≠实测功率
```

当前AGC内部保存的是上一轮设备命令，并用它代表设备当前状态，没有读取六台设备实际功率。

所以PV1试验已经证明：

> 在动态过程中，"上一轮命令等于设备当前功率"这个假设并不严格成立。

但这还没有证明该差异一定会使AGC失稳，也没有证明必须采用命令—实测融合算法。后面必须通过完整AGC闭环试验确认它是否真的造成控制性能下降。

# 二、我们是不是在证明AGC周期0.1 s不合理

**不是。**

PV1响应时间约1 s，而AGC周期为0.1 s，只能说明：

```text
一个设备动态过程中
AGC可能更新约10次
```

但控制器的更新周期比被控对象响应速度快，是常见情况，并不自动代表周期错误。

判断`0.1 s`是否合理，不能只看：

```
T_AGC < T_device
```

而要看完整闭环结果：

* PCC是否稳定跟踪；
* 是否持续超调；
* 是否重复增加命令；
* 是否发生振荡；
* 最终是否进入死区；
* 命令是否触及资源边界。

因此真正判断0.1 s是否合理的是**第三个试验：理想通信下基础AGC闭环阶跃试验**。

可能出现三种结果：

| AGC闭环结果      | 判断                      |
| ------------ | ----------------------- |
| 稳定、误差小、无持续振荡 | 0.1 s可以保留，不需要因为PV响应慢就修改 |
| 有明显超调，但仍稳定   | 可以调整周期、增益或加入变化率限制       |
| 持续累加、振荡或方向错误 | 基础AGC本身需要修改，论文方向也要重新评估  |

所以现在不能下结论说`0.1 s不合理`，更不能直接改周期。

# 三、老师的模型参数为什么还需要测试

老师给出的参数是当前模型的**基线设计值**，但我们的后续工作不是只重复老师已有的仿真，而是要：

1. 把算法迁移到外部板；
2. 建立板子与RT-LAB的真实闭环；
3. 在延时、丢包、数据冻结等情况下验证；
4. 找到可以形成论文的问题并改进。

一旦算法从Simulink内部移到板子上，系统会新增：

* 1 s通信周期；
* 编码和解码；
* 网络延时；
* 数据陈旧；
* 命令丢失；
* 心跳和状态机；
* 外部命令接管与退出；
* 通信恢复后的重新投入。

因此，老师原模型中的参数只能作为基线，不能直接替代板端接入后的重新验证。

我们的工作不是修改老师的所有参数，而是先回答：

> 在当前参数下，模型实际表现是什么？

只有基线确定后，后续修改周期、算法或通信策略才有对照，否则改完后无法证明改善来自哪里。

# 四、15项策略波形已经有了，我们为什么还要做这些试验

15项策略波形主要验证的是：

```text
给定输入和阈值
→ 对应策略是否触发
→ status/alarm/metric/cmd是否符合预期
```

例如：

* AGC跟踪误差是否报警；
* 防逆流是否输出抑制量；
* 平滑策略是否输出平滑需求；
* 削峰填谷是否输出充放电建议。

这些波形对应的是策略逻辑验证。文档明确说明，15项策略输出主要是建议控制量，当前还缺少统一仲裁和六台设备分配。

我们现在测试的是：

```text
设备收到功率命令后
真实逆变器和电气模型如何响应
```

两者层级不同：

| 老师已有波形                     | 我们当前试验            |
| -------------------------- | ----------------- |
| 验证策略逻辑输出                   | 验证设备执行和物理响应       |
| 主要看status/alarm/metric/cmd | 主要看Pref/Pmeas/PCC |
| 多数是策略建议量                   | 是实际接入设备的命令        |
| 不包含外部板                     | 为外部板接入建立基线        |
| 不回答命令与实测差异                 | 专门回答命令与实测差异       |

所以不是重复工作。

# 五、是不是必须把六台设备全部完整测试一遍

**不需要六台都做完全相同的详细动态试验。**

因为两台PV、两台ESS、两台EV基本采用相同控制模板。合理的最小测试集合是：

## 需要详细测试

### PV1

已经完成：

```text
发电功率增加响应
```

### ESS1

需要两组：

```text
0 → 正值：放电响应
0 → 负值：充电响应
```

因为储能是双向设备，充电和放电可能表现不同。

### EV1

需要两组：

```text
−0.6 → −0.3：减少充电
−0.3 → −0.6：增加充电
```

因为EV是负荷，符号与PV相反。

## 只需要一致性检查

对PV2、ESS2、EV2不必再完整测响应时间，只需确认：

* 符号一致；
* 0.3 pu对应约30 kW；
* 同类设备没有接线或参数异常。

所以不是要机械测试六台，而是要覆盖三类资源的不同物理性质：

```text
PV：单向发电
ESS：双向充放电
EV：单向可控负荷
```

# 六、测试ESS和EV到底有什么实质作用

## 1. 确定40109～40114的正式定义

V3.2已经预留：

```text
40109～40114：六台设备实际功率
```

但当前第一阶段它们只是辅助监测点，默认不参与有效性判断。

通过测试才能确定：

* 每个点接模型中的哪个信号；
* 正负号；
* 标幺转kW比例；
* 正常范围；
* 是否需要滤波；
* 是否值得作为未来AGC输入。

这会直接推动V4和V5接口冻结。

## 2. 为V5调试建立正常基准

以后板端写命令后，如果ESS实际功率没有变化，需要判断是：

* 板端算法错误；
* Modbus编码错误；
* RT-LAB解码错误；
* 外部命令没有接管；
* 还是设备本地正常响应较慢。

现在先测清楚设备正常动态，V5调试时才能快速定位。

## 3. 判断论文问题是否具有普遍性

如果只有PV响应约1 s，而ESS和EV很快，那么论文不能泛化成"所有资源都有明显命令—实测差异"。

可能需要研究：

> 异构资源动态响应差异下的功率分配。

如果PV、ESS和EV都存在明显不同的动态速度，那么按静态可调裕度比例分配可能存在问题，论文价值更强。

如果三类资源都响应很快、最终准确，那么命令—实测融合可能不是最强方向，应转向通信数据陈旧和恢复重投。

所以测试三类资源不是为了积累曲线，而是为了决定论文方向是否成立。

# 七、接下来真正关键的试验是什么

当前建议不要无限扩展设备测试。完成最小的ESS和EV代表性试验后，应尽快进入最关键的闭环试验。

## 第一步：ESS1代表性测试

验证：

* 正命令是否放电；
* 负命令是否充电；
* 响应时间；
* 稳态跟踪；
* SOC变化方向。

## 第二步：EV1代表性测试

验证：

* 负命令是否对应充电；
* 命令绝对值增大时，实际充电功率是否增大；
* 响应速度和稳态误差。

## 第三步：理想通信下基础AGC闭环阶跃

这是决定后续方向的核心。

它要回答：

> 当前AGC在不考虑外部通信问题时，本身能不能稳定控制PCC？

观察：

* PCC目标跟踪；
* 六路命令；
* 六路实测；
* `dP`；
* `remain`；
* `status`；
* 是否重复分配；
* 是否超调、振荡或触及边界。

## 第四步：再加入通信非理想

只有理想基线正常后，才加入：

* 固定延时；
* 随机丢包；
* 测量冻结；
* 通信中断和恢复。

这样才能证明性能下降确实由通信造成。

# 八、这些工作能否推进项目和论文

## 对项目工程的推动

已经产生的直接成果：

1. 发现模型PCC方向与我们制定的点表相反；
2. 建立了13路命令—实测—PCC观测通道；
3. 确认PV1命令到实际功率的完整链路有效；
4. 得到PV1正常动态响应基准；
5. 为40109～40114真实接线提供依据；
6. 为V4/V5接口和调试建立分层判断方法。

这不是旁支工作，而是在为V4、V5降低风险。

## 对论文的推动

目前得到的是一条初步证据：

```text
设备稳态能够跟踪命令
但动态阶段存在约1 s响应过程
```

它提示命令—实测融合可能有价值，但还不足以锁定论文。

真正能推动论文定题的是：

```text
设备动态差异
+
基础AGC闭环表现
+
通信非理想造成的性能退化
```

完成这三层后，我们才能有依据选择：

* 命令—实测融合；
* 异构资源动态裕度；
* 数据新鲜度感知；
* 延时补偿；
* 通信恢复无扰投入；
* 或基础AGC周期和分配机制改进。

---

## 当前工作边界

接下来只做必要的最小集合：

```text
ESS1充/放电
→ EV1增/减充电
→ 理想通信AGC闭环
```

不需要把六台设备全部做成一套完整论文级测试，也不应现在直接修改AGC周期。

**0.1 s周期是否需要调整，由理想通信AGC闭环结果决定；论文是否继续走命令—实测融合方向，由PV、ESS、EV三类资源的动态差异和后续闭环性能共同决定。**
