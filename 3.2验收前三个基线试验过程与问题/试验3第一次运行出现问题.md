# 试验3第一次运行出现问题

## 结论

**这次基础AGC闭环没有通过预期测试。**

目标由约`−60 kW`变为`−40 kW`后，PCC没有稳定在`−40 kW`附近，而是继续上升到约`−20 kW`，产生约20 kW的持续超调。同时：

* `dP`长期约为负的20 kW；
* `remain`长期约为正的20～30 kW；
* `agc_status`稳定在`−2`；
* PV命令升高到约`0.52 pu`；
* ESS始终为0；
* EV命令仍保持约`−0.60 pu`。

这说明当前闭环进入了：

```text
PV出力增加过多
→ PCC超过目标
→ AGC识别到需要减小微网出力
→ 但对应的负向调节没有真正落实
→ PCC长期停留在目标上方
```

不过，**现在还不能直接得出"AGC周期0.1 s不合理"或"老师的AGC算法有错误"的结论**。当前试验还存在启动过程干扰和命令链路疑点，需要先排除。

# 一、五张图分别说明什么

## 1. PCC目标跟踪图

蓝色目标：

```text
−60 kW → −40 kW
```

黄色实际PCC：

```text
约−60 kW
→ 穿过−40 kW
→ 最终中心约−20 kW
```

这证明调节方向最初是正确的：

```text
目标要求少购电20 kW
→ PV增加
→ PCC向正方向上升
```

但AGC没有在`−40 kW`附近停止，出现明显过调。

---

## 2. `dP`和`remain`

目标阶跃后期：

```text
dP ≈ −20 kW
remain ≈ 20～30 kW
```

当PCC约为`−20 kW`、目标为`−40 kW`时：

```
dP = -40 - (-20) = -20 kW
```

所以负的`dP`是合理的，它表示当前微电网出力过多，需要增加用电或减少发电。

但`remain`长期不为0，说明AGC认为这部分负向调节需求没有被设备能力完全承担。

---

## 3. `agc_status=-2`

代码中，当本轮分配后仍有超过死区的剩余调节量时：

```
status = 2 × sign(dP)
```

因此：

```text
status = −2
```

表示：

> 当前需要负向调节，但算法认为资源调节能力不足，仍存在未分配量。

可是当前EV仍有从`−0.60 pu`向`−1.00 pu`增加充电的理论空间，储能也可以进入充电，因此这个现象需要进一步排查。

---

## 4. PV图

两台PV的命令由约`0.30 pu`逐级上升到约`0.52 pu`，实测功率跟随到相近水平。

这说明：

```text
AGC增加PV命令
→ 内部通信链路传递成功
→ 两台PV实际执行
```

但是PV命令在目标阶跃前就已经开始逐级变化，这暴露出一个试验设计问题：

> AGC从模型启动时刻就已使能，它把逆变器启动暂态和PCC初始波动也当成了调节偏差。

所以当前PV命令在正式目标阶跃前已经偏离初始值，目标阶跃试验不是从一个干净稳态开始。

---

## 5. ESS和EV

ESS命令与实测始终约为0。

EV命令始终约为`−0.60 pu`，实测在启动后稳定到约`−0.60 pu`。

按照代码，当`dP<0`时，正常顺序应为：

```text
先增加EV充电
→ 再增加ESS充电
→ 最后降低PV
```

但当前图中这三类负向动作都没有明显发生，而状态却变成`−2`。因此需要确认：

* AGC内部原始六路输出是否已经变化；
* 模型内部通信后、设备实际收到的命令是否一致；
* 是否有测试模型残留连线；
* AGC内部persistent状态是否在启动期间已经发生异常积累。

---

# 二、当前试验真正发现了什么

这次结果已经证明：

1. PCC反馈闭环是通的；
2. AGC能够改变PV命令；
3. PV实际功率和PCC能够响应；
4. 当前基线在这次运行中没有跟踪到目标；
5. 负向调节阶段存在明显异常；
6. AGC从启动暂态就开始调节，使试验基线受到污染。

所以这次试验不是失败得毫无价值，而是暴露了两个必须分开的潜在问题：

```text
问题A：试验没有等待系统稳态后再投入AGC
问题B：AGC负向调节命令可能没有正确形成或传递
```

# 四、下一步应怎么处理

不要继续进入通信延时、丢包试验，也不要马上修改AGC周期。

下一步应重新做一次**干净的基础AGC闭环试验**，同时增加原始命令诊断。

## 1. 延迟投入AGC

将原来的固定：

```matlab
CFG_AGC_enable = 1
```

改成Step：

```text
0～3 s：AGC_enable = 0
3 s以后：AGC_enable = 1
```

这样0～3 s内：

* 六台设备按初始命令运行；
* 设备实际功率完成启动；
* PCC先稳定在约`−60 kW`；
* AGC不对启动暂态做出错误反应。

## 2. 将目标阶跃推迟

设置：

```text
0～5 s：P_target = −60 kW
5 s以后：P_target = −40 kW
```

时间关系变成：

```text
0～3 s：设备自行启动，AGC关闭
3～5 s：AGC投入，但目标仍等于初始PCC
5 s以后：正式施加20 kW目标阶跃
```

这样才能把"启动暂态"和"目标阶跃响应"彻底分开。

## 3. 增加六路AGC原始输出观测

当前记录的是设备最终收到的六路Pref。下一次Build前建议把观测向量再加入：

```text
AGC原始PV1命令
AGC原始ESS1命令
AGC原始EV1命令
AGC原始PV2命令
AGC原始ESS2命令
AGC原始EV2命令
AGC_enable
```

然后比较：

```text
AGC_Controller原始输出
        ↓
模型内部通信链路后命令
        ↓
设备实际Pmeas
```

这样可以明确：

* AGC是否真的输出了EV增加充电或ESS充电命令；
* 命令是否在内部通信模块中丢失或保持旧值；
* 问题来自AGC计算层，还是命令传输和设备接线层。

# 六、问题2：Simulink模型内AGC缺少负向调节分支

## 结论

你发现的是当前异常的直接根因。Simulink模型内的AGC代码与之前上传的完整.m文件确实不一致。

我重新逐行比较后确认：

* 外部文件`AGC_Controller(2).m`包含完整的正、负两个调节分支；
* Simulink模块中导出的`simulinkAGC_Controller.m`只保留了`dPnow>0`的正向分支；
* 整个`dPnow<0`对应的else负向调节分支被缺失了。

我之前默认外部.m文件就是模型内实际运行的代码，这是错误的。实际仿真必须以Simulink MATLAB Function块里的代码为准。

---

## 一、两版代码的关键差异

### 外部完整.m文件

完整版本的结构是：

```matlab
if abs(dPnow) > P_DEAD
    if dPnow > 0
        % PV增加
        % ESS放电
        % EV减少充电
    else
        % EV增加充电
        % ESS充电
        % PV降低
    end

    if rem > P_DEAD
        status = 2.0*sign(dPnow);
    end
end
```

其中负向分支明确执行：

```matlab
status = -1.0;

[Pev, used] = alloc_up(Pev, [P_UNIT, P_UNIT], rem);
rem = rem - used;

essLower = [-P_UNIT, -P_UNIT];
[Pess, used] = alloc_down(Pess, essLower, rem);
rem = rem - used;

[Ppv, used] = alloc_down(Ppv, [0.0, 0.0], rem);
rem = rem - used;
```

也就是：

```text
dP < 0：
EV增加充电
→ ESS增加充电
→ PV降低出力
```

### Simulink模块中的实际代码

Simulink版只存在：

```matlab
if abs(dPnow) > P_DEAD
    if dPnow > 0.0
        status = 1.0;

        [Ppv, used] = alloc_up(...);
        ...
        [Pess, used] = alloc_up(...);
        ...
        [Pev, used] = alloc_down(...);
        ...
    end

    if rem > P_DEAD
        status = 2.0*sign(dPnow);
    end
end
```

在`dPnow>0`分支结束后直接进入remain判断，没有else分支。

---

## 二、这能完全解释刚才的试验现象

当目标为：

```
P_target = −40 kW
```

而PCC超调到约：

```
P_PCC = −20 kW
```

则：

```
dP = −40 − (−20) = −20 kW
```

此时模型中的实际代码执行过程是：

```text
dP < 0
→ 不进入 if dPnow > 0
→ 没有 else 负向分支
→ PV、ESS、EV命令全部保持上一状态
→ rem仍等于|dP|
→ rem > P_DEAD
→ status = −2
```

因此必然出现我们看到的现象：

```text
PV：保持在已经升高的约0.48～0.50 pu
ESS：始终为0
EV：始终为−0.60 pu
PCC：停留在约−20 kW
dP：持续为负
remain：持续大于0
status：持续为−2
```

所以这次异常：

* **不是**内部通信吞掉了命令；
* **不是**ESS或EV执行失败；
* **不是**首先由`Ts_agc=0.1 s`造成；
* **不是**设备响应约1 s直接造成；
* **而是**Simulink模型中的AGC缺少负向调节代码。

---

## 三、这也解释了为什么原始命令与最终命令完全重合

我们此前观察到：

```text
ESS原始命令 = 最终命令 = 0
EV原始命令 = 最终命令 = −0.60
```

这不是通信层把变化后的命令丢失了，而是：

> AGC模块本身从来没有生成ESS充电和EV增加充电的新命令。

因此原始命令与最终命令完全相同是合理的，说明内部通信链路反而没有暴露出问题。
