# 试验三修改后成功运行与新问题

## 结论

**替换完整AGC代码后，基础AGC闭环已经能够把PCC从约−60 kW调节并稳定到−40 kW附近。此前PCC停在−20 kW、`status=-2`且ESS/EV不动作的问题，确实由Simulink模块缺失负向调节分支造成。**

但本次结果又暴露出一个新的、真正属于算法性能的问题：

> **AGC虽然最终实现了PCC目标跟踪，却通过PV增发、EV增充和ESS充电相互对冲来实现，资源动作幅度明显过大。**

---

# 一、本次结果证明了什么

## 1. 完整AGC闭环已经跑通

PCC图显示：

```text
0～5 s：目标约−60 kW
5 s以后：目标变为−40 kW
```

实际PCC最终也稳定在−40 kW附近。因此完整链路已经成立：

```text
PCC目标
→ AGC计算dP
→ 六路命令分配
→ PV/ESS/EV执行
→ PCC变化
→ 再反馈给AGC
```

这说明当前完整AGC已经具备作为后续V4板端代码移植参考基线的基本条件。

## 2. 负向调节分支已经实际生效

更换完整代码后可以看到：

* EV命令由约`−0.60 pu`逐步下降至`−1.00 pu`；
* ESS命令由0逐步变为约`−0.20 pu`；
* PV不再只增不减，而会根据偏差继续调整。

这正是完整代码中`dP<0`时的调节逻辑：

```text
EV增加充电
→ ESS增加充电
→ PV降低
```

完整代码按PCC偏差的正负执行两套资源分配逻辑。

因此此前ESS和EV始终不动作，并不是设备或内部通信问题，而是模型中运行的代码版本不完整。

## 3. AGC原始命令与设备最终命令一致

PV、ESS、EV的图中，原始命令与内部通信后的最终命令重合，说明：

```text
AGC输出
→ 内部Modbus/RS485链路
→ 设备Pref
```

没有出现明显命令丢失、符号改变或延迟异常。

目前算法计算层到设备命令输入层的链路是正常的。

## 4. `dP`和`remain`不再长期异常

目标变化后，`dP`在0附近正负波动，`remain`基本接近0或只出现短时小值。

这说明：

* AGC能够识别正、负偏差；
* 调节需求基本可以分配完；
* 不再长期保持`status=-2`和大额未分配量。

# 二、当前真正暴露出来的问题

虽然PCC最终跟踪成功，但六台设备的最终状态并不合理。

大致可以看到：

```text
PV1、PV2：
约0.30 pu → 接近1.00 pu

EV1、EV2：
约−0.60 pu → −1.00 pu

ESS1、ESS2：
约0 → 约−0.20 pu
```

初始与最终总功率变化可粗略理解为：

### PV增加

两台PV合计：

```
(1.0 - 0.3) × 2 × 100 = +140 kW
```

### EV增加充电

两台EV合计：

```
(-1.0 + 0.6) × 2 × 100 = -80 kW
```

### ESS充电

若两台各约`−0.20 pu`：

```
-0.2 × 2 × 100 = -40 kW
```

最终净变化约为：

```
140 - 80 - 40 = 20 kW
```

刚好对应PCC目标从−60 kW变为−40 kW所需的20 kW变化。

也就是说，算法最终采用的是：

```text
PV多发140 kW
同时EV多用80 kW
同时ESS充电40 kW
最终净增加20 kW
```

PCC目标虽然实现了，但内部产生了明显的相互对冲。

---

# 三、为什么会出现资源相互对冲

当前AGC是增量式分配：

1. 每隔`0.1 s`读取一次PCC误差；
2. 将当前全部偏差继续叠加到上一轮命令；
3. PV、ESS和EV实际响应约需1 s；
4. PCC原始功率还存在较明显纹波；
5. 死区只有2 kW。

因此可能形成：

```text
PCC略低于目标
→ 连续增加PV命令

PV尚未完成响应
→ AGC再次增加PV

PCC随后越过目标
→ 开始增加EV充电

继续越过
→ ESS也开始充电

最后依靠多类资源相互抵消稳定在目标
```

现有AGC保存上一周期命令状态，而不是根据六台实际功率重新估计设备当前状态。

因此，本次结果比之前单设备试验更进一步证明：

> 命令—实测约1 s的动态差异，确实可能在闭环中造成重复调节和资源对冲。

但还不能只凭这一组试验确定根因完全是`Ts_agc=0.1 s`。PCC纹波、2 kW死区、增量分配方式和缺少命令回退机制也可能共同作用。

# 四、这对工程和论文有什么意义

## 工程方面

现在已经确认：

1. 完整AGC代码才是可用基线；
2. 当前内部通信链路可以正确传输六路命令；
3. PCC目标跟踪闭环能够成立；
4. 当前算法可能导致资源快速触及边界；
5. V4不能移植Simulink中的残缺代码，必须以完整`.m`版本为准。

在向工程师交付板端算法前，应冻结完整AGC代码的版本和校验值，防止再次出现模型代码与独立`.m`文件不一致。

## 论文方面

这组结果已经形成了比"随机丢包可能有影响"更具体的问题：

> 现有AGC在设备响应滞后和高频更新条件下，可能通过多类资源反复、对冲调节实现PCC跟踪，导致不必要的功率动作和资源占用。

这与策略2"AGC目标跟踪"和策略7"联络线功率控制"直接相关。

后续可能形成的研究方向包括：

* 基于设备实际功率的动态裕度计算；
* 命令—实测融合；
* 面向设备响应时间的AGC周期协调；
* 增加命令变化率限制；
* PCC反馈滤波与自适应死区；
* 避免相反资源同时动作的协调分配方法。

现在仍不应立即锁定最终方案，要通过单变量对照试验判断哪一种因素贡献最大。

# 五、SOC显示接近0需要单独检查

你说SOC显示在0上方一点点，这不符合当前模型设定。

SOC初始值应为约：

```
SOC1 = SOC2 = 0.60
```

即使ESS在后半段充电，10 s内SOC也只能略微增加，不可能从0.6变到接近0。SOC代码会从配置的初始值开始积分并限制在上下限内。

因此需要检查：

```text
Mux输入18、19
```

是否确实接到了：

```text
SOC_Calculation输出SOC1、SOC2
```

而不是储能功率、SOC增量或其他同名信号。这个问题不影响本轮PCC跟踪结论，但在后续SOC边界试验和板端40107、40108接入前必须修正。

# 六、本轮应正式记录的结论

> 在补全Simulink AGC模块缺失的负向调节分支后，基础AGC能够在理想通信条件下将PCC由约−60 kW调节至−40 kW目标附近，`dP`和`remain`最终接近0，原始命令与设备最终命令一致，证明完整闭环及内部命令链路有效。但控制过程中两台PV逐步升至接近额定出力，两台EV升至最大充电功率，两台ESS同时进入充电，最终通过多类资源相互对冲获得约20 kW净调节量，表明当前增量式AGC存在命令累积和资源协调效率不足的问题。

下一步应先保存这组完整代码基线结果，并核对SOC观测连接；随后只改变一个因素进行对照，首选比较`Ts_agc=0.1 s`与`1.0 s`，判断命令累积是否主要由控制更新过快造成。
