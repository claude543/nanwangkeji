# 1. 最高原则：项目记录与个人知识严格分离

本项目长期维护两套完全不同的文档体系。

## A. 项目正式记录 / 过程留存

用途：
- 项目交付；
- 负责人检查；
- 第三方复现；
- 测试验收；
- 版本追溯；
- 技术证据。

```text
事实

环境
配置
操作步骤
原始数据
截图
日志
性能数字
测试结果
问题闭环
```

## B. 个人知识复盘 / 能力内化

用途：
- 真正理解自己做过的事情；
- 将项目经验转化为长期技术能力；
- 补齐相关基础知识；
- 建立跨岗位可迁移知识体系；
- 形成以后科研、工程、求职、面试、答辩可直接使用的个人知识资产。

重点记录：
```text
为什么
原理是什么
为什么这样设计
前后因果关系
有哪些替代方案
为什么最终选择当前方案
哪里最容易理解错

如何用自己的话讲清楚
```

两套文档不得混写。

# 2. 个人知识复盘的最终目标

目标不是“项目结束后有很多Markdown文件”，而是：

> 把整个项目中能够学习、迁移、扩展、用于求职和科研的知识尽可能完整地提取出来，经过讲解、重构和自测，最终变成自己能够理解、复述、画图、判断、应用和继续学习的能力。

最终要做到：

```text
看到一个模型
→ 能判断信号和控制链

看到一个算法
→ 能理解输入、状态、输出和作用

看到一段C代码
→ 能理解模块边界、状态和生命周期

看到一个通信点表
→ 能理解数据类型、方向、缩放和协议

看到一个测试
→ 能解释为什么这样设计

看到一个异常
→ 能形成系统化排查路径

看到一个新工程任务
→ 能复用本项目的方法拆解
```

# 5. 每一个个人复盘文档的固定结构

以后任何阶段形成个人学习文档，优先使用以下结构。

## 5.1 这一阶段实际做了什么
只用最短篇幅说明：
```text
做了什么
解决了什么问题
结果是什么
```

## 5.2 宏观上处在整个系统的什么位置
先画：
```text
上游
↓
当前模块 / 当前阶段
↓
下游
```
禁止一开始直接钻函数、参数或代码行。

## 5.3 为什么必须存在
回答：
> 如果没有它，系统会出现什么问题？

## 5.4 输入—状态—处理—输出
所有模型、算法、C模块、控制器都尽量整理成：
```text
Input（输入）
State（内部状态）
Processing（处理逻辑）
Output（输出）
```

有状态模块再说明：
```text
上一周期保存什么
什么时候更新
什么时候保持
什么时候Reset
```

## 5.5 前后信号因果链
讲清：
```text
信号从哪里产生
为什么进入这里
在这里怎样处理
输出送到哪里
最后影响哪个物理对象
```

## 5.6 专业讲解版
要求：
- 英文术语第一次出现立即标中文；
- 参数名保留原名；
- 解释物理意义；
- 不只描述表面功能。

## 5.7 通俗理解版
再用普通语言重新解释一次，保证以后忘记细节后仍能快速恢复逻辑。

## 5.8 为什么采用当前设计
只要存在明显设计选择，都说明：
```text
可选方案
当前方案
为什么选择当前方案
```

## 5.9 测试与验证方法
不能只写“PASS”，必须理解：
```text
为什么这样测试
为什么这个参数能触发
观察什么
预期是什么
什么算真正通过
```

## 5.10 易错点
单独列：
```text
最容易理解错什么
当时哪里曾经理解错
以后如何避免
```

## 5.11 工程排查方法
凡是出现过问题，都提炼：
```text
现象
错误猜测
真实根因
定位路径
最终修复
验证
通用排查方法
```

## 5.12 可迁移能力
说明这项知识以后还能用于：
- 电网；
- 新能源；
- 储能；
- 逆变器；
- PCS；
- EMS；
- BMS；
- 电源；
- 嵌入式；
- 控制器；
- HIL；
- 半导体；
- 软件工程。

## 5.13 职业岗位映射
每个重要主题都判断它与不同岗位的相关性，例如：
```text
电网 / 电力系统
储能 / 新能源
电源 / 电力电子
嵌入式软件
硬件工程
半导体 / TI类
测试 / HIL
控制算法
```

## 5.14 项目未覆盖但未来应补的知识
不能因为项目没做就忽略，例如：
```text
PCB
MOSFET / IGBT / SiC
Gate Driver
ADC采样
MCU / DSP
定点算法
EMC
热设计
磁性元件
LLC
Buck / Boost
双向DC/DC
```
必须明确区分“项目做过”和“未来需要补课”。

## 5.15 自测问题
每个重要文档最后给10～30个问题。
不看文档能回答，才算真正内化。

## 5.16 面试 / 答辩表达
每个重要阶段至少形成：
```text
30秒版本
2分钟版本
一个真实问题案例
```

# 7. 职业价值扫描

每完成一个重要阶段，都主动判断它对以下方向的价值。

## 电网 / 电力系统
重点：微电网、PCC、调度、电压频率、并离网、实时仿真、HIL、电网控制。

## 储能 / 新能源
重点：ESS、PCS、SOC、BMS/EMS/PCS协同、充放电、GFM、黑启动、通信、HIL。

## 华为 / 电源 / 电力电子
重点：DC/DC、逆变器、数字控制、环路、PWM、器件、驱动、实时控制、嵌入式、测试和保护。

## 嵌入式软件 / 控制软件
重点：C、Linux、状态机、API、通信、数据结构、实时调度、测试、配置、日志、生命周期。

## 硬件工程
重点：接口、电源、采样、隔离、PCB、驱动、保护、EMC、器件和测试。

## 半导体 / TI类岗位
重点：功率器件、模拟电路、数字控制、MCU、ADC、Gate Driver、电源管理、嵌入式和应用工程。

当前项目未真正覆盖的内容必须标记为“未来补课”，不得包装成已完成经验。

# 8. 知识来源级别

以后个人复盘的重要结论建议标注：

## 【项目事实】
来自模型、代码、MAT、测试、正式接口或仓库记录。

## 【原理解释】
基于项目事实解释背后的控制、软件、通信或电力电子原理。

## 【通用扩展】
超出当前项目实现，但属于相关通用知识。

## 【未来补课】
项目没有真正做过，但对未来职业有价值，需要后续系统学习。

以后只要用户要求：
- 复盘；
- 学习；
- 内化；
- 总结项目知识；
- 解释模型；
- 解释代码；
- 解释测试；
- 准备求职；
- 准备答辩；

助手必须主动做到：

1. 从项目真实事实出发；
2. 先宏观后微观；
3. 把信号、状态、因果串起来；
4. 英文术语立即标中文；
5. 提供专业版和通俗版；
6. 不遗漏可迁移的工程思想；
7. 主动检查硬件、电力电子、嵌入式、软件、半导体关联；
8. 明确哪些是项目真实做过的；
9. 明确哪些是通用扩展知识；
10. 明确哪些是未来必须补课的；
11. 给出自测问题；
12. 给出职业/面试价值；
13. 必要时单独生成新的个人Kxx Markdown文档；
14. 不把个人学习复盘内容混入正式项目验收/交付报告。

# 17. 一句话长期规则

> 以后每推进一步项目，都要同时问：这一步除了把项目做完，还能让我学会什么、形成什么可迁移能力、暴露什么知识缺口、未来在哪些岗位会用到；凡是有价值的内容都要单独整理成个人知识复盘文档，并通过专业解释、通俗解释、因果链、案例、自测和职业映射真正内化。
