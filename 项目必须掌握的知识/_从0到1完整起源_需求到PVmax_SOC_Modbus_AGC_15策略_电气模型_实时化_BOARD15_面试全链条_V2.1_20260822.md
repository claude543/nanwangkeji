# 1. 项目从0开始到底在解决什么问题？

项目对象是一个光储充微电网：

```text
PV：分布式新能源
ESS：双向储能
EV：可控充电负荷
普通负荷
上级配电网
```

这些对象的物理属性不同：

## PV

```text
优点：清洁、边际燃料成本低
限制：受光照约束，不能想发多少就发多少
```

## ESS

```text
优点：充放电双向、响应快、可缓冲波动
限制：既有功率上限，又有能量/SOC限制
```

## EV

当前基线主要把EV作为柔性充电负荷：

```text
增加充电 → 多吸收电
减少充电 → 释放负荷
```

## 上级Grid

```text
提供并网电压/频率基准
向微网供电
接受或限制微网外送
接收调度/联络线目标
```

因此项目真正研究的是：

> **怎样让一个包含随机新能源、可充放储能、柔性负荷和上级电网接口的系统，在正常、经济、故障、并离网等多场景下仍然可测、可控、可协调、可安全运行。**

# 4. 为什么从需求会自然推导出 Grid + PCC + PV + ESS + EV + Load + Breaker？

这一节是“原有微电网电气仿真基础到底怎么从0搭”的起点。

---

## 4.1 为什么先有上级Grid？

项目要求：

```text
主配微协同
联络线控制
防逆流
并网/离网
需量
```

这些概念都需要一个“外部大电网”。

没有Grid：

```text
不存在购电/外送
不存在联络线
不存在并网
不存在防逆流
```

所以首先建立一个10 kV三相上级电网模型。

早期模型使用 `Three-Phase Programmable Voltage Source` 模拟强电网。

---

## 4.2 为什么要10 kV？

项目面对配电侧微网，10 kV是典型中压配电电压等级之一。

这让后续：

```text
低压逆变器
→ 升压变压器
→ 10 kV母线
```

成为合理工程结构。

注意：10 kV是当前模型场景选择，不是所有微网都必须10 kV。

---

## 4.3 为什么一定要PCC？

PCC = Point of Common Coupling（公共连接点）。

它把系统分成：

```text
微网内部
↕ PCC
上级电网
```

项目很多功能都直接问：

```text
微网整体现在进口多少？
外送多少？
是否超过反送边界？
是否跟上调度计划？
```

这些都必须在一个统一边界测量。

所以PCC不是“为了有个测量点”，而是系统级协调的核心观测点。

当前内部功率符号：

```text
Ppcc > 0：微网向上级电网外送
Ppcc < 0：微网从上级电网进口
```

---

## 4.4 为什么必须有PV？

因为项目是“光储充”，且要求：

```text
新能源消纳
平滑出力
防逆流
多目标优化
```

没有PV，上述新能源问题根本无法验证。

---

## 4.5 为什么必须有ESS？

很多功能都需要一个快速双向资源：

```text
平滑PV
防逆流
削峰填谷
AGC
联络线控制
黑启动
孤岛构网
动态扩容
```

ESS同时具备：

```text
充电吸收
放电支撑
快速响应
储存能量
```

因此它天然是微网最重要的调节资源之一。

---

## 4.6 为什么必须有EV/充电负荷？

项目不仅有源和储，还要体现“荷侧柔性”。

EV在当前基线主要作为可控负荷：

```text
功率过剩 → 增加充电
功率不足 → 减少充电
```

所以它能参与：

```text
PCC调节
新能源内部消纳
低压低频减载
```

---

## 4.7 为什么还有普通Load？

真实园区不只有充电桩。

还有：

```text
不可控/固定负荷
```

所以需要固定Load构造基础用电背景。

但要特别记住：后续用实际 `shiyansan` 核实后，当前冻结PCC测量边界为：

```text
六设备网络
→ PCC V-I Measurement
→ Load1 / Load2 + PCC Breaker + Grid
```

因此当前基线PCC量主要用于六设备对外交换口径，不能简单套用早期概念图理解。

---

## 4.8 为什么需要PCC Breaker？

项目要求：

```text
并网
↔
孤岛
```

必须存在一个实际可以断开/重合的电气执行器。

所以PCC三相断路器是：

```text
模式逻辑
→ 真实物理解列/重合
```

之间的桥梁。

# 7. 为什么最底层一定要先有直流侧？

功率电子变流器不能凭空产生能量。

## PV

真实系统：

```text
太阳能
→ PV组件
→ DC
→ 逆变器
→ AC
```

## ESS

```text
电池
→ DC
↔ 双向变流器
↔ AC
```

## EV

当前项目在交流微网侧主要把它表示为可控充电功率接口，但真实充电过程本质仍包含：

```text
AC
→ 变换
→ DC电池
```

因此模型可以用简化DC源/直流侧等效来保留功率交换接口，而不必把PV组件、电池电化学、车载BMS全部详细建模。

**为什么可以简化？**

因为项目当前研究重点是：

```text
微网协调控制
+
并网功率电子接口
+
实时HIL
```

而不是PV组件或BMS本身。

# 8. 为什么需要 Two-Level Converter（两电平变流器）？

## 8.1 两电平是什么？

三相两电平桥典型有：

```text
3个桥臂
× 每个桥臂上下2个功率开关
= 6个主要开关器件
```

每个桥臂中点在直流母线正/负侧之间高速切换，因此称Two-Level（两电平）。

---

## 8.2 为什么不能直接用“受控功率源”？

如果只研究小时级能量优化，受控功率源更轻量。

但本项目后续要验证：

```text
PWM
本地电流控制
P/Q功率环
GFL/GFM
并离网
RT-LAB实时动态
```

所以开关级变流器能保留：

- 控制器动态；
- PWM开关效应；
- 电流内环；
- 变压器/滤波器动态；
- 模式切换。

代价就是计算量变大，这也直接导致后续100 μs实时化问题。

---

## 8.3 变流器的“输入”到底有哪些？

### 电气输入

```text
DC侧电压/能量
```

### 控制输入

```text
6路PWM门极脉冲
```

它**不直接读取**：

```text
SOC
PVmax
PCC目标
防逆流阈值
```

这些属于更上层的决策。

变流器只负责：

> 按门极脉冲让功率器件导通/关断，形成实际交流端电压和电流。

---

# 9. 为什么变流器后面一定有滤波器？

PWM输出含大量开关频率高频分量。

若直接接入电网：

- 电流谐波大；
- 电压纹波大；
- 电能质量差；
- 控制测量被高频噪声污染。

所以需要L/C等滤波元件。

## 9.1 为什么电感能抑制快速电流变化？


电感关系：

\[
v_L=L\frac{di}{dt}
\]

高频意味着较大的 \(di/dt\)，电感会对快速电流变化表现出更强阻碍。

## 9.2 为什么电容可以旁路高频？

电容阻抗：

\[
X_C=\frac{1}{2\pi f C}
\]

频率越高，电容阻抗越小，高频分量更容易被旁路。

所以L+C组合能够让最终送入电网的主要成分接近50 Hz基波。

---

# 10. 为什么需要升压变压器？

逆变器低压侧通常是几百伏等级，而项目公共母线是10 kV。

因此需要：

```text
低压逆变器
↓
变压器
↓
10 kV接入网络
```

变压器还同时带来：

- 电气隔离；
- 电压等级转换；
- 接线组别；
- 漏阻抗；
- 相位关系。

后续实时分核之所以能使用Transformer Stubline，一个关键就是：

> 变压器本来就有漏R/L，可以把这部分物理阻抗迁入Stubline作为数值解耦位置，而不是凭空加入一段完全新的线路。

# 11. 为什么每台设备都需要自己的 `prim_*` 测量？

例如：

```text
prim_PV1
prim_PV2
prim_ESS1
prim_ESS2
prim_EV1
prim_EV2
```

它们位于每台设备自己的高压接入侧。

最先得到：

```text
Vabc
Iabc
```

然后本地Control System继续从这些量计算：

```text
PLL相角/频率
Pmeas
Qmeas
dq电压电流
```

---

## 11.1 为什么不能所有设备都只用PCC的V/I？

因为设备与PCC之间存在：

```text
变压器
馈线R/L
不同节点
```

所以：

```text
V_device_local
不一定等于
V_PCC
```

本地控制器要稳定控制自己的电流和功率，就必须看自己的实际端口状态，而不是只看一个远端PCC总状态。

---

## 11.2 `prim` 和 PCC 测量分别回答什么？

```text
prim：
“这一台设备自己的接入点现在发生了什么？”

PCC：
“整个微电网加起来对上级电网表现成什么？”
```

这就是为什么两者并不重复。

# 12. 最终实际旧模型的馈线结构为什么不是对称的？

真实冻结拓扑：

```text
公共母线
│
├─ PV1：直接接入
├─ PV2line  → PV2
├─ ESS2line → ESS2
├─ EV2line  → EV2
└─ ESS1line → 中间节点
               ├─ ESS1
               └─ EV1line → EV1
```

## 12.1 这客观上产生什么作用？

### PV1条件相对简单
靠近公共母线，独立馈线阻抗忽略。

### PV2/ESS2/EV2
各有一段独立馈线，因此本地端电压受自身线路压降影响。

### ESS1/EV1
共享上游 `ESS1line`，EV1还更远。

这会形成节点耦合：

```text
EV1充电变化
↓
EV1line电流变化
↓
ESS1line上游电流也变化
↓
中间节点电压变化
↓
ESS1本地prim也可能感受到变化
```

这不是控制器互发消息，而是通过共同电气网络发生物理影响。

---

## 12.2 为什么不能编造“老师就是为了某个具体实验才这么接”？

现有模型能证明：

> 拓扑确实如此，并构造了不同电气距离。

但现有资料不能严格证明原作者当时唯一主观意图。

面试更稳的说法：

> **这种结构让模型比六台理想同母线资源更接近小型径向配电网络，并让本地控制面对不同电气环境。**

# 13. 为什么必须有本地 Control System，而不是AGC直接给PWM？

因为两者处在完全不同时间尺度和抽象层次。

AGC处理：

```text
PCC目标
kW级功率任务
约1 s更新
```

PWM处理：

```text
功率开关门极
μs级
```

中间必须有设备本地闭环：

```text
Pref/Qref
↓
功率外环
↓
Id*/Iq*
↓
电流内环
↓
Vd*/Vq*
↓
调制波
↓
PWM
↓
Converter
```

---

# 14. 为什么功率外环输出的是“电流参考”？

在PLL同步的dq坐标系中，如果d轴与电网电压矢量对齐，可直观理解：

\[
P\propto V_d I_d
\]

\[
Q\propto -V_d I_q
\]

因此：

```text
要改变P
→ 调Id

要改变Q
→ 调Iq
```

所以：

```text
Pref - Pmeas
↓ PI
Id_ref

Qref - Qmeas
↓ PI
Iq_ref
```

这就是“功率外环产生电流参考”。

---

# 15. 为什么电流内环输出的是“电压指令”？

对滤波电感，简化电压方程：

\[
L\frac{di}{dt}=v_{conv}-v_{grid}-Ri
\]

如果想让电流按照 \(I^*\) 变化，本质上必须控制：

```text
变流器端电压 v_conv
```

所以：

```text
Id_ref - Id_meas
Iq_ref - Iq_meas
↓
PI + dq交叉耦合补偿 + 电网电压前馈
↓
Vd_cmd / Vq_cmd
```

然后再变成三相调制电压。

这就是：

> **外环告诉内环“我要多少电流”，内环告诉PWM“我要产生什么电压”。**

---

# 16. 为什么电流内环必须比功率外环快？

如果功率外环已经快速改变Id_ref，但电流实际还迟迟跟不上：

```text
外层继续认为误差存在
→ 再加命令
→ 容易过调/振荡
```

所以控制系统遵循带宽分层：

```text
电流内环最快
功率/电压环次之
AGC更慢
经济优化更慢
```

这是多时间尺度控制的基本原则。

---

# 17. 为什么需要PLL？

GFL（Grid-Following，跟网型）逆变器必须知道：

```text
电网当前相角θ
电网当前频率f
```

PLL从三相电压中估计这些量。

有了θ，才能把三相abc量转成同步旋转dq量，使原本交流的正弦量在稳态下变成近似直流量，从而方便PI控制。

没有PLL，跟网型控制器就没有可靠同步参考。

---

# 18. 为什么还需要GFM和Droop？

并网时：

```text
上级电网已经建立V/f
GFL只需跟随
```

孤岛以后：

```text
PCC breaker断开
```

如果所有设备都只会“跟别人”，系统就没人建立电压频率。

所以至少一个资源必须GFM（Grid-Forming，构网型）。

当前通常选ESS，因为ESS：

- 双向功率；
- 响应快；
- 能量可控；
- 不受瞬时日照直接限制。

典型Droop：

\[
f=f_{ref}-K_fP
\]

\[
V=V_{ref}-K_vQ
\]

用于多电源在无强电网时形成类似同步机的频率/电压外特性。

---

# 19. 为什么 `Droop_On=1` 不等于设备已经切到GFM？

项目中必须区分：

```text
Droop_On
```

和：

```text
GridOn / ConnectMode
```

### Droop_On
允许/启动Droop分支计算。

### GridOn / ConnectMode
决定最终到底选择GFL还是GFM控制路径进入后续电流环/PWM。

所以可能：

```text
Droop已经在后台计算
但GridOn=1
→ 最终仍是GFL实际控制
```

不能说“3 s打开Droop以后设备就自动构网”。

# 20. 为什么还要 Microgrid Supervisory Control？

设备本地快速环负责：

```text
让本机跟踪P/Q或V/f
```

但微网系统还需要统一：

```text
Fref
Vref
系统模式
```

尤其在：

- 孤岛；
- 构网；
- 频率/电压恢复；
- 多设备协同。

Supervisor就是设备层和系统协调层之间的一个全局参考管理层。

# 21. 到这里为什么还不能马上写AGC和15策略？

因为第一步必须先证明：

```text
Plant本身可信
+
每台设备本地控制闭环可信
+
```

如果连：

# 22. PVmax为什么会从项目要求中“必然长出来”？——从第一性问题开始推导

PVmax不是为了让模型多一个变量。

它解决的是一个非常具体的问题：

> **控制器必须知道PV“当前最多还能发多少”，否则无法判断调节能力。**

下面逐层推。

---

# 23. 为什么知道PV额定功率还不够？

假设逆变器铭牌：

```text
P_rated = 100 kW
```

这个值只回答：

> 硬件额定能力大致是多少。

它不回答：

> 当前太阳条件下真的有多少能量可用。

同一台100 kW光伏：

```text
夜间：≈0 kW
阴天：可能20～50 kW
晴天中午：可能接近100 kW
```

所以：

```text
P_rated
≠
P_available(t)
```

项目为了做：

```text
AGC
平滑
新能源消纳
```

必须知道第二个量。

于是定义：

```text
PVmax(t)
= 当前时刻最大可用有功功率
```

---

# 24. 为什么不能直接把 `Pmeas` 当PVmax？

这是面试最容易追问的地方。

## `Pmeas`
回答：

> 现在实际发了多少。

## `PVmax`
回答：

> 当前条件下最多能发多少。

例：

```text
PVmax = 80 kW
Pref  = 40 kW
Pmeas ≈ 40 kW
```

如果把Pmeas当PVmax：

```text
控制器会以为这台PV只能发40
```

但真实还有：

```text
80-40=40 kW
```

向上调节裕度。

因此：

```text
Pmeas = 当前执行状态
PVmax = 当前能力边界
```

这两个概念绝不能混。

---

# 25. `P_rated / PVmax / Pref / Pmeas` 四个量怎么区分？

| 量 | 核心问题 | 典型来源 |
|---|---|---|
| `P_rated` | 这台设备名义上多大？ | 铭牌/配置 |
| `PVmax` | 当前太阳条件下最多能发多少？ | available power/辐照度/预测/profile |
| `Pref` | 控制器希望它现在发多少？ | AGC/调度 |
| `Pmeas` | 它实际发了多少？ | 本地V/I测量计算 |

正常条件下大致要求：

```text
0 ≤ Pref ≤ PVmax ≤ P_rated
```

但：

```text
Pmeas ≈ Pref
```

只在设备正常、未限幅、动态基本完成时成立。

---

# 26. 为什么PVmax直接对应项目的三个重要功能？

## 26.1 AGC

AGC需要知道：

```text
PV还能增加多少？
```

最基本向上裕度：

\[
R_{PV,up}=\max(P_{PV,max}-P_{PV,current},0)
\]

没有PVmax，AGC就不知道“这台PV还能不能继续加”。

---

## 26.2 S6平滑出力

平滑关注的是：

```text
新能源资源可用出力本身是否快速变化
```

例如云层变化导致：

```text
PVmax: 65 → 95 → 55 → 65 kW
```

这比单纯改PCC目标更直接代表PV资源波动。

后续LOCAL15真实测试中，最开始改tie-line target时S6不动作，最终沿真实信号追踪确认S6读的是 `Ppv_max1/2`，改 `PV_profile_pu` 后才正确触发ESS平滑补偿。

这就是非常典型的面试问题：

> “为什么你测试S6不能随便改PCC目标？”

回答：

> 因为S6监测的是PV资源变化，测试必须作用在它真正读取的PVmax输入上。

---

## 26.3 S12新能源最大化消纳

要判断弃光，必须知道：

```text
本来可以发多少
-
实际利用多少
```

只有Pmeas：

```text
只能知道实际发了多少
```

无法知道有没有“未利用的可发能力”。

所以新能源消纳率、弃光估计都天然需要available power/PVmax概念。

---

# 27. 真实工程里的PVmax应该从哪里来？

真实产品可以有多种来源：

```text
1. PV逆变器直接上送 Available Power / Pmax
2. MPPT状态或直流侧功率估计
3. 辐照度 + 温度 + PV模型估算
4. 短期光伏预测
5. 站级EMS给出的可用出力
```

当前项目为什么没有把这些全部建进去？

因为研究重点是：

```text
微网协调控制与HIL
```

而不是：

```text
光伏组件I-V曲线/MPPT算法
```

所以前期仿真把复杂太阳资源压缩成一个最小必要状态：

> **当前最大可用有功。**

---

# 28. 为什么仿真要用归一化 `PV_profile_pu`？

定义：

\[
g_{PV}(t)\in[0,1]
\]

表示：

```text
当前资源条件
=
额定能力的多少比例
```

比如：

```text
0.65 = 当前最多能达到65%额定功率
```

如果：

```text
P_unit=100 kW
```

则：

```text
PVmax=65 kW
```

## 为什么不用直接存kW曲线？

因为pu有三个优点：

1. 与额定容量解耦；
2. 换100 kW/500 kW设备时曲线可以复用；
3. 便于不同设备归一化比较。

---

# 29. 为什么还要 `PV_time_s`？

只给：

```text
PV_profile_pu=[0.2,0.5,0.8,0.4]
```

系统不知道这些值发生在什么时候。

所以还要：

```text
PV_time_s=[0,10,20,30]
```

形成完整的时间—能力曲线：

```text
0s  →0.2
10s →0.5
20s →0.8
30s →0.4
```

---

# 30. 为什么必须插值？

仿真时间连续推进。

假设当前：

```text
t=15s
```

但曲线只有：

```text
10s →0.5
20s →0.8
```

不能等到20s才突然跳。

当前代码采用最简单确定的线性插值。

设：

\[
a=\frac{t-x_k}{x_{k+1}-x_k}
\]

\[
g(t)=g_k+a(g_{k+1}-g_k)
\]

代入：

\[
a=\frac{15-10}{20-10}=0.5
\]

\[
g(15)=0.5+0.5(0.8-0.5)=0.65
\]

若 `P_unit=100 kW`：

```text
PVmax=65 kW
```

---

# 31. 为什么线性插值适合当前项目？

它不是最精细的太阳物理模型，但有：

```text
简单
确定
无随机隐藏状态
容易转C
容易复现
容易控制测试
```

对“协调控制功能验证”很合适。

如果以后研究：

```text
秒级云影预测
PV组件动态
MPPT
```

才有必要换成更复杂模型。

# 32. 实际 `PVcurve.m` 每一行为什么这么写？

真实核心：

```matlab
pu = interp_profile(time_s, PV_time_s, PV_profile_pu);
pmax = max(P_unit_kW, 0.0) * max(pu, 0.0);
Ppv_max1_kW = pmax;
Ppv_max2_kW = pmax;
```

## `interp_profile(...)`

从时间曲线中求当前可用比例。

## `max(P_unit_kW,0.0)`

防御异常配置：额定功率不允许因为参数错误变成负数。

## `max(pu,0.0)`

即使profile误填负值，也不让“最大可用光伏功率”变负。

## 两路都等于 `pmax`

当前Baseline假设：

```text
PV1、PV2
容量相同
天气profile相同
```

这只是模型简化，不是物理定律。

# 33. 为什么接口仍然保留 `Ppv_max1` 和 `Ppv_max2` 两个独立输出？

因为未来完全可能：

```text
PV1遮挡
PV2无遮挡
```

或：

```text
容量不同
朝向不同
组件故障不同
```

所以AGC接口从一开始保留两路独立能力变量是合理的。

面试可以说：

> 当前基线用同一profile是为了简化测试，但数据接口不把两台PV绑定死。

# 34. 为什么PVmax不是控制命令？

PVmax描述：

```text
环境 + 设备当前能力
```

Pref描述：

```text
控制器的意图
```

AGC能做的是：

```text
在[0,PVmax]内选择Pref
```

不能因为“想多发”就直接把PVmax命令成100 kW。

因此：

> **PVmax属于capability state（能力状态），Pref属于control action（控制动作）。**

---

# 35. 如果PVmax突然从80 kW掉到40 kW，而Pref原来70 kW，会怎样？

物理上70 kW命令已经不可实现。

合理流程应该：

```text
PV能力下降
↓
PVmax=40
↓
AGC/执行映射把PV Pref限制≤40
↓
剩余PCC调节任务
转给ESS/EV等其他资源
```

这也是为什么上层协调器必须持续更新资源能力，不能只记住历史命令。

# 36. PVmax相关“为什么库”——必须脱口而出

1. 为什么额定功率不能替代PVmax？——额定容量不反映瞬时光照。
2. 为什么Pmeas不能替代PVmax？——实际输出不包含未使用余量。
3. 为什么PVmax不是Pref？——能力边界不是控制意图。
4. 为什么用pu曲线？——容量解耦、复用、归一化。
5. 为什么需要time数组？——给profile定义时间轴。
6. 为什么要插值？——仿真时间落在离散节点之间。
7. 为什么线性插值？——简单、可复现、足够支撑协调控制验证。
8. 为什么两台PV当前PVmax相同？——Baseline简化，不是接口限制。
9. 为什么AGC需要PVmax？——计算向上headroom。
10. 为什么S6需要PVmax？——它关心PV资源波动而非PCC目标变化。
11. 为什么S12需要PVmax？——要区分“本来能发”和“实际利用”。
12. 真实产品PVmax从哪来？——逆变器available power、辐照度模型、预测等。
13. 为什么不建完整PV组件？——研究目标是微网协调控制，不是PV组件物理。
14. PVmax突然掉了怎么办？——限制PV指令并重分配其他资源。

# 37. SOC为什么会从项目要求中“必然长出来”？

SOC不是为了显示一个百分数。

它解决的是：

> **ESS除了“瞬时能输出多大功率”，还必须知道“还剩多少能量”。**

---

# 38. 为什么只知道ESS额定100 kW不够？

100 kW是Power（功率）能力：

> 每个瞬间能以多快速度充/放。

但如果电池只剩很少能量：

```text
仍不能长期100 kW放电
```

所以储能必须同时有：

```text
Power limit：功率上限 kW
Energy state：能量状态 kWh / SOC
```

这就是PV和ESS能力建模最大的区别之一。

---

# 39. SOC的最基本物理定义是什么？

\[
SOC=\frac{E_{stored}}{E_{nominal}}
\]

例：

```text
额定容量 E_nom=200 kWh
当前储能 E=120 kWh
```

则：

\[
SOC=120/200=0.60
\]

即60%。

---

# 40. 为什么项目那么多功能都必须用SOC？

## AGC

```text
SOC过低
→ 不允许继续增加放电

SOC过高
→ 不允许继续增加充电
```

## S9削峰填谷

```text
峰时想放电
但必须先确认有能量
```

## S12新能源消纳

```text
想用ESS吸收PV
但SOC接近上限就没有足够空间
```

## S14黑启动

```text
如果ESS能量不足
不能假装它能长期构网并恢复负荷
```

## 日前优化

储能计划必须满足：

\[
SOC_{min}\le SOC(t)\le SOC_{max}
\]

所以SOC是：

> **跨时间的能量可行性约束。**

---

# 41. 为什么SOC必须由功率积分得到？

功率定义：

\[
P=\frac{dE}{dt}
\]

于是：

\[
dE=Pdt
\]

离散化：

\[
\Delta E=P\Delta t
\]

SOC是能量除以额定容量：

\[
\Delta SOC=\frac{\Delta E}{E_{nom}}
\]

所以：

\[
\Delta SOC=\frac{P\Delta t}{E_{nom}}
\]

这不是拍脑袋公式，而是直接来自功率和能量的定义。

---

# 42. 为什么实际代码分母要乘3600？

当前单位：

```text
P：kW
E：kWh
time：s
```

而：

```text
1 h = 3600 s
```

因此：

```text
kW × s / 3600
= kWh
```

所以代码：

\[
\Delta SOC
=
\frac{P_{kW}\Delta t_s}
{E_{kWh}\times3600}
\]

如果忘了3600，SOC变化会快3600倍，是严重单位错误。

---

# 43. 为什么当前公式前面是负号？

当前项目ESS功率方向：

```text
Pess > 0：放电，能量减少
Pess < 0：充电，能量增加
```

所以：

\[
SOC_{k+1}
=
SOC_k
-
\frac{P_{ess}\Delta t}
{E_{nom}\times3600}
\]

### 放电

```text
Pess>0
→ 减去正数
→ SOC下降
```

### 充电

```text
Pess<0
→ 减去负数
→ SOC上升
```

一个负号同时统一了两个方向。

---

# 44. 为什么输入是 `Pess_pu × P_unit_kW`？

本地设备命令经常用pu标幺值。

假设：

```text
Pess_pu=0.5
P_unit=100 kW
```

则真实功率：

\[
P=0.5\times100=50kW
\]

SOC容量使用kWh，所以必须先把pu恢复成kW。

这也是为什么“标幺值”和“工程单位”一定要清楚区分。

---

# 45. 实际 `SOC_Calculation.m` 每个核心变量为什么存在？

真实函数保存：

```text
persistent soc1 soc2 last_t
```

## `soc1/soc2`

因为SOC是状态，取决于过去所有充放电历史。

当前50 kW不能单独决定当前SOC。

## `last_t`

需要计算真实：

```text
dt = time_s - last_t
```

而不是假设每次调用间隔永远固定。

---

# 46. 为什么第一次调用和时间回退时要Reset？

正常仿真时间应单调增加。

如果：

```text
time_s < last_t
```

通常意味着：

```text
Reset / 仿真重新开始
```

如果继续沿用上一轮的persistent SOC：

```text
新实验会继承旧实验电量
```

完全错误。

所以重新用：

```text
SOC0_ess1
SOC0_ess2
```

初始化。

# 47. 为什么要 `lo=min(SOC_min,SOC_max)` 和 `hi=max(...)`？

这是防御式编程。

即使配置误写：

```text
SOC_min=0.9
SOC_max=0.2
```

内部仍先整理成：

```text
lo=0.2
hi=0.9
```

避免clamp上下限彻底反掉。

---

# 48. 为什么要clamp到 `[SOC_min,SOC_max]`？

有两层原因。

## 数值层

避免积分产生：

```text
SOC<0
SOC>1
```

## 控制层

当前工程不是用0/1极限，而是留安全窗口，例如：

```text
SOC_min=0.20
SOC_max=0.90
```

原因：

- 避免过放；
- 避免过充；
- 保留安全裕量；
- 给AGC清晰资格边界。

# 49. 一个完整SOC放电例子

设：

```text
SOC0=0.60
E=200 kWh
P_unit=100 kW
Pess=+1 pu
```

即100 kW放电。

持续1 h：

\[
\Delta SOC=-\frac{100}{200}=-0.5
\]

理论：

```text
0.60→0.10
```

若：

```text
SOC_min=0.20
```

代码最终clamp到：

```text
0.20
```

# 50. 一个完整SOC充电例子

设：

```text
SOC=0.60
Pess=-0.5 pu
P_unit=100 kW
E=200 kWh
```

即50 kW充电。

持续1 h：

\[
\Delta SOC
=-\frac{-50}{200}
=+0.25
\]

所以：

```text
SOC: 0.60→0.85
```

这能直接检查功率符号是否理解正确。

# 51. 为什么6月29日说明文档写了效率η，但实际代码没有？

说明文档给过更一般形式：

\[
SOC_{k+1}=SOC_k+
\frac{\eta_{ch}P_{ch}-P_{dis}/\eta_{dis}}
{E_{nom}}\Delta t
\]

它表达了：

```text
真实充电有损耗
真实放电也有损耗
```

但当前实际 `SOC_Calculation.m` 使用的是简化理想效率积分，没有显式η。

因此面试必须说准确：

> **说明文档保留了可扩展的通用公式，当前实际控制验证代码采用简化能量积分，未显式加入充放电效率。**

不能说“代码已经完整考虑效率”。

# 52. 为什么前期SOC可以用ESS命令积分？

早期想先建立：

```text
AGC命令
→ ESS
→ SOC约束
```

命令积分有优点：

- 实现简单；
- 没有Pmeas高频纹波；
- 容易测试；
- 能快速给AGC提供SOC边界。

但隐含假设：

```text
命令 ≈ 实际执行
```

在正常离线基线中可以接受。

# 53. 为什么后来LOCAL15必须让SOC跟 `FINAL_APPLIED_ESS`？

随着项目引入：

```text
Source Router
Execution Fault Injector
Safety Gate
```

开始出现：

```text
上游命令
≠
最终真正进入Plant的命令
```

例如：

```text
候选ESS=+0.8 pu
执行故障后真正Plant=+0.3 pu
```

如果SOC仍按0.8积分：

```text
SOC下降过快
```

内部能量状态会和真实Plant脱离。

所以后来把SOC源对齐到：

```text
FINAL_APPLIED_ESS
```

核心原则：

> **物理状态应该跟真正执行的量走，而不是跟控制器上游“想执行”的量走。**

这也是后续论文“controller state vs physical state”思维的工程先例。

# 54. 为什么不直接做高精度BMS SOC算法？

真实BMS可以有：

```text
库仑计量
OCV校正
等效电路
EKF/UKF
温度补偿
老化SOH修正
```

但当前项目研究的是：

```text
微网协调控制器
```

不是BMS算法。

所以简化SOC模型只需要保证：

```text
能量随充放电正确变化
+
有安全上下限
+
上层控制可使用
```

即可。

这体现模型设计原则：

> **复杂度必须服务于研究目标。**

# 55. SOC相关“为什么库”——必须脱口而出

1. 为什么SOC不是功率？——SOC是能量比例，功率是能量变化速率。
2. 为什么需要kWh容量？——只有功率上限不知道能持续多久。
3. 为什么用积分？——来自 \(P=dE/dt\)。
4. 为什么有3600？——秒和小时换算。
5. 为什么正Pess让SOC下降？——项目定义正ESS功率为放电。
6. 为什么负Pess让SOC上升？——减去负数等于增加SOC。
7. 为什么用pu×Punit？——把标幺恢复为kW。
8. 为什么要persistent？——SOC依赖历史。
9. 为什么要last_t？——计算真实积分时间间隔。
10. 为什么时间回退要Reset？——避免新实验继承旧能量状态。
11. 为什么要clamp？——保证数值和安全边界。
12. 为什么上下限不直接0/1？——留运行保护裕量。
13. 为什么两台ESS要两个SOC？——两台设备历史可不同。
14. 为什么早期用命令积分？——快速、平滑、适合初始控制验证。
15. 为什么后来改FINAL_APPLIED？——让能量状态与真实执行一致。
16. 实际代码有没有η？——没有显式加入。
17. 为什么不做BMS精细模型？——研究目标是微网协调，不是电池SOC估计。

# 56. PVmax和SOC为什么正好代表两种完全不同的资源约束？

## PVmax

描述：

```text
瞬时可发能力
```

它回答：

> 现在还能向上加多少PV？

## SOC

描述：

```text
跨时间能量状态
```

它回答：

> ESS现在是否还有资格继续充/放？

所以AGC同时使用二者，本质上是在结合：

```text
新能源瞬时能力约束
+
储能能量约束
```

这就是为什么这两个看似独立的小模块实际上是基础协调算法的关键输入。

---

# 57. 基础AGC为什么会从项目要求中自然产生？

项目要求：

> 联络线功率按目标计划运行，让整个微网对上级电网表现成一个可调度电源或负荷。

这句话数学化以后，第一件事就是定义：

```text
目标PCC功率 Ptarget
实际PCC功率 Ppcc
```

于是总有功调节需求：

\[
dP=P_{target}-P_{pcc}
\]

这个式子只回答：

> **整个微网净功率还需要往哪个方向、调多少。**

它还不是六台设备命令。

---

# 58. 为什么 `dP=Ptarget-Ppcc` 的符号很重要？

当前内部符号：

```text
Ppcc > 0：向上级电网外送
Ppcc < 0：从上级电网进口
```

例：

```text
Ptarget=-100 kW
Ppcc=-120 kW
```

则：

```text
dP=+20 kW
```

含义：

```text
当前进口120
目标只进口100
↓
微网净出力需要增加20
```

实现方式可以：

```text
多发电
或
少用电
```

所以正dP对应：

```text
PV↑ / ESS放电↑ / EV充电↓
```

---

# 59. 为什么需要 `P_dead` 死区？

真实PCC会有：

- 测量噪声；
- 功率纹波；
- 设备正常动态；
- 小范围随机波动。

如果0.1 kW误差也调：

```text
AGC可能来回抖动
资源频繁微调
```

所以：

```text
|dP| ≤ P_dead
→ 不做新的资源分配
```

死区不是“控制不精确”，而是：

> **用少量稳态容差换取更稳定、更少动作的控制。**

---

# 60. 为什么dP>0时优先PV→ESS→EV？

实际基础AGC采用：

```text
PV增加
↓
ESS放电
↓
EV减少充电
```

## 60.1 PV为什么先？

- 清洁能源优先利用；
- 不消耗储能SOC；
- 只要PVmax还有余量就可以增加；
- 少弃光符合项目新能源消纳目标。

## 60.2 ESS为什么第二？

- 快速双向调节；
- 可以补功率缺口；
- 但会消耗电池能量；
- 受SOC下限约束。

## 60.3 EV为什么最后减充？

- 它是用户侧负荷；
- 减少充电相当于牺牲充电服务；
- 所以基础规则把它放在后级。

这是一套**工程Baseline优先级**，不是项目书规定的唯一全局最优解。

---

# 61. 为什么dP<0时优先EV加充→ESS充电→PV降出力？

当微网净出力过剩时，希望：

```text
多用电
或
少发电
```

## 61.1 EV先增加充电

多余电能优先在内部被柔性负荷消纳。

## 61.2 ESS再充电

把多余能量存起来。

## 61.3 PV最后降出力

弃光是最后手段。

所以：

```text
EV charging↑
→ ESS charge↑
→ PV curtailment
```

体现：

> **优先内部消纳和储能，再减少新能源利用。**

---

# 62. 为什么同类两台设备不是“平均分”？

实际代码使用 `alloc_up/alloc_down` 按剩余余量比例分配。

假设：

```text
PV1当前20，PVmax1=80 → 余量60
PV2当前50，PVmax2=70 → 余量20
```

总余量：

```text
80
```

如果需要增加40 kW：

```text
PV1分30
PV2分10
```

即按：

\[
\Delta P_i=\frac{R_i}{\sum R_j}\Delta P_{req}
\]

为什么比平均分合理？

因为平均分20/20会让PV2直接从50→70到顶，而PV1仍有40 kW剩余能力；余量比例可以更平衡地使用当前可调能力。

**面试禁区：** 不能说“原算法是平均分，后来我改成余量分配”。原基础AGC已经是余量比例分配。

# 63. 为什么AGC还需要SOC硬约束？

正向增加净出力时，ESS要放电。

如果：

```text
SOC1≤SOC_min
```

则代码把ESS1向上放电上限改为0，不允许继续增加放电。

负向时，ESS要充电。

如果：

```text
SOC1≥SOC_max
```

则不允许继续增加充电。

所以SOC在基础AGC里主要是：

```text
Hard Constraint（硬边界）
```

不是复杂的连续SOC优化权重。

# 64. 为什么AGC要保存 `Ppv/Pess/Pev` persistent状态？

当前AGC不是每1 s都完全从零解一个优化问题。

它会在上一轮内部资源命令基础上继续调整。

因此保存：

```text
Ppv[2]
Pess[2]
Pev[2]
```

它们表达：

> **控制器认为当前六资源调度状态是什么。**

这后来会成为论文的重要问题：

```text
Controller internal allocation state
不一定等于
Physical executed state
```

# 65. 为什么EV内部 `Pev` 是正充电幅值，而输出是负pu？

内部为了方便：

```text
Pev=60 kW
```

表示“充电60 kW”。

但微网功率方向定义：

```text
负功率=负荷吸收
```

所以输出：

\[
P_{EV,pu}=-P_{ev}/P_{unit}
\]

例：

```text
Pev=60
Punit=100
→ 输出=-0.6 pu
```

因此面试看到EV“增加充电”时，模型命令数值反而会变得**更负**。

# 66. 为什么AGC是1 s，而Plant是100 μs？

控制时间尺度不同。

## Plant 100 μs

需要解析：

- PWM；
- 开关状态；
- 电流内环；
- 电磁暂态。

## AGC 1 s

处理：

```text
PCC系统级功率协调
```

设备功率本身有约秒级响应动态。

如果AGC也100 μs：

```text
上一条命令还没形成物理Pmeas
↓
AGC又看到误差
↓
继续叠加
↓
容易命令累积/过调
```

所以：

> **越靠近开关越快，越靠近调度越慢。**

# 67. 为什么基础AGC会出现PV和EV对冲？

当前算法主要依据：

```text
PCC总误差
+
内部历史命令
```

如果误差方向在多个AGC周期中来回变化：

```text
某轮先加PV
后面误差反向
→ 又加EV充电
```

它不一定优先彻底撤销前一类资源已有动作。

长期可能出现：

```text
PV大发电
+
EV大充电
```

但两者净抵消后：

```text
PCC仍接近目标
```

这说明两个非常重要的概念：

```text
PCC Tracking Correct
≠
Resource Coordination Optimal
```

和：

```text
系统级KPI正确
≠
设备级状态合理
```

不是。

```text
内部资源状态管理/最优性不足
```

# 69. 为什么不一开始就直接实现项目书里的MPC/PSO/动态权重？

研发要先建立Minimum Viable Closed Loop（最低可用闭环）：

```text
PCC能测
↓
总误差能算
↓
六设备能分配
↓
设备能执行
↓
PCC能回目标
```

规则型AGC：

- 确定；
- 可解释；
- 易调试；
- 易转C；
- 易做Golden对比。

复杂优化可以建立在可信工程底座上，而不应该在底层闭环尚未证明时把所有复杂度一次堆进去。

面试准确说法：

# 70. 15种策略究竟怎样从项目高级应用需求一步一步提炼？

每项业务需求先问六个问题：

```text
1. 这个功能解决什么问题？
2. 需要哪些测量/参数输入？
3. 正常与异常边界是什么？
4. 是否需要历史状态或计时？
5. 用什么metric量化严重程度？
6. 触发后希望系统做什么？
```

然后统一输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

这就是早期 `Advanced_Microgrid_15_Strategies` 的工程抽象思想。

# 71. 为什么统一为 `status/alarm/metric/cmd`？

如果每项功能单独拉十几根线，顶层模型会失控。

统一接口有利于：

- 批量日志；
- 测试；
- 显示；
- 后处理；
- 以后迁C。

四类量可以理解：

## status
当前功能处于什么状态/阶段。

## alarm
是否触发阈值事件。

## metric
“问题有多严重/指标是多少”。

## cmd
策略建议系统往哪个方向、调多少。

# 72. 为什么15个 `cmd` 不能直接相加？

因为它们物理含义不同。

例如：

```text
S3 cmd = 无功kvar
S8 cmd = 减载kW
S14 cmd = 黑启动阶段编号
S15 cmd = 模式切换请求
```

即使都是kW的S1/S4/S7，也可能一个是：

```text
主目标
```

另一个是：

```text
硬约束
```

所以：

> **“统一数组接口”只解决数据组织，不等于“控制命令可以数学相加”。**

这正是后来LOCAL15必须新增Normalizer/Arbiter/P-Q-Mode分域的原因。

# 80. 为什么S3 Q分配必须知道当前P？

逆变器视在功率：

\[
S^2=P^2+Q^2
\]

若标幺额定 \(S=1\)：

\[
Q_{cap}=\sqrt{1-P^2}
\]

所以当前P越大，剩余Q越少。

不能简单：

```text
总Q/6
```

LOCAL15/C05按当前P占用后的剩余视在容量比例分Q。

# 84. 为什么S15重同步至少要比较 ΔV / Δf / Δθ？

```text

频率不同
相角不同
```

所以：

```text

Δθ满足阈值
持续稳定一段时间
↓
允许PCC重合
```

当前LOCAL15还通过ESS主机Fref trim微调相位/频率，实现受控重同步，而不是简单等几秒直接合闸。

# 85. 原模型为什么必须专门建立 Modbus/RS485 通信层？

这是V2.1必须补齐的一层。

前面已经建立了：

```text
PCC测量
↓
基础AGC
↓
六路PV/ESS/EV功率命令
```

如果此时把六路AGC输出直接连到六台设备的 `Pref`，在纯Simulink数学上完全可以运行。

但它隐含了一个非常强、也非常不真实的假设：

```text
控制器在这一时刻算出的命令
=
设备在同一时刻立刻收到的命令
=
数据一定正确
=
从不延迟
=
从不丢失
=
从不损坏
=
从不把旧命令当新命令
```

真实微网协调控制器显然不是这样工作的。

项目立项要求的最终对象是一个真正的“智能微网协调控制器”。它需要通过RS485、以太网、CAN等工业接口与光伏逆变器、储能PCS、充电设备交换数据，并支持Modbus等协议。因此从项目需求向仿真模型继续推导时，中间天然缺少一层：

```text
Algorithm
算法算出命令
↓
Communication
通信传输与协议映射
↓
Device
设备真正获得命令
```

所以前期 `MicroGrid_AGC_10kV` 没有采用：

```text
AGC_Controller
→ 六台设备Pref
```

而是采用：

```text
AGC_Controller
→ 六路AGC原始cmd_pu
→ AGC_Modbus_RS485_Link
→ 六路decoded Pref
→ 六台设备
```

后续对旧标准模型 `shiyansan` 的接口追踪也正式确认：

> 原AGC前6路命令并不是直接进入设备，而是先经过 `AGC_Modbus_RS485_Link`；该模块内部包含Modbus/RS485编码解码、延时、丢包、CRC、Last Good、从站ID、功能码和寄存器参数。

因此，这个通信层不是后来为了“让模型看起来复杂”临时添加的，而是把**实际协调控制器和现场设备之间存在通信边界**这个工程事实放进仿真。

## 85.1 如果完全没有这个通信层，会少掉什么？

没有它，模型只能验证：

```text
算法算对了吗？
设备能不能跟踪Pref？
PCC能不能回目标？
```

有了它以后，才能进一步问：

```text
命令晚到怎么办？
这一帧没到怎么办？
这一帧内容坏了怎么办？
链路中断怎么办？
设备继续保持旧命令会怎样？
控制器内部状态会不会和设备实际状态分叉？
```

所以它把模型从：

```text
Ideal Control Loop
理想控制闭环
```

推进到：

```text
Networked Control Loop
带通信边界的网络化控制闭环
```

这一步非常重要，因为后续项目真正发现的很多问题——包括通信延时、丢包、中断、恢复后PCC突跳、控制器状态和设备执行状态不一致——都只能在这种思想下被观察到。

## 85.2 Modbus和RS485到底是不是同一个东西？

不是。

这是面试非常容易被连续追问的一点。

### RS485是什么？

RS485首先解决的是：

> **电气层怎么传0和1。**

它主要规定：

- 差分传输；
- A/B线电气特性；
- 多点总线能力；
- 工业环境下较好的抗共模干扰能力；
- 较长距离传输。

它本身不规定：

```text
第一个字节是谁
功能码是多少
哪个寄存器表示Pref
负功率怎么编码
CRC具体怎么组织
```

### Modbus是什么？

Modbus解决的是：

> **这些0和1按照什么协议语义组织。**

它涉及：

- 从站地址；
- 功能码；
- 数据地址；
- 寄存器；
- 数据内容；
- 读写操作；
- RTU模式下的CRC校验。

因此典型关系是：

```text
Modbus RTU
    ↓
使用RS485作为物理通信介质
```

所以：

```text
RS485 ≠ Modbus
```

更准确地说：

```text
RS485
= Physical Layer / Electrical Interface
物理电气传输层

Modbus RTU
= Application/Protocol Framing
报文和数据语义层
```

原函数名称：

```text
Modbus_RTU_RS485_Encode_Channel_Decode
```

正是在表达：

> 用Modbus RTU风格的报文语义，去模拟一条RS485设备通信链。

## 85.3 为什么不是“加一个Delay块”就够？

因为通信问题不只有“慢”。

至少应该区分四类：

### 1. Protocol / Encoding
协议和数据表达问题

例如：

```text
+0.6 pu
到底怎样放进16位寄存器？
-0.4 pu怎样表示？
这是发给PV1还是ESS2？
```

### 2. Delay
时延

```text
这一帧最后会到
但晚了20 ms / 1 s
```

### 3. Packet Loss
丢包

```text
这一帧根本没有到
```

### 4. Corruption / CRC Error
内容损坏

```text
报文到了
但接收方发现内容不可信
```

另外还有：

### 5. Link Failure
整条链路断开

这五种现象对控制器和设备造成的影响并不完全相同。

如果只用一个：

```text
comm_bad = 1
```

把所有情况混成一起，就无法做定向工况，也无法知道究竟是哪类异常造成PCC和设备响应问题。

## 85.4 为什么原模型会出现3个独立代码模块？

实际提供的三个源文件是：

```text
modbus.m
RS485delay.m
RS485PACKETLOSS.m
```

它们并不是三套互不相关的“算法”，而是把一个完整通信模型拆成三个不同关注点。

### 模块A：`modbus.m`

正式函数：

```text
Modbus_RTU_RS485_Encode_Channel_Decode
```

它负责：

```text
工程量
↓
寄存器计数
↓
16位编码
↓
从站地址
↓
功能码
↓
寄存器描述
↓
P/Q/Enable/Sequence
↓
CRC
↓
接收校验
↓
有符号数恢复
↓
pu解码
```

它回答的是：

> **这条命令“是什么数据、发给谁、怎样编码、有没有损坏”。**

---

### 模块B：`RS485delay.m`

正式函数：

```text
RS485_Delay_Steps
```

它只负责：

```text
用户配置的时间延迟（秒）
↓
换算成
↓
Simulink应该延迟多少个离散仿真步
```

它回答的是：

> **这条命令应该晚多少个sample到。**

---

### 模块C：`RS485PACKETLOSS.m`

正式函数：

```text
RS485_Packet_Loss_Mask
```

它只负责生成：

```text
pass1
pass2
pass3
pass4
pass5
pass6
```

告诉外围逻辑：

```text
这一轮PV1的新报文是否通过？
这一轮PV2的新报文是否通过？
……
这一轮EV2的新报文是否通过？
```

它回答的是：

> **这一帧到底到不到。**

## 85.5 为什么不把三个函数全部写成一个大函数？

数学上完全可以。

但工程上不划算。

如果全部混在一起：

```text
编码
CRC
时延
丢包
链路状态
Last Good
```

任何一个测试失败时，都很难快速定位。

拆开以后可以独立设置：

### 协议基线

```text
delay = 0
loss = 0
CRC正常
```

只看：

```text
编码→解码是否一致
```

### 时延试验

```text
loss = 0
CRC正常
只改变delay
```

### 丢包试验

```text
delay = 0
CRC正常
只改变packet_loss_rate
```

### CRC故障试验

```text
delay = 0
loss = 0
force_crc_error = 1
```

### 断链试验

```text
link_enable = 0
```

这就是：

> **Separation of Concerns（关注点分离）**

也是为什么“需要三个模块”的真正答案。

不是因为通信理论规定必须正好三个，而是因为这样更容易：

- 单独验证；
- 单独注入故障；
- 调参；
- 定位；
- 复现实验；
- 后续替换真实通信。

## 85.6 但必须注意：完整通信链不只有这3个代码函数

这是旧讲解最容易遗漏的地方。

```text

12个输出
```

```text

6 × RS485_Last_Good Unit Delay
6 × RS485_Packet_Loss_Switch
```

以后绝对不要只看三个 `.m` 文件，就说自己已经解释完整个通信模块。

## 85.9 为什么六台设备要有六个Slave ID？

如果是典型RS485多点总线：

```text
                 ┌── PV1
                 ├── PV2
Master ──────────┼── ESS1
                 ├── ESS2
                 ├── EV1
                 └── EV2
```

一条总线上的节点可能都能“听到”同一串差分电气信号。

那设备怎样判断：

> 这一帧是不是给我的？

必须有地址。

所以当前函数每一台设备调用：

```text
process_one(cmd, slave_id, ...)
```

并将：

```text
b1 = slave_id
```

作为报文字节的一部分。

所以Slave ID本质上是：

> **逻辑设备地址。**

---

## 85.10 为什么AGC的浮点pu命令不能直接放进一个16位寄存器？

AGC内部可能产生：

```text
PV1 = +0.6500 pu
ESS1 = -0.4000 pu
EV1 = -0.6000 pu
```

这些是MATLAB `double`。

Modbus Holding Register的基本数据单元通常是：

```text
16 bit word
```

因此必须进行：

```text
工程量
→ 整数计数
```

当前代码：

```matlab
scale = max(abs(p_scale_counts_per_pu),1.0);
pCount = round(cmd * scale);
```

如果：

```text
scale = 10000 counts/pu
```

则：

```text
+0.6500 pu
→ +6500 counts

-0.4000 pu
→ -4000 counts
```

这就是：

> **Scaling（比例缩放）**

---

## 85.11 为什么必须有 `p_scale_counts_per_pu`？

因为寄存器中的：

```text
6500
```

自身没有工程意义。

它可能代表：

```text
6500 kW
650.0 kW
65.00 kW
6.500 pu
0.6500 pu
```

必须由通信双方约定：

\[
N=\operatorname{round}(P_{\mathrm{pu}}\times S)
\]

接收端：

\[
P_{\mathrm{pu}}=\frac{N}{S}
\]

其中：

```text
S = counts per pu
```

这就是：

> **Data Contract（数据契约）**

后续真实Modbus TCP点表里“工程量↔raw寄存器”的比例系数，本质上仍然是同一个问题。

---

## 85.12 为什么需要 `round()`？

因为：

```text
寄存器只能存整数word
```

例如：

```text
cmd = 0.650037 pu
scale = 10000
```

得到：

```text
6500.37
```

不能直接装进整数寄存器，所以：

```text
round → 6500
```

解码：

```text
0.6500 pu
```

这意味着引入：

> **Quantization Error（量化误差）**

如果scale越大：

- 分辨率越高；
- 但可表示的工程范围越小。

所以scale是：

> **范围和分辨率的权衡。**

---

## 85.13 为什么 `pCount` 要限制在 `-32768~32767`？

有符号16位整数范围：

\[
-2^{15}\le x\le2^{15}-1
\]

即：

```text
-32768 ～ 32767
```

如果：

```text
cmd × scale = 50000
```

已经无法放进一个有符号16位值。

所以先：

```matlab
clamp(...,-32768,32767)
```

这相当于通信编码层的数值保护。

---

## 85.14 为什么负功率还要转成UINT16？

Modbus寄存器本质上保存的是：

```text
16 bit word
```

ESS、EV命令又可能为负。

当前代码：

```matlab
function w = signed_to_uint16(x)
    if x < 0
        w = 65536.0 + x;
    else
        w = x;
    end
end
```

这是典型16位补码解释。

例如：

```text
-4000
```

编码：

\[
65536-4000=61536
\]

发送word：

```text
61536
```

接收：

```matlab
if d >= 32768
    y = d - 65536;
end
```

得到：

```text
61536 - 65536
= -4000
```

再：

```text
/10000
= -0.4 pu
```

完整链：

```text
-0.4 pu
→ -4000
→ 61536 uint16 word
→ -4000 signed
→ -0.4 pu
```

这也是为什么后续真实Modbus寄存器处理里：

```text
INT16 / UINT16
补码
scale
```

必须非常小心。

## 85.15 为什么发送帧里不仅有P，还放Q、Enable、Seq？

`process_one()` 当前逻辑会组织：

```text
P command
Q reference
Enable
Sequence
```

设计意图是：

> 一条设备控制消息不仅有“功率是多少”，还应该能够表达无功参考、控制是否投入、命令属于哪一轮。

当前函数中：

```text
P
→ pWord

Q
→ qWord

Enable
→ enWord

Sequence
→ seqWord
```

这说明前期通信原型已经开始从：

```text
“传一个double”
```

向：

```text
“定义设备控制帧”
```

转变。

## 85.16 为什么要有 `command_enable`？

因为：

```text
命令数值存在
```

和：

```text
当前允许执行
```

是两个不同事实。

例如：

```text
P = 0.6 pu
Enable = 0
```

合理解释应是：

> 0.6这个命令值仍然存在于数据结构中，但当前控制未使能。

如果只用：

```text
P=0
```

同时表达“停用”和“真正要求0功率”，语义会混在一起。

所以：

> **Value和Validity/Enable应该分离。**

这一思想后来在V3.2、V4、V5和BOARD15中继续发展成：

```text
EXT_CONTROL_ENABLE
validity
MODEL_STATUS
heartbeat
domain valid mask
```

## 85.17 为什么要有 `seqWord`？

代码：

```matlab
seqWord =
mod(floor(time_s / pollPeriod),65535.0) + 1.0;
```

它近似表达：

> 当前属于第几轮通信。

为什么需要这个概念？

因为接收方不能只看到：

```text
P=0.4
```

还可能需要知道：

```text
这是刚刚新来的0.4
还是很久以前就停在寄存器里的0.4？
```

Sequence Counter就是区分：

```text
值相同
```

和：

```text
信息是否更新
```

的一种常用方法。

后续正式工程中的 `CMD_SEQ` 就是更严格的发展版本，但两者语义不能简单说成完全相同。

## 85.18 为什么Sequence按 `poll_period_s` 变化，而不是每100 μs都加1？

因为：

```text
Real-Time Simulation Step
实时仿真步
```

和：

```text
Communication Transaction Period
通信业务周期
```

不是同一时间尺度。

例如：

```text
仿真步 = 100 μs
通信poll = 100 ms
```

那么100 ms内：

```text
1000个Plant计算步
```

但逻辑上只属于：

```text
同一轮通信
```

所以：

\[
slot=\left\lfloor\frac{t}{T_{\mathrm{poll}}}\right\rfloor
\]

比：

```text
每个100 μs都把sequence加1
```

更合理。

这是多时间尺度在通信层的另一个体现。

```text
b4  = Start Offset Low

b15 = Sequence Low
```

然后：

```text
CRC16
→ CRC Low / CRC High
```

因此从设计思想看，报文在表达：

```text
给谁
+
做什么
+
从哪里写
+
写多少
+
数据是什么
+
数据有没有损坏
```

## 85.20 一个必须纠正的边界：当前 `modbus.m` 不是完整通用Modbus协议栈

这是面试不能讲错的地方。

函数虽然有：

```text
function_code
```

并把它放入：

```text
b2
```

但当前源码没有：

```matlab
if function_code == 3
    ...
elseif function_code == 6
    ...
elseif function_code == 16
    ...
```

这种针对不同Modbus功能码实现完全不同PDU逻辑的分支。

同时它当前的软件帧包含：

```text
起始地址
寄存器数量
Byte Count
多个数据word
```

因此最稳妥的说法是：

> 当前 `modbus.m` 是一个 **Modbus RTU风格的软件协议仿真器**，保留从站地址、功能码、寄存器、16位编码、CRC等核心语义，用于在Simulink中模拟“协议化设备命令”；它不是完整的串口驱动，也不是覆盖所有Modbus功能码的通用协议栈。

不要说：

> “我这里已经完整实现了Modbus所有03/06/16标准行为。”

源码不支持这样的表述。

## 85.21 `start_reg_offset` 和 `start_reg_display` 为什么分开？

当前函数同时有：

```text
start_reg_offset
start_reg_display
```

其中：

```text
start_reg_offset
```

真正被拆成High/Low Byte放进软件报文。

而：

```text
start_reg_display
```

主要用于：

```text
rx_start_reg
```

诊断显示。

从用途上可以理解为：

```text
协议内部地址offset
```

和：

```text
人机界面/文档显示寄存器号
```

做了分离。

这与实际Modbus工程里常见：

```text
PDU offset
```

和：

```text
4xxxx文档地址
```

不是同一个表示方式的思想相似。

但当前源码没有把具体换算规则写死，所以面试应该说：

> 这里设计上把协议offset和显示编号分开了。

不要在没有点表佐证时自作主张说：

```text
start_reg_display = 40001 + offset
```

## 85.22 为什么需要CRC？

串行通信可能受到：

- 电磁干扰；
- 噪声；
- 线路质量；
- 数据位翻转

影响。

如果本来：

```text
0.60 pu
```

的某个bit发生变化，接收端可能得到完全不同的数。

所以发送端根据报文字节计算：

```text
CRC16
```

接收端再对收到的数据重新计算。

如果：

```text
calculated CRC
==
received CRC
```

则：

```text
crcOk=1
```

否则：

```text
crcOk=0
```

核心作用：

> **检测报文内容有没有被破坏。**

注意：

> CRC主要是检错，不是纠错。

它发现：

```text
这帧不可信
```

但不会自动把错误bit修回来。

---

## 85.23 为什么专门有 `force_crc_error`？

如果模型只在理想环境中运行：

```text
CRC永远正确
```

你无法证明接收侧CRC拒绝逻辑真的有效。

所以代码：

```matlab
if force_crc_error > 0.5
    crcLo = bitxor_int(crcLo,1.0);
end
```

故意翻转CRC低字节中的一个bit。

于是：

```text
数据主体不变
但附加CRC错误
```

接收端：

```text
重新计算CRC
≠
收到的CRC
```

最终：

```text
crcOk=0
```

这就是：

> **Fault Injection（故障注入）**

它的测试价值比“正常跑通一次”更高，因为它验证了：

```text
错误真的会被拒绝
```

## 85.24 CRC错误和Packet Loss为什么必须分开？

因为物理含义不同。

### CRC错误

```text
报文到达了
↓
但内容/校验不可信
↓
接收方拒绝
```

### Packet Loss

```text
这一帧压根没有到达
```

二者最终都可能造成：

```text
新命令未生效
```

但诊断原因不同。

如果后续要研究：

```text
通信可靠性
故障统计
保护逻辑
```

就必须区分。

## 85.25 `link_enable=0` 时 `modbus.m` 为什么把六路ok清零？

当前函数在：

```text
link_enable <= 0.5
```

时，六路：

```text
decoded = 0
ok = 0
crc = 0
```

它表达的是：

> 协议通信链本身不可用。

但注意：

> **这不等于六台设备最终一定立刻得到0功率命令。**

因为完整模型后面还有：

```text
Packet Loss Switch
+
Last Good
```

设备端最终可能继续保持上一条有效命令。

所以一定要区分：

```text
Protocol Decode Output
```

和：

```text
最终Device Pref
```

## 85.26 为什么 `comm_ok` 要把六台设备的ok取最小值？

当前：

```matlab
comm_ok =
min(ok1,ok2,...,ok6);
```

因为ok是0/1，所以它等价于：

```text
六台全部成功
→ 1

任意一台失败
→ 0
```

这是一个非常保守的：

> **Global Communication Health（全局通信健康标志）**

同理：

```text
crc_ok
```

表示六台全部CRC都正确。

优点：

- 简单；
- 易作为全局策略输入；
- 任一设备通信异常即可触发整体“通信不完全健康”。

缺点：

- 只看一个bit不知道具体哪台失败。

这也是后来系统为什么逐渐发展出：

```text
per-device validity
signal masks
execution state
```

更细粒度状态。

## 85.27 `rx_slave / rx_func / rx_start_reg / rx_reg_value` 是做什么的？

它们更多属于：

> **诊断/显示输出。**

当前函数：

```matlab
slot =
mod(floor(time_s/pollPeriod),6)+1;
```

然后：

```text
slot=1 → 显示PV1
slot=2 → 显示PV2
...
slot=6 → 显示EV2
```

所以可以在Display里看到：

```text
当前轮询显示的是哪个Slave
功能码
起始寄存器
当前寄存器值
```

## 85.28 一个非常重要的源码边界：它并没有严格模拟真实RS485总线逐帧占线

每次函数调用，实际上代码都会执行：

```text
process_one(PV1)
process_one(PV2)
process_one(ESS1)
process_one(ESS2)
process_one(EV1)
process_one(EV2)
```

也就是说：

> 六个设备通信结果在软件函数内被并行计算。

后面的：

```text
slot
```

主要用于决定诊断输出当前显示哪个设备。

所以不能把它描述成：

> “真实UART主站严格按照PV1→PV2→ESS1→……每次只发一帧，占用总线一定时间。”

当前实现没有把串口波特率、字节级发送时长、总线争用等做成完整离散事件仿真。

最准确的定位：

> **这是用于控制研究的软件级Modbus RTU/RS485通信行为抽象，而不是精确的串口总线时序仿真器。**

## 85.29 `RS485_Delay_Steps` 为什么需要单独一个函数？

源码：

```matlab
function delay_steps =
RS485_Delay_Steps(rs485_delay_s,sim_step_s)

step = max(sim_step_s,1e-9);

delay_steps =
max(
    round(
        max(rs485_delay_s,0.0)/step
    ),
    0.0
);
```

它解决的是一个非常具体的单位转换问题。

人设置通信延迟时习惯：

```text
20 ms
1 s
```

但Simulink离散Delay块需要：

```text
延迟多少个sample
```

所以：

\[
N_{\mathrm{delay}}
=
\operatorname{round}
\left(
\frac{T_{\mathrm{delay}}}{T_s}
\right)
\]

---

## 85.30 一个完整Delay换算例子

假设：

```text
通信延迟 = 20 ms = 0.02 s
仿真步长 = 100 μs = 0.0001 s
```

那么：

\[
N=\frac{0.02}{0.0001}=200
\]

所以：

```text
delay_steps = 200
```

意思：

> 这一路新命令要在200个实时仿真step之后才从Delay块输出。

---

## 85.31 如果仿真步长从100 μs改成50 μs，为什么delay_steps要变？

同样20 ms：

\[
N=\frac{0.02}{50\times10^{-6}}
=400
\]

所以：

```text
100 μs → 200 steps

50 μs → 400 steps
```

这说明：

> 用户想模拟的是“20 ms物理时延”，不是固定“200步”。

所以必须将：

```text
秒
```

根据当前模型步长换算成：

```text
离散步数
```

---

## 85.32 为什么要 `round()`？

如果：

```text
delay=2.03 ms
Ts=0.1 ms
```

则：

```text
20.3 steps
```

离散模型没有：

```text
0.3个sample
```

所以必须近似成整数。

`round()` 是取最接近的sample数。

这会带来最大约：

```text
±0.5个仿真步
```

的时间离散误差。

## 85.33 为什么代码要保护 `sim_step_s >= 1e-9`？

如果误输入：

```text
sim_step_s=0
```

直接除法会除零。

所以：

```matlab
step=max(sim_step_s,1e-9)
```

是防御式编程。

它不是通信理论要求，而是：

> **防止非法参数把仿真直接算崩。**

## 85.34 最关键的纠正：`RS485_Delay_Steps` 本身根本没有延迟任何数据

它只输出：

```text

```

真正保存命令并延后输出的是模型中的：

```text

...
```

这6个 `Delay` 块。

所以面试不要说：

## 85.36 `RS485_Packet_Loss_Mask` 为什么不是直接把命令变成0？

函数输出：

```text
pass5
pass6

```

它只回答：

> **当前poll slot里，这一路新报文能不能通过。**

没有直接决定：

```text
还是旧值
还是安全值
```

这是非常重要的职责分离。

## 85.37 为什么Packet Loss必须按“通信轮次”随机，而不是每100 μs随机一次？

当前：

```matlab
slot = floor(time_s / pollPeriod);
```

假设：

```text
Plant step = 100 μs
poll period = 100 ms
```

那么同一轮报文跨越：

```text
1000个仿真step
```

如果每100 μs重新抽一次随机数，可能变成：

```text
同一条报文：
第1个step收到
第2个step丢失
第3个step又收到
```

这在“报文”语义上没有意义。

按：

```text
slot=floor(t/Tpoll)
```

以后，同一个通信周期内slot不变，所以：

```text
同一帧
→ pass结果保持不变
```

这才更接近：

> 一条报文要么收到，要么没收到。

## 85.38 `packet_loss_rate=0.3` 到底是什么意思？

代码最终：

```matlab
pass = double(u >= loss_rate);
```

其中：

```text
u ≈ [0,1)
```

如果：

```text
loss_rate = 0.3
```

大约：

```text
u < 0.3
```

的通信轮次：

```text
pass=0
```

所以长期统计上大约30%丢包。

但注意：

> 这不是“每10帧固定丢3帧”。

随机序列可能出现：

```text
连续丢3帧
```

也可能：

```text
很长一段都不丢
```

这是Bernoulli式随机丢包思想，而不是固定周期删除。

## 85.39 为什么用固定 `random_seed`？

科研/工程测试最重要的是：

> **可复现。**

如果每次运行都真正随机：

```text
Run A
在12 s、15 s、28 s丢包

Run B
在5 s、18 s、40 s丢包
```

那么更改算法以后很难公平比较。

当前函数用：

```text
slot
+
channel
+
seed
```

确定一个伪随机值。

因此同样：

```text
seed
poll period
simulation time
```

会产生同样的丢包序列。

于是：

```text
Baseline
vs
Improved
```

可以在完全相同的通信异常序列下比较。

---

## 85.40 为什么不直接用 `rand()`？

当前基于：

```text
sin(...)
→ 取小数部分
```

的伪随机方式有几个工程便利：

- 输入确定 → 输出确定；
- 不依赖全局随机数状态；
- 同一seed容易复现；
- 更适合代码生成环境；
- 六通道可以显式引入不同channel偏移。

它不是为了做“高质量密码学随机数”，而是为了：

> **构造可重复的故障注入序列。**

---

## 85.41 为什么每个设备还要加 `channel*17`？

如果所有设备都只使用：

```text
slot + seed
```

那么同一个slot：

```text
PV1
PV2
ESS1
ESS2
EV1
EV2
```

会得到完全相同的随机值。

结果：

```text
六台一起丢
或
六台一起过
```

不符合“不同设备报文可以独立丢失”的试验需求。

所以加入：

```text
channel × 17
```

使不同通道在同一slot得到不同伪随机结果。

`17` 本身不是一个具有电力系统物理意义的常数，它只是用来拉开不同通道的确定性扰动相位。

---

## 85.42 为什么还有 `random_seed * 0.013`？

同理，seed必须真正进入伪随机映射。

不同：

```text
random_seed
```

应该得到不同故障序列。

`0.013` 只是当前数学映射的一部分，不应包装成某种物理参数。

---

## 85.43 `link_enable=0` 时为什么六路pass都为0？

因为：

```text
链路整体不可用
```

此时不存在：

```text
某个设备的新报文还能正常通过
```

所以：

```text
pass1...pass6 = 0
```

---

## 85.44 `packet_loss_enable=0` 时为什么pass都为1？

因为这一轮试验：

```text
不启用随机丢包
```

此时可以单独研究：

- Delay；
- CRC；
- Link断开。

这正是把不同异常机制拆开的意义。

---

## 85.45 `all_pass` 为什么取六路最小值？

因为：

```text
pass_i ∈ {0,1}
```

所以：

```matlab
all_pass =
min(pass1,...,pass6);
```

等价于：

```text
六台本轮全部通过
→ 1

任意一台丢
→ 0
```

它是：

> **这一轮六设备通信是否全部成功**

的全局标志。

---

## 85.46 最关键纠正：`RS485_Packet_Loss_Mask` 本身也没有真正“删除数据”

它只生成：

```text
pass mask
```

真正的选择动作由：

```text
RS485_Packet_Loss_Switch_1
...
RS485_Packet_Loss_Switch_6
```

完成。

因此准确说：

> Packet Loss函数负责决定“新报文有没有到”；Switch负责决定“设备实际采用新值还是旧值”。

---

## 85.47 为什么还必须有 `RS485_Last_Good_1~6`？

这才真正把“丢包”变成一个有控制意义的设备行为。

例：

```text
10 s：
设备最后一次成功收到
Pref = 0.40 pu

11 s：
AGC计算新命令
Pref = 0.60 pu
```

但11 s这一帧：

```text
pass=0
```

设备不可能神奇地知道0.60。

典型设备更可能：

```text
继续保持上一条成功命令0.40
```

所以模型必须保存：

```text
Last Good = 0.40
```

然后：

```text
pass=1
→ 使用新的0.60

pass=0
→ 继续使用Last Good 0.40
```

这就是Last Good的核心意义。

---

## 85.48 为什么Last Good用Unit Delay实现？

因为：

```text
上一条有效命令
```

是一个跨时间状态。

当前输出依赖：

```text
过去
```

就必须有记忆。

`Unit Delay` 本质上就是一个最基本的离散状态存储单元。

所以：

```text
Last Good
```

不是纯组合逻辑，而是：

> **有状态通信接收端行为。**

---

## 85.49 Packet Loss Switch到底在做什么？

概念逻辑：

```text
if pass_i == 1
    output_i = delayed_new_command_i;
else
    output_i = last_good_i;
end
```

因此它回答：

> **这一次设备最终用哪一个值。**

这也是为什么：

```text
Packet Loss Mask
```

和：

```text
Last Good
```

必须同时存在。

如果只有Mask：

```text
知道“丢了”
```

但不知道：

```text
设备下一拍到底执行什么
```

控制仿真仍不完整。

---

## 85.50 为什么完整通信链最好记成“四层”，而不是死记三个代码文件？

真正最有用的结构是：

```text
第一层：Protocol Layer
Modbus Encode / Decode / CRC

第二层：Timing Layer
Delay Steps + Variable Delay

第三层：Reliability Layer
Packet Loss Mask

第四层：Receiver Execution Policy
Switch + Last Good
```

这四层分别回答：

```text
数据怎样表达？
什么时候到？
到不到？
没到时设备怎么办？
```

这样理解以后，即使以后把：

```text
RS485
```

换成：

```text
Ethernet / CAN / IEC104
```

你仍然知道应该从哪些维度设计通信接口。

---

## 85.51 `comm_ok / crc_ok / all_pass` 三个状态有什么区别？

### `crc_ok`

回答：

> 六路软件报文的CRC检查是否全部正常？

属于：

```text
数据完整性
```

---

### `comm_ok`

在 `modbus.m` 内部由六路：

```text
ok1~ok6
```

汇总。

当前 `ok` 至少要求：

```text
CRC正确
功能码字段一致
起始offset一致
寄存器数量一致
```

所以它更接近：

> 协议解析层是否成功。

---

### `all_pass`

来自Packet Loss模块。

回答：

> 这一poll slot里六路随机丢包是否全部通过？

所以：

```text
crc_ok
≠
all_pass
```

可能出现：

```text
软件报文本身完全正确
但链路丢包
```

也可能：

```text
报文到达
但CRC错误
```

---

## 85.52 为什么还有 `RS485_comm_ok_with_loss`？

模型结构里确认有一个：

```text
RS485_comm_ok_with_loss
```

Product块。

它的设计思想就是把：

```text
协议层comm_ok
```

和：

```text
packet loss结果
```

合成一个更接近“当前链路整体可用”的状态。

概念上类似：

\[
comm_{\mathrm{effective}}
=
comm_{\mathrm{protocol}}
\times all_{\mathrm{pass}}
\]

这样高级策略就不需要自己再分别读取：

```text
CRC
Loss
```

才能得到一个总通信状态。

---

## 85.53 为什么高级策略S5一度把通信状态作为孤岛判据之一？

前期高级策略原型里，防孤岛使用过：

```text
频率
电压
通信状态
```

等综合信息。

这反映早期设计思想：

> 通信完全失联可能意味着设备/微网状态异常，需要提高保护警惕。

但后续LOCAL15做安全闭环以后，又进一步明确：

> **单纯通信异常不能等同于真实电气孤岛，不能仅因通信异常就物理跳开PCC。**

这正是从“早期功能原型”向“严格安全执行逻辑”演进的一个典型例子。

---

## 85.54 为什么原通信模块对后续论文特别重要？

因为它第一次在模型中创造出：

```text
AGC内部新命令
≠
设备当前命令
```

的可能性。

### 理想通信

```text
AGC cmd(t)
=
Device Pref(t)
```

### 固定延迟

```text
AGC cmd(t)
≠
Device Pref(t)

但未来：
Device Pref(t+τ)
≈
AGC cmd(t)
```

### 丢包

```text
AGC cmd(new)
≠
Device Pref

Device Pref
=
Last Good
```

### CRC失败

```text
控制器算了新值
但接收端拒绝该帧
```

于是“命令”第一次被拆成：

```text
控制器认为应该做什么
```

和：

```text
设备真正收到了什么
```

两层。

这正是后来：

```text
u_calc
u_commit
u_applied
Pmeas
```

不断继续细分的逻辑起点。

## 85.55 为什么后来离线通信试验会出现PCC严重过调和恢复突跳？

理解Last Good以后就很容易。

例如下行中断：

```text
AGC每1 s继续计算
↓
内部状态继续更新
↓
但设备因为通信中断
仍执行旧命令
↓
PCC没有按照AGC预期变化
↓
AGC继续认为误差还没消失
↓
内部命令进一步累积
```

通信恢复后：

```text
最新累计命令突然被设备获得
↓
设备功率大跳
↓
PCC超调
↓
AGC再反向修正
```

所以真正的问题不是简单：

> “网络慢了一点。”

而是：

> **控制器内部状态在通信异常期间继续前进，而物理设备状态没有同步前进。**

这就是网络化控制中的“状态分叉”。

---

## 85.56 为什么上行异常也会出问题？

后续通信实验又加入了PCC/设备测量上行异常。

如果：

```text
真实PCC已经变化
```

但：

```text
PCC_rx仍然冻结在旧值
```

AGC会根据陈旧反馈继续计算。

于是：

```text
Controller Perception
控制器认知

≠

Physical PCC
真实PCC
```

这与下行问题形成镜像：

```text
下行：
命令认知 ≠ 设备执行

上行：
控制器反馈 ≠ 真实物理
```

因此后来论文中“controller/resource-state mismatch”不是凭空构造，而是从早期通信模型和真实通信实验一步一步暴露出来的。

# 86. 为什么后来把旧模型内的RS485仿真删除，并改成真实Modbus TCP？

这个问题必须和上一章一起讲。

## 86.1 删除旧通信模块是不是说明它设计错了？

不是。

它完成的是：

> **离线功能原型阶段的软件通信仿真任务。**

早期：

```text
Simulink里的AGC
↓
Simulink里的虚拟Modbus/RS485
↓
Simulink里的设备
```

可以让我们在没有真实板卡时研究：

- 延迟；
- 丢包；
- CRC；
- Last Good；
- 通信中断。

后期平台已经具备：

```text
真实外部Board
↕
真实Ethernet
↕
OP5700
```

如果还把旧：

```text
AGC_Modbus_RS485_Link
```

串在模型内部，就相当于：

```text
真实通信
+
虚拟通信
```

连续经过两遍。

那就不再代表真实架构。

因此删除它是：

> **验证层级升级。**

不是：

> 前期方案错误。

## 86.2 K10为什么先直接 `MATLAB AGC → Pref`？

后续实时模型K10故意采用：

```text
MATLAB基础AGC
→ 六路Pref
→ IO_Mux
→ OpComm
→ SS
→ 六台设备
```

暂时绕过旧内部通信层。

目的不是永久放弃通信。

而是先单独证明：

```text
实时Plant正确
+
基础AGC正确
```

这样以后接真实Board出现问题时，可以把问题定位到：

```text
通信 / Board / I/O
```

而不是还怀疑：

```text
Plant本身是不是错的。
```

这是一种典型的：

> **Layer-by-Layer Validation（分层验证）**

## 86.3 为什么真实平台最后选Modbus TCP而不是继续模拟RS485？

暑期实际平台是：

```text
OP5700
↕ Ethernet
外部控制板
```

所以以太网是最直接的工程接口。

后续采用：

```text
Board = Modbus TCP Master/Client
OP5700 = Modbus TCP Slave/Server
```

配合Holding Register点表实现双向通信。

主要原因：

- 板和OP5700都有以太网；
- RT-LAB支持Modbus TCP接口；
- 工程师已有TCP主站程序基础；
- 点表可以清楚冻结数据合同；
- 部署和调试方便。

## 86.4 旧Modbus RTU/RS485和后来的Modbus TCP，哪些思想没变？

没变的是：

```text
设备/服务端地址和角色
寄存器
数据比例
16位word
读写方向
数据有效性
命令版本/序号
控制器与Plant分离
```

所以旧模型教会我们的：

```text
控制算法不能直接等于设备执行
```

这个思想完全保留下来了。

---

## 86.5 哪些东西变了？

### 物理通信介质

早期：

```text
RS485-style software simulation
```

后来：

```text
Real Ethernet
```

### 协议封装

早期：

```text
Modbus RTU-style
CRC16
```

后来：

```text
Modbus TCP
TCP/IP承载
```

Modbus TCP不再使用RTU串行帧末尾的那套CRC16作为应用层帧尾校验。

所以不要说：

> 后续真实Modbus TCP仍然运行 `crc16_modbus_15()`。

没有。

## 86.6 为什么V3.2还要重新设计Heartbeat和安全状态机？

旧模型的 `comm_ok` 主要回答：

```text
这一轮软件通信是否成功
```

但真实网络还有一个更棘手的问题：

> 寄存器里有一个“看起来合法的旧值”，不代表对方现在还活着。

例如Board突然死机：

```text
OP5700寄存器
仍然可能保留最后一次数值
```

如果只看：

```text
数据范围合法
```

可能误以为通信正常。

所以V3.2增加：

```text
RTLAB_HEARTBEAT
BOARD_HEARTBEAT
MODEL_STATUS
```

并设计：

```text
DISCONNECTED
↓
WAIT_VALID
↓
ENABLED
```

让“值是什么”和“对方是否持续更新”分开。

这是旧通信模型向真实工业通信的第一次明显升级。

## 86.7 为什么V4又发展出candidate/commit？

旧Last Good已经意识到：

```text
报文失败
→ 设备继续旧命令
```

但V4进一步从“控制器内部状态”角度解决：

```text
如果FC16写失败
AGC内部能不能把新命令当成已经执行？
```

答案：

```text
不能
```

因此：

```text
official state
↓
copy candidate
↓
calculate new command
↓
try FC16
↓
success?
├─ yes → commit
└─ no  → official state不变
```

这比旧：

```text
Last Good
```

又前进了一层。

旧Last Good主要保护：

```text
Device side command
```

V4 candidate/commit还保护：

```text
Controller internal state
```

## 86.8 为什么V5又发展出真实Takeover？

V4虽然：

```text
Board真实读
Board真实算
Board真实写
```

但六台设备仍由本地AGC控制。

这是Shadow。

确认：

- 编码；
- 符号；
-C算法；
- commit；
- heartbeat；
- 安全状态

无误后，V5才允许：

```text
Board Pref
↓
Safety Gate
↓
Plant
```

这就是：

> **先观测和比较，后真正接管。**

## 86.9 为什么后来还要区分 `u_calc / u_commit / u_applied`？

旧通信模块最多已经体现：

```text
AGC cmd
≠
Device Last Good
```

后来真实工程进一步发现至少有三层：

### `u_calc`
算法当前算出的候选命令。

### `u_commit`
确认完整成功发布、可以成为控制器正式历史的命令。

### `u_applied`
经过：

- 执行故障；
- 模式；
- 安全门；
- 能力限制

以后，Plant真正采用的命令。

因此：

```text
u_calc
可能 ≠ u_commit

u_commit
可能 ≠ u_applied
```

再往后：

```text
u_applied
和
Pmeas
```

之间又有正常设备动态。

这就是从一个简单“RS485丢包模型”逐步发展成完整工业控制状态语义的全过程。

```text
↓
发现命令可能晚到/丢失
↓
加入Last Good
↓
发现Controller cmd ≠ Device cmd

真实Modbus TCP
↓
发现成功计算 ≠ 成功发布
↓
candidate / commit
↓
真实Takeover
↓
```

## 86.11 面试专项：为什么原模型需要三个通信代码模块？

可以直接回答：

> 项目最终控制器与PV、ESS、EV之间不是Simulink理想信号线，而是工业通信，所以前期必须在AGC和设备之间建立通信边界。我们把它按关注点拆成三段：`modbus.m` 负责把六路pu功率命令按Modbus RTU风格做16位寄存器编码、从站地址、功能码、P/Q/Enable/Sequence和CRC校验并解码；`RS485delay.m` 只把秒级通信延迟转换成Simulink的离散Delay步数；`RS485PACKETLOSS.m` 按poll周期、通道号和固定seed生成六路可重复的丢包mask。外围再用6个Variable Delay、6个Packet Loss Switch和6个Last Good Unit Delay真正实现命令晚到以及丢包后设备保持上一有效命令。这样协议、时延、丢包和接收端保持行为可以分开验证，出了问题也能定位是哪一层。

---

## 86.12 面试专项：这三个文件中哪个真正“把数据延迟了”？

答案：

> **三个 `.m` 文件里没有任何一个真正保存六路历史数据并延迟输出。**

`RS485_Delay_Steps`：

```text
只计算N个sample
```

真正数据延迟：

```text
6个RS485_Variable_Delay块
```

这是非常容易被问住的细节。

---

## 86.13 面试专项：哪个文件真正“丢掉了一条命令”？

答案也不是：

```text
RS485PACKETLOSS.m
```

它只生成：

```text
pass_i=0/1
```

真正决定：

```text
采用新值
还是
继续Last Good
```

的是：

```text
Packet Loss Switch + Last Good
```

## 86.14 面试专项：为什么丢包后不是直接置0？

因为：

```text
“没收到新命令”
```

不等于：

```text
“收到了一条0功率命令”
```

两件事的物理语义完全不同。

如果误把丢包处理成0：

```text
每次丢包
→ PV/ESS/EV突然跳0
```

会制造一种并不代表实际设备常见保持行为的巨大扰动。

使用Last Good意味着：

> 没有新指令时继续保持最后已知有效命令。

## 86.16 面试专项：这个旧通信模型有哪些局限？

# 89. 为什么实时化成为后续最大工程问题之一？


# 91. Stubline为什么能够帮忙分核？

没有Stubline时：

```text
SM本步电压
依赖SS本步电流

SS本步电流
又依赖SM本步电压
```

需要同一步联立求解。

Stubline具有一个传播时间步，使两端可以使用上一拍边界信息：

```text
本步SM
← 已知边界历史

本步SS
← 已知边界历史
```

于是一个大网络可以拆成多个小网络独立计算。

# 92. 为什么普通Stubline方案不够好？

# 93. 为什么最后采用Transformer Differential Stubline？


2. 利用原物理元件作为数值边界；

4. 提供一步传播延时；
5. 能形成RT-LAB任务级电气解耦。

# 94. PMIO / Stubline / OpComm三个概念为什么必须分开？

## PMIO

```text
物理建模接口
```

让不同实时子系统可以拥有物理电气端口。

## Stubline

```text
具有传播延时的电气解耦元件
```

真正打断同一步电气联立。

## OpComm

```text
普通数字信号跨任务通信
```

例如：

```text
Vabc/Iabc/Fref/Vref/Pref/Qref/GridOn/Droop
```

因此：

```text
电气能量关系 → PMIO + Stubline
控制/测量数值 → OpComm
```

绝不能混。

# 113. 面试专项：PVmax完整回答模板

> **为什么会有PVmax？**  
> 项目要求做PCC有功协调、PV平滑和新能源最大化消纳，所以控制器不仅要知道PV现在实际发了多少，还必须知道当前天气条件下“最多还能发多少”。额定功率只是硬件铭牌上限，不能反映光照随时间变化；Pmeas又只是当前实际输出，不能体现尚未利用的调节裕度。因此我们定义PVmax作为当前最大可用功率。仿真阶段为了避免把研究重点转成复杂PV组件建模，用一条归一化PV profile描述日照资源，通过时间节点线性插值得到 \(g_{PV}(t)\)，再乘设备额定功率得到 \(P_{PV,max}=P_{unit}g_{PV}(t)\)。PVmax进入AGC计算光伏剩余headroom，也进入S6平滑和S12新能源消纳。当前两路PV采用同一profile属于Baseline简化，接口仍保留PVmax1/2两个独立输入，工程上可以换成逆变器available power、辐照度模型或短期预测。

如果继续追问：

### “PVmax和Pmeas最大区别？”

```text
PVmax = 能力上限
Pmeas = 实际结果
```

### “为什么不用额定功率？”

额定功率不随太阳变化。

### “为什么不用实际出力？”

实际出力可能是控制器主动限出来的，不能代表剩余可用能力。

### “PVmax突然下降怎么办？”

先把PV指令限制到新的能力范围，再让ESS/EV等承担剩余PCC任务。

# 114. 面试专项：SOC完整回答模板

> **为什么需要SOC？**  
> 储能和普通发电资源最大的不同是它除了功率约束还有能量约束。100 kW额定功率只告诉我瞬时能多快充放，不告诉我还能持续多久，所以必须用SOC表示当前剩余能量相对于额定容量的比例。根据 \(P=dE/dt\)，离散以后 \(\Delta E=P\Delta t\)，再除以额定kWh容量得到SOC变化。项目内部规定ESS正功率为放电、负功率为充电，因此当前简化公式是 \(SOC_{k+1}=SOC_k-P_{ess}\Delta t/(E_{nom}3600)\)，3600是秒到小时的单位换算。代码保存上一时刻SOC和时间，Reset时恢复初值，并把SOC限制在安全上下限。前期为了快速建立闭环用ESS命令积分，后续加入Router、Safety和Execution Fault以后，我又把SOC状态源对齐到FINAL_APPLIED ESS命令，使内部能量状态尽量跟真实Plant执行一致。当前这是微网协调控制用的简化能量模型，不是高精度BMS SOC估计算法，而且实际代码未显式加入充放电效率。

如果继续追问：

### “为什么有负号？”

正ESS功率代表放电，能量应该减少。

### “为什么有3600？”

kW×秒需要除3600才能换成kWh。

### “为什么不用0～1全范围？”

工程运行留安全裕量，当前Baseline用0.2～0.9。

### “为什么后来不用AGC命令直接积分？”

因为上游命令不一定等于最终实际执行。

# 116. 面试专项：为什么功率外环→电流参考→电压参考？

> 在PLL同步的dq坐标系中，d轴电流主要对应有功，q轴电流主要对应无功，所以功率外环比较Pref/Pmeas和Qref/Qmeas后，最自然的输出是Id/Iq参考。电流本身不能被直接“命令”，它由滤波电感两端电压差决定，\(Ldi/dt=v_{conv}-v_{grid}-Ri\)，所以电流内环再根据Id/Iq误差算出Vd/Vq电压指令，最后经调制和PWM决定IGBT开关。也就是说，功率环回答“为了达到目标功率需要多少电流”，电流环回答“为了形成目标电流需要施加多少电压”。

# 117. 面试专项：15策略怎么写出来的？

> 我把每项项目业务功能都按同一套需求工程方法拆解：先确定它要解决的业务问题，再确定需要哪些实时输入、正常和异常的边界、是否需要历史状态/计时、怎样定义量化metric，以及触发后希望系统做什么。前期统一成status/alarm/metric/cmd四类输出方便批量仿真和日志。但是这些cmd物理含义不一样，不能直接相加，所以后续我继续把它们按有功主目标、有功硬约束、有功辅助、无功和模式安全分域，通过Normalizer、Arbiter、AGC、Q Allocator、Mode Manager、Black Start和Resynchronization形成真实六设备命令。这一步才把“15项功能判断”变成真正的LOCAL15闭环控制栈。

# 118. 面试专项：基础AGC怎么写出来的？

> 联络线控制的最基本问题就是目标PCC功率和实际PCC功率之间的差，因此先定义 \(dP=P_{target}-P_{pcc}\)。如果误差在死区内不动作；如果需要提高微网净出力，先用PV剩余可用功率，再让SOC允许的ESS放电，最后减少EV充电；如果需要降低净出力，则先增加EV充电，再给ESS充电，最后降低PV。两台同类资源按当前剩余裕度比例分配而不是简单均分。这个算法有persistent Ppv/Pess/Pev状态，所以它是一套状态型规则协调器。它的定位是工程Baseline，用来先建立PCC闭环、实时化和板端C基线，不等价于立项书中完整的MPC/多目标动态权重最终算法。

# 119. 面试专项：为什么一开始不直接做MPC/PSO？

> 因为复杂优化必须建立在可信Plant、测量、执行和通信底座上。研发先要建立最低可用闭环，证明PCC能测、总需求能算、六设备能执行、PCC能回目标；规则型AGC结构确定、易验证、易转C，非常适合作为工程基线。MPC、日前PSO、多目标优化属于更高层或后续优化方法，不能在基础系统还没有实时跑通时把所有复杂度一次堆进去。

---

# 120. 面试专项：为什么100 μs，而AGC是1 s？

> 100 μs对应的是开关级Plant和本地快速控制，需要解析PWM、电流环和电磁暂态；AGC是系统级慢控制，调的是PCC功率任务，而且PV/ESS/EV的功率响应本身接近秒级。如果AGC也按100 μs更新，设备还没完成上一条命令，上层就会重复看到误差并继续累加。所以多时间尺度设计是越靠近开关越快，越靠近调度越慢。

---

# 121. 面试专项：为什么最终要1SM+3SS？

> 这不是项目书规定的，而是OP5700真实算力约束倒逼出来的。原六逆变器单任务约970～981 μs，无法在100 μs实时；单SM设置多核也没有自动解决强耦合电气方程。后来我们采用官方Transformer Differential Stubline结构，把变压器次级漏阻抗迁入带一步传播延时的Stubline，逐级从单EV扩展到2+2+2，最终形成1SM+3SS。同类两台资源分别放在EV/ESS/PV三个SS，高压公共网络和PCC留在SM，实际J2在100 μs下长期Overrun=0，所以这是通过工程验证得到的可行任务分区。

---

# 122. 面试专项：为什么“Build PASS”不等于模型正确？

> Build只证明模型可以被工具链编译。分核过程中我们曾遇到PCC数百kW异常和EV功率几十pu，说明虽然结构能算，物理拓扑仍可能接错。后来用拆分前标准模型shiyansan做数值Golden，重新核对PCC边界、五段馈线、prim方向和EV1测量源，恢复后两者PCC均值只差约0.11 kW。所以我会把数值正确、物理正确、功能正确和实时正确分开验证。

---

# 123. 面试专项：为什么先Shadow再Takeover？

> 外部Board第一次加入时，如果同时引入通信、C算法和真实设备接管，一旦系统异常很难知道根因。所以V4先让Board真实读、真实算、真实写回，但不控制设备，专门验证数据、符号、状态机、candidate/commit和日志；这些通过后V5才把板端40001～40006真正接到六设备Pref。这种先Shadow再Takeover的方式本质是降低一次改动的风险和故障定位范围。

---

# 124. 面试专项：candidate / commit为什么是工业控制器关键？

> 算法算出命令不等于命令已经成功发布。AGC本身有历史状态，如果我先推进内部状态但FC16写失败，下一轮控制器就会以为一个Plant根本没收到的命令已经执行过。因此我们把正式状态复制成candidate，在candidate上计算，只有输出合法、编码成功并且FC16完整写成功后才commit。这样控制器的正式历史只代表成功发布的控制内容。再往后还要区分u_commit和u_applied，因为发布成功也不代表设备一定形成了相同物理状态。
