# 3. 测试设计最重要的第一原则：从“功能命题”反推“工况”

假设你有一个功能：

> S4（防逆流）要防止微电网外送超过允许值。

不能随便运行60 s然后看波形。

必须先把功能写成一个可验证命题：

```text
如果：
PCC外送 > 允许外送上限

那么：
S4必须产生负方向纠偏

并且：
最终六设备命令必须使PCC外送下降
```

然后再反推工况：

```text
怎样确保PCC真的外送过限？
怎样让S4的限制和当前主目标发生明显冲突？
修正量理论上大概是多少？
```

这就是“测试设计”。

# 4. 为什么测试参数不能随便设置

很多人做仿真测试的方式是：

```text
阈值改一下
跑一下
有波形
截图
```

这不叫严谨验证。

我们后来的参数设计都尽量遵循一个原则：

> **参数要制造一个数值明确、方向明确、因果明确的场景。**

例如S1：

```text
主P控制：
希望进口100 kW

S1需量限制：
最多进口50 kW
```

那么你不用看复杂公式就知道：

```text
应该产生大约50 kW的约束修正
```

如果最后没有这个量级的修正，就值得检查。

所以参数不是“为了让策略亮灯”。

而是：

> **为了建立一个可以事先预测结果的实验。**

# 5. 五种你以后应该反复使用的测试设计方法

## 方法1：主目标与约束故意冲突

典型：

- S1 需量控制；
- S4 防逆流；
- S11 外送限制。

设计：

```text
主目标故意要求越界
+
约束设置清晰边界
```

观察：

```text
objective_dP（主目标调节量）
↓
effective_dP（约束后的有效调节量）
```

这个方法非常通用。

以后做：

- 电流限幅；
- 功率限幅；
- SOC约束；
- 温度降额；
- 电压边界；
- 电池充放电边界；

都可以用同样思路。

---

## 方法2：正向动作 + 负向安全边界

典型S5。

正向：

```text
真正电压/频率异常
→ 应该离网
```

负向：

```text
只有通信异常
→ 不应该错误跳PCC
```

这比只证明“能动作”高级得多。

因为安全控制真正关心：

```text
该动作的时候动作
+
不该动作的时候绝对不要乱动作
```

以后做：

- 保护；
- 故障检测；
- 安全互锁；
- BMS（电池管理系统）；
- 逆变器保护；
- 汽车控制器；

都必须有这种意识。

---

## 方法3：双方向测试

典型S6。

```text
PV快速上升
→ ESS往充电方向补偿

PV快速下降
→ ESS往放电方向补偿
```

如果只测一个方向：

> 符号写反、饱和边界错误可能完全发现不了。

以后验证：

- 电流正负；
- 充放电；
- 升降压；
- 电机正反转矩；
- P/Q双方向；
- 功率流方向；

都应该想到双向测试。

---

## 方法4：透明回归测试

新增一个Router（路由器）、Gate（门控）或者Safety Layer（安全层）以后：

```text
新功能关闭
↓
最终输出必须和旧系统完全一样
```

这证明：

> **仅仅插入新结构，没有破坏原系统。**

这是非常重要的软件/控制工程思想。

以后做：

- 新控制算法旁路；
- A/B版本；
- 新安全层；
- 新滤波器；
- 新保护；
- 版本升级；

都应该首先做透明回归。

---

## 方法5：状态机分阶段测试

典型：

- S14 Black Start（黑启动）；
- S15 Resynchronization（重同步）。

不能只看：

```text
最后系统恢复正常
```

必须看：

```text
Stage1是否正确
↓
Stage2是否正确
↓
Stage3是否正确
↓
每个状态的进入条件
↓
每个动作的执行顺序
↓
退出条件
```

这就是 State Machine Verification（状态机验证）。

# 6. 为什么“文件名写PASS”绝对不能算通过

最终LOCAL15测试形成了一个很重要的原则：

> **PASS必须有因果证据。**

例如S4：

```text

↓

↓
```

```text

↓

↓
Command（命令）
↓
Actuation（执行）
↓
Plant Response（对象响应）
```

这六层就是项目非常重要的测试资产。

# 8. LOCAL15为什么要先做成15/15 Golden Reference（黄金参考）

这是C迁移阶段的基础。

如果LOCAL15自己都没有冻结：

```text
今天改S4
明天改S8
后天又改S15
```

此时同时写C：

```text
你根本不知道C应该复制哪个版本。
```

所以正确工程顺序是：

```text
先冻结模型语义
↓
15/15 PASS
↓
模型成为Golden Reference
↓
再迁移到C
```

Golden Reference不是说：

> “Simulink一定永远是最优实现。”

而是：

> **它是迁移期间用来判断C代码是否保持原功能的标准答案。**

# 11. 为什么算法不能直接认识“40101”“40001”

这是一条非常值得以后记住的软件架构原则。

错误：

```c
project15_core(reg40101, reg40102, modbus_socket, json);
```

正确：

```text
Modbus raw register
↓
Engineering Main Program（工程主程序）
解码
↓
ControllerInput
↓
控制算法
↓
ControllerOutput
↓
工程主程序编码
↓
Modbus register
```

原因：

> **算法应该知道物理量，不应该知道通信地址。**

例如算法只需要知道：

```text
pcc_p_kw
```

而不应该知道：

```text
它来自40101
线端符号和算法符号相反
INT16缩放0.1
```

这些都属于 I/O Adapter（输入输出适配）职责。

这是非常标准、非常通用的软件分层思想。

# 12. C01～C10到底是什么：按“依赖关系”逐层建立完整控制器

必须先纠正一个认识：

> C01～C10不是十个互相平行的算法，也不是S1～S10。

它们是把最终LOCAL15按软件依赖关系拆开验证。

---

## C01｜Strategy15 Core（15策略判断核心）

目标：

> 把原15策略判断从MATLAB迁移到C。

重点验证：

- S1～S15输出；
- 原persistent状态显式化；
- 状态随时间连续更新；
- C和参考实现一致。

你要掌握：

> **有状态算法迁移时，不能只测一个输入点，而要测时间序列。**

---

## C02｜P Objective（有功目标/约束）

目标：

> 从各P策略里决定“当前总共应该调多少”。

包括：

- 主目标选择；
- S2/S7去重；
- S1/S4/S11约束；
- S10 target→dP；
- S12方向转换。

你要掌握：

> **策略层决定总任务，资源协调层决定谁承担。**

---

## C03｜P Coordination Baseline（基础有功资源协调）

输入：

```text
effective_dP
```

输出：

```text
6路基础Pref
```

考虑：

- PVmax；
- SOC；
- EV；
- 资源余量；
- 1 s AGC更新；

# 13. candidate / pending / commit：你必须真正弄懂

假设控制器这一轮计算：

```text
PV1 = 0.5 pu
ESS1 = 0.2 pu
...
```

此时只代表：

> **算法算出来了。**

还没有证明Modbus FC16真的成功写进RT-LAB。

所以先形成：

`candidate（候选命令）`

保存成：

`pending（待提交候选）`

然后：

```text
FC16成功
↓
controller_commit
↓
才成为official / committed command
```

为什么这么做？

因为如果：

```text
算法内部已经认为自己执行了新命令
但是网络写失败
Plant仍在执行旧命令
```

下一轮控制器和Plant的状态就发生分叉。

因此：

> **控制器内部状态推进必须和真实命令发布结果建立明确关系。**

这是非常通用的分布式控制/嵌入式控制思想。

# 14. 为什么FC16失败以后不能简单“全部重算”

假设：

```text
Snapshot A（测量快照A）
↓
计算Candidate A
↓
FC16失败
```

如果还没有新的测量：

```text
Plant状态没有新的证据
```

可以对同一candidate重试。

但如果已经取得：

`Snapshot B（新的测量快照B）`

那么：

> A对应的是旧Plant状态，不能继续无条件发送。

必须：

```text
废弃旧pending
↓
基于Snapshot B重新计算
```

你应该从这里学会：

> **控制命令必须和产生它的输入快照绑定。**

这个思想以后做：

- 网络控制；
- 实时数据处理；
- 多线程；
- 机器人；
- 汽车控制器；
- 分布式能源控制；

都很有用。

# 15. 为什么普通重连不能等于Reset

TCP断开：

```text
连接没了
```

并不一定意味着：

```text
控制器内部历史全部失效
```

如果每次网络抖动都：

```text
controller_reset
```

可能造成：

- AGC内部资源状态突然回初值；
- 黑启动/恢复状态丢失；
- 控制命令跳变；
- 恢复不连续。

所以最终规则：

```text
普通Modbus reconnect（重新连接）
≠ controller reset
```

Reset必须是：

> **显式、有定义的状态重建行为。**

# 21. 为什么点表里有 INT16 / UINT16 / bool / enum / bitmask

## UINT16（16位无符号整数）

只表示非负数。

适合：

- SOC；

- 频率；
- 心跳；
- 序号；

## bool（布尔编码）


例如：

## enum（枚举编码）

一个整数代表一个状态。

## bitmask / bitfield（位掩码/位域）

一个16位整数同时表示多个开关或状态。

```text
...
```

你不需要背所有bit。

# 22. 为什么有缩放Scale（比例系数）

Modbus寄存器通常传整数。

但真实工程量可能是：

```text
-123.4 kW
49.98 Hz
0.7654 p.u.
```

所以约定：

```text
原始整数 × scale = 工程量
```

例如：

```text
raw = 4998
scale = 0.01
→ 49.98 Hz
```

这是非常典型的工业控制接口设计。

# 23. 为什么Runtime Config需要“原子更新”

假设80个配置寄存器不是一瞬间写完。

如果Board刚好在中间读取：

```text
前40个是新配置
后40个是旧配置
```

会产生：

> **一份从来没有人真正配置过的混合控制器参数。**

所以使用：

```text
CONFIG_SEQ
+
CONFIG_SEQ_ECHO
+
seq_before
+
seq_after
```

只有：

```text
before = echo = after
```

才接受整块配置。

这叫：

> **Atomic Snapshot（原子快照）思想。**

这是非常值得掌握的软件/通信一致性知识。

# 35. 一个非常适合面试的真实问题案例：S6为什么一开始不动作


- 会定位问题；

# 36. 另一个很值得讲的案例：为什么要candidate/commit

问题：

```text
控制器计算了新命令
```

如果内部直接更新：

```text
Plant实际还在执行旧命令
```

状态失配。

解决：

```text
candidate
↓
pending
↓
FC16成功
↓
commit
```

这个案例比单纯说“我会Modbus”更能体现工程深度。
