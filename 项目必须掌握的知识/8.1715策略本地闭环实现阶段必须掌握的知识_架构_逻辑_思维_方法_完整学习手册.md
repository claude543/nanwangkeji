# 1. 第一层必须掌握：什么才叫“真正闭环”

这是本阶段最重要的第一原则。

最开始的15策略模块：

```text
Advanced_Microgrid_15_Strategies
（15种高级应用策略模块）
```

已经能输出：

```text
status[15]
（15路状态）

alarm[15]
（15路告警）

metric[15]
（15路指标）

cmd[15]
（15路策略命令）
```

但这不等于：

```text
15策略已经闭环
```

因为这些量可能只是：

```text
显示
记录
离线分析
```

真正闭环必须完整经历：

```text
Measurement（测量）
↓
Strategy Decision（策略判断）
↓
Request Normalization（请求标准化）
↓
Arbitration / Constraint（仲裁 / 约束）
↓
Allocation（资源分配）
↓
Final Command（最终命令）
↓
Actuator / Converter（执行器 / 变流器）
↓
Plant（被控对象）
↓
Measurement（重新测量）
```

因此以后你看到任何“控制算法”，第一问不是：

> “它的公式是什么？”

而是：

> **“它最后到底改变了哪个真实执行量？这个执行量有没有进入Plant（被控对象）？Plant变化以后有没有重新反馈回来？”**

# 2. 你必须建立一个永远通用的“闭环分层图”

建议你把下面这张图背下来。

```text

        ↑
        │

        ↑
        │

        ↑
        │

        ↑
        │

        ↑
```

每一层只回答一个问题。

---

## 2.1 Measurement Layer（测量层）

回答：

> 现在系统真实是什么状态？

例如：

```text
PCC P（公共耦合点有功）
PCC Q（公共耦合点无功）

Freq（频率）
PVmax（光伏最大可用功率）
SOC（储能荷电状态）
Pmeas（设备实测功率）
```

---

## 2.2 Strategy Layer（策略层）

回答：

> 根据当前状态，某个策略认为应该做什么？

例如：

```text
S1：
进口太多，需要减少进口

S3：
电压偏差，需要无功

S8：
低压/低频，需要减载

S14：
当前进入黑启动第3阶段
```

---

## 2.3 Arbitration Layer（仲裁层）

回答：

> 多个策略同时说话时，到底谁说了算？

例如：

```text
S7 / S9 / S10 / S12 / S13
只能选一个作为P主目标

S1 / S4 / S11
不是主目标，而是硬约束
```

---

## 2.4 Allocation Layer（资源分配层）

回答：

> 已经知道“总共要调多少”，六台设备分别承担多少？

例如：

```text
AGC（自动有功调节）
→ 6路Pref（有功参考）

Q Allocator（无功分配器）
→ 6路Qref（无功参考）
```

---

## 2.5 Execution Layer（执行层）

回答：

> 算出来以后，这个命令能不能真正送设备？

这里包括：

```text
Execution Mapper（执行映射）
Source Router（控制源路由）
Fault Injector（执行故障注入）
Final Safety（最终安全接口）
Mode Router（模式路由）
Breaker Router（断路器路由）
```

---

## 2.6 Plant（被控对象）

真正执行：

```text

Qref
Fref
Vref
Droop
GridOn
PCC Breaker
```

然后重新产生测量。

# 3. 第二层必须掌握：`u_calc → u_commit → u_applied → Pmeas`

这是本阶段最值得长期保留的状态链。

---

## 3.1 `u_calc（候选算法命令）`

含义：

> 算法本轮“想”让设备执行什么。

当前大致对应：

```text
AGC Candidate（AGC候选命令）
```

例如：

```text
ESS1 candidate = +0.8 pu
```

表示算法想让ESS1放电0.8标幺。

---

## 3.2 `u_commit（正式提交命令）`

含义：

> 经过执行映射、辅助策略、黑启动门控、控制源选择以后，系统真正决定要提交什么。

当前主要由：

```text
Command Source Router（控制源路由）
```

输出。

例如：

```text
CONTROL_SOURCE（控制来源） = LOCAL15
```

以后：

```text
u_commit = LOCAL15最终候选
```

---

## 3.3 `u_applied（实际采用命令）`

含义：

> 执行侧实际采用了什么。

当前通过：

```text
Execution Fault Injector（执行故障注入器）
```

显式构造。

例如：

```text
u_commit = 0.8
fault gain（故障增益） = 0.3
```

则：

```text
u_applied = 0.24
```

---

## 3.4 `Pmeas（实测功率）`

含义：

> 设备真正经过本地功率环、电流环、PWM（脉宽调制）、变流器、滤波器以后，最后形成的真实物理功率。

所以：

```text
u_applied
≠
Pmeas
```

也很正常。

因为设备存在动态响应。

# 14. GFL（跟网型）和GFM（构网型）的通俗理解

## GFL（跟网型）

像：

> “跟着别人走。”

它需要已有电网提供：

```text
频率
相位
电压基准
```

---

## GFM（构网型）

像：

> “自己当领队。”

它自己建立：

```text
电压
频率
相位参考
```

孤岛以后如果所有设备都还是GFL：

```text
没有人提供电网基准
```

所以必须至少一个GFM。

当前默认：

```text
ESS1
```

作为孤岛主机。


## RECLOSE HOLD（重合保持）

```text

```

## NORMAL（返回正常）

```text

ESS1 GFM → GFL
```

# 18. 第十一层必须掌握：实时系统必须有“第k拍 / 第k+1拍”意识

本质：

```text

↓
B当前计算
↓
```

没有先后关系。

实际上定义：

```text

判断

第k+1拍：
执行
```

以后做：

```text

嵌入式
网络控制
状态机
```

都必须问：

# 21. 为什么不能“写完就直接接Plant”

# 63. 第三十五层必须掌握：为什么Q能力要看 Final Pref，而不是 Candidate

变流器视在功率满足大致：

```text
S² = P² + Q²
```

如果：

```text
有功已经占很多
```

无功能力就少。

所以计算Q余量时应该使用：

```text
实际最终有功占用
```

也就是：

```text
FINAL_APPLIED Pref
```

而不是：

```text
AGC Candidate
```

这体现：

> **资源能力计算必须基于真实执行状态，而不是控制意图。**

# 99. 如果最终只记住10句话，就记住这10句

```text
1.
算法会算，不等于系统闭环。

2.
意图、提交、实际执行、物理响应必须分层。

3.
主目标和硬约束永远不要混在一起。

4.
仲裁器决定谁说了算，分配器决定任务怎么分。

5.
状态数字没有意义，状态必须对应真实动作。

6.
实时控制必须明确第k拍和第k+1拍。

7.
新功能先Shadow，再透明回归，再真实接管。

8.
测试不是让曲线动，而是制造有鉴别力的因果证据。

9.
脚本成功、Build成功、功能PASS是三个不同层次。

10.
模型/代码事实 → 可验证证据 → 项目结论/论文主张。
```
