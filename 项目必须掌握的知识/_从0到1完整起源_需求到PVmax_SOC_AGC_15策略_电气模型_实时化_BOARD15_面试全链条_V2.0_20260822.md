# 1. 项目从0开始到底在解决什么问题？

项目对象是一个光储充微电网：

```text
PV：分布式新能源
ESS：双向储能
EV：可控充电负荷
普通负荷
上级配电网
```

这些对象的物理属性不同：

## PV

```text
优点：清洁、边际燃料成本低
限制：受光照约束，不能想发多少就发多少
```

## ESS

```text
优点：充放电双向、响应快、可缓冲波动
限制：既有功率上限，又有能量/SOC限制
```

## EV

当前基线主要把EV作为柔性充电负荷：

```text
增加充电 → 多吸收电
减少充电 → 释放负荷
```

## 上级Grid

```text
提供并网电压/频率基准
向微网供电
接受或限制微网外送
接收调度/联络线目标
```

因此项目真正研究的是：

> **怎样让一个包含随机新能源、可充放储能、柔性负荷和上级电网接口的系统，在正常、经济、故障、并离网等多场景下仍然可测、可控、可协调、可安全运行。**

# 4. 为什么从需求会自然推导出 Grid + PCC + PV + ESS + EV + Load + Breaker？

这一节是“原有微电网电气仿真基础到底怎么从0搭”的起点。

---

## 4.1 为什么先有上级Grid？

项目要求：

```text
主配微协同
联络线控制
防逆流
并网/离网
需量
```

这些概念都需要一个“外部大电网”。

没有Grid：

```text
不存在购电/外送
不存在联络线
不存在并网
不存在防逆流
```

所以首先建立一个10 kV三相上级电网模型。

早期模型使用 `Three-Phase Programmable Voltage Source` 模拟强电网。

---

## 4.2 为什么要10 kV？

项目面对配电侧微网，10 kV是典型中压配电电压等级之一。

这让后续：

```text
低压逆变器
→ 升压变压器
→ 10 kV母线
```

成为合理工程结构。

注意：10 kV是当前模型场景选择，不是所有微网都必须10 kV。

---

## 4.3 为什么一定要PCC？

PCC = Point of Common Coupling（公共连接点）。

它把系统分成：

```text
微网内部
↕ PCC
上级电网
```

项目很多功能都直接问：

```text
微网整体现在进口多少？
外送多少？
是否超过反送边界？
是否跟上调度计划？
```

这些都必须在一个统一边界测量。

所以PCC不是“为了有个测量点”，而是系统级协调的核心观测点。

当前内部功率符号：

```text
Ppcc > 0：微网向上级电网外送
Ppcc < 0：微网从上级电网进口
```

---

## 4.4 为什么必须有PV？

因为项目是“光储充”，且要求：

```text
新能源消纳
平滑出力
防逆流
多目标优化
```

没有PV，上述新能源问题根本无法验证。

---

## 4.5 为什么必须有ESS？

很多功能都需要一个快速双向资源：

```text
平滑PV
防逆流
削峰填谷
AGC
联络线控制
黑启动
孤岛构网
动态扩容
```

ESS同时具备：

```text
充电吸收
放电支撑
快速响应
储存能量
```

因此它天然是微网最重要的调节资源之一。

---

## 4.6 为什么必须有EV/充电负荷？

项目不仅有源和储，还要体现“荷侧柔性”。

EV在当前基线主要作为可控负荷：

```text
功率过剩 → 增加充电
功率不足 → 减少充电
```

所以它能参与：

```text
PCC调节
新能源内部消纳
低压低频减载
```

---

## 4.7 为什么还有普通Load？

真实园区不只有充电桩。

还有：

```text
不可控/固定负荷
```

所以需要固定Load构造基础用电背景。

但要特别记住：后续用实际 `shiyansan` 核实后，当前冻结PCC测量边界为：

```text
六设备网络
→ PCC V-I Measurement
→ Load1 / Load2 + PCC Breaker + Grid
```

因此当前基线PCC量主要用于六设备对外交换口径，不能简单套用早期概念图理解。

---

## 4.8 为什么需要PCC Breaker？

项目要求：

```text
并网
↔
孤岛
```

必须存在一个实际可以断开/重合的电气执行器。

所以PCC三相断路器是：

```text
模式逻辑
→ 真实物理解列/重合
```

之间的桥梁。

# 7. 为什么最底层一定要先有直流侧？

功率电子变流器不能凭空产生能量。

## PV

真实系统：

```text
太阳能
→ PV组件
→ DC
→ 逆变器
→ AC
```

## ESS

```text
电池
→ DC
↔ 双向变流器
↔ AC
```

## EV

当前项目在交流微网侧主要把它表示为可控充电功率接口，但真实充电过程本质仍包含：

```text
AC
→ 变换
→ DC电池
```

因此模型可以用简化DC源/直流侧等效来保留功率交换接口，而不必把PV组件、电池电化学、车载BMS全部详细建模。

**为什么可以简化？**

因为项目当前研究重点是：

```text
微网协调控制
+
并网功率电子接口
+
实时HIL
```

而不是PV组件或BMS本身。

# 8. 为什么需要 Two-Level Converter（两电平变流器）？

## 8.1 两电平是什么？

三相两电平桥典型有：

```text
3个桥臂
× 每个桥臂上下2个功率开关
= 6个主要开关器件
```

每个桥臂中点在直流母线正/负侧之间高速切换，因此称Two-Level（两电平）。

---

## 8.2 为什么不能直接用“受控功率源”？

如果只研究小时级能量优化，受控功率源更轻量。

但本项目后续要验证：

```text
PWM
本地电流控制
P/Q功率环
GFL/GFM
并离网
RT-LAB实时动态
```

所以开关级变流器能保留：

- 控制器动态；
- PWM开关效应；
- 电流内环；
- 变压器/滤波器动态；
- 模式切换。

代价就是计算量变大，这也直接导致后续100 μs实时化问题。

---

## 8.3 变流器的“输入”到底有哪些？

### 电气输入

```text
DC侧电压/能量
```

### 控制输入

```text
6路PWM门极脉冲
```

它**不直接读取**：

```text
SOC
PVmax
PCC目标
防逆流阈值
```

这些属于更上层的决策。

变流器只负责：

> 按门极脉冲让功率器件导通/关断，形成实际交流端电压和电流。

---

# 9. 为什么变流器后面一定有滤波器？

PWM输出含大量开关频率高频分量。

若直接接入电网：

- 电流谐波大；
- 电压纹波大；
- 电能质量差；
- 控制测量被高频噪声污染。

所以需要L/C等滤波元件。

## 9.1 为什么电感能抑制快速电流变化？


电感关系：

\[
v_L=L\frac{di}{dt}
\]

高频意味着较大的 \(di/dt\)，电感会对快速电流变化表现出更强阻碍。

## 9.2 为什么电容可以旁路高频？

电容阻抗：

\[
X_C=\frac{1}{2\pi f C}
\]

频率越高，电容阻抗越小，高频分量更容易被旁路。

所以L+C组合能够让最终送入电网的主要成分接近50 Hz基波。

---

# 10. 为什么需要升压变压器？

逆变器低压侧通常是几百伏等级，而项目公共母线是10 kV。

因此需要：

```text
低压逆变器
↓
变压器
↓
10 kV接入网络
```

变压器还同时带来：

- 电气隔离；
- 电压等级转换；
- 接线组别；
- 漏阻抗；
- 相位关系。

后续实时分核之所以能使用Transformer Stubline，一个关键就是：

> 变压器本来就有漏R/L，可以把这部分物理阻抗迁入Stubline作为数值解耦位置，而不是凭空加入一段完全新的线路。

# 11. 为什么每台设备都需要自己的 `prim_*` 测量？

例如：

```text
prim_PV1
prim_PV2
prim_ESS1
prim_ESS2
prim_EV1
prim_EV2
```

它们位于每台设备自己的高压接入侧。

最先得到：

```text
Vabc
Iabc
```

然后本地Control System继续从这些量计算：

```text
PLL相角/频率
Pmeas
Qmeas
dq电压电流
```

---

## 11.1 为什么不能所有设备都只用PCC的V/I？

因为设备与PCC之间存在：

```text
变压器
馈线R/L
不同节点
```

所以：

```text
V_device_local
不一定等于
V_PCC
```

本地控制器要稳定控制自己的电流和功率，就必须看自己的实际端口状态，而不是只看一个远端PCC总状态。

---

## 11.2 `prim` 和 PCC 测量分别回答什么？

```text
prim：
“这一台设备自己的接入点现在发生了什么？”

PCC：
“整个微电网加起来对上级电网表现成什么？”
```

这就是为什么两者并不重复。

# 12. 最终实际旧模型的馈线结构为什么不是对称的？

真实冻结拓扑：

```text
公共母线
│
├─ PV1：直接接入
├─ PV2line  → PV2
├─ ESS2line → ESS2
├─ EV2line  → EV2
└─ ESS1line → 中间节点
               ├─ ESS1
               └─ EV1line → EV1
```

## 12.1 这客观上产生什么作用？

### PV1条件相对简单
靠近公共母线，独立馈线阻抗忽略。

### PV2/ESS2/EV2
各有一段独立馈线，因此本地端电压受自身线路压降影响。

### ESS1/EV1
共享上游 `ESS1line`，EV1还更远。

这会形成节点耦合：

```text
EV1充电变化
↓
EV1line电流变化
↓
ESS1line上游电流也变化
↓
中间节点电压变化
↓
ESS1本地prim也可能感受到变化
```

这不是控制器互发消息，而是通过共同电气网络发生物理影响。

---

## 12.2 为什么不能编造“老师就是为了某个具体实验才这么接”？

现有模型能证明：

> 拓扑确实如此，并构造了不同电气距离。

但现有资料不能严格证明原作者当时唯一主观意图。

面试更稳的说法：

> **这种结构让模型比六台理想同母线资源更接近小型径向配电网络，并让本地控制面对不同电气环境。**

# 13. 为什么必须有本地 Control System，而不是AGC直接给PWM？

因为两者处在完全不同时间尺度和抽象层次。

AGC处理：

```text
PCC目标
kW级功率任务
约1 s更新
```

PWM处理：

```text
功率开关门极
μs级
```

中间必须有设备本地闭环：

```text
Pref/Qref
↓
功率外环
↓
Id*/Iq*
↓
电流内环
↓
Vd*/Vq*
↓
调制波
↓
PWM
↓
Converter
```

---

# 14. 为什么功率外环输出的是“电流参考”？

在PLL同步的dq坐标系中，如果d轴与电网电压矢量对齐，可直观理解：

\[
P\propto V_d I_d
\]

\[
Q\propto -V_d I_q
\]

因此：

```text
要改变P
→ 调Id

要改变Q
→ 调Iq
```

所以：

```text
Pref - Pmeas
↓ PI
Id_ref

Qref - Qmeas
↓ PI
Iq_ref
```

这就是“功率外环产生电流参考”。

---

# 15. 为什么电流内环输出的是“电压指令”？

对滤波电感，简化电压方程：

\[
L\frac{di}{dt}=v_{conv}-v_{grid}-Ri
\]

如果想让电流按照 \(I^*\) 变化，本质上必须控制：

```text
变流器端电压 v_conv
```

所以：

```text
Id_ref - Id_meas
Iq_ref - Iq_meas
↓
PI + dq交叉耦合补偿 + 电网电压前馈
↓
Vd_cmd / Vq_cmd
```

然后再变成三相调制电压。

这就是：

> **外环告诉内环“我要多少电流”，内环告诉PWM“我要产生什么电压”。**

---

# 16. 为什么电流内环必须比功率外环快？

如果功率外环已经快速改变Id_ref，但电流实际还迟迟跟不上：

```text
外层继续认为误差存在
→ 再加命令
→ 容易过调/振荡
```

所以控制系统遵循带宽分层：

```text
电流内环最快
功率/电压环次之
AGC更慢
经济优化更慢
```

这是多时间尺度控制的基本原则。

---

# 17. 为什么需要PLL？

GFL（Grid-Following，跟网型）逆变器必须知道：

```text
电网当前相角θ
电网当前频率f
```

PLL从三相电压中估计这些量。

有了θ，才能把三相abc量转成同步旋转dq量，使原本交流的正弦量在稳态下变成近似直流量，从而方便PI控制。

没有PLL，跟网型控制器就没有可靠同步参考。

---

# 18. 为什么还需要GFM和Droop？

并网时：

```text
上级电网已经建立V/f
GFL只需跟随
```

孤岛以后：

```text
PCC breaker断开
```

如果所有设备都只会“跟别人”，系统就没人建立电压频率。

所以至少一个资源必须GFM（Grid-Forming，构网型）。

当前通常选ESS，因为ESS：

- 双向功率；
- 响应快；
- 能量可控；
- 不受瞬时日照直接限制。

典型Droop：

\[
f=f_{ref}-K_fP
\]

\[
V=V_{ref}-K_vQ
\]

用于多电源在无强电网时形成类似同步机的频率/电压外特性。

---

# 19. 为什么 `Droop_On=1` 不等于设备已经切到GFM？

项目中必须区分：

```text
Droop_On
```

和：

```text
GridOn / ConnectMode
```

### Droop_On
允许/启动Droop分支计算。

### GridOn / ConnectMode
决定最终到底选择GFL还是GFM控制路径进入后续电流环/PWM。

所以可能：

```text
Droop已经在后台计算
但GridOn=1
→ 最终仍是GFL实际控制
```

不能说“3 s打开Droop以后设备就自动构网”。

# 20. 为什么还要 Microgrid Supervisory Control？

设备本地快速环负责：

```text
让本机跟踪P/Q或V/f
```

但微网系统还需要统一：

```text
Fref
Vref
系统模式
```

尤其在：

- 孤岛；
- 构网；
- 频率/电压恢复；
- 多设备协同。

Supervisor就是设备层和系统协调层之间的一个全局参考管理层。

# 21. 到这里为什么还不能马上写AGC和15策略？

因为第一步必须先证明：

```text
Plant本身可信
+
每台设备本地控制闭环可信
+
```

如果连：

# 22. PVmax为什么会从项目要求中“必然长出来”？——从第一性问题开始推导

PVmax不是为了让模型多一个变量。

它解决的是一个非常具体的问题：

> **控制器必须知道PV“当前最多还能发多少”，否则无法判断调节能力。**

下面逐层推。

---

# 23. 为什么知道PV额定功率还不够？

假设逆变器铭牌：

```text
P_rated = 100 kW
```

这个值只回答：

> 硬件额定能力大致是多少。

它不回答：

> 当前太阳条件下真的有多少能量可用。

同一台100 kW光伏：

```text
夜间：≈0 kW
阴天：可能20～50 kW
晴天中午：可能接近100 kW
```

所以：

```text
P_rated
≠
P_available(t)
```

项目为了做：

```text
AGC
平滑
新能源消纳
```

必须知道第二个量。

于是定义：

```text
PVmax(t)
= 当前时刻最大可用有功功率
```

---

# 24. 为什么不能直接把 `Pmeas` 当PVmax？

这是面试最容易追问的地方。

## `Pmeas`
回答：

> 现在实际发了多少。

## `PVmax`
回答：

> 当前条件下最多能发多少。

例：

```text
PVmax = 80 kW
Pref  = 40 kW
Pmeas ≈ 40 kW
```

如果把Pmeas当PVmax：

```text
控制器会以为这台PV只能发40
```

但真实还有：

```text
80-40=40 kW
```

向上调节裕度。

因此：

```text
Pmeas = 当前执行状态
PVmax = 当前能力边界
```

这两个概念绝不能混。

---

# 25. `P_rated / PVmax / Pref / Pmeas` 四个量怎么区分？

| 量 | 核心问题 | 典型来源 |
|---|---|---|
| `P_rated` | 这台设备名义上多大？ | 铭牌/配置 |
| `PVmax` | 当前太阳条件下最多能发多少？ | available power/辐照度/预测/profile |
| `Pref` | 控制器希望它现在发多少？ | AGC/调度 |
| `Pmeas` | 它实际发了多少？ | 本地V/I测量计算 |

正常条件下大致要求：

```text
0 ≤ Pref ≤ PVmax ≤ P_rated
```

但：

```text
Pmeas ≈ Pref
```

只在设备正常、未限幅、动态基本完成时成立。

---

# 26. 为什么PVmax直接对应项目的三个重要功能？

## 26.1 AGC

AGC需要知道：

```text
PV还能增加多少？
```

最基本向上裕度：

\[
R_{PV,up}=\max(P_{PV,max}-P_{PV,current},0)
\]

没有PVmax，AGC就不知道“这台PV还能不能继续加”。

---

## 26.2 S6平滑出力

平滑关注的是：

```text
新能源资源可用出力本身是否快速变化
```

例如云层变化导致：

```text
PVmax: 65 → 95 → 55 → 65 kW
```

这比单纯改PCC目标更直接代表PV资源波动。

后续LOCAL15真实测试中，最开始改tie-line target时S6不动作，最终沿真实信号追踪确认S6读的是 `Ppv_max1/2`，改 `PV_profile_pu` 后才正确触发ESS平滑补偿。

这就是非常典型的面试问题：

> “为什么你测试S6不能随便改PCC目标？”

回答：

> 因为S6监测的是PV资源变化，测试必须作用在它真正读取的PVmax输入上。

---

## 26.3 S12新能源最大化消纳

要判断弃光，必须知道：

```text
本来可以发多少
-
实际利用多少
```

只有Pmeas：

```text
只能知道实际发了多少
```

无法知道有没有“未利用的可发能力”。

所以新能源消纳率、弃光估计都天然需要available power/PVmax概念。

---

# 27. 真实工程里的PVmax应该从哪里来？

真实产品可以有多种来源：

```text
1. PV逆变器直接上送 Available Power / Pmax
2. MPPT状态或直流侧功率估计
3. 辐照度 + 温度 + PV模型估算
4. 短期光伏预测
5. 站级EMS给出的可用出力
```

当前项目为什么没有把这些全部建进去？

因为研究重点是：

```text
微网协调控制与HIL
```

而不是：

```text
光伏组件I-V曲线/MPPT算法
```

所以前期仿真把复杂太阳资源压缩成一个最小必要状态：

> **当前最大可用有功。**

---

# 28. 为什么仿真要用归一化 `PV_profile_pu`？

定义：

\[
g_{PV}(t)\in[0,1]
\]

表示：

```text
当前资源条件
=
额定能力的多少比例
```

比如：

```text
0.65 = 当前最多能达到65%额定功率
```

如果：

```text
P_unit=100 kW
```

则：

```text
PVmax=65 kW
```

## 为什么不用直接存kW曲线？

因为pu有三个优点：

1. 与额定容量解耦；
2. 换100 kW/500 kW设备时曲线可以复用；
3. 便于不同设备归一化比较。

---

# 29. 为什么还要 `PV_time_s`？

只给：

```text
PV_profile_pu=[0.2,0.5,0.8,0.4]
```

系统不知道这些值发生在什么时候。

所以还要：

```text
PV_time_s=[0,10,20,30]
```

形成完整的时间—能力曲线：

```text
0s  →0.2
10s →0.5
20s →0.8
30s →0.4
```

---

# 30. 为什么必须插值？

仿真时间连续推进。

假设当前：

```text
t=15s
```

但曲线只有：

```text
10s →0.5
20s →0.8
```

不能等到20s才突然跳。

当前代码采用最简单确定的线性插值。

设：

\[
a=\frac{t-x_k}{x_{k+1}-x_k}
\]

\[
g(t)=g_k+a(g_{k+1}-g_k)
\]

代入：

\[
a=\frac{15-10}{20-10}=0.5
\]

\[
g(15)=0.5+0.5(0.8-0.5)=0.65
\]

若 `P_unit=100 kW`：

```text
PVmax=65 kW
```

---

# 31. 为什么线性插值适合当前项目？

它不是最精细的太阳物理模型，但有：

```text
简单
确定
无随机隐藏状态
容易转C
容易复现
容易控制测试
```

对“协调控制功能验证”很合适。

如果以后研究：

```text
秒级云影预测
PV组件动态
MPPT
```

才有必要换成更复杂模型。

# 32. 实际 `PVcurve.m` 每一行为什么这么写？

真实核心：

```matlab
pu = interp_profile(time_s, PV_time_s, PV_profile_pu);
pmax = max(P_unit_kW, 0.0) * max(pu, 0.0);
Ppv_max1_kW = pmax;
Ppv_max2_kW = pmax;
```

## `interp_profile(...)`

从时间曲线中求当前可用比例。

## `max(P_unit_kW,0.0)`

防御异常配置：额定功率不允许因为参数错误变成负数。

## `max(pu,0.0)`

即使profile误填负值，也不让“最大可用光伏功率”变负。

## 两路都等于 `pmax`

当前Baseline假设：

```text
PV1、PV2
容量相同
天气profile相同
```

这只是模型简化，不是物理定律。

# 33. 为什么接口仍然保留 `Ppv_max1` 和 `Ppv_max2` 两个独立输出？

因为未来完全可能：

```text
PV1遮挡
PV2无遮挡
```

或：

```text
容量不同
朝向不同
组件故障不同
```

所以AGC接口从一开始保留两路独立能力变量是合理的。

面试可以说：

> 当前基线用同一profile是为了简化测试，但数据接口不把两台PV绑定死。

# 34. 为什么PVmax不是控制命令？

PVmax描述：

```text
环境 + 设备当前能力
```

Pref描述：

```text
控制器的意图
```

AGC能做的是：

```text
在[0,PVmax]内选择Pref
```

不能因为“想多发”就直接把PVmax命令成100 kW。

因此：

> **PVmax属于capability state（能力状态），Pref属于control action（控制动作）。**

---

# 35. 如果PVmax突然从80 kW掉到40 kW，而Pref原来70 kW，会怎样？

物理上70 kW命令已经不可实现。

合理流程应该：

```text
PV能力下降
↓
PVmax=40
↓
AGC/执行映射把PV Pref限制≤40
↓
剩余PCC调节任务
转给ESS/EV等其他资源
```

这也是为什么上层协调器必须持续更新资源能力，不能只记住历史命令。

# 36. PVmax相关“为什么库”——必须脱口而出

1. 为什么额定功率不能替代PVmax？——额定容量不反映瞬时光照。
2. 为什么Pmeas不能替代PVmax？——实际输出不包含未使用余量。
3. 为什么PVmax不是Pref？——能力边界不是控制意图。
4. 为什么用pu曲线？——容量解耦、复用、归一化。
5. 为什么需要time数组？——给profile定义时间轴。
6. 为什么要插值？——仿真时间落在离散节点之间。
7. 为什么线性插值？——简单、可复现、足够支撑协调控制验证。
8. 为什么两台PV当前PVmax相同？——Baseline简化，不是接口限制。
9. 为什么AGC需要PVmax？——计算向上headroom。
10. 为什么S6需要PVmax？——它关心PV资源波动而非PCC目标变化。
11. 为什么S12需要PVmax？——要区分“本来能发”和“实际利用”。
12. 真实产品PVmax从哪来？——逆变器available power、辐照度模型、预测等。
13. 为什么不建完整PV组件？——研究目标是微网协调控制，不是PV组件物理。
14. PVmax突然掉了怎么办？——限制PV指令并重分配其他资源。

# 37. SOC为什么会从项目要求中“必然长出来”？

SOC不是为了显示一个百分数。

它解决的是：

> **ESS除了“瞬时能输出多大功率”，还必须知道“还剩多少能量”。**

---

# 38. 为什么只知道ESS额定100 kW不够？

100 kW是Power（功率）能力：

> 每个瞬间能以多快速度充/放。

但如果电池只剩很少能量：

```text
仍不能长期100 kW放电
```

所以储能必须同时有：

```text
Power limit：功率上限 kW
Energy state：能量状态 kWh / SOC
```

这就是PV和ESS能力建模最大的区别之一。

---

# 39. SOC的最基本物理定义是什么？

\[
SOC=\frac{E_{stored}}{E_{nominal}}
\]

例：

```text
额定容量 E_nom=200 kWh
当前储能 E=120 kWh
```

则：

\[
SOC=120/200=0.60
\]

即60%。

---

# 40. 为什么项目那么多功能都必须用SOC？

## AGC

```text
SOC过低
→ 不允许继续增加放电

SOC过高
→ 不允许继续增加充电
```

## S9削峰填谷

```text
峰时想放电
但必须先确认有能量
```

## S12新能源消纳

```text
想用ESS吸收PV
但SOC接近上限就没有足够空间
```

## S14黑启动

```text
如果ESS能量不足
不能假装它能长期构网并恢复负荷
```

## 日前优化

储能计划必须满足：

\[
SOC_{min}\le SOC(t)\le SOC_{max}
\]

所以SOC是：

> **跨时间的能量可行性约束。**

---

# 41. 为什么SOC必须由功率积分得到？

功率定义：

\[
P=\frac{dE}{dt}
\]

于是：

\[
dE=Pdt
\]

离散化：

\[
\Delta E=P\Delta t
\]

SOC是能量除以额定容量：

\[
\Delta SOC=\frac{\Delta E}{E_{nom}}
\]

所以：

\[
\Delta SOC=\frac{P\Delta t}{E_{nom}}
\]

这不是拍脑袋公式，而是直接来自功率和能量的定义。

---

# 42. 为什么实际代码分母要乘3600？

当前单位：

```text
P：kW
E：kWh
time：s
```

而：

```text
1 h = 3600 s
```

因此：

```text
kW × s / 3600
= kWh
```

所以代码：

\[
\Delta SOC
=
\frac{P_{kW}\Delta t_s}
{E_{kWh}\times3600}
\]

如果忘了3600，SOC变化会快3600倍，是严重单位错误。

---

# 43. 为什么当前公式前面是负号？

当前项目ESS功率方向：

```text
Pess > 0：放电，能量减少
Pess < 0：充电，能量增加
```

所以：

\[
SOC_{k+1}
=
SOC_k
-
\frac{P_{ess}\Delta t}
{E_{nom}\times3600}
\]

### 放电

```text
Pess>0
→ 减去正数
→ SOC下降
```

### 充电

```text
Pess<0
→ 减去负数
→ SOC上升
```

一个负号同时统一了两个方向。

---

# 44. 为什么输入是 `Pess_pu × P_unit_kW`？

本地设备命令经常用pu标幺值。

假设：

```text
Pess_pu=0.5
P_unit=100 kW
```

则真实功率：

\[
P=0.5\times100=50kW
\]

SOC容量使用kWh，所以必须先把pu恢复成kW。

这也是为什么“标幺值”和“工程单位”一定要清楚区分。

---

# 45. 实际 `SOC_Calculation.m` 每个核心变量为什么存在？

真实函数保存：

```text
persistent soc1 soc2 last_t
```

## `soc1/soc2`

因为SOC是状态，取决于过去所有充放电历史。

当前50 kW不能单独决定当前SOC。

## `last_t`

需要计算真实：

```text
dt = time_s - last_t
```

而不是假设每次调用间隔永远固定。

---

# 46. 为什么第一次调用和时间回退时要Reset？

正常仿真时间应单调增加。

如果：

```text
time_s < last_t
```

通常意味着：

```text
Reset / 仿真重新开始
```

如果继续沿用上一轮的persistent SOC：

```text
新实验会继承旧实验电量
```

完全错误。

所以重新用：

```text
SOC0_ess1
SOC0_ess2
```

初始化。

# 47. 为什么要 `lo=min(SOC_min,SOC_max)` 和 `hi=max(...)`？

这是防御式编程。

即使配置误写：

```text
SOC_min=0.9
SOC_max=0.2
```

内部仍先整理成：

```text
lo=0.2
hi=0.9
```

避免clamp上下限彻底反掉。

---

# 48. 为什么要clamp到 `[SOC_min,SOC_max]`？

有两层原因。

## 数值层

避免积分产生：

```text
SOC<0
SOC>1
```

## 控制层

当前工程不是用0/1极限，而是留安全窗口，例如：

```text
SOC_min=0.20
SOC_max=0.90
```

原因：

- 避免过放；
- 避免过充；
- 保留安全裕量；
- 给AGC清晰资格边界。

# 49. 一个完整SOC放电例子

设：

```text
SOC0=0.60
E=200 kWh
P_unit=100 kW
Pess=+1 pu
```

即100 kW放电。

持续1 h：

\[
\Delta SOC=-\frac{100}{200}=-0.5
\]

理论：

```text
0.60→0.10
```

若：

```text
SOC_min=0.20
```

代码最终clamp到：

```text
0.20
```

# 50. 一个完整SOC充电例子

设：

```text
SOC=0.60
Pess=-0.5 pu
P_unit=100 kW
E=200 kWh
```

即50 kW充电。

持续1 h：

\[
\Delta SOC
=-\frac{-50}{200}
=+0.25
\]

所以：

```text
SOC: 0.60→0.85
```

这能直接检查功率符号是否理解正确。

# 51. 为什么6月29日说明文档写了效率η，但实际代码没有？

说明文档给过更一般形式：

\[
SOC_{k+1}=SOC_k+
\frac{\eta_{ch}P_{ch}-P_{dis}/\eta_{dis}}
{E_{nom}}\Delta t
\]

它表达了：

```text
真实充电有损耗
真实放电也有损耗
```

但当前实际 `SOC_Calculation.m` 使用的是简化理想效率积分，没有显式η。

因此面试必须说准确：

> **说明文档保留了可扩展的通用公式，当前实际控制验证代码采用简化能量积分，未显式加入充放电效率。**

不能说“代码已经完整考虑效率”。

# 52. 为什么前期SOC可以用ESS命令积分？

早期想先建立：

```text
AGC命令
→ ESS
→ SOC约束
```

命令积分有优点：

- 实现简单；
- 没有Pmeas高频纹波；
- 容易测试；
- 能快速给AGC提供SOC边界。

但隐含假设：

```text
命令 ≈ 实际执行
```

在正常离线基线中可以接受。

# 53. 为什么后来LOCAL15必须让SOC跟 `FINAL_APPLIED_ESS`？

随着项目引入：

```text
Source Router
Execution Fault Injector
Safety Gate
```

开始出现：

```text
上游命令
≠
最终真正进入Plant的命令
```

例如：

```text
候选ESS=+0.8 pu
执行故障后真正Plant=+0.3 pu
```

如果SOC仍按0.8积分：

```text
SOC下降过快
```

内部能量状态会和真实Plant脱离。

所以后来把SOC源对齐到：

```text
FINAL_APPLIED_ESS
```

核心原则：

> **物理状态应该跟真正执行的量走，而不是跟控制器上游“想执行”的量走。**

这也是后续论文“controller state vs physical state”思维的工程先例。

# 54. 为什么不直接做高精度BMS SOC算法？

真实BMS可以有：

```text
库仑计量
OCV校正
等效电路
EKF/UKF
温度补偿
老化SOH修正
```

但当前项目研究的是：

```text
微网协调控制器
```

不是BMS算法。

所以简化SOC模型只需要保证：

```text
能量随充放电正确变化
+
有安全上下限
+
上层控制可使用
```

即可。

这体现模型设计原则：

> **复杂度必须服务于研究目标。**

# 55. SOC相关“为什么库”——必须脱口而出

1. 为什么SOC不是功率？——SOC是能量比例，功率是能量变化速率。
2. 为什么需要kWh容量？——只有功率上限不知道能持续多久。
3. 为什么用积分？——来自 \(P=dE/dt\)。
4. 为什么有3600？——秒和小时换算。
5. 为什么正Pess让SOC下降？——项目定义正ESS功率为放电。
6. 为什么负Pess让SOC上升？——减去负数等于增加SOC。
7. 为什么用pu×Punit？——把标幺恢复为kW。
8. 为什么要persistent？——SOC依赖历史。
9. 为什么要last_t？——计算真实积分时间间隔。
10. 为什么时间回退要Reset？——避免新实验继承旧能量状态。
11. 为什么要clamp？——保证数值和安全边界。
12. 为什么上下限不直接0/1？——留运行保护裕量。
13. 为什么两台ESS要两个SOC？——两台设备历史可不同。
14. 为什么早期用命令积分？——快速、平滑、适合初始控制验证。
15. 为什么后来改FINAL_APPLIED？——让能量状态与真实执行一致。
16. 实际代码有没有η？——没有显式加入。
17. 为什么不做BMS精细模型？——研究目标是微网协调，不是电池SOC估计。

# 56. PVmax和SOC为什么正好代表两种完全不同的资源约束？

## PVmax

描述：

```text
瞬时可发能力
```

它回答：

> 现在还能向上加多少PV？

## SOC

描述：

```text
跨时间能量状态
```

它回答：

> ESS现在是否还有资格继续充/放？

所以AGC同时使用二者，本质上是在结合：

```text
新能源瞬时能力约束
+
储能能量约束
```

这就是为什么这两个看似独立的小模块实际上是基础协调算法的关键输入。

---

# 57. 基础AGC为什么会从项目要求中自然产生？

项目要求：

> 联络线功率按目标计划运行，让整个微网对上级电网表现成一个可调度电源或负荷。

这句话数学化以后，第一件事就是定义：

```text
目标PCC功率 Ptarget
实际PCC功率 Ppcc
```

于是总有功调节需求：

\[
dP=P_{target}-P_{pcc}
\]

这个式子只回答：

> **整个微网净功率还需要往哪个方向、调多少。**

它还不是六台设备命令。

---

# 58. 为什么 `dP=Ptarget-Ppcc` 的符号很重要？

当前内部符号：

```text
Ppcc > 0：向上级电网外送
Ppcc < 0：从上级电网进口
```

例：

```text
Ptarget=-100 kW
Ppcc=-120 kW
```

则：

```text
dP=+20 kW
```

含义：

```text
当前进口120
目标只进口100
↓
微网净出力需要增加20
```

实现方式可以：

```text
多发电
或
少用电
```

所以正dP对应：

```text
PV↑ / ESS放电↑ / EV充电↓
```

---

# 59. 为什么需要 `P_dead` 死区？

真实PCC会有：

- 测量噪声；
- 功率纹波；
- 设备正常动态；
- 小范围随机波动。

如果0.1 kW误差也调：

```text
AGC可能来回抖动
资源频繁微调
```

所以：

```text
|dP| ≤ P_dead
→ 不做新的资源分配
```

死区不是“控制不精确”，而是：

> **用少量稳态容差换取更稳定、更少动作的控制。**

---

# 60. 为什么dP>0时优先PV→ESS→EV？

实际基础AGC采用：

```text
PV增加
↓
ESS放电
↓
EV减少充电
```

## 60.1 PV为什么先？

- 清洁能源优先利用；
- 不消耗储能SOC；
- 只要PVmax还有余量就可以增加；
- 少弃光符合项目新能源消纳目标。

## 60.2 ESS为什么第二？

- 快速双向调节；
- 可以补功率缺口；
- 但会消耗电池能量；
- 受SOC下限约束。

## 60.3 EV为什么最后减充？

- 它是用户侧负荷；
- 减少充电相当于牺牲充电服务；
- 所以基础规则把它放在后级。

这是一套**工程Baseline优先级**，不是项目书规定的唯一全局最优解。

---

# 61. 为什么dP<0时优先EV加充→ESS充电→PV降出力？

当微网净出力过剩时，希望：

```text
多用电
或
少发电
```

## 61.1 EV先增加充电

多余电能优先在内部被柔性负荷消纳。

## 61.2 ESS再充电

把多余能量存起来。

## 61.3 PV最后降出力

弃光是最后手段。

所以：

```text
EV charging↑
→ ESS charge↑
→ PV curtailment
```

体现：

> **优先内部消纳和储能，再减少新能源利用。**

---

# 62. 为什么同类两台设备不是“平均分”？

实际代码使用 `alloc_up/alloc_down` 按剩余余量比例分配。

假设：

```text
PV1当前20，PVmax1=80 → 余量60
PV2当前50，PVmax2=70 → 余量20
```

总余量：

```text
80
```

如果需要增加40 kW：

```text
PV1分30
PV2分10
```

即按：

\[
\Delta P_i=\frac{R_i}{\sum R_j}\Delta P_{req}
\]

为什么比平均分合理？

因为平均分20/20会让PV2直接从50→70到顶，而PV1仍有40 kW剩余能力；余量比例可以更平衡地使用当前可调能力。

**面试禁区：** 不能说“原算法是平均分，后来我改成余量分配”。原基础AGC已经是余量比例分配。

# 63. 为什么AGC还需要SOC硬约束？

正向增加净出力时，ESS要放电。

如果：

```text
SOC1≤SOC_min
```

则代码把ESS1向上放电上限改为0，不允许继续增加放电。

负向时，ESS要充电。

如果：

```text
SOC1≥SOC_max
```

则不允许继续增加充电。

所以SOC在基础AGC里主要是：

```text
Hard Constraint（硬边界）
```

不是复杂的连续SOC优化权重。

# 64. 为什么AGC要保存 `Ppv/Pess/Pev` persistent状态？

当前AGC不是每1 s都完全从零解一个优化问题。

它会在上一轮内部资源命令基础上继续调整。

因此保存：

```text
Ppv[2]
Pess[2]
Pev[2]
```

它们表达：

> **控制器认为当前六资源调度状态是什么。**

这后来会成为论文的重要问题：

```text
Controller internal allocation state
不一定等于
Physical executed state
```

# 65. 为什么EV内部 `Pev` 是正充电幅值，而输出是负pu？

内部为了方便：

```text
Pev=60 kW
```

表示“充电60 kW”。

但微网功率方向定义：

```text
负功率=负荷吸收
```

所以输出：

\[
P_{EV,pu}=-P_{ev}/P_{unit}
\]

例：

```text
Pev=60
Punit=100
→ 输出=-0.6 pu
```

因此面试看到EV“增加充电”时，模型命令数值反而会变得**更负**。

# 66. 为什么AGC是1 s，而Plant是100 μs？

控制时间尺度不同。

## Plant 100 μs

需要解析：

- PWM；
- 开关状态；
- 电流内环；
- 电磁暂态。

## AGC 1 s

处理：

```text
PCC系统级功率协调
```

设备功率本身有约秒级响应动态。

如果AGC也100 μs：

```text
上一条命令还没形成物理Pmeas
↓
AGC又看到误差
↓
继续叠加
↓
容易命令累积/过调
```

所以：

> **越靠近开关越快，越靠近调度越慢。**

# 67. 为什么基础AGC会出现PV和EV对冲？

当前算法主要依据：

```text
PCC总误差
+
内部历史命令
```

如果误差方向在多个AGC周期中来回变化：

```text
某轮先加PV
后面误差反向
→ 又加EV充电
```

它不一定优先彻底撤销前一类资源已有动作。

长期可能出现：

```text
PV大发电
+
EV大充电
```

但两者净抵消后：

```text
PCC仍接近目标
```

这说明两个非常重要的概念：

```text
PCC Tracking Correct
≠
Resource Coordination Optimal
```

和：

```text
系统级KPI正确
≠
设备级状态合理
```

不是。

```text
内部资源状态管理/最优性不足
```

# 69. 为什么不一开始就直接实现项目书里的MPC/PSO/动态权重？

研发要先建立Minimum Viable Closed Loop（最低可用闭环）：

```text
PCC能测
↓
总误差能算
↓
六设备能分配
↓
设备能执行
↓
PCC能回目标
```

规则型AGC：

- 确定；
- 可解释；
- 易调试；
- 易转C；
- 易做Golden对比。

复杂优化可以建立在可信工程底座上，而不应该在底层闭环尚未证明时把所有复杂度一次堆进去。

面试准确说法：

# 70. 15种策略究竟怎样从项目高级应用需求一步一步提炼？

每项业务需求先问六个问题：

```text
1. 这个功能解决什么问题？
2. 需要哪些测量/参数输入？
3. 正常与异常边界是什么？
4. 是否需要历史状态或计时？
5. 用什么metric量化严重程度？
6. 触发后希望系统做什么？
```

然后统一输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

这就是早期 `Advanced_Microgrid_15_Strategies` 的工程抽象思想。

# 71. 为什么统一为 `status/alarm/metric/cmd`？

如果每项功能单独拉十几根线，顶层模型会失控。

统一接口有利于：

- 批量日志；
- 测试；
- 显示；
- 后处理；
- 以后迁C。

四类量可以理解：

## status
当前功能处于什么状态/阶段。

## alarm
是否触发阈值事件。

## metric
“问题有多严重/指标是多少”。

## cmd
策略建议系统往哪个方向、调多少。

# 72. 为什么15个 `cmd` 不能直接相加？

因为它们物理含义不同。

例如：

```text
S3 cmd = 无功kvar
S8 cmd = 减载kW
S14 cmd = 黑启动阶段编号
S15 cmd = 模式切换请求
```

即使都是kW的S1/S4/S7，也可能一个是：

```text
主目标
```

另一个是：

```text
硬约束
```

所以：

> **“统一数组接口”只解决数据组织，不等于“控制命令可以数学相加”。**

这正是后来LOCAL15必须新增Normalizer/Arbiter/P-Q-Mode分域的原因。

# 80. 为什么S3 Q分配必须知道当前P？

# 89. 为什么实时化成为后续最大工程问题之一？

普通Simulink：

```text
1秒物理过程
算2秒也可以
```

实时仿真：

```text
每100 μs物理过程
必须在现实100 μs以内计算完
```

否则Target出现Overrun，仿真无法跟现实时间同步。

原六逆变器单任务约：

```text
970～981 μs/step
```

目标：

```text
100 μs/step
```

所以不是“优化一点代码”就够，需要任务级结构重构。

# 90. 为什么简单给一个SM设置4个CPU核没有自动快4倍？

因为一个强耦合电气系统本质上要解：

```text
一个大联立方程
```

如果方程当前步互相依赖：

```text
CPU1算一半
CPU2算一半
```

也要频繁等待彼此，不能自动实现真正并行。

所以原则：

> **先找到数学/物理上可以解耦的边界，再分CPU任务。**

# 91. Stubline为什么能够帮忙分核？

没有Stubline时：

```text
SM本步电压
依赖SS本步电流

SS本步电流
又依赖SM本步电压
```

需要同一步联立求解。

Stubline具有一个传播时间步，使两端可以使用上一拍边界信息：

```text
本步SM
← 已知边界历史

本步SS
← 已知边界历史
```

于是一个大网络可以拆成多个小网络独立计算。

# 92. 为什么普通Stubline方案不够好？

```text
+
```

# 94. PMIO / Stubline / OpComm三个概念为什么必须分开？

## PMIO

```text
物理建模接口
```

让不同实时子系统可以拥有物理电气端口。

## Stubline

```text
具有传播延时的电气解耦元件
```

真正打断同一步电气联立。

## OpComm

```text
普通数字信号跨任务通信
```

```text

```

因此：

```text
电气能量关系 → PMIO + Stubline
控制/测量数值 → OpComm
```

绝不能混。

# 100. 为什么V3.2要有 DISCONNECTED / WAIT_VALID / ENABLED 三状态？

网络连上不代表数据立刻可信。

### DISCONNECTED

没有有效连接。

### WAIT_VALID

连接已经恢复，但需要连续新鲜、合法数据确认。

### ENABLED

确认通信和测量满足条件后才允许外部控制。

为什么不能：

```text
TCP连上 → 立刻控制
```

因为刚恢复时可能还有：

- 旧寄存器；
- 心跳未更新；
- 模型未Execute；
- 测量越界；
- 数据未同步。

安全状态机就是防止“通信刚通就误控”。

```text
错误会继续积累
```

所以：

## HOLD

阻止普通资源分配状态继续推进。

## RECONSTRUCTION

使用执行估计把AGC内部：

```text
Ppv/Pess/Pev
```

重新对齐现实。

## RECOVERY

不是瞬间重新施加全部PCC调节量，而是逐步恢复。

因此论文主线不是“HOLD创新”，而是：

```text
Execution Evidence
→ Coordination State Management
→ Allocation-State Reconciliation
→ Effective-Capability Reallocation
→ Controlled Re-entry
```

# 113. 面试专项：PVmax完整回答模板

> **为什么会有PVmax？**  
> 项目要求做PCC有功协调、PV平滑和新能源最大化消纳，所以控制器不仅要知道PV现在实际发了多少，还必须知道当前天气条件下“最多还能发多少”。额定功率只是硬件铭牌上限，不能反映光照随时间变化；Pmeas又只是当前实际输出，不能体现尚未利用的调节裕度。因此我们定义PVmax作为当前最大可用功率。仿真阶段为了避免把研究重点转成复杂PV组件建模，用一条归一化PV profile描述日照资源，通过时间节点线性插值得到 \(g_{PV}(t)\)，再乘设备额定功率得到 \(P_{PV,max}=P_{unit}g_{PV}(t)\)。PVmax进入AGC计算光伏剩余headroom，也进入S6平滑和S12新能源消纳。当前两路PV采用同一profile属于Baseline简化，接口仍保留PVmax1/2两个独立输入，工程上可以换成逆变器available power、辐照度模型或短期预测。

如果继续追问：

### “PVmax和Pmeas最大区别？”

```text
PVmax = 能力上限
Pmeas = 实际结果
```

### “为什么不用额定功率？”

额定功率不随太阳变化。

### “为什么不用实际出力？”

实际出力可能是控制器主动限出来的，不能代表剩余可用能力。

### “PVmax突然下降怎么办？”

先把PV指令限制到新的能力范围，再让ESS/EV等承担剩余PCC任务。

# 114. 面试专项：SOC完整回答模板

> **为什么需要SOC？**  
> 储能和普通发电资源最大的不同是它除了功率约束还有能量约束。100 kW额定功率只告诉我瞬时能多快充放，不告诉我还能持续多久，所以必须用SOC表示当前剩余能量相对于额定容量的比例。根据 \(P=dE/dt\)，离散以后 \(\Delta E=P\Delta t\)，再除以额定kWh容量得到SOC变化。项目内部规定ESS正功率为放电、负功率为充电，因此当前简化公式是 \(SOC_{k+1}=SOC_k-P_{ess}\Delta t/(E_{nom}3600)\)，3600是秒到小时的单位换算。代码保存上一时刻SOC和时间，Reset时恢复初值，并把SOC限制在安全上下限。前期为了快速建立闭环用ESS命令积分，后续加入Router、Safety和Execution Fault以后，我又把SOC状态源对齐到FINAL_APPLIED ESS命令，使内部能量状态尽量跟真实Plant执行一致。当前这是微网协调控制用的简化能量模型，不是高精度BMS SOC估计算法，而且实际代码未显式加入充放电效率。

如果继续追问：

### “为什么有负号？”

正ESS功率代表放电，能量应该减少。

### “为什么有3600？”

kW×秒需要除3600才能换成kWh。

### “为什么不用0～1全范围？”

工程运行留安全裕量，当前Baseline用0.2～0.9。

### “为什么后来不用AGC命令直接积分？”

因为上游命令不一定等于最终实际执行。

# 116. 面试专项：为什么功率外环→电流参考→电压参考？

> 在PLL同步的dq坐标系中，d轴电流主要对应有功，q轴电流主要对应无功，所以功率外环比较Pref/Pmeas和Qref/Qmeas后，最自然的输出是Id/Iq参考。电流本身不能被直接“命令”，它由滤波电感两端电压差决定，\(Ldi/dt=v_{conv}-v_{grid}-Ri\)，所以电流内环再根据Id/Iq误差算出Vd/Vq电压指令，最后经调制和PWM决定IGBT开关。也就是说，功率环回答“为了达到目标功率需要多少电流”，电流环回答“为了形成目标电流需要施加多少电压”。

# 118. 面试专项：基础AGC怎么写出来的？

> 联络线控制的最基本问题就是目标PCC功率和实际PCC功率之间的差，因此先定义 \(dP=P_{target}-P_{pcc}\)。如果误差在死区内不动作；如果需要提高微网净出力，先用PV剩余可用功率，再让SOC允许的ESS放电，最后减少EV充电；如果需要降低净出力，则先增加EV充电，再给ESS充电，最后降低PV。两台同类资源按当前剩余裕度比例分配而不是简单均分。这个算法有persistent Ppv/Pess/Pev状态，所以它是一套状态型规则协调器。它的定位是工程Baseline，用来先建立PCC闭环、实时化和板端C基线，不等价于立项书中完整的MPC/多目标动态权重最终算法。

# 119. 面试专项：为什么一开始不直接做MPC/PSO？

> 因为复杂优化必须建立在可信Plant、测量、执行和通信底座上。研发先要建立最低可用闭环，证明PCC能测、总需求能算、六设备能执行、PCC能回目标；规则型AGC结构确定、易验证、易转C，非常适合作为工程基线。MPC、日前PSO、多目标优化属于更高层或后续优化方法，不能在基础系统还没有实时跑通时把所有复杂度一次堆进去。

# 120. 面试专项：为什么100 μs，而AGC是1 s？

> 100 μs对应的是开关级Plant和本地快速控制，需要解析PWM、电流环和电磁暂态；AGC是系统级慢控制，调的是PCC功率任务，而且PV/ESS/EV的功率响应本身接近秒级。如果AGC也按100 μs更新，设备还没完成上一条命令，上层就会重复看到误差并继续累加。所以多时间尺度设计是越靠近开关越快，越靠近调度越慢。

# 121. 面试专项：为什么最终要1SM+3SS？

> 这不是项目书规定的，而是OP5700真实算力约束倒逼出来的。原六逆变器单任务约970～981 μs，无法在100 μs实时；单SM设置多核也没有自动解决强耦合电气方程。后来我们采用官方Transformer Differential Stubline结构，把变压器次级漏阻抗迁入带一步传播延时的Stubline，逐级从单EV扩展到2+2+2，最终形成1SM+3SS。同类两台资源分别放在EV/ESS/PV三个SS，高压公共网络和PCC留在SM，实际J2在100 μs下长期Overrun=0，所以这是通过工程验证得到的可行任务分区。

# 122. 面试专项：为什么“Build PASS”不等于模型正确？

> Build只证明模型可以被工具链编译。分核过程中我们曾遇到PCC数百kW异常和EV功率几十pu，说明虽然结构能算，物理拓扑仍可能接错。后来用拆分前标准模型shiyansan做数值Golden，重新核对PCC边界、五段馈线、prim方向和EV1测量源，恢复后两者PCC均值只差约0.11 kW。所以我会把数值正确、物理正确、功能正确和实时正确分开验证。

# 123. 面试专项：为什么先Shadow再Takeover？

> 外部Board第一次加入时，如果同时引入通信、C算法和真实设备接管，一旦系统异常很难知道根因。所以V4先让Board真实读、真实算、真实写回，但不控制设备，专门验证数据、符号、状态机、candidate/commit和日志；这些通过后V5才把板端40001～40006真正接到六设备Pref。这种先Shadow再Takeover的方式本质是降低一次改动的风险和故障定位范围。

# 124. 面试专项：candidate / commit为什么是工业控制器关键？

> 算法算出命令不等于命令已经成功发布。AGC本身有历史状态，如果我先推进内部状态但FC16写失败，下一轮控制器就会以为一个Plant根本没收到的命令已经执行过。因此我们把正式状态复制成candidate，在candidate上计算，只有输出合法、编码成功并且FC16完整写成功后才commit。这样控制器的正式历史只代表成功发布的控制内容。再往后还要区分u_commit和u_applied，因为发布成功也不代表设备一定形成了相同物理状态。

# 127. 3分钟面试总述版

> 我做的是一个2PV、2ESS、2EV的并网光储充微电网协调控制与硬件在环项目。项目从立项阶段就要求控制器具备联络线功率、防逆流、AGC/AVC、平滑、削峰填谷、孤岛、黑启动和并离网等高级功能，并最终在RT-LAB和外部控制板上验证。我们先从Plant出发：建立10 kV上级电网、PCC和六台功率电子资源，每台资源通过两电平变流器、滤波器、变压器和本地GFL/GFM控制接入网络。上层为了协调资源，用PVmax表示光伏当前可用能力，用SOC表示储能跨时间能量状态，再用基础AGC根据PCC偏差和资源边界生成六路Pref。高级应用前期统一成15项status/alarm/metric/cmd判断接口，我后续重点把它们继续工程化成有功、无功、辅助和模式安全几个真实执行域。
