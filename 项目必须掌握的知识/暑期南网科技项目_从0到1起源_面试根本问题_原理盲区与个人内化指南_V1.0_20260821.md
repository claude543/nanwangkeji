# 第一部分｜项目最初到底要求了什么

# 1. 初始项目文件给的是“问题与功能”，不是最终代码

从项目执行计划看，最初的四类核心任务是：

```text
1. 控制策略设计优化与模型构建
2. RT-LAB高保真实时仿真模型搭建
3. 控制策略仿真实现与测试
4. 控制代码生成或向嵌入式团队提供详细实现指导
```

也就是说：

> **算法本身本来就是研发任务，而不是项目方已经给好、你只负责运行。**

初始高级应用需求包括：

```text
平滑出力
需量控制
防逆流
联络线功率控制
AGC / AVC
低压/低频减载
孤岛检测
削峰填谷
周期计划
并离网无缝切换
新能源最大化消纳
黑启动
主配微协同
多目标优化
动态扩容
支持定制
```

这些是：

```text
“系统应该具备什么能力”
```

而不是：

```text
“算法必须写成第几行MATLAB”
```

---

# 2. 项目初始文档对算法只规定到“路线级”

例如项目最初提出：

## 日前优化

```text
历史数据
↓
场景生成
↓
优化模型
↓
购电成本 + 储能寿命成本
↓
功率平衡 / SOC / 联络线约束
↓
启发式算法求解
```

甚至提出可以采用：

```text
PSO（粒子群）
或其他启发式/人工智能算法
```

## 实时控制

提出：

```text
MPC（模型预测控制）
用于短时域滚动优化

Droop（下垂）
用于频率/电压支撑

孤岛检测
并离网切换
防逆流
动态扩容
```

注意：

> 这些是“算法家族/方法路线”。

它并没有给出：

```text
具体状态变量
具体阈值
具体权重
完整控制器方程
C接口
数据结构
具体资源优先级
```

这些仍需要研发过程中设计。

---

# 3. 产品级架构也是“方向约束”，不是我们的RT-LAB模型结构

公司立项书中，最终产品的软件架构目标甚至是：

```text
Linux + RTOS双系统
```

其中：

```text
Linux：
全局优化
协议
数据
业务

RTOS：
硬实时控制
保护
并离网
安全逻辑
```

这和我们暑期阶段实际使用的：

```text
AArch64 Linux控制板
+
OP5700实时Plant
+
Modbus TCP
```

不是同一个层次。

必须区分：

```text
产品最终架构
≠
当前算法原型/HIL验证架构
```

这是以后面试非常容易被追问的地方。

# 第二部分｜15种策略最初是怎么“长出来”的

# 4. 原始15策略不是凭空来的

最合理的来源链是：

```text
项目功能需求
↓
每个功能需要监测什么？
↓
什么时候算“触发”？
↓
用什么指标描述严重程度？
↓
触发以后系统希望做什么？
↓
把它抽象成统一接口
↓
status / alarm / metric / cmd
```

这就是早期：

```text
Advanced_Microgrid_15_Strategies
```

的本质。

---

# 5. 为什么早期设计成四组15维向量

因为15个功能完全不同。

如果每个策略都单独拉：

```text
输入
输出
告警
状态
指标
命令
```

模型会非常混乱。

因此早期原型设计了统一接口：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

例如：

```text
S4 防逆流

status(4)
→ 当前策略状态

alarm(4)
→ 是否发生反送越限

metric(4)
→ 超出限制多少kW

cmd(4)
→ 建议抑制多少kW
```

这个设计特别适合：

```text
功能验证
批量测试
日志记录
统一后处理
```

但它有一个天然限制：

> **cmd(1)～cmd(15)不是同一种物理量，因此不能直接作为最终设备命令。**

这正是后来LOCAL15必须增加：

```text
Normalizer
Arbiter
P/Q/Mode分域
AGC
Execution Mapper
Router
```

的原因。

---

# 6. 原15策略和项目初始要求不是严格1:1

这是你以后一定要会讲的。

| 原策略 | 功能 | 初始需求是否直接出现 |
|---|---|---|
| S1 | 需量控制 | 是 |
| S2 | AGC/PCC跟踪 | 部分对应AGC/联络线 |
| S3 | AVC | 是 |
| S4 | 防逆流 | 是 |
| S5 | 防孤岛 | 是 |
| S6 | 平滑出力 | 是 |
| S7 | 联络线功率控制 | 是 |
| S8 | 低压/低频减载 | 是 |
| S9 | 削峰填谷 | 是 |
| S10 | 周期计划 | 是 |
| S11 | 自发自用/余电上网 | **属于工程扩展，不是执行计划中的独立原始条目** |
| S12 | 新能源最大化消纳 | 是 |
| S13 | 多目标优化 | 是 |
| S14 | 黑启动 | 是 |
| S15 | 并离网无缝切换 | 是 |

与此同时，项目初始要求中的：

```text
主配微协同
动态扩容
支持定制
```

并没有简单变成：

```text
S16 / S17 / S18
```

所以：

> **“15策略”是研发团队对需求进行的一次具体功能映射与原型化设计，不是合同原文天然规定的15个函数。**

---

# 7. 为什么原始15策略很多看起来比较“简单”

因为它们最初的定位不是最终产品控制器，而是：

> **高级应用策略判断/验证层。**

例如：

```text
防逆流：
检测越界 → 算抑制量

低压低频：
判断阈值 → 给减载阶段

黑启动：
按时间/状态推进阶段

S15：
识别切换条件 → 输出切换请求
```

这些逻辑主要在回答：

```text
“当前应该做什么？”
```

而不是完整解决：

```text
“六台设备最后分别输出多少P/Q？”
“PCC什么时候真实跳开？”
“GFM由谁建立？”
“重同步如何闭合？”
```

所以后来的LOCAL15其实是在完成：

```text
Strategy Judgement
策略判断

↓

Execution Control
真实执行控制
```

之间缺失的一大段。

# 第三部分｜基础AGC最初是怎么来的

# 8. 项目为什么天然需要一个基础AGC

微电网要让PCC跟踪目标，本质问题非常简单：

```text
目标交换功率
P_target

减去

实际交换功率
P_PCC
```

得到：

```text
dP = P_target - P_PCC
```

这个量回答：

> 整个微网还需要多调多少有功？

但这还不是设备命令。

接下来必须回答：

```text
PV调多少？
ESS调多少？
EV调多少？
```

因此基础AGC实际上包含两个层次：

```text
PCC Error
↓
Total Regulation Requirement

+

Resource Allocation
↓
Six Device Pref
```

---

# 9. 为什么最早采用相对简单的资源优先级

基础原型采用：

```text
需要增加微网净出力：
PV
→ ESS放电
→ EV减少充电

需要降低微网净出力：
EV增加充电
→ ESS充电
→ PV降出力
```

这是一种很典型的：

```text
规则型协调器
```

优点：

```text
简单
确定
容易调试
容易验证
容易转C
容易解释
```

缺点：

```text
不是全局最优
可能产生历史命令累积
可能产生资源对冲
经济性/寿命没有显式优化
```

因此：

> **它非常适合作为工程Baseline，但不是项目立项书中“多目标动态权重最优控制”的最终高级算法。**

---

# 10. 为什么AGC还必须知道PVmax和SOC

只知道：

```text
dP = 20 kW
```

还不够。

因为：

```text
PV可能没有20 kW余量
ESS可能SOC太低
ESS可能SOC太高
EV可能已经不能再调
```

所以资源分配必须计算：

```text
当前理论可调区间
```

例如：

```text
PV upward headroom
= PVmax - Pcurrent

ESS discharge ability
受SOC_min限制

ESS charge ability
受SOC_max限制
```

这就是：

```text
控制目标
+
物理约束
```

结合起来的最简单形式。

---

# 11. 当前基础AGC与“传统电力系统AGC”不是完全同一概念

这是面试特别容易问的。

传统大电网AGC通常强调：

```text
ACE
频率偏差
联络线偏差
机组二次调频
```

而本项目所谓基础AGC主要是：

```text
微电网PCC有功目标跟踪
+
六资源有功协调分配
```

所以面试不要只说：

> “AGC就是自动发电控制。”

应该说：

> 本项目沿用了AGC这个名称，但实际实现更接近微电网二次有功/联络线功率协调控制器，以PCC功率偏差为主误差，在PV、ESS和EV之间分配有功调节任务。

# 第四部分｜分核以前的六逆变器模型从哪里来

# 12. 初始项目确实要求“光储充实时模型”

项目执行计划明确要求：

```text
光储充Simulink模型
+
RT-LAB高保真实时模型
+
HIL验证
```

并且对象本身就是：

```text
PV
ESS
充电设备
PCC
```

6月29日的早期验证模型已经明确采用：

```text
2 PV
+
2 ESS
+
2 EV/充电桩
```

所以：

> **2PV+2ESS+2EV这个系统级对象不是分核时临时发明的。**

---

# 13. 但“1SM+3SS”绝对不是项目初始要求

初始文件没有要求：

```text
SM_Master
SS_Slave
SS_Slave2
SS_Slave3
18条Stubline
```

这些是后续为了满足：

```text
OP5700
100 μs实时运行
```

才产生的工程实现方案。

原六逆变器模型最开始更像：

```text
一个完整Simulink电气网络
+
六台变流器
+
六套本地控制
+
PCC
+
上级电网
+
上层AGC/策略
```

当它真正放到RT-LAB以后，单任务计算时间太长：

```text
约970～981 μs / step
```

而目标：

```text
100 μs / step
```

显然无法实时。

于是才产生：

```text
“怎么把电气网络拆成可并行实时任务？”
```

这个问题。

---

# 14. 为什么不能随便把Simulink模型切成几个Subsystem

因为电气网络有：

```text
瞬时电压电流耦合
```

如果只是普通信号拆分：

```text
Subsystem A
Subsystem B
```

并不能让电力网络求解器真正分开。

要形成真正独立任务，需要：

```text
电气解耦
```

因此后来使用：

```text
Stubline
```

本质是：

> 用具有传播延迟的线路等效，把“同一时刻必须联立求解”的电气网络切成“可以使用上一传播信息独立计算”的网络区域。

---

# 15. 为什么最后是1SM+3SS、每个SS两台设备

它不是理论上唯一的方案。

它是经过：

```text
单EV
→ 2EV
→ 多SS
→ 2+1+1
→ 2+2+1
→ 2+2+2
```

逐步验证出来的工程结构。

最终：

```text
SM
→ 公共电网/PCC/公共母线/测量

SS1
→ EV1+EV2

SS2
→ ESS1+ESS2

SS3
→ PV1+PV2
```

这种分法同时满足：

```text
结构清晰
同类设备归组
任务负载较均衡
实际Build/Execute成功
```

所以它是：

```text
实验验证得到的工程架构
```

而不是项目最初的一条需求。

---

# 16. 原六逆变器设备模型本身为什么长成“两电平+滤波+变压器+控制器”

这主要来自：

```text
功率电子变流器的物理实现
+
并网控制的一般结构
```

一个典型并网变流器的因果链：

```text
Pref / Qref
↓
功率控制器
↓
dq电流参考
↓
电流内环
↓
dq电压参考
↓
abc调制电压
↓
PWM
↓
IGBT/开关桥
↓
滤波
↓
变压器/线路
↓
PCC
```

因此这些不是“项目经理要求模型里一定有某个Mux”。

它们来自：

```text
真实设备物理
+
控制理论
+
实时仿真需要
```

# 第五部分｜如果今天让你从0开始，这个项目应该怎么做

# 17. 第一步永远不是打开Simulink

真正正确的第一步：

# **Requirements Decomposition（需求分解）**

先回答：

```text
系统要解决什么业务问题？
```

例如：

```text
PCC不能逆流
PCC要跟计划
电压不能越限
频率跌落要减载
断网要能孤岛
全黑后要能恢复
新能源尽量不弃
```

然后形成：

```text
功能需求矩阵
```

---

# 18. 第二步：定义系统边界

明确：

```text
谁是Plant？
谁是Controller？
谁是上级系统？
谁是可控资源？
谁只是测量？
```

本项目可以定义：

```text
Plant
=
2PV + 2ESS + 2EV + Grid + PCC + Load

Controller
=
微网协调控制器

Northbound
=
主站/调度

Southbound
=
PV/ESS/EV设备
```

---

# 19. 第三步：冻结符号、单位和Base

在任何算法以前必须先冻结：

```text
PCC正负方向
设备功率正负方向
kW / pu
Q正负
SOC
电压基准
频率基准
```

本项目后来出现过策略方向BUG，根本原因就是：

> 符号合同没有一开始统一到底。

---

# 20. 第四步：先设计电气Plant，不急着做15策略

先建立：

```text
1台变流器
↓
验证

1PV
1ESS
1EV
↓
验证

2PV+2ESS+2EV
↓
验证

PCC / Grid / Loads
↓
验证
```

每台设备都先验证：

```text
Pref阶跃
→ Pmeas方向正确

Qref阶跃
→ Q方向正确

GridOn
Droop
GFL/GFM
```

---

# 21. 第五步：建立“最低可用闭环”

先不要做15策略。

先做：

```text
PCC Target
↓
基础AGC
↓
六设备Pref
↓
PCC
```

只要这个闭环都不成立：

> 上层高级策略没有执行载体。

---

# 22. 第六步：把高级应用拆成“检测/决策”和“执行”

这是本项目早期最容易混掉的地方。

例如防逆流：

```text
检测层：
PCC是否外送越限？

决策层：
需要修正多少kW？

执行层：
这20kW由PV降多少？
ESS充多少？
EV加多少？
```

原始15策略主要实现前两层。

LOCAL15后来补齐第三层。

---

# 23. 第七步：定义策略优先级和冲突关系

因为：

```text
削峰填谷
新能源消纳
联络线跟踪
防逆流
```

可能同时要求不同动作。

所以必须分：

```text
主目标
硬约束
辅助动作
安全模式
```

例如：

```text
S7/S9/S10/S12/S13
→ 主目标

S1/S4/S11
→ 硬约束

S6/S8
→ 辅助动作

S5/S14/S15
→ 模式/安全
```

---

# 24. 第八步：定义统一控制接口

对每个控制周期定义：

```text
Input
State
Config
Output
Diagnostics
```

这一步越早做，后面转C越容易。

---

# 25. 第九步：再做离线Simulink功能验证

此时验证：

```text
Trigger
→ Decision
→ Arbitration
→ Command
→ Plant
→ Response
```

而不是只看：

```text
cmd非零
```

---

# 26. 第十步：在做RT-LAB之前先估算实时预算

如果：

```text
Ts = 100 μs
```

那么每个实时任务必须：

```text
execution time < 100 μs
```

而且需要留裕量。

所以应该尽早：

```text
Benchmark
```

而不是整个模型做完以后才发现：

```text
970 μs
```

跑不了。

```text

计算复杂度
设备分组
通信边界
```

```text

Build
↓
Load
↓
Execute
↓
Overrun
```

# 35. 电气与控制类

## Q6. PCC为什么是整个项目最核心的观测点？

因为它代表：

```text
微网整体
与
上级电网
```

之间的净交换。

内部六设备怎么互相抵消，最终上级电网看到的是PCC。

---

## Q7. 为什么控制PCC功率就可以协调六设备？

功率平衡：

```text
P_PCC
≈
ΣP_source
+
ΣP_storage
+
ΣP_controllable_load
+
其他负荷
```

调节可控资源，就能改变净交换。

---

## Q8. Pref最终是怎么变成真实Pmeas的？

必须能完整说出：

```text
Pref
↓
功率外环
↓
dq电流参考
↓
电流内环
↓
dq电压指令
↓
abc
↓
PWM
↓
两电平变流器
↓
滤波器
↓
变压器/线路
↓
Pmeas
```

这是非常典型的面试追问。

---

## Q9. 为什么功率外环输出电流参考，而电流内环输出电压参考？

因为：

```text
功率主要由电压、电流决定
```

在电网电压已知的dq坐标系中：

```text
P/Q
可以通过控制Id/Iq实现
```

所以：

```text
P/Q外环
→ Id/Iq*

电流内环
→ Vd/Vq*
```

再由PWM实现电压。

---

## Q10. GFL和GFM是什么？为什么孤岛时要GFM？

GFL：

```text
跟着已有电网电压和频率运行
```

GFM：

```text
自己建立电压和频率基准
```

孤岛后没有强电网基准，因此至少需要一个构网源。

---

## Q11. 为什么通常选ESS做GFM主机？

因为ESS：

```text
功率双向
响应快
能量可控
适合建立电压/频率
```

PV受光照约束，EV通常是负荷。

---

## Q12. 为什么Q分配必须考虑当前P？

逆变器受：

```text
P² + Q² ≤ S²
```

约束。

P占得越多，剩余Q能力越小。

---

## Q13. 功率和能量有什么区别？SOC为什么不能直接根据Pref瞬间改变？

功率：

```text
kW
= 能量变化速率
```

SOC来自：

```text
功率对时间积分
```

所以必须考虑：

```text
P × Δt / E_nom
```

---

## Q14. 为什么SOC一定要跟FINAL_APPLIED，而不能跟某个AGC候选输出？

因为：

> SOC是物理状态，必须跟真正施加到储能的功率一致。

否则会出现：

```text
模型认为在放电
实际却在充电
```

# 36. AGC类

## Q15. 你们基础AGC的控制变量和被控变量分别是什么？

被控：

```text
PCC active power
```

操纵量：

```text
6路设备Pref
```

---

## Q16. 为什么AGC采用1 s更新，而不是100 μs？

因为：

```text
Plant电气控制
≈ 100 μs

设备功率响应
≈ 1 s量级

AGC属于上层慢控制
```

如果AGC远快于Plant响应，会反复根据尚未完成的响应继续累加命令。

---

## Q17. 为什么你们测试过0.1 s AGC以后觉得不合理？

因为设备还没来得及响应，上层就再次认为“误差还没消失”，继续叠加调节量。

这会造成：

```text
command accumulation
```

甚至过调。

---

## Q18. 为什么基础AGC会出现PV和EV对冲？

因为基础算法根据：

```text
当前PCC偏差
+
历史资源命令
+
方向优先级
```

逐轮增量调整。

一旦误差换方向，它可能调用另一类资源，而不是优先撤销上一方向已有命令。

因此长期可能形成：

```text
PV大发电
+
EV大充电
```

净PCC仍然正确，但内部资源互相抵消。

---

## Q19. 这说明AGC失败了吗？

不是。

它说明：

```text
PCC tracking功能可以成功
```

但：

```text
resource coordination optimality
存在缺陷
```

这两件事必须区分。

# 37. 实时仿真类

## Q20. 普通Simulink仿真和实时仿真的本质区别是什么？

普通仿真：

```text
计算多快都可以
```

实时仿真：

```text
每个100 μs计算步
必须在真实100 μs以内完成
```

否则：

```text
Overrun
```

---

## Q21. 为什么你们必须做100 μs？

因为电力电子开关、控制器和电磁暂态需要较高时间分辨率。

但严格来说：

> 100 μs是当前模型与平台权衡后的工程选择，不是所有电力电子HIL唯一正确的步长。

---

## Q22. 原模型为什么无法直接跑100 μs？

一个任务中六台逆变器、电力网络和控制器的单步计算接近：

```text
~970 μs
```

远大于：

```text
100 μs
```

---

## Q23. 给SM设置4核为什么没自动加速？

因为：

> 一个强耦合电气网络求解并不会因为“有4个CPU核”自动变成4个独立任务。

并行化首先需要：

```text
可解耦的任务边界
```

---

## Q24. Stubline是什么？为什么能帮助分核？

它不是普通信号延迟。

它是：

```text
带传播时延的电气线路等效
```

利用传播延迟打断瞬时电气耦合，使两个网络区域可以在不同任务中计算。

---

## Q25. Stubline会不会改变原系统物理特性？

会存在模型变化风险。

所以必须做：

```text
离线等效
+
P/Q
+
设备响应
+
PCC
```

对比。

这就是为什么分核不是单纯软件优化。

---

## Q26. 为什么最终选择1SM+3SS？

不是因为理论证明“3SS最优”。

而是经过逐层Build和实时性能验证后：

```text
结构清晰
负载足够低
100 μs
Overrun=0
```

的一套可行解。

---

## Q27. Overrun=0能证明什么，不能证明什么？

能证明：

```text
实时任务没有超过时间预算
```

不能证明：

```text
电气模型物理上一定正确
控制算法一定正确
```

所以还必须做物理等效和功能验收。

## Q32. Heartbeat和普通数据有什么区别？

普通数据告诉你：

```text
值是什么
```

Heartbeat告诉你：

```text
对方现在是不是还活着、还在更新
```

寄存器里保留一个旧值不等于通信正常。

## Q33. 为什么FC16失败后不能马上更新AGC内部正式状态？

因为：

```text

```

但：

```text

```

会造成控制器状态和物理状态分叉。

## Q34. candidate / pending / commit分别是什么？

```text
candidate
算出来了

pending
准备发送/等待确认

commit
确认完整发送成功后
正式成为控制器历史
```

---

## Q35. reconnect为什么不能等于reset？

通信断线只是：

```text
网络状态变化
```

不意味着：

```text
算法物理历史不存在
```

如果每次TCP重连都把控制器状态清零，会造成不必要的突跳。

---

## Q36. 为什么要区分u_calc / u_commit / u_applied？

因为现实系统存在：

```text
算出来
≠
成功发送
≠
设备真实执行
```

这三个层次。

# 结尾：你应该怎样重新认识这段项目经历

你不是从一张白纸开始做这个项目。

这是事实，不需要回避。

真正应该建立的认知是：

```text
项目需求
↓
前期团队已经形成第一版模型和算法原型
↓
你接手一个“能离线运行、但远未工程闭环”的系统
↓
在真实平台约束下不断暴露问题
↓
重新理解物理、控制、实时、通信和软件
↓
把原型逐层推向可实时、可闭环、可板端、可验证、可交付
```

对于求职而言，这并不比“从零写模型”价值低。

很多真实工程岗位的核心能力正是：

> **接手一个别人做过但不够完善的复杂系统，读懂它、发现隐含假设、找到真实瓶颈、建立验证方法、逐步重构并最终交付。**

这恰恰是本项目最值得你带走的能力之一。
