# 2. 8月16日第一件重要事情：修复SOC必须跟“真实最终执行命令”一致

## 2.1 发现了什么问题

Stage07后，ESS真实Plant已经在听：

```text
AA15_FINAL_APPLIED_ESS1
AA15_FINAL_APPLIED_ESS2
```

但SOC积分支路仍可能沿用旧的：

```text
V5A_FINAL_ESS1
V5A_FINAL_ESS2
```

这会形成非常严重但很隐蔽的内部不一致：

```text
Plant真实按LOCAL15放30 kW

但SOC模型可能仍按旧V5-A命令80 kW积分
```

那么下一步的：

```text
SOC限制
ESS可用能力
AGC资源分配
后续论文执行状态判断
```

都会被污染。

## 2.2 怎么修

SOC输入统一改为：

```text
ESS1 SOC ← AA15_FINAL_APPLIED_ESS1
ESS2 SOC ← AA15_FINAL_APPLIED_ESS2
```

也就是：

> **内部状态必须跟随最终真正进入Plant的命令，而不是某个上游候选控制源。**

## 2.3 你要从这个问题中真正学会什么

这不是一个“接错线”的小问题。

它是整个项目最重要的一类工程思维：

```text
控制器想执行什么
≠
最后真正执行了什么
```

真正做系统时必须追踪：

```text
u_calc
u_commit
u_applied
Plant State
```

内部SOC、执行评估、恢复逻辑都应该尽可能基于“真实最终执行侧”的语义，而不是基于某个早期控制器内部变量。

# 4. 8月16日第三件大事：Stage09让S3 AVC真正控制六设备Qref

原S3以前会算：

```text
qCmd
```

但并不等于六台逆变器的Qref真的被它控制。

Stage09建立：

```text
S3 AVC Normalizer
↓
Q Capability Allocator
↓
6 × FINAL_QREF
↓
六台设备Mux input7
```

## 4.1 为什么不能“总Q / 6”

因为逆变器有：

```text
P² + Q² ≤ S²
```

如果一台设备当前P已经接近满功率，它的剩余Q能力很小。

所以当前Q能力：

```text
Qcap_i ≈ sqrt(max(1 - Pref_i², 0))
```

再按能力比例分配。

## 4.2 Q方向怎么验证

增加：

```text
CFG15_Q_SIGN_GAIN
```

而不是根据记忆猜：

```text
“正Q一定升压”
```

最终真实Plant验证：

```text
CFG15_Q_SIGN_GAIN = +1
```

方向正确。

## 4.3 为什么这一点后来对BOARD15特别重要

因为到了BOARD15 C05，我们仍然保留：

```text
总Q请求
↓
当前最终P candidate
↓
Qcap
↓
六路Qref
```

这说明8月16日LOCAL15的真实工程语义，后来直接成为8月18日C迁移的Golden语义。

# 9. Stage11最重要的安全修正：communication-only不能直接解列

原S5算法中：

```text
V异常
或
f异常
或
通信异常
```

都可能让原策略报警。

如果机械把S5 cmd直接接PCC Breaker，就可能出现：

```text
通信断一下
→ 直接物理解列
```

这既不安全，也会把以后所有通信异常实验变成“断网=离网”，根本失去研究意义。

所以真实物理解列资格重新定义：

```text
electrical_bad
=
v_bad OR f_bad
```

真正：

```text
S5_execute
```

只由电气异常产生。

通信异常：

```text
可以报警
可以记录
可以影响上层控制资格

但不能单独打开PCC
```

这条后来在BOARD15 C06、C09、C10都被继续保留。

# 10. Stage12：GFL / GFM接口真正冻结

```text

input5 Droop_On
input6 Pref
```


只是开启下垂控制，不等于“设备已经GFM”。

```text

```
