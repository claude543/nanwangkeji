# V3.2三状态状态机、连续有效周期，以及异常退出与恢复

## V3.2第四轮内化

上一轮解决了：

```text
40115 MODEL_STATUS：
模型当前是否具备外部控制条件

40116 RTLAB_HEARTBEAT：
RT-LAB数据是否仍在持续刷新
```

这一轮把这些判断装进板子侧的三状态状态机：

```text
DISCONNECTED
WAIT_VALID
ENABLED
```

本轮不是学习程序怎么写，而是彻底理解：

> 板子从启动到允许外部控制，为什么必须经过这些状态；每个状态能做什么、不能做什么；出现不同异常时应该退到哪里；恢复以后为什么不能立即重新投入。

V3.2要求板子建立明确的通信与数据有效性状态机，程序启动进入 `DISCONNECTED`，连接成功后先进入 `WAIT_VALID`，只有全部条件连续满足默认3个周期后才能进入 `ENABLED`。

---

## 一、三种状态分别代表什么

### 1. `DISCONNECTED`

表示板子与OP5700之间没有一条可以正常使用的Modbus TCP连接。

此时可能是：

```text
程序刚启动
尚未连接服务器
网线断开
OP5700未监听1502端口
连续通信失败后主动关闭连接
正在等待重新连接
```

这个状态下：

- 板子本地外部使能必须为0
- 不能认为RT-LAB测量数据有效
- 不能认为板子命令已经送到RT-LAB

由于没有连接，板子通常无法真正向RT-LAB写入，`40010 = 0`。所以RT-LAB还必须依靠 `40012 BOARD_HEARTBEAT` 停止变化来独立发现板子已经失联。

### 2. `WAIT_VALID`

表示Modbus TCP连接已经建立，但系统还没有证明当前数据和控制条件连续可靠。这是一个"已连接、未授权"的状态。

此时板子可以：

- 读取40101～40116
- 解码测量量
- 检查MODEL_STATUS
- 检查RT-LAB心跳
- 检查五个核心测量点
- 向RT-LAB写测试值
- 更新CMD_SEQ
- 更新BOARD_HEARTBEAT
- 记录连续有效周期

但必须保持 `40010 EXT_AGC_ENABLE = 0`。因此，即使40001～40009已经写进RT-LAB，也只是测试数据，不得被模型作为有效外部控制命令采用。

### 3. `ENABLED`

表示连接、模型状态、RT-LAB心跳、核心测量和人工投入请求等条件已经连续验证通过，板子允许RT-LAB使用外部命令。此时 `40010 = 1`。

但是 `ENABLED` 不是永久状态。板子每个通信周期仍要重新检查所有条件。只要出现一次明确异常，就必须立即退出 `ENABLED`。

---

## 二、用"进入厂区"的故事理解三个状态

把OP5700看成一座重要工厂，板子是一名外部调度员。

### `DISCONNECTED`：还没进厂门

调度员与工厂没有联系。可能是电话没接通、通信线路断开或者厂区尚未开放。此时调度员连工厂的实时情况都不知道，更不能发控制命令。

### `WAIT_VALID`：已经进了门卫室，但还没获得操作许可

电话已经接通，但门卫还要核实：

```text
工厂是否正在运行
仪表数据是否有效
外部控制接口是否准备好
工厂是否故障
现场时钟是否仍在跳动
关键测量是否合理
负责人是否真的申请外部控制
```

即使第一次全部正常，也不能马上放行。必须连续检查几次，证明这不是偶然的一次正常。

### `ENABLED`：正式取得操作许可

连续验证完成后，调度员可以提出当前外部控制命令可以使用。但门卫不会因此停止检查。一旦发现工厂故障、数据冻结或关键测量异常，操作许可立刻撤销。

所以状态机遵循：**慢投入，快退出。**

---

## 三、完整状态转换关系

```text
程序启动
    ↓
DISCONNECTED
    │
    │ TCP连接成功
    ↓
WAIT_VALID
    │
    │ 全部条件连续有效3个周期
    ↓
ENABLED
```

异常路径：

```text
ENABLED
    │
    │ 模型状态异常
    │ RT-LAB心跳超时
    │ 核心测量越界
    │ external_enable_request=false
    │ 单次通信读写失败
    ↓
WAIT_VALID
```

连接真正中断或需要重建时：

```text
WAIT_VALID或ENABLED
    │
    │ TCP连接丢失
    │ 连续通信失败达到阈值
    ↓
DISCONNECTED
```

连接恢复：

```text
DISCONNECTED
    │
    │ 重新连接成功
    ↓
WAIT_VALID
```

绝不能：`DISCONNECTED → 直接ENABLED`。

## 四、为什么程序启动必须进入 `DISCONNECTED`

程序刚启动时，板子还不知道：

```text
OP5700是否在线
1502端口是否监听
RT-LAB模型是否Execute
寄存器是否可读取
40115是否正常
40116是否持续更新
核心测量是否有效
```

因此最安全的初始结论只能是：外部命令无效。

所以启动时必须：

```text
state = DISCONNECTED
ext_agc_enable_local = 0
valid_count = 0
40010逻辑值 = 0
```

不能因为JSON中的测试命令已经配置好，就直接宣布外部控制有效。

---

## 五、为什么连接成功不能直接进入 `ENABLED`

TCP连接成功只能证明板子能和 `192.168.1.100:1502` 建立网络会话。它不能证明：

- 模型已经运行
- 测量数据已经初始化
- 外部接口准备完成
- 模型没有故障
- 心跳仍在变化
- SOC和PV最大出力合理

考虑以下场景：板子成功连接OP5700，但RT-LAB模型尚未Execute。此时TCP服务器可能仍然可以响应，但寄存器中可能是旧值、零值、初始化值、尚未刷新的值。

所以连接成功后只能进入 `WAIT_VALID`，表示通道有了，但数据资格还没有得到证明。

---

## 六、`WAIT_VALID` 中每个周期要检查什么

V3.2要求每个通信周期检查六类条件。

### 条件1：FC03读取和响应格式正常

板子必须成功读取40101～40116。不仅要收到网络数据，还要确认：

- 返回功能码正确
- 返回寄存器数量正确
- 响应格式完整
- 没有Modbus异常响应

如果FC03失败，本周期测量数据不能使用。

### 条件2：MODEL_STATUS准备位满足要求

要求：

```text
bit0 MODEL_RUNNING = 1
bit1 MEAS_VALID = 1
bit2 EXT_INTERFACE_READY = 1
```

等价于 `(status & 7) == 7`。

### 条件3：MODEL_FAULT未置位

要求 `bit4 MODEL_FAULT = 0`，等价于 `(status & 16) == 0`。

### 条件4：RTLAB_HEARTBEAT已经建立且未超时

必须确认：

- 已经至少观察到心跳变化
- 最近一次变化距离现在未超过3500 ms

第一次读取到某个心跳值时，只保存初值，不能马上把这一周期计为完整有效周期。

### 条件5：五个核心测量点全部有效

当前默认强制检查：

```text
40101 PCC_P
40105 PV1_P_MAX
40106 PV2_P_MAX
40107 ESS1_SOC
40108 ESS2_SOC
```

任一超出其 `valid_min/valid_max`，本周期即无效。

### 条件6：`external_enable_request = true`

这是JSON中的人工或上层允许开关。它表示用户当前确实申请让板子进入外部控制可用状态。

即使所有通信条件正常，如果 `"external_enable_request": false`，板子也必须保持 `WAIT_VALID`，`40010 = 0`。

---

## 七、`external_enable_request` 和 40010 不是同一个量

- **`external_enable_request`**：来自板子JSON配置，是用户给板子的允许条件。可以理解为"我是否申请启动外部控制资格判断"。
- **40010 `EXT_AGC_ENABLE`**：由板子计算后写给RT-LAB。它表示在人工申请开启的前提下，板子综合判断当前所有安全条件是否满足。

关系可以写成：

```text
external_enable_request 只是 40010 变为1的必要条件之一
```

不是 `external_enable_request = true` 就直接令 `40010 = 1`。

---

## 八、为什么默认配置为false

需求文件要求JSON支持 `"external_enable_request": false`。默认关闭的好处是：程序启动后即使网络和数据全部正常，也不会自动投入外部控制。这给调试人员留下检查时间。

例如第一次联调时，可以先观察FC03是否稳定、40115是否正确、40116是否变化、核心测量是否合理、40011和40012是否更新。确认无误后，再把 `external_enable_request` 改为 `true` 进行使能测试。

因此，如果工程师程序运行后始终停留在 `WAIT_VALID`、`40010 = 0`，首先要检查的并不一定是程序故障，也可能只是JSON中的人工请求仍为 `false`。

---

## 九、什么叫"连续3个有效周期"

参数：

```json
"valid_cycles_before_enable": 3
```

这里的"连续"是关键。只有某个周期全部条件均满足，才能 `valid_count = valid_count + 1`。任何一项失败都必须 `valid_count = 0`。不能累计三个分散的正常周期。

### 例子一：真正连续正常

```text
周期1：全部正常 → valid_count = 1
周期2：全部正常 → valid_count = 2
周期3：全部正常 → valid_count = 3
```

达到3后进入 `ENABLED`，并准备写 `40010 = 1`。

### 例子二：中途出现异常

```text
周期1：全部正常           → valid_count = 1
周期2：全部正常           → valid_count = 2
周期3：ESS1_SOC越界      → valid_count = 0
周期4：全部恢复正常       → valid_count = 1
周期5：全部正常           → valid_count = 2
周期6：全部正常           → valid_count = 3
```

最终要到周期6才能进入 `ENABLED`。周期1、2不能和周期4拼在一起计算。

---

## 十、为什么必须连续3个周期

假设连接刚恢复时，第一帧数据看起来正常。但有可能：

- 第一帧是缓存旧值
- 下一帧才暴露测量异常
- 心跳刚恢复一次后又停止
- 模型状态在启动阶段短暂跳变

如果只看一帧就使能，可能造成 `40010` 快速变成1、随后又立即变成0，甚至在短暂错误窗口内使用外部命令。

连续3个周期相当于一个简单的稳定确认窗口。当前通信周期为1000 ms，因此在理想情况下，从心跳已经建立以后，还需要约3秒连续正常才能投入。但启动总等待时间可能更长，因为第一次心跳读取只用于保存初值。

---

## 十一、从启动到使能的完整逐周期过程

假设：

```text
通信周期 = 1 s
external_enable_request = true
40115始终为7
核心测量全部正常
```

### t = 0：程序启动

```text
state = DISCONNECTED
valid_count = 0
ext_agc_enable_local = 0
```

板子尝试连接OP5700。

### t ≈ 0：连接成功

状态变化：`DISCONNECTED → WAIT_VALID`。日志：`STATE DISCONNECTED -> WAIT_VALID reason=CONNECTED`。不能直接使能。

### 第1个读取周期

读取 `40116 = 105`。因为是第一次读取，只保存 `last_rtlab_hb = 105`。此时尚未证明心跳发生过变化，所以 `valid_count = 0`、`40010 = 0`。

板子仍可通过FC16写入：40001～40009测试值，40010 = 0，40011当前命令序号，40012板子心跳。

### 第2个读取周期

读取 `40116 = 106`。确认 `105 → 106`，心跳有效。如果本周期所有其他条件也正常：`valid_count = 1`，`40010 = 0`，`state = WAIT_VALID`。

### 第3个读取周期

读取 `40116 = 107`。全部正常：`valid_count = 2`，`40010 = 0`。

### 第4个读取周期

读取 `40116 = 108`。全部正常：`valid_count = 3`。

状态转换：`WAIT_VALID → ENABLED`。板子本周期准备 `40010 = 1`。日志：`STATE WAIT_VALID -> ENABLED reason=VALID_3_CYCLES`。

只有这次FC16成功后，RT-LAB侧才真正收到 `40010 = 1`。如果这次FC16失败，就不能认为使能已经成功发布。按照V3.2安全要求，应立即撤销板子本地使能、清零 `valid_count`，不允许继续维持有效状态。

---

## 十二、在 `WAIT_VALID` 中为什么仍要写40001～40009

需求明确规定：`WAIT_VALID` 期间，40001～40009仍可按 `test_mode` 生成并写入，但40010始终为0，RT-LAB不得采用这些命令。

这样做有两个目的。

### 目的1：提前验证命令数据链

即使尚未使能，也可以检查：

- 测试值是否正确生成
- INT16/UINT16编码是否正确
- FC16是否能写12个寄存器
- RT-LAB解码是否正确

### 目的2：把"数据传输"和"控制授权"分开

例如 `40001 = 0.3 pu` 可以已经正确写入RT-LAB。但由于 `40010 = 0`，RT-LAB必须认为这是一条可以观察但不能使用的命令。这种设计允许先把链路调通，再正式授权控制。

---

## 十三、进入 `ENABLED` 后为什么还要继续检查

`ENABLED` 只表示过去连续几个周期正常，并且当前周期满足要求。它不意味着未来永久正常。

下一周期可能发生：RT-LAB心跳停止、MODEL_STATUS变成23、ESS_SOC解码成1.20、FC03读取失败、`external_enable_request` 被关闭、网线断开。

因此进入 `ENABLED` 后，每个周期仍要执行完整检查。不能进入 `ENABLED` 后就停止读取40115、40116或停止范围检查。

---

## 十四、异常退出为什么只需要一个周期

投入需要连续3个有效周期，但退出只需要一次明确异常。

例如 `state = ENABLED`，`40010 = 1`。下一周期读取到 `ESS1_SOC = 1.20`，这个值已经超出物理有效范围。不能再等待三次确认。必须立即：

```text
measurements_valid = false
ext_agc_enable_local = 0
valid_count = 0
state = WAIT_VALID
40010准备写0
```

状态日志：`STATE ENABLED -> WAIT_VALID reason=MEASUREMENT_INVALID`
异常日志：`INVALID point=ESS1_SOC value=1.20 range=[0,1]`

这种不对称规则就是：**进入谨慎，退出迅速。**

---

## 十五、不同异常应该退到哪里

这取决于问题发生在哪一层。

### 1. 数据或模型条件异常

例如：`MODEL_STATUS = 1`、`MODEL_STATUS = 23`、RT-LAB心跳超时、PCC_P越界、SOC越界、`external_enable_request = false`。

说明TCP连接可能仍然存在，但控制条件不满足。因此进入 `WAIT_VALID`。

### 2. 连接中断

例如：TCP socket断开、服务器关闭、网络不可达、程序确认连接已经丢失。

说明通信通道本身不存在。因此进入 `DISCONNECTED`。

### 3. 单次FC03或FC16失败

需求规定，任一次读写失败都必须立即：

```text
ext_agc_enable_local = 0
valid_count = 0
```

如果连接仍被认为可用，板子至少不能继续停留在有效控制状态，应按等待重新验证处理。如果确认连接中断，则进入 `DISCONNECTED`。

---

## 十六、一次通信失败和三次连续失败的区别

V3.2中有两个不同层面的处理。

### 第一次失败：先保证控制安全

任一次FC03或FC16失败，立即：本地40010逻辑置0，`valid_count = 0`，退出外部有效状态。因为本周期数据或命令已经不完整可信。

### 连续三次失败：再重建TCP连接

配置：

```json
"max_consecutive_failures": 3
```

这个参数只用于决定什么时候关闭当前TCP连接并重新建立。

例如：

```text
第1次失败：
撤销使能，但先不一定关闭socket

第2次连续失败：
继续保持无效

第3次连续失败：
关闭并重建TCP连接
转入DISCONNECTED
```

不能把逻辑写成"连续失败3次以后才撤销40010"，那样会让系统在前两次失败期间仍然把旧命令当作有效。需求明确说明，`max_consecutive_failures` 只决定何时关闭并重建连接，不用于延迟外部使能撤销。

---

## 十七、`valid_count` 与 `consecutive_failures` 不是同一个计数器

### `valid_count`

统计连续多少个周期全部安全条件成立。用途：决定是否能够从 `WAIT_VALID` 进入 `ENABLED`。任何模型状态、心跳、测量或读写异常都应清零。

### `consecutive_failures`

统计连续发生多少次Modbus读写失败。用途：决定是否关闭并重建TCP连接。

以下异常不一定属于Modbus失败：`MODEL_STATUS = 23`、`SOC = 1.20`、RT-LAB心跳长期不变、`external_enable_request = false`。这些会清零 `valid_count` 并撤销使能，但不应该仅因为它们存在就重建TCP连接。原因是网络通信本身可能完全正常。

---

## 十八、FC16失败为什么特别危险

考虑当前处于 `ENABLED`、`40010 = 1`。板子检测到异常后，准备通过FC16写 `40010 = 0`，但恰好这次FC16失败。

此时：板子本地已经知道命令无效，但RT-LAB寄存器中可能仍保留旧的 `40010 = 1`。如果RT-LAB只看40010，就会继续错误使用旧命令。

因此RT-LAB必须独立检查 `40012 BOARD_HEARTBEAT`。FC16失败或连接中断后，RT-LAB侧的40012不会继续更新。超过板子心跳超时后，RT-LAB自行令 `BOARD_HB_OK = 0`、`EXTERNAL_COMMAND_VALID = 0`。

这就是双向安全监督存在的原因。

---

## 十九、断线后的完整过程

假设当前 `state = ENABLED`，`40010 = 1`。突然拔掉网线。

### 板子侧

下一次通信操作失败：`ext_agc_enable_local = 0`，`valid_count = 0`。由于网线已经断开，板子无法真正写出 `40010 = 0`。确认连接丢失后：`state = DISCONNECTED`。然后每隔 `reconnect_interval_ms = 1000` 尝试重新连接。

### RT-LAB侧

寄存器中可能暂时保留 `40010 = 1`。但 `40012 BOARD_HEARTBEAT` 停止变化。RT-LAB计算的 `BOARD_HB_AGE_S` 不断增加。超过阈值后：`BOARD_HB_OK = 0`，`EXTERNAL_COMMAND_VALID = 0`。

因此即使40010残留为1，外部命令也会被撤销。

---

## 二十、重新连接后为什么必须回到 `WAIT_VALID`

假设网线重新插回。板子成功连接后，能证明的只有TCP通信通道恢复。还不能证明：

- RT-LAB模型仍处于原状态
- 心跳已经重新建立
- 测量数据已经刷新
- 旧命令是否仍然适用
- 核心测量是否正常

所以必须：`DISCONNECTED → WAIT_VALID`。然后第一次心跳只保存，重新检查MODEL_STATUS，重新检查核心测量，重新累计1→2→3个连续有效周期，才能再次进入 `ENABLED`。

这可以避免网络一恢复、旧40010立即重新变成1、旧命令突然重新接管设备。

---

## 二十一、异常恢复的逐周期例子

假设原来处于 `ENABLED`，随后40115由7变成23。

### 异常周期

`MODEL_STATUS = 23`。立即：`state = WAIT_VALID`，`valid_count = 0`，`40010 = 0`。

### 下一周期：状态恢复为7

不能立即使能。若其他条件也正常：`valid_count = 1`，`40010 = 0`。打印 `RECOVER reason=MODEL_STATUS_NORMAL`。但恢复日志不等于重新使能。

### 再下一周期

`valid_count = 2`，`40010 = 0`。

### 第三个连续正常周期

`valid_count = 3`，`WAIT_VALID → ENABLED`，`40010 = 1`。

因此完整原则是：**发现恢复 ≠ 允许投入。恢复后仍需重新证明稳定。**

---

## 二十二、40012在三个状态中的表现

### `DISCONNECTED`

板子无法通过FC16成功写入OP5700。因此RT-LAB中的40012会停止变化。板子本地可能仍有循环计数，但远端看不到更新。

### `WAIT_VALID`

板子程序正常、连接正常，可以执行FC16。所以40012应持续变化：`35 → 36 → 37 → 38`。即使 `40010 = 0`，也要更新心跳。这说明板子还活着，只是尚未取得控制资格。

### `ENABLED`

40012同样持续变化。同时 `40010 = 1`。如果40012停止，即使40010仍为1，RT-LAB也要撤销外部命令。

---

## 二十三、40011在状态机中的作用

`CMD_SEQ` 表示成功发布的命令批次。在 `WAIT_VALID` 中，板子仍可能成功写入整批40001～40012，因此CMD_SEQ也可以持续变化。

这意味着 `state = WAIT_VALID`、`40010 = 0`、`CMD_SEQ` 持续变化、`BOARD_HEARTBEAT` 持续变化，是合理现象。它表示板子和命令发布链正常，但安全投入条件尚未满足。

如果FC16写入失败，不能把该批次视为成功发布。

---

## 二十四、状态机的核心不是"有没有命令"，而是"命令能否使用"

在 `WAIT_VALID` 中：40001～40009可能有完整测试值，40011持续增加，40012持续增加。但是 `40010 = 0`。因此这些命令不能投入。

这说明状态机管理的不是板子有没有产生数据，而是**RT-LAB当前是否被允许使用板子数据控制设备**。

## 二十五、联合调试时应该看到什么

### 场景1：默认不开启外部请求

JSON: `"external_enable_request": false`

预期：连接成功，`state = WAIT_VALID`，40012持续变化，40011持续变化，40010始终为0，`valid_count` 不能完成使能。这不是故障。

### 场景2：开启请求且全部正常

设置 `"external_enable_request": true`。预期经过：首次心跳基线 → `valid_count = 1` → `valid_count = 2` → `valid_count = 3`，然后 `WAIT_VALID → ENABLED`，`40010 = 1`。

### 场景3：ENABLED时SOC越界

将40107改成相当于 `ESS1_SOC = 1.20`。预期立即：`40010 = 0`，`valid_count = 0`，`ENABLED → WAIT_VALID`。

### 场景4：SOC恢复

恢复到 `ESS1_SOC = 0.75`。预期不立即使能，重新累计3个连续有效周期。

### 场景5：RT-LAB心跳冻结

40116停止变化超过3500 ms。预期：`40010 = 0`，`valid_count = 0`，`ENABLED → WAIT_VALID`。TCP连接可能仍然保持，因此不一定进入 `DISCONNECTED`。

### 场景6：拔掉网线

预期板端：通信失败，本地使能立即撤销，最终进入 `DISCONNECTED`，持续自动重连。

RT-LAB侧：40010可能短暂残留1，40012停止变化，`BOARD_HB_OK` 超时后变0，`EXTERNAL_COMMAND_VALID` 变0。

### 场景7：网线恢复

预期：`DISCONNECTED → WAIT_VALID`，不能直接 `ENABLED`，重新建立心跳基线，重新连续验证3个周期。

## 二十六、日志为什么是状态机验收的关键

单看40010只能知道现在是0还是1，但不知道为什么。

日志必须打印状态变化原因，例如：

```text
STATE DISCONNECTED -> WAIT_VALID reason=CONNECTED
STATE WAIT_VALID -> ENABLED reason=VALID_3_CYCLES
STATE ENABLED -> WAIT_VALID reason=RTLAB_HEARTBEAT_TIMEOUT
STATE ENABLED -> DISCONNECTED reason=CONNECTION_LOST
```

这样调试时才能区分：

- 是模型状态异常，还是心跳超时
- 是测量越界，还是网络断开
- 是人工请求关闭，还是连续通信失败

没有原因日志，状态机即使看起来在变化，也很难验收是否按正确逻辑变化。

## 二十七、本轮需要完全掌握的两个独立层级

### 控制资格层

由以下内容决定：MODEL_STATUS、RT-LAB心跳、核心测量范围、`external_enable_request`、连续有效周期。

决定：`WAIT_VALID` 还是 `ENABLED`，40010是0还是1。

### 通信连接层

由以下内容决定：TCP是否连接、FC03/FC16是否连续失败、是否达到重连阈值。

决定：是否进入 `DISCONNECTED`，是否关闭并重建连接。

所以：**数据无效 ≠ 网络断开**。例如SOC越界时，网络可以保持正常，不应为了SOC越界重建TCP连接。

## 二十八、论文注意点记录

### 1. 状态机构成控制接口的"准入层"

整个系统可以分为：

```text
通信层：数据是否能传输
语义层：数据类型和缩放是否正确
准入层：数据和命令是否满足安全使用条件
控制层：AGC如何计算六路命令
```

V3.2主要建立的是准入层。

### 2. "慢投入、快退出"可以形成实验指标

可以记录：异常检测时间、40010撤销时间、断线后外部命令最长残留时间、恢复到重新使能的时间、错误使能次数、状态反复切换次数。这些指标以后适合评价通信安全管理机制。

### 3. `valid_cycles_before_enable` 决定恢复速度

通信周期为1秒、连续有效周期为3时，恢复后至少要经历约3个有效通信周期才能重新使能。参数较大：更稳定，恢复更慢。参数较小：恢复更快，但更容易在短暂正常时误投入。这是安全性和恢复速度之间的权衡。

### 4. 双侧失效判断避免状态认知不一致

板子认为"我已经撤销使能"，不代表RT-LAB一定收到了40010 = 0。RT-LAB必须通过板子心跳独立判断。这反映了通信系统中的一个重要问题：**控制双方对当前状态的认知可能不一致。**

后续论文若研究通信异常，这一问题比单纯"增加延时"更有实际意义。

### 5. V3.2状态机本身仍主要是工程基础

它能提高系统完整性，但不能仅凭三状态状态机就断言形成论文核心创新。更合理的论文结构仍是：

```text
V3.2安全通信平台
+
某一种控制策略
+
通信非理想工况
+
针对性改进方法
+
RT-LAB硬件在环验证
```

板子允许RT-LAB使用外部命令，40010=1。

有效计数：
必须连续，任一异常立即清零。

投入：
需要3个连续有效周期。

退出：
一次明确异常立即撤销。

数据异常：
通常退回WAIT_VALID。

连接断开：
进入DISCONNECTED。

一次读写失败：
立即撤销使能。

连续3次读写失败：
关闭并重建TCP连接。

valid_count：

consecutive_failures：
决定是否重建连接。
