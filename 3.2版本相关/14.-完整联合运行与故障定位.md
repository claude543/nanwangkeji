# V3.2 第七轮内化：完整联合运行过程与故障定位

> 课题：AGC算法内化理解 · 2026暑期项目南网科技
> 整理日期：2026-07-20（周一）
> 本轮主题：把前六轮所有要素串成完整运行故事，建立故障定位固定链路

---

## 本轮学习目标

本轮结束后，你应当具备两项实际能力：

1. **看到板端日志和 RT-LAB 显示，就能判断系统目前走到了哪一步**。
2. **联调失败时能够沿固定链路定位问题**，而不是猜测是网络、模型还是程序错误。

## 前情提要（前六轮拆解要素）

| 轮次 | 主题 |
|------|------|
| 40101～40116 | RT-LAB 提供的测量与管理信息 |
| 40115 | 模型是否具备外部控制条件 |
| 40116 | RT-LAB 数据是否持续刷新 |
| 三状态状态机 | DISCONNECTED / WAIT_VALID / ENABLED |
| 第五轮 | 核心测量有效性检查 |
| 第六轮 | 40010 板子侧使能请求 / 40011 命令批次号 / 40012 板子心跳 |

本轮把这些功能**全部串起来**，研究系统从启动到正常投入、异常退出、自动重连和重新投入的完整过程。

> 📌 V3.2 规定：**任一次 FC03 或 FC16 失败都立即撤销板子本地使能并清零有效计数**；只有**连续失败达到 3 次**时才关闭并重建 TCP 连接。通信断开后，RT-LAB 还要通过 40012 心跳超时独立撤销外部命令。

## 一、先建立完整的运行主循环

板子每 1000 ms 执行一次通信循环。一轮完整过程为：

```
1. 检查或建立 TCP 连接
        ↓
2. FC03 读取 40101～40116
        ↓
3. 检查 Modbus 响应格式
        ↓
4. INT16/UINT16 及 scale 解码
        ↓
5. 判断 40115 MODEL_STATUS
        ↓
6. 判断 40116 RTLAB_HEARTBEAT
        ↓
7. 检查 5 个核心测量点
        ↓
8. 更新 DISCONNECTED / WAIT_VALID / ENABLED 状态
        ↓
9. 生成 40001～40012
        ↓
10. FC16 整批写入 40001～40012
        ↓
11. 根据写入结果更新 CMD_SEQ、失败计数和日志
        ↓
12. 等待下一通信周期
```

> ⚠️ **这个顺序很重要**。例如，必须先把 40107 的原始寄存器解码成 SOC 工程量，才能检查它是否处于 0～1；**不能直接对原始整数做工程量范围判断**。

## 二、正常启动全过程

### 设定参数

| 参数 | 值 |
|------|-----|
| OP5700 地址 | 192.168.1.100 |
| 端口 | 1502 |
| 通信周期 | 1000 ms |
| 连续有效周期 | 3 |
| RT-LAB 心跳超时 | 3500 ms |
| external_enable_request | true |
| MODEL_STATUS | 7 |
| 五个核心测量点 | 全部正常 |

假设 40116 心跳依次为 `105 → 106 → 107 → 108 ……`

### 第 0 阶段：板子程序启动

程序启动后必须先进入：
```
state = DISCONNECTED
ext_agc_enable_local = 0
valid_count = 0
```

同时打印配置摘要：
```
START version=V3.2 ip=192.168.1.100 port=1502
cycle_ms=1000 valid_cycles=3 hb_timeout_ms=3500
external_request=true
```

**这行日志首先回答：**

| 检查项 | 是否正确 |
|--------|----------|
| 启动的是不是 V3.2 程序 | version=V3.2 |
| IP 和端口是否正确 | 192.168.1.100:1502 |
| 通信周期是否正确 | 1000 ms |
| 连续有效周期是不是 3 | valid_cycles=3 |
| 心跳超时是不是 3500 ms | hb_timeout_ms=3500 |
| 人工投入请求是否开启 | external_request=true |

> ⚠️ 如果这里显示 `external_request=false`，后面即使所有通信条件正常，40010 也不会变成 1。

### 第 1 阶段：TCP 连接成功

板子主动连接 `192.168.1.100:1502`。

**成功后状态变化：**
```
DISCONNECTED → WAIT_VALID
```

**日志：**
```
STATE DISCONNECTED -> WAIT_VALID reason=CONNECTED
```

**此时只证明：** 板子与 OP5700 之间的 TCP 和 Modbus 通信通道已经建立。

**尚未证明：**
- 模型正在运行
- 测量已经有效
- 心跳正在更新
- 核心测量正常
- 外部接口已经准备

所以 **40010 必须保持 0**。

## 三、第一次读取为什么不能直接计入有效周期

板子第一次通过 FC03 读到：
```
40115 MODEL_STATUS = 7
40116 RTLAB_HEARTBEAT = 105
```

五个核心点也全部正常。

但对于 40116，板子**只能知道：**
> "当前寄存器中存着 105"

**不能知道** 105 是刚刚产生的，还是很久以前遗留的旧值。

因此第一次读取只执行：
```
last_rtlab_heartbeat = 105
保存首次读取时间
```

此时：
```
valid_count = 0
state = WAIT_VALID
40010 = 0
```

板子仍然通过 FC16 写入 40001～40012，其中：
- 40001～40009：测试数据
- 40010 = 0
- 40011：当前 CMD_SEQ
- 40012：当前 BOARD_HEARTBEAT

> 如果 FC16 成功，RT-LAB 能够看到板子程序和写入链路已经开始工作，但**不能使用测试命令**。

---

## 四、连续有效周期如何建立

### 第二次读取

板子读到 `40116 = 106`，已经观察到 `105 → 106`，这才证明 RT-LAB 心跳确实在更新。

若本周期同时满足：
- FC03 成功
- MODEL_STATUS 满足要求
- 无 MODEL_FAULT
- 心跳健康
- 五个核心点正常
- `external_enable_request = true`

则：
```
valid_count = 1
40010 = 0
state = WAIT_VALID
```

### 第三次读取

读到 `40116 = 107`，全部条件正常：
```
valid_count = 2
40010 = 0
```

### 第四次读取

读到 `40116 = 108`，全部条件正常：
```
valid_count = 3
```

状态转换为：
```
WAIT_VALID → ENABLED
```

并准备发送 `40010 = 1`。

**日志：**
```
STATE WAIT_VALID -> ENABLED reason=VALID_3_CYCLES
```

> ⚠️ 只有本次 FC16 成功后，RT-LAB 才真正收到 40010=1。
>
> 因此**必须区分**：
> - 板子本地决定进入 ENABLED
> - RT-LAB 成功收到 40010=1
>
> 中间还隔着一次 FC16 写入。

---

## 五、正常 ENABLED 状态的一轮通信

系统已经处于 `state=ENABLED, 40010=1`。

**每个周期仍然不能停止检查**，一轮正常过程是：

```
FC03 读取成功
        ↓
40115 满足 bit0、bit1、bit2=1 且 bit4=0
        ↓
40116 仍在超时范围内持续更新
        ↓
5 个核心点均在范围内
        ↓
external_enable_request = true
        ↓
继续保持 ENABLED
        ↓
FC16 写入 40001～40012
```

### RT-LAB 侧观察

```
40010：           1
40011：           20 → 21 → 22
40012：           35 → 36 → 37
BOARD_HB_OK：     1
EXTERNAL_COMMAND_VALID：1
```

**这说明：**
- 板子认为命令可以使用
- 命令批次持续成功发布
- 板子写入链路持续运行
- RT-LAB 确认板子心跳正常

> 📌 但仍要记住：**V3.2 中的 EXTERNAL_COMMAND_VALID=1 只是表明外部命令具备使用资格**。目前正式板端 AGC 尚未接入，六路命令也尚未正式接管设备 Pref。

## 六、正常运行摘要应该怎样阅读

需求规定通信周期为 1 秒时，每 5 个周期打印一行摘要，例如：

```
RUN state=WAIT_VALID status=0x0007 rtlab_hb=105
valid=2/3 enable=0 cmd_seq=20 board_hb=35
read=OK write=OK
```

### 逐项解释

| 字段 | 含义 |
|------|------|
| `state=WAIT_VALID` | 已经连接，但尚未完成连续有效验证 |
| `status=0x0007` | MODEL_STATUS 为 7，模型状态基本正常 |
| `rtlab_hb=105` | 当前读到的 RT-LAB 心跳值 |
| `valid=2/3` | 已经连续正常 2 轮，还差 1 轮 |
| `enable=0` | 40010 仍为 0，RT-LAB 不得采用板子命令 |
| `cmd_seq=20` | 命令批次当前值 |
| `board_hb=35` | 板子心跳当前值 |
| `read=OK write=OK` | 本轮 FC03 和 FC16 均成功 |

**所以这一行日志已经能说明：** 网络、读写、模型状态基本正常；当前只是尚未完成第 3 个连续有效周期。

## 七、场景一：核心测量越界

### 触发条件

假设当前处于 `state=ENABLED, 40010=1`，下一周期读取 `ESS1_SOC = 1.20`。

### 板子侧处理

FC03 虽然成功，但解码后的工程值超出允许范围 `[0,1]`，因此立即：
```
measurements_valid = false
ext_agc_enable_local = 0
valid_count = 0
state = WAIT_VALID
```

本周期通过 FC16 尝试写 `40010 = 0`。

**日志：**
```
INVALID point=ESS1_SOC value=1.20 range=[0,1]
STATE ENABLED -> WAIT_VALID reason=MEASUREMENT_INVALID
```

### 不应该发生什么

> ⚠️ **不应该：**
> - 把 1.20 限幅成 1.00 继续使用
> - 关闭 TCP 连接
> - 退出板端程序
> - 停止更新 BOARD_HEARTBEAT

因为这是数据内容异常，不一定是网络异常。

### 正确结果

```
通信继续运行
40012 继续变化
40011 在成功写入时继续变化
40010 保持 0
等待 SOC 数据恢复
```

> 📌 **输入越界必须判无效，不能限幅后继续使用；但通信程序不得因单个测量越界而退出。**

---

## 八、核心测量恢复后的过程

下一周期 SOC 恢复为 `ESS1_SOC = 0.75`，**不能立即使能**，重新累计：

| 周期 | 状态 |
|------|------|
| 恢复周期 1 | `valid_count=1, 40010=0` |
| 恢复周期 2 | `valid_count=2, 40010=0` |
| 恢复周期 3 | `valid_count=3, ENABLED, 40010=1` |

> 📌 **检测到恢复 ≠ 立即重新投入**。仍然要重新证明数据连续稳定。

## 九、场景二：MODEL_STATUS 变为故障

### 触发条件

假设当前 `40115 = 23 = 0x0017`，其 bit0、bit1、bit2 虽然均为 1，但 bit4 故障位也为 1。

### 板子处理

应立即：
```
40010 = 0
valid_count = 0
ENABLED → WAIT_VALID
```

**日志：**
```
INVALID model_status=0x0017 reason=MODEL_FAULT
STATE ENABLED -> WAIT_VALID reason=MODEL_FAULT
```

TCP 连接继续保持，因为：
> "模型主动报告故障" ≠ "Modbus 网络已经中断"

当 MODEL_STATUS 重新恢复为 7 时，仍然重新完成 3 个连续有效周期。

## 十、场景三：RT-LAB 心跳冻结

### 触发条件

假设 `MODEL_STATUS` 始终为 7，FC03 每轮都成功，核心测量值也正常，但 40116 停留在 `105`。

### 为什么不能立即故障

由于心跳更新周期和板子读取周期可能存在相位差，**一次读到相同值不一定异常**。

板子记录：
> 距离上次观察到心跳变化的时间

在未超过 3500 ms 前，仍可认为尚未超时。

### 超过 3500 ms 后

立即：
```
ext_agc_enable_local = 0
valid_count = 0
state = WAIT_VALID
40010 = 0
```

**日志：**
```
INVALID rtlab_hb=105 unchanged_ms=4000
reason=HEARTBEAT_TIMEOUT

STATE ENABLED -> WAIT_VALID
reason=RTLAB_HEARTBEAT_TIMEOUT
```

这里 TCP 仍可能正常，所以**不必进入 DISCONNECTED**。

> 📌 这个故障的准确含义是：**Modbus 还能读到寄存器，但 RT-LAB 侧数据刷新过程可能已经停止，当前值可能是旧数据。**

---

## 十一、心跳恢复后怎样处理

40116 从 105 恢复变化到 106。板子可以打印：
```
RECOVER reason=RTLAB_HEARTBEAT_CHANGED
```

但仍然保持：
```
state = WAIT_VALID
40010 = 0
```

若其他条件均正常，**恢复变化的周期可作为重新验证的第一个有效周期**，随后继续累计到 3。

> ⚠️ **不能出现：** 心跳刚变化一次 → 立即 40010=1

---

## 十二、场景四：单次 FC03 失败

假设板子处于 ENABLED，本轮 FC03 读取失败。

由于本轮没有取得可靠的新测量数据，板子必须立即：
```
ext_agc_enable_local = 0
valid_count = 0
```

如果 TCP 连接仍然可写，应尝试通过 FC16 发送 `40010 = 0`。

**日志：**
```
MODBUS_READ_FAILED count=1
```

### 状态处理

| 情况 | 处理 |
|------|------|
| 连接仍存在 | 退回 WAIT_VALID，等待重新验证 |
| 确认连接已经中断 | 进入 DISCONNECTED |

> ⚠️ **第一次 FC03 失败就要撤销控制资格，但不一定第一次就关闭 TCP 连接。**

---

## 十三、场景五：单次 FC16 失败

FC03 和所有数据判断可能都正常，但最后 FC16 写入失败。这意味着：
> RT-LAB 没有确认收到这一整批 40001～40012

所以本批命令**不能视为成功发布**。必须立即：
```
ext_agc_enable_local = 0
valid_count = 0
```

并且：
> 该批 CMD_SEQ **不能**被记录为成功发布

如果连接仍然存在，下一次成功写入时应先发送 `40010 = 0`，重新进入验证过程。

此时 RT-LAB 可能仍然保留上一批：
```
40010 = 1     ← 旧值
旧 CMD_SEQ    ← 旧值
旧 BOARD_HEARTBEAT  ← 旧值
```

所以 **RT-LAB 还必须通过板子心跳年龄独立保护**。

---

## 十四、为什么一次失败撤销使能，三次失败才重建连接

这两个规则解决**不同问题**。

| 规则 | 触发条件 | 目标 |
|------|----------|------|
| **一次失败** | 本周期数据或命令不完整可信 | 保证控制安全 |
| **连续 3 次失败** | 当前 TCP 连接可能失去恢复价值 | 修复通信通道 |

### 一次失败

立即：
```
40010 本地逻辑置 0
valid_count 清零
```

### 连续 3 次失败

```
关闭当前连接
进入 DISCONNECTED
重新建立 TCP 连接
```

> ⚠️ 因此 `max_consecutive_failures=3` **只决定何时重建连接，不能用于延迟使能撤销**。

## 十五、连续失败计数的故事

### 场景 A：非连续失败

| 周期 | 结果 | failure_count |
|------|------|---------------|
| 第 1 周期 | FC03 失败 | 1 |
| 第 2 周期 | FC03 成功、FC16 成功 | 清零 |
| 第 3 周期 | FC03 失败 | 1 |

**不会重建 TCP。**

### 场景 B：连续失败

| 周期 | 结果 | failure_count |
|------|------|---------------|
| 第 1 周期 | 失败 | 1 |
| 第 2 周期 | 失败 | 2 |
| 第 3 周期 | 失败 | 3 |

**结果：**
```
关闭当前连接
进入 DISCONNECTED
按 1000 ms 间隔自动重连
```

> 📌 **与此同时，从第 1 次失败开始，外部使能资格就已经撤销。**

## 十六、场景六：网线物理断开

### 断线前状态

```
板子状态：ENABLED
40010 = 1
CMD_SEQ = 50
BOARD_HEARTBEAT = 100

RT-LAB：
BOARD_HB_OK = 1
EXTERNAL_COMMAND_VALID = 1
```

拔掉网线。

### 板子侧

下一次 FC03 或 FC16 失败：
```
ext_agc_enable_local = 0
valid_count = 0
```

但由于网线已断开，板子**不能真正把 40010=0 写给 RT-LAB**。

确认连接中断后：
```
state = DISCONNECTED
```

然后每 1000 ms 尝试重连。

### RT-LAB 侧

寄存器可能仍然保持**断线前的旧值**：
```
40010 = 1         ← 旧值
CMD_SEQ = 50      ← 旧值
BOARD_HEARTBEAT = 100  ← 旧值
```

RT-LAB 观察到：
```
BOARD_HEARTBEAT 不再变化
BOARD_HB_AGE_S 持续增加
```

超过模型侧设定的板子心跳超时后：
```
BOARD_HB_OK = 0
```

于是：
```
EXTERNAL_COMMAND_VALID
= (40010==1) AND BOARD_HB_OK
= 1 AND 0
= 0
```

> ✅ 因此即使 40010 仍然残留为 1，外部命令也会失效。
>
> 📌 **这就是 V3.2 双侧安全监督的核心价值。**

## 十七、场景七：网络恢复与自动重连

重新插回网线后，板子按 `reconnect_interval_ms=1000` 持续尝试连接。

**连接成功：**
```
DISCONNECTED → WAIT_VALID
```

**日志：**
```
RECOVER reason=MODBUS_RECONNECTED
STATE DISCONNECTED -> WAIT_VALID reason=CONNECTED
```

此时**第一批成功写入应当保持 `40010=0`**。

RT-LAB 可能看到：
```
BOARD_HEARTBEAT 重新变化
BOARD_HB_OK 恢复为 1
```

但 `EXTERNAL_COMMAND_VALID` **仍为 0**（因为 40010 尚未恢复为 1）。

随后板子重新经历：
```
第一次心跳基线
连续有效周期 1
连续有效周期 2
连续有效周期 3
```

才重新进入 ENABLED。

> 📌 **不能因为 RT-LAB 重新 Execute，就直接恢复断开前的 40010=1。**

---

## 十八、场景八：external_enable_request 关闭

假设当前已经 ENABLED，JSON 或启动配置中的人工请求为 `external_enable_request=false`。

板子应当：
```
40010 = 0
valid_count = 0
state = WAIT_VALID
```

**但不需要：**
- 断开 TCP
- 停止 FC03
- 停止 FC16
- 停止 BOARD_HEARTBEAT

因为这是**人工撤销控制授权**，不是通信故障。

当配置重新改为 true 并重启程序后，也必须重新完成连续有效验证。

> 📌 V3.2 第一版**不要求运行中热加载 JSON**，修改配置后重启程序生效即可。

## 十九、RT-LAB Reset / Load / Execute 时会发生什么

实际联调中很常见：
> 板子程序保持运行，RT-LAB 执行 Reset → Load → Execute

期间可能发生：
- 1502 连接短时中断
- MODEL_STATUS 变为未准备
- RTLAB_HEARTBEAT 停止或重新开始
- 寄存器值重新初始化

**板子不能崩溃退出**。正确行为应是：
```
发现连接或数据异常
→ 撤销本地使能
→ 进入 WAIT_VALID 或 DISCONNECTED
→ 自动重连
→ 模型重新 Execute 后读取新数据
→ 重新建立心跳基线
→ 连续验证 3 个周期
→ 再次 ENABLED
```

## 二十、把完整过程串成一个故事

可以把系统想象成**两个值班室**。

### RT-LAB 值班室

每秒更新：
- 模型运行状态
- 测量数据
- RT-LAB 心跳

### 板子值班室

每秒先读取 RT-LAB 报告，再决定：
- 是否允许外部命令投入
- 命令批次号是多少
- 自己的程序是否还活着

### 两边正常时

```
RT-LAB：我正在运行，数据持续更新
板子：我已经连续验证通过，可以使用我的命令
RT-LAB：我也确认板子心跳正常
```

**外部命令资格成立。**

### 如果 RT-LAB 数据冻结

```
板子发现 RT-LAB 心跳超时
→ 主动撤销 40010
```

### 如果板子突然断线

```
板子无法写 40010=0
→ RT-LAB 自己发现板子心跳超时
→ 独立撤销外部命令
```

> 📌 **所以 V3.2 不是单方面说"我正常"，而是：**
> **双方分别证明自己仍然正常，并分别检查对方是否仍然正常。**

## 二十一、故障定位的固定顺序

联调出现异常时，**不应直接猜"程序写错了"或"RT-LAB 没配置好"**。按以下顺序检查：

### 第 1 层：物理网络与 TCP

| 检查项 |
|--------|
| 网线是否连接 |
| 板子和 OP5700 网口灯 |
| IP 是否为 192.168.1.100 |
| 1502 端口是否监听 |
| 板子是否处于 DISCONNECTED |
| 是否持续自动重连 |

**问题表现：** TCP 无法建立，FC03、FC16 均无法进行

### 第 2 层：Modbus 读写

| 检查项 |
|--------|
| FC03 是否成功 |
| 返回数量是否为 16 |
| FC16 是否成功 |
| 写入数量是否为 12 |
| 是否收到 Modbus 异常响应 |
| 连续失败次数 |

**问题表现：** TCP 存在，但 read=FAIL 或 write=FAIL

### 第 3 层：类型、缩放和地址

| 检查项 |
|--------|
| 40101～40116 是否对应正确 offset |
| INT16/UINT16 是否正确 |
| scale 是否正确 |
| 负数补码是否正确 |

**问题表现：** 报文成功，但工程量明显错误（例如 SOC=7500、ESS 功率显示 61536）— 属于 V3.1 层问题。

### 第 4 层：MODEL_STATUS

| 检查项 |
|--------|
| 40115 原始值 |
| ready mask 是否为 7 |
| fault mask 是否为 16 |
| bit 判断是否正确 |

**问题表现：** 板子一直 WAIT_VALID，status 可能是 1 或 23

### 第 5 层：RT-LAB 心跳

| 检查项 |
|--------|
| 40116 是否持续变化 |
| 第一次读取是否只保存 |
| unchanged_ms 是否超过 3500 |
| 65535→0 是否正常处理 |

**问题表现：** status=7，但板子仍报告 HEARTBEAT_TIMEOUT

### 第 6 层：核心测量有效性

| 检查项 |
|--------|
| PCC_P / PV1/2_P_MAX / ESS1/2_SOC |
| range_check_enable |
| 各点 range_check |
| valid_min/valid_max |

**问题表现：** 模型状态和心跳正常，但 valid_count 总是清零

### 第 7 层：人工请求和连续计数

| 检查项 |
|--------|
| external_enable_request 是否为 true |
| valid_count 是否正确累计 |
| 异常是否清零 |
| 是否要求连续 3 轮 |

**问题表现：** 所有数据都正常，但 40010 始终为 0

### 第 8 层：板子写回

| 检查项 |
|--------|
| 40010 是否正确 |
| 40011 是否持续变化 |
| 40012 是否持续变化 |
| FC16 是否成功 |

**问题表现：** 板端日志显示 ENABLED，但 RT-LAB 中 40010 仍为 0

> 📌 此时重点检查 FC16、寄存器 offset 和解码，**而不是继续检查 40115**。

### 第 9 层：RT-LAB 独立有效判断

| 检查项 |
|--------|
| BOARD_HB_AGE_S |
| BOARD_HB_OK |
| EXTERNAL_COMMAND_VALID |

**问题表现：** 40010=1，但 EXTERNAL_COMMAND_VALID=0

**最可能原因：** `BOARD_HB_OK=0`（板子心跳没有被 RT-LAB 正确识别）

### 第 10 层：设备控制路径

> 只有后续版本接入 Pref 以后才检查。

| 检查项 |
|--------|
| EXTERNAL_COMMAND_VALID → 命令选择器 → 设备 Pref → 设备实际功率 → PCC 反馈 |

> 📌 当前 V3.2 即使 EXTERNAL_COMMAND_VALID=1，设备功率不变化也不一定是故障，因为 V3.2 **尚未正式接管设备 Pref**。

## 二十二、常见现象与定位结论

| 现象 | 优先检查 |
|------|----------|
| 板子一直 DISCONNECTED | IP、端口、网线、1502 监听 |
| 板子在 WAIT_VALID，40115=7、心跳变化 | external request、核心测量、valid_count、读写结果 |
| valid_count 到 2 后反复归零 | 查看异常日志，找哪项条件间歇失败 |
| 板端显示 ENABLED，RT-LAB 中 40010=0 | FC16 写入、offset、寄存器解码 |
| 40010=1，但 EXTERNAL_COMMAND_VALID=0 | BOARD_HB_OK 和 BOARD_HB_AGE_S |
| 40012 变化但 40011 不变化 | CMD_SEQ 递增或成功发布逻辑 |
| 40011 和 40012 都停止，40010 仍为 1 | 旧寄存器残留，等待 RT-LAB 心跳超时撤销 |
| 核心点恢复后仍未立即使能 | 正常，需要重新连续验证 3 周期 |
| 辅助点越界但 40010 仍为 1 | 在 range_check=false 时属于预期行为 |
| 40001 发生变化但设备功率不变 | V3.2 尚未接入 Pref，不能据此判定通信失败 |

## 二十四、本轮论文注意点

### 1. V3.2 可以定义四类时间

| 时间 | 定义 | 当前值 |
|------|------|--------|
| 通信周期 | 每隔多久读写一次 | 1000 ms |
| 连续验证时间 | 恢复后多久允许重新投入 | 约 3 个有效周期 |
| RT-LAB 失效检测时间 | 由 3500 ms 心跳超时决定 | 3500 ms |
| 板子失效检测时间 | 由 RT-LAB 侧 BOARD_HEARTBEAT 超时决定 | 由模型侧配置 |

> 📌 这些时间**不能统称为"通信延时"**。

### 2. 旧命令残留窗口是重要工程问题

板子断线以后，RT-LAB 可能暂时保留：
- 旧控制命令
- 旧 40010=1

直到板子心跳超时才撤销。**这一段时间可定义为：外部命令残留窗口。**

后续研究通信故障影响时，需要观察在这个窗口中设备会发生什么。

### 3. 恢复机制同样可能影响控制

重连后连续验证 3 秒左右才重新投入，可以降低误投入风险，但也意味着**控制恢复存在延迟**。

| 恢复速度 | 风险 |
|----------|------|
| 恢复过快 | 可能使用尚未稳定的数据 |
| 恢复过慢 | 系统长时间失去外部协调控制 |

### 4. 状态不同步是双向通信系统的真实问题

板子本地已经 `enable=0`，但 RT-LAB 尚未收到，仍保留 `40010=1`。**说明双方对系统状态的认知在短时间内可能不一致。**

> 📌 **双向心跳正是为了缩短和限制这种不一致。**

### 5. 论文不能把 V3.2 称为完整控制闭环

V3.2 能够证明：**安全双向通信和命令准入机制成立**。

但**还不能证明**：板端算法已经控制设备并形成物理反馈闭环。

论文正式写作时**必须准确区分：**
- 通信闭环平台
- 安全准入层
- 算法闭环
- 设备功率闭环

## 二十五、本轮压缩记忆

```
正常启动：
  DISCONNECTED
  → 连接成功
  → WAIT_VALID
  → 第一次心跳只保存
  → 连续有效 1、2、3
  → ENABLED
  → 40010=1

核心测量或模型异常：
  立即 40010=0
  valid_count=0
  退回 WAIT_VALID
  通信继续运行

RT-LAB 心跳冻结：
  未超过 3500 ms 不立即故障
  超过超时后撤销使能
  恢复后重新验证 3 周期

一次 FC03/FC16 失败：
  立即撤销使能
  但不一定立即重建 TCP

连续 3 次通信失败：
  关闭并重建连接
  进入 DISCONNECTED

网线断开：
  板子可能无法写 40010=0
  RT-LAB 依靠 40012 心跳超时独立撤销外部命令

网络恢复：
  进入 WAIT_VALID
  不能直接 ENABLED
  重新建立心跳和连续验证

故障定位顺序：
  网络
  → Modbus
  → 编解码
  → MODEL_STATUS
  → RT-LAB 心跳
  → 核心测量
  → valid_count
  → 40010～40012
  → BOARD_HB_OK
  → EXTERNAL_COMMAND_VALID
```
