# V3.2 第六轮内化：40010、40011、40012，以及 RT-LAB 为什么必须独立判断板子命令是否有效

> 课题：AGC算法内化理解 · 2026暑期项目南网科技
> 整理日期：2026-07-20
> 本轮主题：板子→RT-LAB 方向的安全管理——40010/40011/40012 三寄存器协同机制

---

## 前情提要（前几轮完成的方向）

前几轮已经完成 **RT-LAB → 板子** 的方向：

| 寄存器 | 作用 |
|--------|------|
| 40115 MODEL_STATUS | 模型当前是否可用 |
| 40116 RTLAB_HEARTBEAT | RT-LAB 数据是否还在刷新 |
| 40101～40114 | 具体测量量是否可信 |

**本轮转向板子 → RT-LAB 的安全管理方向：**

| 寄存器 | 作用 |
|--------|------|
| 40010 EXT_AGC_ENABLE | 板子是否认为当前命令允许使用？ |
| 40011 CMD_SEQ | 板子成功发布到了第几批命令？ |
| 40012 BOARD_HEARTBEAT | 板子通信程序及写入链路是否仍在持续运行？ |

---

## ⚠️ 重要校正（针对上一轮预告）

> 在当前 V3.2 的 RT-LAB 最终有效判断中，**直接参与判断的是 40010 和 40012**；40011 主要提供命令批次和新鲜度证据，目前**不是 EXTERNAL_COMMAND_VALID 的强制条件**。

因此**不是三者在当前公式里都"缺一不可"**，而是三者各自提供不同层面的信息。

V3.2 要求板子通过**一次 FC16** 将 40001～40012 作为一批写入，其中 40010～40012 承担安全与管理功能。

---

## 一、先用"控制指令包裹"理解这三个量

板子每个通信周期准备一批数据：

| 寄存器范围 | 内容 |
|------------|------|
| 40001～40006 | 六台设备功率命令 |
| 40007～40009 | AGC 状态、dP、remain |
| 40010 | 这批命令是否允许采用 |
| 40011 | 这批命令的编号 |
| 40012 | 发送者是否还活着 |

**类比**：可以把它想象成板子寄出一个控制包裹。包裹里有设备命令，但外面还贴了三张标签：

- 🏷️ **第一张标签 40010**：这批命令当前可以使用，或者不可以使用。
- 🏷️ **第二张标签 40011**：这是第 N 批控制命令。
- 🏷️ **第三张标签 40012**：控制器的主通信程序仍在正常运行。

> RT-LAB 不能只看包裹里面的功率数值，还要先检查这些标签。

---

## 二、40010：EXT_AGC_ENABLE 到底表示什么

| 属性 | 值 |
|------|-----|
| 名称 | EXT_AGC_ENABLE |
| 类型 | UINT16 |
| 取值 | 0 或 1 |

**含义：**
- `0`：RT-LAB 不得采用 40001～40009 中的板子数据
- `1`：板子认为当前通信、模型、心跳和测量条件满足

它是**板子经过状态机综合判断后形成的结果**。板子不是根据某一个条件直接设置 40010，而是综合判断：

- Modbus 读写是否正常
- MODEL_STATUS 是否准备完成
- RT-LAB 心跳是否正常
- 五个核心测量点是否有效
- `external_enable_request` 是否为 true
- 是否已经连续满足 3 个有效周期

只有**全部条件满足**，板子才会进入 `ENABLED`，并准备写 `40010=1`。

---

## 三、为什么把 40010 称为"有效请求"，而不是最终有效结论

> ⚠️ **本轮最重要的概念之一**

40010 表达的是：**板子一侧认为命令可以使用。**

但板子不能替 RT-LAB 完成全部判断。因为 RT-LAB 还必须确认：
- 板子现在是否仍在线
- 40010 是否只是以前留下的旧值

因此，**40010 不是最终的 `EXTERNAL_COMMAND_VALID`，而是最终判断中的一个输入条件。**

### 当前 RT-LAB 侧的基本逻辑

$$
\text{EXTERNAL\_COMMAND\_VALID} = (40010 == 1) \;\text{AND}\; \text{BOARD\_HB\_OK}
$$

也就是：
```
板子主动申请使能
+
RT-LAB 确认板子心跳未超时
=
外部命令具备有效资格
```

---

## 四、为什么只看 40010 会产生严重问题

**假设系统正常运行时：**
```
40010 = 1
40012 = 100
```

随后突然**拔掉网线**。

板子立即发现通信失败，并在自己内部执行：
```
ext_agc_enable_local = 0
```

但是网线已经断开，板子没有办法把新的 `40010=0` 真正写进 OP5700。

因此，OP5700 中的寄存器可能继续保持：
```
40010 = 1
```

**这是断线前留下的旧值。**

如果 RT-LAB 只检查 40010，就会误认为板子仍然允许使用外部命令——**实际上板子已经完全失联**。

> 📌 这就是为什么 V3.2 明确要求 **RT-LAB 独立监测 40012 板子心跳**：通信中断时，板子可能无法写出 40010=0，RT-LAB 必须自行判定外部命令失效。

---

## 五、40012：BOARD_HEARTBEAT 到底证明什么

| 属性 | 值 |
|------|-----|
| 名称 | BOARD_HEARTBEAT |
| 类型 | UINT16 |
| 范围 | 0～65535，之后回到 0 |

**要求：**
- 板子每个通信循环递增 1
- WAIT_VALID 期间也要递增
- ENABLED 期间也要递增

它回答：**板子的主通信循环是否仍然运行，并且更新值是否还能通过 FC16 到达 RT-LAB？**

正常情况下，RT-LAB 可能看到 `35 → 36 → 37 → 38`，说明板子通信程序持续运行，FC16 写入链路也在持续工作。

### 为什么说它不仅反映"程序活着"

假设板子内部程序还在运行，但 FC16 一直发送失败。板子本地计数器可能继续变化，但 RT-LAB 接收不到新值，因此 RT-LAB 中的 40012 仍然停留在原值。

**从 RT-LAB 的角度**："看不到新的 BOARD_HEARTBEAT"说明至少有一个环节发生问题：
- 板子程序停止
- 网络中断
- Modbus 写入失败
- OP5700 未接收新批次

所以 40012 实际上反映的是：**板子主通信程序与板子到 RT-LAB 写入路径的综合活性。** 它不是单纯的 CPU 程序存活标志。

---

## 六、RT-LAB 如何根据 40012 生成 BOARD_HB_OK

RT-LAB 侧需要保存**上一次读取到的板子心跳**。基本过程是：

```
读取当前 BOARD_HEARTBEAT
        ↓
与上一值比较
        ↓
┌─────────────────────┬──────────────────────┐
│ 发生变化             │ 没有变化              │
│ ↓                   │ ↓                    │
│ 更新上一值           │ 心跳年龄继续增加       │
│ 心跳年龄清零         │                      │
└─────────────────────┴──────────────────────┘
                    ↓
        年龄超过阈值：BOARD_HB_OK = 0
```

RT-LAB 侧设置了两个变量：

| 变量 | 含义 |
|------|------|
| `BOARD_HB_AGE_S` | 距离最近一次观察到板子心跳变化已经过去多久 |
| `BOARD_HB_OK` | 板子心跳是否仍在允许的时间范围内 |

> ⚠️ RT-LAB 监视板子心跳所使用的超时阈值，应以 RT-LAB 模型侧实际配置为准；它**不必自动等于**板子监视 RT-LAB 时使用的 3500 ms。3500 ms 是当前文件中明确给**板子**检查 40116 所用的初始参数。RT-LAB 检查 40012 可以采用对应的模型侧参数，但**两端应在联调时统一核实**。

---

## 七、为什么 BOARD_HEARTBEAT 不能只判断是否非零

假设 RT-LAB 看到 `40012 = 35`，**不能**因此认定板子正常。因为 35 可能是网线断开前留下的旧值。

**真正要观察的是：**
```
35 → 36 → 37 → 38
```

也就是**数值是否持续发生变化**。

### 回绕处理

`65534 → 65535 → 0 → 1` 属于正常变化。

> ⚠️ **不能采用"当前值必须大于上一值"这种判断**，否则 65535 回到 0 时会误报故障。

正确判断是：**当前值是否不同于上一值**，并结合未变化时长判断是否超时。

---

## 八、40010 和 40012 组合后的四种典型状态

| 场景 | 40010 | BOARD_HB_OK | EXTERNAL_COMMAND_VALID | 含义 |
|------|-------|-------------|------------------------|------|
| 一 | 0 | 1 | 0 | 板子通信正常，但认为命令不允许使用 |
| 二 | 1 | 1 | **1** | 板子认为命令可用，RT-LAB 也确认在线 |
| 三 | 1 | 0 | **0** ⚠️ | 40010 中的 1 可能是旧值，必须撤销 |
| 四 | 0 | 0 | 0 | 板子未申请 + 通信已失效 |

### 情况一：40010=0，BOARD_HB_OK=1

**含义**：板子仍然正常运行并持续通信，但板子认为当前外部命令不允许使用。

**可能原因：**
- 仍处于 WAIT_VALID
- `external_enable_request = false`
- MODEL_STATUS 未准备
- RT-LAB 心跳尚未建立
- 核心测量越界
- 尚未完成 3 个连续有效周期

这是正常的等待或失效状态，不一定是通信故障。

### 情况二：40010=1，BOARD_HB_OK=1

**含义**：板子认为命令可用，RT-LAB 也确认板子仍在线。`EXTERNAL_COMMAND_VALID = 1`。

> 📌 但 V3.2 阶段仍要记住：**具备有效资格 ≠ 六路命令已经正式接入设备 Pref。** 当前版本主要建立这一安全判断，正式控制切换属于后续闭环阶段。

### 情况三：40010=1，BOARD_HB_OK=0 ⚠️ 最重要的保护场景

**含义**：40010 中的 1 可能是旧值；板子心跳已经停止或超时。

**最终必须** `EXTERNAL_COMMAND_VALID = 0`。**不能**因为 40010 仍然显示 1，就继续使用外部命令。

### 情况四：40010=0，BOARD_HB_OK=0

板子没有申请外部控制，并且板子侧通信也已失效。同样 `EXTERNAL_COMMAND_VALID = 0`。

## 九、40011：CMD_SEQ 到底是什么

| 属性 | 值 |
|------|-----|
| 名称 | CMD_SEQ |
| 类型 | UINT16 |
| 范围 | 0～65535，之后回到 0 |

**它表示：板子成功发布的控制命令批次号。**

例如 RT-LAB 观察到 `20 → 21 → 22 → 23`，说明新的 FC16 控制批次在持续发布。

即使 40001～40009 的具体数值没有变化，只要板子完成一次新的成功写入，命令批次仍然应该推进。

因为：
> **命令值未变化** ≠ **板子没有重新确认和发布这批命令**

---

## 十、CMD_SEQ 的精确递增规则

需求要求：

> 某次 FC16 成功写入 40001～40012 → 这一批命令视为成功发布 → 下一次发送的 CMD_SEQ 递增 1

例如初始值为 0：

| 周期 | 操作 | 结果 |
|------|------|------|
| 周期 1 | 发送 CMD_SEQ=0，FC16 成功 | 下一次准备发送 1 |
| 周期 2 | 发送 CMD_SEQ=1，FC16 成功 | 下一次准备发送 2 |
| 周期 3 | 发送 CMD_SEQ=2，**FC16 失败** | 第 2 号命令批次没有成功发布 |

> ⚠️ **板子不能把"已经成功发布的序号"继续推进。** 下一次重试仍应遵守：只有成功写入后，才确认该批次发布完成。

这可以避免日志显示板子已经发布了很多命令，但 RT-LAB 实际上没有收到。

---

## 十一、CMD_SEQ 和 BOARD_HEARTBEAT 为什么不能合并成一个计数器

它们看起来都在递增，但**表达的对象不同**。

| 计数器 | 关注点 | 推进规则 |
|--------|--------|----------|
| BOARD_HEARTBEAT | 板子的通信主循环是否还在持续运行 | 按通信循环推进 |
| CMD_SEQ | 新的控制命令批次是否已经成功发布 | 按成功 FC16 批次推进 |

### 关键差异场景

考虑以下情况：
> 板子程序仍然正常运行，但 FC16 写入连续失败

此时板子本地通信循环仍在执行，但 RT-LAB 无法接收到新的控制批次。

**所以：**
- "程序运行活性"和"命令发布成功"是**两个不同问题**。

---

## 十二、BOARD_HEARTBEAT 和 CMD_SEQ 在 FC16 失败时的差异

假设板子每个循环都在本地增加心跳：
```
本地 BOARD_HEARTBEAT: 100 → 101 → 102 → 103
```

但中间两次 FC16 失败。RT-LAB 可能实际看到：
```
100 → 103
```

中间的 101、102 没有成功传到 RT-LAB。

**这个跳变仍然能够证明：**
- 后续写入链路已经恢复
- 板子程序持续运行过

而 CMD_SEQ 按照"成功发布后才推进"的原则，**理想上不应**因为失败的 FC16 而无故跳过成功批次。

> 📌 因此两者的递增语义不同。

---

## 十三、为什么 CMD_SEQ 当前还没有直接参与 EXTERNAL_COMMAND_VALID

当前 RT-LAB 侧的基本判断是：
$$
\text{EXTERNAL\_COMMAND\_VALID} = (40010 == 1) \;\text{AND}\; \text{BOARD\_HB\_OK}
$$

40011 目前主要用于：
- 显示和日志
- 观察命令批次是否持续更新
- 判断是否存在陈旧命令
- 后续扩展更严格的新鲜度判断

**它还没有被作为 V3.2 第一阶段的强制使能条件。**

所以当前**不能**直接说：
> CMD_SEQ 不变化 → RT-LAB 一定立即撤销外部命令

除非后续明确增加 `CMD_SEQ 新鲜度监视` 并把它纳入最终有效性逻辑。

### 为什么当前先不强制使用 CMD_SEQ

因为 40012 已经能够判断板子通信写入是否持续工作。当前阶段的主要目标是：
> **防止板子失联后旧 40010 继续生效**

BOARD_HEARTBEAT 已经能够解决这一核心问题。

CMD_SEQ 则提供更细的信息：
- 板子是否真的持续发布新命令批次
- 命令是否重复
- 是否发生批次停滞
- 是否存在丢失或跳变

这些**更适合后续通信新鲜度研究和论文实验**。

## 十四、异常一：心跳变化，但命令序号不变化

假设 RT-LAB 观察到：
```
BOARD_HEARTBEAT: 35 → 36 → 37 → 38
CMD_SEQ:         20 → 20 → 20 → 20
```

**这可能说明：**
- 板子通信循环仍然在运行
- 但命令批次没有按设计成功推进

**需要排查：**
- CMD_SEQ 递增逻辑是否错误
- FC16 成功确认后是否正确更新
- 程序是否反复写同一个序号
- 命令发布模块是否卡住

> 在当前 V3.2 中，这**不一定**自动导致 `EXTERNAL_COMMAND_VALID=0`，但是重要异常线索。

---

## 十五、异常二：命令序号变化，但 40010 始终为 0

例如：
```
CMD_SEQ:         20 → 21 → 22 → 23
BOARD_HEARTBEAT: 35 → 36 → 37 → 38
40010:           始终为 0
```

**这通常说明：** 板子和 FC16 写入链路正常，但控制资格条件尚未满足。

**可能原因：**
- `external_enable_request = false`
- 仍处于 WAIT_VALID
- 未达到 3 个连续有效周期
- MODEL_STATUS 异常
- RT-LAB 心跳未建立或超时
- 核心测量值越界

> 📌 此时**不要优先怀疑网络**，应该检查板端状态机和异常日志。

---

## 十六、为什么 40001～40012 要用一次 FC16 整批写入

板子写入：
```
起始 offset = 0
数量 = 12
```

也就是把六路命令、AGC 诊断量、使能、序号、心跳**作为同一个通信批次发送**。

**这样设计的核心目的**，是让 RT-LAB 尽量同时获得：
- 这批控制值是什么
- 这批控制值是否允许使用
- 这是第几批控制值
- 板子当时是否仍在运行

否则，如果分别写入多个寄存器，可能出现：
```
六路功率命令已经更新
但使能仍是上一周期值
```

或者：
```
使能已经变为 1
但六路命令还没有全部更新
```

> ✅ 使用同一次 FC16 批量写入，可以**显著减少这种批次不一致风险**。

## 十七、断线场景的完整逐步过程

**初始正常状态：**
```
state          = ENABLED
40010          = 1
CMD_SEQ        = 50
BOARD_HEARTBEAT = 100
BOARD_HB_OK    = 1
EXTERNAL_COMMAND_VALID = 1
```

### 突然拔掉网线

**板子侧下一周期** —— FC03 或 FC16 失败。

板子内部立即：
```
ext_agc_enable_local = 0
valid_count = 0
```

但因为网络已断开，**无法成功将 40010=0 写到 RT-LAB**。板子随后进入 `DISCONNECTED`，并按重连间隔继续尝试连接。

**RT-LAB 侧短时间内** —— 寄存器可能仍保持：
```
40010 = 1         ← 断线前的旧值
CMD_SEQ = 50      ← 断线前的旧值
BOARD_HEARTBEAT = 100  ← 断线前的旧值
```

RT-LAB 发现 `BOARD_HEARTBEAT 长期没有变化`：
```
BOARD_HB_AGE_S 不断增加
```

超过 RT-LAB 侧配置的超时阈值后：
```
BOARD_HB_OK = 0
```

最终：
```
EXTERNAL_COMMAND_VALID = 1 AND 0 = 0
```

> ✅ 因此外部命令失效。

---

## 十八、为什么这个过程不能保证"零延迟撤销"

当网线突然断开时，RT-LAB 不能立即知道板子是否真的离线。它只能等待：
> 板子心跳在规定时间内没有继续变化

才判定超时。

所以外部命令撤销存在一个检测时间：
> 从最后一次心跳变化 → BOARD_HB_OK 变为 0

其长度由 RT-LAB 侧心跳超时阈值和模型检测周期决定。

**这是工程上不可忽略的：心跳机制能发现失联，但不是瞬时发现。**

> 📌 论文实验中可以把它定义为：
> - 板端失联检测时间
> - 外部命令最长残留时间

---

## 十九、重新连接后的完整过程

板子重连成功后**必须**进入 `WAIT_VALID`。所以第一次恢复 FC16 写入时，应包含：
```
40010 = 0
新的 CMD_SEQ
新的 BOARD_HEARTBEAT
```

由于 40001～40012 作为同一批写入，RT-LAB 会同时看到：
```
板子心跳恢复
但外部使能仍为 0
```

于是：
```
BOARD_HB_OK 可能恢复为 1
EXTERNAL_COMMAND_VALID 仍保持 0
```

之后板子重新完成 3 个连续有效周期，才会发送 `40010=1`。

> ✅ 这避免了：
> - 心跳刚恢复
> - 旧命令立即重新接管设备

## 二十、五种典型组合及其排查方向

| 40010 | CMD_SEQ | BOARD_HEARTBEAT | 主要含义 |
|-------|---------|-----------------|----------|
| 0 | 变化 | 变化 | 板子和写入正常，但尚未获得控制资格 |
| 1 | 变化 | 变化 | 当前通信安全条件基本正常 |
| 1 | 不变 | 不变 | ⚠️ 极可能是板子或通信已失效，40010 为旧值 |
| 0 | 不变 | 变化 | 板子仍活着，但命令发布逻辑可能异常 |
| 1 | 不变 | 变化 | 板子仍活着，但命令批次可能陈旧，应进一步检查 |

最后一种情况在当前 V3.2 公式中可能暂时仍得到 `EXTERNAL_COMMAND_VALID = 1`（因为 CMD_SEQ 尚未作为强制判断条件）。但从工程诊断角度，**它不应被忽略**。

## 二十一、联调时你应该观察哪些量

RT-LAB 侧至少同时观察：

| 观测项 | 用途 |
|--------|------|
| 40010 EXT_AGC_ENABLE | 板子是否申请使能 |
| 40011 CMD_SEQ | 命令批次变化 |
| 40012 BOARD_HEARTBEAT | 板子通信活性 |
| BOARD_HB_AGE_S | 心跳年龄 |
| BOARD_HB_OK | 心跳健康标志 |
| EXTERNAL_COMMAND_VALID | 外部命令最终有效性 |

**不能只盯着 40010。**

### 正常 WAIT_VALID 状态

**预期：**
```
40010 = 0
40011 持续变化
40012 持续变化
BOARD_HB_OK = 1
EXTERNAL_COMMAND_VALID = 0
```

**含义**：板子通信正常，但尚未获得命令投入资格。

### 正常 ENABLED 状态

**预期：**
```
40010 = 1
40011 持续变化
40012 持续变化
BOARD_HB_OK = 1
EXTERNAL_COMMAND_VALID = 1
```

### 板子断线

**预期：**
```
40010 可能暂时残留 1
40011 停止变化
40012 停止变化
BOARD_HB_AGE_S 持续增大
BOARD_HB_OK 在超时后变 0
EXTERNAL_COMMAND_VALID 变 0
```

### 板子恢复

**预期：**
```
40012 重新变化
40011 重新变化
40010 先保持 0
BOARD_HB_OK 恢复
EXTERNAL_COMMAND_VALID 仍为 0
```

完成连续验证后：
```
40010 变 1
EXTERNAL_COMMAND_VALID 变 1
```

## 二十二、板端日志应该怎样帮助你判断

每 5 个周期的摘要应至少包含：

| 字段 | 含义 |
|------|------|
| state | 当前状态机状态 |
| model_status | RT-LAB 模型状态字 |
| rtlab_hb | RT-LAB 心跳 |
| valid_count | 有效计数（如 2/3） |
| enable | 40010 当前值 |
| cmd_seq | 40011 当前值 |
| board_hb | 40012 当前值 |
| read/write 结果 | 本轮读写是否成功 |

**示例日志：**
```
RUN state=WAIT_VALID
    status=0x0007
    rtlab_hb=105
    valid=2/3
    enable=0
    cmd_seq=20
    board_hb=35
    read=OK
    write=OK
```

**从这一行可以判断：**
- 模型状态正常
- RT-LAB 心跳已读到
- 当前累计 2 个有效周期
- 板子尚未使能
- 命令批次和板子心跳仍在更新
- 本轮读写成功

> ⚠️ 如果只打印 `通信正常`，你无法知道板子究竟停在哪一步。

## 二十三、本轮与未来控制闭环的关系

当前 V3.2 还没有正式接入板端 AGC 和设备 Pref。

但以后外部命令选择器基本会遵循：
```
EXTERNAL_COMMAND_VALID = 1
  → 允许选择板子六路命令

EXTERNAL_COMMAND_VALID = 0
  → 不允许选择板子六路命令
  → 转入内部或安全回退路径
```

> 📌 所以 40010 和 40012 最终控制的**不是功率值本身**，而是：
> **六路外部命令是否拥有控制设备的资格。**

这相当于在板子命令和设备 Pref 之间**增加了一道安全门**。

## 二十四、论文注意点记录

### 1. 必须区分三种新鲜度

V3.2 实际上提供了三个不同维度：

| 寄存器 | 维度 |
|--------|------|
| 40010 | 控制资格是否有效 |
| 40011 | 命令批次是否持续发布 |
| 40012 | 控制器通信程序是否仍活跃 |

> 📌 论文中**不应**将三者都模糊称为"通信状态"。

### 2. 旧使能残留是实际通信风险

断线后寄存器可能保持最后值。所以：
> "最后一次收到使能 1" **不能**被解释为"当前仍然使能"

必须结合数据年龄或发送方心跳。

### 3. 心跳机制存在检测延时

| 超时阈值设置 | 影响 |
|--------------|------|
| 越短 | 故障发现更快，但误判风险更高 |
| 越长 | 误判减少，但旧命令保留时间变长 |

**这个权衡可以成为后续实验参数。**

### 4. CMD_SEQ 不能直接测量通信延时

CMD_SEQ 能够判断：
- 是否有新批次
- 批次顺序是否推进
- 是否出现重复或停滞

但它**没有携带时间戳**，因此**不能直接计算**"一条命令传输了多少毫秒"。

> 若论文要研究精确端到端延时，还需增加：
> - 时间戳
> - 发送时间
> - 接收时间
> - 或外部网络测量
>
> **不能**仅凭 CMD_SEQ 宣称得到了通信延时。

### 5. 当前 V3.2 可作为论文实验平台的安全层

后续论文可以在这套安全层之上研究：
- 心跳超时期间旧命令影响
- 命令重复
- 数据陈旧
- 恢复后的重新投入冲击
- CMD_SEQ 停滞
- 双侧状态认知不一致

但 V3.2 机制本身仍主要是工程平台基础，论文还需要控制策略或针对通信问题的改进方法。

## 二十五、本轮压缩记忆

```
40010：
  板子认为命令是否允许使用。
  它只是板子侧请求，不是 RT-LAB 最终结论。

40011：
  成功发布的命令批次号。
  只有成功 FC16 后，才推进已发布批次。

40012：
  板子主通信循环和 FC16 写入路径是否持续工作。

RT-LAB 最终基本判断：
  EXTERNAL_COMMAND_VALID
  = 40010 为 1
    且
    BOARD_HB_OK 为 1

断线时：
  40010 可能残留为 1，
  但 40012 停止变化，
  RT-LAB 通过心跳超时独立撤销外部命令。

CMD_SEQ 和 BOARD_HEARTBEAT 不同：
  一个证明命令批次发布，
  一个证明板子通信程序及写入路径活跃。

当前 CMD_SEQ 尚未作为 EXTERNAL_COMMAND_VALID
的强制条件，主要用于诊断和未来命令新鲜度判断。

恢复连接后：
  板子先写 40010=0 并重新等待连续有效周期，
  不能立即恢复外部控制。
```
