## 整体数据链（先建立全局视角）

这五张图共同完成了 RT-LAB 侧的三项任务：
1. 生成并向板子发送 V3.2 管理量和测试测量量
2. 接收并监视板子写回的三个管理量
3. 在 RT-LAB 侧独立判断板子命令是否仍然有效

整体数据链可以压缩成：

```
RT-LAB 生成：
  MODEL_STATUS、RTLAB_HEARTBEAT、测量量
                    ↓
              40101～40116
                    ↓
                  板子
                    ↓
板子写回：
  六路命令、AGC 诊断量、
  EXT_AGC_ENABLE、CMD_SEQ、BOARD_HEARTBEAT
                    ↓
              40001～40012
                    ↓
RT-LAB 监视板子心跳
                    ↓
EXTERNAL_COMMAND_VALID
```

> 📌 V3.2 暂不接入正式 AGC，核心目标是通信状态、数据有效性和安全管理；40115、40116 由 RT-LAB 产生，40010～40012 由板子产生。

> ⚠️ 截图没有展开两个 MATLAB Function 模块的内部源码，因此下面会把根据接口和 V3.2 要求可以确定的逻辑讲清楚；少数需要打开函数源码才能确认的实现细节，会单独标注。

## 一、先将五张图分成四类

| 类型 | 对应图片 | 作用 |
|------|----------|------|
| **RT-LAB 状态与心跳生成** | 图 5 | 生成 40115 和 40116，并支持故障注入 |
| **测量异常注入** | 图 4 | 人为制造 ESS1_SOC 正常或越界工况 |
| **板子管理量接收与原始监视** | 图 1 | 观察 40010、40011、40012 是否正确写入 |
| **板子心跳与命令有效性判断** | 图 2、图 3 | 计算 hb_ok、hb_age_s 和 EXTERNAL_COMMAND_VALID |

其中还要区分**三种性质**：

| 性质 | 模块 | 作用 |
|------|------|------|
| **真正参与安全判断的模块** | `Board_Heartbeat_Monitor` / `Check_EXT_AGC_ENABLE` / `AND` | 决定控制是否有效 |
| **用于故障测试的模块** | `MODEL_STATUS_MODE` 选择器 / `RTLAB_HB_FREEZE` / `SOC1_TEST_MODE` 选择器 | 验收测试用 |
| **只负责观察和打包的模块** | `Modbus_Raw_Monitor` / `double` / `Mux` / 状态向量输出 | 不参与逻辑判断 |

> 📌 **这一区分非常重要**——并非所有新增模块都会决定控制是否有效。

## 二、图 5：MODEL_STATUS 和 RTLAB_HEARTBEAT 生成模块

这张图位于 RT-LAB 向板子发送数据的方向，负责生成：
- **40115** MODEL_STATUS
- **40116** RTLAB_HEARTBEAT

### 1. MODEL_STATUS_MODE 为什么要增加

左侧有四个输入：

| 输入 | 值 |
|------|-----|
| `MODEL_STATUS_MODE` | 0 |
| `MODEL_STATUS_TEST` | 7 |
| `MODEL_STATUS_TEST1` | 1 |
| `MODEL_STATUS_TEST2` | 23 |

它们进入一个多路选择器。选择关系为：

| MODE | 输出 |
|------|------|
| 0 | 7（正常状态） |
| 1 | 1（模型未准备） |
| 2 | 23（模型故障） |

选择器输出形成 `MODEL_STATUS_raw`，通过信号标签路由到后面的 40115 寄存器映射和监视位置。

### 2. 为什么需要 7、1 和 23 三个测试值

**7 = 二进制 `00111`**

| bit | 含义 | 值 |
|-----|------|-----|
| bit0 | MODEL_RUNNING | 1 |
| bit1 | MEAS_VALID | 1 |
| bit2 | EXT_INTERFACE_READY | 1 |
| bit4 | MODEL_FAULT | 0 |

板子可以继续累计有效周期。

**1 = 二进制 `00001`**

只表示模型正在运行，但：
- `MEAS_VALID = 0`
- `EXT_INTERFACE_READY = 0`

板子应保持：
```
WAIT_VALID
40010 = 0
valid_count = 0
```

**23 = 二进制 `10111`**

前三个准备位虽然正常，但：
- `bit4 MODEL_FAULT = 1`

板子必须立即撤销外部使能。

> 📌 这些值与 V3.2 文件规定的正常、未准备、故障测试值**完全对应**。

### 3. 为什么使用选择器，而不是直接把 40115 固定为 7

如果 40115 永久固定为 7，只能验证"板子在正常状态下能否进入 ENABLED"。**无法验证：**
- 模型突然未准备时能否退出
- 模型发生故障时能否立即撤销 40010
- 状态恢复后是否重新等待 3 个周期

选择器相当于一个**模型状态故障注入开关**。它让你不需要修改板端代码，也不需要破坏真实模型，只改变 `MODEL_STATUS_MODE` 即可制造三种验收工况。

### 4. RTLAB_Heartbeat_Generator 为什么要增加

下方 MATLAB Function 模块：

| 输入 | 含义 |
|------|------|
| `time_s` | 来自 `Simulation_Time` |
| `freeze` | 来自 `RTLAB_HB_FREEZE` |

| 输出 | 含义 |
|------|------|
| `hb` | 心跳值 |

其作用应当是：

| freeze 值 | 行为 |
|-----------|------|
| 0 | 根据仿真时间每 1000 ms 推进一次心跳 |
| 1 | 保持当前心跳不再变化 |

最终输出形成 `RTLAB_HEARTBEAT_raw` 并路由到 40116。

V3.2 要求 40116 每 1000 ms 递增一次、65535 后回到 0，板子通过它判断 RT-LAB 数据是否持续刷新。

### 5. 为什么使用 Simulation_Time

心跳必须证明 **RT-LAB 实时模型本身还在持续运行**，因此使用模型的仿真时间，而不是一个与模型无关的外部计数器。

| 状态 | 表现 |
|------|------|
| 正常 Execute | Simulation_Time 持续推进 → 心跳持续变化 |
| 模型停止 / 心跳函数停止更新 | 心跳保持不变 → 板子最终判断 RT-LAB 数据冻结 |

> 📌 这使 40116 反映的是**模型运行链路**，而不仅仅是 Modbus 服务器进程仍然存在。

### 6. RTLAB_HB_FREEZE 为什么不是简单把心跳设为 0

验收重点不是检查"心跳是否等于 0"，而是检查"心跳是否长期不变化"。

冻结测试应当保持最后一个值，例如：
```
105 → 106 → 107 → 107 → 107 → 107
```

而不是不断输出新的异常值。这样可以模拟**最危险的一种情况**：
- TCP 还连接着
- FC03 还能读取
- 40115 仍可能是 7
- 测量值也仍然存在
- **但所有数据实际上已经陈旧**

板子必须依靠 40116 超时识别这种情况。

## 三、图 4：ESS1_SOC 正常值与越界值注入模块

这张图是为 V3.2 的输入测量范围检查准备的**测试装置**。

### 核心组成

| 元素 | 值 |
|------|-----|
| `SOC1_INVALID_RAW` | 12000 |
| `SOC1_NORMAL_RAW` | 6000 |
| `SOC1_TEST_MODE` | 0 或 1 |
| `Switch` 阈值 | 0.5 |
| 输出 | `Op40107` |

40107 正是 `ESS1_SOC`。

### 1. 两个原始值分别表示什么

ESS1_SOC 的比例为 `scale = 0.0001`，因此：

**正常值 6000**
$$
6000 \times 0.0001 = 0.6000
$$

表示 `ESS1_SOC = 60%`，处于 0～1 的合法范围。

**异常值 12000**
$$
12000 \times 0.0001 = 1.2000
$$

表示 `ESS1_SOC = 120%`，超过物理有效范围。

板子必须判定：
```
measurements_valid = false
40010 = 0
valid_count = 0
进入或保持 WAIT_VALID
```

> ⚠️ **不能把 1.2 限幅成 1.0 后继续使用**。V3.2 明确要求输入测量越界时判无效，而不是像输出命令一样限幅。

### 2. Switch 为什么这样连接

Simulink `Switch` 的逻辑是：

| `SOC1_TEST_MODE` | 选择 |
|------------------|------|
| ≥ 0.5 | 上方输入 12000 |
| < 0.5 | 下方输入 6000 |

所以：

| `SOC1_TEST_MODE` | 40107 输出 | SOC |
|------------------|------------|-----|
| 0 | 6000 | 0.6（正常） |
| 1 | 12000 | 1.2（异常） |

### 3. 为什么需要在 Simulink 侧做这个开关

没有这个开关时，要制造 SOC 异常，可能需要：
- 修改 JSON
- 改寄存器定义
- 修改 SOC 计算代码
- 改变储能模型

这些方法会干扰其他模块。现在只需切换一个常量：
```
0 → 1
```

就能验证完整反应链：
```
RT-LAB 输出 SOC = 1.2
        ↓
板子 FC03 读到 12000
        ↓
板子解码为 1.2
        ↓
range_check 发现越界
        ↓
40010 立即变 0
        ↓
板子退回 WAIT_VALID
        ↓
恢复 0.6 后重新等待 3 周期
```

> 📌 这就是一个标准的**单点故障注入装置**。

### 4. 为什么只故意改变 40107，其他点保持不变

图中 40106 和 40108 继续由固定测试值提供。这样可以确保：
- 只有 ESS1_SOC 发生变化
- 其他核心输入保持稳定

如果 40010 退出，就能明确判断原因是"ESS1_SOC 越界"，而不是同时有多个变量变化，导致无法定位故障来源。

图中的 206、208 属于其他通道的原始测试值，其具体数值不是这张图的核心；关键是它们在 SOC1 故障注入过程中保持不变。

## 四、图 1：接收 40010、40011、40012 并形成管理原始量监视

图 1 展示的是板子写回 RT-LAB 后的**接收和观察部分**。

### 左侧三个信号

| 信号 | 对应 |
|------|------|
| `EXT_AGC_ENABLE_raw` | 40010 |
| `CMD_SEQ_raw` | 40011 |
| `BOARD_HEARTBEAT_raw` | 40012 |

### 1. 为什么都有 raw 后缀

`raw` 表示：**从 Modbus 保持寄存器直接读出的原始数值，尚未经过逻辑判断**。

例如：
```
EXT_AGC_ENABLE_raw = 1
CMD_SEQ_raw = 20
BOARD_HEARTBEAT_raw = 35
```

此时**只能说明 RT-LAB 寄存器中读到了这些数**，还不能直接得出"外部命令一定有效、板子一定仍在线"——因为还需要后面的心跳年龄判断。

### 2. 为什么连接到 Modbus_Raw_Monitor 的 10、11、12 号输入

| 版本 | 写入范围 | 寄存器数量 |
|------|----------|------------|
| V3.1 | 40001～40009 | 9 |
| V3.2 | 40001～40012 | 12 |

新增三个点正好是第 10、11、12 个输入：

| 输入序号 | 寄存器 | 含义 |
|----------|--------|------|
| 10 | 40010 | EXT_AGC_ENABLE |
| 11 | 40011 | CMD_SEQ |
| 12 | 40012 | BOARD_HEARTBEAT |

把它们接入 Modbus_Raw_Monitor，就是为了确认：
- FC16 是否真的从 9 路扩展成 12 路
- 地址顺序是否正确
- 三个新寄存器是否被 RT-LAB 正确接收
- 原始值是否与板端日志一致

### 3. 为什么还要从同一信号处分支

每个信号同时连接到：
- `Modbus_Raw_Monitor`（原始数据显示）
- 其他安全判断模块（逻辑判断）
- 管理向量 `Mux`（状态向量输出）

这种分支**不会复制出不同数据，也不会改变原值**。同一个信号被分别用于：

| 用途 | 价值 |
|------|------|
| 原始数据显示 | 排查寄存器地址和原始传输问题 |
| 逻辑判断 | 决定控制是否有效 |
| 状态向量输出 | SC 界面集中观察 |

因此，一根线出现分叉是正常的。

### 4. mux1 为什么要增加

右侧黑色竖条 `mux1` 将多个标量信号组合成一个向量。从该图的五路连接及命名看，`modbus_management_raw_vec` 用于集中输出**五个 V3.2 管理原始量**：

| 序号 | 信号 | 来源 |
|------|------|------|
| 1 | `MODEL_STATUS_raw` | RT-LAB 自身生成 |
| 2 | `RTLAB_HEARTBEAT_raw` | RT-LAB 自身生成 |
| 3 | `EXT_AGC_ENABLE_raw` | 板子写回 |
| 4 | `CMD_SEQ_raw` | 板子写回 |
| 5 | `BOARD_HEARTBEAT_raw` | 板子写回 |

> 📌 具体向量第 1～5 项顺序，应以 Mux 自上而下的实际连接为准，后续需要写进信号说明，**不能只靠记忆**。

### 5. 为什么先 Mux，再转成 double

Modbus 原始信号可能是：
- `UINT16`
- `INT16`
- `boolean`

而 RT-LAB 监视向量或 SC 界面通常更适合接收统一的 `double` 向量。

所以：
```
多个原始管理量 → Mux 组成向量 → double 统一数据类型 → modbus_management_raw_vec
```

`double` 只改变数据类型，**不改变数值含义**。例如：
```
UINT16 的 35 → double 的 35.0
```

它不会变成工程量，也不会进行缩放。

### 6. 右侧椭圆中的"5"是什么意思

椭圆是 Simulink Outport，里面的 `5` 表示**该子系统的第 5 号输出端口**，不是单独表示寄存器 40005。该输出名称是 `modbus_management_raw_vec`。

> 📌 黑色 Mux 确实也汇集了多路管理量，但端口内部数字应理解为**端口序号**。

## 五、图 3：Monitor_Board_Heartbeat 子系统内部接口

图 3 是图 2 中 `Board_Heartbeat_Monitor` 模块的内部结构。

| 方向 | 信号 | 含义 |
|------|------|------|
| 输入 | `time_s` | 当前仿真时间 |
| 输入 | `board_hb_raw` | 40012 原始值 |
| 输入 | `timeout_s` | 超时阈值 |
| 输出 | `hb_ok` | 心跳是否正常 |
| 输出 | `hb_age_s` | 心跳年龄（秒） |

它解决的问题是：**RT-LAB 不能因为 40012 当前是一个非零数，就认为板子仍然在线；必须判断这个数最近是否持续变化**。

### 1. time_s 为什么必须输入

心跳判断不是只比较两个值，还要知道**多久没有变化**。因此需要当前仿真时间，用于计算：
$$
hb\_age\_s = time\_s - last\_change\_time
$$

### 2. board_hb_raw 是什么

它是板子写入的 `40012 BOARD_HEARTBEAT`。正常情况下可能变化为：
```
35 → 36 → 37 → 38
```

监视器需要记住上一值。当发现：
```
current_hb ≠ last_hb
```

就说明收到了一次新的板子活动证明。此时应当：
- 更新 `last_hb`
- 记录当前 `time_s` 为最近变化时间
- 将 `hb_age_s` 清零

### 3. timeout_s 为什么作为输入，而不是写死在代码中

图中超时值来自外部常量 `BOARD_HB_TIMEOUT_S = 3.5`。将它作为输入的好处是：
- 后续可以调整 3.5 秒
- 不用修改 MATLAB Function 源码
- 测试不同阈值更方便

### 4. hb_age_s 表示什么

`hb_age_s` 表示：**距离 RT-LAB 上一次观察到 BOARD_HEARTBEAT 变化，已经过去多少秒**。

它**不是**：
- 网络报文延时
- 单次 FC16 传输时间
- 板子程序执行周期

例如：

| 时间点 | 状态 |
|--------|------|
| 最近一次变化 | t = 10.0 s |
| 当前 | t = 12.4 s |
| `hb_age_s` | **2.4 s** |

### 5. hb_ok 表示什么

合理逻辑应为：

| 条件 | 行为 |
|------|------|
| 已经观察到至少一次真实心跳变化 **且** `hb_age_s ≤ timeout_s` | `hb_ok = 1` |
| 超过 3.5 秒没有变化 | `hb_ok = 0` |

### 6. 该函数内部应当接近以下逻辑

> 📌 以下是**功能伪代码**，不是对截图中源代码的逐字还原：

```matlab
if 第一次运行
    保存 board_hb_raw 作为基线
    记录当前时间
    hb_ok = 0
end

if board_hb_raw ~= 上一次心跳
    保存新的心跳
    最近变化时间 = time_s
    已观察到心跳变化 = true
end

hb_age_s = time_s - 最近变化时间

hb_ok = 已观察到心跳变化 && hb_age_s <= timeout_s
```

**还应考虑：**
- `65535 → 0` 是正常变化，因为判断的是"不相等"，不是"必须增大"
- 模型重新 Execute、仿真时间从大值回到 0 时，也应重新建立心跳基线，避免年龄计算错误

> ⚠️ 这些细节需要打开 MATLAB Function 代码最终核对。

## 六、图 2：RT-LAB 侧最终外部命令有效性判断

图 2 是五张图中最关键的**安全判断部分**。

它把"板子心跳是否正常"和"板子是否请求使能"组合成最终的 `External_Command_Valid`。

### 1. Board_HB_Time 为什么连接到心跳监视器

左上角 Clock `Board_HB_Time` 提供当前模型时间。连接：
```
Board_HB_Time → Board_Heartbeat_Monitor.time_s
```

用于计算心跳年龄。

### 2. BOARD_HB_TIMEOUT_S 为什么设为 3.5

常量 `3.5` 连接：
```
BOARD_HB_TIMEOUT_S → Board_Heartbeat_Monitor.timeout_s
```

表示 40012 超过 3.5 秒未变化，就判定板子心跳失效。

> 板子通信周期为 1 秒，3.5 秒可以容忍少量调度抖动或一次未观察到更新，但又不会让旧命令长期残留。

### 3. Check_EXT_AGC_ENABLE 为什么用"==1"

下方比较器 `EXT_AGC_ENABLE_raw == 1` 将原始寄存器转换成严格布尔条件。

原因是 40010 只允许 `0` 或 `1`。如果错误收到 `2` 或 `65535`，**不能将"非零"一律当成有效**。因此只有"恰好等于 1"才认为板子提出了有效请求。

### 4. AND 模块为什么必须存在

AND 的两个输入为：
- `Check_EXT_AGC_ENABLE`
- `hb_ok`

因此：
$$
External\_Command\_Valid = (EXT\_AGC\_ENABLE\_raw = 1) \land hb\_ok
$$

这就是 RT-LAB 侧的**独立安全判断**。

### 5. 为什么不能直接把 40010 作为最终有效信号

正常情况下：
```
40010 = 1
BOARD_HEARTBEAT 持续变化
```

外部命令有效。

但如果网线突然断开：
- 板子无法继续写入
- 40010 可能残留为 1
- BOARD_HEARTBEAT 停止变化

几秒后 `hb_ok = 0`，于是：
$$
External\_Command\_Valid = 1 \land 0 = 0
$$

RT-LAB 不再信任旧的板子命令。

> 📌 这正对应 V3.2 文件中"通信中断时板子可能无法把 40010 写 0，因此 RT-LAB 必须独立检测 40012 超时"的要求。

### 6. 三种典型组合

| 40010 | hb_ok | External_Command_Valid | 含义 |
|-------|-------|------------------------|------|
| 0 | 1 | 0 | 板子在线，但尚未允许命令投入 |
| 1 | 1 | 1 | 板子申请使能且心跳正常 |
| 1 | 0 | 0 | 40010 可能是旧值，板子已经失联 |
| 0 | 0 | 0 | 板子既未使能，也已经不在线 |

### 7. double 模块为什么较多

图中 `hb_ok` / `hb_age_s` / `External_Command_Valid` 以及其他管理信号，在送入黑色 Mux 前都转换成 `double`。

原因是 Mux 后的 `v32_rtlab_status_vec` 需要是统一类型的监视向量，便于：
- RT-LAB SC 显示
- Scope 记录
- OpComm 输出
- 数据保存

逻辑量转成 double 后：
```
false → 0.0
true  → 1.0
```

逻辑意义不变。

### 8. 两个显示为"-T-"的标签块是什么作用

截图中两个标签块没有显示完整标签名，只能确认它们**通过 Goto/From 标签引入其他 V3.2 管理信号**。

它们本身不计算、不延时，也不改变数值，只是避免在大模型中拉很长的连线。

> ⚠️ 具体是哪个信号及状态向量顺序，需要打开标签参数或检查 Mux 输入。**不能只凭该截图断言它们的准确名称**。

### 9. v32_rtlab_status_vec 为什么需要增加

该向量将 RT-LAB 侧的 V3.2 状态集中输出，例如：

| 元素 | 含义 |
|------|------|
| EXT_AGC_ENABLE 判断结果 | 板子是否申请使能 |
| BOARD_HEARTBEAT 原始值 | 板子心跳 |
| CMD_SEQ | 命令批次号 |
| hb_ok | 心跳是否正常 |
| hb_age_s | 心跳年龄 |
| External_Command_Valid | 最终有效信号 |

> 📌 具体顺序以 Mux 自上而下的连接为准。

它的价值是：**联调时不必在模型各处分别寻找状态量，可以在一个向量或 SC 界面中一次观察整个安全链**。右侧 Outport 中的"6"表示该子系统第 6 号输出端口。

板子进入 ENABLED

## 八、四个故障测试怎样贯穿五张图

### 测试一：模型未准备

**设置：** `MODEL_STATUS_MODE = 1`

| 模块 | 表现 |
|------|------|
| 图 5 输出 | 40115 = 1 |
| 板子反应 | 40010 = 0, valid_count = 0, WAIT_VALID |
| 图 1 观察 | `EXT_AGC_ENABLE_raw = 0` |
| 图 2 最终 | `External_Command_Valid = 0` |

### 测试二：模型故障

**设置：** `MODEL_STATUS_MODE = 2`

| 模块 | 表现 |
|------|------|
| 图 5 输出 | 40115 = 23 |
| 板子反应 | 识别 bit4 故障位，立即撤销 40010 |

### 测试三：核心 SOC 越界

**设置：** `SOC1_TEST_MODE = 1`

| 阶段 | 表现 |
|------|------|
| 故障时 | 40107 = 12000 → SOC1 = 1.2，板子范围检查失败，立即写 40010 = 0 |
| 恢复时（`SOC1_TEST_MODE = 0`） | 40107 = 6000 → SOC1 = 0.6 |

> ⚠️ **不能立即重新使能**，必须重新累计 3 个有效周期。

### 测试四：RT-LAB 心跳冻结

**设置：** `RTLAB_HB_FREEZE = 1`

图 5 的 40116 停止变化。板子仍可能：
- FC03 读取成功
- 40115 仍为 7
- SOC 等测量仍处于范围内

但超过 3500 ms 后，板子必须判断 RT-LAB 数据陈旧，写：
```
40010 = 0
```

### 测试五：板子掉线

停止板子程序或拔掉网线。

| 模块 | 表现 |
|------|------|
| 图 1 的 `BOARD_HEARTBEAT_raw` | 停止变化 |
| 图 3 的 `hb_age_s` | 不断增加 |
| 超过 3.5 秒 | `hb_ok = 0` |
| 图 1 的 `EXT_AGC_ENABLE_raw` | 仍残留 1 |
| 图 2 的 AND | 输出 `External_Command_Valid = 0` |

> 📌 **即使 40010 残留 1，外部命令资格也会被撤销**——这就是 V3.2 双侧监督的价值。

## 九、为什么这些模块之间的连线缺一不可

| 连线 | 缺少后的问题 |
|------|--------------|
| `Simulation_Time → Heartbeat_Generator` | 无法根据模型运行时间生成确定心跳 |
| `Freeze → Heartbeat_Generator` | 无法验收板子是否能识别 RT-LAB 数据冻结 |
| `MODEL_STATUS 选择器 → 40115` | 无法测试未准备和故障退出 |
| `SOC1 选择器 → 40107` | 无法测试核心测量越界处理 |
| `40012 → Heartbeat_Monitor` | RT-LAB 无法独立识别板子失联 |
| `Clock → Heartbeat_Monitor` | 无法计算心跳多久未变化 |
| `timeout → Heartbeat_Monitor` | 无法形成明确超时判据 |
| `40010 → ==1` | 无法将寄存器语义转成严格布尔条件 |
| `hb_ok` 和 40010 判断 → `AND` | 无法防止旧 40010 在断线后继续生效 |
| 信号 → `Raw_Monitor` | 无法排查寄存器地址和原始传输问题 |
| 状态量 → `Mux` / 向量 | SC 界面无法集中观察完整安全链 |

## 十一、最后必须核对的八个实现细节

这些是从截图中无法完全确认、但最终验收前应打开模块参数或源码核实的内容。

1. **首次读取是否只建立基线**：`Monitor_Board_Heartbeat` 第一次读取时只建立基线，必须观察到一次变化后才允许 `hb_ok = 1`。
2. **心跳判断使用"不相等"**：保证 65535→0 不误判。
3. **仿真时间从大值回到 0 时**：心跳监视器是否重新初始化。
4. **freeze=1 时**：RTLAB_Heartbeat_Generator 是否保持最后值，而不是持续输出新的数。
5. **Check_EXT_AGC_ENABLE**：是否严格判断等于 1。
6. **BOARD_HB_TIMEOUT_S 实际值**：是否确实为 3.5 秒，并与联调口径一致。
7. **状态向量元素顺序**：`modbus_management_raw_vec` 和 `v32_rtlab_status_vec` 的元素顺序是否已记录。
8. **寄存器映射确认**：MODEL_STATUS、RTLAB_HEARTBEAT 最终是否确实映射到 40115、40116，三个板端管理量是否确实来自 40010～40012。

## 十二、对后续论文最有价值的观察量

这套模块以后可以直接提供以下**实验指标**：

| 指标 | 含义 |
|------|------|
| RT-LAB 故障到板子撤销 40010 的时间 | 板子识别 RT-LAB 异常的响应速度 |

| SOC 异常被识别的时间 | 输入越界检测速度 |
| 错误使能次数 | 误使能统计 |
| External_Command_Valid 反复切换次数 | 链路稳定性 |
