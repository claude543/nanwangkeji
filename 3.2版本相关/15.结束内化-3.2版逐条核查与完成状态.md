| 40003～40004 | 两台 ESS 命令 | INT16 | -1～1 p.u. |

### 🤔 为什么必须保持不变

- **40008 必须有符号**：dP 可能为正，也可能为负，因此必须是 INT16

### ✅ 通过标准

## 四、40115 MODEL_STATUS 对应核查

### 📋 文件要求

40115 为 UINT16 状态字，无缩放：

| 位 | 含义 |
|----|------|
| bit0 | MODEL_RUNNING |
| bit1 | MEAS_VALID |
| bit2 | EXT_INTERFACE_READY |
| bit3 | INTERNAL_FALLBACK_READY |
| bit4 | MODEL_FAULT |

**可用条件：**
```
bit0、bit1、bit2 均为 1
bit4 为 0
```

**测试值：**
- 正常：7
- 未准备：1
- 故障：23

### 🤔 为什么需要它

仅仅连接成功不能证明模型可以接受外部命令。例如：
- 模型正在运行，但测量尚未准备
- 模型运行、测量有效，但外部接口尚未准备

**都不能使能。**

### ✅ 正确判断方式

**必须使用位掩码：**
```
(status & 7)  == 7
(status & 16) == 0
```

> ⚠️ **不能只判断 `status == 7`**，因为以后 bit3 或其他保留位可能为 1，而模型仍然满足基本可用条件。

### 🛠️ 板子负责

读取并解释每一个状态位。

### 🛠️ RT-LAB 负责

根据模型状态生成状态字。当前测试阶段至少能够设置：`7` / `1` / `23`。

### 🧪 测试方法

| 测试 | 输入 | 预期 |
|------|------|------|
| 正常测试 | 40115=7 | 允许累计有效周期 |
| 未准备测试 | 40115=1 | 40010=0, valid_count=0, state=WAIT_VALID |
| 故障测试 | 40115=23 | 立即退出 ENABLED，日志明确打印 MODEL_FAULT |

### 📊 当前状态

RT-LAB 侧 40115 已设置；**板子位掩码判断尚待验证**。

## 五、40116 RTLAB_HEARTBEAT 对应核查

### 📋 文件要求

| 项 | 值 |
|------|-----|
| 类型 | UINT16 |
| 缩放 | 无 |
| 更新规则 | RT-LAB 每 1000 ms 递增 1，65535 后回 0 |
| 读取频率 | 板子每 1000 ms 读取一次 |

**第一次读取：** 只保存初值，不计入有效周期
**后续判断：** 是否变化；超过 3500 ms 不变化，则立即撤销 40010

### 🤔 为什么需要它

40115 即使一直显示 7，也可能只是模型停止前留下的旧值。例如：
```
40115 = 7
40101 PCC_P = 50 kW
40107 SOC = 0.7
```

如果这些值已经 5 秒没有刷新，就不能再用于控制。

> 📌 40116 用来证明：**RT-LAB 侧的数据生成过程仍在继续**。

### ✅ 正确判断方式

- 不应要求每轮都严格加 1
- 不应要求当前值大于上一值
- 只需要：**观察到数值变化**，并记录最近一次变化时间
- 正常回绕 `65535 → 0` 也算变化

### 🤔 第一次读取为什么不能计入有效周期

- 第一次读到 105 **只能证明寄存器中存在 105**
- 第二次看到 `105 → 106` 才能证明心跳确实在运行

### 🧪 测试方法

| 测试 | 场景 | 预期 |
|------|------|------|
| 正常递增 | 105→106→107 | 板子保持心跳健康 |
| 暂时一次不变 | 105→106→106→107 | 只要未超过 3500 ms，不应立即误报 |
| 冻结超时 | 105 保持超过 3500 ms | 40010=0, valid_count=0, ENABLED→WAIT_VALID |
| 恢复 | 恢复递增后 | 不能立即使能，必须重新累计 3 个有效周期 |

### 📊 当前状态

RT-LAB 心跳生成逻辑已设置；板端**首次读取、超时和回绕判断尚待验证**。

## 七、40010 EXT_AGC_ENABLE 对应核查

### 📋 文件要求

| 值 | 含义 |
|----|------|
| 0 | RT-LAB 不得使用板子命令 |
| 1 | 板子认为当前通信和数据条件满足 |

### 🤔 为什么它不是最终有效结论

40010 只表达：**板子一侧认为命令有效**。

如果网线突然断开，板子虽然在本地已经令使能为 0，却可能无法将 0 写到 RT-LAB。**RT-LAB 中的 40010 可能残留为 1。**

因此 RT-LAB 最终应结合板子心跳：
```
EXTERNAL_COMMAND_VALID
= (40010 == 1)
  AND
  BOARD_HB_OK
```

### 🛠️ 板子负责

根据状态机条件生成 0 或 1。

### 🛠️ RT-LAB 负责

读取 40010，**但不能只依赖 40010**。

### ✅ 通过标准

| 状态 | 行为 |
|------|------|
| WAIT_VALID | 40010 始终为 0 |
| 连续 3 个有效周期后 | 40010 变为 1 |
| 任一异常 | 立即准备写 0 |

### 📊 当前状态

RT-LAB 的 EXTERNAL_COMMAND_VALID 基本逻辑已设置；**板子 40010 生成和联合测试待完成**。

## 八、40011 CMD_SEQ 对应核查

### 📋 文件要求

CMD_SEQ 表示**成功发布的命令批次号**。

**规则：**
- 每次 FC16 成功后，下一次发送序号加 1
- 测试值不变化，序号仍需增加
- FC16 失败，不视为成功发布
- 65535 后回 0

### 🤔 为什么存在

它证明：**板子是否持续成功发布新的完整控制批次**。

它与命令数值是否变化无关。例如六路命令连续 10 秒完全相同，CMD_SEQ 仍应持续增加，因为板子每秒都在重新确认并发布这一批命令。

### 🎯 当前 V3.2 中的作用

目前主要用于：
- 日志
- 显示
- 命令批次诊断
- 以后识别重复或陈旧命令

> 📌 **当前文件没有规定**它必须直接参与 `EXTERNAL_COMMAND_VALID`，所以当前**不能自行增加**"CMD_SEQ 不变一次就立即失效"这种要求。

### ✅ 通过标准

| 场景 | 预期 |
|------|------|
| 成功写入 | 序号推进 |
| 写入失败 | 成功发布序号不推进 |
| 65535→0 | 正常 |

### 📊 当前状态

等待板端程序验证。

## 九、40012 BOARD_HEARTBEAT 对应核查

### 📋 文件要求

- 每个通信循环递增 1
- 65535 后回 0
- WAIT_VALID 和 ENABLED 都持续更新

### 🤔 为什么 WAIT_VALID 也要更新

WAIT_VALID 只表示命令尚未取得控制资格，**不表示板子程序故障**。因此可能出现：
```
40010 = 0
40012 持续变化
```

这表示：板子通信正常，只是仍在等待有效条件。

### 🛠️ RT-LAB 怎样使用

RT-LAB 观察 40012 是否持续变化，并计算：
```
BOARD_HB_AGE_S
BOARD_HB_OK
```

心跳停止超时后：
```
BOARD_HB_OK = 0
EXTERNAL_COMMAND_VALID = 0
```

### ⚠️ 需要补充明确的一点

上传文件规定 RT-LAB 应独立检测 40012 超时，**但没有明确写出 RT-LAB 侧的板子心跳超时阈值**。

板子检查 RT-LAB 心跳的阈值明确为 3500 ms；RT-LAB 检查板子心跳的阈值也需要在最终模型说明或需求中明确，例如：
```
BOARD_HEARTBEAT_TIMEOUT_S
```

否则验收时无法准确判断多少秒后 `BOARD_HB_OK` 应该变 0。

### 📊 当前状态

RT-LAB 侧 BOARD_HB_AGE_S、BOARD_HB_OK 已设置；**阈值和首次心跳建立规则仍应在联合测试前再次确认**。

## 十、三状态状态机对应核查

### 📋 文件要求

```
DISCONNECTED
WAIT_VALID
ENABLED
```

| 状态 | 含义 |
|------|------|
| DISCONNECTED | Modbus 未连接或连接已中断 |
| WAIT_VALID | 连接成功，但数据尚未连续验证通过 |
| ENABLED | 通信、模型状态、心跳和测量数据连续有效 |

### 🤔 为什么必须分三种状态

只使用"连接/断开"两个状态，无法表达：
- 网络已经连接，但模型还没准备好
- 通信正常，但 SOC 测量越界

因此需要中间状态 WAIT_VALID。

### 正常状态路径

```
程序启动 → DISCONNECTED
连接成功 → WAIT_VALID
连续 3 个有效周期 → ENABLED
```

### 异常路径

| 触发条件 | 状态变化 |
|----------|----------|
| 数据或模型异常 | ENABLED → WAIT_VALID |
| 连接中断 | ENABLED 或 WAIT_VALID → DISCONNECTED |
| 连接恢复 | DISCONNECTED → WAIT_VALID |

> 📌 **不能直接恢复到 ENABLED**。

### 📊 当前状态

板端状态机**尚待工程师实现和验收**。

## 十一、WAIT_VALID 六项检查对应核查

### 📋 文件要求每周期检查

1. FC03 及响应格式正常
2. bit0、bit1、bit2 均为 1
3. bit4 为 0
4. RTLAB_HEARTBEAT 持续变化且未超时
5. range_check=true 的点均未越界
6. external_enable_request=true

> 只有**全部条件连续满足 3 个周期**才进入 ENABLED。

### 🎯 这六项分别证明什么

| 条件 | 证明内容 |
|------|----------|
| FC03 正常 | 本轮数据完整收到 |
| ready 位正常 | 模型运行、测量和接口准备好 |
| fault 位为 0 | 模型未主动报告故障 |
| 心跳健康 | 数据不是冻结的旧值 |
| 核心测量有效 | 工程量没有明显错误 |
| external request=true | 用户确实申请外部投入 |

### 💡 一个重要理解

> "全部条件连续 3 周期"**不是只检查五个测量点**。其中任何一项失败，都应：`valid_count = 0`。

### 📊 当前状态

需求明确；板端逻辑**待验证**。

## 十二、连续 3 个有效周期对应核查

### 📋 文件要求

默认：`valid_cycles_before_enable = 3`

### 🤔 为什么需要

防止连接恢复或数据短暂正常时立即投入。

### ✅ 正常例子

```
第一次心跳读取：只保存，valid=0
观察到心跳变化：valid=1
下一周期正常：valid=2
下一周期正常：valid=3
进入 ENABLED
```

> 📌 因此，从第一次成功读取开始，**通常需要至少四次读取**才能完成：心跳基线 + 三个有效周期。具体实际时间还取决于连接成功与通信循环的相位。

### ✅ 异常中断例子

```
正常：1
正常：2
异常：0
恢复：1
正常：2
正常：3
```

> ⚠️ **不能把异常前后的正常周期拼接**。

### 📊 当前状态

待板端联合验证。

## 十三、输入有效性与输出限幅对应核查

### 📋 文件要求

| 类型 | 处理方式 |
|------|----------|
| V3.1 输出命令越界 | 限幅到边界，继续发送 |
| V3.2 输入测量越界 | 不得限幅后继续使用，判定 `measurements_valid=false`，40010=0，valid_count=0，退回 WAIT_VALID |

### 🤔 为什么处理完全不同

**输出命令**是板子自己的要求，可以主动修正。

**输入测量**是系统状态报告，越界可能表示：
- 地址错误
- 缩放错误
- 类型错误
- 模型信号错误
- 数据尚未准备

> ⚠️ **把 SOC 1.2 限幅成 1.0 会隐藏真实故障**。

### 📊 当前状态

需求理解已经明确；**板端实现待验证**。

## 十五、测量范围对应核查

### 📋 当前文件规定

| 点 | 范围 | 是否强制 |
|----|------|----------|
| PCC_P | -1000～1000 kW | ✅ 是 |

### ⚠️ 必须区分三种范围


**例如：**
- SOC=0.1 在 0～1 内，**所以测量有效**
- 但如果 AGC 的 SOC 下限为 0.2，则 AGC 应**禁止继续放电**
- **不能因为低于 0.2 就把 SOC 测量判为通信错误**

## 十六、通信周期对应核查

### 📋 文件要求

```
通信周期：1000 ms
```

每个周期完成：
```
FC03 读取 → 解码 → 检查 → 状态机更新 → FC16 写入
```

### 🤔 它不是什么

它**不是**：
- RT-LAB 电气模型固定步长
- AGC 控制周期
- 网络端到端延时

它是**板子和 RT-LAB 进行状态交换与安全判断的周期**。

### ⚠️ 文件中存在的一处需要补全

上传文件虽然规定通信周期为 1000 ms，**但 JSON 字段列表里没有明确给出通信周期参数名**。

最终需求应明确使用一个字段，例如：
```
"send_interval_ms": 1000
```
或
```
"communication_cycle_ms": 1000
```
并与现有程序字段保持一致。

> 📌 否则工程师可能把 1000 ms 硬编码，或者继续沿用旧字段但文档没有说明。

## 十八、任一次 FC03 或 FC16 失败对应核查

### 📋 文件要求

**任一次失败立即：**
```
ext_agc_enable_local = 0
valid_count = 0
```

| 情况 | 处理 |
|------|------|
| TCP 仍然可写 | 本周期尝试写 40010=0 |
| 连接已经中断 | 进入 DISCONNECTED，由 RT-LAB 通过 40012 心跳超时独立失效 |

**连续失败达到 3 次：**
```
关闭并重建 TCP 连接
```

### 🤔 为什么一次失败就撤销，但三次才重连

- **一次失败**说明：本周期的数据或命令不再完整可信 → 立即撤销控制资格
- **三次连续失败**说明：当前连接很可能需要重建 → 关闭 TCP

### ⚠️ 文件中另一处需要进一步明确

文件没有非常明确地写出：**单次 FC03 或 FC16 失败、但 TCP 尚未确认断开时，状态机具体进入哪个状态**。

从整体逻辑看，最合理、也与前面要求一致的处理应明确为：

| 当前状态 | 后续处理 |
|----------|----------|
| ENABLED | 立即退回 WAIT_VALID |
| 已确认连接丢失 | 进入 DISCONNECTED |

> 📌 建议在正式验收口径中固定这一点。

## 二十三、论文注意点汇总

### 1. V3.2 提供的是安全准入层

完整层次应写成：
```
Modbus 传输层
→ 工程量编解码层
→ 数据有效性和新鲜度层
→ 外部命令准入层
→ 后续控制算法层
```

V3.2 主要完成第三、第四层。

### 2. "失联检测时间"不是通信延时

3500 ms 表示心跳停止多久后判失效。**它不是一条 Modbus 报文实际传输所需时间**。

### 3. 断线后存在旧命令残留窗口

从板子最后一次心跳到 RT-LAB 判定超时之间，旧寄存器可能继续保留。

> 📌 这一时间窗口以后应作为通信故障实验的重要观察对象。

### 4. 慢投入与快退出可以量化

后续可记录：
- 异常到 40010 撤销的时间
- 异常到 EXTERNAL_COMMAND_VALID 撤销的时间
- 恢复到重新使能的时间
- 错误使能次数
- 状态反复切换次数

### 5. CMD_SEQ 不等于时间戳

它能证明批次推进，**但不能直接计算端到端延时**。研究精确延时仍需时间戳或外部计时。

### 6. V3.2 本身不等于论文创新

它是 RT-LAB 双向硬件在环平台的**安全基础**。

论文仍需要：
- 基础控制策略
- 通信异常问题
- 改进方法
- 实时硬件在环验证
