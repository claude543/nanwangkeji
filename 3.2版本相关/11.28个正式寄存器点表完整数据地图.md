# V3.2完整数据地图——28个寄存器分别从哪里来、到哪里去、为什么存在

## 新阶段第二轮内化

上一轮解决了总体通信结构：

```text
板子作为Modbus TCP客户端
主动读取RT-LAB测量量
再主动写入控制与管理量
```

这一轮把整个通信链路中的28个寄存器彻底拆开。

本轮重点不是背地址，而是建立以下认识：

> 每个寄存器都应当具有明确的来源、物理含义、编码方式、使用者和安全作用。

学完后，你看到任意一个寄存器，应该能回答：

- 谁生成它？
- 谁读取它？
- 它是什么工程量？
- 它是测量、命令、诊断还是管理数据？
- V3.2是否用它决定40010？
- 它异常时应当发生什么？

V3.2维持原有40101～40114和40001～40009定义，并增加40115、40116以及40010～40012。正式AGC尚未接入。

---

## 一、先用"两组文件柜"理解整个点表

可以把OP5700中的Modbus寄存器看成两个文件柜。

### 第一个文件柜：40101～40116

这个文件柜由RT-LAB填写。

里面放的是：

```text
微电网当前测量
设备当前状态
模型是否可用
RT-LAB是否仍在运行
```

板子每个通信周期主动读取一次。

数据方向是：

```text
RT-LAB模型 → 40101～40116 → 板子读取
```

### 第二个文件柜：40001～40012

这个文件柜由板子填写。

里面放的是：

```text
六路设备命令
AGC诊断结果
外部控制投入请求
命令批次号
板子运行心跳
```

数据方向是：

```text
板子 → 40001～40012 → RT-LAB读取
```

因此可以先压缩成：

```text
401xx：
现场给控制器的"状态报告"

400xx：
控制器给现场的"命令和健康证明"
```

## 二、地址40101和offset=100为什么不是矛盾

板子读取时使用：

```text
FC03
起始offset=100
数量=16
```

对应用户习惯中的 `40101～40116`。

原因是Modbus报文中通常使用从0开始的偏移地址。

对应关系为：

| 用户地址 | offset |
| ----: | ----: |
| 40001 | 0 |
| 40002 | 1 |
| …… | …… |
| 40101 | 100 |
| 40116 | 115 |

所以 `FC03` 读取offset 100、数量16，就是读取 `40101～40116`。板子写入时 `FC16` 写offset 0、数量12，就是写入 `40001～40012`。

另外，当前项目中的40101～40116仍然通过 `FC03` 读取。不能因为编号以401开头，就误认为必须使用FC04输入寄存器。

## 四、40101：PCC有功功率

```text
名称：PCC_P
类型：INT16
缩放：0.1 kW/count
有效范围暂定：-1000～1000 kW
range_check = true
```

它回答：微电网现在通过公共连接点与上级电网交换多少有功功率？

它是当前基础AGC最关键的反馈量。基础AGC利用它计算 `dP = P_target - P_PCC`。所以如果40101错误，板子后续计算的整个调节方向和调节量都会错误。

### 为什么必须用INT16

因为PCC功率可能有正有负。

例如 `PCC_P = -70.5 kW`，编码过程：`-70.5 ÷ 0.1 = -705 count`。板子读取到16位寄存器后，应按INT16解释为-705，再乘0.1恢复：`-705 × 0.1 = -70.5 kW`。

V3.1已经实际验证过：RT-LAB发送 `0xFD3F` → 板子按INT16解释为-705 → 解码为-70.5 kW。

### PCC符号仍需做物理试验确认

当前通信点表采用的约定是：**正值：购电；负值：反送**。但在后续把基础AGC正式接入板子前，还必须做一次确定性的模型试验——固定其他设备，提高一台PV的Pref，观察40101 PCC_P是增大还是减小。原因是通信点表的符号约定必须与AGC内部的控制方向完全一致。

V3.2当前只要求正确、稳定地传输40101。它暂时不负责解决AGC内部是否需要对40101取反的问题。这是V4/V5前必须完成的接口一致性确认。

## 五、40102：PCC无功功率

```text
名称：PCC_Q
类型：INT16
缩放：0.1 kvar/count
有效范围暂定：-1000～1000 kvar
range_check = false
```

它回答：微电网当前与上级电网交换多少无功功率？

基础有功AGC目前不使用它，因此V3.2第一阶段正常读取、正常解码、正常打印，但不参与40010投入判断。

这不代表PCC_Q没有价值。以后接入AVC、电压无功控制、功率因数控制时，它会成为关键反馈量。

## 六、40103：PCC电压

```text
名称：PCC_V
类型：UINT16
缩放：1 V/count
有效范围暂定：8000～12000 V
range_check = false
```

假设PCC线电压为10000 V，原始寄存器就是10000（缩放1 V/count）。它目前是辅助监测量，不参与基础有功AGC。

虽然文档中预留了8000～12000 V的有效范围，但当前 `range_check = false`。这是因为还要确认模型输出的是线电压还是相电压、是瞬时值还是有效值、具体测量位置、以及模型启动过程中是否短时为0。在这些语义没有全部冻结前，不宜让40103决定40010。

---

## 七、40104：PCC频率

```text
名称：PCC_F
类型：UINT16
缩放：0.01 Hz/count
有效范围暂定：45～55 Hz
range_check = false
```

例如 `49.98 Hz` 编码为 `49.98 ÷ 0.01 = 4998`。板子读到4998后恢复 `4998 × 0.01 = 49.98 Hz`。它目前仍是辅助量，以后研究低频减载、孤岛运行、频率恢复等问题时才可能成为强制输入。

---

## 八、40105和40106：两台光伏最大可用出力

```text
40105：PV1_P_MAX
40106：PV2_P_MAX
类型：UINT16
缩放：0.1 kW/count
有效范围：0～100 kW
range_check = true
```

它们不是光伏实际功率，而是当前光照等条件下，每台光伏最多能够发多少功率。

例如 `PV1_P_MAX = 72.5 kW`，原始寄存器为 `725`，板子恢复 `725 × 0.1 = 72.5 kW`。

### 为什么必须强制检查

当前基础AGC需要用它们确定光伏功率上限。如果错误读取 `PV1_P_MAX = 500 kW` 而实际设备额定只有100 kW，算法可能形成不合理命令。因此任何一个越出 `0～100 kW` 范围的值，都应当立即导致 `measurements_valid = false`、`40010 = 0`、状态进入或保持 `WAIT_VALID`。

### 最大可用出力与实际功率的区别

假设 `PV1_P_MAX = 80 kW`，`PV1_P_MEAS = 50 kW`，含义分别是"最多能够发80 kW"和"现在实际发50 kW"。二者不能互相替代。当前基础AGC代码主要使用 `PV1_P_MAX` 和 `PV2_P_MAX`，并利用自身保存的上一轮命令状态估算光伏运行点。当前基础AGC尚未使用40109、40110实际功率反馈。

## 九、40107和40108：储能SOC

```text
40107：ESS1_SOC
40108：ESS2_SOC
类型：UINT16
缩放：0.0001/count
单位：p.u.
有效范围：0～1
range_check = true
```

例如 `SOC = 0.75`，编码为 `0.75 ÷ 0.0001 = 7500`。板子读到7500后恢复 `7500 × 0.0001 = 0.75`。

### 为什么有效范围是0～1，而不是0.2～0.9

必须区分两个概念：

- **测量物理合法范围**：`0 ≤ SOC ≤ 1`，这是V3.2数据有效性判断。
- **AGC允许运行边界**：例如 `SOC_min = 0.2`、`SOC_max = 0.9`，这是控制算法约束。

所以 `SOC = 0.10` 虽然低于AGC放电下限，但它仍然是一个合法的SOC测量。正确处理是：V3.2认为测量有效，AGC禁止继续放电。不能因为SOC低于0.2就认为通信数据损坏。而 `SOC = 1.20` 已经超出物理可能范围，V3.2必须认为数据无效。

## 十、40109～40114：六台设备实际有功功率

|    地址 | 名称            | 当前推荐范围   |
| ----: | ------------- | ---------- |
| 40109 | `PV1_P_MEAS`  | 0～100 kW  |
| 40110 | `PV2_P_MEAS`  | 0～100 kW  |
| 40111 | `ESS1_P_MEAS` | -100～100 kW |
| 40112 | `ESS2_P_MEAS` | -100～100 kW |
| 40113 | `EV1_P_MEAS`  | -100～0 kW |
| 40114 | `EV2_P_MEAS`  | -100～0 kW |

全部使用 `INT16`、`0.1 kW/count`。它们表示设备真正实现的功率，不是板子下发的功率指令。

### 光伏实际功率

40109、40110：正值表示发电。例如 `PV1_P_MEAS = 48.3 kW → raw = 483`。

### 储能实际功率

40111、40112：正值表示放电，负值表示充电。例如 `ESS1_P_MEAS = -40 kW` 表示储能1正在吸收40 kW充电，原始有符号值为 `-400`。

### EV实际功率

40113、40114：负值表示充电，0表示停止充电。例如 `EV1_P_MEAS = -60 kW` 表示EV1吸收60 kW。

## 十一、为什么已经传实际功率，但当前基础AGC暂时不用

这是之前已经校正过的重要问题。当前基础AGC函数没有六台设备实际功率输入。它使用上一轮Ppv命令、上一轮Pess命令、上一轮Pev命令作为设备当前运行点的估计。

所以40109～40114当前主要用于：监测设备响应、比较命令与实际功率、验证设备是否跟踪命令、形成后续论文实验数据、为未来基于实测反馈的裕度重估预留接口。它们在V3.2第一阶段 `range_check = false`，仍会读取、解码和打印，但不会阻止40010投入。

### 为什么保留它们很重要

以后形成控制闭环后，可以比较 `40001 Ppv1命令` 与 `40109 PV1实际功率`。例如命令为0.8 p.u.、额定功率100 kW、理论命令80 kW，但实际功率只有65 kW。这说明设备没有完全跟踪命令，原因可能是光伏最大可用出力不足、本地限幅、设备动态滞后、通信延迟或模型故障。这种"命令—实际响应差异"正是RT-LAB硬件在环实验相对于纯算法仿真的重要价值。

## 十二、40115：模型状态字

```text
名称：MODEL_STATUS
类型：UINT16
无缩放
```

它不是普通测量量。它回答的是：RT-LAB模型当前是否具备接受外部控制的基本条件？

各位含义：

```text
bit0：MODEL_RUNNING
bit1：MEAS_VALID
bit2：EXT_INTERFACE_READY
bit3：INTERNAL_FALLBACK_READY
bit4：MODEL_FAULT
```

板子要求 `bit0`、`bit1`、`bit2` 全部为1，并且 `bit4` 为0。40115不使用普通的 `valid_min` / `valid_max` 判断，而是按二进制位判断。这一点将在下一轮深入。

---

## 十三、40116：RT-LAB心跳

```text
名称：RTLAB_HEARTBEAT
类型：UINT16
无缩放
```

正常变化：`0 → 1 → 2 → … → 65535 → 0`。它不代表任何电气工程量。它只回答：RT-LAB侧模型和心跳生成逻辑是否还在持续向前运行？

40116不做范围检查，因为0～65535中的每一个值都可能合法。板子只判断它是否在规定时间内发生变化。所以 `105` 本身没有"正常"或"异常"的含义，只有 `105 → 106 → 107` 才能证明数据仍在刷新。

---

## 十四、40101～40116的三层分类

这是这一轮最重要的分类。

### 第一类：AGC核心输入

```text
40101 PCC_P
40105 PV1_P_MAX
40106 PV2_P_MAX
40107 ESS1_SOC
40108 ESS2_SOC
```

作用：当前基础AGC直接需要。默认 `range_check = true`。任一点越界立即撤销40010。

### 第二类：辅助监测量

```text
40102 PCC_Q
40103 PCC_V
40104 PCC_F
40109～40114 六台设备实际功率
```

作用：正常读取和记录，但V3.2第一阶段不参与40010判断。默认 `range_check = false`。

### 第三类：通信与模型管理量

```text
40115 MODEL_STATUS
40116 RTLAB_HEARTBEAT
```

作用：决定模型是否具备外部控制资格，判断RT-LAB数据是否持续刷新。它们不按普通工程量范围判断。

V3.2文档明确按这三类思想对输入进行分级。

---

## 十五、P_target为什么不在40101～40116中

当前基础AGC还有一个重要输入 `P_target`，但当前点表中没有设置专门的目标功率寄存器。

V3阶段规划是将以下参数先放在板子JSON中：

```text
P_target
P_dead
P_unit
SOC_min
SOC_max
Ts_agc
PV_init
EV_init
```

所以当前数据来源是：**动态系统状态由RT-LAB通过401xx发送，算法配置和目标由板子JSON提供**。

这说明当前P_target不是运行中由RT-LAB实时下发的。以后若研究计划曲线、调度目标动态变化、峰谷控制或联络线功率计划，可能需要把目标值增加到通信点表中，但这不属于V3.2任务。

## 十七、40001和40002：两台PV功率命令

范围：0～1 p.u.，缩放0.0001。例如 `Ppv1_pu = 0.30` 编码为 `3000`。RT-LAB读取3000后解码 `3000 × 0.0001 = 0.30 p.u.`。如果额定功率为100 kW，则对应30 kW。

V3.2中正式AGC尚未进入板子。所以40001、40002可能仍由 `test_mode` 产生固定测试值，用于验证编码、FC16写入、RT-LAB接收和工程量解码。

---

## 十八、40003和40004：两台ESS功率命令

范围：-1～1 p.u.。**正值：放电；负值：充电**。

例如 `Pess1_pu = -0.40` 编码为有符号值 `-4000`。如果RT-LAB原始显示使用无符号方式显示16位字，可能看到 `65536 - 4000 = 61536`。这不表示功率是61536 p.u.。正确解释是：原始16位61536，按INT16解释为-4000，乘0.0001得 `-0.40 p.u.`。

---

## 十九、40005和40006：两台EV功率命令

范围：-1～0 p.u.。**负值：充电；0：停止充电**。

例如 `Pev1_pu = -0.60` 编码为 `-6000`，RT-LAB原始无符号显示可能为 `59536`，按INT16解码后才是 `-0.60 p.u.`。这一点曾经在旧资料中存在符号冲突，目前修正版以"EV负值表示充电"为准。

---

## 二十、40007：AGC状态

```text
名称：AGC_STATUS
类型：INT16
无缩放
范围：-2～2
```

含义：

- 0：死区内或未执行正式调节
- +1：正向调节，资源基本满足
- -1：反向调节，资源基本满足
- +2：正向调节资源不足
- -2：反向调节资源不足

它是诊断量，不是设备功率命令。RT-LAB显示它的目的，是让你知道板子中的AGC本轮做了什么判断。V3.2阶段它仍可由测试模式生成固定值。

---

## 二十一、40008：AGC初始偏差dP

```text
名称：DP_KW
类型：INT16
缩放：0.1 kW/count
```

它可以为正也可以为负。例如 `dP = 25.5 kW → raw = 255`，`dP = -25.5 kW → raw = -255`。

它表示最近一次AGC更新开始时的偏差，不是未分配量，也不一定是RT-LAB当前每个仿真步长的实时偏差。

---

## 二十二、40009：未分配需求remain

```text
名称：REMAIN_KW
类型：UINT16
缩放：0.1 kW/count
范围：0～6553.5 kW
```

例如 `remain = 3.2 kW → raw = 32`。它没有正负号，方向由 `dP` 或 `AGC_STATUS` 表达。remain只表示当前算法完成资源分配后，还有多少需求没有分配出去。它不等于当前PCC实时误差。

---

## 二十三、40010：外部AGC有效请求

```text
名称：EXT_AGC_ENABLE
类型：UINT16
只能为0或1
```

含义：

- **0**：板子认为当前命令不得使用
- **1**：板子认为当前通信、模型、心跳和测量条件满足

必须注意：**40010是板子提出的"有效请求"，不是RT-LAB最终的有效结论**。RT-LAB还要检查 `BOARD_HEARTBEAT` 是否正常。

因此最终可以形成：

```text
EXTERNAL_COMMAND_VALID = (40010 == 1) 且 BOARD_HB_OK
```

即使40010寄存器中残留1，只要板子心跳超时，RT-LAB仍应判定外部命令无效。

---

## 二十四、40011：命令批次号

```text
名称：CMD_SEQ
类型：UINT16
范围：0～65535后回0
```

它回答：这是板子成功发布的第几批控制数据？例如 `20 → 21 → 22 → 23`，说明控制命令批次持续发布。即使40001～40009数值没有发生变化，只要完成了一次新的成功写入，序号仍应向前变化。

### FC16失败时为什么不能算新批次

假设板子准备发送 `CMD_SEQ = 23`，但FC16写入失败。OP5700并没有确认收到这一批完整数据，因此不能认为第23批命令成功发布。下一次重试时，命令序号的处理必须符合"成功发布后才推进"的原则。

40011证明的是"命令批次是否持续成功发布"，不是单纯证明板子程序还活着。

---

## 二十五、40012：板子心跳

```text
名称：BOARD_HEARTBEAT
类型：UINT16
范围：0～65535后回0
```

它回答：板子主通信程序是否仍在持续执行通信循环？

在 `WAIT_VALID` 期间，即使40010仍为0，40012也应当持续变化。原因是板子虽然尚未获得外部控制资格，但板子程序仍然正常运行。所以 `40010 = 0`、`40012` 持续变化是完全可能且正常的。

---

## 二十六、40010、40011、40012的区别

这三个量可以用"司机和车辆"类比。

### 40012：司机是否还醒着

`BOARD_HEARTBEAT` 证明板子程序还在运行。

### 40011：是否持续送出了新批次货物

`CMD_SEQ` 证明新的命令批次在持续成功发布。

### 40010：当前货物是否允许使用

`EXT_AGC_ENABLE` 证明板子认为这批命令满足投入条件。

因此可能出现：

**情况一**：`40012` 变化，`40011` 变化，`40010 = 0`。含义：板子正常运行，命令批次正常写入，但模型状态或测量条件不满足，所以命令不得采用。

**情况二**：`40012` 停止，`40010` 旧值仍为1。含义：板子可能已经掉线或程序停止，40010是残留旧值，RT-LAB必须独立撤销命令有效性。

**情况三**：`40012` 变化，`40011` 长期不变。可能表示板子程序仍在运行，但控制命令没有持续成功发布。这种情况后续需要通过日志和实现规则进一步判断。

## 二十七、一次完整数据生命周期

现在把28个点串起来。

### 第一步：RT-LAB模型产生信号

例如当前模型计算出 `PCC_P = -70.5 kW`、`PV1_P_MAX = 80 kW`、`ESS1_SOC = 0.75`、`PV1` 实际功率 = 50 kW、`MODEL_STATUS = 7`、`RTLAB_HEARTBEAT = 105`。

### 第二步：RT-LAB编码到40101～40116

```text
PCC_P = -70.5     → -705 count
PV1_P_MAX = 80    → 800 count
SOC = 0.75        → 7500 count
```

### 第三步：板子发送FC03

读取offset = 100，数量 = 16，一次取得40101～40116。

### 第四步：板子解码

板子根据每个点的 `INT16/UINT16`、`scale`、`unit` 恢复成工程量。

### 第五步：板子分类判断

板子检查 `MODEL_STATUS`、`RTLAB_HEARTBEAT`、五个核心输入范围、`external_enable_request`、连续有效周期数。辅助点仍正常保留，但暂不参与总有效性。

### 第六步：板子准备40001～40012

V3.2阶段可能为：40001～40009为测试值，40010为0或1，40011为命令序号，40012为板子心跳。

### 第七步：板子进行输出限幅和编码

```text
ESS命令 = -0.4   → -4000
dP = 25.5        → 255
remain = 3.2     → 32
```

### 第八步：板子发送FC16

写offset = 0，数量 = 12，将40001～40012作为一个连续批次写入。

### 第九步：RT-LAB解码和显示

RT-LAB得到六路功率命令、AGC状态、dP、remain、外部使能、命令序号、板子心跳。

### 第十步：RT-LAB判断外部命令资格

当前至少结合 `40010 EXT_AGC_ENABLE` 和 `40012 BOARD_HEARTBEAT`，得到 `EXTERNAL_COMMAND_VALID`。但V3.2仍未把正式板端AGC接入六台设备Pref，所以这一步是在建立安全条件，并不是最终控制闭环。

---

## 二十八、故事串联：现场报表、调度指令和安全封条

把OP5700看作微电网现场，把板子看作调度中心。

现场每秒更新一份报告：PCC功率、电压、频率、光伏能力、储能SOC、六台设备实际功率、模型状态、现场心跳。这份报告就是 `40101～40116`。

调度中心读取报告后，准备一份指令：六台设备应该执行多少功率、AGC当前处于什么状态、误差是多少、还有多少未分配。这部分是 `40001～40009`。

但是指令还要贴三个标签：

- **40010**：这份指令现在是否允许使用
- **40011**：这是第几批指令
- **40012**：调度中心是否仍在持续运行

所以V3.2不是只增加三个数字，而是为命令增加**有效标签、批次标签和发送者健康证明**。

## 二十九、本轮最容易混淆的九个问题

### 1. `PV_P_MAX` 不是PV实际功率

40105、40106：最大能力。40109、40110：实际输出。

### 2. 设备实际功率不是设备命令

40001～40006：板子要求设备做什么。40109～40114：设备实际上做了什么。

### 3. 当前基础AGC尚未使用六台实际功率

这些点当前主要用于监测和以后改进。

### 4. SOC有效范围不是SOC控制边界

V3.2测量有效范围：0～1。AGC运行约束：例如0.2～0.9。

### 5. P_target不在401xx点表中

当前从板子JSON配置获得。

### 6. 40007～40009不是通信管理量

它们是 `AGC_STATUS`、`dP`、`remain`。通信管理量是新增的40010～40012。

### 7. 40010不是最终有效结论

它只是板子侧的有效请求。

### 8. 40011不是板子心跳

它证明命令批次持续发布。

### 9. 40012不证明命令一定可用

它只证明板子通信程序仍在运行。

## 三十、本轮论文注意点

### 1. 命令与实际功率必须分别记录

未来论文不能只展示板子命令曲线，还应同时展示设备实际功率曲线和PCC功率曲线，这样才能证明控制命令真正产生了物理响应。

### 2. 通信有效性应基于不同层级数据

V3.2将数据分为控制必需核心数据、辅助监测数据、通信管理数据。这种分级思想可以用于论文中的控制接口设计说明。

### 3. 命令新鲜度与程序存活是两个问题

`CMD_SEQ` 和 `BOARD_HEARTBEAT` 分别反映命令发布和板子运行。后续研究数据陈旧问题时，不能只使用一个总的"通信正常"标志。

### 4. PCC符号必须在实验中实测确认

论文中不能只根据点表写符号约定。必须通过设备功率阶跃验证PV增加后PCC_P实际向哪个方向变化，确认整个模型、通信接口和AGC公式一致。

### 5. 当前目标功率来自本地JSON

这意味着当前方案更接近固定目标运行。若论文涉及调度计划动态下发，需要增加目标值的通信路径，不能假设当前点表已经支持。
