# 暑期南网科技项目｜每轮项目操作“技术推进 + 报告取证 + 窗口交接”统一输出规范
## ——从下一轮开始固定执行，保证中途换窗口也能无损接续

> **版本**：V1.0  
> **日期**：2026-08-18  
> **适用范围**：RT-LAB模型、Modbus通信、代码生成/导出、BOARD15 C迁移、外部控制器部署、联调、自测、CHIL。  
> **目标**：今后每一次关键操作都同时形成一份可保存的Markdown过程文件，使技术推进、负责人要求的自测/流程报告取证、后续正式报告撰写和新窗口交接四件事同步完成。

---

# 1. 从下一轮开始，每个关键操作都必须形成一个Markdown过程文件

建议命名：

```text
Rxx_TC-XXXX-xx_本轮操作主题_过程记录_YYYYMMDD.md
```

例如：

```text
R04_TC-CODE-C02_P目标与约束C迁移_过程记录_20260818.md

R04_TC-CODEGEN-01_RTLAB代码生成首次成功_过程记录_20260818.md

R05_TC-DEP-03_Board程序编译部署_过程记录_20260820.md

R07_TC-INT-09_FC16异常与安全保持_过程记录_20260825.md
```

不要使用：

```text
记录1.md
最终.md
最后版.md
副本.md
```

---

# 2. 每一轮Markdown固定包含九个部分

---

## 第一部分｜【归属正式报告】

必须明确：

```text
正式报告编号：
R04

报告名称：
《控制算法代码生成/导出、C迁移与等价性自测报告》

测试用例编号：
TC-CODE-C02

本轮在正式报告中的位置：
第xx章 / xx测试用例 / xx附件
```

这样换窗口后，新助手一眼就知道：

> 这一轮不是孤立操作，而是最终哪份项目报告的一部分。

---

## 第二部分｜【本轮技术目标】

只写本轮真正要解决的问题，不扩大范围。

例如：

```text
本轮只完成：
Request Normalizer
+
P Objective Selection
+
S1/S4/S11 Constraint Manager
的C语言迁移和离线验证。

本轮不进入：
AGC
S6/S8
Q
Mode
S14
S15
```

必须明确：

```text
本轮完成边界
本轮不做边界
```

避免后续把“规划”误写成“已完成”。

---

## 第三部分｜【本轮开始前必须留存】

在真正开始操作以前，先列清楚需要保存的材料。

固定分为：

### A. 版本

```text
当前SLX：
当前MATLAB：
当前RT-LAB：
当前Board程序：
当前C代码版本：
当前Git commit：
当前点表：
当前JSON：
```

### B. 原始文件

```text
□ 当前模型原件
□ 当前脚本
□ 当前C/H文件
□ 当前配置
□ 当前点表
```

### C. 环境截图

根据本轮实际需要明确：

```text
□ Model Settings
□ RT-LAB界面
□ Variables Table
□ Board终端
□ 网络设置
...
```

### D. 初始化状态

```text
□ 是否Reset
□ 初始P/Q
□ 初始SOC
□ Breaker
□ Mode
□ CONTROL_SOURCE
□ Strategy Enable
```

如果某项本轮不适用，写：

```text
NA
```

而不是删除。

# 4. 第四部分｜【正式操作步骤】

所有真正操作必须逐步编号。

标准写法：

```markdown
### Step 1｜操作名称

**目的：**

**具体操作：**

1. 打开……
2. 进入……
3. 参数……改为……
4. 点击……

**命令：**
```text
完整命令
```

**正常现象：**

**异常现象：**

**本步必须保存：**
- 截图：
- 日志：
- 文件：

**PASS判据：**
```

必须达到：

> 第三方只看本Markdown即可重复操作。

---

# 5. 第五部分｜【操作过程中必须截图/保存】

不能等实验结束才想起来。

每轮提前列一个截图索引：

| 图号 | 在哪一步截 | 必须包含什么 | 用来证明什么 | 建议文件名 |
|---|---|---|---|---|
| FIG01 | Step 1 | 软件版本/模型名 | 当前版本 | `...FIG01.png` |
| FIG02 | Step 3 | Build成功界面 | 代码生成成功 | `...FIG02.png` |
| FIG03 | Step 5 | Board启动日志 | 程序成功启动 | `...FIG03.png` |

同时列：

```text
【必须保存的原始文本】
□ build.log
□ terminal.txt
□ ping.txt
□ compiler.log

【必须保存的原始数据】
□ MAT
□ CSV
□ JSON
□ generated code
```

---

# 6. 第六部分｜【本轮实际结果】

实验/操作结束以后填写。

至少包含：

```text
最终是否成功：
PASS / FAIL / PARTIAL

实际发生了什么：

关键数值：

运行时长：

错误/Warning：

生成了哪些文件：

与预期是否一致：
```

如果失败：

```text
不能只写“失败”
```

必须继续写：

```text
失败发生在哪一步
完整错误
初步判断
是否已经定位根因
```

# 7. 第七部分｜【实验结束归档检查】

每一轮结束以前必须逐项检查：

```text
□ 当前版本已记录
□ 初始条件已记录
□ 实际操作步骤完整
□ 所有关键命令已保存
□ 必要截图已编号
□ 原始日志已保存
□ MAT/CSV已保存
□ 配置文件已保存
□ 结果已量化
□ PASS/FAIL依据明确
□ 异常及处理已记录
□ 本轮最终文件清单已填写
```

缺一项就在当轮补，不留到以后。

# 8. 第八部分｜【这批材料未来进入报告哪一章节】

这是负责人要求和我们过程工作的真正连接点。

例如：

```text
本轮材料未来进入：

R04
《控制算法代码生成/导出、C迁移与等价性自测报告》

第3章：

A04-C02-02 编译日志
A04-C02-03 验证数据
```

这样以后正式写报告时：

> 不需要重新搜索整个项目仓库。

```text

1.

3.

1.
2.

1.
2.

...

...

下一轮需要的文件：
...
```

这部分相当于：

> 小型“窗口交接说明”。

# 10. 每一轮除了过程Markdown，还要给出“本轮文件清单”

固定写在Markdown内：

| 文件 | 类型 | 用途 | 是否正式证据 |
|---|---|---|---|
| `xxx.c` | C源文件 | 本轮实现 | 是 |
| `xxx.h` | 头文件 | 接口 | 是 |
| `build.log` | 日志 | 编译证据 | 是 |
| `xxx.mat` | 原始数据 | 运行结果 | 是 |
| `plot.m` | 绘图 | 后处理 | 附件 |

以后不再出现：

> 文件生成了，但几轮以后不知道这个文件是干什么的。

# 15. 一个关键原则：当天形成，不后补

以后每一轮真正执行完以后：

```text
技术结论确定
↓
立即生成本轮Markdown
↓
再进入下一轮
```

不能：

```text
连续做10轮
↓
最后统一回忆
```

---

# 16. 中途换窗口时怎么做

如果当前窗口接近上限：

只需要在新窗口上传：

```text
最近1份本轮过程Markdown
+
当前正式模型/代码
+
必要的最新配置/数据
```

新窗口就可以从：

```text
【本轮结束状态 + 下一轮唯一入口】
```

继续。

因此以后每轮Markdown不仅是报告材料，也是：

> **项目连续工作的最小交接单元。**

---

# 17. 阶段结束还要形成“阶段汇总Markdown”

例如：

```text
C01～C03结束
```

再生成：

```text
R04_C01-C03阶段汇总与证据索引.md
```

内容只做：

```text
三个TC的状态
正式文件
PASS证据
未关闭问题
下一阶段入口
```

不重复每轮细节。

从下一轮开始，无论窗口是否可能更换：

> **每一个真正改变项目状态的关键轮次，必须留下至少一份独立Markdown过程文件。**

```text
