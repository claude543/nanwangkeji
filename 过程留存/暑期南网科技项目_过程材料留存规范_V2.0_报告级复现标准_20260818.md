# 暑期南网科技项目｜过程材料留存规范 V2.0
## ——按“第三方可独立复现 + 自测报告可直接成稿 + 验收证据可追溯”标准执行

> **版本日期**：2026-08-18  
> **适用范围**：Modbus TCP通信链路、RT-LAB模型实时化与代码导出、控制器代码部署、BOARD15算法自测、RT-LAB/控制器闭环、CHIL正式实验。  
> **制定原则**：后续任何关键测试，不再只保存“结果文件”，而是同时保存**环境、配置、步骤、输入、过程、结果、截图、日志、判据、异常闭环**。  
> **最终目标**：半年后由一个此前未参与项目的人，仅根据归档文档和附件，即可完成同样的环境配置、程序部署、参数设置、实验操作、结果核验和PASS/FAIL判断。

---

# 0. V2.0相对原留存规范的核心升级

原V1重点解决“应该保存什么文件”。

V2.0进一步要求：

```text
保存材料
↓
组织成标准测试用例
↓
每个测试用例具备前置条件、步骤、预期、实际、截图、量化判据
↓
形成可直接转化为自测报告/实验报告的证据包
```

从现在开始，每轮关键实验都必须按“**报告级留存**”处理，而不是实验结束后再补写。

# 2. 每个测试用例必须具备的“十二要素”

每个正式测试用例必须至少写清楚：

## 2.1 用例编号

统一编号，例如：

```text
TC-COMM-01
TC-CODEGEN-01
TC-DEPLOY-01
TC-BOARD15-S07-01
TC-CHIL-S15-01
```

不要只写“试验1”“第一轮”。

---

## 2.2 测试名称

例如：

```text
Modbus 100 ms连续通信稳定性测试
RT-LAB模型代码生成完整流程测试
BOARD15 S7联络线功率跟踪测试
S15重同步与PCC重合闸测试
```

---

## 2.3 测试目的

必须写成“要验证什么能力”，而不是只写“测试S7”。

例如：

> 验证外部控制器在100 ms Modbus TCP通信周期下能够持续读取PCC及资源状态、计算六设备有功指令并完整写回RT-LAB，且在规定运行时长内无通信中断、无命令序号异常、无心跳失效。

---

## 2.4 前置条件

必须明确：

```text
模型已Build/Load成功
目标机已Execute
Board程序版本
JSON版本
点表版本
网络已连通
初始SOC
初始Pref/Qref
PCC断路器状态
当前CONTROL_SOURCE
当前策略Enable
是否Reset
是否已清空旧日志
```

---

## 2.5 测试初始条件

必须给出**可重复设置的具体数值**。

例如：

```text
PV1_P_MAX = 80 kW
PV2_P_MAX = 60 kW
ESS1_SOC = 0.60
ESS2_SOC = 0.55
PCC目标 = -100 kW
负荷 = xxx kW
通信周期 = 100 ms
CONTROL_MASTER_ENABLE = 1
P_OBJECTIVE_MODE = 0
```

不能只写：

```text
“设置为正常状态”
```

---

## 2.6 测试方法

说明本用例为什么这样设计，以及主要观察对象。

例如：

```text
通过改变PCC目标制造有功缺额；
观察P Objective、effective_dP、六资源Pref及PCC响应；
判断资源调用顺序和最终PCC误差是否符合设计。
```

---

## 2.7 测试步骤

这是最重要的复现部分。

必须细到：

```text
第1步：打开哪个软件
第2步：进入哪个界面
第3步：选择哪个项目/模型
第4步：点击哪个按钮
第5步：输入哪个IP/端口
第6步：执行哪条命令
第7步：哪个参数改成多少
第8步：何时点击Reset/Execute
第9步：在第几秒改变哪个参数
第10步：观察哪个窗口/日志/波形
```

如果是终端命令，**原命令必须完整保存**。

如果是GUI操作，截图要能看见：

```text
菜单
按钮
字段
输入值
```

---

## 2.8 预期结果

必须在测试前写。

例如：

```text
FC03/FC16连续成功
BOARD_HEARTBEAT持续递增
CMD_SEQ仅在新控制内容成功发布时递增
PCC误差进入设定死区
PV/ESS/EV调用顺序符合预期
```

---

## 2.9 实际结果

不能只写：

```text
“符合预期”
```

必须尽量量化：

```text
通信连续运行 1800 s
FC03失败 0 次
FC16失败 0 次
最大单周期耗时 8.4 ms
PCC最终误差 1.7 kW
恢复时间 0.82 s
```

并注明：

```text
数据来源：
Board CSV / RT-LAB MAT / log / UI
```

---

## 2.10 测试结果截图

每个用例至少有能够证明关键结论的截图。

截图下面必须有：

```text
图号
截图时间
截图内容
说明它证明什么
```

例如：

```text
图 TC-COMM-01-03
Board终端连续打印FC03/FC16成功及心跳递增，
证明控制器与RT-LAB双向通信已建立。
```

---

## 2.11 判定标准

必须是可以客观判断PASS/FAIL的标准。

例如：

```text
连续运行≥1800 s；
FC03/FC16失败率=0；
心跳无中断；
无异常重连；
判定PASS。
```

不要只写：

```text
“运行正常则通过”
```

---

## 2.12 测试结论

统一：

```text
PASS
FAIL
NA
```

并给一句结论。

# 9. 每轮实验前的“初始化流程”必须固定

这是参考报告中非常值得吸收的一点。

多轮实验最容易因为上一轮残留状态导致不可复现。

所以以后每个测试章节都必须写：

```text
每轮测试开始前：
1. Reset Controller / RT-LAB指定状态
2. 恢复PCC breaker
3. 恢复6设备Pref/Qref
4. 恢复SOC或指定SOC初值
5. 恢复PVmax
6. 恢复负荷
7. 恢复策略Enable
8. 清理旧CSV/log
9. 确认heartbeat
10. 再开始正式工况
```

必要时专门写：

```text
《统一初始化SOP》
```

# 30. 最终验收标准

一轮实验只有同时满足以下条件才叫“材料归档完成”：

```text
□ 软件/硬件版本明确
□ 模型/程序/配置文件可定位
□ 网络和接口配置明确
□ 初始条件明确
□ 参数值明确
□ 操作步骤可逐步复现
□ 预期结果在实验前定义
□ 实际结果有量化数据
□ 有启动/过程/结果截图
□ 有原始MAT/CSV/log
□ 有明确PASS/FAIL标准
□ 有异常/问题记录
□ 有测试结论
□ 第三方无需口头指导即可复现
```

只要其中关键项缺失，就不能视为正式报告级过程材料。
