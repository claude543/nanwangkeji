# 2. 本轮新发现并关闭的问题

## 2.1 点表40029正文说明仍是旧四位定义

虽然V0.5的 `Bitfields（位域说明）` 工作表已经改成：

```text
bit0 P
bit1 Q
bit2 MODE
bit3 BLACKSTART
bit4 RESYNC
bit5 FINAL_MODE_ROUTE
```

但 `Command_Frame（命令帧）` 工作表中40029仍写：

```text
bit0=P
bit1=Q
bit2=MODE
bit3=SYNC
```

这会直接导致工程师按主表实现错误。

本轮已升级点表V0.6并统一成bits0～5。

---

## 2.2 点表中的未来算法字段仍容易让工程师误以为当前必须实现

40031～40059、40062～40064以及40258～40279是为后续扩展保留的稳定地址。

当前正式BOARD15只实现：

```text
P_COORDINATION_MODE（有功协调方式）=0 BASELINE（基础有功协调）
METHOD_VARIANT（方法变体）=0 BASELINE（基础方法）
```

本轮已把点表主表说明改为：

```text
未来字段当前写0/保留
不要求当前实现执行状态感知算法
```

避免工程师多做一套尚未启用的算法。

---

## 2.3 100 ms周期不能理解成“通信阻塞后再快速补跑几个周期”

旧JSON（配置文件）的通信超时参数可能大于100 ms。

因此正式要求需要明确：

```text
100 ms
是正常目标调度周期

通信异常导致某一周期超过100 ms
→ 标记CYCLE_OVERRUN（周期超时）
→ 不同时启动第二个重叠控制周期
→ 不在恢复后突发补算多个历史周期
```

整个控制器保持单一时间顺序。

---

## 2.4 `snapshot_fresh（测量快照新鲜）` 与 `RTLAB_HEARTBEAT（RT-LAB心跳）变化` 不是同一个概念

正式冻结：

```text
snapshot_fresh=1
表示本次成功取得了一份新的完整40101～40124读取结果

RTLAB_HEARTBEAT
负责判断RT-LAB数据源是否持续活跃
```

不能要求“心跳必须每次变化”才把每个FC03响应算作新快照。

---

## 2.5 `signal_valid_mask（信号有效位域）` 表示“字段本身读取/解码有效”，不是字段内部布尔值必须等于1

例如：

```text
40121 PHASE_VALID（相角有效标志）=0
```

可以是一个**合法读取到的值**。

此时：

```text
SIG_VALID_PHASE_FLAG（相角有效标志字段有效位）仍然可以=1
```

只是：

```text
phase_valid（相角当前可用值）=0
```

会阻止S15（策略15）同步资格。

同理：

```text
40122内EXEC_ROUTE_VALID（执行路由有效）=0
```

不代表40122这个寄存器读取失败。

---

## 2.6 `RETRY_PENDING（重试待提交候选）` 中“相同”只约束控制候选，不要求整个40001～40064逐字节不变

真正必须保持：

```text
同一pending ControllerOutput（待提交控制器输出）
同一candidate CMD_SEQ（候选命令序号）
同一控制状态
```

工程字段仍按当前循环更新，例如：

```text
BOARD_HEARTBEAT（板端心跳）
COMM_STATUS（通信状态）
```

因此重试时重新组完整FC16帧，但控制候选内容和候选CMD_SEQ不重新计算。

---

## 2.7 `LAST_FC16_OK（最近一次FC16成功）` 必须理解为“当前帧发送以前最近已经完成的FC16结果”

40030 `COMM_STATUS（通信状态）` 本身就在当前FC16帧里。

因此：

```text
当前帧不可能提前知道当前FC16是否成功
```

40030 bit4表示：

```text
在形成当前帧之前，最近一次已经完成的FC16结果
```

当前FC16完成后更新本地主程序状态，供下一帧使用。

---

## 2.8 FC16失败时pending不能立刻被清掉

真正的FC16失败处理：

```text
不controller_commit（提交）
pending继续存在
```

后续：

```text
如果仍属于同一Measurement Snapshot（测量快照）
→ 可精确重试

如果接受到新Snapshot
→ Adapter自动废弃旧pending并重算

如果发生measurement break（测量连续性中断）
→ controller_notify_measurement_break自动清pending
```

只有：

```text
本地编码失败
本地帧形成错误
显式放弃
```

才主动 `controller_abort_pending（放弃待提交候选）`。

---

## 2.9 初始化前必须先取得一份完整Runtime Config（运行时配置）

程序启动后不能只读取40101～40124就直接初始化控制器。

需要：

```text
先取得40124 CONFIG_SEQ（配置序号）
↓
按原子协议读取40201～40280
↓
得到完整合法ControllerConfig（控制器配置）
↓
再controller_init（控制器初始化）
```

配置尚未建立时：

```text
通信和WAIT_VALID仍可运行
但EXT_CONTROL_ENABLE（外部整体控制有效）保持0
```

---

## 2.10 序号和心跳全部为UINT16（16位无符号整数），必须允许自然回绕

包括：

```text
CMD_SEQ（命令序号）
CONFIG_SEQ（配置序号）
CONTROLLER_RESET_SEQ（控制器复位序号）
RTLAB_HEARTBEAT（RT-LAB心跳）
BOARD_HEARTBEAT（板端心跳）
```

程序判断“是否变化”时使用：

```text
相等/不相等
```

或已有回绕安全逻辑。

不能使用：

```text
new > old
```

作为唯一判断，因为65535之后会回到0。

# 3. 当前最终模型中已确认的Project15IntegrationConfig（PROJECT15固定集成配置）

对上传最终模型进行结构检查后确认：

```text
六设备Legacy GridOn（原始并网/构网状态）
均来自Constant（常数）1

六设备Legacy Droop（原始下垂状态）
均来自Step（阶跃）
默认0 → 1
切换时间3 s

BOARD15正常运行模式的PCC Breaker（公共连接点断路器）
在模式执行链正常状态下请求闭合
```

因此最终BOARD15使用正常稳态基础值：

```text
baseline_grid_on
=
[1, 1, 1, 1, 1, 1]

baseline_droop
=
[1, 1, 1, 1, 1, 1]

baseline_breaker_close
=
1
```

六设备顺序：

```text
PV1
PV2
ESS1
ESS2
EV1
EV2
```

这些值进入最终JSON（配置文件）的 `Project15IntegrationConfig（PROJECT15固定集成配置）`。

# 5. V1.0正式文档新增的工程实现细节

相对V0.2，V1.0进一步写清：

1. 启动时首次Runtime Config读取；
2. 100 ms周期遇到阻塞/超时时不并发、不补跑；
3. `snapshot_fresh（测量快照新鲜）` 的准确定义；
4. `signal_valid_mask（信号有效位域）` 与布尔信号值的区别；
5. `command_channel_valid（命令通道有效）` 的使用边界；
6. 同一pending重试时工程字段仍可更新；
7. FC16失败不主动abort pending；
8. 当前帧内 `LAST_FC16_OK（最近一次FC16成功）` 表示上一已完成发送结果；
9. `CONFIG_STATUS（配置状态）` 按本周期配置处理结果输出；
10. UINT16序号/心跳自然回绕；
11. Project15IntegrationConfig三个模型基础值正式填入；
12. Controller接口非成功返回值的统一处理原则。
