# 3.1 版本模型改动

为了验证 V3.1，我们在 Simulink/RT-LAB 侧主要做了两类改动：

> **第一类：给板子提供可控、已知的 16 路测试输入。**
> **第二类：把板子写回来的 9 路原始寄存器值，同时显示为 raw 值和实际工程量。**

这些改动的目的不是让板子正式控制微电网，而是完整验证：

```text
RT-LAB发出的值，板子能否正确理解
+
板子发回的值，RT-LAB能否正确恢复
```

V3.1 规定了 16 路读取点和 9 路写入点的地址、类型、缩放、符号及范围。

---

## 一、总体上没有改什么

V3.1 没有改变 V2 已经打通的通信骨架。

仍然是：

```text
板子通过FC03读取：
40101～40116
offset 100
数量16

板子通过FC16写入：
40001～40009
offset 0
数量9
```

以下内容也保持不变：

- 板子是 Modbus TCP 客户端；
- RT-LAB 是 Modbus TCP 服务器；
- IP 为 `192.168.1.100`；
- 端口为 1502；
- Unit ID 为 1；
- `I/O Interfaces` 中的 Modbus Slave 结构；
- `Configuration` 中的 16 路读、9 路写映射；
- 原有 OpInput、OpOutput 和 OpComm 通信路径。

原因是 V3.1 只验证"数据含义"，不希望同时改变通信结构。否则出现问题时，无法区分是通信配置错误还是数据编解码错误。

---

## 二、RT-LAB 发给板子的方向做了什么

### 1. 保留 16 路测试源

在实时计算模型中，40101～40116 暂时由已知的 Constant 测试值产生。

路径可以理解为：

```text
Constant测试值
→ OpOutput
→ RT-LAB Configuration
→ Holding Register 40101～40116
→ 板子FC03读取
```

开始时使用过：

```text
40101 = 201
40102 = 202
……
40115 = 215
40116 = 999
```

这些值并不是合理的真实电网工况，只是"已知输入"。

例如：

```text
40101 PCC_P
raw=201
scale=0.1 kW/count
→ 板子应显示20.1 kW
```

```text
40104 PCC_F
raw=204
scale=0.01 Hz/count
→ 板子应显示2.04 Hz
```

虽然 2.04 Hz 不是真实正常频率，但这项测试只是在验证程序是否使用了正确缩放系数。

### 2. 为什么必须使用已知 Constant

因为只有输入是已知的，我们才能判断板子是否解码正确。

例如 RT-LAB 明确发送 201，而板子显示：

```text
raw=201
value=20.1 kW
```

就能分别确认：

- 地址是 40101；
- 顺序没有错；
- 类型解释没有错；
- 缩放 0.1 正确；
- 单位 kW 正确。

如果一开始直接接真实动态测量量，数值一直变化，出现错误时很难判断是模型变化还是通信解析错误。

---

## 三、为了负数输入测试，修改了 40101

为了验证 **RT-LAB → 板子** 这个方向能否正确传输负数，我们把 40101 对应的 Constant 从普通正数改为 `64831`。

64831 的 16 位形式为 `0xFD3F`。

同一组 16 位数据：

```text
按UINT16解释 = 64831
按INT16解释  = -705
```

因为 40101 定义为：

```text
PCC_P
INT16
0.1 kW/count
```

所以板子应恢复为：

```text
raw = -705
value = -705 × 0.1
     = -70.5 kW
```

实际日志正是：

```text
40101 PCC_P raw=-705 value=-70.5 kW
```

这项临时修改证明：

```text
Simulink发送负数补码
→ Modbus不改变16位内容
→ 板子按INT16恢复负数
→ 再乘scale恢复工程量
```

---

## 四、40116 改成 999 起什么作用

V2 阶段 40116 原来曾使用 216，V3.1 阶段把它改成 999。

板子随后读到：

```text
40116 RTLAB_TEST_VALUE raw=999
```

它证明板子不是：

- 在程序里写死 216；
- 一直打印旧缓存；
- 只在启动时读取一次。

而是在每个通信周期重新执行 FC03，并读取 RT-LAB 当前寄存器内容。

这属于对"周期动态读取"的初步验证。

---

## 五、板子写回 RT-LAB 的方向做了什么

板子从 JSON 取得九路测试输出：

```text
0.10
0.20
0.30
-0.40
-0.50
-0.60
1
25.5
3.2
```

编码后通过 FC16 写入 `40001～40009`。

RT-LAB 侧原始接收路径是：

```text
板子FC16
→ Holding Register 40001～40009
→ Configuration
→ Simulink OpInput
→ 原始Display
```

原始 Display 看到：

```text
40001 = 1000
40002 = 2000
40003 = 3000
40004 = 61536
40005 = 60536
40006 = 59536
40007 = 1
40008 = 255
40009 = 32
```

其中 61536、60536、59536 是负数补码被按 UINT16 显示后的结果。

---

## 六、为什么不能只看原始 Display

例如 40004 实际命令为 `Pess2 = -0.40 pu`。

板子编码过程是：

```text
-0.40 ÷ 0.0001
= -4000
→ 16位补码0xF060
```

RT-LAB 原始 Display 按 UINT16 显示：

```text
0xF060 = 61536
```

所以看到 61536 不能直接判断它代表什么。必须继续完成：

```text
61536
→ 按INT16恢复为-4000
→ 乘0.0001
→ -0.40 pu
```

这就是我们在 Simulink 中增加工程量解码支路的原因。

---

## 七、在 sc_display 中增加了哪些模块

我们没有删除原来的 raw 显示，而是从每路信号分出一条新支路：

```text
原始信号
├─ 原Display：显示寄存器raw
└─ 解码模块
   → 工程量Display
```

这样可以同时观察：

```text
底层寄存器值
+
实际工程量
```

---

## 八、40001～40006 的解码模块

六路 PV、ESS、EV 指令采用同一基本结构：

```text
原始Modbus值
→ Data Type Conversion：int16
→ Data Type Conversion：double
→ Gain：0.0001
→ 工程量Display
```

### 第一个 Data Type Conversion：转 int16

作用是恢复有符号 raw。

例如 `61536 → int16 → -4000`。

关键设置：

```text
输出数据类型：int16
"对整数溢出进行饱和处理"：不勾选
```

为什么不勾选饱和？

如果勾选，61536 超过 int16 最大值 32767 后，会被限制成 `32767`，无法恢复为 -4000。

关闭饱和后按 16 位回绕：

```text
61536 - 65536 = -4000
```

因此第一个模块解决的是：

> **这组 16 位数据应解释为正数还是负数。**

### 第二个 Data Type Conversion：转 double

作用是把 `int16` 类型的 -4000 转换成 `double` 类型的 -4000.0，便于后续乘小数缩放系数，也便于 Display 显示。

它不改变数值大小，只改变数据类型。

### Gain = 0.0001

作用是把通信 raw 恢复成 pu 工程量：

```text
工程量 = raw × 0.0001
```

例如 `-4000 × 0.0001 = -0.40 pu`。

所以三块模块的分工是：

```text
第一个转换：恢复正负号
第二个转换：便于小数运算
Gain：恢复实际比例和单位
```

---

## 九、40007、40008、40009 分别怎么处理

### 40007 AGC_STATUS

定义为 INT16，缩放 1：

```text
原始信号
→ int16
→ double
→ Display
```

可不加 Gain，或者 Gain 设为 1。

当前显示 1，未来还要支持 `-2、-1、0、1、2`。

### 40008 dP

定义为 INT16，缩放 0.1 kW/count：

```text
原始信号
→ int16
→ double
→ Gain 0.1
→ Display
```

例如 `255 × 0.1 = 25.5 kW`。

未来负 dP 也能通过 INT16 恢复。

### 40009 remain

定义为 UINT16、非负，缩放 0.1：

```text
原始信号
→ double
→ Gain 0.1
→ Display
```

不需要先转 int16，因为 remain 不允许负值。

例如 `32 × 0.1 = 3.2 kW`。

## 十、为什么保留两组 Display

最终 SC 中同时保留：

### 原始 Display

```text
1000
2000
3000
61536
60536
59536
1
255
32
```

用于证明：

- Modbus 寄存器内容正确；
- 补码字节正确；
- 地址顺序正确；
- FC16 写入没有错位。

### 工程量 Display

```text
0.10
0.20
0.30
-0.40
-0.50
-0.60
1
25.5
3.2
```

用于证明：

- INT16/UINT16 解释正确；
- 缩放系数正确；
- 正负方向正确；
- 模型最终拿到的控制值正确。

如果只看工程量，无法确认底层字节是否正确。如果只看 raw，人又无法直接判断实际功率指令。两组同时保留，能够把故障分层定位。

## 十一、模型修改与板子 JSON 修改为什么不同

这一点在 V3.1 测试中很重要。

### 修改 Simulink

例如：

```text
40101 Constant：201 → 64831
增加Data Type Conversion
增加Gain
增加Display
```

这些属于模型结构或模型参数变化，需要：

```text
保存 → Build → Load → Execute
```

因为实时目标机必须重新生成并部署模型代码。

### 修改板子 JSON

例如将正常测试输出改成越界测试值：

```text
PV1：0.1 → 1.2
EV1：-0.5 → 0.3
remain：3.2 → -3.2
```

这只改变板子程序启动时读取的配置，不改变 Simulink 模型。

因此只需要：

```text
停止板子程序
→ 修改/更换JSON
→ 重新启动板子程序
```

不需要 Build。

这也是为什么我们把负数输入测试和限幅测试合并在一次 Build 之后完成。

## 十二、这些改动怎样串联成完整验证链路

### RT-LAB 到板子方向

```text
Simulink Constant
→ OpOutput
→ Configuration
→ 40101～40116
→ FC03
→ 板子收到16位raw
→ 按INT16/UINT16解释
→ 乘scale
→ 打印工程量
```

它验证的是：

> **RT-LAB 产生的数据，板子能否正确读取和理解。**

### 板子到 RT-LAB 方向

```text
JSON测试工程量
→ 板子限幅
→ 除以scale
→ 转成raw
→ 负数补码编码
→ FC16写40001～40009
→ Configuration
→ Simulink OpInput
→ 原始Display
→ int16恢复
→ double转换
→ Gain缩放
→ 工程量Display
```

它验证的是：

> **板子产生的数据，RT-LAB 能否正确接收和理解。**

两个方向合起来，就形成了 V3.1 的完整"双向数据语义闭环"。

| Simulink 改动       | 目的         | 最终证明                 |
| ------------------ | ------------ | ------------------------ |
| 16 路 Constant 测试源 | 提供已知输入   | 地址、顺序和 scale 正确     |
| 40116 改 999       | 验证实时更新   | 板子不是读取旧缓存           |
| 40101 改 64831     | 构造负数补码   | 板子能够解析负 PCC 功率      |

| double 转换         | 支持小数计算   | 后续缩放不受整数运算限制       |
| Gain 0.0001        | 恢复 pu       | -4000 恢复为 -0.4 pu     |
| Gain 0.1           | 恢复 kW       | 255 恢复为 25.5 kW        |

## 十四、这些模块现在只用于显示吗

V3.1 阶段主要用于：

```text
通信验收
数据解释验证
SC监视
```

还没有把六路板子命令正式接到：

```text
PV1 Pref
PV2 Pref
ESS1 Pref
ESS2 Pref
EV1 Pref
EV2 Pref
```

原因是我们当时发送的仍是 JSON 测试值，不是真正 AGC 输出。如果此时直接接到 Pref，测试值会实际驱动电气模型，增加不必要风险。

后续进入真实闭环时，同样的解码原理会被用于正式命令入口：

```text
Modbus raw
→ INT16恢复
→ Gain恢复pu
→ 安全有效性判断
→ Switch
→ 设备Pref
```

所以 V3.1 添加的模块不仅为了截图，它们也验证了未来正式控制入口需要使用的解码方式。

---

## 十五、这些改动在整体项目中的作用

V3.1 的 Simulink 改动完成后，我们可以确定：

```text
板子发-0.4，RT-LAB不会误认为61536 pu
板子发25.5 kW，RT-LAB不会误认为255 kW
RT-LAB发负PCC功率，板子不会误认为6483.1 kW
```

这意味着通信双方已经对以下内容达成一致：

- 地址；
- 顺序；
- 数据类型；
- 正负号；
- 缩放比例；
- 单位；
- 物理范围；
- 负数补码。

因此后续接入 AGC 时，如果计算结果不正确，我们可以优先检查算法，而不需要重新怀疑基础编解码链路。

## 最后用一条完整记忆链总结

为了验证 V3.1，我们在 Simulink 中做的是：

```text
用Constant制造已知的板子输入
→ 用OpOutput和Configuration发布到Modbus
→ 用特殊补码值验证负数读取
→ 接收板子写回的9路raw
→ 保留raw Display验证底层寄存器
→ 增加int16转换恢复正负号
→ 转double支持小数计算
→ 用Gain恢复pu或kW
→ 用工程量Display验证最终含义
```

这些改动共同证明：

> **RT-LAB 和板子不仅"能够传数字"，而且能对这些数字代表的真实电气量作出完全一致的解释。**
