# EE Journal Writing — 使用说明

## 使用原则
安装后直接用自然语言提出论文任务即可，不需要记住内部模式名、模块名或英文判断标签。

面向你的分析、判断、检查结论默认全部使用中文。只有在以下情况下保留英文：
- 给出可以直接写进论文的英文句子；
- 比较某个英文词或短语应该怎样使用；
- 论文题目、算法名、标准名、公式、变量或必要缩写本身需要保留。

必要缩写第一次出现时会先用中文解释。

## 常用调用方式

### 从已有研究材料起草
- `根据我上传的研究材料写引言，缺的信息不要编。`
- `根据这些模型、算法和实验结果起草方法部分，保持所有公式和符号不变。`

### 修改已有章节
- `润色这段结果，只改逻辑和英文，不改变技术含义。`
- `重写这个引言，让研究缺口更清楚，但不能增加没有证据支持的创新点。`
- `继续按刚才的标准修改讨论部分。`

### 只检查技术逻辑或证据
- `只检查研究缺口和贡献，不用润色英文。`
- `这个结果够不够支撑 robust 这个词？`
- `检查每条贡献后面有没有真正对应的证据。`
- `检查这些引用是否真的支持附近的论断。`

### 目标期刊适配
- `按 IEEE Transactions on Power Electronics 的当前要求检查这篇论文是否适合投稿。`
- `按目标期刊改这个摘要，先核对官方要求，再参考近期同类型论文。`
- `学习这个期刊近期同类型文章的引言组织方式，但不要模仿原句。`

### 审稿与投稿前检查
- `模拟审稿人，先告诉我最严重的问题。`
- `只根据我上传的摘要检查，没有看到的内容不要断言缺失。`
- `做投稿前完整检查，重点看论断—证据、符号一致性和结论是否夸大。`

### 收到审稿意见
- `根据这些审稿意见和修订稿逐条检查回复信，不能声称没有实际做过的修改。`
- `先判断审稿人第3条意见影响哪条论断，再告诉我最小充分修改是什么。`
- `我不同意这条审稿意见，先检查我们有没有足够技术依据，再帮我起草专业回复。`

## 新增的语言实现能力
当技术内容和证据已经稳定后，Skill 还会按需检查：
- 句子是否真的有功能，还是空话/重复；
- 读者能否看清“本文做的、前人做的、标准流程、系统事实、数学关系”分别是什么；
- 因果和确定性表达是否超过证据；
- 关键数字是否有比较基准和工程意义；
- 结果篇幅是否与核心贡献重要性匹配；
- 讨论部分回访概念时术语是否漂移；
- 摘要是否从正文忠实压缩，而不是另起炉灶；
- 标题是否存在范围过宽、名词链歧义或强词过度承诺；
- 引用位置是否会造成技术归属混淆。

这些能力不会覆盖或改变技术事实。

## 什么时候不需要调用
- 单纯学习电路、控制理论或电力系统知识；
- 与论文无关的编程、仿真调试、项目管理；
- 从零替你决定整个研究课题或凭空创造创新点。

## 推荐工作顺序
通常可以按以下顺序使用，但不是强制流程：

研究缺口/贡献检查 → 系统与问题定义 → 方法与理论 → 验证与结果 → 讨论与局限 → 摘要/标题/结论 → 目标期刊适配 → 审稿检查 → 投稿前终检。
