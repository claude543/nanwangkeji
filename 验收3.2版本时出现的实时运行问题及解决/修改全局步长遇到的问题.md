# V3.2 发现时间问题后修改全局步长遇到的问题

---

## 结论

这次报错说明：

> **当前完整微电网模型不能仅通过把全局步长从 100 μs 改成 2 ms 来实现实时运行。**

原因是 100 μs 不仅是求解器步长，它已经嵌入多个 PLL 控制模块的设计参数中。2 ms 修改失败不是操作错误，而是模型结构对步长存在约束。

---

## 一、报错具体是什么意思

所有报错都指向 `PLL (3ph)` 模块：

```
The time constant for derivative action (1.000000e-04)
must be higher or equal to the block sample time (2.000000e-03)
```

其中：

| 参数 | 值 | 换算 |
|------|----|------|
| PLL 内部微分环节时间常数 | 0.0001 s | 100 μs |
| 修改后的模块采样时间 | 0.002 s | 2 ms |

该 PLL 要求 $T_{\text{derivative}} \geq T_{\text{sample}}$，但现在变成 $0.0001 < 0.002$，所以不满足要求。

通俗理解：

> PLL 内部想识别和处理 100 μs 尺度的变化，但现在模型每 2 ms 才计算一次。相当于每 2 秒拍一张照片，却想观察 0.1 秒内发生的动作，采样速度根本不够。

因此 PLL 拒绝初始化。

---

## 二、为什么这么多模块同时报错

报错涉及：

- PV1、PV2 的控制测量 PLL
- PV1、PV2 的 PCC 测量 PLL
- ESS1、ESS2 的控制测量 PLL
- ESS1、ESS2 的 PCC 测量 PLL
- EV1、EV2 的控制测量 PLL
- EV1、EV2 的 PCC 测量 PLL
- Grid Measurements
- Microgrid Supervisory Control
- PCC Measurements

这说明全局变量 `Ts` 不只是控制 Solver 和 powergui，还被**大量设备控制模块继承**。

当前模型实际上是：

```
InitFcn：Ts = 100e-6
         ↓
Solver 基础步长 = Ts
powergui 离散步长 = Ts
大量 PLL 采样时间 = Ts
其他控制和测量模块也可能使用 Ts
```

所以改变 `Ts` 不是只改变"RT-LAB 计算速度"，而是在同时改变**整个模型的控制采样体系**。

---

## 三、这次试验说明了什么

### 1️⃣ 100 μs 并非完全随意设置

此前只知道 100 μs 来自 `InitFcn` 中的 `Ts=100e-6;`。现在进一步确认，PLL 内部也存在**微分时间常数 = 100 μs**。因此 100 μs 已经成为模型设计的一部分。

### 2️⃣ 任何大于 100 μs 的全局步长都会遇到相同问题

例如 200 μs、500 μs、1 ms、2 ms 都满足 $T_s > 100\ \mu s$，在不修改 PLL 参数的情况下都会出现同类报错。所以没有必要继续尝试 1 ms。

### 3️⃣ 改成 50 μs 可以满足 PLL 约束，但实时性能更差

`init_pv.m` 中的 `Ts=50e-6;` 满足 $100\ \mu s \geq 50\ \mu s$，PLL 可能不会因为这个条件报错。但模型每秒需要计算 20000 次，实时压力比 100 μs 再增加一倍。50 μs 不是解决方案。

---

## 四、能不能把 PLL 的 100 μs 也改成 2 ms

从参数形式上看，可以把多个 PLL 的微分时间常数改大，使其满足 $T_{\text{derivative}} \geq 2\ \text{ms}$。

但现在**不能这样做**。原因在于这不再是单纯的"运行设置修改"，而是**对全部 PLL 及相关控制环节进行重新设计和整定**。

把 100 μs 改成 2 ms，相当于将相关时间常数放大 20 倍，可能影响：

- PLL 锁相速度
- 相角跟踪
- 频率测量
- dq 变换
- 电压电流控制
- 并网稳定性
- 暂态响应
- AGC 测量反馈

且当前只暴露了 PLL，后面可能还有 PWM、滤波器、离散控制器和 Rate Transition 继续报错。因此不能为了让模型通过更新，就批量把这些参数全部改为 2 ms。

## 五、现在先恢复测试副本

不要 Build 当前 2 ms 版本。确认操作的是测试副本，然后在 MATLAB 命令窗口执行：

```matlab
mdl = bdroot;

set_param(mdl,'InitFcn','Ts=100e-6;');
save_system(mdl);

clear Ts
set_param(mdl,'SimulationCommand','update');

Ts
```

正常应显示：

```
Ts =

   1.0000e-04
```

然后重新打开 powergui，应恢复为：

```
Sample time：Ts
计算值：0.0001
```

这一步只恢复测试副本，不修改正式模型的其他内容。

---

## 六、当前解决路线需要调整

原先初步考虑：把完整模型步长增大到 2 ms → 降低 CPU 使用率 → 解决 overrun。现在已证明这条直接路线不可行。

正确做法应拆成**两条任务线**。

### 路线一：优先完成 V3.2 通信验收

V3.2 要验证的是：FC03 和 FC16、28 个寄存器、MODEL_STATUS、双方心跳、连续 3 个有效周期、使能与安全退出、断线和恢复、数据范围检查。

这些功能**不需要**完整 PV、ESS、EV 及 15 个 PLL 同时实时运行。

建立一个**轻量 V3.2 通信验收模型**：

```
保留 40001～40012 输入
保留 40101～40116 输出
保留状态字和心跳逻辑
40101～40114 使用 Constant 或简单 Step 生成
删除或不运行复杂微电网主体
```

轻量模型可以采用 1 ms 或更宽松的步长，因为其中没有这些高速 PLL 约束。

这样可以先完整验收工程师的 V3.2 程序，不让完整模型实时性能问题阻塞通信任务。

### 路线二：单独处理完整模型实时化

完整模型继续保留 100 μs 设计，再研究：

- 主模型是否能分配到多个 CPU 核心
- 是否存在重复 PLL 和重复测量计算
- 是否能采用平均化逆变器模型
- 是否能降低开关模型计算量
- 是否需要 FPGA / eHS
- 是否可以建立快、慢多速率结构
- 哪些模块必须 100 μs，哪些控制和通信可以 1 ms 或 1 s 执行

这属于完整 HIL 模型优化，不应通过简单修改一个 `Ts` 完成。

---

## 七、这次报错的阶段性价值

这次试验**并不是失败**，它明确回答了一个关键问题：

> 当前 100 μs 不仅是 Solver 设置，而是完整模型多个 PLL 和控制模块共同依赖的基础采样时间。

目前准确结论是：

```
完整模型在 100 μs 下无法实时运行；
但全局步长又不能直接扩大到 2 ms；
扩大步长需要重新设计 PLL 和其他快速控制模块；
因此 V3.2 通信验收应先使用轻量模型；
完整模型实时化作为独立优化任务推进。
```

恢复测试副本到 100 μs 后，下一步应建立轻量 V3.2 通信验收模型，而不是继续逐个修改这些 PLL。
