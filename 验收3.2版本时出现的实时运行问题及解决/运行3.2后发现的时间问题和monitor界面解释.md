# 运行 V3.2 后发现的时间问题

> 当前问题的完整梳理

---

## 一句话理解

当前 RT-LAB 模型被要求：

> **每 100 μs 完成一次完整计算。**

但 OP5700 实际上平均需要约：

> **981 μs 才能完成一次。**

相当于老师要求你每 0.1 秒完成一道题，但你实际每道题需要约 1 秒。程序仍然在做题，也不会立即崩溃，但会越来越跟不上现实时间。

这就是当前问题的本质：

```
模型能够运行
≠
模型能够实时运行
```

---

## 一、问题是在什么情况下暴露出来的

原本正在进行 V3.2 程序的第一轮安全启动验收。

当时的条件：

```
external_enable_request = false
test_mode = true
板端通信周期 = 1 s
RT-LAB 心跳超时 = 3.5 s
```

板端程序成功连接到 `192.168.1.100:1502`，随后正常完成 FC03 读取 40101~40116、FC16 写入 40001~40012。日志还显示 `MODEL_STATUS = 0x0007`、`CMD_SEQ` 持续增加、`BOARD_HEARTBEAT` 持续增加、`read=OK`、`write=OK`。——说明基础 Modbus 通信已经成功。

但是程序反复输出：

```
HEARTBEAT_NOT_ESTABLISHED
HEARTBEAT_TIMEOUT
RECOVER reason=RTLAB_HEARTBEAT_CHANGED
```

并始终保持 `WAIT_VALID`、`valid=0/3`、`enable=0`。

日志中可以看到，RT-LAB 心跳从 175 变成 176 后，又长时间保持不变，板端在 4 秒、5 秒、6 秒等时刻连续报告心跳超时。

因此最初看到的**表面现象**是：

> **板端可以读写 RT-LAB，但认为 RT-LAB 的心跳不正常。**

---

## 二、V3.2 心跳原本应该怎样工作

RT-LAB 的 40116 心跳由以下代码生成：

```matlab
live_value = uint16(mod(floor(max(time_s, 0.0)), 65536.0));
```

通俗来说：

```
模型时间为 0~0.999 s：心跳 = 0
模型时间为 1~1.999 s：心跳 = 1
模型时间为 2~2.999 s：心跳 = 2
```

所以它设计为：**每经过 1 秒"模型时间"，心跳增加 1**。

板端程序每 1 秒读取一次 40116。如果心跳超过 3.5 秒不变化，就认为 RT-LAB 可能停止、卡死或数据不再更新，于是拒绝使能。

V3.2 的安全保护逻辑：

```
RT-LAB 正常运行 → 心跳持续变化 → 板端允许数据进入有效计数
RT-LAB 卡住或停止 → 心跳不再变化 → 板端立即撤销外部使能
```

当前 V3.2 要求连续 3 个有效周期才能从 `WAIT_VALID` 进入 `ENABLED`；任一明确异常都必须立即使 40010 回到 0。

---

## 三、为什么板端会认为心跳超时

关键在于存在**两种"时间"**。

### 1️⃣ 现实时间

墙上的钟、Windows 时间和板端 Linux 时间。板端程序的 1000 ms 通信周期、3500 ms 心跳超时，都是按照现实时间计算。

### 2️⃣ 模型时间

Simulink 中的 `Clock` 输出的是**仿真时间**，不是直接读取墙上的时间。

在真正实时运行时，两者应基本一致：**现实经过 1 秒 ≈ Simulink 模型时间增加 1 秒**。

但当前模型并没有跟上现实时间。实际情况接近：

```
现实经过约 10 秒 → 模型时间只增加约 1 秒 → 40116 心跳只增加 1
```

板端看到的是：

```
第 1 秒：40116 = 175
第 2 秒：40116 = 175
第 3 秒：40116 = 175
第 4 秒：仍为 175 → 超过 3.5 秒 → HEARTBEAT_TIMEOUT
...
约 10 秒后：40116 从 175 变成 176 → RECOVER
```

因此：**心跳本身没有坏，心跳只是把"模型运行速度严重落后"这个问题暴露了出来。**

---

## 四、我们最初排查了哪些可能性

刚看到心跳 10 秒才变化一次时，不能马上认定是模型超限。依次检查了以下可能性。

### 1️⃣ 怀疑心跳代码写错

检查 `RTLAB_Heartbeat_Generator` 代码。核心是 `floor(time_s)`，确实应该每 1 个模型秒增加 1，没有除以 10、没有 10 秒周期，也没有错误计数逻辑。

> ✅ 心跳代码正确

### 2️⃣ 怀疑 freeze 误变成 1

心跳模块中如果 `freeze=1`，心跳会被人为冻结。确认 `freeze` 由 Constant 直接设置为 0，正常运行时不可能冻结。

> ✅ freeze 不是原因

### 3️⃣ 怀疑 Clock 的 Decimation = 10

Clock 模块设置了抽取值 10，一度考虑是否导致输出每 10 秒更新。但这个参数主要影响模块显示或观察抽取，不代表 Clock 输出每 10 秒才计算一次。而且即使把它当成疑点，也无法解释后面 Monitoring 中几乎每一步都超限的结果。

> ✅ Clock 的 Decimation 不是根因

### 4️⃣ 怀疑 RT-LAB 的 Time Factor 被设成 10

打开 Execution Properties 后确认：`Real-time simulation mode = Software synchronized`，`Time Factor = 1.0`。

> ✅ Time Factor 不是原因

### 5️⃣ 怀疑 Modbus 地址或刷新链路错误

日志已证明 FC03 读取正常、FC16 写入正常、`MODEL_STATUS=7`、`CMD_SEQ` 和 `BOARD_HEARTBEAT` 持续增加。40116 并非完全不变化，而是约 10 秒变化一次——更像心跳生成源本身推进缓慢，而不是地址完全接错。

> ✅ Modbus 基础通信不是根因

到这个阶段，需要直接检查：**模型是否真的按照现实时间运行。**

---

## 五、Monitoring 是怎样最终定位问题的

RT-LAB 的 Monitoring 可以理解成：

> 给实时模型装了一个"每步计算计时器"。

它会记录模型每个计算周期实际花了多长时间，并与允许的步长进行比较。

当前模型顶部显示：

```
Ts = 1.0E-4 s
```

即 $T_s = 0.0001\ \mathrm{s} = 100\ \mu s$。

这意味着模型**每一步只有 100 μs 的计算预算**。

---

## 六、Monitoring 界面每一部分是什么意思

### 1️⃣ 顶部的 Ts

```
Ts = 1.0E-4 s
```

表示基本步长 **100 μs**，即 OP5700 每 100 μs 必须完成一次完整模型更新。理论上每现实 1 秒要执行 $1 / 0.0001 = 10000$ 个计算步。

### 2️⃣ Number of overruns

截图显示约 **2,926,676**。Overrun 就是：当前计算步还没有完成，下一步规定的开始时间已经到了。

当时模型时间约 $T = 292.6599\ s$，理论计算步数约 $292.6599 / 0.0001 = 2,926,599$，与 overrun 数量几乎相同。说明**几乎每一个计算步都发生了超限**——不是偶尔慢一步，而是持续性、系统性的无法满足 100 μs 要求。

### 3️⃣ Usage [%]

根节点和 `sm_circuit` 都显示 **100.0%**。结合红色显示和 overrun 数量，实际含义是**已经超过允许预算**。由于显示上限通常只显示 100%，即使实际需要 900% 以上，也可能仍显示 100%。

### 4️⃣ Min、Max、Mean

这三列分别表示采集期间最短、最长、平均计算时间。例如 `sm_circuit`：

| 指标 | 时间 |
|------|------|
| Min | 693.55 μs |
| Max | 1157.07 μs |
| Mean | 926.30 μs |

允许时间只有 **100 μs**。即使最快的一步，也超过预算约 6.9 倍。

### 5️⃣ 总步时间与实时速度比

Total step size 平均约 **981.21 μs**，与预算 100 μs 的比例为 $981.21 / 100 \approx 9.81$。当前模型大约只能达到 **0.102 倍实时速度**——现实经过约 9.8 秒，模型时间才前进约 1 秒，与 40116 约 10 秒才变化一次完全对应。

## 七、各个 Monitoring 项目具体表示什么

### Major computation time

```
Min  = 654.50 μs
Max  = 1117.96 μs
Mean = 887.22 μs
```

最主要的模型计算时间，包含大量主电路、逆变器、控制和电气系统计算。这是当前**最大的瓶颈**。

### Minor computation time

```
Mean ≈ 36.77 μs
```

辅助计算、小步处理或其他次级计算任务。与 Major 叠加后约 924 μs，与 Execution cycle 的 926.30 μs 基本一致。

### Execution cycle

```
Min  = 693.55 μs
Max  = 1157.07 μs
Mean = 926.30 μs
```

模型从本周期开始计算到主要执行任务结束，实际使用的时间。

### Total step size

```
Min  = 700.11 μs
Max  = 1200.26 μs
Mean = 981.21 μs
```

最容易用来和 100 μs 直接比较的数据——一个完整仿真步从开始到下一步之间的总实际耗时。

### Total idle

```
Mean = -881.17 μs
```

负数表示本周期不但没有空闲，而且已经欠下一周期约 881 μs（来自 $100 - 981.17 = -881.17$）。这是最直观的超限证据之一。

### New data acquisition

```
Mean ≈ 0.16 μs
```

耗时很小，说明 Monitoring 数据采集本身不是造成 981 μs 总耗时的主要原因。

### Data 区域中的 1~6

右侧 Data 1~6 是最近抓取的若干个实时样本。例如 Execution cycle 中显示 1011.95、1009.82、844.71、829.06、695.44、1012.38 μs 等。红色叉号表示这些采样对应周期存在 overrun——因为这些值全部远大于 100 μs，所以连续多个样本都显示红色。

## 八、为什么模型能够 Execute，却仍然有问题

本次最重要的认识之一。RT-LAB 显示 Build/Load/Execute 成功，分别只说明：

| 状态 | 含义 |
|------|------|
| Build 成功 | 模型能够生成并编译代码 |
| Load 成功 | 代码能够下载到目标机 |
| Execute 成功 | 模型进程能够启动并持续计算 |

**它们不自动证明每一步都能在规定时间内完成。**

当前模型 Performance Properties 中设置的是 `Action on overruns = Continue`，所以即使每一步都超限，模型仍继续运行，不会自动停止。如果没有板端心跳和 Monitoring，我们可能只看到 Scope 波形在变化，误以为实时运行完全正常。

因此这次 V3.2 心跳实际上帮助我们发现了一个此前隐藏的问题。

## 九、这个问题对当前任务有什么影响

### 对 V3.2 通信验收的影响

板端要求心跳持续变化且连续 3 个有效周期才能使能。但 RT-LAB 心跳约 10 秒才变化一次，板端 3.5 秒就判定超时。会形成：心跳变化 → 短暂恢复 → 可能刚进入 ENABLED → 很快超过 3.5 秒 → 立即退出 ENABLED。最终可能表现为使能周期性投入和退出。

因此当前不能把 `external_enable_request: true` 作为正式验收继续运行。当前保持 false 时程序停留在 `WAIT_VALID`，正是正确的安全行为。

### 对 V4 板端 AGC 的影响

V4 板端 AGC 计划每 1 秒读取一次 RT-LAB 数据。但 RT-LAB 模型时间比现实慢约 10 倍：板端每秒读取的数据可能只是模型推进约 0.1 秒后的结果，板端和模型对同一时刻的理解不一致，AGC 比较结果失去时间对齐。所以即使通信能收发，也不能认为 V4 影子运行已经具备正确的实时条件。

### 对 V5 硬件闭环的影响

V5 中板端命令将真正作用于 RT-LAB 设备。模型严重落后会造成：命令更新频率与模型动态不匹配、设备响应时间测量失真、故障发生和保护动作的实际时序失真、HIL 结果不能代表真实控制器与电网的实时交互。对最终闭环而言，这是**必须解决的问题**。

### 对此前 AGC 试验的理解

此前在普通 Simulink 或 RT-LAB 中看到的控制趋势，仍可用于分析算法方向、资源优先级、稳态分配和逻辑是否闭合。但在严重超限条件下，不能直接把现实秒表测得的时间当成模型动态响应时间。需要区分**模型时间轴上的 1 秒**和**现实墙钟上的 1 秒**——只有实时运行后，两者才能直接等同。

## 十一、100 μs 是否必须保留

不一定。100 μs 只是当前模型的固定基本步长，代表模型希望每 100 μs 更新一次。它可能是原建模人员为了描述逆变器、电流环、电压环或较快电气暂态而选择的。

一个合理的实时步长必须同时满足：

```
1️⃣ 足够描述目标物理过程
2️⃣ 数值计算稳定
3️⃣ 目标机能在该步长内完成计算
```

当前 100 μs 明显不满足第三项。因此真正的要求不是"无论如何必须坚持 100 μs"，而是：**在保证研究所需模型精度的前提下，选择目标机能够稳定实时完成的步长或模型结构。**

## 十二、接下来初步决定怎样处理

### 第一阶段：保存当前基线

保留当前 100 μs 模型、Monitoring 截图、overrun 数量、V3.2 板端日志、心跳 175/176 缓慢变化记录。这组材料证明了问题发生前的原始状态。

### 第二阶段：复制模型再试验

为避免破坏当前模型，先建立副本（例如 `three_two_v32_step_test`），所有步长修改只在副本中完成。

### 第三阶段：确认步长设置和采样依赖

进入 Simulink → Model Settings → Solver，确认 `Fixed-step size = 0.0001`。并检查模型内部是否存在写死的 0.0001 s 采样时间、PWM 周期、控制周期、Rate Transition、离散滤波器周期等——因为基本步长增大后，这些模块可能需要同步调整或重新评估。

### 第四阶段：初步测试 2 ms

当前平均总步耗时约 981 μs，最大约 1200 μs。如果步长改成 1 ms，平均计算时间已接近 1 ms、最大时间又超过 1 ms，仍可能频繁 overrun。

初步候选值：**2 ms**（即 `Fixed-step size = 0.002 s`）。在计算量近似不变的情况下，平均使用率约 49%，最大使用率约 60%，可以留下一定安全余量。

> 2 ms 只是第一个工程试验值，不是最终认定值。

### 第五阶段：重新验证

修改副本后重新 Build → Load → Execute → Monitoring。通过标准至少包括：

```
不再连续 overrun
Total idle 为正
CPU Usage 不长期 100%
40116 每现实约 1 秒增加 1
板端不再 HEARTBEAT_TIMEOUT
```

建议实时使用率不要刚好接近 100%，而应留出一定余量。

### 第六阶段：验证模型结果是否还能接受

实时运行成功不代表模型精度一定合格。还要比较 100 μs 和 2 ms 下的 PCC 稳态值、PV/ESS/EV 实际功率、设备命令响应、电压和频率、AGC 闭环结果，以及是否出现振荡或数值异常。

如果 2 ms 满足通信验收但无法准确表示电力电子快速动态，就需要分开处理：

- **V3.2 通信验收**：使用轻量模型或较大步长副本
- **最终完整 HIL**：优化模型、分核、平均化，或使用 FPGA/eHS

## 十三、当前最准确的阶段性结论

> 在 V3.2 首次联合运行中，板端程序成功完成 FC03、FC16 以及状态字、命令序号和板端心跳交互，但持续报告 RT-LAB 心跳超时。检查心跳代码、冻结输入、Clock 抽取参数、RT-LAB 运行模式和 Time Factor 后，均未发现错误。通过 RT-LAB Monitoring 最终确认，当前模型固定步长为 100 μs，而一个完整计算步平均需要约 981 μs，最大约 1200 μs，几乎每一步均发生 overrun，导致模型时间仅以约 0.1 倍现实速度推进。40116 基于模型时间生成，因此约每 10 个现实秒才增加 1，板端在 3.5 秒后正确判定心跳超时。当前问题的核心不是通信或心跳程序，而是完整微电网模型在 100 μs 步长下无法实时运行。下一步将在模型副本中检查采样时间依赖，并初步测试 2 ms 步长，再通过 Monitoring、心跳和关键电气结果共同判断是否可用。
