# 1. 先只记住一句话：这个模型到底在干什么

整个LOCAL15（本地15策略闭环）做的事情可以压缩成一句话：

> **先由15种高级策略“看懂当前微电网发生了什么、提出控制建议”，再把这些性质不同的建议按P/Q/模式等执行域分类、仲裁、翻译成六台设备和PCC断路器真正能执行的命令，最终送进2PV+2ESS+2EV真实实时对象，并重新测量形成闭环。**

因此真正的因果链不是：

```text
15个策略
↓
直接控制6台设备
```

而是：

```text
真实微电网测量
↓
15种策略判断
↓
策略输出标准化
↓
按执行域分类
↓
同类策略仲裁
↓
资源分配
↓
设备命令生成
↓
控制源选择
↓
执行故障/能力差异
↓
最终设备实际命令
↓
2PV + 2ESS + 2EV Plant（被控对象）
↓
PCC / 六设备重新测量
↓
反馈到下一轮判断
```

这就是你理解整个模型最重要的主轴。

# 2. 为什么15种策略一定要“分类执行”，不能把15个cmd直接相加

原始模块：

`Advanced_Microgrid_15_Strategies（15种微电网高级策略判断模块）`

输出四个15维向量：

- `strategy_status[15]（15策略状态）`
- `strategy_alarm[15]（15策略告警）`
- `strategy_metric[15]（15策略指标）`
- `strategy_cmd[15]（15策略原始控制建议）`

问题在于：

> `cmd(1)` 到 `cmd(15)` 虽然都叫 `cmd（命令/建议量）`，但它们根本不是同一种物理量。

例如：

| 策略 | 原始 `cmd（建议量）` 的实际含义 |
|---|---|
| S1 | 需要减少购电峰值的有功修正量，kW |
| S2 | PCC跟踪所需 `dP（有功调节量）`，kW |
| S3 | 总无功需求，kvar |
| S4 | 外送越限后需要压回的有功修正量，kW |
| S5 | 孤岛/异常判断标志，不是kW |
| S6 | 光伏爬坡率超过允许值的程度，不是直接设备Pref |
| S7 | 联络线PCC跟踪所需 `dP（有功调节量）`，kW |
| S8 | 低压/低频下需要减载的kW |
| S9 | 削峰填谷有功调节量，kW |
| S10 | 周期计划给出的PCC目标功率，kW |
| S11 | 余电外送越限修正量，kW |
| S12 | 为新能源消纳需要增加的内部吸收量，后续需翻译为有功方向 |
| S13 | 多目标策略给出的有符号有功建议 |
| S14 | 黑启动阶段号/状态，不是设备功率 |
| S15 | 并离网切换请求/状态，不是设备功率 |

所以：

```text
cmd1 + cmd2 + ... + cmd15
```

在物理意义上就是错误的。

真正正确的做法是：

```text
先判断：
这个策略最终要改变什么？

改变P？
改变Q？
改变运行模式？
改变PCC断路器？
改变ESS的GFM/GFL？
改变ESS频率参考？
改变EV负荷？
```

然后再进入对应执行链。

这就是 `AA15_LOCAL_CONTROL_STACK（本地15策略控制栈）` 存在的根本原因。

# 3. 最终应该把15策略理解成“四个主要执行域 + 一个公共执行尾部”

虽然模型界面上你主要画了：

- `P链（有功链）`
- `Q链（无功链）`
- `模式链（运行模式链）`

但从最终功能上，为了真正理解，我建议你在脑子里分成下面五块。

## 3.1 P Domain（有功执行域）

负责：

> “PCC总共需要增加/减少多少有功，以及六台设备的Pref（有功参考）最终应该是多少？”

包括：

- S1
- S2
- S4
- S6
- S7
- S8
- S9
- S10
- S11
- S12
- S13

其中又分：

```text
主目标
S7 / S9 / S10 / S12 / S13
（S2可作为S7关闭时的专门测试/回退目标）

硬约束/纠偏
S1 / S4 / S11

辅助执行
S6 / S8
```

---

## 3.2 Q Domain（无功执行域）

负责：

> “S3提出多少无功需求，以及六台逆变器各自分多少Qref（无功参考）？”

主要就是：

- S3 AVC（自动电压控制）

---

## 3.3 Mode / Safety Domain（模式/安全执行域）

负责：

> “系统此刻应该是正常并网、应急、正在离网、已孤岛、黑启动还是重同步？PCC断路器是否允许开/合？哪台ESS应该成为GFM（构网型）主机？”

主要涉及：

- S5 防孤岛
- S8 低压/低频应急状态
- S14 黑启动
- S15 并离网/恢复

---

## 3.4 Recovery / Synchronization Domain（恢复/同步执行域）

这是模式链的后半段，但为了理解最好单独看。

负责：

> “已经孤岛以后，怎样比较Grid（上级电网）和PCC两侧电压、频率、相角，怎样调ESS主机频率，什么时候允许PCC重合闸，什么时候恢复NORMAL（正常并网）？”

核心是：

- S15 Recovery（策略15恢复）
- PCC重合闸
- ESS主机 `Fref（频率参考）` 修正

---

## 3.5 Common Execution Tail（公共执行尾部）

主要针对P命令：

```text
Command Source Router（命令源路由）
↓
u_commit（准备正式执行的命令）
↓
Execution Fault Injector（执行故障注入）
↓
u_applied（设备实际采用命令）
↓
Active-P Takeover / Safety（最终安全选择）
↓
FINAL_APPLIED（最终送给Plant的有功命令）
```

它回答的是：

> “控制算法算出来了以后，这条命令究竟有没有被选中、有没有被执行故障改变、最后真正送给设备的又是多少？”

# 4. 你现在模型中的“P链 / Q链 / 模式链”区域划分到底对不对

## 4.1 结论

**概念方向是对的，但不能把彩色区域边界当成严格的软件模块边界。**

当前SLX中三个区域实际大致覆盖：

### Q链区域

主要包含：

- `AA15_S3_AVC_Normalizer（S3自动电压控制标准化器）`
- `AA15_Q_Allocator_Router（无功能力分配与路由器）`

这一区域最干净，**划分正确。**

---

### P链区域

主要包含：

- `AA15_Request_Normalizer（请求标准化器）`
- `AA15_Request_Normalizer_P_Extension（有功请求扩展标准化器）`
- `AA15_P_Objective_Arbiter（早期有功目标仲裁器）`
- `AA15_P_Objective_Constraint_Manager（最终有功目标/约束管理器）`
- `AA15_Arbitrated_Baseline_AGC（仲裁后基础AGC）`
- `AA15_Execution_Mapper（执行映射器）`
- `AA15_P_Auxiliary_Executor（有功辅助执行器）`
- `AA15_Black_Start_Pref_Gate（黑启动有功参考门控）`
- `AA15_Command_Source_Router（命令源路由器）`
- `AA15_Execution_Fault_Injector（执行故障注入器）`
- `AA15_Active_P_Takeover（有功最终安全接管）`

**整体是正确的。**

其中 `AA15_Black_Start_Pref_Gate（黑启动有功参考门控）` 虽然由S14模式状态驱动，但它改变的是六设备Pref，所以放在P链也合理。

---

### 模式链区域

主要包含：

- `AA15_Mode_Manager（模式管理器）`
- `AA15_Grid_Mode_Execution_Manager（电网模式执行管理器）`
- `AA15_Device_Mode_Router（设备模式路由器）`
- `AA15_S15_Recovery_Manager（S15恢复管理器）`

概念也正确。

但有几个跨域模块在视觉位置上并不完全符合“链”的语义：

1. `AA15_S6_S8_Normalizer（S6/S8标准化器）`视觉上位于模式链区域，但：
   - S6主要进入P辅助链；
   - S8既进入P辅助执行，又进入Mode Manager（模式管理器）产生EMERGENCY（应急）状态。
   - 所以它本来就是跨P/模式两个域。

2. `AA15_S5_S14_S15_Normalizer（S5/S14/S15标准化器）`在模式链彩色区域外，但语义上属于模式链前端。

3. `AA15_PCC_Breaker_Command_Router（PCC断路器命令路由器）`在模式链区域下方，但逻辑上就是模式/恢复链的最终执行端。

4. `AA15_S15_Master_Fref_Router（S15主机频率参考路由器）`也在彩色区域外，但它逻辑上属于S15恢复链。

因此：

> **模型的区域划分适合帮助看大类，但真正学习时应按“信号因果链”而不是按彩色框的位置理解。**

当前模型已经冻结，不需要为了视觉分类重新改结构。

# 7. SM_Master中与LOCAL15真正有关、但在控制栈外面的模块

下面这些模块是你之前最容易忽略的。它们之所以放在 `AA15_LOCAL_CONTROL_STACK（本地15策略控制栈）` 外面，是因为它们承担的是“数据采集、配置、原系统接口或真实Plant接线”职责，不适合全部塞进算法栈。

---

## 7.1 `Advanced_Microgrid_15_Strategies（15种微电网高级策略判断模块）`

### 为什么存在

它是15种策略的**原始判断层**。

它读取：

- `Ppcc（PCC有功）`
- `Qpcc（PCC无功）`
- `Vpcc（PCC电压）`
- `Freq（频率）`
- `SOC1/SOC2（储能荷电状态）`
- `PV1/PV2（光伏最大可用功率）`
- `comm（通信状态）`
- 15种策略阈值参数

输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

### 它不负责什么

它**不负责**：

- 六设备资源分配；
- Pref/Qref最终生成；
- GFM/GFL（构网/跟网）切换；
- PCC真实断路器；
- 最终控制源选择。

因此可以把它理解成：

> **“15个专家给出建议”，而不是“15个执行器直接抢设备控制权”。**

---

## 7.2 `AA15_CFG15_PANEL（LOCAL15统一配置面板）`

### 为什么存在

它统一产生：

- `CFG15_MASTER_ENABLE（LOCAL15总使能）`
- `CFG15_CONTROL_SOURCE（控制源）`
- `CFG15_P_OBJECTIVE_MODE（有功主目标模式）`
- `CFG15_EXEC_S01～S15（各策略执行许可）`
- `CFG15_MODE_ACTUATION_ENABLE（模式真实执行使能）`
- `CFG15_PCC_BREAKER_ACTUATION_ENABLE（PCC断路器真实执行使能）`
- `CFG15_BLACKSTART_MASTER（黑启动主ESS）`
- `CFG15_ISLAND_MASTER（孤岛主ESS）`
- S15同步阈值、频率修正参数
- 执行故障注入参数等。

### 它和 `CFG_AA_*（原15策略参数）` 的区别

`CFG_AA_*（原策略参数）`：

> 决定策略本身怎么判断。

例如：

- 防逆流阈值；
- 低频阈值；
- AVC电压死区。

`CFG15_*（LOCAL15执行框架参数）`：

> 决定策略有没有执行权、谁是主目标、是否允许真实接管。

这是两个不同层级。

---

## 7.3 `AA15_CFG15_TUNABILITY_MONITOR（配置可调性监视器）`

这不是控制算法。

作用是：

> 验证 `CFG15_*` 参数在RT-LAB运行时仍保持Tunable（可在线修改），防止代码生成以后参数被优化成不可调。

所以它属于：

**配置质量检查 / 诊断辅助**

不是：

**控制链核心。**

---

## 7.4 `AA15_AGC_INPUT_TAPS（AGC输入旁路抽取模块）`

这是非常重要但很容易觉得“多余”的模块。

### 它做什么

从原AGC（自动发电控制）的真实输入线上无侵入复制：

- `t（时间）`
- `P_target（PCC目标）`
- `P_pcc（PCC实际有功）`
- `PVmax1/2（光伏最大可用功率）`
- `SOC1/2（储能荷电状态）`
- `enable（使能）`
- `P_unit（功率基准）`
- `P_dead（有功死区）`
- `SOC_min/max（SOC上下限）`
- `Ts_agc（AGC更新周期）`
- `PV_init（PV初值）`
- `EV_init（EV初值）`

然后用Goto（标签发送）发布给LOCAL15内部AGC。

### 为什么不直接再拉一套线

因为要保证：

```text
旧AGC
和
LOCAL15使用的AGC
```

吃到完全同源的输入。

否则输出不同的时候，你无法判断到底是：

- 算法差异；
还是
- 输入源差异。

## 7.5 `AA15_BASELINE_AGC_SHADOW（基础AGC影子对照）`

它是**对照组**，不是最终控制路径。

它的作用是在早期证明：

```text
旧AGC内部自己算
dP = Ptarget - Ppcc

与

外部先算dP
再送给改造后的AGC
```

两者完全等价。

这一步证明后，最终真正使用的是：

`AA15_Arbitrated_Baseline_AGC（仲裁后基础AGC）`

而不是这个Shadow（影子）模块。

所以：

> **BASELINE_AGC_SHADOW应该理解为“实验标尺”，不是最终LOCAL15控制器。**

## 7.11 `AA15_S11_STRATEGY_MODE_TAPS（模式判断输入抽取）`

# 9. P链：从“策略提出要求”到“六设备真正得到Pref”的完整因果链

P链是当前最复杂、也是你最应该彻底掌握的一条链。

---

## 9.1 第一步：`AA15_Request_Normalizer（请求标准化器）`

### 解决什么问题

原来只有：

```text
cmd(2)
cmd(7)
```

这种“按索引取值”。

它把它们变成有明确名字的信号：

- `S2_DPREQ_KW（策略2有功调节请求）`
- `S7_DPREQ_KW（策略7有功调节请求）`

同时保留：

- status（状态）
- alarm（告警）
- metric（指标）

### 为什么S2/S7先单独提取

当前老师原始算法里：

```text
S2 cmd = Ptarget - Ppcc
S7 cmd = Ptarget - Ppcc
```

数值语义相同。

所以正常不能：

```text
S2 + S7
```

叠加两次。

---

## 9.2 `AA15_P_Objective_Arbiter（早期P目标仲裁器）`：你必须知道它现在是什么身份

它是Stage03时建立的早期S2/S7仲裁器。

逻辑：

```text
S7开启
→ S7执行
→ 如果S2也开启，S2只监视

S7关闭、S2开启
→ S2可以在专项测试中执行
```

但最终Stage08以后，真正驱动AGC的已经不是它。

最终真正控制P链的是：

`AA15_P_Objective_Constraint_Manager（P目标/约束管理器）`

因为后者已经统一纳入：

- S1
- S2
- S4
- S7
- S9
- S10
- S11
- S12
- S13

所以：

> **`AA15_P_Objective_Arbiter` 当前更应该理解成“早期结构保留/诊断对照”，而不是最终P链的唯一仲裁核心。**

这是阅读最终模型时一个非常重要的纠正。

---

## 9.3 `AA15_Request_Normalizer_P_Extension（P请求扩展标准化器）`

从 `cmd15（15维原始命令）` 里提取：

- S1
- S4
- S9
- S10
- S11
- S12
- S13

并把它们翻译成统一P语义：

### S1

`S1_IMPORT_RELIEF_KW（购电超限修正量）`

正值表示：

> 当前购电太多，需要把微电网净有功往“更正”的方向推。

---

### S4

`S4_EXPORT_RELIEF_KW（外送超限修正量）`

正值代表“超限幅度”。

进入最终P管理器时会被翻译成：

> 需要负方向dP，压低外送。

---

### S9

`S9_DPREQ_KW（削峰填谷有功请求）`

保留原有符号。

---

### S10

`S10_TARGET_KW（周期计划PCC目标）`

注意它不是dP。

后面需要计算：

```text
dP = target - current PCC
```

---

### S11

`S11_EXPORT_RELIEF_KW（余电外送约束修正量）`

属于外送约束，与S4同方向。

---

### S12

原始S12正cmd表示：

> 还需要吸收更多新能源。

当前PCC内部方向下，增加充电/吸收意味着负dP，所以标准化为：

```text
S12_DPREQ = -max(cmd12, 0)
```

---

### S13

保留原策略给出的有符号P建议。

---

## 9.4 `AA15_P_Objective_Constraint_Manager（最终P目标/约束管理器）`

这是最终P链真正的“交通警察”。

它把有功策略分成两类。

### A. Main Objective（主目标）

一次只能选一个：

```text
P_OBJECTIVE_MODE = 0
→ S7为主
→ S7没执行时可用S2

P_OBJECTIVE_MODE = 1
→ S9

P_OBJECTIVE_MODE = 2
→ S10

P_OBJECTIVE_MODE = 3
→ S12

P_OBJECTIVE_MODE = 4
→ S13
```

为什么主目标不能相加？

因为它们回答的是同一个问题：

> “这一轮PCC最终应该往哪个方向调多少？”

如果S7、S9、S10同时相加，就是三个调度目标相互叠加，物理意义不清。

---

### B. Corrective Constraint（纠偏约束）

- S1：购电过大约束；
- S4：防逆流/外送过大约束；
- S11：余电外送约束。

它们不重新定义“我要去哪”，而是说：

> “无论你主目标是什么，都不能突破当前硬边界。”

所以最后形成两个重要量：

```text
objective_dP（主目标有功调节量）
↓
叠加/裁剪约束
↓
effective_dP（真正交给AGC执行的有功调节量）
```

你必须会区分这两个量。

---

## 9.5 `AA15_Arbitrated_Baseline_AGC（仲裁后基础AGC）`

输入核心变成：

`effective_dP（最终有效有功调节需求）`

而不是让AGC自己决定PCC目标。

它负责：

> **“已经确定总共需要调多少以后，六台资源各自承担多少？”**

所以P链清楚分成：

```text
策略层：
决定“为什么调、总共调多少”

AGC资源协调层：
决定“谁来调、各调多少”
```

AGC输出：

- PV1 Pref Candidate（PV1候选有功）
- PV2 Pref Candidate
- ESS1 Pref Candidate
- ESS2 Pref Candidate
- EV1 Pref Candidate
- EV2 Pref Candidate

以及：

- AGC status（AGC状态）
- dP
- remain（剩余未满足量）

---

## 9.6 `AA15_Execution_Mapper（执行映射器）`

AGC的六路结果还不能无条件认为合法。

该模块做设备物理域裁剪：

```text
PV：
0 ～ +1 pu

ESS：
-1 ～ +1 pu
正 = 放电
负 = 充电

EV：
-1 ～ 0 pu
负 = 充电
0 = 停止充电
```

同时检查：

- 是否有限数；
- `master_enable（总使能）`
- `request_valid（请求是否合法）`

最终形成：

`local_active_valid（LOCAL15有功候选有效）`

可以把它理解成：

> **把“调度员写的计划”转换成“每台设备物理上允许的命令”。**

---

## 9.7 `AA15_S6_S8_Normalizer（S6/S8标准化器）`

从15维原始策略输出里抽出：

### S6

- S6 status
- S6 alarm
- S6 metric
- `S6_CMD_RATE_EXCESS（S6爬坡超限量）`

### S8

- `S8_STATUS_STAGE（S8减载阶段）`
- S8 alarm
- S8 metric
- `S8_CMD_SHED_KW（S8减载需求kW）`

它本身不最终改设备，只负责把匿名向量变成明确接口。

---

## 9.8 `AA15_P_Auxiliary_Executor（P辅助执行器）`

它插在：

```text
Execution Mapper
↓
P Auxiliary Executor
↓
Command Source Router
```

这个位置非常关键。

### 为什么S6/S8不放到P主目标前

因为：

- S7/S9/S10等决定长期PCC主调度；
- S6是快速平滑补偿；
- S8是紧急负荷减载。

它们不是同一层级。

---

### S6实际怎么做

当前模型的S6依据PV最大可用功率变化形成平滑参考。

如果光伏突然上升/下降：

```text
PV变化
↓
平滑参考不能一步跟上
↓
得到补偿功率需求
↓
ESS1/ESS2按当前剩余充放电空间承担
```

所以S6最终主要改变：

- ESS1 Pref
- ESS2 Pref

它不是重新修改PCC主目标。

---

### S8实际怎么做

S8的 `cmd8（策略8命令）` 是需要减掉的负荷kW。

当前可控负荷采用EV充电：

```text
先减少EV2充电
↓
还不够
再减少EV1充电
```

由于EV充电Pref是负值：

```text
减载
=
把EV Pref从更负的值往0移动
```

因此S8属于P辅助执行。

同时S8的stage（阶段）还会送给Mode Manager（模式管理器），让系统进入：

`EMERGENCY（应急模式）`

所以S8是典型的跨P/模式策略。

---

## 9.9 `AA15_Black_Start_Pref_Gate（黑启动有功参考门控）`

这是P链与模式链第一次明显交叉。

它读取：

- P辅助执行以后六路Pref；
- `executed_system_mode（实际执行系统模式）`
- S14 black-start stage（黑启动阶段）
- selected master（选定构网主机）

如果不是Black Start（黑启动）：

```text
精确透传原六路Pref
```

如果进入Black Start：

### Stage 1（阶段1）

```text
PV = 0
ESS1 = 0
ESS2 = 0
EV = 0
```

主ESS通过GFM（构网）/Droop（下垂）建立电压频率，不靠P_ref强推有功。

### Stage 2（阶段2）

恢复非主ESS有功命令。

主ESS仍保持P_ref=0，由GFM/Droop维持系统。

### Stage 3（阶段3）

恢复PV发电。

### Stage 4（阶段4）

最后恢复EV充电负荷。

因此：

> **S14虽然是模式策略，但它必须深入P链，因为黑启动的核心就是“负荷/电源按顺序恢复”，最终一定要改变Pref。**

---

## 9.10 `AA15_Command_Source_Router（命令源路由器）`

它回答：

> “这一轮六路Pref到底听谁的？”

当前模型：

```text
CFG15_CONTROL_SOURCE = 0
→ LEGACY_V5A（原V5-A链）

CFG15_CONTROL_SOURCE = 1
→ LOCAL15（本地15策略链）

CFG15_CONTROL_SOURCE = 2
→ BOARD15（板端15策略）
→ 当前最终LOCAL15模型里仍是预留，不可用
```

对于LOCAL15，只有：

`local_valid（本地候选有效）`

成立时才允许选择。

它输出：

`u_commit（准备正式提交/执行的六路命令）`

### 为什么叫u_commit

它表示：

> **控制器这一轮“认为应该执行”的完整六设备命令。**

但是：

> `u_commit ≠ 设备最后一定真的做到。`

这就是下一层存在的原因。

---

## 9.11 `AA15_Execution_Fault_Injector（执行故障注入器）`

输入：

`u_commit`

根据测试参数，可对某台设备注入：

- 指定时间段；
- 指定设备；
- 指定gain（执行比例）。

例如：

```text
控制器要求ESS1 = +0.8 pu
fault_gain = 0.3
↓
设备实际采用 = +0.24 pu
```

于是：

```text
u_commit = +0.8
```

# 11. Q链：为什么比P链短，但绝不是“把S3平均分给六台设备”

Q链当前非常清楚：

```text
Advanced_Microgrid_15_Strategies
↓
S3原始AVC输出
↓
AA15_S3_AVC_Normalizer
↓
AA15_Q_Allocator_Router
↓
六设备FINAL_QREF
↓
六设备Mux input7
↓
逆变器
↓
PCC电压/Q重新变化
```

---

## 11.1 `AA15_S3_AVC_Normalizer（S3 AVC标准化器）`

从四个15维向量中抽出：

- S3 status
- S3 alarm
- S3 metric
- `S3_Q_REQUEST_KVAR（S3总无功需求）`

只是“命名和物理语义明确化”。

---

## 11.2 `AA15_Q_Allocator_Router（无功能力分配器）`

它不是平均分Q。

它先读取六台设备当前已经最终采用的有功：

`AA15_FINAL_APPLIED_PV1...EV2`

因为逆变器受到视在功率限制：

```text
S² = P² + Q²
```

当前用标幺形式估算每台剩余无功能力：

```text
Qcap_i = sqrt(1 - |P_i|²)
```

所以：

> 当前P越接近1 pu，可留给Q的空间越少。

总Q需求被按各设备剩余Q能力比例分配。

例如：

```text
某台设备P很高
→ 剩余Q能力小
→ 少分Q

某台设备P较低
→ 剩余Q能力大
→ 多分Q
```

这就是为什么Q链必须读取P链的FINAL_APPLIED。

---

## 11.3 `CFG15_Q_SIGN_GAIN（无功符号修正系数）`

当前最终模型确认：

```text
CFG15_Q_SIGN_GAIN = +1
```

适合当前K26_V5/LOCAL15接线。

它用于校准：

> S3产生的Q命令方向是否和设备控制器Qref正方向一致。

所以Q链不是孤立的，它依赖：

- S3策略判断；
- 当前六设备P运行点；
- 控制源；
- 策略执行许可；
- Q符号约定。

# 14. `AA15_Mode_Manager（模式管理器）`

这是模式判断的“大脑”。

它不会直接控制断路器，而是先把原始证据整理成系统模式请求。

---

## 14.1 为什么S5不能直接让PCC跳闸

原S5 `islandScore（孤岛评分）` 是：

```text
频率异常
OR
电压异常
OR
通信异常
```

如果直接：

```text
cmd(5)=1
→ PCC跳闸
```

那么纯通信故障也会断开PCC。

LOCAL15专门重新判断：

```text
v_bad（电压异常）
f_bad（频率异常）
electrical_bad（电气异常）
comm_bad（通信异常）
comm_only_raw（只有通信异常）
```

真正的：

`S5 execute request（S5真实离网执行请求）`

明确要求：

```text
electrical_bad = 1
```

所以：

> **通信异常可以报警，但通信异常本身不能作为PCC电气跳闸理由。**

这是安全逻辑里非常重要的一点。

---

## 14.2 Mode Manager输出的system_mode（系统模式）

编码：

```text
0 = NORMAL（正常并网）
1 = EMERGENCY（并网应急）
2 = ISLANDING（正在离网）
3 = ISLANDED（已孤岛，后续执行管理层形成）
4 = BLACK_START（黑启动）
5 = RESYNCHRONIZATION（重同步，恢复管理层形成）
6 = FAULT_SAFE（故障安全）
```

Mode Manager当前原始优先级：

```text
BLACK_START
>
ISLANDING
>
EMERGENCY
>
NORMAL
```

其中：

- S14请求 → BLACK_START；
- S15 + 有效电气异常 → ISLANDING；
- S8减载阶段有效 → EMERGENCY；
- 否则NORMAL。

---

## 14.3 `allow_normal_p / allow_normal_q / allow_s6`

Mode Manager还会输出：

- `allow_normal_p（允许正常P控制）`
- `allow_normal_q（允许正常Q控制）`
- `allow_s6（允许S6平滑）`

但必须注意：

> **在当前最终LOCAL15模型中，这几个量主要是模式语义/诊断信号，并没有成为所有P/Q执行器的统一硬门控。**

当前核心代码本身也明确：

`Permissions are advisory（这些许可当前是建议/语义性输出）`

所以不能看到它们就误以为：

```text
allow_q = 0
→ Q链一定立刻全部清零
```

当前不是这样。

---

# 15. `AA15_Grid_Mode_Execution_Manager（电网模式执行管理器）`

Mode Manager只是说：

> “我认为应该离网/黑启动。”

但真正执行需要：

- `master_enable（总使能）`
- LOCAL15被选中；
- `mode_actuation_enable（模式真实执行使能）`
- `breaker_actuation_enable（断路器真实执行使能）`
- route valid（路由有效）

所以又需要一层：

`Grid Mode Execution Manager（电网模式执行管理器）`

---

## 15.1 为什么内部有很多Z1/Unit Delay（一个步长延迟）

它把Mode Manager的动态证据先延迟一个100 μs步长再执行。

作用是：

- 打断组合反馈；
- 避免模式判断和真实执行形成代数环；
- 让“上一拍的判断”在“下一拍”成为真实动作。

这是实时控制结构中常见的状态边界。

---

## 15.2 Island Latch（孤岛锁存）

如果满足：

```text
S5真实电气异常
+
S15转离网请求
```

建立：

`island_latch（孤岛锁存）`

之后即使瞬时原始信号恢复，也不会马上把系统又切回并网。

最终：

```text
executed_system_mode = ISLANDED
breaker request = OPEN
```

直到S15 Recovery（恢复管理器）完成同步并明确清除孤岛锁存。

---

## 15.3 Black Start Latch（黑启动锁存）

S14请求成立：

```text
blackstart_latch = 1
executed_system_mode = BLACK_START
PCC breaker = OPEN
```

黑启动锁存和普通孤岛锁存是分开的。

S15普通恢复逻辑明确不在blackstart_latch存在时运行。

---

# 16. `AA15_S15_Recovery_Manager（S15恢复管理器）`

这是最终模型里最像“完整恢复状态机”的模块。

它的输入包括：

- 当前实际系统模式；
- 当前断路器请求；
- island latch（孤岛锁存）；
- blackstart latch（黑启动锁存）；
- Grid/PCC的频率；
- Grid/PCC的电压；
- Grid/PCC的相角；
- `phase_valid（相角有效）`；
- 恢复请求；
- 同步阈值；
- 主ESS配置；
- 模式/断路器执行许可。

---

## 16.1 它先计算三个同步差

### 电压差

`ΔV（标幺电压差）`

```text
|Vpcc - Vgrid| / |Vgrid|
```

### 频率差

`Δf（频率差）`

```text
fgrid - fpcc
```

### 相角差

`Δθ（相角差）`

并做：

`wrap180（限制到-180°～180°）`

---

## 16.2 sync_ok（同步条件满足）

只有同时满足：

```text
phase_valid = 1
Grid V/f有效
PCC V/f有效
|ΔV| <= 阈值
|Δf| <= 阈值
|Δθ| <= 阈值
```

才认为当前同步合格。

---

## 16.3 S15恢复状态机

当前LOCAL15内部状态可以理解为：

### state 0：IDLE（空闲）

还没开始恢复。

如果：

```text
island_latch = 1
+
recovery_request = 1
```

进入state 1。

---

### state 1：RESYNCHRONIZING（同步中）

保持：

```text
system mode = RESYNCHRONIZATION
PCC breaker = OPEN
```

同时通过Fref修正，让主ESS把PCC孤岛侧频率/相角逐步拉向Grid。

同步条件连续满足 `sync_stable_s（同步稳定时间）` 后：

进入state 2，并请求PCC闭合。

---

### state 2：RECLOSE HOLD（重合闸保持）

```text
PCC breaker = CLOSE
system mode仍保持RESYNCHRONIZATION
```

保持 `reclose_hold_s（重合闸保持时间）`。

之后进入state 3。

---

### state 3：RETURN NORMAL（返回正常）

请求：

```text
system mode = NORMAL
PCC breaker = CLOSE
clear_island = 1
```

等Grid Mode Execution Manager真正清掉island latch以后：

回到state 0。

---

# 17. `AA15_S15_Master_Fref_Router（S15主ESS频率参考路由器）`

S7/S9/S10/S12/S13不能简单相加。

它只负责：

它们是主P命令形成后的辅助/应急动作。

因为：

有功占得越多，无功空间越少。

当前只在ESS1/ESS2中选择一个。

## 9. 通信异常不能自动等价成电气孤岛

当前S5真实跳闸资格要求电气异常证据。

控制器下了命令，不代表设备已经做到。

这是后续论文最关键的物理现实之一。

# 29. 最容易讲错的10件事

1. **“15策略输出直接控制六台设备。”**

3. **“S1/S4/S11也是P主目标。”**  
   错。最终它们是约束修正。

4. **“S6是新的AGC目标。”**  
   错。S6是P辅助补偿。

5. **“S8只属于模式链。”**  
   错。S8同时改变EV Pref，并产生EMERGENCY模式。

6. **“S14只属于模式链。”**

   错。按当前P运行点对应的剩余无功能力分配。

9. **“模式链一接管，所有设备都GFM。”**

10. **“模型彩色框就是严格软件边界。”**  
    错。S6/S8、S14、S15天然跨域，彩色框只是视觉辅助。

# 30. 你应该能够脱离文档讲出的“三分钟版本”

如果老师或工程师突然问：

> “你们这15策略本地闭环到底怎么实现的？”

你可以按下面逻辑讲：

**第一段：先讲为什么要改。**

原模型虽然已经有15种高级策略，但输出只是15组status/alarm/metric/cmd，15个cmd物理意义不同，不能直接相加或直接接设备，所以我们增加了一套LOCAL15执行控制架构。

**第二段：讲分类。**

先按执行域把策略分成P链、Q链和模式/恢复链。P链里，S7/S9/S10/S12/S13属于可选择的主目标，S1/S4/S11属于硬约束，S6/S8属于辅助执行；S3单独进入Q链；S5/S14/S15主要进入模式和恢复链，其中S8、S14、S15会跨域。

**第三段：讲P链。**

原始策略输出先标准化，再由P Objective Constraint Manager选一个主目标并叠加硬约束，得到effective dP；AGC只负责把这个总dP分给2PV+2ESS+2EV；Execution Mapper做物理限幅；S6用ESS补偿PV波动，S8通过减小EV充电实现减载；黑启动时Black Start Pref Gate再按阶段控制资源恢复顺序；然后Source Router在Legacy和LOCAL15之间选控制源，形成u_commit；故障注入以后得到u_applied；最后安全接管形成真正送给六台设备的FINAL_APPLIED Pref。

**第四段：讲Q链。**

S3产生总无功需求，Q Allocator根据六台设备当前有功运行点计算剩余无功能力，再按能力分配六路Qref。

**第五段：讲模式链。**

S5/S14/S15进入Mode Manager。S5不是通信坏了就跳闸，而是必须有电压/频率电气异常。真实离网以后由Grid Mode Execution Manager建立island latch、断开PCC并选一个ESS做GFM；S14黑启动通过模式和Pref门控逐阶段恢复；S15恢复时比较Grid/PCC的ΔV、Δf、Δθ，调主ESS Fref，同步稳定后重合PCC，再恢复NORMAL。

**第六段：讲真实Plant。**

最终六台设备Mux中，Pref、Qref、Droop、GridOn分别来自LOCAL15最终输出，ESS同步时Fref也会被修正，PCC断路器有独立最终命令。Plant响应以后PCC和六设备重新测量，再进入下一轮闭环。

如果这六段能够顺畅讲出来，你就已经真正掌握了这套LOCAL15的总逻辑。
