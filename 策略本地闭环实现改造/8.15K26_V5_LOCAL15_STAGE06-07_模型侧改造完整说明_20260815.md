# 3. 为什么必须区分 `u_calc`、`u_commit`、`u_applied`

未来论文和最终项目都必须明确区分三个量：

```text
u_calc
=
算法算出来的候选命令

u_commit
=
经过仲裁、约束、控制源选择后，
系统决定真正提交的命令

u_applied
=
设备实际采用/真正施加到Plant上的命令
```

当前模型中可以近似对应：

```text
S04 AGC Candidate
≈ u_calc

S05 Router输出
= u_commit SHADOW

S06 Fault Injector输出
= u_applied SHADOW

S07 Final Applied输出
= 实际进入六设备Pref的最终u_applied
```

这三层不能混为一个变量。

因为论文核心问题之一正是：

```text
控制器认为自己提交了 u_commit
但真实对象只采用了 u_applied
```

一旦：

```text
u_commit ≠ u_applied
```

就可能产生：

```text
控制器认知状态
≠
设备真实执行状态
```

这正是后续Strategy2执行状态评估需要识别的对象。

S06的目标不是直接制造某一个固定论文Case。

S06建立的是一个通用的：

```text

```

也就是：

> **执行层故障/执行失配注入基础设施。**

它允许以后根据试验需要选择：

```text

是否启用
```

因此S06解决的是“模型具不具备制造执行失配的能力”，而不是“论文最终一定用ESS1、gain=0.3、20~40秒”。

# 6. 为什么Fault Injector必须放在Source Router之后

如果把故障注入放在AGC之前：

```text
AGC会知道自己输出被改了
```

那就不再是“执行器/设备执行失配”。

如果放在：

```text
Source Router
↓
u_commit
```

之后，则可以形成真正的：

```text
控制器提交：
u_commit = 1.0

设备实际采用：
u_applied = 0.3
```

而控制器本身仍然可以认为：

```text
自己提交的是1.0
```

这才符合论文想研究的：

```text
controller belief / committed command
与
plant-side real actuation
发生分叉
```

# 10. S06当前采用的执行故障模型

当前V0.1使用：

```text
u_applied(device)
=
gain × u_commit(device)
```

例如：

```text
u_commit_ESS1 = 0.8 pu
gain = 0.3
```

则：

```text
u_applied_ESS1
=
0.24 pu
```

但：

```text
u_commit_ESS1
仍然是0.8 pu
```

因此产生：

```text
u_commit ≠ u_applied
```

# 11. 为什么选择“增益退化”作为第一版执行故障

因为它具有三个优点。

第一：

```text
简单、可解释
```

例如：

```text
gain=0.3
```

非常明确地表示：

```text
设备只能执行30%的提交命令
```

第二：

```text
连续可调
```

以后可以比较：

```text
gain=0.8
0.5
0.3
0
```

而不是只有：

```text
正常/完全故障
```

第三：

```text
非常适合论文Strategy2验证
```

因为通信可以保持完全正常：

```text
FC03正常
FC16正常
CMD_SEQ正常
heartbeat正常
```

但设备真实执行：

```text
Pmeas
```

会逐渐表现出和提交命令不一致。

这能把“执行失配”和“通信故障”干净地分开。

# 12. 为什么S06把gain限制在 `[0,1]`

脚本中：

```text
g = clamp(fault_gain, 0, 1)
```

所以：

```text
gain < 0
→ 按0处理

gain > 1
→ 按1处理
```

原因是当前S06定义的是：

> **执行能力退化**

而不是：

```text
命令反相
过执行
倍增故障
```

如果以后论文或项目确实需要：

```text
stuck
bias
deadband
delay
sign reversal
```

可以扩展Fault Mode。

但第一版先保证：

```text
故障模型简单、稳定、物理意义明确
```

# 13. S06的故障时间窗

只有满足：

```text
CFG15_EXEC_FAULT_ENABLE = 1
```

并且：

```text
fault_start_s <= t < fault_end_s
```

才真正注入。

如果：

```text
fault_end_s <= fault_start_s
```

则不注入。

如果：

```text
FAULT_ENABLE = 0
```

则：

```text
六路 u_applied = 六路 u_commit
```

# 29. 为什么S07只对NaN/Inf回退，不对“故障退化”回退

这点非常重要。

例如S06制造：

```text
u_commit_ESS1 = 0.8
gain=0.3
u_applied_ESS1 = 0.24
```

0.24是：

```text
有限合法值
```

所以S07必须：

```text
让0.24真正进入Plant
```

不能因为它和Legacy不同就自动恢复。

否则：

```text
执行故障永远到不了Plant
```

也就无法形成真实：

```text
u_commit ≠ u_applied
```

所以S07只保护：

```text
非法数值
```

而不是“把一切差异都消掉”。
