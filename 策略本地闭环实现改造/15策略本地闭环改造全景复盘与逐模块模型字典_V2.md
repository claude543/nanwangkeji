# 1. 最开始的问题到底是什么

最初模型里已经有：

```text
Advanced_Microgrid_15_Strategies
```

它输入：

```text
P
Q
V
f
SOC
PVmax
通信状态
各类策略参数
...
```

输出：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

表面上看“15个策略都存在”。

但它本质仍然是：

> **策略判断层 / 高级应用建议层**

而不是：

> **真实六设备协调执行层**

## 1.1 为什么 `cmd[15]` 不能直接接设备

因为15个 `cmd` 的物理含义根本不同。

例如：

```text
S2 / S7
→ 有功调节请求 dP

S3
→ 总无功需求

S4
→ 出口越限量

S6
→ 平滑需求/变化率

S8
→ 需要减载多少 kW

S10
→ PCC目标值

S14
→ 黑启动阶段

S15
→ 并离网切换请求
```

因此绝不能做：

```text
cmd1 + cmd2 + ... + cmd15
```

也不能：

```text
每个cmd直接接一台设备
```

真正需要的是：

```text
策略判断
↓
请求翻译
↓
模式判断
↓
策略仲裁
↓
资源分配
↓
设备执行
↓
真实Plant
↓
重新测量
```

# 3. 为什么实际拆成 Stage00～Stage15

最开始规划比较粗：

```text
00 AUDIT
01 SCAFFOLD
02 BASELINE AGC EQUIVALENCE
03 LOCAL15 CONTROL STACK
04 COMMAND ROUTER
05 AUX SIGNALS
06 TEST HARNESS
```

但实际动模型以后发现：

```text

S6/S8辅助
模式判断
GFM/GFL
Breaker
黑启动
同步
重合闸
```

每个都可能破坏实时模型。

所以最终实际拆成：

| Stage | 最终解决的问题 |
|---|---|
| Stage00 | 模型审计 + 参数在线可调基础 |
| Stage01 | CFG15统一配置面板 |
| Stage02 | AGC目标生成与资源分配解耦 |
| Stage03 | S2/S7 Normalizer + 有功仲裁 |
| Stage04 | 仲裁后AGC → 6 Candidate Pref |
| Stage05 | Execution Mapper + Source Router → `u_commit` |
| Stage06 | Execution Fault Injector → `u_applied` |
| Stage07 | 六设备 Pref 真正接管 |
| Stage08 | SOC执行一致性 + 全P目标/约束统一 |
| Stage09 | S3 AVC → Q Allocator → Qref真实接管 |
| Stage10 | S6平滑 + S8减载真实执行 |
| Stage11 | S5/S14/S15模式判断与执行资格 |
| Stage12 | Droop/GridOn统一模式执行 |
| Stage13 | PCC Breaker + executed mode + 真实离网 |
| Stage14 | 黑启动 Pref 四阶段真实执行 |
| Stage15 | 重同步 + 重合闸 + GFM→GFL返回 |

因此：

> 原架构没有被推翻，只是被拆成了更安全、更容易逐步验证的工程Stage。

# 4. Stage00：先让参数能够在 Load 后在线修改

Stage00 几乎不增加控制块。

主要锁定：

```text
DefaultParameterBehavior = Tunable
ParameterTunabilityLossMsg = error
```

## 4.1 为什么必须 Tunable

后面15策略测试必须频繁在线修改：

```text
策略执行许可
P_OBJECTIVE_MODE
CONTROL_SOURCE
故障设备
故障gain
模式真实接管开关
Breaker真实接管开关
黑启动主机
孤岛主机
...
```

如果每次都要：

```text
改值
→ Build
→ Load
→ Execute
```

15策略完整验收几乎无法推进。

所以最终测试流程冻结成：

```text
Build一次
↓
Load
↓
Variables Table
↓
在线改 Tunable 参数
↓
Execute
↓
Reset
↓
下一工况
```

这就是后面所有正式LOCAL15测试的基础。

## 4.2 `ParameterTunabilityLossMsg = error`

它不是算法。

它的作用是：

```text
本来设计为可调
但代码生成优化后失去可调性
```

时直接报错，而不是悄悄生成一个“看起来能调、Target实际不能调”的模型。

## 5.1 `CFG_AA_*` 和 `CFG15_*` 为什么必须分开

### 原 `CFG_AA_*`

是：

> 策略算法本身的物理参数 / 阈值

例如：

```text
demand_limit
anti_reverse_limit
AVC Q limit
UV threshold
UF threshold
blackstart enable
...
```

### 新 `CFG15_*`

是：

> 整个执行框架的模式、许可、测试和仲裁参数

例如：

```text
S5有没有执行权
S15有没有执行权
当前P主目标是谁
当前听V5A还是LOCAL15
Breaker是否允许真实接管
```

这样不会出现：

```text
同一个策略阈值有两套配置
```

# 6. Stage02：把 AGC 的“想调多少”和“谁来承担”彻底分开

原AGC：

```text
Ptarget
Ppcc
↓
AGC内部：
dP = Ptarget - Ppcc
↓
PV/ESS/EV资源分配
```

也就是说一个AGC同时负责：

```text
1. 生成总调节请求
2. 六资源分配
```

15策略加入后，这个结构不能继续。

因为未来总调节请求可能来自：

```text
S7 联络线
S9 削峰填谷
S10 周期计划
S12 新能源消纳
S13 多目标
```

所以必须变成：

```text
策略/仲裁
↓
统一 dP_request
↓
AGC只负责资源分配
```

## 6.1 新增 `AA15_AGC_INPUT_TAPS`

从正在驱动旧AGC的15根真实输入线上直接分支：

```text
原真实信号
├─→ 原AGC
└─→ AA15_AGC_INPUT_TAPS
```

作用：

> 保证旧AGC和新Shadow AGC吃到完全同源的数据。

这样以后输出不同，才有资格判断是“算法差异”，而不是“输入源不同”。

# 12. Stage06：建立 `u_commit → u_applied`

新增：

```text
AA15_Execution_Fault_Injector
```

必须放：

```text
Command Source Router
↓
u_commit
↓
Execution Fault Injector
↓
u_applied
```

## 12.1 为什么不能放AGC前

如果AGC前就把命令改掉：

```text
控制器自己会知道自己被修改
```

那不叫执行器失配。

真正需要制造：

```text
控制器认为：
u_commit = 0.8

Plant实际：
u_applied = 0.24
```

例如：

```text
fault device = ESS1
gain = 0.3

u_applied = gain × u_commit
```

于是：

```text
u_commit ≠ u_applied
```

这为论文的执行状态失配提供真实模型基础。

---

## 12.2 为什么第一版选择 gain degradation

优点：

```text
简单
连续可调
容易解释
通信可以保持正常
```

例如：

```text
gain=0.8
gain=0.5
gain=0.3
gain=0
```

表示设备实际执行能力逐步退化。

# 14. Stage08-A：修 ESS SOC 执行一致性

Stage07以后发现一个严重风险：

```text
ESS真实Plant Pref
=
AA15_FINAL_APPLIED_ESS*

但SOC更新
仍可能读：
V5A_FINAL_ESS*
```

如果LOCAL15或故障注入导致两者不同：

```text
Plant实际放30 kW
SOC却按80 kW积分
```

这会污染：

```text
SOC
AGC能力
后续状态评估
```

所以SOC支路改成：

```text
AA15_FINAL_APPLIED_ESS1
├→ ESS1 Plant
└→ ESS1 SOC

AA15_FINAL_APPLIED_ESS2
├→ ESS2 Plant
└→ ESS2 SOC
```

但 S05 Legacy Router桥仍继续读：

```text
V5A_FINAL_ESS*
```

# 73. `Goto / From` 到底是什么，为什么我们大量使用

通俗理解：

```text
Goto
=
“给这个信号起一个全局名字并发布”

From
=
“在别的地方按名字把这个信号拿出来”
```

例如：

```text
AA15_FINAL_APPLIED_ESS1
```

在Stack内部：

```text
Goto
```

发布。

设备附近：

```text
From
```

按同一个Tag读取。

优点：

```text
避免顶层跨几千像素拉长线
模块之间更清楚
适合当前SM_Master大模型
```

缺点：

```text
看模型的人如果不知道Tag含义，
会感觉“线突然消失又突然出现”
```

所以学习模型时：

> 看到From/Goto，一定先读 `GotoTag`，不能只看Block显示名称。

# 116. 你自己讲模型时的标准口述模板

建议以后对老师/工程师不要从“我们Stage00做了什么”开始。

先从功能架构讲。

可以按下面顺序说：

---

## 第一段：原问题

> 原模型已经有15种高级应用策略，但 `Advanced_Microgrid_15_Strategies` 主要输出 `status/alarm/metric/cmd`，它们的物理含义不同，没有统一仲裁和真实设备执行链，所以不能直接认为15策略已经闭环。

---

## 第二段：总体解决方法

> 我们保留原15策略作为判断层，在其后增加 Request Normalizer、P Objective/Constraint Manager、Mode Manager、AGC/Q Allocator、Execution Mapper、Source Router、u_commit/u_applied执行层以及GFM/GFL和Breaker执行层。

---

## 第三段：有功

> 有功方面，S7/S9/S10/S12/S13是可选主目标，S1/S4/S11作为硬约束，得到最终 `AA15_P_DPREQ_EFFECTIVE`，再由原有AGC资源分配逻辑分到2PV+2ESS+2EV。

---

## 第四段：辅助有功

> S6和S8不作为新的PCC主目标，而是在基础六路Pref上进行ESS平滑补偿和EV减载，然后经过黑启动Gate形成完整LOCAL15六设备命令。

---

## 第五段：控制源和执行状态

> V5-A、LOCAL15以及未来BOARD15统一进入 Command Source Router。Router输出是 `u_commit`，之后Execution Fault Injector可以制造执行能力退化得到 `u_applied`，最后Active P Takeover把合法最终值送入六设备Pref。

---

## 第六段：无功

> S3单独走Q链，根据当前六设备 `FINAL_APPLIED Pref` 计算剩余视在容量，再分配六路Qref。

---

## 第七段：模式

> S5/S14/S15进入Mode Manager。通信异常和电气孤岛资格被分开，只有V/f电气异常才允许S5形成真实解列请求。

---

## 第八段：GFM和PCC

> S13用100 μs状态边界形成真正executed mode；S12根据executed mode选择ESS1或ESS2为GFM主机；Breaker Router同时决定PCC物理边界。

---

## 第九段：黑启动

> S14在BLACK_START模式下通过Pref Gate实现ESS、PV、EV逐阶段恢复。

---

## 第十段：恢复

> S15在Grid恢复后计算两侧ΔV、Δf和Δθ，对构网ESS的Fref进行微调，连续满足同步条件0.5 s后重合PCC，再保持0.2 s，清除island latch，ESS由GFM返回GFL，最终回到NORMAL。

---
