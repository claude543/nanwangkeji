# 3. 到 S07 为止，我们已经有什么

## 3.1 S03：把原始策略输出变成“有明确语义的请求”

原始15策略只给：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

S03 增加：

```text
AA15_Request_Normalizer
```

先从15维向量里抽出：

```text
S2
S7
```

因为当前原始算法中：

```text
cmd(2) = Ptarget - Ppcc
cmd(7) = Ptarget - Ppcc
```

两者数值本质一致。

然后：

```text
AA15_P_Objective_Arbiter
```

负责避免：

```text
S2 + S7
```

被重复叠加。

S03 的核心结论是：

```text
正常综合运行：
S7拥有执行权
S2作为跟踪/KPI监视

专门测试S2时：
可以只开S2
```

---

## 3.2 S04：把一个 dP 请求分成六台设备的 Pref

S04 建立：

```text
AA15_Arbitrated_Baseline_AGC
```

它不是重新发明一套AGC。

它是在 S02 已经验证等价的基础 AGC 上，把：

```text
原来AGC内部自己算：
Ptarget - Ppcc
```

改成：

```text
外部给我：
dP_request
```

然后仍然按原 AGC 的逻辑在：

```text
2PV + 2ESS + 2EV
```

之间分配有功调节任务。

所以：

```text
策略/仲裁层
决定“系统总共需要调多少”

AGC
决定“六台设备各自承担多少”
```

这两个层次不能混。

```text
AA15_Execution_Mapper
```

```text
0 ~ +1 pu

ESS：
-1 ~ +1 pu
```

## 3.4 S06：区分“提交命令”和“设备实际采用命令”

```text

```

```text

↓
```


这使：


```text

V5A_FINAL_ESS2_TO_SOC
```

S08 没有删掉这两个 SOC 支路。

而是把它们读取的 GotoTag 从：

```text

V5A_FINAL_ESS2
```

改成：

```text
AA15_FINAL_APPLIED_ESS1
AA15_FINAL_APPLIED_ESS2
```

所以现在是：

```text
AA15_FINAL_APPLIED_ESS1
├─→ ESS1真实Pref
└─→ ESS1 SOC积分/更新

AA15_FINAL_APPLIED_ESS2
├─→ ESS2真实Pref
```


# 12. S08必须始终遵守的PCC符号

当前真实模型已经统一：

```text
PCC > 0
= 微网向上级电网出口

PCC < 0
= 微网从上级电网进口
```

所以：

```text
dP > 0
意味着希望PCC往更正方向移动
即：
增加微网净出力 / 减少进口

dP < 0
意味着希望PCC往更负方向移动
即：
减少微网净出力 / 增加吸收/充电
```

这是理解 S1/S4/S11/S12 的基础。

# 13. S1：为什么被翻译成“进口减轻请求”

原策略：

```text
pImport = max(-Pcc,0)

cmd1 =
max(forecastDemand - demandLimit, 0)
```

所以：

```text
cmd1 > 0
```

意味着：

```text
当前进口太多
需要把PCC往正方向拉
```

因此 S08：

```text
s1_import_relief_kw = max(cmd1,0)
```

它不是一个完整的新 Ptarget。

而是一个：

> **至少要产生这么大的正向dP纠偏量。**

---

# 14. S4：为什么是“出口减轻请求”

原策略：

```text
pExport = max(Pcc,0)

reverseOver =
max(pExport - antiReverseLimit - deadband, 0)

cmd4 = reverseOver
```

因此：

```text
cmd4 > 0
```

表示：

```text
出口过多
```

要减少出口，就必须：

```text
PCC往负方向调整
```

所以 S08 记录：

```text
s4_export_relief_kw = max(cmd4,0)
```

然后在约束管理器里把它翻译成：

```text
负向dP约束
```

---

# 15. S9：削峰填谷为什么可以直接作为 signed dP

当前 S9 原始策略：

```text
如果进口 > peak：
cmd9 > 0

如果进口 < valley：
cmd9 < 0
```

因此它本身已经带方向：

```text
峰时：
正dP
→ 减少进口

谷时：
负dP
→ 增加充电/吸收
```

所以：

```text
AA15_NORM_S09_DPREQ_KW = cmd9
```

直接保留。

---

# 16. S10：为什么不能直接把 `cmd10` 当 dP

当前 S10：

```text
cmd10 =
Ptarget + 周期变化项
```

它代表的是：

```text
一个新的PCC目标值
```

而不是：

```text
当前应该再调多少
```

因此必须：

```text
S10 target
-
当前 Pcc
=
S10 dP request
```

即：

```text
objective_dp =
cmd10 - Pcc
```

这是典型的：

```text
目标值
→
控制偏差
```

转换。

---

# 17. S11：为什么和S4同属“出口纠偏”

当前 S11：

```text
cmd11 =
max(pExport - exportAllowance, 0)
```

所以：

```text
cmd11 > 0
```

同样表示：

```text
出口超过允许值
```

因此它和 S4 的物理方向相同：

```text
都要求负dP
```

但语义不同：

```text
S4：
防逆流/硬安全类限制

S11：
自发自用/余电上网政策类限制
```

# 18. S12：为什么正的原始cmd要变成负dP

当前 S12 的 `cmd12` 表示：

# 36. `AA15_Q_Allocator_Router`为什么需要当前六路 `FINAL_APPLIED Pref`

所以无功分配不是：



# 72. 你现在真正应该掌握的几个句子

如果只保留最核心的理解，请记住：

1. **原15策略模块是“判断和建议层”，不是最终设备控制器。**
2. **S03/S08负责把不同有功策略翻译、选择并约束成唯一 `effective_dP`。**
3. **S04 AGC不决定系统目标，它只负责把总dP分给2PV+2ESS+2EV。**
4. **S05决定命令属于哪个设备合法范围，并决定当前听V5A还是LOCAL15。**
5. **S06把 `u_commit` 和 `u_applied` 分开，是论文执行失配的基础。**
6. **S07让最终有功命令真正进入六台设备Mux input6。**
7. **S08让ESS SOC也跟随这个真实最终命令，并把当前已有有功策略集接进统一P链。**
8. **S09把S3 AVC从“只会算cmd3”升级成“能真正输出六路Qref”的闭环。**
9. **S09的Q分配依赖S07的最终Pref，因为P先占用视在容量，剩下的才是Q能力。**
10. **现在每台设备 input6 是P，input7 是Q；P和Q控制目标分开，但在变流器容量上耦合。**
11. **Group28不是控制器，它只是把每个阶段的重要中间量按时间轴统一记录下来。**
12. **以后读模型不要从Goto/From名字开始，而要沿“策略→请求→仲裁→分配→Router→实际执行→Plant”方向看。**
