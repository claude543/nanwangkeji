# 5. S03：为什么首先做S2和S7

S03没有一口气处理15个策略。

原因是当前15个策略的cmd并不是同一种物理量。

例如：

```text
S2 / S7
→ 有功功率偏差 / dP

S3
→ 无功需求

S6
→ 平滑约束

S8
→ 减载请求

S14
→ 黑启动状态/动作

S15
→ 并离网模式动作
```

因此不能：

```text
cmd1 + cmd2 + ... + cmd15
```

当前最适合先整理的是：

```text
S2
S7
```

因为二者当前原始算法中都对应：

```text
Ptarget - Ppcc
```

也就是说它们目前具有相同的有功请求语义。

但这也带来一个关键问题：

> 如果S2和S7同时开启，绝不能把同一个dP叠加两次。

所以S03首先解决：

```text
同类请求识别
+
职责分离
+
仲裁
```

# 9. 为什么要有Request Normalizer

原15策略输出是：

```text
status[15]
alarm[15]
metric[15]
cmd[15]
```

它们的问题是：

```text
只有“第几个元素”
没有明确执行语义
```

例如：

```text
cmd15(2)
```

只看位置很难知道：

```text
这是S2
它代表kW还是pu？
它是Ptarget还是dP？
它能不能直接进入AGC？
```

因此总体设计中必须有：

```text
Request Normalizer
```

它的职责不是“做最终仲裁”，而是：

> 把原策略层的匿名向量输出转换为有明确名称、有明确物理意义、以后可以被仲裁器使用的请求接口。

S03第一版先只规范化S2和S7。

# 15. 为什么必须要Arbiter

因为“策略提出请求”和“系统真正执行哪个请求”是两件不同的事。

例如：

```text
S2说：需要dP
S7也说：需要dP
```

不能：

```text
两个都执行
两个都加
```

所以必须有一个统一层回答：

```text
现在是哪种P Objective Mode？
哪些策略有执行许可？
谁是主目标？
谁只监测？
请求是否有效？
是否发生重复请求保护？
```

这就是Arbiter。
