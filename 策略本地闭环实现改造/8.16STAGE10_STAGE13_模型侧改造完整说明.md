# 4. S10：为什么把 S6/S8 放在 Execution Mapper 与 Source Router 之间

最终位置：

```text

        ↓

        ↓
S10 P Auxiliary Executor
        ↓

        ↓
u_commit
        ↓
S06 Execution Fault Injector
        ↓
u_applied
        ↓
```

为什么必须放这里？

## 4.1 不能放在 AGC 前面

因为 S6/S8 不是新的 PCC 主目标。

```text

“发生低压/低频，需要释放50 kW可控负荷”
```

它们层级不同。

所以不能写成：

```text

→ 再一起当PCC目标
```

```text

```

# 8. S6原算法到底算了什么

原 `Advanced_Strategy_Core` 中 S6 核心是：

```text
pvAvail = max(PV1,0) + max(PV2,0)

pvRatePctPerMin
=
100 × |pvAvail - pv_prev|
/ pRated
× 60 / dt
```

然后：

```text
metric(6) = pvRatePctPerMin

alarm(6)
=
pvRatePctPerMin > pft

cmd(6)
=
max(pvRatePctPerMin - srl, 0)

status(6)
=
cmd(6) > 0
```

其中：

```text
srl = smooth_rate_limit_pct_per_min
pft = pv_fluct_trigger_pct
```

一个容易混淆的点：

```text
pft
影响 alarm(6)

srl
直接进入 cmd(6)
```

所以真正决定 S10 是否需要平滑的核心是：

```text
cmd(6)
以及
srl
```

而不是 `pft` 单独决定执行。

# 9. S10 的 S6 Executor：为什么“PV升→ESS充，PV降→ESS放”

S10 不把 `cmd(6)` 当成有功 kW 命令直接接 ESS。

因为原 `cmd(6)` 只是：

```text
“爬坡率超限幅度”
```

没有正负方向。

所以 S10 自己维护一个：

```text
smooth_ref
```

它代表：

> 按允许爬坡率运行时，光伏总可用出力“应该走到哪里”。

每个时步允许变化：

```text
allowed
=
srl / 100
× (2 × P_unit)
× dt / 60
```

然后：

```text
residual = pv_now - smooth_ref
```

并把 `smooth_ref` 每次只移动 `allowed` 那么多。

因此：

```text
Pess_smooth
=
smooth_ref - pv_now
```

再除以 `P_unit` 变成 pu。

---

## 9.1 PV突然上升

例如：

```text
原来：
PV总可用 = 130 kW

突然：
PV总可用 = 190 kW
```

由于 `smooth_ref` 不能瞬间从130跳到190：

```text
smooth_ref < pv_now
```

所以：

```text
smooth_ref - pv_now < 0
```

得到：

```text
S6 compensation < 0
```

当前 ESS 约定：

```text
ESS Pref > 0 = 放电
ESS Pref < 0 = 充电
```

所以负补偿表示：

```text
PV突然上升
↓
ESS增加充电
↓
吸收多出来的变化
```

---

## 9.2 PV突然下降

反过来：

```text
pv_now突然变小
smooth_ref还没来得及下降
```

所以：

```text
smooth_ref - pv_now > 0
```

得到：

```text
ESS正补偿
= 放电
```

即：

```text
PV突然下降
↓
ESS放电补上
```

这就是平滑的物理含义。

# 10. S6为什么不是两台ESS平均分，而是按方向余量分

S10 先读取 S05 已经给出的：

```text
ESS1 base Pref
ESS2 base Pref
```

例如需要增加放电时：

```text
room1 = 1 - ESS1当前Pref
room2 = 1 - ESS2当前Pref
```

需要增加充电时：

```text
room1 = ESS1当前Pref + 1
room2 = ESS2当前Pref + 1
```

然后按余量比例分：

```text
ESS1承担
=
总请求 × room1 / (room1+room2)

ESS2承担
=
总请求 × room2 / (room1+room2)
```

这样不会出现：

```text
ESS1已经接近极限
ESS2还有很多余量
却仍然强制五五分
```

如果总余量不足：

```text
s6_unserved_pu
```

会记录未执行部分。

# 12. 为什么 S8 不去切 Load1/Load2，而是削 EV

当前平台已经有：

```text

```

而 EV 本身就是可控充电负荷。

S10 选择：

```text

→ EV1其次
```

而不是额外改固定负荷拓扑。

当前 EV 约定：

```text

-1.0 pu
= 100 kW充电

0
= 不充电
```

所以“减载”不是：

```text
让EV更负
```

而是：

```text
让EV Pref向0移动
```

例如 EV2 当前：

```text
-1.0 pu
= 100 kW充电
```

需要减50 kW：

```text
-1.0
→
-0.5
```

于是释放50 kW负荷。

如果 EV2 不够，再交给 EV1。

# 78. 为什么 S10用 persistent 可以，而 S13最后必须显式 Unit Delay

S10内部：

```text

persistent smooth_ref
```

用于保存平滑参考。

S10没有形成：

```text
当前输出
→ 下游
→ 立即反馈当前输入
```

所以它可以合法保存内部状态。

而 S13 V2：

```text

→ S12
→ S12输出
→ S13
```

形成代数环。

这时 MATLAB Function 再更新 persistent 就不合法。

因此不是：

```text
“项目以后禁止persistent”
```

而是：

> **状态能否放在 MATLAB Function 里，要看它是否处在直接反馈环中；对系统级模式状态，显式 Unit Delay 更清晰、更安全、更容易验证。**
