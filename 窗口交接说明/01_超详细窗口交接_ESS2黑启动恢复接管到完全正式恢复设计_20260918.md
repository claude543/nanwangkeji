# 5. Q外环为什么后来没有继续做“Qref=0正式试验”

这是本窗口一个很重要的路线修正，新窗口不能又按早期计划把Q PI重新拉进来。

## 5.1 在线Q Loop开关本身没有失效


```text

=

```

所以开关确实有效。

问题在于Q参考来源。

## 5.2 当前Stage2～4故意让旧Q PI几乎没有误差

当前无功误差采用现有符号约定：

```text

```

V4.7阶段逻辑：

```text
Stage0/1：legacy Qref
Stage2/3/4：QrefEff ≈ Qmeas
Stage5：约0.5 s从Qmeas平滑恢复到legacy Qref
```

因此Stage2/3/4：

```text

```

这不是bug，而是历史孤岛工程设计：防止强网时期旧Q PI在弱孤岛里突然抢无功/电压控制权。

## 5.3 当前正式岛内Q/V职责

当前更合理的孤岛设计是：

```text

+
V4.8 q-bias（中央慢速电压/无功恢复）
```

而不是Stage2～4重新让旧Q PI追一个固定Qref。

因此本窗口最终决定：

> **不为了“形式上P+Q都验收”而强行恢复一个最终孤岛阶段本来就不使用的旧Q PI。**

Qref=0 override（零无功参考覆盖）可以保留为未来诊断工具，但不是当前黑启动正式恢复的必做环节。

# 6. 从小功率到正式接管：为什么需要R2.2健康恢复与handover设计

```text

+

```

然后：


核心思想：

```text
handover（交权）只换“谁给命令”
不能同时改变“命令是多少”
```

这就是无扰接管（bumpless transfer，无扰切换）的关键。

# 7. R2.2改模：精确位置、为什么原来不够、改后解决什么

本轮正式健康恢复/接管改模主干只落在几个已有核心，不是继续无脑叠MATLAB Function（MATLAB函数）块。

## 7.1 Restore Executor（储能2恢复执行器）

准确路径：

```text
K26_K50_CLEAN_P1
/SS_Slave2
/AA15_ESS2_RESTORE_EXECUTOR
/CORE
```

### 修改前问题

诊断模式更偏固定时间观察；状态6/7语义无法直接承担正式“首任务合格→保持资格事实→当前健康另行报告”。

另外第一版R2里 `releaseAllowed`（当前继续推进许可）前面算完以后，函数尾部又按状态统一赋值，导致健康许可被覆盖为1。

### 修改后

- 首任务资格基于 `prefApplied`（本地实际收到的外部有功命令）而不是只看内部 `prefEff`；
- ±500 W目标的功率误差候选从±25 W改成±50 W，即0.0005 pu；
- 首次资格仍需约3 s连续满足；
- `state7` 表示“首次资格曾经成立”；
- `releaseAllowed` 表示“此刻是否允许继续推进”；
- state7以后普通小偏差只使当前许可变0，不把state7退回6；
- 严重欠压/过流/非有限等既有硬路径保留。

这样把：

```text
完成历史
```

和：

```text
当前是否健康
```

分开，避免短时波动导致整个恢复过程从头反复。

# 8. R2/R2.1工具错误：这部分是脚本工程教训，不是模型问题

## 8.1 R2错误：整模型SHA/bytes硬门

最初 `PATCH_E2_HEALTH_HANDOVER_R2` 把审计时整个SLX字节/SHA当成准入条件。

用户的模型会滚动修改，文件变了并不代表选错模型。因此出现：

```text
Original-model bytes differ from audited source. No write performed.
```

### 正确修正

R2.1开始：

- 不比较整个SLX SHA；
- 不比较整个文件字节/时间戳/大小；
- 只检查本Patch真正要修改的目标核心是否仍属于可安全升级的语义版本；
- whole-model SHA只做provenance（出处记录），不做hard gate（硬阻断）。

这是以后所有滚动开发Patch的永久规则。

## 8.2 R2.1错误：辅助函数依赖引用错误

`SELFTEST_E2_HEALTH_HANDOVER_R2_1.m` 调用了：

```text
e2hh_bundlecheck_R2
```

而包里实际是：

```text
e2hh_bundlecheck_R2_1
```

用户执行时MATLAB又提示辅助文件存在于另一路径，说明包并没有做到自包含。

### R2.2正确修复

- Patch/Selftest/Verify三个入口先用自身 `mfilename('fullpath')` 确定包根目录；
- 临时 `addpath` 包根，退出恢复原path；

# 14. q-bias（q轴偏置）当初为什么加、现在怎么复用

V4.8 q-bias不是为了“再叠一个Q控制器”。

旧Voltage Secondary（电压二次恢复）路径：

```text
PCC电压误差
→ dVSecondary
→ 五台VsupportRef
→ slow-q
```

历史数据出现：

```text
dVSecondary已经到限制
但母线电压仍明显偏高
```

说明旧“改VsupportRef再经过slow-q”的执行权限不足以建立所需稳态Q工作点。

V4.8改为：

```text
PCC慢速电压误差
→ central q-bias（中央q轴偏置）
→ transport/router（传输/路由）
→ 各GFL本地Finalizer（最终执行器）
→ 直接形成可长期保持的q轴偏置
```

它已有：

```text
qsec request
current-circle capability（电流圆能力）
modulation derating（调制降额）
CapPos/CapNeg
IqSecApplied
QsecClip
```

所以黑启动不需要重造Q慢控制器；需要适配入口。

## 14.1 黑启动必须适配的q-bias内容

计划孤岛原来可捕获切岛前PCC电压作为Vtarget；黑启动没有正常“切岛前母线”。因此：

```text
Vtarget_BS ≈ ESS1正式建网目标 ≈ 1.0 pu
```

不能把“捕获失败fallback=1.0”当正式黑启动设计。

还要：

```text
S14-70：Frequency Secondary ON，q-bias OFF
S14-75：Frequency Secondary继续，q-bias从0平滑ON
```

因为当前审计证明Frequency Secondary和q-bias都曾依赖同一个Coordinator Stage3语义，如果直接粗暴Stage2→3，会一次打开两层慢控制，因果不清。

# 15. ESS1主、ESS2辅助：正常功率责任到底应该怎么迁移

最终关系不是：


所以S14-80需要的是：


```text
死区
迟滞

```

避免ESS2追随ESS1每一点纹波。

# 16. P/Q联合能力：为什么不能只扩大P authority

进入S14-75后，ESS2可能已经承担q-bias，所以d轴P和q轴Q共享：

```text
电流容量
kVA容量
调制度
```

至少必须满足类似：

```text
Id^2 + Iq^2 <= Imax^2
```

因此S14-80的“正常放开”不是：

```text
0.001 → 0.02 → 1.0
```

而是：

```text
ESS2正常P允许范围
=
ESS2自身P能力
∩ ESS1当前可释放能力
∩ P/Q共享电流能力
∩ 调制余量
∩ V/f健康许可
```

这也是最终把q-bias安排在正常责任释放之前的原因。

日期：2026年9月17日。

**本次改动既包含上一版准备的健康恢复和接管功能，也包含这一轮50瓦容差、普通波动继续观察及接口修正。下面从未改模的原模型讲到本版最终状态，不要求先应用第一版。**

## 0．先记住这次要达到什么

首轮过程仍然是：


**功率目标不变，接管前后不扩大功率。**有功比例增益0.06、积分增益0.5；旧无功功率外环、直接电流诊断支路、四路附加支撑、一次和二次修正在首轮不投入。

本轮把允许的实测功率偏差从±25瓦改成±50瓦。以吸收功率描述，就是在其他条件满足时，450—550瓦可作为首个约500瓦任务的候选合格区间。50瓦是本轮工程候选，不是规范指标，也不是稳定性证明。

## 1．你的“尽量先跑起来、从数据分析”原则怎样进入代码

不是取消全部判断，也不是每出现一点波动就结束。现在明确分成三种情况。

| 情况 | 新版实际做法 | 不会做什么 |
|---|---|---|
| 尚未首次合格 | 保持当前已允许的任务，持续记录；连续合格计时可重新开始 | 不因时间到了而假装合格，不为了60秒目标强行接管 |
| 已合格以后出现普通偏差，未越过既有严重边界 | 保留曾经完成的状态；降低“当前继续推进许可”；混合暂停或新任务暂停，继续记录 | 不因一拍偏差就把状态7退回6，不自动切回旧命令或复位 |
| 严重电气边界、已有故障码、非法命令或非有限数据 | 保留既有故障处理和保护上下文；后续运行脚本按明确故障规则停止或取证 | 不把严重故障隐藏成普通告警，不伪造真实电流反馈 |

### 1.1 尚未合格不等于试验失败

例如功率持续在目标附近波动，但尚未满足连续合格时间：模型停留在当前环节继续采集。如果60秒内没有形成资格，结果应是“未完成资格／未完成接管，但已有波形可分析”，不是稳定通过，也不要求自动重跑。

### 1.2 普通偏差不等于取消此前完成事实

例如已经在450—550瓦范围内完成首个资格，后来短时变成吸收440瓦：如果没有触发严重电气条件，本地状态保留7，但当前继续推进许可为0。这样既没有隐瞒偏差，也不会反复重新启动接管。

### 1.3 保护没有取消

原代码在功率恢复状态6、7中将超过既有严重电压区间、超过既有严重电流上限、限流标志触发等列入严重路径；诊断总分支还检查明显异常频率。本版保留这些判断及原异常分闸配置的作用。

因此，“普通波动继续观察”有明确边界，不是任何幅值的振荡都允许无限运行。本文不新增也不放宽这些电气阈值，具体数值仍以实际配置回读为准。

## 4．恢复执行器具体改了什么

### 4.1 先区分两项输入

`prefApplied`（本地实际收到的外部有功命令）来自本地诊断向量第24项；`prefEff`（内部处理后的有效参考）来自第26项。

举例：上层任务500瓦，内部暂时只允许100瓦，设备确实做到100瓦，并不表示500瓦任务已完成。所以首任务资格检查真实到达本地的命令与首个目标，然后检查实测值，不只看内部参考。

### 4.2 50瓦放在真正生效的代码里

原有参数 `CFG_ESS2_RESTORE_PICKUP_PERR_MAX_PU`（储能2功率恢复误差上限）本版保存默认0.0005。健康恢复分支同时把最大候选容差从0.00025改为0.0005。

```text
0.0005 × 100000瓦 = 50瓦
```

命令是否到达的容差不改，它与实测功率精度不是同一个量。有功比例积分器本体不因放宽资格而重新调参，没有另加功率滤波器。

### 4.3 首次资格仍需连续满足

本地状态6表示电流执行已放行，正在运行与观察。任务到位、误差、方向、电压、频率、电流、限幅和执行许可满足后，才累计首次资格时间。条件不满足就清除该次连续计时，但保持当前已允许的任务继续采集。

原有约3秒持续时间保留；它是推进资格，不是“证明所有慢振荡不存在”的结论。当前直接比较已有实测信号，不假装新增了平均窗口或振荡辨识算法。

### 4.4 状态7和当前许可分开

本地状态7现在明确表示“首次资格已经达到过”。它不代表以后每一拍都健康。

- 首次资格事实：状态7保留。
- 当前能不能继续混合或增加任务：看恢复输出第6项 `releaseAllowed`（当前继续推进许可）。

固定任务模式2、3下，普通误差越界会让当前许可变0，但不将状态7退回6、不将电流执行系数清零。这个输出必须结合本地状态解释：状态6执行非零任务时，它不独立代表首任务已合格；上层接管仍同时要求本地状态7和当前许可。未来模式4、5已经允许改变任务，因此当前许可看运行健康，不永久要求回到第一次500瓦目标。

### 4.5 修正被最后一次赋值覆盖的问题

第一版在分支中算出 `releaseAllowed`（当前继续推进许可），但函数结尾按状态6／7统一赋值为1，把前面的计算覆盖了。

本版把健康许可的最终赋值放在结束映射之后。电流放行与“下一步允许”不再混淆：可以继续执行当前命令、保留真实反馈，同时不允许扩大下一步动作。

### 4.6 没改哪些量

恢复器输入仍6个，输出仍3个；状态向量仍5项，主要执行输出仍12项，追踪向量仍9项。没有扩宽原主从任务中的恢复向量，没有修改真实断路器电气线或电流控制器。

## 5．策略14具体改了什么

### 5.1 编号的含义

| 所属程序 | 编号 | 含义 |
|---|---:|---|
| 储能2本地执行器 | 6 | 当前电流执行已放行，等待首任务资格或观察 |
| 储能2本地执行器 | 7 | 首任务资格曾成立，继续报告当前健康 |

| 策略14 | 50 | 匹配、平滑交权、接管后保持 |
| 策略14 | 60 | 后续受限任务或一次调节测试，本轮默认不到这里 |
| 策略14 | 90 | 明确故障／结构失败上下文，不是普通功率偏差 |

没有新增步骤70，也没有把“本地7”和“上层50”拼成一套连续数字。

### 5.2 健康计时与总诊断位不再绑死

原模式1保留原来的固定时间诊断。新模式2—5真正使用健康推进，但仍维持本地跟网阶段2和四路支撑隔离，不能一切换到健康模式就连同支撑、无功方式一起改变。

### 5.3 普通等待超过参考时间，不再直接进90

在新模式下，建压健康等待、接入资格等待、零任务等待、小功率资格等待、接管匹配等待的普通超时改为记录告警。没有合格就不推进，但也不因普通等待把真实任务撤销或丢失后半段数据。

原模式0、1的历史行为保留。系统严重故障、恢复器报告故障、错误主设备、非法混合输入等仍走原有明确失败路径。

60秒由配套的新运行脚本负责正常结束采集，本次改模不新增停止仿真块。60秒结束未完成接管，就是该轮证据中的一个结果。

### 5.4 接管中普通波动，怎么暂停而不是退回

本版继续使用原 `BetaRateLimiter`（命令混合比例变化率限制器）。正常条件满足时，目标混合比例为1；普通条件暂不满足时，目标取当前混合比例的已有回授值。

```text
两路任务一致、当前许可有效 → 继续向协调器交权
普通许可暂时无效 → 保持当前混合比例
许可恢复 → 从当前比例继续
```

存在原来的一拍反馈延时，不能把它描述为理想零延时冻结。这里没有增加一套新的混合算法。原变化率限制模块在输入等于上次输出时保持该值；具体模块定义见文末官方资料。

混合中两路数字命令突然不一致，或命令出现非有限值，是命令约定被破坏，不属于实测功率的普通波动。此类情况仍进入明确故障上下文。

### 5.5 接管完成后不自动启动新任务

模式3混合比例达到1以后，继续停在步骤50，要求仍为500瓦，修正为零。当前健康随后有小波动，只记录并暂停后续推进，不自动退回旧来源。

模式4、5仍需独立后保持条件才到步骤60。条件未合格就观察，不为了在60秒内跑完全部阶段而省略。

## 6．正常协调器具体改了什么

### 6.1 接管基准是实际施加的命令，不是逐拍测量

## 10．本包为什么能避免第一版反复叠加

主脚本识别三种明确情况：

- 原审计模型：一次应用完整第二版，不先应用第一版。
- 已识别的完整第一版布线：定点升级，不重复添加已存在的延时、常数和记录字段。
- 已是第二版：只读验证，不重复改模。

未识别源码、第一版中途失败后被手工保存的混合状态、缺失关键端口都停止写入，不能以“尽量运行”为理由猜着改源模型。这与运行中普通波动继续采集完全不是一回事。

第一版因未声明的健康输出，原包可能在副本阶段阻断。若出现这种情况，正式文件原则上未被原补丁写回；不要为了升级先重跑第一版。
