# 2. 8月7日：SC / OpComm时间问题彻底收口，并冻结正式数据记录方法

## 2.1 发现的问题

- 很容易误以为AGC本身有几十秒异常延迟。

---

## 2.2 排查过程

先后检查和尝试：

1. SC各OpComm Acquisition Group；
2. 插值开关；
3. Synchronization；
4. Probe Control；
5. Samples per signal；
6. Missed data；
7. SC采样周期；
8. 模型Execution mode；
9. 增加统一 `AGC_CORE_MUX23`；
10. 关键量统一进SC Group9；
11. 同时记录 `SM Clock`。

最终看到：

```text
SC time继续前进
但SM Clock大量重复
Missed data很高
```

这说明：

> **SC并没有让Target停止，而是在重复旧Target快照/漏掉部分Target帧。**

---

## 2.3 最终结论

以后必须固定：

```text
SC = 在线观察
Target MAT = 正式证据
```

不能：

- 用SC时间直接代表Target真实事件时间；
- 用不同Acquisition Group之间的SC时间差做精确延迟结论；
- 因SC重复帧反过来怀疑100 μs实时模型。

## 6.2 问题二：Round输出“数值是整数”但数据类型仍是double


根本原因：




加入：

```text
Data Type Conversion
```

职责彻底分开：

```text
Gain
= 单位比例和符号

Round
= 量化成最近整数count

Data Type Conversion
= double整数值 → 真正int16/uint16
```

## 17.1 Klaes 2023：HOLD碰撞比预想更强

Klaes不仅有普通的：

```text
data loss
→ previous control value hold
```

它的FB1还做了：

```text
DER收不到新控制数据
→ DER读取自己的当前实际P_DER
→ 把这个当前真实功率作为新的本地设定值
→ 保持当前运行点
```

因此以下必须：

```text
DROP_AS_NOVELTY
```

- 通信中断时HOLD；
- 保持上一命令；
- 使用当前DER实际功率进行本地HOLD。

```text
→ 新数据恢复
→ unfreeze
```

因此：

```text

= DROP_AS_NOVELTY
```

可以借用，但只能作为已有机制/baseline。

## 17.3 “现有研究没考虑recovery”已经不能这样写

Klaes存在：

```text
freeze
→ communication available
→ unfreeze
```

Chaves存在：

```text
communication failure
→ primary autonomous mode
→ PCC power-flow control lost
```

通信条件恢复后也能重新获得稳定。

所以不能再写：

> “现有研究只研究故障期间，没有考虑通信恢复。”

更准确的是：

> **已有resume/re-enable/recovery，但尚需判断是否有显式controller/resource-state reconstruction。**

## 17.4 Chaves 2025：逐DER实际功率和可用能力反馈也已经被直接做过

```text
实际P/Q
Pmax/Pmin/Qmax等可用能力

CC：
重新计算α/β

CC → DER：
协调系数
```

因此：

```text
逐DER实测功率反馈参与PCC协调
DER可用能力参与集中分配
```

也必须：

```text
DROP_AS_NOVELTY
```

这一点极其重要。

# 18. 当前真正还能保留的论文核心

全文复核后，最核心的剩余问题不是：

```text
HOLD
PI freeze
Pmeas反馈
通信恢复
```

而是：

> **通信异常造成中央控制器所认知的“已执行控制状态”与各DER真实执行状态发生分叉后，通信恢复时显式识别这种失配，并利用恢复得到的逐DER实际执行信息重构中央控制器/资源分配器内部状态，再受控恢复PCC有功协调。**

压缩为：

```text
execution-state mismatch
→ explicit reconstruction
→ controlled re-entry
```

---

## 18.1 “重构”必须比fresh measurement → recompute更强

如果最终方法只是：

```text
通信恢复
→ 重新读六台DER当前功率
→ 根据PCC误差重新计算下一条命令
```

创新风险仍然很大。

因为Chaves正常控制周期本来就是：

```text
收实际DER状态
→ 计算集中分配
→ 下发
→ 再收实际状态
```

所以真正的reconstruction必须明确：

1. 哪个controller-side state在断线后失真；
2. 为什么失真；
3. 哪个device-side state是恢复后的权威现实；
4. 如何从物理现实更新/重新初始化controller-side state；
5. 重构后如何避免第一拍突跳；
6. 如何渐进/受控重新接管。

---

## 18.2 当前最重要的状态关系

未来必须明确区分：

```text
u_raw / u_calc
中央算法算出的原始命令

u_sent / u_commit
中央侧确认成功发布的命令

u_applied
DER实际接受并采用的命令

Pmeas
DER真实物理功率
```

真正有价值的失配：

```text
u_controller-believed != u_applied
```

而不只是：

```text
PCC != Ptarget
```
