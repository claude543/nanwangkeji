# 8.17 后续板端设计规划

对，这样更现实，也更符合我们之前 V4 的合作方式。

**不必强求工程师现在把完整源码、编译环境全部交给我们。** 后面等我们自己的改进算法 C 代码真正冻结后，再把新的 `.c/.h` 文件交给工程师，让他按已经预留好的接口接进去即可。

因此我们现在真正需要做的，是：

> **把这最后一版项目程序的"骨架"一次设计正确，使未来增加新的控制算法时，只是增加/替换算法模块，不需要重新推翻通信、状态机、点表、日志、候选提交和RT-LAB接口。**

这比"现在拿到全部源码"更重要。

---

## 一、现在要预留的核心不是"四套特殊模式"，而是一个统一算法插槽

工程师现在看到的程序可以非常纯粹：

```text
Modbus通信
↓
数据解码
↓
安全状态机
↓
固定本周期 Input Snapshot（输入快照）
↓
Controller Adapter（控制算法适配层）
↓
当前项目15策略算法
↓
Candidate Output（候选输出）
↓
编码
↓
FC16
↓
成功后 Commit（正式提交）
```

其中关键是增加一个很普通的：

```text
Controller Adapter
（控制算法适配层）
```

现在它只接：

```text
project15_core
```

以后我们把新的C代码交给工程师，他只需要：

```text
新增 new_controller.c/.h
↓
在 Controller Adapter 里增加一种选择
```

而不需要重新碰整个主程序。

---

## 二、算法接口现在一定要一次冻结好

建议不管以后装进去什么算法，主程序都只认这几个动作：

```c
controller_reset(...)
controller_init(...)
controller_step(...)
```

并且统一使用四种结构：

```text
ControllerInput
（动态输入）

ControllerConfig
（参数）

ControllerState
（持续状态）

ControllerOutput
（输出）
```

现在：

```text
controller_step()
↓
调用 project15_core
```

以后：

```text
controller_step()
↓
调用我们后续提供的新控制算法
```

主程序不需要知道算法内部发生了什么。

**这就是最重要的预留。**

---

## 三、candidate / commit 必须对"整个控制器"通用，而不是只绑死当前AGC

V4现在的逻辑非常值得继续保留：

```text
正式状态
↓复制
candidate_state
↓
算法计算
↓
candidate_output
↓
编码
↓
FC16成功
↓
正式commit
```

未来应该从：

```text
AgcState
```

升级为泛化的：

```text
ControllerState
```

这样无论里面运行的是：

```text
当前15策略
```

还是以后我们自己设计的新算法，都天然拥有：

```text
候选状态
→ 成功通信
→ 正式提交
```

这一整套机制。

这对我们后续非常重要，因为我们现在的研究方向本身就严格区分 `u_calc（候选命令）` 和 `u_commit（正式提交命令）`。当前蓝图也已经明确，FC16成功只能定义"正式提交"，不能直接等同于设备已经物理执行。

---

## 四、输入数据现在必须准备"够"，以后算法升级不能再因为缺测量改主程序

这一点我要特别重视。

现在工程程序每个周期形成的统一 `ControllerInput`，应该把**已经存在且以后可能有用的真实测量全部提供进去**，而不是只把"当前15策略恰好使用的几个输入"塞进去。

至少包括：

```text
PCC：
P
Q
V
f

资源：
PV1/PV2 Pmax
ESS1/ESS2 SOC

六设备：
PV1 Pmeas
PV2 Pmeas
ESS1 Pmeas
ESS2 Pmeas
EV1 Pmeas
EV2 Pmeas

通信/系统：
MODEL_STATUS
RTLAB_HEARTBEAT
通信状态
测量有效状态
当前时间
CMD_SEQ / 最近提交状态
```

V4本来就已经要求40109～40114六路设备实测功率即使基础AGC不用，也必须继续读取、解码和记录。

这说明我们以前已经有这个意识。

未来算法只需要：

```text
ControllerInput
```

就能获得全部状态。

不需要再告诉工程师：

> "现在麻烦再给新算法多接六个测量量。"

---

## 五、输出接口也要一次做到完整，不能只为当前六路Pref设计

这次 BOARD15 项目本身就要求完整15策略，所以输出接口必须已经覆盖：

```text
6 × Pref
6 × Qref

6 × GridOn
6 × Droop

PCC Breaker

ESS相关 Fref / Fref trim

Mode
Selected Master

控制有效状态
```

这样以后新的控制算法如果需要改变：

```text
有功
无功
模式
断路器
频率参考
```

都已经有现成的出口。

不需要再次扩通信程序。

这也是为什么最终 BOARD15 点表必须比现在 V5-A 的六路 Pref 接管更完整。V5-A目前已经把六路板端命令真正接入设备Pref，并建立了 `EXTERNAL_COMMAND_VALID + LAST_APPLIED` 的安全接管逻辑；最终版本应继承并扩展，而不是另起炉灶。

---

## 六、模式选择现在给工程师怎么写最合适

这里我建议比前面更克制。

**不要现在要求工程师实现5种具体算法模式。**

现在正式项目只需要：

```text
algorithm_mode = PROJECT15
```

但程序结构要求：

> `algorithm_mode` 必须作为可配置的软件模式字段保留，算法调用通过统一 Adapter（适配层）完成，不得把 `project15_core` 直接散落硬编码在主循环中，以便后续增加其它控制算法实现时无需修改通信、状态机、寄存器编码和主循环结构。

可以预留例如：

```text
0 = PROJECT15
1~N = RESERVED
```

或者工程师程序内部用：

```text
algorithm_mode
```

字符串/枚举。

这样他看到的只是非常普通的：

> **"后续算法扩展能力"。**

没有任何其它含义。

以后我们把新的C算法交给他，再把：

```text
RESERVED 1
```

正式接成新的 Controller。

---

## 七、运行参数和配置机制现在也必须做成通用的

以后我们希望尽量：

```text
不改C程序
```

就能改变实验条件。

所以最终项目程序最好有两层：

```text
JSON
= 启动默认参数
```

例如：

```text
IP
Port
周期
默认算法模式
默认策略配置
日志
```

以及：

```text
Runtime Config
（运行时配置）
```

从RT-LAB动态送过去：

```text
strategy_enable_mask
P_objective_mode
目标值
阈值
限值
恢复请求
设备主机选择
……
```

并使用：

```text
CONFIG_SEQ
```

保证整批参数原子更新。

这样以后无论当前项目15策略，还是我们将来增加新的控制算法，测试时都可以继续通过：

```text
RT-LAB
→ 配置寄存器
→ BOARD
```

在线修改。

---

## 八、现在要预留一小块"通用扩展参数区"

这一点我建议加入最终点表。

不要把每一个未来参数都猜出来。

而是专门预留：

```text
EXT_CONFIG_xx
```

例如固定一段连续寄存器：

```text
若干个 UINT16 / INT16 配置字
```

再配：

```text
EXT_CONFIG_SEQ
EXT_CONFIG_APPLY
```

现在：

```text
默认不用
= 0
```

以后我们自己的新算法需要：

```text
某个阈值
某个时间常数
某个模式开关
```

就可以定义这些预留寄存器的含义。

这样如果只是增加几个算法参数：

> **甚至可能不需要工程师再扩 Modbus 点表，只需要让新算法读取已经预留的配置槽。**

具体预留多少，我们后面做最终点表时再算，不应该现在随口定32还是64。

---

## 九、同样建议预留少量"扩展诊断输出区"

原因也是以后少改工程主程序。

当前正常项目日志照常记录。

另外预留：

```text
EXT_DIAG_01
EXT_DIAG_02
...
```

以后新算法可以把：

```text
内部状态
误差
可信度
能力
恢复状态
```

映射进去。

工程程序不需要知道这些诊断量是什么，只负责：

```text
读取ControllerOutput中的扩展诊断数组
↓
写CSV / 寄存器
```

这样未来我们把新C模块交给工程师时，他只需要接算法文件和定义映射，不需要重新设计整个日志系统。

---

## 十、日志框架现在就要支持"算法扩展诊断"，但不用告诉工程师为什么

可以要求每轮CSV至少分成：

```text
Common Diagnostics
（公共诊断）

Controller Diagnostics
（算法诊断）
```

公共部分固定：

```text
time
communication state
FC03 result
measurements
candidate output
committed output
FC16 result
CMD_SEQ
heartbeat
```

扩展部分由：

```text
ControllerOutput.diag[]
```

提供。

当前 PROJECT15 用自己的诊断。

以后新算法换自己的诊断。

主程序日志框架完全不改。

---

## 十一、这样以后我们再次找工程师时，工作量会很小

理想情况应该是：

```text
我们：
给他新的
new_controller.c
new_controller.h

并说明：
algorithm_mode = 1
接口完全遵守原Controller API
扩展参数0~N分别是什么意思
扩展诊断0~M分别是什么意思
```

工程师只需要：

```text
把新文件加入工程
↓
Adapter增加一个case
↓
重新编译
```

而不是：

```text
重新设计Modbus
重新设计状态机
重新设计心跳
重新设计candidate/commit
重新设计日志
重新设计RT-LAB接口
```

这就是我们现在真正需要提前规划好的东西。

---

## 十二、因此我修正前面的"源码交付"要求

不把：

> "必须交付完整源码和我们能自己编译"

作为当前硬要求。

更现实的要求变成：

> **程序必须采用明确的模块化算法接口和可扩展算法适配结构；当前15策略算法由我方提供并通过统一接口调用，通信、安全状态机、候选提交、配置和日志不得与具体算法内部实现强耦合，以便后续增加其它控制算法模块时只需增加算法文件和相应适配，不需要重新设计整个主程序。**

这个是完全合理的项目软件设计要求，也不会暴露任何其它意图。

---

## 十三、现在我们的内部设计重点就更加清楚了

下一步我们要冻结的其实是这6件东西：

```text
① ControllerInput
当前和未来算法都够用的完整输入

② ControllerOutput
P/Q/Mode/Breaker/Fref全部覆盖

③ ControllerState
支持整个算法candidate / commit

④ ControllerConfig
项目配置 + 通用扩展参数区

⑤ ControllerAdapter
当前PROJECT15 + 后续RESERVED插槽

⑥ ControllerDiagnostics
公共诊断 + 通用扩展诊断槽
```

然后外围固定：

```text
V3.2通信安全框架
+
V4 candidate/commit
+
V5真实接管
+
BOARD15完整P/Q/Mode/Breaker/Fref
```

如果这部分设计好，未来我们再给工程师增加一套新的C算法时，就不会重新经历现在这种"大版本需求设计"。

---

所以你这个修正以后，最终策略比之前更合理：

> **现在不强求工程师交完整源码和编译环境；我们要求他把最终BOARD15程序设计成"主程序稳定、算法模块可插拔"的结构。当前项目只集成我们的15策略C模块，同时提前预留统一算法接口、扩展配置和扩展诊断能力。后续我们的新算法冻结后，再把C代码交给工程师按同一接口增加进去，避免重新修改通信、安全、点表、日志和主循环。**

这应该作为后面最终程序要求设计的一条核心原则。
