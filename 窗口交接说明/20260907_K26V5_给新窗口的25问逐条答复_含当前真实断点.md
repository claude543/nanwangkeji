

来判断。

因此严谨说法：

```text

```

是事实。

但：

```text
“完全因为 metadata”
```

不能只靠 SHA 自身证明。

我们有后续语义核对支持它仍处于 V4.8 控制合同，而不是 raw SHA 自己证明。

# 10. ESS1 OldPI shadow 在未来 reset/mode change 时再次作为 matchTarget 是否安全？

## 回答

这个问题值得保留为**尚未完全闭环验证的设计风险**。

当前设计：

```text
首次初始化
或 reset
或 EffectiveMode 变化
→ 用 old Current Regulator output
作为 matchTarget
```

目的：

```text
bumpless takeover
```

但是旧 Current Regulator：

```text
已经不再拥有实际执行权
仍用旧局部 AW
```

如果它长期 shadow 运行后状态偏离新 adapter，则 mode change 时重新对它 match，理论上可能把旧偏差重新注入。

### R5 是否明确覆盖“长时间新adapter运行→mode change→再次match old shadow”的整套真实序列？

当前已有 R5 汇总不能支持我们宣称“完整覆盖”。

因此不要写 PASS。

正确结论：

```text
首次/局部 match 逻辑通过候选测试
但完整长运行后的 repeated mode-change rematch
仍需正式运行证据
```

如果后续数据显示 shadow mismatch 长期扩大，正确升级方向是：

```text
shadow 跟踪新 adapter state
或
mode-change match 到真实可执行 PI share
```

而不是盲信 old PI。

# 11. Manager 新方向映射的 rawd/rawq 准确源和 Stage2～4语义是什么？

这一点现在可以比旧交接说得更准确。

```text
AA15_ISLAND_GFL_SUPPORT_MANAGER
```

顶层 input2：

```text

← Power Control Loop output1
```

Power Control Loop output1 是：

```text
[id_raw, iq_raw]
```

其中第二分量与：

```text
Qmeas - Qref
→ Q PI D1
```

直接对应。

进入 Manager 内部后：

```text
AA15_RAWI_DEMUX output1
→ AA15_FINAL_GFL_LIMIT_CORE input1
```

即 `rawd`。

而 q 侧不是直接把 raw Q PI 当 `rawq`。

```text
AA15_QBASE_TRACK_HOLD_CORE_V47
```

其 output1：

```text
→ AA15_FINAL_GFL_LIMIT_CORE input2
```

因此 Stage2～4 新 LimitCore 使用的 `rawq`：

> **是经过 V4.7 Q-authority track/hold 后的基础 q scalar，而不是最终 Support_q，也不是二次 qsec，也不是已经混入全部物理支撑的最终 q 轴。**

这正是 V4.9 能把：

```text
rawd → iP scalar
rawq → iR/base-Q scalar
```

再映射到：

```text
u / n
```

的关键合同。

单位：

```text
current-reference pu
```

与现有 `RawIpq / FinalIref / measured IdIq` 同一控制电流标幺体系。

这一条现在有实际模型连线支撑。

# 12. Manager 新脚本 `gp=gq=lam` 是不是取消旧独立 gP/gQ？

## 回答

在 **Final LimitCore 最终可行性缩放这一层**，是有意合并成：

```text
common base-vector scale = lam
gp = lam
gq = lam
```

原因：

V4.9 已不再把：

```text
physical d axis
physical q axis
```

直接等同：

```text
P axis
Q axis
```

基础电流已经变成：

```text
i_base = u*iP + n*iR
```

在最终硬电流圆里缩放整个 base vector 时，用一个 `lam` 才保持方向一致。

但这不等于：

```text
所有历史 GammaP / GammaQ 职责被删掉
```

上游：

```text
AA15_FINAL_GFL_STATE_CORE
```

仍保留：

```text
GammaQ
GammaP
slow-q
damping
UV relief
```

等职责。

LimitCore 的 `gp/gq` 现在更接近：

```text
final feasibility scale report
```

而不是旧意义下两个独立物理 d/q 轴 scale。

下游现有 diag：

```text
row33 gP
row34 gQ
```

因此 V4.9 analyzer 必须注明：

> 两行在最终 LimitCore 中会相等为 `lam`，不能继续按旧“独立 P/Q 限制器”解释。

# 13. `u/n` 的 RawVdq 来源、0.2 pu、双 UDIR 状态怎么理解？

## 回答

### RawVdq 来源

Manager input1：

```text
RawVdq
```

在实际控制器父图中来自 tag：

```text
VdVqs
```

是现有执行坐标下的 dq 电压向量。

Manager 内：

```text
AA15_RAWV_DEMUX
```

直接拆 vd/vq。

因此不是恢复五套 PLL。

### 它是不是足够滤波？

不能把它叫“开关瞬时 PWM 原始采样”。

它来自现有控制测量/执行链已有 dq 电压信号。

但当前证据也不支持把它包装成“专门为 V4.9 新设计的强滤波 phasor”。

严谨称：

```text
现有控制链使用的 dq voltage vector
```

### `vm >= 0.2`

V4.9 正式候选脚本里用了：

```text
vm >= 0.2
```

作为方向有效性基本门。

它不是行业保护定值，也不是由设备保护规范推导的最终 threshold。

它是：

```text
避免低幅值归一化/方向随机放大
```

的 first corrective build 工程阈值。

后续若要改，必须看：

```text
低压工况
方向噪声
恢复连续性
```

而不是随便扫。

### Manager / Finalizer 两套 UDIR 为什么不共享？

设计目的是：

```text
各子系统局部自包含
避免跨层反馈和代数耦合
```

它们用：

```text
同一个 RawVdq source
同样的有效判断
同样的 update law
```

正常情况下应保持一致。

但“两个独立状态一定逐拍 bit-exact 一致”还需要正式运行/编译验证。

长期更干净的架构确实可以考虑：

```text
单一 direction owner
→ 显式广播 u
```

但本轮不为了架构美化再新增跨层接口。

# 14. 中央 q-bias 的 releaseZero 删除了，但 Finalizer releaseZero 还在，对吗？

## 回答

对。

### 中央 q-bias state

```text
已有非零 qstate
只要 dqdes 反向
→ 固定 0.15/s 向零清空
```

这把：

```text
正常工作点微调
```

错误当成：

```text
状态失效
```

所以被删除。

### Local Finalizer qsec

如果本地已经施加：

```text
qsec_used > 0
```

新 target 变成：

```text
< 0
```

Finalizer 先：

```text
release to zero
```

再跨符号，目的是：

```text
避免 local reference 一拍反向跳变
```

这是本地 actuator command 的 bumpless sign reversal，不是中央工作点状态清空。

所以以后必须写：

```text
central ordinary releaseZero removed
≠
all releaseZero in V4.9 removed
```

# 15. Mod hard state 后 qsec 为什么不是立即归零？


```text
避免 Secondary current reference 突然跳变
```


```text
六台 current execution residual AW
```

它直接处理最终电压执行限制。

所以当前职责分层：

```text
current adapter AW = hard execution consistency
qsec release = bumpless supervisory command withdrawal
```

如果 V4.9 新数据证明：

```text
hard modulation 已发生
qsec release 明显拖慢退出
```

才有证据增加：

```text
emergency release branch
```

当前不能提前造。

# 16. 中央 qapplied 仍是 reference-applied，不是 actual current，对吗？

## 回答

对。

固定层级：

```text

→ local qsec reference applied
→ Final Iref
→ current controller / converter
→ measured Id/Iq
→ actual P/Q/V
```

中央：

```text

```

仍是五台：

```text
IqSecApplied
```

之和。

不是实测 physical q-current。

本轮有意没有把中央 qbias 再改成 actual-current-aware。

因为 first corrective build 先修：

```text
执行层自己必须知道最终 actuator saturation
```

如果之后数据显示：

```text
reference-applied qsec
与
measured actual response
长期系统性脱节
```

并且这会导致 central state 再 windup，才升级中央 AW。

# 18. Diagnostic23 是否落盘？现有 row 哪些语义变化？

# 20. Verifier R2 failure cleanup 是否不足？

## 回答

是，这个担忧合理。

成功路径有：

```text
term
恢复 AlgebraicLoopMsg
```

但旧 verifier 没有做到所有 assert failure 都由：

```text
onCleanup / try-finally equivalent
```

保证：

```text
退出 compiled state
恢复原 setting
```

这类不完整 cleanup 可能留下：

```text
compile state
Dirty
setting changed
```

虽然不必然每次发生。

后续 verifier 必须采用“compile ownership guard”：

```text
ownedCompile=true
onCleanup:
  if ownedCompile -> term
  restore AlgebraicLoopMsg
  never save
```

这个应该写进永久模板。

# 21. 为什么 Verifier 只 contains，不 hash 新函数正文？

## 回答

这是独立 verifier 的弱点。

`contains` 能检查：

```text
关键 marker 存在
```

不能证明：

```text
完整函数就是我们生成的那一版
```

正式生成器是 deterministic 的情况下，更合理：

```text
Patch 生成后
→ 记录 expected content SHA
→ Verifier 从 Stateflow 读正式正文
→ normalize line endings
→ exact SHA compare
```

同样 current adapter 应验证：

```text
CORE source hash
cfg constants
input source
output destination
packing topology
```

而不是只：

```text
block exists
out width [2 2 23]
```

后来的 matrix leakage 就说明：

```text
width-only verifier
```

不够。
