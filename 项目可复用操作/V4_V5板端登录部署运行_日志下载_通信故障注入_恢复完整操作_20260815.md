# 0. 先记住当前系统到底是什么

当前实际链路：

```text
Windows电脑
    │
    │ RT-LAB工程管理 / SSH
    ↓
RTServer / OP5700
管理IP：192.168.10.87
通信口eth1：192.168.1.100

    │ 192.168.1.x物理网络
    ↓
```

由于Windows不能直接访问板子的 `192.168.1.10:10022`，当前稳定登录方式是通过RTServer建立SSH本地端口转发：

```text
Windows 127.0.0.1:10023
        ↓
RTServer 192.168.10.87
        ↓
Board 192.168.1.10:10022
```

```text
RT-LAB / OP5700
40101~40116
      ↓ FC03
外部板
基础C AGC / 后续15策略
      ↓ FC16
40001~40012
      ↓
RT-LAB
      ↓
2PV + 2ESS + 2EV
```

当前V5-A已经证明：

```text
40001~40006
不是Shadow记录量

而是真正：
PV1 / PV2 / ESS1 / ESS2 / EV1 / EV2
```

# 6. 每次实验开始前必须检查iptables是否干净

这一步现在列为**强制步骤**。

在RTServer窗口1执行：

```bash
iptables -L INPUT -v -n --line-numbers
```

重点检查是否存在我们此前用于实验的：

```text
DROP ... source 192.168.1.10 ... dpt:1502
```

或者带：

```text
STRING match
```

的FC16规则。

## 为什么必须检查

此前实际出现过：

```text
iptables添加STRING规则时终端看起来卡住
↓
误以为规则没有生效
↓
实际上DROP规则已经安装
↓
累计丢弃1508个FC16数据包
↓
后续实验FC16持续timeout
```

因此：

> **任何iptables命令执行后，都必须重新 `iptables -L INPUT -v -n --line-numbers` 检查真实规则。**

绝不能只根据命令窗口是否返回判断成功或失败。

---

# 7. 绝对禁止直接flush整个iptables

不要执行：

```bash
iptables -F
```

也不要随意清空其他链。

原因：

```text
RTServer本身已有系统网络规则
并且SSH等服务依赖现有规则
```

我们的原则始终是：

```text
只增加自己明确知道的实验规则
只删除自己明确增加的实验规则
```

当前RTServer原有：

```text
ACCEPT tcp dpt:10022
```

等系统规则不要动。

# 20. MODEL_STATUS当前位定义

当前：

```text
bit0 RUNNING
bit1 MEAS_VALID
bit2 EXT_INTERFACE_READY
bit3 INTERNAL_FALLBACK_READY
bit4 MODEL_FAULT
```

基础可用判据：

```text
(status & 7) == 7
且
(status & 16) == 0
```

典型正常：

```text
MODEL_STATUS = 7
```

# 21. 为什么不能只看40010

模型侧真正的外部命令有效逻辑是：

```text
EXTERNAL_COMMAND_VALID
=
(40010 == 1)
AND
BOARD_HB_OK
```

因为：

```text
板端进程突然死亡
↓
40010可能仍然残留为1
↓
但BOARD_HEARTBEAT停止变化
↓
BOARD_HB_OK在超时后变0
↓
外部命令被撤权
```

因此后续所有板端死亡/通信中断实验都必须同时记录：

```text
40010
BOARD_HEARTBEAT
BOARD_HB_OK
EXTERNAL_COMMAND_VALID
```

# 22. V5-A失联后的当前物理策略

V5-A当前模型：

```text
板端有效
→ FINAL_CMD = BOARD_CMD

板端失效
→ FINAL_CMD = LAST_APPLIED
```

即：

```text
HOLD最后真实执行命令
```

而不是：

```text
立即切回本地MATLAB AGC
```

原因：

```text
本地AGC内部历史
可能已经和板端AGC内部历史不同

失联瞬间强行切回
可能引起更大的命令突跳
```

这也是后续论文Strategy7要解决的恢复管理问题之一。

# 26. RTServer上的tcpdump基本用法

抓取板子与OP5700之间的Modbus：

```bash
tcpdump -i eth1 -nn -s 0 -X -c 16 'host 192.168.1.10 and tcp port 1502'
```

参数含义：

```text
-i eth1
抓通信口

-nn
不做DNS和端口名解析

-s 0
抓完整包

-X
同时打印HEX和ASCII

-c 16
抓16个包后自动停止
```

如果需要更多：

```bash
tcpdump -i eth1 -nn -s 0 -X -c 50 'host 192.168.1.10 and tcp port 1502'
```

# 27. tcpdump最容易产生的误解

必须记住：

> `tcpdump` 能看到某个包到达eth1，不等于这个包最后已经被Modbus应用程序正常处理。

例如：

```text
板子FC16 TCP包
↓
到达eth1
↓
tcpdump已经能抓到
↓
iptables INPUT DROP
↓
Modbus应用程序根本收不到
```

因此在iptables故障实验中出现：

```text
tcpdump能看到FC16
但板端FC16 timeout
```

并不矛盾。

# 31. 恢复完整Modbus通信

不要flush。

优先使用**和添加时完全相同的规则规格**删除：

```bash
iptables -D INPUT -p tcp -s 192.168.1.10 --dport 1502 -j DROP
```

# 38. FC16定向DROP不能被误解成“完美单周期FC16故障”

这一点非常重要。

iptables工作在TCP层。

当我们丢掉一个FC16 TCP数据段：

```text
后续TCP字节序列
可能因为Sequence Gap无法继续被应用层正常消费
```

因此实际可能出现：

```text
初期：
FC03还能成功
FC16 timeout

随后：
TCP流阻塞
后续FC03也异常
重新连接
```

所以该方法适合：

```text
工程上证明可以定向拦截FC16
观察写失败和安全退化行为
```

但不适合作为论文或最终验收中的：

```text
“只失败一次FC16
下一拍其他消息立即完全正常”
```

这种精确语义。

如果需要**精确单次FC16写失败 + 保持TCP序列完整 + 同一candidate重试**，最好的办法是：

```text
板端程序内部增加fault injection
```

由工程师在应用层控制。

# 49. 论文相关：通信实验在论文中应该怎样定位

论文不再把：

```text
固定通信延迟
随机丢包
HOLD
resume
```

作为主要创新。

通信的角色是：

> **制造“控制器认知状态、成功提交状态和设备真实执行状态不再一致”的工程条件。**

因此后续核心通信Case更建议：

```text
正常
↓
通信中断
↓
HOLD期间plant/资源状态发生变化
↓
通信恢复
↓
Baseline直接恢复
vs
Proposed Reconstruction + Recovery
```

而不是把大量时间用于枚举：

```text
10% loss
20% loss
30% loss
500 ms delay
1 s delay
2 s delay
```

延迟/随机丢包如果需要，放补充鲁棒性即可。

# 50. 论文相关：单DER执行异常不通过iptables制造

单设备真实执行异常最终应在RT-LAB模型内部制造：

```text
u_commit_ESS1
↓
Execution Fault Injector
↓
u_applied_ESS1 = gain × u_commit_ESS1
↓
ESS1
↓
Pmeas_ESS1
```

例如：

```text
fault gain = 0.3
```

只影响ESS1。

其他5台：

```text
u_applied = u_commit
```

这样可以形成：

```text
通信完全正常
FC03正常
FC16正常
CMD_SEQ正常
但单台设备执行失配
```

这才真正验证论文Strategy2。
