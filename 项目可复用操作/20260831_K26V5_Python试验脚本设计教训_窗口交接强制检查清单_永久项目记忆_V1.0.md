# 1. R2 多次返工到底教会了什么

## 1.1 R2 V1.0：F25 锁存太早

错误时序：

```text
S7/AGC仍持续改变六台Pcmd
↓
F25提前PREPARE / PREPARED_HOLD
↓
F25正确地冻结了当时pre-bias
↓
上层dispatch继续移动
↓
真实IOUT工作点变化
↓
Host反而责怪F25“没有重新回到PCC≈0”
```

### 错误本质

```text
local quasi-steady
≠
system final operating point
```

20 ms 本地看起来稳定，不代表上层调度已经停止。

### 永久规则

> F25 PREPARE 必须属于 **final planned-islanding preparation phase**，只能在上层 dispatch 已经冻结后 Late-Bind。

正确顺序：

```text
P/Q COMMIT
→ S7 OFF
→ AGC OFF
→ frozen strong-grid point
→ F25 PREPARE
```

---

## 1.2 R2 V1.1：把异步 Host 样本当成 100 μs 模型边沿真值

错误判断：

```text
Host在HOLD_REQ前约2 ms读一次Pcmd
↓
模型在真正HOLD_REQ上升沿捕获当前Pcmd
↓
AGC在最后2 ms正常移动了约2e-4 pu
↓
Host要求二者差 <1e-6
↓
正常COMMIT被判FAIL
```

### 错误本质

> Host 采样不是模型 100 μs 边沿真值。

### 永久规则

如果模型是：

```text
rising edge
→ latch current state
```

那么：

> **边沿后模型锁存值才是唯一权威值。**

COMMIT 前允许 live dispatch 正常运动；COMMIT 后再要求严格常值。

严禁：

```text
pre-edge Host sample == model edge-latched state
```

这种没有物理依据的严格等式。

---

## 1.3 R2 V1.2：把“工况等价指标”误写成“安全硬门”

F25 Late-Bind 后：

```text
PCC:
约(-1 kW,+3 kvar)
→
约(-2 kW,+6 kvar)
```

六台命令完全冻结、F24 READY、电压/频率健康。

但是脚本仍然沿用：

```text
|Ppcc| <= 5 kW
|Qpcc| <= 5 kvar
```

作为硬回退条件。

于是 Q 稍微跨过 5 kvar 就被 Reset。

### 错误本质

以下三类指标混在了一起：

```text
A. 实验有效性/安全硬门
B. 工况等价性/质量指标
C. 最终物理结果指标
```

### 永久规则

三者必须完全分层。

#### A. 硬门

只有失败后“实验本身不再具有解释意义”的条件：

```text
错误拓扑
错误mode
J1状态错误
P/Q没有真正冻结
S7/AGC没有退出
F24/F25没有到对应正式状态
NaN / Inf
```

#### B. 等价性诊断

例如：

```text
PCC是不是仍接近0
是否与历史V25A5差2kW/3kvar
```

正常情况下：

```text
记录、比较、WARNING
```

不能随意 Reset。

#### C. 结果指标

例如：

```text
J1后V下降
频率偏移
某个模态增长
F25 candidate迟迟不成熟
```

这些本来就是实验要观察的“结果”，更不能为了“安全”把证据提前掐掉。

---

## 1.4 R2 V1.3：隐藏的状态语义跨阶段复用

Stage 8B：

```text
F25 state2 = PREPARED_HOLD
```

helper：

```text
r2_frozen_f25_point_ok()
```

内部隐藏：

```text
F25_state == 2
```

Stage 9 发：

```text
EDGE_ARM_REQ
```

F25 正常进入：

```text
state3 = EDGE_ARMED
```

但 Python 又调用同一个 state2 helper：

```text
state3
→ state2-only predicate=False
→ Host误判工作点丢失
→ Reset
```

### 错误本质

> helper 名字看起来是“work-point check”，实际隐藏了阶段特定 state==2 语义。

### 永久规则

**每个状态阶段必须有独立 predicate。**

例如：

```text
Stage8B:
prepared_point_ok()
只接受 state2

Stage9:
armed_point_ok()
只接受 state3

Stage10:
fast_edge_ok()
只接受 state4 / physical edge contract
```

严禁未经审计把一个 helper 跨阶段复用。

# 2. 每次写新 Python 前必须先做“阶段状态表”

脚本编码前先写表，不写表不开始编码。

模板：

| Phase | 入口条件 | 本阶段模型状态 | 允许动作 | 退出条件 | 硬回退 | 只记录 |
|---|---|---|---|---|---|---|
| P0 | PAUSED | GFL/J1 closed | init params | baseline healthy | topology wrong | small PCC offset |
| P1 | baseline | live AGC | prebalance | capture region | numeric fail | command movement |
| P2 | capture point | commit | HOLD | hold ack | hold missing | value differs from prior Host |
| ... | ... | ... | ... | ... | ... | ... |

尤其状态机必须明确：

```text
F25:
0 BYPASS
1 PREPARE_ESTIMATE
2 PREPARED_HOLD
3 EDGE_ARMED
4 FAST_TRANSFER
5 SMOOTH_COMMIT
6 ISLAND_HOLD
7 FALLBACK_HOLD
```

每一阶段必须明确：

```text
当前允许哪些state？
下一步期望转成哪个state？
哪些state变化是“正常转换”而不是故障？
```

# 3. 所有 raise / Reset 路径必须做“逐条证明目标审计”

在把脚本给用户之前，必须列出：

```text
脚本中每一个 raise / fail-safe / Reset
```

并逐条回答：

1. 它发生在哪个 Phase？
2. 它证明实验已经失去解释意义吗？
3. 如果不 Reset，会不会真的破坏设备/数值安全？
4. 它是不是只是一个结果指标？
5. 它是不是用旧阶段阈值检查新阶段？
6. 它是不是依赖异步 Host 样本？
7. 它会不会把我们真正要观察的失败过程提前掐断？

如果不能回答：

> “该条件失败后，继续运行将使实验合同本身无效或出现数值不可用。”

就不应做硬 Reset。

# 4. J1 前与 J1 后的监督哲学必须不同

## J1 前

目标是：

> 保证进入真实切岛时的初始工况具有因果解释意义。

所以允许较严格硬门：

```text
拓扑
mode
P/Q冻结
S7/AGC状态
F24 READY
F25 PREPARED / EDGE_ARMED
旧控制路径OFF
数值finite
```

---

## J1 后

目标是：

> 收集物理失败的完整证据。

因此采用：

# Evidence-First（证据优先）

只要仍然是有限数值：

```text
低压
高压
频率偏移
F25 timeout
candidate失败
F24/F25有限状态异常
控制量偏差
```

原则上：

```text
WARNING
+
继续落盘
```

真正立即停止只保留：

```text
NaN
Inf
API / runtime不可用
明显非有限数值灾难
```

避免再次出现：

> 关键失稳刚出现，Python为了“安全”把MAT最有价值的尾部Reset掉。

# 5. 物理事件的时间真值优先级

以后统一：

```text
模型本地100 μs状态 / event
>
Group29/30高速记录
>
Host 0.2/1/10/100 ms轮询
```

因此：

- J1 falling edge 用 `J1_applied` + F22 `event_pulse`；
- F25边沿动作看模型 state / event；
- P/Q COMMIT看模型 latch 后输出；
- F24 HOLD看模型 state；
- 不允许用 Host “大约+5ms”当控制算法的最终触发机制。

Host只负责：

```text
监督
发上层arm/commit request
记录
```

不负责替代本地物理边沿。

# 6. 不允许把历史阈值机械搬到新阶段

例如：

```text
PCC ±5kW / ±5kvar
```

在某一历史阶段可能是：

> 找COMMIT capture point的辅助条件。

它绝不自动等于：

> F25接管后也必须永远满足的安全边界。

任何阈值进入新脚本前必须回答：

```text
这个阈值在当前Phase的物理意义是什么？
超出以后为什么实验就无效？
```

没有物理理由就只能做诊断。

---

# 7. Controller timeout 也不是“普通脚本参数”

本轮最新新增的重大教训：

```text
F25_FAST_MAX_N_SAMPLES = 1000 = 100 ms
```

在 R1 单ESS1下足够：

```text
FAST
→ candidate
→ smooth commit
→ state6
```

但这不代表：

> 六机拓扑也一定100 ms内完成责任重分布。

R2六机下：

```text
+90 ms raw target仍剧烈移动
+100.2 ms
F25因为固定MAX_N进入state7 fallback
```

而明显电压低于9kV发生在：

```text
约+175 ms
```

所以：

> **控制器时间上限本身也是一个待验证的拓扑相关设计假设。**

以后任何：

```text
timeout
ready_n
stable_windows
hold_n
max duration
```

从单机推广到六机前，必须明确它是否已经在目标拓扑验证过。

# 10. 正交实验的长期纪律

任何根因实验尽量：

```text
一次只改变一个真正因果变量
```

如果同时改变：

- topology；
- F25 timeout；
- F22 support；
- Voltage PI；
- GFL PLL；

那么即使成功也无法知道是谁起作用。

尤其当前后续必须防止：

```text
为了“更容易稳定”
同时把多个support全打开
```

这会毁掉根因闭环。

```text

→ CLOSED / GateA
```

# 12. 当前尚未关闭的根因必须在交接中明确写成“竞争假设”

截至最新R2 V1.4，完整六机剩余问题不能再粗暴写成：

```text
就是五GFL aggregate dynamic
```

因为还有一个重要未排除项：

```text
H1:
F25固定100 ms FAST horizon过短
→ 六机责任重分布尚未成熟就进入fallback

H2:
即使F25继续正确FAST，
五GFL聚合动态与ESS1 GFM输出阻抗仍本质不稳定
```

以后新窗口必须先知道这两个竞争假设。

在H1被排除之前：

> 不允许直接去调PLL / Voltage PI / output impedance。

# 15. 最终冻结的一句话

> **以后写K26_V5实时试验Python，第一目标不是“尽可能多加安全判断”，而是“只在实验合同真的失效时阻止试验，其余物理异常必须被完整记录”。脚本必须按模型状态机的真实阶段语义设计，而不是靠Host时间、历史阈值和泛化helper拼起来。每个timeout、capture band、ready条件和state predicate都必须说明在当前拓扑下的物理意义。这样才能避免脚本本身成为新的干扰源和返工源。**
