# OP5700 与控制板直连网口指示灯不亮｜eth1 DOWN 排查与恢复

## 0. 一句话结论

本次“控制板与 OP5700（实时仿真器）之间网线感应灯突然不亮”的直接原因已经定位：

> **OP5700 的 `eth1（以太网接口1）`在重启后处于行政关闭状态，没有被系统自动拉起。**

执行：

```bash
ip link set eth1 up
```

后立即恢复为：

```text
UP, LOWER_UP
Speed: 1000Mb/s
Duplex: Full
Link detected: yes
```

这证明：

- 控制板网口正常；
- OP5700 对应物理网口正常；
- 网线正常；
- 两端千兆以太网协商正常；
- 此前指示灯不亮不是 V4.9 控制模型、RT-LAB Build、Modbus TCP 或 License 本身造成的。

但当前仍有一个后续项：

> **`eth1` 虽然已经恢复物理链路，但原来的 IPv4 地址 `192.168.1.100` 尚未重新出现。**

所以严格地说：

```text
物理链路问题：已解决
板子 ↔ OP5700 完整 IP / Modbus 通信：仍需继续恢复和验证
```

板端最终访问：

是 OP5700 / RTServer 的管理口，用于 Windows 主机登录 RTServer，不要和控制板通信口混淆。

# 2. 本次故障现象

在 OP5700 重启后出现：

```text
控制板 ↔ OP5700 直连网线指示灯不亮
```

此前该灯正常亮。

由于网口灯属于物理以太网链路层现象，因此第一原则是：

> **先检查网口和链路状态，不先修改 RT-LAB 模型、V4.9 控制逻辑、Modbus 参数或许可证。**

---

# 3. 第一步：检查 `eth1` 基本状态

在 RTServer 中执行：

```bash
cat /sys/class/net/eth1/carrier
cat /sys/class/net/eth1/operstate
```

本次实际结果：

```text
cat: /sys/class/net/eth1/carrier: Invalid argument
down
```

其中最重要的是：

```text
operstate = down
```

这说明 `eth1` 当前没有处于工作状态。

但这时还不能直接说：

```text
网线坏了
```

因为还要区分：

```text
A. 网口被操作系统行政关闭
B. 网口已开启，但没有检测到物理载波
```

---

# 4. 第二步：同时看接口标志、IP 和物理协商

执行：

```bash
ip link show eth1
ip addr show eth1
ethtool eth1
```

本次实际结果：

```text
3: eth1: <BROADCAST,MULTICAST> mtu 1500 qdisc noop qlen 1000
    link/ether ac:1f:6b:60:f7:5b brd ff:ff:ff:ff:ff:ff
```

注意这里没有：

```text
UP
LOWER_UP
```

同时：

```bash
ip addr show eth1
```

没有看到原来的：

```text
inet 192.168.1.100/24
```

`ethtool eth1` 显示：

```text
Speed: Unknown! (65535)
Duplex: Unknown! (255)
Link detected: no
```

## 判断

这组信息非常关键：

```text
eth1 没有 UP
+
没有 LOWER_UP
+
没有 IPv4 地址
+
Link detected: no
```

其中最先应该处理的是：

> **`eth1` 本身没有被系统启用。**

因此这时不能把 `Link detected: no` 直接解释成物理网线故障。

---

# 5. 第三步：先把接口行政性启用

执行：

```bash
ip link set eth1 up
```

命令本身无输出属于正常。

随后立即重新检查：

```bash
ip link show eth1
ethtool eth1 | grep -E 'Speed|Duplex|Link detected'
ip addr show eth1
```

本次实际结果：

```text
3: eth1: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc pfifo_fast qlen 1000
```

并且：

```text
Speed: 1000Mb/s
Duplex: Full
Link detected: yes
```

---

# 6. 这一步证明了什么

`UP` 和 `LOWER_UP` 含义不同：

```text
UP
= 操作系统已经把该接口行政性启用

LOWER_UP
= 网卡底层已经检测到真实物理链路
```

再结合：

```text
Speed: 1000Mb/s
Duplex: Full
Link detected: yes
```

可以确认：

```text
OP5700 网口
        │
        │ 1000 Mb/s Full Duplex
        │
控制板网口
```

物理层已经成功建立。

因此本次可以排除：

```text
网线完全断路
控制板网口完全损坏
OP5700 对应 PHY 完全损坏
两端无法完成自动协商
```

并且原本不亮的网口灯理论上此时也应恢复。

---

# 7. 当前最准确的根因口径

不要写成：

```text
已经证明 OP5700 重启一定会关闭 eth1
```

目前证据不能支持这么强的结论。

最准确表述是：

> **本次 OP5700 重启后，RTServer 中 `eth1` 没有处于 UP 状态，且 IPv4 地址也没有恢复；因此控制板与 OP5700 的物理以太网链路没有建立。手动执行 `ip link set eth1 up` 后，链路立即恢复为 `UP,LOWER_UP`、1000 Mb/s、全双工、Link detected=yes，证明此次指示灯不亮的直接原因是 `eth1` 未被启用，而不是网线或两端物理接口故障。**

至于为什么重启后没有自动恢复：

```text
启动阶段网络配置未加载
网络服务未恢复该接口
OPAL-RT 当前启动环境未自动拉起该通信口
```

目前都只能视为可能机制。

在没有继续审计启动脚本 / 网络配置前，不把其中任何一条写成已经证实的根因。


# 20. 为什么当时检查 1502 没有输出

恢复网络后曾执行：

```bash
ss -lntp | grep ':1502'
```

当时没有输出。

之后确认此时 RT-LAB（实时仿真平台）模型正在：

```text
Load（加载）
```

因此这个现象不能解释为：

```text
Modbus TCP 1502 故障
```

原因是 RT-LAB 在 Load 过程中正在重新部署和初始化：

```text
实时任务
I/O 接口
OpComm / 通信相关对象
Modbus Slave 服务
```

1502 监听可能尚未建立，或处于重新初始化阶段。

所以正确判断顺序应为：

```text
Load 尚未结束
→ 1502 暂无 LISTEN
→ 暂不判故障

Load 完成 / Execute
→ 再检查 1502
```

这次事件最终没有继续暴露 Modbus TCP 层异常，因此：

> **不能把“Load 阶段 1502 暂时没有输出”记录成新的故障点。**
